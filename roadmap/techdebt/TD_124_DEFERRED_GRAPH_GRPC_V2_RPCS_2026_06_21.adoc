== Context

PR #126/#130 migrated the SDK graph surface to the v2-native
`proto/proximadb/v2/graph.proto` `ProximaGraphService` with 14 core RPCs
(Create/Get/Update/Delete Node+Edge, QueryNodes/QueryEdges, GetNeighbors,
TraverseGraph, ShortestPath, GetGraphStats). The deprecated
`proximadb.v1.GraphService` (~30 RPCs) is flag-gated OFF by default
(`enable_grpc_v1_compat`). The analytic/batch/constraint/streaming RPCs and the
declarative `ExecuteQuery` were left off the v2 surface as "deferred — TD-124".

== Work done (this TD)

Added to v2 `ProximaGraphService`, each delegating to the same backing
`GraphOperationsService` the existing 14 handlers use (v2↔v1-internal mapping in
the `conv` helpers, `effective_graph_id` tenant namespacing preserved):

* `StreamTraverse` (server-streaming) — backing engine materialises the
  traversal eagerly; one terminal chunk (`done = true`), mirroring v1. The
  streamed wire shape (`GraphTraversalChunk`) leaves room for incremental
  frontiers without a contract break.
* `GetConnectedComponents` → `connected_components` (weak components as node-id
  sets).
* `HasCycle` → `has_cycle`.
* `AddUniqueConstraint` / `RemoveUniqueConstraint` → `add_/remove_unique_constraint`
  (success/error reported in-band, matching v1, so clients can branch on it).
* `BatchCreateNodes` / `BatchCreateEdges` → `batch_create_nodes` /
  `batch_create_edges`.
* `ExecuteQuery` (Cypher) — routes through the shared unified-query facade
  (`QueryFacadeAdapter::graph_query`), the same backing the v1 adapter uses when
  a `query_adapter` is configured (it is, in production). This is a *genuine but
  intentionally narrow* engine: the openCypher parser feeds
  `lower_supported_graph_query_expr`, which supports single-node patterns and
  linear traversal chains with equality property constraints, executed against
  the live `GraphOperationsService`. When no adapter is wired (e.g. the
  standalone-graph test build), it returns `unimplemented`, mirroring v1.

All RPCs use v2-native (`Graph*`-prefixed) message names; no v1 type appears on
the v2 wire. Python SDK methods added in
`clients/python/src/proximadb_sdk/protocols/grpc_sync.py` against
`v2_graph_pb2_grpc.ProximaGraphServiceStub`.

== Residual deferrals (with reasons)

* `ExecuteHybridQuery` — still v1-only. It depends on the *full* vector+graph
  `UnifiedHandlers` (it runs a vector search then a graph traversal), and its v1
  `HybridSearchRequest`/`HybridSearchResponse` reference the large v1 vector
  message graph (`VectorSearchRequest`, `SearchVectorRecord`, …) that has no
  clean v2-native equivalent and overlaps the vector v2 surface. Porting it is a
  separate, larger effort (cross-modality fusion API), not a mechanical
  graph-only port. The backing logic exists
  (`UnifiedHandlers::execute_hybrid_query`); only the v2 wire surface is missing.
* `CreateGraphWithEngine`, `GetPulsarStats` — *not implemented anywhere* on the
  live tonic path (PULSAR/QUASAR engines are retired). Nothing to delegate to;
  leaving them off v2 is correct.
* `GREMLIN` declarative language — reserved on the v2 `GraphQueryLanguage` enum
  but unbacked; `ExecuteQuery` rejects it with `unimplemented`.

== Notes

* Cypher coverage is the supported subset only; the lowering layer rejects
  unsupported clauses (OPTIONAL MATCH, variable-length paths, explicit path
  bindings, disconnected matches, non-equality property maps) with a clear
  error. Widening the subset is out of scope here.
* `ExecuteGraphQueryRow` surfaces each result item as a single `data` string
  column (matching the v1 adapter), with the richer `QueryValue` typing reserved
  on the v2 contract for a future engine expansion.
