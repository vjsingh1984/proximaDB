= TD-122 Persist detailed index/quantization config for collection GET round-trip
:toc:
:toclevels: 3
:sectnums:

Status: Open / proposed +
Date: 2026-06-21 +
Owner: Collection service / catalog

== Context

The v2 gRPC `CreateCollection` now accepts v2-native index/quantization config
(`V2IndexSpec` with `V2HnswConfig`/`V2IvfConfig`, `V2QuantizationConfig`) and maps it to the
v1 `IndexConfig`/`HnswConfig`/`IvfConfig`/`QuantizationConfig` the collection service
consumes — the same `handle_collection_operation_for_tenant` path REST/v1 use. Verified e2e:
the `CreateCollection` *response* carries the full config (e.g. `hnsw{m=24, ef_construction=150}`,
`is_primary=true`, quantization `enabled=true, strategy=aggressive`), confirming the config
reaches the collection service.

== Problem (grounded)

`GetCollection`/`ListCollections` do **not** echo the detailed index/quant config back: a
read-after-create returns `hnsw.m=0`, `is_primary=false`, `quantization.enabled=false`. The
loss is in the **catalog persistence layer** — the stored collection metadata round-tripped by
GET does not retain per-index HNSW/IVF parameters or the quantization config (only the
coarse shape: name/dimension/distance/storage + a normalized index entry). This is
pre-existing and surface-agnostic (REST/v1 GET have the same gap); it is *not* introduced by
the v2 enrichment, and the create-path plumbing is functional regardless.

== Work

. Extend the collection catalog/metadata schema (and the create persistence path) to retain
  per-index HNSW/IVF parameters, `is_primary`, and the quantization config.
. Ensure the collection-store read path repopulates them so `collection_to_v2`
  (`src/network/grpc/v2/record_service.rs`) + the REST `get_collection_v2` echo what was set.
. Add a read-after-create round-trip assertion (gRPC + REST) to lock it in.

== Notes

* The v2 reverse mapping (`collection_to_v2`) is already in place and correct — it will echo
  the full config automatically once the catalog persists it; no v2-surface change needed.
* Until then, the v2 create-path enrichment configures the index/quant functionally (the
  service receives it), but GET reflects only the persisted (coarse) shape.
