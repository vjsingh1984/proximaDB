== Context

The client surface is hand-maintained three times (axum REST handlers, the hand-edited
`docs/openapi/proximadb-openapi.yaml`, and N hand-written SDKs, linked only by `openapi_contract`
tests), and the per-language packages are kitchen sinks (Python `proximadb_sdk` is ~86k `src/` LOC,
of which the actual wire client is ~19k; the rest is chunking/embeddings/integrations). Full
analysis + rationale: `docs/12-design/SDK_MODULARIZATION_AND_SPEC_DRIVEN_GENERATION_2026_06_21.adoc`.

Goal: the wire client becomes *generated from a single source of truth per shape* (OpenAPI for
REST, proto for gRPC) plus a thin hand-written ergonomic facade; the value-add libraries
(chunking, embeddings, integrations) move into separate, opt-in packages.

[NOTE]
====
*Phase 1 shipped (2026-06-21).* `utoipa` (5.x, `axum_extras`/`preserve_order`/`yaml`) is wired into
the root `proximadb` crate. The published spec is now generated, not hand-edited.

*Annotated in code* (`#[utoipa::path]` + `#[derive(ToSchema)]` on the live v2 handlers in
`src/network/rest/v2/`): the core v2 surface — collection lifecycle
(`createCollection`/`listCollections`/`getCollection`/`deleteCollection`), schema
(`getCollectionSchema`/`updateCollectionSchema`), records
(`insertRecords`/`scanRecords`/`getRecord`/`deleteRecord`), `searchRecords`, and the query facade
(`executeQuery`/`explainQuery`) — 13 operations and their request/response DTOs.

*Generator + drift gate.* `src/network/rest/openapi.rs` aggregates the annotated paths into an
`ApiDoc` (`OpenApi` derive), folds in a checked-in supplement fragment
(`docs/openapi/_supplement.yaml`), and renders canonical YAML. The integration test
`tests/openapi_spec_gen.rs` is both the generator (`UPDATE_OPENAPI_SPEC=1 cargo test -p proximadb
--test openapi_spec_gen` writes `docs/openapi/proximadb-openapi.yaml`) and the gate (default run
fails on drift). CI: the `openapi-spec-drift` job in `.github/workflows/ci.yml` regenerates and
`git diff --exit-code`s the spec (mirrors the `proto-compat` generated-artifact pattern); also wired
as `make verify-openapi-spec`.

*Not yet annotated (carried verbatim by the supplement; tracked for a later increment):* `/health*`
and `/api/v2/_meta/capabilities` (handlers return dynamic `serde_json::Value` — no concrete DTO),
the graph surface (`/api/v2/graphs/*` — handlers + private request DTOs live in the `proximadb-api`
crate), and the free-form `hybrid` / `document-collections` / `observability` passthrough endpoints.
Keeping these in the supplement ensures the published spec does not regress the operations the
per-SDK `openapi_contract` gates depend on (notably graphs + health probes). The drift gate covers
the *merged* result, so neither the generated half nor the supplement can silently diverge. Closing
the residual = annotate those handlers (and lift the graph DTOs to public/`ToSchema` in
`proximadb-api`) and shrink the supplement toward empty.

[NOTE]
====
*Phase 2 pilot shipped (2026-06-21) — Go, `oapi-codegen` v2.4.1.* The Go REST SDK's wire
plumbing is now GENERATED from `docs/openapi/proximadb-openapi.yaml`, behind the existing thin
hand-written facade. The public Go SDK API (`proximadb` package, `Client` interface,
`NewClient`) is unchanged, so existing users + tests keep working.

*Tool + pipeline.* `oapi-codegen` v2.4.1 (the standard mature Go OpenAPI generator), pinned in
its own isolated module `clients/go/codegen/go.mod` (`tools.go` build-tagged `tools`) so the
generator's heavy dependency tree — kin-openapi, speakeasy, etc. — stays *out* of the SDK
module's closure: the SDK module only gains `github.com/oapi-codegen/runtime v1.4.2`. Because the
published spec is OpenAPI *3.1* (which oapi-codegen / kin-openapi do not yet support —
https://github.com/oapi-codegen/oapi-codegen/issues/373), the generation step first down-converts
3.1 → 3.0.3 into a *temporary* file (`clients/go/codegen/openapi_31_to_30.py`: rewrites
`type: [T, "null"]` → `type: T` + `nullable: true`, and collapses the 3.1 optional-`$ref` idiom
`oneOf: [{type: null}, {$ref}]`). The source spec is never edited (it is generated + drift-gated
by Phase 1); the down-conversion is a build-time adapter only. The generator emits the raw
`Client` (returns `*http.Response`); a `response-type-suffix` avoids a name collision between
component schemas and the unused `ClientWithResponses` wrappers.

*Generated vs. hand-written split.* All 15 SDK v2 REST operations the contract test covers route
through the generated client: `createCollection`, `listCollections`, `getCollection`,
`deleteCollection`, `getCollectionSchema`, `updateCollectionSchema`, `insertRecords` (+ upsert),
`getRecord`, `deleteRecord`, `searchRecords`, `executeQuery`, `explainQuery`, `getHealth`,
`getLiveness`, `getReadiness`. The generated layer owns URL/path building, query-param + body
JSON marshaling, path-param escaping, and the Content-Type header. The hand-written facade
(`clients/go/proximadb/internal/rest/adapter.go`) owns the value-add the generator does not
produce: connection setup (HTTP pooling, TLS, timeouts), bearer auth (via `RequestEditorFn`),
response decoding + HTTP-status→`AdapterError` mapping, the per-ID `Get`/`Delete` fan-out (the
spec exposes only single-record reads), and the stable public Go model structs that the SDK
facade + contract test depend on. The gRPC transport (`internal/grpc`) is unchanged — out of
scope for this REST pilot.

*LOC delta.* `internal/rest/adapter.go` was 814 hand-written LOC, of which the wire mechanics —
the `doRequest` HTTP loop, per-operation `fmt.Sprintf` URL strings, `url.PathEscape` calls, and
inline request marshaling across 15 operations — were the maintenance burden. Those mechanics are
now delegated to the ~7,700-LOC GENERATED `internal/genrest/genrest.gen.go` (regenerated by `make
gen-go-sdk`, never hand-touched). The file is now 913 LOC, but its character changed: it is
*facade + model mapping* only (connection setup, auth editors, response decode, error mapping, the
`Get`/`Delete` fan-out, and the public model structs + their `<->` generated-type mappers). It
slightly grew because the explicit public→generated field mappers replace what was previously
struct-tag-driven marshaling — a deliberate trade: the wire contract (paths/verbs/body shapes) is
no longer hand-maintained and cannot drift from the spec, at the cost of a small amount of
explicit, reviewable mapping code. Net: ~the transport half of a 5k-LOC network SDK is now
spec-generated.

*`make gen-go-sdk` + drift gate.* `make gen-go-sdk` runs `clients/go/codegen/gen.sh`
(down-convert → `go run oapi-codegen` from the pinned codegen module → `gofmt`), mirroring the
`verify-openapi-spec` / proto-sync target style. The new CI job `go-sdk-codegen-drift` (modeled
on `openapi-spec-drift`) sets up Go 1.24 + Python, runs `make gen-go-sdk`, and
`git diff --exit-code`s `clients/go/proximadb/internal/genrest/` — so the generated client cannot
silently diverge from the published spec. Triggered on `go_sdk` or `openapi_spec` changes. The
existing `go-lint` + `sdk-contract-gates` Go pins were bumped 1.21 → 1.24 (the SDK module is
`go 1.24.0` and the facade now uses a generic `ptr[T]` helper).

*Parity.* The Go `openapi_contract` test (16 cases incl. `AllV2OperationsCovered`) + the SDK's
`client_test.go` / `middleware_test.go` all pass against the regenerated transport
(`go test ./...` green). A live e2e smoke (`TestLiveSmokeE2E`, gated on `PROXIMADB_SMOKE_URL`)
exercises collection create/list/get/delete + a record insert/get round-trip through the re-based
public SDK against a running server.

*Phase-1 annotation follow-ups (noted, not fixed here — spec is frozen this PR):* the SDK calls a
few operations the spec covers only via inline (un-`$ref`'d) schemas or the supplement (health
probes); these generate fine. No SDK operation was found missing from the spec. If a future SDK
method needs an operation the spec lacks, annotate the handler (Phase-1 `#[utoipa::path]`) rather
than hand-editing the yaml.

== Scope / non-goals

* The `*-embedded` SDKs (maturin/FFI in-process) are NOT spec-generated — they stay hand-written.
* pgwire (SQL) is not an SDK we generate — clients use a standard PostgreSQL driver.
* This does not change wire behavior; it changes how the client code is produced and packaged.

== Acceptance

* `proximadb-openapi.yaml` is generated from the handlers with a CI drift gate (no hand edits).
* At least one network SDK's transport + models are generated, behind a thin ergonomic facade,
  passing the existing contract tests.
* The Python core install is lightweight (no tree-sitter/onnx/langchain in the default dependency
  set); chunking/embeddings/integrations are separate installable packages/extras.
