= TD-120 pg_catalog Completeness for ORM/Driver Compatibility

== Context

The design doc `docs/12-design/PROXIMADB_AS_LAKEHOUSE_NATIVE_PG_ENGINE_2026_06_17.md` §0.7/8 flags
`pg_catalog` completeness as the #1 tax on "Postgres-wire compatible" engines: ORMs/drivers run heavy
catalog introspection, and incomplete catalogs break them (Materialize/RisingWave/QuestDB all hit
this). Since ProximaDB is committed to the custom-engine-over-pgwire path, this tax must be paid
deliberately.

== Current State (grounded)

* `catalog_introspection.rs` detects a few `pg_catalog`/`information_schema` join shapes and returns
  **hardcoded** rows (relkind='r', relnamespace=2200, atttypid=23).
* No catalog-backed `pg_type`/`pg_class`/`pg_attribute`/`pg_namespace`/`pg_index`/`pg_constraint`.
* The translator (`src/network/postgres/translator.rs:73`) echoes catalog queries back.

== Target Design

Catalog-backed `pg_catalog` views computed from the real `CatalogTableSchema` / `CatalogNamespace` /
`ProximaType` metadata and relational constraints, routed through the existing introspection service.
Reference `datafusion-postgres`'s pg_catalog-over-DataFusion layer.

== Deliverables

1. `pg_type` from the `ProximaType`↔OID mapping.
2. `pg_class` / `pg_namespace` from `CatalogTableSchema` / `CatalogNamespace`.
3. `pg_attribute` from real column order/type/nullability.
4. `pg_index` / `pg_constraint` from relational constraints (`relational.rs`: PK/UNIQUE/FK/CHECK/NOT
   NULL) and vector indexes (HNSW/IVF).
5. Route these in `translator.rs` to `CatalogIntrospectionService::execute_select()`.

== Acceptance

* SQLAlchemy `Inspector.get_table_names` / `get_columns` / `get_pk_constraint` and JDBC
  `DatabaseMetaData.getTables` / `getColumns` / `getIndexInfo` return correct results against a live
  collection.
