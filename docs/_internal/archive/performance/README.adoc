=== Performance Tuning by Engine

==== SST Engine (Recommended for Most Use Cases)

**Best For**: OLTP workloads, balanced read/write

**Configuration**:
[source,toml]
----
[storage]
default_engine = "sst"

[storage.sst_config]
block_size_kb = 1024
compression = "lz4"  # 11% faster than no compression
bloom_filter_enabled = true
cache_size_mb = 2048
----

**Performance Tips**:
- Enable LZ4 compression (faster + saves disk)
- Increase block size for better compression (trade-off: more memory)
- Enable bloom filters for faster negative lookups
- Tune cache size based on working set

==== HELIX Engine (Disk-Efficient)

**Best For**: High-throughput writes, minimal disk usage

**Configuration**:
[source,toml]
----
[storage]
default_engine = "helix"

[storage.helix_config]
compression = "none"  # Fastest at 10K scale
hilbert_curve_order = 10
progressive_search_enabled = true
----

**Performance Tips**:
- No compression is fastest for <10K vectors
- Use Snappy for light compression with minor overhead
- Progressive search improves latency

==== VIPER Engine (Analytics)

**Best For**: Read-heavy analytics, columnar access patterns

**Configuration**:
[source,toml]
----
[storage]
default_engine = "viper"

[storage.viper_config]
row_group_size = 10000
compression = "snappy"  # Good balance for Parquet
filterable_columns = ["category", "price", "timestamp"]
----

**Performance Tips**:
- Define filterable columns for metadata you'll query
- Larger row groups = better compression, slower writes
- Use Snappy or Zstd compression
- Best for batch analytics workloads

== Compression Recommendations

=== SST: Use LZ4

**Benchmark results** (10K vectors):
[source,text]
----
No compression:  5.97ms
LZ4:            5.34ms  (-11% faster, saves disk space!)
Snappy:         5.45ms  (-9% faster)
Zstd:           6.12ms  (+2% slower, best compression ratio)
----

**Recommendation**: **LZ4 for production** - faster AND smaller

=== HELIX: No Compression at Small Scale

**Benchmark results** (10K vectors):
[source,text]
----
No compression: 13.51ms (fastest)
Snappy:         13.27ms (-1.8%, minor benefit)
LZ4:            13.59ms (+0.6%)
Zstd:           14.33ms (+6% slower)
----

**Recommendation**: **No compression** for <10K vectors, **Snappy** for >10K

=== Dataset Size Guide

[source,text]
----
< 5K vectors:    SWIFT or HELIX (no compression)
5K - 50K:        SST with LZ4 (best choice)
> 50K:           VIPER or SST with LZ4
----

== Performance Tuning

=== Memory Optimization

[source,toml]
----
[storage]
# Adjust cache size based on working set
cache_size_mb = 4096  # Default, increase for large datasets

# Memory pools
[storage.memory_pool]
pool_size_mb = 2048
vector_pool_size = 1000

# WAL buffers
[storage.wal_config]
memory_flush_size_bytes = 16777216  # 16MB (default)
# Increase for write-heavy workloads:
# memory_flush_size_bytes = 33554432  # 32MB
----

=== Write-Heavy Optimization

[source,toml]
----
[storage]
default_engine = "sst"

[storage.sst_config]
compression = "lz4"
bloom_filter_enabled = true

[storage.wal_config]
memory_flush_size_bytes = 33554432  # 32MB
global_flush_threshold = 8589934592  # 8GB

# Disable fsync for maximum throughput (not recommended for production)
# fsync_enabled = false
----

=== Read-Heavy Optimization

[source,toml]
----
[storage]
default_engine = "sst"  # Or "viper" for analytics
cache_size_mb = 8192    # Large cache

[storage.sst_config]
compression = "lz4"
block_size_kb = 2048    # Larger blocks for better compression

# Enable query result caching
enable_query_cache = true
query_cache_size_mb = 2048
----

=== Cloud Storage Optimization

**S3/Azure/GCS**: ProximaDB's engines (especially HELIX and VIPER) are optimized for cloud storage:
- Minimal disk footprint reduces storage costs
- Efficient partial I/O minimizes API calls and data transfer
- LZ4 compression reduces network bandwidth

[source,toml]
----
[[storage.storage_locations]]
url = "s3://my-bucket/proximadb-data"
weight = 1

[storage]
# Use HELIX or VIPER for lowest cloud storage costs
default_engine = "helix"  # 45.9MB vs Qdrant's 199MB

# Enable compression to reduce transfer costs
[storage.helix_config]
compression = "lz4"
----

== Troubleshooting Performance

=== Slow Queries

[source,bash]
----
# Check cache hit rate
curl http://localhost:5678/metrics | grep cache_hit_rate

# If < 80%, increase cache size
[storage]
cache_size_mb = 8192

# Enable query logging
RUST_LOG=proximadb::core::search=debug cargo run --bin proximadb-server

# Check for metadata filter usage
# Ensure filterable_columns are defined for frequently queried metadata
----

=== High Memory Usage

[source,bash]
----
# Check current usage
curl http://localhost:5678/metrics | grep memory

# Reduce cache size
[storage]
cache_size_mb = 2048

# Reduce WAL buffer
[storage.wal_config]
memory_flush_size_bytes = 8388608  # 8MB
----

=== Slow Writes

[source,bash]
----
# Check WAL flush frequency
RUST_LOG=proximadb::storage::persistence::write_ahead_log=debug

# Increase WAL buffer
[storage.wal_config]
memory_flush_size_bytes = 33554432  # 32MB

# Use LZ4 compression (faster)
[storage.sst_config]
compression = "lz4"

# Consider SST engine for write-heavy workloads
[storage]
default_engine = "sst"
----

== Production Performance Tips

1. **Use SST with LZ4** for most workloads (best balanced performance)
2. **Enable bloom filters** for faster negative lookups
3. **Size cache appropriately** (>90% hit rate target)
4. **Define filterable columns** for frequently queried metadata
5. **Use HELIX or VIPER** for minimal cloud storage costs
6. **Monitor cache hit rate** and adjust cache size accordingly
7. **Batch operations** when possible (better throughput)
8. **Use label-based queries** over property filters when possible (faster)
