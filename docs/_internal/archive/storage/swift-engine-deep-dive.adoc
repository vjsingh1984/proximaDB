**Why SWIFT exists and how three-tier hierarchy enables enterprise organization**

== Design Philosophy

=== The Problem SWIFT Solves

Enterprise vector databases face organizational challenges beyond raw performance:

* **Multi-tenant isolation**: Different customers need separate data silos
* **Departmental boundaries**: Marketing vectors shouldn't mix with Engineering vectors
* **Hierarchical access**: Tenant → Department → Project → Document
* **Predictable query scope**: Search within a specific organizational unit

Traditional flat storage forces linear scans even when queries target a specific tenant or department.

=== The Three-Tier Hierarchy Solution

**Key insight**: Organizational hierarchy creates natural data clusters. SWIFT exploits this by co-locating vectors that will be queried together.

=== Core Design Decisions

[cols="2,3,3", options="header"]
|===
| Decision | Rationale | Trade-off

| **Three-tier hierarchy**
| SuperBlock → DataBlock → Records mirrors enterprise org charts (Tenant → Department → Documents)
| More complex writes; requires data pre-organization

| **AdaCurve (learned curves)**
| K-means discovers natural clusters; curves adapt to data distribution
| Training overhead; model drift if data changes

| **Two-level pruning**
| Prune SuperBlocks first, then Blocks within selected SuperBlocks
| Requires accurate centroids at both levels

| **64 blocks per SuperBlock**
| sqrt(64) = 8 blocks scanned per SuperBlock; good balance of organization and pruning
| Fixed granularity may not fit all use cases
|===

== Architecture Overview

=== Why Three Tiers?

[source,text]
----
Enterprise Organization              SWIFT Mapping

    Company                          File (single collection)
       │
    ┌──┴──┬───────┐
Tenant A  Tenant B  Tenant C        SuperBlocks (tenant isolation)
    │
┌───┴───┬───────┐
Dept 1  Dept 2  Dept 3              Blocks within SuperBlock
    │
 Vectors                            Records within Block

Query: "Find similar docs in Tenant A, Dept 2"
→ Skip SuperBlocks B, C (tenant pruning)
→ Within SuperBlock A, skip Depts 1, 3 (centroid pruning)
→ Scan only Dept 2's vectors
----

=== Two-Level Pruning Pipeline

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
flowchart TB
    Q[Query: Tenant A similarity search]

    subgraph L1["Level 1: SuperBlock Pruning"]
        SB1["SuperBlock 0: Tenant A<br/>centroid: [0.12, ...]"]
        SB2["SuperBlock 1: Tenant B<br/>centroid: [0.45, ...]"]
        SB3["SuperBlock 2: Tenant C<br/>centroid: [0.78, ...]"]

        Q --> SB1
        Q -.->|"Skip: wrong tenant"| SB2
        Q -.->|"Skip: wrong tenant"| SB3
    end

    subgraph L2["Level 2: Block Pruning (within Tenant A)"]
        B1["Block 0: Dept 1<br/>centroid: [0.11, ...]"]
        B2["Block 1: Dept 2<br/>centroid: [0.13, ...]"]
        B3["Block 2: Dept 3<br/>centroid: [0.15, ...]"]

        SB1 --> B2
        SB1 -.->|"Skip: centroid far"| B1
        SB1 -.->|"Skip: centroid far"| B3
    end

    subgraph SEARCH["Progressive Search"]
        B2 --> R[Scan Block 1 vectors only]
    end

    style L1 fill:#e6f3ff,stroke:#4a90e2
    style L2 fill:#fff3e6,stroke:#f4a261
    style SEARCH fill:#e6ffe6,stroke:#93c47d
----

**Pruning math**:

* 16 SuperBlocks → scan sqrt(16) = 4 SuperBlocks
* 64 Blocks per SuperBlock → scan sqrt(64) = 8 Blocks per selected SuperBlock
* Total: 4 × 8 = 32 blocks scanned out of 16 × 64 = 1024 → **97% pruning**

=== When to Choose SWIFT

[cols="1,4", options="header"]
|===
| Choose SWIFT When | Rationale

| **Multi-tenant platform**
| SuperBlocks provide natural tenant isolation; queries skip irrelevant tenants

| **Departmental organization**
| Three-tier hierarchy maps to Company → Department → Team structure

| **Predictable query scope**
| Most queries target specific organizational units; hierarchy enables skipping

| **Clustered data distribution**
| AdaCurve learns cluster structure; better than fixed Hilbert for non-uniform data
|===

=== When NOT to Choose SWIFT

[cols="1,2,2", options="header"]
|===
| Scenario | Better Choice | Why

| Flat data, no hierarchy
| **SST**
| Three-tier overhead without pruning benefit

| Cross-tenant queries common
| **HELIX** or **SST**
| SWIFT's hierarchy penalizes queries spanning SuperBlocks

| Real-time write-heavy
| **SST**
| SWIFT's SuperBlock organization has higher write latency

| Small dataset (<100K)
| **SST** or **HELIX**
| Three-tier overhead not justified
|===

== AdaCurve: Learned Space-Filling Curves

=== Why AdaCurve over Hilbert?

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
graph TB
    subgraph HILBERT["Hilbert (Fixed)"]
        H1["Same curve for all data"]
        H2["Optimal for uniform distribution"]
        H3["Suboptimal for clustered data"]
    end

    subgraph ADACURVE["AdaCurve (Learned)"]
        A1["K-means discovers clusters"]
        A2["Curve adapts to data"]
        A3["Better locality for clusters"]
    end

    style HILBERT fill:#fff3e6,stroke:#f4a261
    style ADACURVE fill:#e6ffe6,stroke:#93c47d
----

|===
| Property | Hilbert | AdaCurve

| **Data adaptation** | None (fixed pattern) | K-means clustering learns structure
| **Best for** | Uniform/random data | Clustered enterprise data
| **Training** | None | Requires sample data
| **Update cost** | None | Retrain if distribution changes
|===

=== AdaCurve Training

[source,text]
----
AdaCurve Training Process:

1. Sample vectors from SuperBlock
   └── Sample 10K vectors (or all if < 10K)

2. K-means clustering (k=256 typical)
   └── Discover natural data clusters

3. Order clusters by Hilbert curve
   └── Ensure globally consistent ordering

4. Create mapping: cluster_id → curve_position
   └── Vectors assigned to nearest cluster

Result: Vectors in same cluster get adjacent curve positions
        → Better locality than fixed Hilbert for clustered data
----

== File Format Design

=== Why SuperBlock Directory in Header?

[source,text]
----
┌──────────────────────────────────────────────────────────────┐
│ SWIFT File Structure                                          │
├──────────────────────────────────────────────────────────────┤
│ Header (256 bytes)                                            │
│   Magic: "SWFT", Version: 2                                   │
│   SuperBlock Count, Total Vectors, Dimension                  │
├──────────────────────────────────────────────────────────────┤
│ ★ SuperBlock Directory ★                                      │
│   SB 0: offset=1024, centroid=[...], adacurve_code=0x...     │
│   SB 1: offset=..., centroid=[...], adacurve_code=0x...      │
│   SB 2: ...                                                   │
├──────────────────────────────────────────────────────────────┤
│ SuperBlock 0 Data                                             │
│   Header: name="tenant_a", block_count=64                    │
│   Block Directory: offset, centroid for each block            │
│   DataBlock 0, DataBlock 1, ... DataBlock 63                  │
├──────────────────────────────────────────────────────────────┤
│ SuperBlock 1 Data                                             │
│   ...                                                         │
└──────────────────────────────────────────────────────────────┘

★ Why directory at top?

For multi-tenant query:
1. Read directory (few KB)
2. Find target tenant's SuperBlock offset
3. Seek directly to SuperBlock (skip others)
4. Apply block pruning within SuperBlock

Without directory: Must scan file to find tenant → O(n) instead of O(1)
----

=== SuperBlock Structure

[source,text]
----
SuperBlock Internal Structure:

┌────────────────────────────────────────────────┐
│ SuperBlock Header                               │
│   ID: 0                                        │
│   Name: "tenant_a" (tenant identifier)         │
│   Centroid: avg(all vectors in SuperBlock)     │
│   AdaCurve Code: spatial position              │
├────────────────────────────────────────────────┤
│ Block Directory                                │
│   Block 0: offset, size, centroid, vector_count│
│   Block 1: offset, size, centroid, vector_count│
│   ... (64 blocks typical)                      │
├────────────────────────────────────────────────┤
│ DataBlock 0 (ProximaDataBlock format)          │
│   Centroid: avg(vectors in block)              │
│   1000-2000 vectors (configurable)             │
│   Compressed with LZ4/ZSTD                     │
├────────────────────────────────────────────────┤
│ DataBlock 1                                    │
│   ...                                          │
└────────────────────────────────────────────────┘

Two centroids enable two-level pruning:
1. SuperBlock centroid: Skip entire tenants
2. Block centroid: Skip departments within tenant
----

== Progressive Search Pipeline

=== Four-Phase Refinement

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
flowchart TB
    subgraph PRUNE["Two-Level Pruning"]
        P1[16 SuperBlocks] -->|sqrt(16)=4| P2[4 SuperBlocks]
        P2 -->|64 blocks each| P3[256 blocks total]
        P3 -->|sqrt(64)=8 per SB| P4[32 blocks to scan]
    end

    subgraph QUANT["Progressive Quantization"]
        Q1[32 blocks, 64K vectors] -->|Binary: Hamming| Q2[10K candidates]
        Q2 -->|INT8: SIMD L2| Q3[2K candidates]
        Q3 -->|PQ8: LUT lookup| Q4[200 candidates]
        Q4 -->|FP32: full precision| Q5[Top-K results]
    end

    PRUNE --> QUANT

    style PRUNE fill:#e6f3ff,stroke:#4a90e2
    style QUANT fill:#e6ffe6,stroke:#93c47d
----

**Total elimination**: 1M vectors → 32 blocks (3%) → 200 candidates (0.02%) → Top-10 (0.001%)

== Configuration Guide

=== Tuning for Multi-Tenant Workloads

[source,toml]
----
[swift]
# One SuperBlock per tenant for isolation
blocks_per_superblock = 64  # Departments per tenant

# Enable tenant metadata for fast filtering
enable_tenant_isolation = true
tenant_superblock_mapping = true

# Cache hot tenants
superblock_cache_mb = 256  # Cache entire hot tenant SuperBlocks
----

=== Tuning for Hierarchical Organization

[source,toml]
----
[swift]
# Match hierarchy depth to org structure
blocks_per_superblock = 64   # sqrt(64)=8 pruned at block level
vectors_per_block = 2000     # Department-sized chunks

# AdaCurve for clustered departments
adacurve_enabled = true
adacurve_cluster_count = 256  # Discover 256 natural clusters
----

== Monitoring & Debugging

=== Key Health Indicators

[cols="2,3,2", options="header"]
|===
| Metric | Healthy Range | Action if Unhealthy

| `superblock_pruning_ratio` | >70% | Verify tenants correctly mapped to SuperBlocks
| `block_pruning_ratio` | >80% | Check block centroids; verify departmental organization
| `cross_superblock_queries` | <10% | If high, data may not match hierarchy; consider SST
| `adacurve_cluster_quality` | >0.9 | Retrain AdaCurve; increase cluster count
|===

== Summary: SWIFT Design Principles

1. **Three-tier hierarchy for enterprise organization** - SuperBlock → Block → Records mirrors Tenant → Department → Document
2. **Two-level centroid pruning** - Skip irrelevant SuperBlocks, then irrelevant Blocks
3. **AdaCurve learned curves** - K-means discovers natural clusters; better than fixed Hilbert for enterprise data
4. **Multi-tenant isolation** - SuperBlocks provide natural tenant boundaries
5. **Progressive quantization** - Binary → INT8 → PQ → FP32 within selected blocks
