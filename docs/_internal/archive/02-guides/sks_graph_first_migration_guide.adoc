= SKS Graph-First Migration Guide
:sectnums:
:toc: left
:toclevels: 3
:icons: font

[.lead]
How to migrate from legacy SKS split-storage to graph-first architecture.

== When to Use This Guide

Use this guide if you're running ProximaDB v0.1.x with the legacy Semantic Knowledge Store (SKS) architecture and want to migrate to the new graph-first architecture (v0.2.0+). The graph-first architecture provides 3-6x faster entity operations, 21% lower memory usage, and simplified storage. Skip this guide if you're starting fresh with v0.2.0 or later (graph-first is the default).

== Prerequisites

* ProximaDB v0.2.0 or later currently running
* Existing SKS data to migrate
* System requirements:
  - Rust 1.88 or later
  - Available RAM: 2x your current data size (temporary during migration)
  - Available disk: 1.5x your current data size
* Full backup of existing data
* Maintenance window for migration (downtime required)

== Understanding the Migration

=== What Changes

**Legacy Architecture (v0.1.x):**
* Entities stored in vector engine (SST/VIPER)
* Relations stored in separate in-memory HashMap
* Metadata in separate key-value store
* Provenance in separate registry

**Graph-First Architecture (v0.2.0+):**
* All data unified in Orion graph engine
* Entities as graph nodes with embedded vectors
* Relations as edges in CSR format
* Single system for all operations

=== Migration Benefits

* **Performance**: 105K+ entities/sec (3-6x faster)
* **Memory**: 21% reduction in memory footprint
* **Simplicity**: One storage system instead of four
* **Query Speed**: Hybrid queries 5x faster

[source,bash]

# Check your ProximaDB version
grep 'version = ' Cargo.toml

----

=== Step 2: Backup Your Data

[source,bash]
----
# Create timestamped backup
BACKUP_DIR="data_backup_$(date +%Y%m%d_%H%M%S)"
cp -r data/ "$BACKUP_DIR"

# Verify backup
du -sh "$BACKUP_DIR"
ls -lh "$BACKUP_DIR"

# Store backup location
echo "$BACKUP_DIR" > migration_backup.txt
----

=== Step 3: Check Available Resources

[source,bash]
----
# Check available memory (need 2x current usage)
free -h

# Check disk space (need 1.5x current usage)
df -h

# Check Rust version
rustc --version  # Should be 1.88 or later
----

=== Step 4: Stop Write Traffic

Before migration, ensure no writes are happening:

[source,bash]
----
# Gracefully stop the server
pkill -TERM proximadb-server

# Wait for shutdown
sleep 5

# Verify it stopped
ps aux | grep proximadb-server
----

== Migration Process

=== Method 1: Automated Migration (Recommended)

**Step 1: Enable graph-first feature**

The `graph-first-sks` feature is enabled by default in v0.2.0:

[source,toml]
----
# Cargo.toml (verify this is present)
[features]
default = ["sql_frontend", "graph-first-sks"]
----

**Step 2: Create migration script**

Create `migrate.rs`:

[source,rust]
----
use proximadb::storage::entity_store::{
    ProximaEntityStore, OrionBackedEntityStore,
    migration::{migrate_to_graph_first, MigrationConfig}
};
use proximadb::graph::GraphOperationsService;
use std::sync::Arc;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    // Initialize services
    let graph_service = Arc::new(GraphOperationsService::new());

    // Configure migration
    let config = MigrationConfig {
        collection_id: "my-collection".to_string(),
        batch_size: 1000,
        validate: true,
        cleanup_legacy: false,  // Set true after validation
    };

    println!("Starting migration for collection: {}", config.collection_id);

    // Run migration
    let stats = migrate_to_graph_first(
        &legacy_store,
        "my-collection",
        graph_service,
        &config
    ).await?;

    // Report results
    println!("Migration complete!");
    println!("  Entities migrated: {}", stats.entities_migrated);
    println!("  Relations migrated: {}", stats.relations_migrated);
    println!("  Duration: {}ms", stats.duration_ms);
    println!("  Errors: {}", stats.errors);

    if stats.errors > 0 {
        eprintln!("WARNING: Migration completed with {} errors", stats.errors);
        return Err(anyhow::anyhow!("Migration had errors"));
    }

    Ok(())
}
----

**Step 3: Run migration**

[source,bash]
----
# Build and run migration
cargo run --release --bin migrate

# Monitor progress
tail -f migration.log
----

**Step 4: Validate migration**

[source,bash]
----
# Run validation tests
cargo test --test sks_graph_first_integration_test

# Should see:
# test test_migration_validation ... ok
# test test_entity_count_matches ... ok
----

**Step 5: Performance testing**

[source,bash]
----
# Compare performance
cargo test test_performance_comparison_legacy_vs_graph_first -- --nocapture

# Expected output:
# Legacy throughput: ~20K entities/sec
# Graph-first throughput: ~105K entities/sec
# Improvement: 5x
----

=== Method 2: Manual Migration

For fine-grained control over the migration process.

**Step 1: Create graph collection**

[source,rust]
----
use proximadb::proto::proximadb_v1::CreateGraphRequest;

let request = CreateGraphRequest {
    graph_id: "my-collection".to_string(),
    name: Some("My Collection (Migrated)".to_string()),
    description: Some("Migrated from legacy SKS".to_string()),
    ..Default::default()
};

graph_service.create_graph_collection(request).await?;
----

**Step 2: Migrate entities in batches**

[source,rust]
----
let batch_size = 1000;
let mut offset = 0;

loop {
    // Fetch batch from legacy store
    let entities = legacy_store
        .list_entities("my-collection", offset, batch_size)
        .await?;

    if entities.is_empty() {
        break;
    }

    // Prepare batch for graph store
    let mut batch = Vec::new();
    for entity in entities {
        let mut entity_copy = entity.clone();
        entity_copy.collection_id = "my-collection".to_string();
        batch.push(entity_copy);
    }

    // Insert into graph store
    let count = graph_store
        .batch_upsert_entities("my-collection", batch)
        .await?;

    println!("Migrated batch: {} entities (offset: {})", count, offset);
    offset += batch_size;
}

println!("Entity migration complete: {} total", offset);
----

**Step 3: Migrate relations**

[source,rust]
----
// Get all relations from legacy store
let relations = legacy_store
    .get_all_relations("my-collection")
    .await?;

println!("Migrating {} relations...", relations.len());

// Insert into graph store
for relation in relations {
    graph_store.add_relation(relation).await?;
}

println!("Relation migration complete");
----

**Step 4: Verify migration**

[source,rust]
----
// Compare counts
let legacy_count = legacy_store
    .list_entities("my-collection", 0, usize::MAX)
    .await?
    .len();

let graph_count = graph_store
    .list_entities("my-collection", 0, usize::MAX)
    .await?
    .len();

assert_eq!(legacy_count, graph_count,
    "Entity count mismatch: {} vs {}", legacy_count, graph_count);

println!("Validation successful: {} entities", graph_count);
----

== Post-Migration Steps

=== Step 1: Update Application Code

The EntityStore trait interface remains the same, so no code changes are required:

[source,rust]
----
// Before (legacy):
let store = ProximaEntityStore::new(...);

// After (graph-first):
let store = OrionBackedEntityStore::new(
    graph_service,
    "my-collection".to_string()
);

// Same API works for both:
let entity = store.get_entity("coll", "id", true, false).await?;
----

=== Step 2: Monitor Performance

Track key metrics after migration:

[source,rust]
----
use std::time::Instant;

// Test entity lookup
let start = Instant::now();
let entity = store.get_entity("coll", "id", true, false).await?;
let latency = start.elapsed();
println!("Lookup latency: {:?}", latency);
// Expected: <50μs (was ~100-200μs)

// Test batch insert
let start = Instant::now();
let count = store.batch_upsert_entities("coll", entities).await?;
let duration = start.elapsed();
let throughput = count as f64 / duration.as_secs_f64();
println!("Throughput: {:.2} entities/sec", throughput);
// Expected: 75K+ (was ~15-25K)
----

=== Step 3: Cleanup Legacy Data

Only after confirming migration success:

[source,bash]
----
# Remove legacy storage files
rm -rf data/legacy_entity_store/
rm -rf data/legacy_relations/
rm -rf data/legacy_provenance/

# Or re-run migration with cleanup enabled:
# config.cleanup_legacy = true
----

=== Step 4: Restart Server

[source,bash]
----
# Build with release optimizations
cargo build --release

# Start server
cargo run --release --bin proximadb-server

# Verify health
curl http://localhost:5678/health
----

== Rollback Procedure

If migration fails or issues arise:

=== Option 1: Restore from Backup

[source,bash]
----
# Stop server
pkill -TERM proximadb-server

# Restore backup
BACKUP_DIR=$(cat migration_backup.txt)
rm -rf data/
cp -r "$BACKUP_DIR" data/

# Rebuild with legacy features (if needed)
cargo build --no-default-features --features sql_frontend

# Restart server
cargo run --bin proximadb-server
----

=== Option 2: Use Rollback Utility

[source,rust]
----
use proximadb::storage::entity_store::migration::rollback_migration;

// Rollback the migration
rollback_migration(graph_service, "my-collection").await?;

// Note: May require manual cleanup
// Delete graph collection if needed
----

== Common Pitfalls

=== Pitfall 1: Insufficient Memory

**Problem:** Migration fails with out-of-memory errors.

**Solution:** Reduce batch size:

[source,rust]
----
let config = MigrationConfig {
    batch_size: 500,  // Reduced from 1000
    ..Default::default()
};
----

=== Pitfall 2: Collection ID Mismatch

**Problem:** Migration fails with "Collection ID mismatch" error.

**Solution:** Ensure all entities have consistent collection_id:

[source,rust]
----
for entity in &mut entities {
    entity.collection_id = "my-collection".to_string();
}
----

=== Pitfall 3: Write Traffic During Migration

**Problem:** Migration inconsistencies due to concurrent writes.

**Solution:** Ensure server is stopped before migration:

[source,bash]
----
# Stop all ProximaDB processes
pkill -9 proximadb-server

# Verify stopped
ps aux | grep proximadb
----

=== Pitfall 4: Validation Disabled

**Problem:** Migration completes but with data inconsistencies.

**Solution:** Always enable validation:

[source,rust]
----
let config = MigrationConfig {
    validate: true,  // ALWAYS enable for production
    ..Default::default()
};
----

=== Pitfall 5: No Backup

**Problem:** Migration fails and data is lost.

**Solution:** ALWAYS create backup before migration:

[source,bash]
----
# Never skip this step!
cp -r data/ "data_backup_$(date +%Y%m%d_%H%M%S)"
----

== Troubleshooting

=== Issue: Migration Hangs

**Symptoms:** Migration appears stuck for >5 minutes.

**Diagnosis:**
[source,bash]
----
# Check process CPU/memory
top -p $(pgrep migrate)

# Check logs
tail -f migration.log
----

**Solution:**
* Reduce batch_size to 500 or 250
* Ensure sufficient available memory
* Check for disk I/O bottlenecks

=== Issue: Validation Fails

**Symptoms:** "Validation failed with N errors" message.

**Diagnosis:**
[source,bash]
----
# Check migration logs for specific errors
grep ERROR migration.log

# Manually inspect failed entities
----

**Solution:**
* Review error logs for specific entity IDs
* Verify entity IDs are consistent
* Check for corrupted data in legacy store

=== Issue: Performance Below Expectations

**Symptoms:** Throughput < 30K entities/sec after migration.

**Checklist:**
- [ ] Verify `graph-first-sks` feature enabled
- [ ] Check available RAM and CPU
- [ ] Ensure running with `--release` flag
- [ ] Verify batch size is 1000-5000

**Solution:**
[source,bash]
----
# Rebuild with optimizations
cargo clean
cargo build --release --features graph-first-sks

# Run performance test
cargo test --release test_performance_comparison -- --nocapture
----
