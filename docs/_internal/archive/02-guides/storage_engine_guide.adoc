[.lead]
How to configure and use ProximaDB's vector and graph storage engines.

== When to Use This Guide

Use this guide when you need to configure storage engines for your collections or understand basic engine concepts. This guide covers the six vector storage engines (SST, VIPER, NOVA, SWIFT, RAPTOR, HELIX) and three graph engines (ORION, PULSAR, QUASAR). For detailed engine selection and optimization, see the Engine Selection and Optimization Guide.

== Prerequisites

* ProximaDB 0.1.4 or later installed
* Access to `config/config.toml` for configuration
* Basic understanding of vector databases and graph databases
* Knowledge of your workload requirements (OLTP, analytics, or graph traversal)

== Vector Storage Engines Overview

ProximaDB provides six specialized vector storage engines:

[cols="2,3,2,3", options="header"]
|===
| Engine | Primary Use Case | Key Feature | When to Use

| **SST**
| Real-time OLTP
| Three-stage filtering
| High write throughput (200K vec/sec)

| **VIPER**
| Analytics/BI
| Parquet columnar storage
| Analytics workloads, compression

| **NOVA**
| Advanced analytics
| Progressive search
| Research, maximum compression

| **SWIFT**
| Ultra-low latency
| Proxima encoding
| <1ms latency requirements

| **RAPTOR**
| Variable workloads
| Adaptive optimization
| Multi-tenant, changing patterns

| **HELIX**
| Spatial data
| Hilbert curve mapping
| Geospatial, time-series data
|===

== Configuring Vector Engines

=== Creating a Collection with an Engine

**Step 1: Choose your engine**

Based on your workload:
* Real-time applications: SST or SWIFT
* Analytics: VIPER or NOVA
* Adaptive workloads: RAPTOR
* Spatial data: HELIX

**Step 2: Create collection via API**

[source,bash]
----
# Create collection with SST engine
curl -X POST http://localhost:5678/v1/collections \
  -H "Content-Type: application/json" \
  -d '{
    "name": "my_collection",
    "dimension": 768,
    "engine": "SST",
    "config": {
      "max_memtable_size_mb": 64,
      "enable_bloom_filters": true
    }
  }'
----

**Step 3: Verify collection created**

[source,bash]
----
# List collections
curl http://localhost:5678/v1/collections

# Get collection details
curl http://localhost:5678/v1/collections/my_collection
----

=== SST Engine Configuration

SST (Sorted String Table) is optimized for real-time OLTP workloads.

**Basic configuration in `config.toml`:**

[source,toml]
----
[storage.sst_config]
# Write optimization
max_memtable_size_mb = 64              # Memtable size
write_buffer_size_mb = 32              # Write buffer

# Read optimization
enable_bloom_filters = true            # Enable bloom filters
bloom_filter_bits_per_key = 10         # 1% false positive rate

# Compression
compression = "lz4"                    # Fast compression
compression_enabled = true
compression_level = 6

# Compaction
compaction_strategy = "leveled"        # Leveled compaction
compaction_threshold = 10
level_count = 7
background_thread_count = 8

# Storage
data_directory = "/var/lib/proximadb/sst_data"
cache_size_mb = 2048                   # Block cache size

# Performance
mmap_enabled = true                    # Memory-mapped files
prefetch_enabled = true
prefetch_size_kb = 128
----

**Common tuning parameters:**

* `max_memtable_size_mb`: Increase for higher write throughput (64-128 MB)
* `bloom_filter_bits_per_key`: Increase for lower false positives (10-15)
* `compression_level`: Balance compression ratio vs speed (3-9)
* `cache_size_mb`: Set based on available memory (1-4 GB)

=== VIPER Engine Configuration

VIPER (Vector-Indexed Parquet Extended Rows) is optimized for analytics.

**Basic configuration in `config.toml`:**

[source,toml]
----
[storage.viper_config]
# Row group optimization
row_group_size = 131072                # 128K vectors per row group
max_row_group_size_mb = 128

# Compression
compression = "zstd"                   # Best compression
compression_enabled = true
compression_level = 3                  # Balance speed/ratio

# Optimization features
enable_statistics = true               # Row group statistics
enable_bloom_filters = true            # Skip row groups
enable_column_indexes = true           # Fast column access

# Storage
data_directory = "/var/lib/proximadb/viper_data"
cache_size_mb = 4096                   # Larger cache for analytics
----

**Common tuning parameters:**

* `row_group_size`: Smaller for selective queries (50K), larger for scans (250K)
* `compression_level`: Higher for cold data (6-9), lower for hot data (1-3)
* `cache_size_mb`: Increase for better analytics performance (4-8 GB)

=== NOVA Engine Configuration

NOVA provides advanced analytics with progressive search.

**Basic configuration in `config.toml`:**

[source,toml]
----
[storage.nova_config]
# Progressive search
enable_progressive_search = true
progressive_stages = ["binary", "int8", "pq8", "fp32"]
quality_threshold = 0.95

# SuperBlock hierarchy
superblock_size = 1048576              # 1M vectors per SuperBlock
superblock_stats_depth = 3
enable_superblock_caching = true

# Zone maps
zone_map_granularity = "fine"
enable_multi_dimensional_pruning = true
selectivity_threshold = 0.1

# Quantization
quantization_strategy = "adaptive"
enable_cost_based_selection = true

# Storage
data_directory = "/var/lib/proximadb/nova_data"
streaming_buffer_size_mb = 256
streaming_thread_count = 8
----

**Common tuning parameters:**

* `progressive_stages`: Customize based on accuracy needs
* `quality_threshold`: Lower for faster queries (0.90), higher for accuracy (0.99)
* `superblock_size`: Larger for better compression (1-2M), smaller for memory (512K)

=== SWIFT Engine Configuration

SWIFT provides ultra-low latency for small datasets.

**Basic configuration in `config.toml`:**

[source,toml]
----
[storage.swift_config]
# Proxima encoding
enable_proxima_encoding = true
proxima_bit_width = 8

# Memory optimization
memory_pool_size_mb = 128
enable_memory_pooling = true

# CPU optimization
enable_cpu_affinity = true
cpu_core_count = 4
enable_numa_awareness = true

# Cache optimization
l1_cache_size_kb = 64
l2_cache_size_kb = 512
enable_cache_line_optimization = true

# Storage
data_directory = "/var/lib/proximadb/swift_data"
----

**Common tuning parameters:**

* `memory_pool_size_mb`: Pre-allocate based on dataset size
* `cpu_core_count`: Dedicate cores for predictable latency
* `proxima_bit_width`: 8 for balanced, 4 for speed, 16 for accuracy

=== RAPTOR Engine Configuration

RAPTOR adapts to variable workload patterns.

**Basic configuration in `config.toml`:**

[source,toml]
----
[storage.raptor_config]
# P×K optimization
enable_pxk_optimization = true
pxk_algorithm_version = "v2"
pxk_coverage_floor = 0.1

# Workload adaptation
workload_adaptation_interval_ms = 5000
adaptation_sensitivity = "medium"
enable_pattern_learning = true

# Row group auto-sizing
row_group_auto_sizing = true
min_row_group_size = 32768             # 32K minimum
max_row_group_size = 262144            # 256K maximum
target_utilization = 0.85

# Boundary detection
boundary_detection_algorithm = "smart"
importance_scoring_enabled = true
spillover_handling = "adaptive"

# Storage
data_directory = "/var/lib/proximadb/raptor_data"
----

**Common tuning parameters:**

* `workload_adaptation_interval_ms`: Faster for dynamic workloads (1000-5000)
* `adaptation_sensitivity`: "high" for rapid changes, "low" for stability
* Row group size limits: Adjust based on memory constraints

=== HELIX Engine Configuration

HELIX optimizes spatial locality using Hilbert curves.

**Basic configuration in `config.toml`:**

[source,toml]
----
[storage.helix_config]
# Hilbert curve optimization
hilbert_curve_order = 8                # 8-bit precision
enable_fast_2d_3d_paths = true
curve_cache_size_mb = 32

# Spatial grouping
spatial_grouping_threshold = 0.85
enable_spatial_locality = true
dimension_based_partitioning = true

# Liquid clustering
enable_liquid_clustering = true
clustering_similarity_threshold = 0.9
query_pattern_learning = true
cluster_adaptation_frequency = 3600    # 1 hour

# PCA optimization
enable_pca_optimization = true
pca_dimensions = 64                    # Reduce to 64D
pca_variance_threshold = 0.95          # Preserve 95% variance

# Storage
data_directory = "/var/lib/proximadb/helix_data"
----

**Common tuning parameters:**

* `hilbert_curve_order`: Higher for more dimensions (10-12), lower for speed (6-8)
* `pca_dimensions`: Balance locality vs information loss (32-128)
* `spatial_grouping_threshold`: Higher for stronger locality (0.90-0.95)

== Graph Storage Engines Overview

ProximaDB provides three graph database engines:

[cols="2,3,3", options="header"]
|===
| Engine | Architecture | When to Use

| **ORION**
| In-memory CSR format
| High-performance traversal (1M+ edges/sec)

| **PULSAR**
| Distributed sharded storage
| Horizontal scaling, large graphs

| **QUASAR**
| Hot/cold tiering
| Cost optimization, mixed workloads
|===

== Configuring Graph Engines

=== Creating a Graph

**Step 1: Choose your engine**

* Small-to-medium graphs (<100M nodes): ORION
* Large distributed graphs (>100M nodes): PULSAR
* Cost-sensitive deployments: QUASAR

**Step 2: Create graph via API**

[source,bash]
----
# Create graph with ORION engine
curl -X POST http://localhost:5679/v1/graphs \
  -H "Content-Type: application/json" \
  -d '{
    "graph_id": "my_graph",
    "name": "My Knowledge Graph",
    "engine": "ORION",
    "config": {
      "enable_wal": true,
      "wal_flush_interval_ms": 1000
    }
  }'
----

**Step 3: Verify graph created**

[source,bash]
----
# List graphs
curl http://localhost:5679/v1/graphs

# Get graph details
curl http://localhost:5679/v1/graphs/my_graph
----

=== ORION Engine Configuration

ORION provides in-memory graph storage with CSR format.

**Basic configuration in `config.toml`:**

[source,toml]
----
[graph.orion_config]
# Memory management
initial_node_capacity = 1000000        # Pre-allocate for 1M nodes
initial_edge_capacity = 5000000        # Pre-allocate for 5M edges
enable_arc_based_sharing = true        # Zero-copy memory sharing

# WAL persistence
enable_wal = true
wal_flush_interval_ms = 1000           # Flush every 1 second
wal_directory = "/var/lib/proximadb/graph_wal"
wal_max_size_mb = 512

# CSR optimization
enable_csr_compression = true
csr_cache_size_mb = 1024

# Storage
data_directory = "/var/lib/proximadb/orion_data"
----

**Common tuning parameters:**

* `initial_node_capacity`: Pre-allocate to avoid reallocation
* `wal_flush_interval_ms`: Lower for durability (100-500), higher for performance (1000-5000)
* `csr_cache_size_mb`: Increase for better traversal performance

=== PULSAR Engine Configuration

PULSAR provides distributed graph storage.

**Basic configuration in `config.toml`:**

[source,toml]
----
[graph.pulsar_config]
# Sharding
shard_count = 16                       # Number of shards
shard_strategy = "hash"                # hash or range
replication_factor = 3                 # Replicas per shard

# Consensus
consensus_protocol = "raft"
election_timeout_ms = 1000
heartbeat_interval_ms = 100

# Storage
data_directory = "/var/lib/proximadb/pulsar_data"
----

=== QUASAR Engine Configuration

QUASAR provides hot/cold tiering for cost optimization.

**Basic configuration in `config.toml`:**

[source,toml]
----
[graph.quasar_config]
# Tiering policy
hot_tier_threshold_days = 30           # Data accessed in last 30 days
warm_tier_threshold_days = 365         # 30-365 days old
cold_tier_storage = "s3"               # Cold tier backend

# Hot tier (ORION)
hot_tier_engine = "orion"
hot_tier_memory_limit_gb = 32

# Cold tier
cold_tier_bucket = "s3://my-bucket/graphs"
cold_tier_region = "us-west-2"

# Storage
data_directory = "/var/lib/proximadb/quasar_data"
----

== Working with Storage Engines

=== Inserting Vectors

[source,python]
----
from proximadb_sdk import ProximaDBClient

client = ProximaDBClient(url="http://localhost:5678")

# Insert vectors into collection
vectors = [
    {
        "id": "vec_1",
        "vector": [0.1, 0.2, 0.3, ...],  # 768 dimensions
        "metadata": {"category": "article", "timestamp": 1234567890}
    },
    {
        "id": "vec_2",
        "vector": [0.4, 0.5, 0.6, ...],
        "metadata": {"category": "product", "timestamp": 1234567891}
    }
]

client.insert_vectors("my_collection", vectors)
----

=== Searching Vectors

[source,python]
----
# Similarity search
results = client.search(
    collection="my_collection",
    vector=[0.1, 0.2, 0.3, ...],
    top_k=10,
    filter={"category": "article"}  # Optional metadata filter
)

for result in results:
    print(f"ID: {result['id']}, Score: {result['score']}")
----

=== Working with Graphs

[source,python]
----
# Create nodes
client.create_nodes("my_graph", [
    {"id": "node_1", "label": "Person", "properties": {"name": "Alice"}},
    {"id": "node_2", "label": "Person", "properties": {"name": "Bob"}}
])

# Create edges
client.create_edges("my_graph", [
    {"from": "node_1", "to": "node_2", "label": "KNOWS", "weight": 0.9}
])

# Traverse graph
results = client.traverse(
    graph="my_graph",
    start_node="node_1",
    max_depth=3,
    direction="outgoing"
)
----

== Common Pitfalls

=== Pitfall 1: Wrong Engine for Workload

**Problem:** Using VIPER for real-time inserts results in slow write performance.

**Solution:** Use SST for real-time writes, VIPER for analytics:

[source,bash]
----
# Wrong: VIPER for real-time
curl -X POST http://localhost:5678/v1/collections \
  -d '{"name": "realtime", "engine": "VIPER"}'

# Right: SST for real-time
curl -X POST http://localhost:5678/v1/collections \
  -d '{"name": "realtime", "engine": "SST"}'
----

=== Pitfall 2: Undersized Cache

**Problem:** Small cache causes frequent disk I/O.

**Solution:** Increase cache size based on working set:

[source,toml]
----
# Wrong:
cache_size_mb = 128

# Right (for 10M vectors):
cache_size_mb = 4096
----

=== Pitfall 3: Disabled WAL for Graphs

**Problem:** Graph data lost on crash without WAL.

**Solution:** Always enable WAL for production:

[source,toml]
----
[graph.orion_config]
enable_wal = true
wal_flush_interval_ms = 1000
----

=== Pitfall 4: Incorrect Row Group Size

**Problem:** Large row groups cause high memory usage in VIPER.

**Solution:** Tune based on query selectivity:

[source,toml]
----
# For selective queries:
row_group_size = 50000

# For full scans:
row_group_size = 250000
----
