How to choose and optimize the right storage engine for your workload.

== When to Use This Guide

Use this guide when you need to select a storage engine for a new collection or optimize an existing one. This guide assumes you understand basic vector database concepts (embeddings, similarity search, k-NN queries) and need practical guidance on matching ProximaDB's six storage engines to your specific performance requirements.

== Prerequisites

* ProximaDB 0.1.4 or later installed and running
* Basic understanding of your workload characteristics:
  - Query latency requirements (1ms, 100ms, or 1s+)
  - Write throughput needs (vectors/second)
  - Memory constraints
  - Data access patterns (real-time, analytics, mixed)
* Access to `config/config.toml` for configuration changes
* Ability to run benchmarks on representative data

== Selecting the Right Engine

=== Decision Framework

Choose your engine based on your primary requirement:

**For Real-Time Applications (Latency < 10ms):**

* **SWIFT**: Ultra-low latency (<1ms p99), small datasets (<100K vectors)
* **SST**: High-throughput OLTP (200K vec/sec), real-time updates

**For Analytics Workloads (Throughput-Optimized):**

* **VIPER**: Standard analytics, BI dashboards (80K vec/sec read)
* **NOVA**: Advanced analytics, compression-critical (90% compression ratio)

**For Variable/Unknown Workloads:**

* **RAPTOR**: Adaptive workloads with changing patterns
* **HELIX**: Spatial/time-series data with locality patterns

== Configuring Each Engine

=== SST Engine (Real-Time OLTP)

**Step 1: Configure basic settings**

Edit `config/config.toml`:

[source,toml]
----
[storage.sst_config]
# Optimize memtable for write throughput
max_memtable_size_mb = 64              # Larger = better batching

# Enable three-stage filtering for fast queries
enable_bloom_filters = true
bloom_filter_bits_per_key = 10         # 1% false positive rate

# Configure compression for storage efficiency
compression_type = "lz4"               # Fast compression
compression_enabled = true

# Write-ahead log for durability
enable_write_ahead_log = true
----

**Step 2: Tune for your workload**

For write-heavy workloads:
[source,toml]
----
max_memtable_size_mb = 128             # Reduce flush frequency
compaction_thread_count = 8            # More parallel compaction
----

For read-heavy workloads:
[source,toml]
----
bloom_filter_bits_per_key = 15         # Lower false positives
enable_quantized_search = true         # Faster similarity search
----

**Step 3: Verify performance**

[source,bash]
----
# Monitor SST metrics
curl http://localhost:5678/metrics | grep sst_write_throughput

# Expected: 150K-200K vectors/second on modern hardware
----

=== VIPER Engine (Columnar Analytics)

**Step 1: Configure row groups**

[source,toml]
----
[storage.viper_config]
# Row group size affects query performance
row_group_size = 131072                # 128K vectors (recommended)

# Compression for storage efficiency
compression_algorithm = "zstd"
compression_level = 3                  # Balance speed/ratio

# Enable columnar optimizations
enable_bloom_filters = true
enable_column_indexes = true
----

**Step 2: Optimize for query patterns**

For selective queries (filtering many rows):
[source,toml]
----
row_group_size = 50000                 # Smaller groups = better pruning
enable_bloom_filters = true            # Skip irrelevant row groups
----

For full-scan analytics:
[source,toml]
----
row_group_size = 250000                # Larger groups = less overhead
compression_level = 6                  # Higher compression
----

**Step 3: Monitor row group efficiency**

[source,bash]
----
# Check how many row groups are scanned per query
RUST_LOG=viper=info cargo run --bin proximadb-server 2>&1 | grep row_groups_scanned

# Lower numbers indicate better pruning efficiency
----

=== SWIFT Engine (Ultra-Low Latency)

**Step 1: Enable SWIFT-specific features**

[source,toml]
----
[storage.swift_config]
# Proxima encoding for fast flush
enable_proxima_encoding = true
proxima_bit_width = 8

# Dedicated memory pool
memory_pool_size_mb = 128
enable_memory_pooling = true

# CPU optimization
enable_cpu_affinity = true
cpu_core_count = 4                     # Dedicate cores
----

**Step 2: System-level tuning (Linux)**

[source,bash]
----
# Lock memory to prevent swapping
echo "proximadb soft memlock 8388608" | sudo tee -a /etc/security/limits.conf
echo "proximadb hard memlock 8388608" | sudo tee -a /etc/security/limits.conf

# Disable CPU frequency scaling
echo performance | sudo tee /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor
----

**Step 3: Verify latency**

[source,bash]
----
# Run latency test
cargo run --release --bin proximadb-bench -- --engine SWIFT --workload latency

# Expected: p99 < 1ms, p50 < 500μs
----

=== NOVA Engine (Advanced Analytics)

**Step 1: Configure progressive search**

[source,toml]
----
[storage.nova_config]
# Progressive search stages
enable_progressive_search = true
progressive_stages = ["binary", "int8", "pq8", "fp32"]
quality_threshold = 0.95               # Stop when 95% quality reached

# SuperBlock hierarchy for pruning
superblock_size = 1048576              # 1M vectors per block
enable_superblock_caching = true
----

**Step 2: Tune compression vs accuracy**

For maximum compression:
[source,toml]
----
quantization_strategy = "adaptive"
compression_level = 9                  # Maximum ZSTD compression
----

For maximum accuracy:
[source,toml]
----
progressive_stages = ["fp32"]          # Skip quantized stages
quality_threshold = 1.0                # Exact search
----

**Step 3: Monitor progressive search**

[source,bash]
----
# See which stages are actually used
RUST_LOG=nova=info cargo run --bin proximadb-server 2>&1 | grep progressive_search_stages_avg

# Lower average = queries stop early (good)
----

=== RAPTOR Engine (Adaptive Workloads)

**Step 1: Enable P×K optimization**

[source,toml]
----
[storage.raptor_config]
# Adaptive row group sizing
enable_pxk_optimization = true
pxk_algorithm_version = "v2"
row_group_auto_sizing = true

# Workload adaptation
workload_adaptation_interval_ms = 5000
enable_pattern_learning = true
----

**Step 2: Set adaptation boundaries**

[source,toml]
----
# Row group size limits
min_row_group_size = 32768             # 32K minimum
max_row_group_size = 262144            # 256K maximum
target_utilization = 0.85              # 85% efficiency target
----

**Step 3: Monitor adaptation**

[source,bash]
----
# Watch RAPTOR adapt to workload changes
RUST_LOG=raptor=info cargo run --bin proximadb-server 2>&1 | grep workload_adaptation

# You should see row group sizes adjust over time
----

=== HELIX Engine (Spatial Locality)

**Step 1: Configure Hilbert curve mapping**

[source,toml]
----
[storage.helix_config]
# Hilbert curve precision
hilbert_curve_order = 8                # 8-bit precision (balanced)
enable_fast_2d_3d_paths = true         # Optimize low dimensions

# Spatial clustering
enable_liquid_clustering = true
clustering_similarity_threshold = 0.9
spatial_grouping_threshold = 0.85
----

**Step 2: Enable PCA for high-dimensional data**

[source,toml]
----
# Reduce dimensions before mapping to Hilbert curve
enable_pca_optimization = true
pca_dimensions = 64                    # Reduce to 64D
pca_variance_threshold = 0.95          # Preserve 95% variance
----

**Step 3: Verify spatial locality**

[source,bash]
----
# Check locality preservation
RUST_LOG=helix=info cargo run --bin proximadb-server 2>&1 | grep locality_preserved

# Expected: >85% for spatial data
----

== Optimization Strategies

=== Multi-Engine Deployments

**Hot/Warm/Cold Architecture:**

[source,bash]
----
# Create collections with different engines
curl -X POST http://localhost:5678/v1/collections \
  -d '{"name": "hot_data", "dimension": 768, "engine": "SST"}'

curl -X POST http://localhost:5678/v1/collections \
  -d '{"name": "warm_data", "dimension": 768, "engine": "VIPER"}'

curl -X POST http://localhost:5678/v1/collections \
  -d '{"name": "cold_data", "dimension": 768, "engine": "NOVA"}'
----

Application logic routes queries based on data age:
[source,python]
----
def search_vectors(query_vector, data_age_days):
    if data_age_days < 30:
        return client.search("hot_data", query_vector, top_k=10)
    elif data_age_days < 365:
        return client.search("warm_data", query_vector, top_k=10)
    else:
        return client.search("cold_data", query_vector, top_k=10)
----

=== Performance Testing

**Step 1: Run built-in benchmarks**

[source,bash]
----
# Benchmark all engines with your data characteristics
cargo run --release --bin proximadb-bench \
  --all-engines \
  --dimensions 768 \
  --dataset-size 100000 \
  --query-pattern mixed
----

**Step 2: Analyze results**

[source,bash]
----
# Results are written to stdout
# Look for:
# - Write throughput (vectors/sec)
# - Query latency (p50, p95, p99)
# - Memory usage (MB)
# - Compression ratio
----

**Step 3: Test with your actual data**

[source,python]
----
import time
import numpy as np
from proximadb_sdk import ProximaDBClient

client = ProximaDBClient(url="http://localhost:5678")

# Test write throughput
vectors = [{"id": f"v{i}", "vector": np.random.rand(768).tolist()}
           for i in range(10000)]

start = time.time()
client.insert_vectors("test_collection", vectors)
duration = time.time() - start
print(f"Write throughput: {10000/duration:.0f} vec/sec")

# Test query latency
latencies = []
for _ in range(100):
    query = np.random.rand(768).tolist()
    start = time.time()
    client.search("test_collection", query, top_k=10)
    latencies.append((time.time() - start) * 1000)

print(f"Query latency p50: {np.percentile(latencies, 50):.2f}ms")
print(f"Query latency p95: {np.percentile(latencies, 95):.2f}ms")
----

== Common Pitfalls

=== Pitfall 1: Wrong Engine for Workload

**Problem:** Using SST for analytics queries results in high memory usage and slow aggregations.

**Solution:** Use VIPER or NOVA for analytics. SST is optimized for point queries and updates, not full-table scans.

**How to detect:**
[source,bash]
----
# High memory usage with analytics queries
curl http://localhost:5678/metrics | grep memory_usage_mb
# If >10GB for <1M vectors, wrong engine
----

=== Pitfall 2: Incorrect Row Group Size

**Problem:** VIPER with 1M vector row groups causes excessive memory usage.

**Solution:** Use 50K-250K vectors per row group depending on query selectivity.

**How to fix:**
[source,toml]
----
[storage.viper_config]
row_group_size = 100000  # Start with 100K, tune based on metrics
----

=== Pitfall 3: Under-Provisioned Memtable

**Problem:** SST with 16MB memtable flushes too frequently, causing write stalls.

**Solution:** Increase memtable size based on write rate.

**How to calculate:**
[source,bash]
----
# Target: Flush every 30-60 seconds
# If write rate = 50K vec/sec, vector size = 768*4 bytes = 3KB
# Memtable size = 50K * 3KB * 45 seconds = ~6.75GB

# Set in config:
max_memtable_size_mb = 6912  # ~6.75GB
----

=== Pitfall 4: Disabled Bloom Filters

**Problem:** VIPER queries scan all row groups without bloom filters.

**Solution:** Always enable bloom filters for filterable metadata fields.

**How to enable:**
[source,toml]
----
[storage.viper_config]
enable_bloom_filters = true
bloom_filter_columns = ["metadata.category", "metadata.timestamp"]
----

=== Pitfall 5: Testing in Debug Mode

**Problem:** Benchmarks in debug mode show 10-100x slower performance.

**Solution:** Always benchmark with `--release` flag.

**Correct approach:**
[source,bash]
----
# Wrong: cargo run --bin proximadb-bench
# Right:
cargo run --release --bin proximadb-bench
----

== Monitoring and Metrics

=== Key Metrics Per Engine

**SST Engine:**
[source,bash]
----
curl http://localhost:5678/metrics | grep sst_

# Important metrics:
# - sst_write_throughput_vectors_per_sec (target: 150K+)

----

**VIPER Engine:**
[source,bash]
----
curl http://localhost:5678/metrics | grep viper_

# Important metrics:
# - viper_row_groups_scanned_per_query (target: <10% of total)
# - viper_compression_ratio (target: 3-10x)
# - viper_query_latency_ms_p95 (target: <100ms)
----

**RAPTOR Engine:**
[source,bash]
----
curl http://localhost:5678/metrics | grep raptor_

# Important metrics:
# - raptor_row_group_utilization (target: >80%)
# - raptor_workload_adaptation_frequency (monitor stability)
----

----

# Query latency above threshold
query_latency_p95_max_ms = 50         # 50ms p95

# Memory usage above threshold
memory_usage_max_gb = 32              # 32GB
----
