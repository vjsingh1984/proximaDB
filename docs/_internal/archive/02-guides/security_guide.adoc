[.lead]
How to configure authentication, authorization, and security features in ProximaDB.

== When to Use This Guide

Use this guide when deploying ProximaDB in production environments that require secure access control. This guide covers authentication methods (JWT, API keys, SSO, mTLS), role-based access control (RBAC), audit logging, TLS encryption, and HTTP security middleware (CORS, rate limiting). If you're running ProximaDB in a development environment without security requirements, you can skip this guide.

== Prerequisites

* ProximaDB 0.1.4 or later installed
* Access to `config/config.toml` for configuration
* For production deployments:
  - TLS certificates (server cert, key, and CA cert)
  - SSO provider credentials (AWS IAM, Azure AD, etc.)
  - Secret management system for JWT secrets
* Basic understanding of authentication concepts (JWT, API keys, OAuth)

== Enabling Security

=== Step 1: Enable Security Mode

Edit `config/config.toml`:

[source,toml]
----
[security]
enabled = true
mode = "production"  # Use "development" for local testing only
----

WARNING: Never use `mode = "development"` in production. Development mode disables critical security features.

=== Step 2: Choose Authentication Methods

Enable at least one authentication method:

[source,toml]
----
[security.authentication]
methods = ["jwt", "api_key"]         # Choose methods for your use case
require_authentication = true        # Enforce authentication on all endpoints
default_session_timeout_minutes = 480  # 8 hours
----

Available methods:
* `jwt`: JSON Web Tokens for stateless authentication
* `api_key`: API keys for service-to-service authentication
* `sso`: Single Sign-On for enterprise environments
* `mtls`: Mutual TLS for certificate-based authentication

== Configuring Authentication Methods

=== API Key Authentication

**Step 1: Enable API key authentication**

[source,toml]
----
[security.authentication]
methods = ["api_key"]

[security.api_keys]
# API keys are defined here or managed via API
enabled = true
----

**Step 2: Generate API keys**

Use the admin API to generate keys:

[source,bash]
----
# Generate a new API key
curl -X POST http://localhost:5678/admin/api-keys \
  -H "Authorization: Bearer ${ADMIN_JWT}" \
  -d '{
    "name": "production-service",
    "permissions": ["read", "write"],
    "expires_at": "2026-12-31T23:59:59Z"
  }'

# Response:
# {
#   "api_key": "pxdb_abc123...",
#   "key_id": "key_123",
#   "name": "production-service"
# }
----

**Step 3: Use API keys in requests**

[source,bash]
----
# Include API key in Authorization header
curl -X POST http://localhost:5678/v1/collections/my-collection/search \
  -H "Authorization: Api-Key pxdb_abc123..." \
  -H "Content-Type: application/json" \
  -d '{"query_vector": [0.1, 0.2, ...], "top_k": 10}'
----

=== JWT Authentication

**Step 1: Configure JWT settings**

[source,toml]
----
[security.jwt]
enabled = true
secret = "${PROXIMADB_JWT_SECRET}"   # Load from environment variable
access_token_expiration_minutes = 15
refresh_token_expiration_days = 7
issuer = "proximadb-production"
audience = "proximadb-clients"
----

**Step 2: Set JWT secret environment variable**

[source,bash]
----
# Generate a secure random secret (256-bit)
export PROXIMADB_JWT_SECRET=$(openssl rand -base64 32)

# Add to systemd service or docker-compose.yml
----

**Step 3: Obtain JWT tokens**

[source,bash]
----
# Login to get tokens
curl -X POST http://localhost:5678/auth/login \
  -H "Content-Type: application/json" \
  -d '{
    "username": "user@example.com",
    "password": "secure-password"
  }'

# Response:
# {
#   "access_token": "eyJhbGciOiJIUzI1NiIs...",
#   "refresh_token": "eyJhbGciOiJIUzI1NiIs...",
#   "expires_in": 900
# }
----

**Step 4: Use JWT in requests**

[source,bash]
----
# Include JWT in Authorization header
curl -X POST http://localhost:5678/v1/collections/my-collection/search \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIs..." \
  -H "Content-Type: application/json" \
  -d '{"query_vector": [0.1, 0.2, ...], "top_k": 10}'
----

**Step 5: Refresh expired tokens**

[source,bash]
----
# Use refresh token to get new access token
curl -X POST http://localhost:5678/auth/refresh \
  -H "Content-Type: application/json" \
  -d '{"refresh_token": "eyJhbGciOiJIUzI1NiIs..."}'
----

=== SSO Authentication

**Step 1: Configure SSO providers**

[source,toml]
----
[security.sso]
enabled = true
providers = ["aws_iam", "azure_ad"]
token_cache_ttl_minutes = 5
----

**Step 2: Configure provider-specific settings**

For AWS IAM:
[source,toml]
----
[security.sso.aws_iam]
region = "us-west-2"
role_arn = "arn:aws:iam::123456789:role/ProximaDBAccess"
----

For Azure AD:
[source,toml]
----
[security.sso.azure_ad]
tenant_id = "${AZURE_TENANT_ID}"
client_id = "${AZURE_CLIENT_ID}"
client_secret = "${AZURE_CLIENT_SECRET}"
----

**Step 3: Authenticate with SSO**

[source,bash]
----
# Get SSO token from your provider
AWS_TOKEN=$(aws sts get-session-token --duration-seconds 3600 --query 'Credentials.SessionToken' --output text)

# Use SSO token with ProximaDB
curl -X POST http://localhost:5678/v1/collections/my-collection/search \
  -H "Authorization: Bearer ${AWS_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{"query_vector": [0.1, 0.2, ...], "top_k": 10}'
----

=== Mutual TLS (mTLS)

**Step 1: Generate client certificates**

[source,bash]
----
# Generate client key and CSR
openssl req -new -newkey rsa:2048 -nodes \
  -keyout client.key -out client.csr \
  -subj "/CN=proximadb-client"

# Sign with CA
openssl x509 -req -in client.csr -CA ca.crt -CAkey ca.key \
  -CAcreateserial -out client.crt -days 365
----

**Step 2: Configure mTLS**

[source,toml]
----
[security.tls]
enabled = true
require_client_certificates = true
cert_file = "/etc/proximadb/tls/server.crt"
key_file = "/etc/proximadb/tls/server.key"
ca_file = "/etc/proximadb/tls/ca.crt"

[security.authentication]
methods = ["mtls"]
----

**Step 3: Connect with client certificate**

[source,bash]
----
# Use client certificate in requests
curl -X POST https://localhost:5678/v1/collections/my-collection/search \
  --cert client.crt --key client.key --cacert ca.crt \
  -H "Content-Type: application/json" \
  -d '{"query_vector": [0.1, 0.2, ...], "top_k": 10}'
----

== Configuring Authorization (RBAC)

=== Step 1: Enable RBAC

[source,toml]
----
[security.rbac]
enabled = true
enable_field_level_permissions = true
enable_audit_logging = true
default_deny = true  # Deny by default, explicitly grant permissions
----

=== Step 2: Define Roles

Create roles with specific permissions:

[source,bash]
----
# Create a read-only role
curl -X POST http://localhost:5678/admin/roles \
  -H "Authorization: Bearer ${ADMIN_JWT}" \
  -d '{
    "name": "reader",
    "permissions": [
      "collections:read",
      "collections:search"
    ]
  }'

# Create a read-write role
curl -X POST http://localhost:5678/admin/roles \
  -H "Authorization: Bearer ${ADMIN_JWT}" \
  -d '{
    "name": "writer",
    "permissions": [
      "collections:read",
      "collections:write",
      "collections:search",
      "vectors:insert",
      "vectors:update",
      "vectors:delete"
    ]
  }'

# Create an admin role
curl -X POST http://localhost:5678/admin/roles \
  -H "Authorization: Bearer ${ADMIN_JWT}" \
  -d '{
    "name": "admin",
    "permissions": ["*"]
  }'
----

=== Step 3: Assign Roles to Users

[source,bash]
----
# Assign role to user
curl -X POST http://localhost:5678/admin/users/user@example.com/roles \
  -H "Authorization: Bearer ${ADMIN_JWT}" \
  -d '{
    "role": "writer"
  }'
----

=== Step 4: Field-Level Permissions

Restrict access to specific metadata fields:

[source,bash]
----
# Create role with field restrictions
curl -X POST http://localhost:5678/admin/roles \
  -H "Authorization: Bearer ${ADMIN_JWT}" \
  -d '{
    "name": "limited-reader",
    "permissions": ["collections:read", "collections:search"],
    "field_restrictions": {
      "allowed_fields": ["id", "vector", "metadata.category"],
      "denied_fields": ["metadata.sensitive_data"]
    }
  }'
----

== Configuring Audit Logging

=== Step 1: Enable audit logging

[source,toml]
----
[security.audit]
enabled = true
storage_backend = "combined"          # Log to file and database
encryption_enabled = true
retention_days = 2555                 # ~7 years
enable_real_time_alerts = true
alert_webhook_url = "${PROXIMADB_SECURITY_WEBHOOK}"
----

=== Step 2: Configure storage backends

For file-based logging:
[source,toml]
----
[security.audit.file]
log_directory = "/var/log/proximadb/audit"
rotation_size_mb = 100
compression_enabled = true
----

For database logging:
[source,toml]
----
[security.audit.database]
# Audit logs stored in main metadata database
collection = "audit_logs"
----

=== Step 3: Query audit logs

[source,bash]
----
# Query recent audit events
curl -X GET http://localhost:5678/admin/audit-logs \
  -H "Authorization: Bearer ${ADMIN_JWT}" \
  -d '{
    "start_time": "2025-12-01T00:00:00Z",
    "end_time": "2025-12-22T23:59:59Z",
    "event_types": ["authentication", "authorization_failure"],
    "limit": 100
  }'
----

== Configuring TLS Encryption

=== Step 1: Obtain TLS certificates

[source,bash]
----
# Option 1: Self-signed certificates (development only)
openssl req -x509 -newkey rsa:4096 -nodes \
  -keyout server.key -out server.crt -days 365 \
  -subj "/CN=proximadb.example.com"

# Option 2: Let's Encrypt (production)
certbot certonly --standalone -d proximadb.example.com
----

=== Step 2: Configure TLS

[source,toml]
----
[security.tls]
enabled = true
cert_file = "/etc/letsencrypt/live/proximadb.example.com/fullchain.pem"
key_file = "/etc/letsencrypt/live/proximadb.example.com/privkey.pem"

# Optional: Require client certificates
require_client_certificates = false
# ca_file = "/etc/proximadb/tls/ca.crt"
----

=== Step 3: Verify TLS is enabled

[source,bash]
----
# Check TLS certificate
openssl s_client -connect localhost:5678 -servername proximadb.example.com

# Verify HTTPS works
curl -v https://localhost:5678/health
----

== Configuring HTTP Security Middleware

=== CORS Configuration

**Step 1: Configure allowed origins**

[source,toml]
----
[network.cors]
enabled = true
development_mode = false  # NEVER true in production
allowed_origins = [
  "https://app.example.com",
  "https://admin.example.com"
]
allowed_methods = ["GET", "POST", "PUT", "DELETE", "OPTIONS"]
allowed_headers = ["Content-Type", "Authorization", "Accept"]
max_age_secs = 3600
allow_credentials = false
----

**Step 2: Test CORS configuration**

[source,bash]
----
# Test preflight request
curl -X OPTIONS http://localhost:5678/v1/collections \
  -H "Origin: https://app.example.com" \
  -H "Access-Control-Request-Method: POST" \
  -v

# Should see Access-Control-Allow-Origin header in response
----

=== Rate Limiting

**Step 1: Configure rate limits**

[source,toml]
----
[network.rate_limit]
enabled = true
requests_per_minute = 1000            # Per IP address
burst_size = 100                      # Allow short bursts
by_ip = true
limit_health_endpoints = false        # Don't rate limit /health
global_requests_per_minute = 10000    # Global limit across all IPs
----

**Step 2: Test rate limiting**

[source,bash]
----
# Send requests rapidly
for i in {1..1100}; do
  curl -X GET http://localhost:5678/v1/collections &
done
wait

# After 1000 requests, should see 429 Too Many Requests
----

=== Request Timeouts

**Step 1: Configure timeouts**

[source,toml]
----
[network.timeout]
enabled = true
request_timeout_secs = 30             # Standard requests
streaming_timeout_secs = 60           # Streaming operations
health_timeout_secs = 5               # Health check endpoints
----

For bulk operations, use longer timeouts:
[source,toml]
----
request_timeout_secs = 300            # 5 minutes for large imports
streaming_timeout_secs = 600          # 10 minutes for exports
----

== Common Pitfalls

=== Pitfall 1: JWT Secret in Config File

**Problem:** Hardcoding JWT secret in `config.toml` exposes it in version control.

**Solution:** Use environment variables:

[source,toml]
----
# Wrong:
secret = "my-hardcoded-secret-123"

# Right:
secret = "${PROXIMADB_JWT_SECRET}"
----

=== Pitfall 2: Development Mode in Production

**Problem:** `development_mode = true` allows any origin for CORS, enabling CSRF attacks.

**Solution:** Always use explicit origin whitelist in production:

[source,toml]
----
[network.cors]
development_mode = false  # NEVER true in production
allowed_origins = ["https://app.example.com"]
----

=== Pitfall 3: Disabled Rate Limiting

**Problem:** No rate limiting allows DoS attacks.

**Solution:** Always enable rate limiting with appropriate thresholds:

[source,toml]
----
[network.rate_limit]
enabled = true  # Always enabled in production
requests_per_minute = 1000
----

=== Pitfall 4: Weak API Keys

**Problem:** Short or predictable API keys are vulnerable to brute force.

**Solution:** Use cryptographically secure key generation (ProximaDB does this automatically):

[source,bash]
----
# ProximaDB generates keys with:
# - 32+ bytes of entropy
# - Prefix (pxdb_) for identification
# - Secure random generation
----

=== Pitfall 5: Missing Audit Logs

**Problem:** Security incidents without audit logs are impossible to investigate.

**Solution:** Always enable audit logging in production:

[source,toml]
----
[security.audit]
enabled = true
retention_days = 2555  # 7 years for compliance
----

== Security Checklist for Production

Before deploying to production, verify:

- [ ] `security.enabled = true` and `mode = "production"`
- [ ] At least one authentication method configured
- [ ] JWT secret loaded from environment variable (not hardcoded)
- [ ] TLS enabled with valid certificates
- [ ] CORS configured with explicit origin whitelist
- [ ] Rate limiting enabled with appropriate thresholds
- [ ] Request timeouts configured
- [ ] RBAC enabled with appropriate roles
- [ ] Audit logging enabled with adequate retention
- [ ] `development_mode = false` for all middleware
- [ ] API keys rotated regularly
- [ ] Client certificates managed securely (for mTLS)

== Monitoring Security

=== Key Security Metrics

[source,bash]
----
# Monitor authentication failures
curl http://localhost:5678/metrics | grep auth_failures_total

# Monitor rate limit hits
curl http://localhost:5678/metrics | grep rate_limit_exceeded_total

# Monitor active sessions
curl http://localhost:5678/metrics | grep active_sessions
----

=== Setting Up Security Alerts

Configure alerts for security events:

[source,toml]
----
[security.audit]
enable_real_time_alerts = true
alert_webhook_url = "https://alerts.example.com/webhook"

[security.audit.alert_rules]
# Alert on multiple failed logins
failed_login_threshold = 5
failed_login_window_minutes = 10

# Alert on privilege escalation attempts
alert_on_authorization_failures = true
----
