== Running Benchmarks

=== Quick Start

[source,bash]
----
# Run all benchmarks
cargo bench

# Run specific benchmark
cargo bench --bench bench_04_storage_unified

# Run with clean output (recommended)
cargo bench 2>&1 | grep -E "(test|time:|Benchmarking)"

# Run with full debug logging
RUST_LOG=debug cargo bench --bench bench_04_storage_unified
----

== Benchmark Output

=== Understanding Console Output

**Typical output format**:

[source,text]
----
test sst_search_10k ... bench:   5,320,000 ns/iter (+/- 450,000)
----

This means:
- **Test name**: sst_search_10k
- **Average time**: 5.32 milliseconds
- **Variance**: ± 450 microseconds

=== Clean Console Output

To reduce verbose logging in benchmarks:

[source,bash]
----
# Run without debug output (clean results)
cargo bench

# If you see too much output, filter it
cargo bench 2>&1 | grep -E "(test|Benchmarking|time:)"
----

=== Detailed Logging (When Needed)

Enable detailed logging only when debugging benchmark issues:

[source,bash]
----
# Enable debug logs for all modules
RUST_LOG=debug cargo bench --bench bench_04_storage_unified

# Enable debug logs for specific module
RUST_LOG=proximadb::storage::engines=debug cargo bench

# Save debug output to file
RUST_LOG=debug cargo bench 2>&1 | tee benchmark_debug.log
----

== Interpreting Results

=== Search Performance Metrics

**Score vs Similarity**:
- **Score**: Distance from query (0.0 = exact match, higher = less similar)
- **Similarity**: Computed similarity (higher = more similar)
- **Distance 0.0**: Perfect vector match

Example results:
[source,text]
----
score=0.000000, similarity=1.000000  → Perfect match
score=0.044359, similarity=0.955641  → Very similar
score=1.523456, similarity=0.476544  → Moderately similar
----

=== Compression Performance

**Comparing compression algorithms**:

[source,text]
----
SST with no compression:  5.97ms
SST with LZ4:            5.34ms  (-11% faster, saves disk space)
SST with Zstd:           6.12ms  (+2% slower, best compression)
SST with Snappy:         5.45ms  (-9% faster, good balance)
----

**Recommendation**: Use LZ4 for SST engine in production.

=== Throughput vs Latency

**Insert throughput** (vectors/second):
[source,text]
----
HELIX:  305,719/s  (highest throughput)
VIPER:  303,384/s
SST:    284,933/s
----

**Search latency** (milliseconds):
[source,text]
----
SST:    5.32ms  (fastest search)
HELIX:  13.2ms
VIPER:  89.5ms
----

**Trade-off**: SST optimizes for search speed, HELIX for insert throughput.

== Common Benchmark Scenarios

=== Compare Storage Engines

[source,bash]
----
# Run storage engine benchmarks
cargo bench --bench bench_04_storage_unified

# Results will show:
# - Insert throughput for each engine
# - Search latency for each engine
# - Disk usage for each engine
# - Compression ratios
----

**Expected output** (10K vectors, 128 dimensions):
[source,text]
----
SST insert:    ~285K/s,  search: 5.3ms,  disk: 102MB
HELIX insert:  ~306K/s,  search: 13.2ms, disk: 46MB
VIPER insert:  ~303K/s,  search: 89.5ms, disk: 46MB
----

=== Test Compression Impact

[source,bash]
----
# Benchmark tests multiple compression algorithms
cargo bench --bench bench_15_encoding_strategies

# Compare results to choose optimal compression
----

**Decision matrix**:
- **Write-heavy workload**: LZ4 or no compression
- **Storage-constrained**: Zstd (best ratio, slower)
- **Balanced**: Snappy or LZ4

=== Graph Performance Testing

[source,bash]
----
# Test graph operations
cargo bench --bench bench_14_graph_operations

# Test engine comparison
cargo bench --bench bench_17_graph_engines

# Generate CSV report
cargo bench --bench graph_engine_reporter
cat target/graph_benchmark_report_latest.csv
----

**Key metrics to watch**:
- Node insertion throughput (K elem/s)
- Edge insertion throughput (K elem/s)
- Traversal latency (BFS/DFS in microseconds)
- Shortest path latency (Dijkstra/A*)

== Troubleshooting Slow Benchmarks

=== Benchmarks Taking Too Long

[source,bash]
----
# Run fewer samples (faster, less precise)
cargo bench -- --sample-size 10

# Run with shorter measurement time
cargo bench -- --measurement-time 5

# Run specific test only
cargo bench --bench bench_04_storage_unified -- sst_search
----

=== Inconsistent Results

**Check system load**:
[source,bash]
----
# Ensure system is idle
top
htop

# Close other applications
# Disable CPU throttling (if applicable)
----

**Run multiple times**:
[source,bash]
----
# Run benchmark 3 times, compare results
for i in 1 2 3; do
  cargo bench --bench bench_04_storage_unified 2>&1 | grep "test.*bench"
done
----

=== Memory Issues During Benchmarks

[source,bash]
----
# Monitor memory usage
watch -n 1 'ps aux | grep bench | grep -v grep'

# Reduce dataset size in benchmark
# (edit benchmark file if needed)

# Run with fewer parallel threads
cargo bench -- --test-threads=1
----

== Comparing Performance Changes

=== Before/After Comparison

[source,bash]
----
# Run baseline benchmarks
git checkout main
cargo bench --bench bench_04_storage_unified > baseline.txt

# Run with changes
git checkout feature-branch
cargo bench --bench bench_04_storage_unified > changes.txt

# Compare
diff baseline.txt changes.txt
----

=== Using Criterion's Built-in Comparison

Criterion automatically compares against previous runs:

[source,text]
----
time:   [5.320 ms 5.450 ms 5.580 ms]
change: [-12.5% -10.2% -8.1%] (p = 0.00 < 0.05)
Performance has improved.
----

This means:
- Current run: 5.45ms average
- Previous run was ~10% slower
- Change is statistically significant (p < 0.05)

== Best Practices

=== Running Reliable Benchmarks

1. **Close unnecessary applications**
2. **Ensure system is idle** (no background tasks)
3. **Run on dedicated hardware** (if possible)
4. **Use release builds** (benchmarks automatically use optimized builds)
5. **Run multiple times** to confirm consistency
6. **Compare against baseline** before claiming improvements

=== When to Use Debug Logging

**Use debug logging when**:
- Benchmark fails unexpectedly
- Results don't match expectations
- Investigating specific component behavior

**Don't use debug logging when**:
- Comparing performance numbers (adds overhead)
- Running production benchmarks
- Generating reports for documentation

=== Benchmark Hygiene

[source,bash]
----
# Clean old benchmark data
cargo clean

# Remove old reports
rm target/*.csv

# Rebuild and benchmark fresh
cargo bench

# Keep benchmark runs reproducible
# - Document system specs
# - Record Git commit hash
# - Note any configuration changes
----

== Integration with CI/CD

=== Running Benchmarks in CI

[source,yaml]
----
# GitHub Actions example
- name: Run benchmarks
  run: |
    cargo bench --no-fail-fast 2>&1 | tee bench_output.txt

- name: Check for regressions
  run: |
    # Parse output, fail if regression > 20%
    ./scripts/check_benchmark_regression.sh bench_output.txt
----

=== Tracking Performance Over Time

[source,bash]
----
# Save benchmark results with timestamp
DATE=$(date +%Y%m%d-%H%M%S)
cargo bench 2>&1 > benchmarks/results-$DATE.txt

# Store CSV reports
cp target/*.csv benchmarks/csv/

# Track in Git (optional)
git add benchmarks/
git commit -m "Benchmark results for commit $(git rev-parse --short HEAD)"
----
