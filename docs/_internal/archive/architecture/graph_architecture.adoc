= Graph Database Architecture
:toc: left
:toclevels: 3
:icons: font

[abstract]
Design rationale and architectural decisions for ProximaDB's native graph database with multi-engine support, distributed operations, and hybrid vector-graph capabilities.

== Executive Summary

ProximaDB implements a native graph database with three specialized engines (ORION, PULSAR, QUASAR) providing in-memory, distributed, and hybrid vector-graph capabilities. This document explains WHY we made specific architectural decisions and the trade-offs involved.

**Key Architectural Decisions**:
- CSR (Compressed Sparse Row) format for memory efficiency
- Arc-based zero-copy memory sharing
- Multi-graph support with isolated storage
- Unified persistence layer with WAL
- Service separation (Collection vs Operations)

== Design Philosophy

=== The Native Graph Approach

**Industry Trend**: Vector databases adding graph features as afterthoughts, or graph databases adding vector search without native integration.

**ProximaDB Solution**: Native graph database with first-class vector integration from the ground up.

== Engine Architecture Decisions

=== ORION: In-Memory Graph Engine

**Design Goal**: Sub-microsecond node lookup with minimal memory overhead.

**Key Decision 1: CSR Format**

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
graph TB
    subgraph "CSR ADVANTAGES"
        A[Compact Memory Layout] --> B[2x-4x Better<br/>than Adjacency Lists]
        C[Cache-Friendly Access] --> D[Better CPU<br/>Cache Utilization]
        E[Zero-Copy Traversal] --> F[No Deserialization<br/>Overhead]
    end

    subgraph "CSR TRADE-OFFS"
        G[Dynamic Updates Costly] --> H[Requires<br/>Rebuilding]
        I[Write Amplification] --> J[LSM + WAL<br/>Solution]
    end

    style A fill:#4caf50,stroke:#2e7d32,stroke-width:2px,color:#000
    style C fill:#4caf50,stroke:#2e7d32,stroke-width:2px,color:#000
    style E fill:#4caf50,stroke:#2e7d32,stroke-width:2px,color:#000
    style G fill:#ff9800,stroke:#f57c00,stroke-width:2px,color:#000
    style I fill:#ff9800,stroke:#f57c00,stroke-width:2px,color:#000
----

**Why CSR Over Alternatives**:

| Format | Memory Efficiency | Traversal Speed | Update Cost | Decision |
|--------|------------------|-----------------|-------------|----------|
| **Adjacency List** | Poor (pointers) | Fast (O(1)) | Low | Rejected: Memory overhead |
| **Edge List** | Good | Slow (O(E)) | Low | Rejected: Traversal performance |
| **CSR** | Excellent | Fast (O(1)) | High | **Chosen**: Best read performance |
| **Adjacency Matrix** | Very Poor | Very Fast | Very Low | Rejected: Memory explosion |

**Trade-off Decision**: Optimize for read-heavy graph traversals (99% of graph workloads) at the cost of write complexity.

**Key Decision 2: Arc-Based Memory Sharing**

**Problem**: Graph operations return nodes/edges that may be accessed by multiple concurrent queries.

**Alternatives Considered**:
1. **Clone Data**: Simple but expensive (2-3x memory overhead)
2. **Reference Counting (Rc)**: Not thread-safe
3. **Arc (Atomic Reference Counting)**: Thread-safe, zero-copy

**Chosen Solution**: Arc-based memory pool

[source,rust]
----
// WHY Arc: Zero-copy sharing across threads
pub struct OrionGraphEngine {
    // Memory pool: Arc allows multiple readers without cloning
    node_pool: DashMap<NodeId, Arc<Node>>,
    edge_pool: DashMap<EdgeId, Arc<Edge>>,

    // CSR structure: Points into Arc pool (no duplication)
    csr_offsets: Vec<usize>,
    csr_edges: Vec<Arc<Edge>>,
}

// Zero-copy return: Cloning Arc is cheap (just atomic increment)
pub async fn get_node(&self, id: &NodeId) -> Option<Arc<Node>> {
    self.node_pool.get(id).map(|r| Arc::clone(r.value()))
}
----

**Trade-off Analysis**:
- Memory overhead: 16 bytes per Arc (vs 100s-1000s bytes for cloned data)
- CPU overhead: Single atomic increment (vs full data copy)
- Concurrency: Lock-free reads (vs mutex contention with Rc)

**Result**: 10-100x better memory efficiency than cloning, with thread-safe concurrent access.

**Key Decision 3: WAL for Durability**

**Challenge**: CSR format is read-optimized but write-expensive.

**Solution**: LSM-style architecture with Write-Ahead Log

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
sequenceDiagram
    participant Client
    participant ORION
    participant WAL
    participant CSR

    Client->>ORION: create_node(node)
    ORION->>WAL: append_entry(node)
    Note over WAL: AWAIT write completion<br/>(durability guarantee)
    WAL-->>ORION: Write confirmed
    ORION->>CSR: update_memory(node)
    ORION-->>Client: Success

    Note over ORION,CSR: Background: Periodic CSR snapshot
----

**Why This Design**:
- **Durability First**: WAL write completes before acknowledgment (ACID compliance)
- **Memory Performance**: CSR updated in-memory after WAL (fast reads)
- **Recovery**: WAL replay reconstructs CSR after crashes

**Historical Context - Critical Bug Fixed**:

Previously, ORION used fire-and-forget `tokio::spawn` for WAL writes:

[source,rust]
----
// ❌ OLD (BROKEN): Fire-and-forget WAL write
tokio::spawn(async move {
    wal.append(entry).await;  // Not awaited by caller!
});
return Ok(());  // Returns BEFORE write completes!
----

**Problem**: Operations returned success before WAL writes completed, causing data loss on crashes.

**Solution**: Made `GraphEngine` trait async and explicitly await WAL operations:

[source,rust]
----
// ✅ NEW (CORRECT): Await WAL write before returning
async fn create_node(&self, node: Node) -> Result<Arc<Node>> {
    // Write to WAL FIRST
    self.wal.append_node(&node).await?;  // AWAIT completion

    // Only update memory after WAL confirms
    self.node_pool.insert(node.id.clone(), Arc::new(node.clone()));

    Ok(Arc::new(node))
}
----

**Result**: Full durability guarantee with minimal performance impact (WAL writes batched automatically).

=== PULSAR: Distributed Graph Engine

**Design Goal**: Scale graph operations across multiple nodes with data sharding.

**Key Decision 1: Content-Based Sharding**

**Trade-off Matrix**:

| Strategy | Load Balance | Locality | Cross-Shard Edges | Decision |
|----------|--------------|----------|-------------------|----------|
| **Range-Based** | Poor (hotspots) | Excellent | Rare | Rejected |
| **Random** | Excellent | Poor | Common | Rejected |
| **Content-Based** | Good | Good | Moderate | **Chosen** |

**Key Decision 2: Cross-Shard Edge Management**

**Problem**: Edges may connect nodes on different shards.

**Solution**: Distributed edge index with local caching

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
flowchart LR

    B -->|Yes| C[Local Storage<br/>Fast access]
    B -->|No| D[Distributed Index<br/>+ Local Cache]

----

**Design Rationale**:
- Most edges connect nearby nodes (high locality)
- Cross-shard edges cached after first access
- Acceptable network overhead for distributed queries

**Trade-off**: Added complexity for automatic tier management in exchange for 10-100x cost reduction without sacrificing performance for hot data.

=== Service Separation Rationale

**Design Decision**: Split graph functionality into two services.

    style I fill:#4caf50,stroke:#2e7d32,stroke-width:2px,color:#000
----

**Why Separate Services?**

**Reasons**:
1. **Consistency with Vector Architecture**: Mirrors CollectionService/VectorOperationsService pattern
2. **Clear Separation of Concerns**: Metadata management vs data operations
3. **Independent Scaling**: Scale operations independently of metadata
4. **Better Testing**: Isolated unit tests for each responsibility

**Alternative Considered**: Single GraphService

**Rejected Because**:
- Violates single responsibility principle
- Harder to maintain (1500+ line service class)
- Inconsistent with rest of ProximaDB architecture
- Poor code organization

**Result**: Clean separation enabling independent evolution of collection management and graph operations.

== Persistence Architecture

=== Multi-Graph Storage Model

**Design Decision**: Each graph has independent storage path.

    D --> G[/graphs/analytics/data/<br/>snapshots/, wal/, indexes/]

    style B fill:#2196f3,stroke:#1565c0,stroke-width:2px,color:#000

    style D fill:#2196f3,stroke:#1565c0,stroke-width:2px,color:#000

**Why Multi-Graph Storage?**

**Benefits**:
- **Isolation**: Graph failures don't affect others
- **Independent Backup**: Snapshot/restore per graph
- **Flexible Storage**: Different graphs on different backends (s3, azure, gcs)
- **Security**: Per-graph access control

**Trade-off**: More complex path management vs simpler single-namespace approach.

**Decision**: Benefits outweigh complexity for enterprise deployments.

=== WAL Path Resolution - Simplified Architecture

**Historical Problem**: Complex WAL path resolution with OptimizedWalPathResolver and assignment service led to bugs where WAL files were written to wrong locations.

**Current Solution**: Direct storage path in collection metadata

[source,rust]
----
// ✅ CURRENT (SIMPLE): Direct path storage
pub struct GraphMetadata {
    pub graph_id: String,
    pub storage_path: String,  // e.g., "s3://bucket/graphs/graph_001"
    // ...
}

impl GraphEngine {
    async fn resolve_wal_path(&self, graph_id: &str) -> Result<String> {
        // Simple: Just append /wal/ to storage path
        let metadata = self.get_graph_metadata(graph_id).await?;
        Ok(format!("{}/wal", metadata.storage_path))
    }
}
----

**Why This Design**:
- **Simplicity**: No complex resolution logic
- **Correctness**: Path stored where it's used (collection metadata)
- **Debuggability**: Easy to trace WAL location
- **No Hidden State**: No separate assignment service or path resolver

**Result**: WAL path bugs eliminated through architectural simplification.

**Algorithm Selection Matrix**:

| Use Case | Algorithm | Ratio | Speed | Decision Rationale |
|----------|-----------|-------|-------|-------------------|
| **ORION (real-time)** | LZ4 | 2-3x | 500MB/s | Minimize latency |
| **PULSAR (distributed)** | Zstd | 3-5x | 300MB/s | Balance bandwidth |
| **QUASAR (cold tier)** | Brotli | 4-6x | 50MB/s | Maximize savings |

**Why Configurable Compression?**

**Rationale**: Different deployment contexts have different priorities:
- Cloud deployments: Maximize compression (reduce bandwidth costs)
- On-premise: Faster compression (CPU is cheap, bandwidth is not)
- Real-time: Minimal compression overhead

**Trade-off**: More configuration complexity for deployment-specific optimization.

**Why Both?**

**Native Operations**:
- Lower latency (no SQL parsing)
- Type-safe API (compile-time checks)
- Better for simple graph traversals

**SQL Queries**:
- Complex multi-way joins
- Hybrid vector + graph queries
- Analytical workloads
- SKS (Semantic Knowledge Store) functions

**Trade-off**: Dual query paths increase complexity but provide flexibility for different use cases.

== Future Architecture Evolution

=== Planned Enhancements

**1. Temporal Graph Support**

**Goal**: Time-traveling queries and versioned graph states.

**Design Challenge**: How to efficiently store and query historical graph snapshots?

**Proposed Solution**:
- Delta-encoded snapshots (only store changes)
- Temporal index for time-based queries
- Configurable retention policies

**Trade-off**: 2-3x storage overhead for complete history vs snapshots-only.

**2. Graph Algorithms Library**

**Goal**: Built-in algorithms (PageRank, community detection, etc.)

**Design Challenge**: Balance generality vs performance.

**Proposed Solution**:
- Core algorithms in engine (optimized)
- Extension API for custom algorithms
- GPU acceleration for supported algorithms

**Trade-off**: More complex engine vs better out-of-box functionality.

**3. Cross-Graph Queries**

**Goal**: Join data across multiple graphs.

**Design Challenge**: Maintain isolation while enabling joins.

**Proposed Solution**:
- Explicit graph references in queries
- Permission-based access control
- Federated query execution

**Trade-off**: Added query complexity for multi-graph flexibility.

=== Design Principles for Future Work

1. **Backward Compatibility**: New features must not break existing graphs
2. **Performance First**: No feature if it degrades core operations
3. **Composability**: Features should combine naturally
4. **Measurable Benefit**: All enhancements must show measured improvement
