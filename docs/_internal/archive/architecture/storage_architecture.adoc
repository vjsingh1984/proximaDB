Design rationale and architectural decisions for ProximaDB's multi-engine storage system.

== Executive Summary

ProximaDB uses a **portfolio architecture** rather than optimizing a single storage format. This document explains WHY we made this choice and the trade-offs involved.

**Key Architectural Decision**: 6 specialized engines instead of 1 universal format.

**Rationale**: No single storage layout optimizes for all workload patterns. Different applications need different trade-offs between:
- Write throughput vs read latency
- Memory usage vs compression ratio
- Random access vs sequential scan
- Real-time updates vs analytical queries

== Design Philosophy

== Unified Format Foundation

=== ProximaBlock: Common Building Block

**Design Decision**: All engines use ProximaBlock as the base format, then add engine-specific optimizations.

**Why**: Enables code reuse while allowing specialization.

**ProximaBlock Features** (automatic):
- Bloom filters for existence checks
- Column statistics (min/max/null counts)
- Range tracking for pruning
- Delete detection
- SIMD encoding selection

**Engine-Specific Layers**:
- SST: Adds three-stage filtering
- SWIFT: Adds hierarchical organization
- HELIX: Adds Hilbert curve clustering
- VIPER: Uses Parquet instead (different design path)

=== Why Not Pure Parquet?

**Question**: Why not use Apache Parquet for everything like competitors?

**Parquet Advantages**:
- Excellent compression (16-32x)
- Mature ecosystem
- Standard tooling

**Parquet Limitations for Vector Workloads**:
1. **No SIMD access to compressed data** - Must decompress first
2. **Row-group overhead** - Minimum 1MB chunks
3. **Write amplification** - Requires full rewrite on updates
4. **No bloom filters** - Must scan row groups

**ProximaDB Approach**:
- Use Parquet where it excels (VIPER analytics engine)
- Use ProximaBlock where SIMD and updates matter (SST, SWIFT, HELIX)

**Result**: Best of both worlds.

=== Design Trade-offs by Engine

==== SST: Real-Time OLTP

**Optimization Goal**: Balance write throughput and read latency.

**Key Design Decisions**:

1. **Three-Stage Filtering**
   - WHY: Avoid scanning irrelevant data
   - Trade-off: 10-15% write overhead for 95% query speedup
   - Alternative considered: Two-stage (bloom + exact)
   - Rejected because: Range maps eliminate another 70% of candidates

2. **1MB Block Size**
   - WHY: Balance I/O efficiency and granularity
   - Trade-off: Some internal fragmentation for better cache locality
   - Alternative considered: 256KB (Lance-style), 4MB (Parquet-style)
   - Chose 1MB: Sweet spot for NVMe I/O and CPU cache

3. **LZ4 Compression**
   - WHY: Compression actually improves query speed (11% faster)
   - Trade-off: Slightly lower compression ratio than Zstd
   - Alternative considered: No compression, Zstd
   - Chose LZ4: Decompression is faster than disk I/O

**Result**: 365ps query latency, 200K inserts/sec.

==== VIPER: Analytics Engine

**Optimization Goal**: Maximum compression for analytical workloads.

**Key Design Decisions**:

1. **Pure Parquet**
   - WHY: Best compression and column pruning
   - Trade-off: Write amplification on updates
   - Alternative considered: Custom columnar format
   - Chose Parquet: Standard format, excellent tools

2. **128K Row Groups**
   - WHY: Balance memory usage and compression ratio
   - Trade-off: Minimum 128K vectors per batch
   - Alternative considered: 64K (less memory), 256K (better compression)
   - Chose 128K: Good compression without excessive memory

3. **Zone Maps**
   - WHY: Prune entire row groups during queries
   - Trade-off: Additional metadata storage
   - Alternative considered: No zone maps
   - Chose zone maps: 70-90% I/O reduction

**Result**: 366ps query latency, 16-32x compression.

==== HELIX: Spatial Optimization

**Optimization Goal**: Preserve vector similarity in physical layout.

**Key Design Decisions**:

1. **Hilbert Curve Clustering**
   - WHY: Spatially similar vectors stored together
   - Trade-off: PCA overhead during indexing
   - Alternative considered: Random placement, K-means clustering
   - Chose Hilbert: Better cache locality than alternatives

2. **PCA Dimensionality Reduction**
   - WHY: High-dimensional Hilbert curves are expensive
   - Trade-off: Some information loss in clustering
   - Alternative considered: Full-dimensional Hilbert, random projection
   - Chose PCA: Best preservation of similarity structure

3. **LSM Structure**
   - WHY: Efficient updates while maintaining clustering
   - Trade-off: Background compaction overhead
   - Alternative considered: In-place updates, append-only
   - Chose LSM: Good write throughput with clustering

**Result**: 90-95% range query pruning, good locality.

==== SWIFT: Ultra-Low Latency

**Optimization Goal**: Sub-millisecond operations.

**Key Design Decisions**:

1. **Hierarchical Organization** (SuperBlock → DataBlock → Records)
   - WHY: Fast top-down traversal
   - Trade-off: Additional memory for hierarchy
   - Alternative considered: Flat structure
   - Chose hierarchy: Better organization for large collections

2. **Hardware-Adapted Encoding**
   - WHY: Match CPU capabilities (AVX512 vs AVX2 vs SSE)
   - Trade-off: More code paths to maintain
   - Alternative considered: One encoding for all hardware
   - Chose adaptive: 2-3x performance improvement

3. **Smaller Block Sizes**
   - WHY: Reduce latency for small queries
   - Trade-off: More metadata overhead
   - Alternative considered: Same 1MB as SST
   - Chose smaller: Better for low-latency goals

**Result**: 101μs flush, sub-1ms queries.

== Design Patterns

=== Composition Over Inheritance

**Pattern**: Engines compose ProximaBlock features rather than inheriting from a base class.

**Why**: Allows cherry-picking features without enforcing rigid hierarchy.

**Example**:
[source,rust]
----
// ✅ Composition (HELIX approach)
pub struct HelixBlockMetadata {
    pub proxima_metadata: ProximaBlockMetadata,  // Reuse all features
    pub hilbert_range: Option<(u64, u64)>,       // Add only what's unique
    pub pca_stats: Option<PCAStats>,
}

// ❌ Inheritance (rejected)
pub struct HelixBlock extends ProximaDataBlock {
    // Forces including ALL ProximaBlock features even if not needed
}
----

=== Automatic Feature Generation

**Pattern**: Metadata generated automatically during block construction, not manually by engines.

**Why**: Reduces code duplication and bugs.

**Features**:
- Bloom filters (95% query elimination)
- Min/max statistics (range pruning)
- Null counts (data quality)
- Delete detection (compaction hints)

**Example**:
[source,rust]
----
// Engine just creates block, gets features for free
let block = ProximaDataBlock::new(records, compression_config);

// All metadata already computed:
assert!(block.bloom_filter.is_some());
assert!(block.metadata.column_stats.len() > 0);
assert!(block.id_range.is_some());
----

=== Hardware-Aware Optimization

**Pattern**: Detect CPU capabilities and choose encoding strategy.

**Why**: Same workload performs differently on different hardware.

**Strategies**:
- AVX-512: 512-bit SIMD, 16 floats at once
- AVX2: 256-bit SIMD, 8 floats at once
- NEON (ARM): 128-bit SIMD, 4 floats at once
- Scalar: No SIMD, fallback

**Design Decision**: Pay runtime detection cost once at startup.
**Alternative Considered**: Compile-time only (rejected: less flexible deployment).

== Future Architecture Evolution

=== Planned Enhancements

==== 1. Adaptive Engine Switching

**Goal**: Automatically migrate collections between engines based on workload changes.

**Design Challenge**: How to migrate without downtime?

**Proposed Solution**:
1. Background copy to new engine
2. Dual-write during migration
3. Atomic swap when complete

**Trade-off**: Temporary 2x storage during migration.

==== 2. Hybrid Engine Composition

**Goal**: Use different engines for hot vs cold data in same collection.

**Design Challenge**: Maintain query consistency across engines.

**Proposed Solution**:
- Hot tier: SWIFT (fast access)
- Warm tier: SST (balanced)
- Cold tier: VIPER (compressed)

**Trade-off**: More complex query routing.

==== 3. Cloud-Native Tiering

**Goal**: Automatic movement between local/SSD/object storage.

**Design Challenge**: Maintain low latency for active data.

**Proposed Solution**:
- Local NVMe: Current working set
- SSD: Recently accessed
- S3/GCS/Azure: Long-term storage

**Trade-off**: More complex cache management.

=== Design Principles for Future Work

1. **Maintain Composability**: New engines should reuse ProximaBlock foundation
2. **Measure, Don't Guess**: All optimizations must show measured improvement
3. **Graceful Degradation**: Fallback paths for unsupported features
4. **Configuration Over Code**: Tunable via config, not source changes
