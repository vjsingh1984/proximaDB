**Contribution guide for developers** - How to build, test, and submit changes to ProximaDB.

== Getting Started

=== Prerequisites

- Rust 1.88+ (MSRV)
- Git
- Docker (optional, for integration tests)
- Python 3.8+ (for SDK development)

=== Fork and Clone

[source,bash]
----
# Fork on GitHub, then:
git clone https://github.com/YOUR_USERNAME/proximaDB.git
cd proximaDB
git remote add upstream https://github.com/proximadb/proximaDB.git
----

== Development Workflow

=== Build and Test

[source,bash]
----
# Fast check (no codegen)
cargo check

# Build (debug mode, fast compilation)
cargo build

# Run tests
cargo test

# Run with formatting and linting
cargo fmt && cargo clippy -- -D warnings && cargo test
----

=== Running the Server

[source,bash]
----
# Debug mode (fast compile, detailed logs)
RUST_LOG=info cargo run --bin proximadb-server

# Release mode (optimized)
cargo run --release --bin proximadb-server

# With custom config
cargo run --bin proximadb-server -- --config config/config.toml
----

=== Quick Test Commands

[source,bash]
----
# Run all tests
cargo test

# Run specific test
cargo test test_sst_insert

# Run unit tests only (fast)
cargo test --lib

# Run integration tests
cargo test --test integration

# Run with output
cargo test -- --nocapture

# Run single-threaded (for port conflicts)
cargo test -- --test-threads=1
----

== Making Changes

=== Create a Feature Branch

[source,bash]
----
git checkout -b feature/your-feature-name
# or
git checkout -b fix/bug-description
----

=== Code Style

**Follow Rust conventions**:
- Use `cargo fmt` for formatting
- Run `cargo clippy` for linting
- Follow existing code patterns
- Add doc comments for public APIs

**Error Handling**:
- Use `Result<T, Error>` for fallible operations
- Avoid `.unwrap()` and `.expect()` in production code
- Use `?` operator for error propagation

=== Adding Tests

**Unit tests** (in same file as code):
[source,rust]
----
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_my_feature() {
        // Test code
        assert_eq!(result, expected);
    }
}
----

**Integration tests** (in `tests/` directory):
[source,rust]
----
// tests/my_integration_test.rs
#[test]
fn test_end_to_end() {
    // Setup
    let db = setup_test_db();

    // Test
    let result = db.insert(...);

    // Assert
    assert!(result.is_ok());

    // Cleanup
    cleanup_test_db(db);
}
----

== Submitting Changes

=== Pre-Submission Checklist

- [ ] Code compiles: `cargo build`
- [ ] Tests pass: `cargo test`
- [ ] Formatting applied: `cargo fmt`
- [ ] No lint warnings: `cargo clippy -- -D warnings`
- [ ] Documentation added for new features
- [ ] Tests added for new features
- [ ] CHANGELOG.md updated (if applicable)

=== Commit Messages

Use clear, descriptive commit messages:

[source,text]
----
# Good examples
fix: Resolve WAL recovery path resolution issue
feat: Add support for Azure Blob Storage backend
docs: Update security configuration guide
test: Add integration tests for graph traversal

# Format
type: Brief description (50 chars max)

Detailed explanation if needed.
Can span multiple lines.

Closes #123
----

**Types**: `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `chore`

=== Create Pull Request

[source,bash]
----
# Push to your fork
git push origin feature/your-feature-name

# Create PR on GitHub
# Include:
# - Clear description of changes
# - Related issue numbers
# - Test results
# - Screenshots (if UI changes)
----

**PR Template**:
```markdown
## Description
Brief description of changes

## Related Issues
Closes #123

## Changes
- Added feature X
- Fixed bug Y
- Updated documentation

## Testing
- [ ] Unit tests pass
- [ ] Integration tests pass
- [ ] Manual testing completed

## Screenshots (if applicable)
```

== Development Areas

=== High-Impact Contributions

**Priority areas** (fastest way to have impact):
1. **AXIS index for SKS hybrid search** - Graph + vector unified queries
2. **Metadata filter parity** - Server + SDK consistent filtering
3. **Prometheus/observability** - Production monitoring improvements
4. **Python SDK enhancements** - Client library features
5. **Documentation** - Guides, examples, tutorials

=== Adding a Storage Engine

[source,rust]
----
// 1. Implement in src/storage/engines/impls/myengine/mod.rs
pub struct MyEngine {
    // State
}

impl UnifiedStorageEngine for MyEngine {
    // Implement required methods
}

// 2. Register in src/storage/engines/factory.rs
match engine_type {
    EngineType::MyEngine => {
        Box::new(MyEngine::new(config)?)
    }
    // ...

// 3. Add tests in tests/engines/my_engine_test.rs

    // Implementation
}

// 4. Add to router in src/network/rest/v1/handlers.rs or grpc service
----

== Testing

=== Test Organization

[cols="2,2,2"]
|===
|Location |Type |Command

|`src/**/mod.rs`
|Unit tests
|`cargo test --lib`

|`tests/*.rs`
|Integration tests
|`cargo test --test <name>`

|`benches/*.rs`
|Benchmarks
|`cargo bench`

|`clients/python/tests/`
|Python SDK tests
|`pytest clients/python/tests/`
|===

=== Debugging Tests

[source,bash]
----
# Enable logging
RUST_LOG=debug cargo test test_name -- --nocapture

# Run specific module tests
cargo test --lib storage::

# Run single-threaded (for debugging)
cargo test -- --test-threads=1 --nocapture

# List tests without running
cargo test -- --list
----

== Code Review Process

1. **Automated checks** run on PR (GitHub Actions)
2. **Maintainer review** (usually within 2-3 days)
3. **Feedback addressed** by contributor
4. **Final approval** and merge

**What reviewers look for**:
- Code quality and style
- Test coverage
- Documentation completeness
- Performance impact
- Breaking changes (requires discussion)

## Getting Help

**Questions about contributing**:
- GitHub Discussions: https://github.com/proximadb/proximaDB/discussions
- Open an issue: https://github.com/proximadb/proximaDB/issues

**Found a bug**:
1. Check existing issues first
2. Create new issue with:
   - Description of bug
   - Steps to reproduce
   - Expected vs actual behavior
   - Environment details (OS, Rust version, ProximaDB version)

**Feature requests**:
1. Open a discussion first to gauge interest
2. If approved, create issue with:
   - Use case description
   - Proposed solution
   - Alternative approaches considered

== Community Guidelines
