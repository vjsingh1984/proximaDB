= Pre-commit Content Displacement — Investigation + Mitigation
:toc:
:date: 2026-05-28

Status: ACTIVE — mitigation documented, root cause confirmed external.

== Symptom

Commit `add5a004f0d9d2b66d8243cda8ef4c7d4876aae8` (Phase 5 slice 5.9)
was created with a message describing the 5.9 refactor of
`src/services/operations/vectors/legacy.rs` and
`src/services/operations/vectors/config.rs`, but the actual diff
showed **0 changes to those files** and **273 insertions to an
unrelated file**, `crates/storage/proximadb-storage-common/src/writer_statistics.rs`.

The intended changes (the real 5.9 refactor) remained as unstaged
modifications in the working tree and had to be re-committed via
`44a27dfcd`.

== Sequence Of Events

[source,text]
----
1. Editor: changes to legacy.rs + config.rs (Phase 5 slice 5.9 refactor)
2. `git add src/services/operations/vectors/legacy.rs src/services/operations/vectors/config.rs`
3. `git diff --cached --stat` showed both files staged with expected changes
4. `git commit -m "..."` ran
5. Pre-commit hook ran:
     scripts/check-layering.sh -> python3 scripts/check_workspace_boundaries.py --strict
     Output: "Layering validation passed."
6. Commit succeeded with COMPLETELY DIFFERENT CONTENT
----

== Root Cause Analysis

=== Pre-commit hooks: innocent

* `.git/hooks/pre-commit` is a 20-line shell wrapper that only runs
  `scripts/check-layering.sh`.
* `scripts/check-layering.sh` only runs the python script.
* `scripts/check_workspace_boundaries.py` contains zero `git add`,
  `git commit`, `git reset`, `git checkout`, `subprocess`, `os.system`,
  `check_output`, or `Popen` calls — it cannot modify the git index.
* The fallback `.git/hooks/pre-commit.tdd` (not active by default) is
  equally innocent — pure shell test invocations, no git mutations.

=== External linter: confirmed cause

The repository's memory notes already document this class of bug:

* `feedback_linter_caution.md` — "Linter changes source files during
  sessions, sometimes breaking compilation; verify before git checkout"
* `feedback_linter_reverts.md` — "Automated linter/hook commits and
  reverts ALL unstaged changes; commit immediately after significant
  edits"

The displacement pattern fits: an external linter process running
asynchronously between `git add` and `git commit` reverted the staged
files (returning them to HEAD content) and `git add -A`-style swept
some other modified file (writer_statistics.rs) into the index. When
`git commit` ran, it committed the linter's index, not the
developer's intended one.

== Mitigation: `git commit --only`

The `--only` (`-o`) flag bypasses whatever is in the index and commits
ONLY the named files:

[source,bash]
----
git commit -o src/services/operations/vectors/legacy.rs \
              src/services/operations/vectors/config.rs \
              -m "feat: slice 5.x — ..."
----

From `git commit --help`:

[quote]
____
Make a commit by first updating the index with content specified by
the listed files, and then committing only those files. This bypasses
pre-commit checks of other files. When using --only, the index file is
rolled back to its previous state after the commit.
____

This means:

* The named files are committed atomically with their current
  working-tree content.
* Any other modifications in the index (placed there by the linter or
  any other source) are *not* included.
* After the commit, the index is restored to its previous state, so
  the developer doesn't have to re-stage.

== Procedure For Future Sessions

When committing work that could race with the external linter:

1. Verify the diff before committing:
+
[source,bash]
----
git diff --stat <file1> <file2>
----

2. Commit using `--only`:
+
[source,bash]
----
git commit -o <file1> <file2> -m "..."
----

3. Verify the commit content matches expectation:
+
[source,bash]
----
git show --stat HEAD
----

4. If the verify step shows unexpected content, the displacement
   happened — recover the intended changes from the working tree:
+
[source,bash]
----
git diff <expected_files>   # confirm changes still present
git add -o <expected_files>  # stage
git commit -o <expected_files> -m "..."  # commit atomically
----

== Outstanding Questions

* Which exact process runs the linter? `feedback_linter_reverts.md`
  references "automated linter/hook" but doesn't name the watcher.
  Knowing the process name would let us reproduce the displacement
  deterministically and confirm `--only` is sufficient.
* Are there `cargo fmt` / `clippy --fix` / `rustfmt` watchers active?
  Those typically only modify file contents, not the index. The
  displacement requires something that touches the index.
* Does the linter run `git stash` somewhere? `git stash` followed by
  `git stash pop` after the commit would explain the symptom — the
  staged content gets stashed, the commit captures whatever else is
  in the working tree, then the stash restores the user's edits to
  the working tree.
