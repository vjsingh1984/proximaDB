== Problem Statement

Capability knowledge is currently split across:

* store traits in `src/storage/multimodel/*`
* query-provider capabilities in `src/query/columnar/*`
* planner assumptions in `src/query/federated/*` and `src/query/unified/*`
* protocol adapters in `src/network/*` and `src/api_handlers/*`
* manually maintained support documentation

As a result:

* unsupported plan shapes can still be parsed and sometimes partially executed
* missing dependencies can degrade late instead of failing at plan time
* support-tier documentation can drift from the real public path

== Goals

* Define one normalized capability model for stores, providers, indexes, and protocols.
* Validate query plans before execution on every public entrypoint.
* Produce a machine-readable capability artifact and generate the supported-surface document from it.
* Surface structured capability errors instead of empty success results or ad hoc `NotImplemented` strings.

== Non-Goals

* expanding query syntax
* changing optimizer search strategy beyond capability validation
* adding autoscaling, resource arbitration, or adaptive placement

== Milestones

=== M1: Capability Model and Registry

Scope:

* introduce normalized capability types
* map existing store and provider capabilities into the new model
* expose registry lookup for query planning and diagnostics

Exit criteria:

* every supported model surface can describe itself through `CapabilityDescriptor`
* registry lookups are available to planner and adapter layers

=== M2: Plan Validation and Structured Errors

Scope:

* add `PlanValidator` to canonical planning flow
* introduce `ExecutionCapabilityError`
* validate REST, gRPC, SQL, UQL, and unified query entrypoints

Exit criteria:

* unsupported plan shapes fail before execution
* missing services or unsupported operators return structured capability errors

=== M3: Generated Support Surface and CI Gates

Scope:

* emit machine-readable capability snapshot
* generate `docs/SUPPORTED_SURFACE.adoc` from the snapshot plus test results
* add CI checks that prevent docs from overstating supported paths

Exit criteria:

* support matrix is generated, not hand-maintained
* CI fails if supported-surface claims exceed the verified capability artifact

== Implementation Tasks

1. Create `src/query/capabilities/*` and define capability descriptors, requirements, and validation results.
2. Add registry adapters for `StoreCapabilities` and `ColumnarCapabilities`.
3. Annotate plan nodes with required capabilities in federated and unified planning flows.
4. Introduce `ExecutionCapabilityError` and unify protocol-level error mapping.
5. Add a capability snapshot command or test utility that emits a machine-readable artifact.
6. Generate the supported-surface table from that artifact and contract-test results.

== Test Plan

=== Unit Tests

* capability descriptor serialization and deserialization
* registry merge behavior across stores, providers, and protocol adapters
* plan validator behavior for missing graph, document, observability, and scan capabilities
* error mapping from `ExecutionCapabilityError` to API-layer response types

=== Integration Tests

* REST unified query rejects unsupported plan nodes before execution
* gRPC and REST report the same capability failure for the same query
* SQL and UQL explain payloads both reflect capability requirements
* facade strategy routing never selects an unsupported execution path

=== Regression Tests

* a query that previously degraded late now fails at planning with explicit capability diagnostics
* supported vector and document and graph and observability flows remain executable on the canonical path

=== CI and Release Tests

* generated capability artifact is stable and diffable
* `SUPPORTED_SURFACE` matches the generated artifact
* support-tier documentation changes fail when they exceed generated capability tiers

== Acceptance Criteria

* Every public query entrypoint performs plan validation using the shared capability registry.
* Unsupported plans fail before execution with a structured, non-empty error response.
* `SUPPORTED_SURFACE` is generated from code-level capability data and verified contract results.
* Explain output includes capability requirements and whether the plan is valid on the current surface.

== Risks and Open Questions

* Capability granularity can become too fine and make planning brittle.
* Some existing traits may require additive adapters instead of direct modification to avoid churn.
* Generated support docs need a stable ownership model so product-facing edits do not fork from engineering truth.

== Definition of Done

* M1 through M3 are complete.
* Capability validation is on every canonical public path.
* Generated support-surface workflow is wired into CI.
* E2 and E3 can consume the registry without introducing their own capability side tables.
