== Problem Statement

The codebase already has substantial planning and execution machinery, but the public multi-model surface is still fragmented:

* federated SQL has a real planner and executor, but generic `QueryType::Sql` is still rejected on the canonical federated context
* UQL uses separate lowering paths, including placeholder vector extraction helpers
* unified execution still exposes degraded `execute_parallel*` paths
* explain semantics are split across SQL explain, unified explain, and planner-specific outputs
* scan planning exists in the optimizer, but live scan execution coverage is incomplete

== Goals

* Define `MultiModelPlan v1` as the single production lowering target for multi-model requests.
* Route SQL extensions, UQL, REST, and gRPC through the same canonical plan compiler and executor.
* Produce one stable explain payload with operator IDs, dependencies, capabilities, and fallback reasons.
* Either back generic scans through the columnar-provider system or fail them explicitly at plan time.

== Non-Goals

* general-purpose SQL completeness beyond the canonical supported scan surface
* introducing a second planner
* expanding the explain system into a UI concern

== Milestones

=== M1: Shared Logical Plan Contract

Scope:

* define `MultiModelPlan v1`
* lower SQL extensions and UQL to the same logical representation
* remove placeholder UQL vector extraction from production flow

Exit criteria:

* SQL and UQL for the same logical request produce the same plan shape

=== M2: Canonical Explain and Execution Entry

Scope:

* one explain schema across REST, gRPC, SQL, and unified query APIs
* one production entry into execution
* capability validation before dispatch

Exit criteria:

* explain output is protocol-independent
* public execution no longer depends on degraded parallel-only entrypoints

=== M3: Scan Surface Closure

Scope:

* either implement generic scan support through `ColumnarReadProvider`
* or gate unsupported scans explicitly with capability validation
* align plan nodes, execution, and explain diagnostics for scan operators

Exit criteria:

* `PlanNodeType::Scan` has an honest supported story on the canonical path

== Implementation Tasks

1. Define `MultiModelPlan v1` and canonical lowering interfaces.
2. Lower UQL and federated SQL into that shared plan contract.
3. Route unified, REST, gRPC, and facade-based execution through the same canonical planner and executor.
4. Consolidate explain output into one protocol-neutral schema.
5. Make `PlanNodeType::Scan` either provider-backed or planner-rejected with explicit capability errors.
6. Deprecate or privatize degraded execution entrypoints that bypass the canonical plan.

== Test Plan

=== Unit Tests

* UQL and federated SQL lowering into equivalent `MultiModelPlan v1` shapes
* explain generation for vector, graph, document, observability, and join operators
* capability-validation failures for unsupported scans and operators

=== Integration Tests

* REST unified query and gRPC query execution produce equivalent results for the same request
* SQL explain and unified explain return the same operator graph and cost metadata
* facade-based execution and direct federated execution produce equivalent plan diagnostics

=== Regression Tests

* no production caller routes through degraded `execute_parallel*` entrypoints
* queries that previously parsed but executed partially now fail or execute fully through the canonical plan
* supported function-backed cross-model joins continue to work after plan convergence

=== Contract and Compatibility Tests

* `PlanNodeType::Scan` either executes through `ColumnarReadProvider` or is rejected with a capability error
* SQL and UQL parity suite for vector search, graph query, document query, logs, and metrics
* explain schema stability checks for API consumers

== Acceptance Criteria

* SQL extensions, UQL, REST, and gRPC all lower into the same canonical multi-model plan.
* Explain output is protocol-independent and exposes operator IDs, capabilities, and fallback reasons.
* Production execution no longer depends on degraded parallel execution shortcuts.
* Generic scans have an honest canonical story: provider-backed support or explicit plan-time rejection.

== Risks and Open Questions

* Reusing current federated plan nodes may be faster than inventing a new plan type; if so, `MultiModelPlan v1` should wrap rather than replace them.
* Some legacy explain consumers may require a compatibility adapter during transition.
* Scan support should be kept narrow initially to avoid reopening generic-SQL scope creep.

== Definition of Done

* M1 through M3 are complete.
* One canonical explain schema is used by all supported multi-model entrypoints.
* Production execution no longer bypasses the canonical plan contract.
* E4, E5, and E6 can build on the shared plan and explain surface without creating new execution forks.
