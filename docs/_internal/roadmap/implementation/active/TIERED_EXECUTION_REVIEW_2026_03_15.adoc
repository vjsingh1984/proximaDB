Fresh tiered review of the codebase, goals, roadmap, and technical debt with a bias toward execution order rather than breadth claims.

== Executive Read

ProximaDB already has a real core product: a builder-first multi-model database that can store and
query vectors, documents, graphs, and observability data in one Rust codebase.

The main problem is not lack of ambition. It is lack of convergence. The codebase, product docs,
roadmap docs, and historical implementation summaries do not consistently agree on what is
production-ready, what is experimental, and what is still scaffolded.

Highest-value work:

. Re-establish a truth layer.
. Finish foundational execution gaps on canonical paths.
. Productize security and operator-facing evidence.
. Narrow the public vision to the parts that are strongest today.

== Strategic Conclusions

=== The Goal Is Valid

The long-term goal still makes sense: one database that assembles context across vectors,
documents, graph structure, temporal facts, and event history.

=== The Near-Term Goal Needs To Be Narrower

The project should not optimize for the widest capability matrix in the next tranche. It should
optimize for the fewest contradictions per user-facing claim.

=== The Roadmap Should Move From Breadth-First To Truth-First

The next three milestones should be:

. Canonical path correctness and telemetry.
. Security and operator evidence.
. Product packaging around the strongest ICPs.

== Methodical Order of Execution

=== Tier 1: Foundational

. Keep `FOUNDATIONAL_MULTIMODEL_EXECUTION_2026.adoc` as the active implementation spine.
. Finish verification for the in-flight F1/F2/F3 work.
. Replace default or estimated stats with real `collection_stats`, disk usage, and cache metrics.
. Close the remaining federated execution gaps: relational scan backend first, real remote transport second.

=== Tier 2: Security

. Finish the mTLS chain with revocation strategy, identity mapping tests, and audit assertions.
. Publish what is genuinely supported now versus what is roadmap only.
. Treat security evidence as a release gate, not a documentation afterthought.

=== Tier 3: Design and Productization

. Publish a supported-surface matrix across engines and subsystems.
. Keep ORION, SST, VIPER, NOVA, and core document/query/observability paths as the production spine.
. Keep RAPTOR, SWIFT, cluster, and AutoML under explicit maturity labels until they have parity and tests.

=== Tier 4: Vision and Packaging

. Standardize the public message around "multi-model AI database" or "context database" rather than mixing it with older vector-only framing.
. Narrow the first two ICPs:
* AI retrieval and semantic application context
* Embedded or low-latency trading and observability workflows
. Stop positioning every planned subsystem as equally ready.

=== Tier 5: Roadmap and Governance

. Retire branch-centric or "% complete" summaries as execution artifacts.
. Use one active tracker, one debt register, and a small GitHub issue backlog.
. Require every roadmap claim to map to code, tests, and docs.

== Bottom Line

With hindsight, the project should stop acting like a nearly-finished everything-platform and start
behaving like a strong multi-model core that is being deliberately hardened. The best path upward
is foundational correctness first, then security and product design, then ecosystem and scale.
