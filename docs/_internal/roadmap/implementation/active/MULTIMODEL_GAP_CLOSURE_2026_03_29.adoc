= Multi-Model Gap Closure Architecture and Implementation Design
:toc: left
:toclevels: 3
:icons: font
:source-highlighter: rouge
:last-updated: 2026-03-29

[.lead]
Evidence-based implementation design for closing the verified gaps in ProximaDB's multi-model execution, transactions, distributed graph/cluster behavior, document schema execution, observability exploration, and tiered graph storage.

== Purpose

This document converts the March 2026 verified findings into concrete implementation workstreams.

It is intentionally stricter than earlier architecture writeups:

* capability claims must follow canonical execution paths, not side paths or partial scaffolds
* experimental subsystems must stay explicitly experimental until fault tolerance and recovery semantics are complete
* cross-model behavior must be expressed through stable traits, durable logs, and regression tests before it is described as "robust"

This document complements link:FOUNDATIONAL_MULTIMODEL_EXECUTION_2026.adoc[Foundational Multi-Model Execution Plan (2026)] and should be treated as the detailed design for the next correctness tranche.

== Verified Baseline

|===
| ID | Verified Gap | Current Evidence | Required Correction

| G1
| Canonical unified execution is incomplete
| `src/query/unified/mod.rs` executes through a simplified path; `src/query/unified/executor.rs` can silently return empty vector or observability results when services are absent.
| Move to a single capability-aware execution graph with explicit service injection and explicit failure semantics.

| G2
| Cross-model transaction correctness is not implemented end-to-end
| `src/storage/transaction/manager.rs` contains deadlock-detection stubs; `src/storage/multimodel/transaction/two_phase_commit.rs` defines the protocol but there are no participant implementations.
| Build participant adapters, durable coordinator decision logging, deadlock detection, and restart recovery before claiming robust cross-model ACID.

| G3
| Distributed graph and cluster surfaces are only partially real
| `src/graph/engines/pulsar/mod.rs` marks PULSAR experimental; `src/cluster/replication.rs` and `src/cluster/rpc/grpc_server.rs` contain simulation fallbacks and ack-only TODO paths.
| Separate local simulation from distributed mode and implement apply-before-ack replication, snapshot install, and cross-shard traversal correctness.

| G4
| Document schema and columnar execution are only partially integrated
| Schema inference/evolution already exist, but `src/storage/multimodel/mod.rs` still marks VIPER/Tantivy integration as in progress and the document store advertises no transactions/ACID.
| Make schema inference/evolution first-class in document ingest/query and formalize hot JSON plus cold columnar execution with late materialization.

| G5
| Observability backend is ahead of the public execution and UI surface
| Internal trace query support exists in `src/observability/mod.rs`, but the trait bridge currently degrades to empty results on non-`trace_id` queries and the dashboard lacks trace/entity exploration.
| Wire the trait bridge to the existing service API and add a focused trace/log/entity exploration surface.

| G6
| QUASAR tiering automation is rudimentary
| `src/graph/engines/quasar/mod.rs` explicitly calls automatic tiering minimal; `src/graph/engines/quasar/tiering.rs` uses simplified candidate selection and guesses item type.
| Replace threshold-only migration with a proper policy engine, node/edge-aware planners, and durable migration state.
|===

== Non-Goals

The following are explicitly out of scope for this tranche:

* new query syntax beyond what is needed to unify existing UQL and federated SQL lowering
* broad rebranding or capability claims before the canonical paths are complete
* making PULSAR or QUASAR default engines before recovery and consistency criteria are met
* adding parallel subsystems when the existing subsystem can be completed by wiring and hardening

== Best-in-Class Design Rules

The implementation should follow these rules consistently:

* Canonical path first. A feature is incomplete if the primary execution path bypasses it.
* No silent degradation. Missing services or unsupported distributed features must return structured errors, not empty success results.
* Durable state transitions before scale claims. If a decision cannot survive process death, it is not distributed correctness.
* Storage-specific participants behind stable contracts. Each engine may optimize internally, but the transaction and execution contracts must be uniform.
* Planner and executor separation. Parsing, lowering, capability resolution, and execution are distinct stages with typed handoff.
* Feature gating with honest defaults. ORION remains the default graph engine until distributed correctness exits experimental status.
* Recovery, fault injection, and regression coverage are part of the feature, not follow-up work.

== Target Architecture

=== Canonical Query Path

[source,text]
----
SQL/UQL Input
  -> Parser / Lowering
  -> MultiModelPlan
  -> Capability Resolver
  -> Execution Graph
  -> Service-backed Subquery Executors
  -> Fusion / Join / Rerank
  -> Result + Diagnostics
----

=== Canonical Transaction Path

[source,text]
----
Client Write Request
  -> Transaction Coordinator
  -> Per-store Write Set Assembly
  -> Durable Prepare Record
  -> Participant Prepare
  -> Durable Global Decision
  -> Participant Commit/Abort
  -> Recovery Sweeper / Retry
----

=== Canonical Distributed Graph Path

[source,text]
----
Graph Mutation / Traversal
  -> Shard Ownership Resolver
  -> Local WAL Append
  -> Replication Transport
  -> Apply-on-Replica
  -> Cross-shard Frontier Expansion
  -> Read / Traversal Result
----

== Workstream G1: Canonical Unified Execution

=== Problems To Fix

* `UnifiedQueryEngine` stores only `UnifiedStorageEngine` and `DocumentService`, even though the executor already supports optional vector, graph, and observability services.
* `execute_parallel()` is public and represents a degraded execution mode.
* UQL and federated SQL describe overlapping capability sets but lower through separate, partially inconsistent paths.
* Missing capabilities are represented as empty results instead of explicit execution errors.

=== Target State

Create a single execution contract for all multi-model queries:

* Add `UnifiedExecutionServices` under `src/query/unified/` containing:
** `storage_engine`
** `vector_ops`
** `document_service`
** `graph_service`
** `observability_service`
** optional `rbac_manager`
** optional query cache / diagnostics sink
* Change `UnifiedQueryEngine` to own `UnifiedExecutionServices` instead of the current partial dependency set.
* Make `ParallelExecutor::execute_parallel()` private or test-only and route all production callers through a capability-aware entry point.
* Introduce `ExecutionCapabilityError` or equivalent typed failure when a query component cannot be satisfied by the provided services.
* Normalize UQL and federated SQL into one typed `MultiModelPlan` so the same execution graph is used regardless of syntax surface.

=== Code Touchpoints

* `src/query/unified/mod.rs`
* `src/query/unified/executor.rs`
* `src/query/unified/uql.rs`
* `src/query/federated/mod.rs`
* `src/query/federated/parser.rs`
* `src/query/facade/adapter.rs`
* `src/query/distributed/coordinator.rs`

=== Implementation Notes

* Replace placeholder UQL lowering in `convert_multimodal_to_query()` with direct AST-to-plan lowering.
* Replace placeholder vector extraction in `extract_vector_search_params()` with typed parameter capture from the parsed predicate tree.
* Move capability checks ahead of execution so missing graph or observability services fail the plan before any subquery runs.
* Preserve intermediate records as typed relations or IDs instead of collapsing to empty-result semantics.
* Add execution diagnostics: `used_capabilities`, `skipped_components`, `fusion_inputs`, and `degraded=false/true`.

=== Required Invariants

* A production query never reports success with silently dropped subqueries.
* SQL and UQL for the same logical request compile to the same execution plan shape.
* A successful fused result is constructed only from explicitly executed subqueries.

=== Test Strategy

* Unit tests for capability resolution and typed lowering.
* Integration tests proving that vector, graph, document, and observability components all execute through the same entry point.
* Regression tests that assert missing services produce an error, not an empty `SubQueryResult`.

=== Exit Criteria

* `UnifiedQueryEngine::execute()` no longer routes through degraded mode.
* Placeholder UQL lowering paths are removed from the production flow.
* Federated SQL and UQL share a common executable multi-model plan.
* Missing service dependencies are surfaced explicitly in API responses and logs.

== Workstream G2: Cross-Model Transaction Correctness

=== Problems To Fix

* `TransactionManager::detect_deadlock()` is stubbed.
* `TwoPhaseCommitProtocol` exists but no store implements `TwoPhaseParticipant`.
* The current 2PC trait does not carry a durable prepared write set or recovery metadata.
* Coordinator decisions are not persisted in a way that guarantees restart recovery across in-doubt transactions.

=== Target State

Build a real participant and recovery layer around the existing coordinator:

* Extend `TwoPhaseParticipant` to operate on a participant-local prepared handle rather than a bare transaction ID.
* Add `PreparedWriteSet`, `PreparedHandle`, and `RecoveryState` types under `src/storage/multimodel/transaction/`.
* Persist coordinator state transitions into a transaction decision log backed by the unified WAL.
* Implement concrete participant adapters for:
** vector writes
** document writes
** graph writes
** observability writes
* Add deadlock detection using a wait-for graph in `src/storage/transaction/manager.rs`.
* Add an in-doubt transaction sweeper that replays commit/abort on startup until all participants acknowledge the durable decision.

=== Code Touchpoints

* `src/storage/transaction/manager.rs`
* `src/storage/multimodel/transaction/two_phase_commit.rs`
* `src/storage/multimodel/transaction/coordinator.rs`
* new `src/storage/multimodel/transaction/participants/*.rs`
* `src/storage/traits.rs`
* per-store service modules that can materialize participant-local write sets

=== Implementation Notes

* `prepare()` must mean "durably staged and replayable after crash", not "validation passed in memory".
* `commit()` and `abort()` must be idempotent and keyed by transaction ID plus participant epoch/handle.
* The coordinator must durably write the global decision before sending commit messages.
* Participants should expose `recover(transaction_id)` so the coordinator can resolve in-doubt states after restart.
* Cross-model ACID should remain opt-in until the participant matrix is complete and fault-injection tests pass.

=== Required Invariants

* A YES vote implies durable, crash-recoverable prepared state.
* Global commit/abort is derivable after coordinator restart from the durable decision log.
* Duplicate commit/abort messages are safe.
* Deadlock detection runs on the actual lock/wait graph, not on a placeholder stub.

=== Test Strategy

* Unit tests for wait-for graph cycle detection.
* Participant contract tests for prepare/commit/abort idempotency.
* Fault-injection tests for crashes between prepare and commit, commit and ack, and recovery sweeps.
* Multi-store integration tests that verify real store state, not only coordinator state transitions.

=== Exit Criteria

* At least vector, document, graph, and observability stores each have a concrete `TwoPhaseParticipant`.
* Coordinator decisions are persisted and replayed on restart.
* Deadlock detection is implemented and covered by regression tests.
* Cross-model ACID is not advertised beyond the participant matrix that has passed restart and duplicate-message tests.

== Workstream G3: Distributed Graph And Cluster Correctness

=== Problems To Fix

* PULSAR is still explicitly experimental, with incomplete cross-shard traversal and distributed transaction support.
* Replication still falls back to local simulation when transport is absent.
* gRPC replication handlers acknowledge entries without applying them.
* Snapshot install is not complete.

=== Target State

Make distributed behavior explicit and correct before optimizing it:

* Split local-only simulation from distributed mode in configuration and code paths.
* When distributed mode is enabled, missing transport or registry wiring must fail startup rather than degrade to simulation.
* Define an explicit shard ownership model:
** source shard owns edge adjacency
** target-shard mirrors are optional and rebuildable
** cross-shard traversals expand frontier batches across owning shards
* Require apply-before-ack semantics for replicated entries.
* Implement staged snapshot install with checksum validation and atomic promotion.
* Keep PULSAR experimental until cross-shard traversal, replication apply, and recovery tests are complete.

=== Code Touchpoints

* `src/graph/engines/pulsar/mod.rs`
* `src/graph/engines/pulsar/coordinator.rs`
* `src/graph/service_engine_factory.rs`
* `src/cluster/consensus.rs`
* `src/cluster/replication.rs`
* `src/cluster/rpc/grpc_server.rs`

=== Implementation Notes

* Remove implicit fallback to simulated replication from production distributed paths.
* Add a replica apply pipeline that appends to WAL, applies to shard state, updates LSN, then acknowledges.
* Snapshot install should write chunk data to a staging area and finalize only after the last verified chunk.
* Cross-shard BFS/DFS should use frontier batching and visited sets carried across shard calls, not repeated whole-shard scans.
* Keep ORION as the production default until PULSAR meets its correctness gate.

=== Required Invariants

* A replica ack means the entry is durable and applied to the local shard state expected by reads.
* Cross-shard traversal cannot silently omit reachable neighbors owned by another shard.
* Distributed mode never silently becomes local simulation.

=== Test Strategy

* Multi-node deterministic integration tests for replication and snapshot recovery.
* Fault-injection tests for leader failover during snapshot and during replicated writes.
* Cross-shard traversal regressions covering source-owned edges, target-owned nodes, and missing-shard failure modes.

=== Exit Criteria

* Replication RPC applies entries before ack.
* Snapshot install is complete and restart-safe.
* PULSAR cross-shard traversal passes deterministic multi-shard integration tests.
* `GraphEngineFactory` and docs still mark PULSAR experimental until the above tests are green in CI.

== Workstream G4: Document Schema And Columnar Execution Closure

=== Problems To Fix

* Schema inference and evolution exist, but they are not yet the canonical document ingest/query control plane.
* The multimodel document store still describes VIPER/Tantivy integration as in progress.
* Dynamic fields need a stable schema-on-read and schema-on-write contract.
* Full document materialization should not happen before selective filters and joins.

=== Target State

Create an explicit document schema execution pipeline:

* Add `DocumentSchemaRegistry` to compose:
** `SchemaInferenceService`
** `SchemaEvolutionService`
** collection-level schema version metadata
* Formalize a dual-path document layout:
** hot JSON/WAL path for fresh writes and canonical document retrieval
** cold/persisted VIPER column projections keyed by `document_id` and `schema_version`
* Add field-promotion rules for dynamic JSON fields:
** inferred field
** promoted column
** indexed text field
** retained opaque JSON field
* Reuse existing columnar late-materialization infrastructure for document queries so only projected rows are materialized back into full JSON when required.

=== Code Touchpoints

* `src/storage/document/*`
* `src/storage/multimodel/stores/document_store.rs`
* `src/services/schema/inference.rs`
* `src/services/schema/evolution.rs`
* `src/storage/engines/core/formats/columnar/columnar_query_engine/*`

=== Implementation Notes

* Store a schema version with every persisted document batch.
* Backfills should be asynchronous and resumable; old schema versions remain readable.
* Use a document-ID spine so hot JSON, cold VIPER, and Tantivy all reference the same logical row.
* Push filters and projections to the columnar path first; materialize the full JSON blob only for surviving rows or requested full-document projections.
* Add a compatibility mode for collections that remain fully schemaless.

=== Required Invariants

* Adding a new dynamic field does not break reads of older rows.
* Schema evolution decisions are auditable by collection and version.
* Late materialization is the default for selective document analytics, not an optimization that only some paths use.

=== Test Strategy

* Schema inference tests on heterogeneous JSON datasets.
* Evolution tests for add/remove/rename/widening scenarios.
* Integration tests proving the same query can execute against hot JSON and cold VIPER data with identical results.
* Performance regressions focused on late materialization and selective predicate pushdown.

=== Exit Criteria

* Document ingest records schema version metadata.
* Document queries can use promoted VIPER columns without full document reads.
* Dynamic field evolution is covered by regression tests and documented by schema history.
* The multimodel document store description can be updated from "integration in progress" only after the above are wired into the canonical path.

== Workstream G5: Observability Exploration And Query Unification

=== Problems To Fix

* The internal observability service already supports time-range and service-based trace queries, but the trait bridge path still degrades to empty results when `trace_id` is not supplied.
* The current dashboard is general-purpose and does not expose trace exploration or entity-linked investigation workflows.

=== Target State

Close the gap by wiring existing observability capabilities through the public surface:

* Change the `ObservabilityStorageOperations` bridge implementation to delegate to `ObservabilityService::query_traces()` rather than directly returning empty results for time-range requests.
* Add a dedicated exploration API with filters for:
** time range
** service
** operation
** latency
** error state
** linked entity or graph node
* Add a UI slice within the existing dashboard style, not a new disconnected app:
** `Overview`
** `Collections`
** `Metrics`
** `System`
** `Logs`
** `Traces`
** `Entity Links`
* Introduce configurable extraction rules that map log/span attributes such as `entity_id`, `tenant_id`, `document_id`, or `graph_node_id` into graph/entity lookups.

=== Code Touchpoints

* `src/observability/mod.rs`
* `src/observability/query/*`
* `src/storage/multimodel/stores/observability_store.rs`
* `src/network/rest/server.rs`
* `src/network/rest/dashboard.html`

=== Implementation Notes

* Reuse the existing `TraceQueryParams` and internal trace summary logic as the primary backend contract.
* Expose an endpoint that returns trace summaries plus linked entity references for the explorer view.
* Keep the UI server-rendered or lightweight JS to match the current dashboard architecture.
* Use attribute extractors instead of hard-coded joins so different workloads can map traces to semantic entities differently.

=== Required Invariants

* Time-range trace queries on the public/trait path are functional, not empty stubs.
* Explorer views link back to canonical trace and entity IDs.
* Observability UI features remain optional and do not block core API operation.

=== Test Strategy

* Bridge regression tests for time-range and service-based trace queries.
* API integration tests for explorer endpoints and attribute-based entity linking.
* Basic dashboard smoke tests for tab rendering and query requests.

=== Exit Criteria

* The trait bridge no longer drops non-`trace_id` trace queries.
* Trace exploration endpoints are present and covered by integration tests.
* The dashboard can navigate from trace summaries to linked semantic entities.

== Workstream G6: QUASAR Tiering Policy Engine

=== Problems To Fix

* The current tiering policy relies on a single utilization threshold and simplistic recency/frequency scoring.
* Item type detection is guessed.
* Migration durability and replay semantics are not first-class.

=== Target State

Replace ad hoc tiering with an explicit policy-and-planner model:

* Add a `TieringPolicy` interface that computes a `HeatScore` using:
** recency
** frequency
** graph fan-out / fan-in
** object size
** query role (entry point, bridge node, cold tail)
* Add a `MigrationPlanner` that groups node and edge migrations into bounded batches with backpressure.
* Add a durable migration journal so interrupted migrations can be resumed or rolled back.
* Add promotion hysteresis so hot-once objects do not churn between tiers.
* Pull node and edge classification from ORION APIs or metadata, never from guessed defaults.

=== Code Touchpoints

* `src/graph/engines/quasar/mod.rs`
* `src/graph/engines/quasar/tiering.rs`
* `src/graph/engines/orion/*` for stats or classification helpers
* `src/storage/cache/orchestrator/*` where heat signals can be reused

=== Implementation Notes

* The policy should separate "eligibility" from "migration scheduling".
* Migration journals should record source tier, destination tier, object identity, and replay status.
* Promotion on cold miss should be bounded and rate-limited.
* Tiering metrics must be exported so policy tuning becomes data-driven.

=== Required Invariants

* Node and edge migrations are type-correct.
* Crash during migration does not orphan data between tiers.
* Repeated cold misses eventually promote hot objects without oscillation.

=== Test Strategy

* Deterministic workload simulations for hot-set shift, bursty access, and cold-tail retention.
* Restart tests during migration.
* Metrics-based regressions for migration churn and promotion latency.

=== Exit Criteria

* Tiering decisions are produced by a policy interface, not fixed thresholds only.
* Migration state is durable and restart-safe.
* QUASAR documentation can describe automatic tiering as policy-driven rather than minimal.

== Cross-Cutting Engineering Standards

Every workstream in this document should adopt the same engineering discipline:

* Feature flags guard incomplete surfaces.
* Metrics and structured diagnostics are added with the feature.
* CI includes focused regression tests for every bug class being closed.
* Docs update only after the canonical code path and tests are in place.
* "Experimental" labels remain until restart, failure, and degraded-mode semantics are verified.

== Definition Of Done For This Gap-Closure Program

This program is complete only when all of the following are true:

* canonical multi-model queries execute through one service-complete path
* unsupported capabilities fail explicitly instead of degrading silently
* cross-model transactions have real participants, durable decisions, and restart recovery
* distributed cluster writes are applied before acknowledgement
* PULSAR remains experimental until its deterministic integration suite is green
* document schema evolution is wired into canonical document ingest and query execution
* public observability trace queries and explorer views use the existing service capabilities instead of stubs
* QUASAR tiering is policy-driven, durable, and observable

Until then, product and roadmap language should continue to describe these areas as in progress or experimental.
