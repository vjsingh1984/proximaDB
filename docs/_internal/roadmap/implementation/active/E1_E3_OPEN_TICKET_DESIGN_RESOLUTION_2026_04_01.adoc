== Scope

This document addresses all currently raised and unresolved E1-E3 tickets:

* `SB-01` through `SB-07` for capability registry, validation, and generated support surface
* `SB-08` through `SB-13` for filtered ANN correctness, candidate generation, and benchmark evidence
* `SB-14` through `SB-20` for canonical multi-model planning, explain convergence, and scan-surface honesty

This document is design-level by intent. It answers:

* what the canonical contracts are
* where responsibilities should live
* how data and control should flow through the system
* which failure modes are acceptable
* what evidence is required before a ticket is considered closed

This document does not replace the execution tickets. It resolves the design choices those tickets should implement.

== Architectural Decisions

The following decisions apply to every ticket in scope:

* Canonical path only. Every supported public entrypoint must lower into the same validated production plan and executor.
* Capability first. Unsupported behavior fails at plan time with a structured capability error, never through partial execution or empty success.
* Exactness before speed. Filtered retrieval may use approximate search only when correctness boundaries, residual verification, and recall evidence are explicit.
* One normalization layer per concern. Filters, capability requirements, and explain metadata each have one canonical representation.
* Narrow support beats aspirational breadth. Scan support, filter operators, and ANN backend coverage remain intentionally narrow until test-backed.
* Explain is part of the runtime contract. If a behavior is supported, explain must surface its operators, dependencies, capabilities, and fallback reasons.
* Evidence drives promotion. `supported`, `beta`, and `experimental` are a function of code-level capabilities and passing contract suites.
* Additive adapters before invasive rewrites. Existing traits and plan nodes should be wrapped or bridged where possible to minimize churn.

== Canonical Runtime Model

The target production flow for all E1-E3 tickets is:

[source,text]
----
Request
-> protocol adapter / parser
-> canonical logical intent
-> MultiModelPlan v1
-> capability validation
-> model-specific normalization
-> physical binding
-> canonical executor
-> residual verification
-> explain / diagnostics / results
----

The target filtered vector flow is:

[source,text]
----
Vector request
-> FilterExpression
-> NormalizedFilter
-> CandidatePlan
-> CandidateSet
-> backend-specific ANN execution
-> exact rerank
-> MVCC and residual filter verification
-> results + diagnostics
----

The target explain contract is:

[source,text]
----
ExplainRequest
-> same lowering and validation path as execution
-> same MultiModelPlan v1
-> same capability registry
-> protocol-neutral ExplainPlan
-> transport adapter
----

== Shared Contracts

=== Capability Contract

The capability system should be additive and serializable. It is not a planner-specific side table.

[source,rust]
----
enum CapabilityTier {
    Supported,
    Beta,
    Experimental,
    Unsupported,
}

enum CapabilitySubject {
    Vector,
    Document,
    Graph,
    Observability,
    Scan,
    Join,
    Explain,
    Transaction,
    Protocol,
}

struct CapabilityDescriptor {
    subject: CapabilitySubject,
    operation: String,
    engine: Option<String>,
    protocol: Option<String>,
    tier: CapabilityTier,
    predicates: Vec<String>,
    limits: Vec<String>,
    evidence: CapabilityEvidence,
}

struct CapabilityRequirement {
    subject: CapabilitySubject,
    operation: String,
    mandatory: bool,
    acceptable_tiers: Vec<CapabilityTier>,
    disallow_fallback: bool,
    reason: String,
}
----

Rules:

* `CapabilityDescriptor` describes what a subsystem claims it can execute.
* `CapabilityRequirement` describes what a plan node requires to execute honestly.
* The registry is composed from stores, providers, indexes, protocol adapters, and service bindings.
* Capability checks happen twice:
** at plan build time for structural validation
** at execution bind time for dependency presence and engine availability

=== Filter and Candidate Contract

The filter model should preserve semantics while allowing efficient candidate planning.

[source,rust]
----
enum NormalizedFilterExpr {
    And(Vec<NormalizedFilterExpr>),
    Or(Vec<NormalizedFilterExpr>),
    Not(Box<NormalizedFilterExpr>),
    Predicate(FilterAtom),
}

struct CandidateSet {
    mode: CandidateMode,
    estimated_cardinality: Option<usize>,
    exact_ids: Option<Vec<RecordId>>,
    bitmap: Option<RoaringBitmap>,
    residual_predicate: Option<NormalizedFilterExpr>,
}

struct BuiltHybridQuery {
    hybrid_query: HybridQuery,
    candidate_set: Option<CandidateSet>,
    residual_predicate: Option<NormalizedFilterExpr>,
    diagnostics: QueryBuildDiagnostics,
}
----

Rules:

* `FilterExpression` is lowered once into `NormalizedFilterExpr`.
* Candidate generation may only discard records when the predicate fragment is provably safe and index-backed.
* Any predicate fragment not proven safe becomes a residual predicate and must be rechecked after retrieval.
* ANN execution is never the final arbiter of filter correctness. Residual verification is mandatory unless the candidate set already encodes the full filter.

=== Multi-Model Plan Contract

`MultiModelPlan v1` should be a stable logical-execution contract, not a bag of transport-specific AST fragments.

[source,rust]
----
struct MultiModelPlanV1 {
    plan_id: PlanId,
    root: OperatorId,
    operators: Vec<PlanOperator>,
    capabilities: Vec<CapabilityRequirement>,
    bindings: PlanBindings,
    diagnostics: PlanDiagnostics,
}

enum PlanOperator {
    VectorSearch(VectorSearchOp),
    GraphQuery(GraphQueryOp),
    DocumentQuery(DocumentQueryOp),
    LogsQuery(LogsQueryOp),
    MetricsQuery(MetricsQueryOp),
    Filter(FilterOp),
    Project(ProjectOp),
    Join(JoinOp),
    Aggregate(AggregateOp),
    Scan(ScanOp),
    Lateral(LateralOp),
}
----

Rules:

* Public SQL extensions, UQL, REST, facade-driven requests, and gRPC must lower into `MultiModelPlanV1`.
* The current federated planner may remain the main physical planner, but it must consume a canonical plan rather than protocol-specific branches.
* Explain uses the same operator graph and requirement set as execution.

=== Explain Contract

Explain must be protocol-neutral and mechanically derivable from the validated plan.

[source,rust]
----
struct ExplainPlan {
    plan_id: PlanId,
    valid: bool,
    operators: Vec<ExplainOperator>,
    required_capabilities: Vec<CapabilityRequirement>,
    missing_capabilities: Vec<CapabilityRequirement>,
    bindings: Vec<ExplainBinding>,
    fallbacks: Vec<ExplainFallback>,
    diagnostics: ExplainDiagnostics,
}
----

Rules:

* All protocols expose the same operator IDs and dependency graph.
* Explain must state whether scan, filter, vector, graph, or provider execution is exact, approximate, unsupported, or degraded.
* If execution would fail due to capability validation, explain still returns a structurally valid `ExplainPlan` with `valid=false`.

== E1 Ticket Resolutions: Capability Registry and Supported Surface

=== SB-01 / Issue #31: Define Capability Registry Core Types

Decision:

* Create a new `src/query/capabilities/*` package that owns the normalized capability model.
* Keep the core type system query-centric, not storage-centric, so the same descriptor language can represent vector, graph, document, observability, scan, protocol, and explain capabilities.
* Add `CapabilityEvidence` and `CapabilityScope` on day one so the registry can later drive generated support docs without structural churn.

Primary interfaces:

* `CapabilityDescriptor`
* `CapabilityRequirement`
* `CapabilityTier`
* `CapabilityRegistry`
* `CapabilityScope`
* `CapabilityEvidence`

Invariants:

* Types must be JSON-serializable for snapshot generation.
* Capability keys must be stable across runs and independent of runtime instance IDs.
* Capability tier must not be inferred from documentation.

Design pattern:

* registry plus descriptor objects, with adapters at the boundaries and no direct dependency from transport code to storage-specific enums

=== SB-02 / Issue #32: Bridge Store and Provider Capabilities into the Registry

Decision:

* Do not replace existing `StoreCapabilities` or `ColumnarCapabilities` immediately.
* Introduce adapters:
** `impl From<&StoreCapabilities> for Vec<CapabilityDescriptor>`
** `impl From<&ColumnarCapabilities> for Vec<CapabilityDescriptor>`
* Add a registry composer that merges descriptors and resolves duplicates by most restrictive tier.

Adapter rules:

* A provider can only advertise `supported` if the backing execution path exists and is test-backed on the public path.
* If store and provider disagree, the registry takes the lower tier and emits a diagnostic warning in the capability snapshot.
* Backend-specific capabilities such as filtered ANN on HNSW or scan pushdown on a provider must remain backend-scoped, not projected as generic system truth.

Failure policy:

* Incomplete adapters are acceptable initially only if the missing capabilities default to `unsupported`, never `supported`.

=== SB-03 / Issue #33: Attach Capability Requirements to Plan Nodes

Decision:

* Attach requirements at operator construction time, not retroactively in the executor.
* Every `PlanOperator` must carry:
** its own `CapabilityRequirement` set
** optional dependency hints
** a stable operator ID for explain

Rules:

* Requirements are declarative and must not contain runtime service pointers.
* Parent operators inherit child requirements only through explicit plan compilation, not by mutating child metadata.
* `Join`, `Lateral`, and `Scan` operators must declare capability requirements even if they are planner-internal only.

Why this matters:

* It keeps explain honest.
* It lets `PlanValidator` reject unsupported shapes before any dispatch.
* It prevents executor-only knowledge from becoming hidden product behavior.

=== SB-04 / Issue #34: Define Protocol-Level Capability Error Mapping

Decision:

* Introduce a single `ExecutionCapabilityError` domain error with transport adapters for REST, gRPC, SQL, and facade consumers.
* Error payload must include:
** `error_code`
** `message`
** `plan_id`
** `operator_id`
** `required_capabilities`
** `missing_capabilities`
** `tier_mismatch`
** `retryable=false`

Transport behavior:

* REST returns deterministic JSON with the same field names across unified and SQL-style APIs.
* gRPC returns structured metadata plus machine-readable fields.
* SQL-style explain and execution endpoints render the same underlying capability error in a SQL-compatible wrapper.

Rule:

* No `NOT_IMPLEMENTED`, empty arrays, or late executor panics are acceptable substitutes for capability failure.

=== SB-05 / Issue #35: Add Canonical Plan Validation to Public Entrypoints

Decision:

* Insert `PlanValidator` after lowering into `MultiModelPlanV1` and before any physical binding or executor dispatch.
* Validate on:
** unified REST
** SQL REST
** gRPC
** facade-produced requests
** UQL execution
** federated SQL execution

Validator behavior:

* Structural validation checks operator legality and requirement presence.
* Capability validation checks registry support and service availability.
* Policy validation checks whether approximate or degraded modes are allowed for the requested surface.

Operational rule:

* Once validation succeeds, the executor may assume plan legality and dependency presence.

=== SB-06 / Issue #36: Add Capability Contract Tests and Snapshot Generation

Decision:

* Add a contract suite that materializes registry snapshots from representative runtime configurations.
* Emit a deterministic artifact such as `CAPABILITY_SNAPSHOT.json` from test or tooling code.

Snapshot content:

* descriptors
* tiers
* evidence references
* protocol surfaces
* capability conflicts and overrides

Test strategy:

* unit tests for adapter conversion
* contract tests for representative single-node service compositions
* parity tests ensuring public entrypoints do not advertise unsupported operators

Release rule:

* a change to capability tiers without artifact delta review is a release-blocking change

=== SB-07 / Issue #37: Generate SUPPORTED_SURFACE and CI Gate Design

Decision:

* `docs/SUPPORTED_SURFACE.adoc` becomes generated or partially generated from:
** capability snapshot
** contract-test results
** benchmark evidence for performance-sensitive claims

Generated sections should include:

* model area
* supported operations
* required engine/provider
* tier
* evidence source
* exclusions and caveats

CI gates:

* fail if docs claim `supported` while snapshot says lower tier
* fail if benchmark-backed claims are missing evidence artifacts
* fail if a canonical public path no longer validates for an advertised capability

== E2 Ticket Resolutions: Filtered ANN Candidate Pipeline

=== SB-08 / Issue #38: Define Normalized Filter, CandidateSet, and HybridQueryBuilder

Decision:

* Create one canonical lowering path from `FilterExpression` to `NormalizedFilterExpr`.
* Normalize boolean structure into negation-normal form and separate predicates into:
** exact pushdown predicates
** candidate-generating predicates
** residual-only predicates
* Centralize `HybridQuery` construction behind `HybridQueryBuilder`.

Builder outputs:

* populated `HybridQuery`
* `CandidateSet` or `CandidatePlan`
* residual predicate
* diagnostics explaining what was pushed down and what was not

Important rule:

* if a request has filter intent, the canonical vector path may not emit an empty `metadata_filters` or `id_filters` unless diagnostics explicitly say no predicate is pushdown-safe

=== SB-09 / Issue #39: Wire Canonical Vector Paths to Build Filtered HybridQuery

Decision:

* Every canonical vector request path must call `HybridQueryBuilder`.
* This includes:
** v1 vector endpoints
** unified handlers
** facade vector strategy
** graph-first semantic search path where vector retrieval is invoked

Module responsibility:

* handlers assemble intent and auth context
* `HybridQueryBuilder` performs filter lowering and query assembly
* vector service executes the built query and collects diagnostics

Rules:

* handlers may not directly construct partially populated `HybridQuery` values
* filter propagation must survive through protocol adapters unchanged

=== SB-10 / Issue #40: Implement Candidate Handling in AXIS Manager

Decision:

* AXIS manager owns candidate planning and candidate execution policy selection.
* Candidate sets should use roaring bitmaps or explicit ID sets as the canonical in-memory representation.

Execution policy:

* If candidate cardinality is very small, perform exact candidate scan plus rerank.
* If backend supports candidate-aware ANN, run ANN constrained by candidate set.
* If backend lacks candidate-aware execution but approximate filtered mode is allowed, use oversampled ANN plus residual verification.
* If neither correctness-preserving path exists, reject through capability validation.

Diagnostics:

* candidate cardinality estimate
* exact IDs vs bitmap source
* chosen backend
* oversampling factor
* residual verification count

Correctness rule:

* AXIS manager must never silently downgrade from filtered ANN to unfiltered ANN plus best-effort filtering without surfacing this in diagnostics and capability policy

=== SB-11 / Issue #41: Apply Backend-Specific Filtered Contracts in HNSW and IVF

Decision:

* HNSW and IVF keep backend-specific policies behind a common contract:
** `prepare(filtered_query, candidate_set, policy)`
** `search(top_k, oversample, constraints)`
** `verify(candidate_hits)`

HNSW policy:

* prefer candidate-aware traversal when candidate set is selective and bitset membership checks are cheap
* otherwise allow oversampled traversal plus exact residual verification
* expose the effective recall policy in diagnostics

IVF policy:

* intersect candidate sets with probed lists where possible
* fall back to candidate-restricted exact distance within selected lists when selectivity is high
* oversample only when post-filter verification still meets the declared capability tier

LSH policy:

* leave unsupported for filtered ANN until there is evidence of correctness and stable performance
* gate with capability validation rather than pretend parity

=== SB-12 / Issue #42: Add Exact-Baseline, Recall, and Graph-First Regressions

Decision:

* Filtered ANN must be differential-tested against an exact baseline, not only smoke-tested.
* Regression suites should cover:
** low selectivity
** medium selectivity
** high selectivity
** graph-first semantic retrieval with metadata filters
** unsupported filter/operator combinations

Evidence thresholds:

* exactness for exact candidate modes
* recall thresholds for approximate filtered modes by selectivity band
* no false positives after residual verification

Graph-first requirement:

* graph-first entity search must reuse the same builder, candidate planning, and verification contracts as canonical vector search

=== SB-13 / Issue #43: Add Filtered ANN Benchmark Harness

Decision:

* Benchmark filtered ANN as a three-way comparison:
** exact filtered scan
** candidate-aware filtered ANN
** ANN then post-filter baseline

Benchmark outputs:

* latency distribution
* throughput
* candidate counts
* rerank counts
* recall
* false positive rate
* memory overhead of candidate handling

Release rule:

* a filtered ANN path can only be called `supported` when it wins materially on representative selective queries and meets documented recall thresholds

== E3 Ticket Resolutions: Canonical Multi-Model Plan and Explain Surface

=== SB-14 / Issue #44: Define MultiModelPlan v1 Contract and Canonical Lowering Interfaces

Decision:

* `MultiModelPlanV1` is the single logical-execution contract for supported multi-model requests.
* The fastest path is to wrap and stabilize existing federated plan machinery rather than build a second planner from scratch.

Contract design:

* logical operators are transport-neutral
* capabilities are attached at operator level
* physical binding is a separate phase
* explain uses the same plan object

Lowering interfaces:

* `SqlLowerer -> MultiModelPlanV1`
* `UqlLowerer -> MultiModelPlanV1`
* `FacadeRequestLowerer -> MultiModelPlanV1`
* `UnifiedRequestLowerer -> MultiModelPlanV1`

Rule:

* the lowerers may differ in parsing, but not in semantic output for equivalent requests

=== SB-15 / Issue #45: Replace Placeholder UQL Lowering

Decision:

* Remove lossy helper flows such as placeholder vector extraction from the production UQL path.
* UQL lowering must emit explicit `VectorSearch`, `DocumentQuery`, `GraphQuery`, `LogsQuery`, or `MetricsQuery` operators plus composition operators like `Join`, `Filter`, and `Project`.

Requirements:

* preserve predicate semantics
* preserve requested top-k and ranking semantics
* preserve explain fidelity

Compatibility strategy:

* retain old helpers only behind tests or transitional adapters
* do not let them remain callable from canonical execution entrypoints

=== SB-16 / Issue #46: Route Federated SQL and Facade Requests into the Shared Plan Contract

Decision:

* Federated SQL and facade-produced requests must both compile into `MultiModelPlanV1`.
* The facade remains a protocol convenience layer, not an execution fork.

Key rule:

* SQL extensions are part of the canonical supported surface only insofar as they lower into supported `MultiModelPlanV1` operators and pass capability validation

Implications:

* generic SQL that cannot lower honestly is rejected
* function-backed SQL remains supported where explicit lowerers exist
* facade strategies must produce the same operator graph as direct execution for equivalent requests

=== SB-17 / Issue #47: Unify Explain Schema and Protocol Payloads

Decision:

* Introduce one protocol-neutral explain DTO in `src/query/explain.rs`.
* REST, gRPC, SQL explain, and unified explain wrap the same DTO instead of building separate payloads.

Explain requirements:

* stable operator IDs
* operator kind
* logical inputs and outputs
* capability requirements
* chosen bindings
* fallback reasons
* estimated costs where available
* validity and failure causes

Compatibility:

* if older consumers need a legacy shape, use a transport adapter layer only
* do not fork explain generation logic

=== SB-18 / Issue #48: Remove or Privatize Degraded execute_parallel Production Entrypoints

Decision:

* There must be one production execution entry:
** validated plan
** bound services
** canonical executor
* `execute_parallel*` helpers may remain only if:
** private to tests or benchmarks
** not callable from supported public paths
** clearly marked as non-canonical

Failure rule:

* no supported request may bypass plan validation or capability checks through a convenience helper

=== SB-19 / Issue #49: Close the Scan Honesty Gap

Decision:

* Support only a narrow provider-backed scan surface on the canonical path.
* Do not present general SQL scan completeness.

Supported initial scan shape:

* provider-backed read
* projection
* simple filters that the provider can evaluate or preserve as residual
* limit
* optionally ordered reads only where provider contract is explicit

Unsupported shapes:

* generic scan over subsystems that have no provider-backed execution contract
* scan plus unsupported joins or aggregates beyond the canonical narrow surface

Validation rule:

* unsupported scan plans fail capability validation with explicit provider or feature mismatch details

=== SB-20 / Issue #50: Add Parity and Plan-Contract Tests for SQL, UQL, REST, and gRPC

Decision:

* Add a cross-protocol contract suite as a tranche-closing requirement.
* This is not optional polish. It is the proof that the canonical plan actually exists.

Required suites:

* SQL vs UQL logical parity
* REST vs gRPC explain parity
* facade vs direct execution parity
* scan support and scan rejection parity
* vector plus graph plus document plus observability representative operator parity

Artifacts:

* plan snapshots
* explain payload fixtures
* capability error fixtures
* selected execution result parity fixtures

== Cross-Ticket Dependency Resolutions

The major inter-ticket ambiguities are resolved as follows:

* `SB-02` must finish before `SB-08` because filter/operator support needs registry-backed honesty, especially for unsupported predicates and ANN backends.
* `SB-03` and `SB-14` are linked by design: plan nodes carry capability requirements from the beginning, so `MultiModelPlanV1` does not need a second requirement system.
* `SB-10` and `SB-11` share one backend contract but allow different internal strategies per backend.
* `SB-17` depends on `SB-14` and `SB-16`, but explain DTO design should begin early so operator IDs and diagnostics are stable while lowerers are implemented.
* `SB-19` is intentionally narrow to prevent generic SQL scope creep from destabilizing the tranche.
* `SB-20` is the gating evidence that E1 through E3 are actually converged.

== Quality Bar and Closure Conditions

No ticket in this tranche should be marked complete unless its design-level closure conditions are satisfied:

* `SB-01` through `SB-07`: capability registry exists, validates public plans, produces deterministic artifacts, and drives generated support docs
* `SB-08` through `SB-13`: filtered ANN path is end-to-end correct, benchmarked, and graph-first compatible
* `SB-14` through `SB-20`: one canonical plan and explain contract is used by all supported entrypoints, degraded execution shortcuts are removed, and scan support is honest

Tranche-level closure requires all of the following:

* issues `#31` through `#50` are implemented against the contracts in this document
* milestone `E1-E3 Tranche` has no open design ambiguities left for capability validation, filtered ANN semantics, or canonical plan ownership
* project `ProximaDB E1-E3 Execution (2026Q2)` reflects implementation progress rather than unresolved architecture churn

== Recommended Next Engineering Moves

After this design-resolution document is accepted, the next clean implementation order is:

1. land `SB-01` through `SB-05` together so unsupported behavior fails early before deeper vector or plan work begins
2. land `SB-08` through `SB-10` with the new filter and candidate contracts before backend-specific ANN tuning
3. land `SB-14` through `SB-17` as one canonical plan-plus-explain convergence slice
4. finish `SB-11`, `SB-12`, `SB-18`, and `SB-19` only after the above contracts are live
5. treat `SB-07`, `SB-13`, and `SB-20` as release gates, not optional trailing cleanup

Primary principle:

*Do not let the board devolve into parallel code churn that invents a second capability model, a second filter model, or a second multi-model plan.*
