ADR-style execution blueprint for moving ProximaDB from broad but uneven multi-model behavior to a canonical, capability-driven, native-storage, operator-grade platform. This document converts the March 2026 re-evaluation into the first 10 engineering epics, their ownership boundaries, acceptance criteria, and dependencies.

Primary rule:

*one canonical execution path per supported capability, one native durability model per subsystem, and no production claim without passing contract tests on the public path.*

== Scope

This blueprint covers the first 10 engineering epics needed to harden:

* vector plus metadata retrieval
* canonical multi-model planning and execution
* graph query execution
* document-native persistence and pruning
* observability query parity and exploration
* cross-model consistency semantics
* distributed transport and replication correctness
* backup, restore, and release-quality verification

This blueprint does not authorize broader surface expansion. If a feature is not on the canonical path, it is not part of the supported product surface.

== Design Guardrails

* Canonical path first. Public entrypoints must traverse the same planning and execution contracts.
* Capability-driven planning. Unsupported operators fail planning, not execution, and never degrade to empty success results.
* Native storage per model. Vector, graph, document, and observability may share control-plane contracts, but not placeholder persistence hacks.
* Immutable data plus background compaction. WAL or append log for ingest, immutable segments for reads, compaction for maintenance.
* Recovery is part of the feature. Every durable feature ships with restart, duplicate-message, and corruption-path coverage.
* Honest maturity tiers. Supported, beta, and experimental are generated from code-level capabilities and test results, not from aspirational docs.

== Epic Workstreams

=== E1: Capability Registry and Supported Surface Generation

Execution ticket:: link:E1_CAPABILITY_REGISTRY_EXECUTION_TICKET.adoc[E1 Capability Registry Execution Ticket]

ADR summary::
Adopt one capability registry that is consulted before planning and before public execution. Generate support-tier artifacts from code-level capability snapshots and contract-test results.

Context::
Capability knowledge is currently spread across store traits, columnar providers, index internals, and documentation. This allows unsupported paths to remain visible and lets product claims drift from the live public path.

Decision::
Introduce a first-class capability layer composed of:

* `CapabilityDescriptor` as the normalized description of what a subsystem can do
* `CapabilityRegistry` as the runtime and test-time source of truth
* `PlanValidator` as a pre-execution gate
* `ExecutionCapabilityError` for fail-fast unsupported-plan outcomes
* generated support artifacts derived from capability snapshots and CI results

Primary owner modules::

* `src/storage/multimodel/traits.rs`
* `src/query/unified_query_optimizer.rs`
* `src/query/federated/*`
* `src/query/columnar/provider.rs`
* `docs/SUPPORTED_SURFACE.adoc`
* new `src/query/capabilities/*`

Deliverables::

* unified capability model spanning stores, indexes, query operators, and protocols
* plan-time validation for all REST, gRPC, SQL, and UQL entrypoints
* generated support-matrix pipeline backed by a machine-readable capability artifact
* structured diagnostics that expose `used_capabilities`, `missing_capabilities`, and `degraded=false`

Acceptance criteria::

* All public query entrypoints validate capability requirements before execution.
* Unsupported graph, document, observability, or scan operators return structured capability errors.
* `SUPPORTED_SURFACE` is generated from code-level artifacts plus contract-test results.
* No production path returns success when a required dependency is absent.

Deferred scope::

* market-facing docs refresh outside the generated support matrix
* capability-driven autoscaling or resource management

=== E2: Filtered ANN Candidate Pipeline

Execution ticket:: link:E2_FILTERED_ANN_EXECUTION_TICKET.adoc[E2 Filtered ANN Execution Ticket]

ADR summary::
Make metadata-aware vector retrieval a staged pipeline: normalized filter -> candidate set -> ANN search -> exact rerank -> MVCC and metadata verification.

Context::
The current vector path has the right pieces but not one coherent pipeline. Filters can be lost before AXIS execution, while AXIS itself has a metadata index and query types that are not fully used on the live path.

Decision::
Create a candidate-set architecture centered on a normalized filter contract:

* `NormalizedFilter` lowered from `FilterExpression`
* `CandidateSet` abstraction for exact IDs, metadata-index hits, bloom-pruned candidates, or universal scan
* `HybridQueryBuilder` that fills `metadata_filters` and `id_filters`
* ANN index adapters that can accept candidate restrictions or post-filter contracts explicitly
* exact baseline and recall benchmark harness

Primary owner modules::

* `src/services/operations/vectors.rs`
* `src/index/axis/management/manager.rs`
* `src/core/search/metadata_filter_pushdown.rs`
* `src/index/axis/indexes/*`
* `src/services/tests/index_first_search_tests.rs`

Deliverables::

* filter normalizer and candidate-set interfaces
* AXIS query path that applies metadata and ID constraints intentionally
* planner diagnostics exposing candidate counts, index choice, exact-vs-approximate mode, and rerank counts
* differential benchmark suite against exact scan baselines

Acceptance criteria::

* The canonical ANN path no longer constructs `HybridQuery` with empty metadata filters when a request contains filters.
* Exact filtered search matches the baseline result set for supported operators.
* ANN filtered search meets documented recall targets against the exact baseline on benchmark corpora.
* Benchmarks show filtered ANN materially outperforming exact scan for selective filters on representative collections.

Deferred scope::

* learned retrieval policies beyond adaptive heuristic selection
* cross-model indexes that combine vector and graph and document state in one physical structure

=== E3: Canonical Multi-Model Plan and Explain Surface

Execution ticket:: link:E3_MULTIMODEL_PLAN_EXECUTION_TICKET.adoc[E3 Multi-Model Plan Execution Ticket]

ADR summary::
Collapse SQL extensions, UQL, REST, and gRPC request lowering onto one typed `MultiModelPlan` and one explainable execution graph.

Context::
The physical planning substrate is substantial, but there are still multiple entry semantics and incomplete scan support. The result is drift between what parses, what plans, and what runs.

Decision::
Introduce `MultiModelPlan v1` as the only production lowering target:

* syntactic fronts remain separate
* logical lowering converges to one IR
* physical planning uses one capability-aware operator graph
* `EXPLAIN` and execution diagnostics are protocol-independent
* unsupported relational scans are either implemented through columnar providers or gated off explicitly

Primary owner modules::

* `src/query/federated/*`
* `src/query/unified/*`
* `src/query/facade/*`
* `src/query/columnar/*`
* `src/network/rest/v1/*`
* `src/api_handlers/*`

Deliverables::

* shared logical plan and physical execution contracts
* one `EXPLAIN` schema with operator IDs, capabilities, cost, and fallback reasons
* stable operator set for vector search, document query, graph traversal, observability query, and joins
* plan validator that rejects unsupported plan nodes before dispatch

Acceptance criteria::

* REST, gRPC, SQL, and UQL multi-model queries traverse the same plan compiler and executor.
* `EXPLAIN` output is stable across protocols for the same logical query.
* Generic relational scans are either backed by `ColumnarReadProvider` implementations or rejected by the planner with a capability error.
* Production execution no longer depends on side paths that bypass the canonical plan contract.

Deferred scope::

* optimizer search-space expansion for non-canonical or experimental operators
* external compute-engine adapters beyond what is required for canonical execution

=== E4: Graph IR and ORION Canonicalization

ADR summary::
Introduce a graph IR above service calls and make ORION the canonical execution backend for supported graph behavior. Treat language adapters and future engines as pluggable frontends and backends to the same graph contract.

Context::
ORION is the only honest canonical graph engine today, but declarative query execution still depends on facade routing and partial Cypher-like translation. Traversal APIs and declarative APIs are not yet one system.

Decision::
Build `GraphIR` with operators such as:

* `NodeScan`
* `NodeSeek`
* `Expand`
* `EdgeFilter`
* `PathMatch`
* `ShortestPath`
* `Aggregate`
* `Project`

Then execute that IR through ORION first. PULSAR and QUASAR remain adapters behind the same IR only after they satisfy the contract.

Primary owner modules::

* `src/graph/service.rs`
* `src/graph/service_engine_factory.rs`
* `src/query/facade/strategies/graph.rs`
* `src/network/rest/v1/graph.rs`
* `src/storage/entity_store/*`
* new `src/graph/query/ir/*`

Deliverables::

* typed graph IR and lowering from declarative and traversal surfaces
* ORION execution adapter for the IR
* completion of edge type and property filters, `if_exists` semantics, and graph stats accuracy
* parity tests across REST, gRPC, and facade-based graph execution

Acceptance criteria::

* Declarative graph queries no longer return `NOT_IMPLEMENTED` on the canonical supported path.
* Overlapping declarative and traversal requests produce equivalent results.
* Edge property and edge type filtering are supported on the public path.
* ORION remains the only default graph engine until PULSAR or QUASAR pass the same graph IR contract suite.

Deferred scope::

* broad language parity with every Neo4j Cypher extension
* graph-algorithm catalog expansion beyond supported ORION behavior

=== E5: Document-Native Segments and Pruning

ADR summary::
Replace placeholder vector-record persistence for documents with immutable document-native segments, typed projections for hot fields, and real path-aware pruning.

Context::
The document hot path is real, but cold-tier persistence still serializes documents into vector records with placeholder vectors. This blocks clean pruning, clean indexing, and a credible document engine story.

Decision::
Keep the current WAL and hot cache, but flush to a document-native cold tier with:

* immutable document segments
* path dictionary and typed field registry
* zonemaps and bloom filters
* optional columnar projections for frequently queried paths
* full-text sidecar indexes on disk
* background compaction and segment merge

Primary owner modules::

* `src/storage/document/service.rs`
* `src/storage/document/storage/document_block.rs`
* `src/storage/document/storage/cold_tier.rs`
* `src/storage/document/query/path_parser.rs`
* `src/storage/document/indexes/*`
* `src/storage/multimodel/stores/document_store.rs`

Deliverables::

* segment format and segment manifest
* hot plus cold query merger with deterministic semantics
* complete path-filter evaluation and block pruning
* disk-backed full-text index integration
* migration path for existing placeholder-based cold-tier data

Acceptance criteria::

* New document flushes do not rely on placeholder vector records for persistence.
* `query_documents()` returns equivalent results whether data is hot, cold, or mixed.
* Block-level pruning reduces scanned documents for selective path filters on benchmark datasets.
* Full-text document search survives restart and rebuild.

Deferred scope::

* geospatial indexing until segment and path execution semantics are stable
* full distributed document sharding

=== E6: Observability Signal Indexes and Exploration

ADR summary::
Treat logs, metrics, and traces as one telemetry plane with signal-native indexes and one canonical exploration API surface.

Context::
The service layer already has meaningful time-range and service-based trace query support, but the trait bridge and some public surfaces still expose partial behavior. Observability is ahead of its external execution contract.

Decision::
Unify observability around:

* append-only ingest
* signal-native indexes for logs, metrics, and traces
* one canonical service API for exploration queries
* protocol adapters that lower to that API without feature loss
* graph and entity correlation fields as first-class metadata

Primary owner modules::

* `src/observability/mod.rs`
* `src/observability/storage/mod.rs`
* `src/observability/query/*`
* `src/storage/multimodel/stores/observability_store.rs`
* protocol handler modules under `src/network/*`

Deliverables::

* full trait-bridge parity with service trace APIs
* OTLP gRPC transport in addition to existing HTTP and JSON paths
* trace and service and time exploration endpoints
* correlation queries joining traces, logs, metrics, and graph-linked entities

Acceptance criteria::

* Time-range and service-based trace queries work through the canonical public API and do not degrade to empty results.
* OTLP gRPC ingest passes end-to-end integration tests.
* Logs, metrics, and traces can be queried with shared correlation identifiers.
* Observability exploration surfaces are explicitly documented as supported or beta from capability artifacts.

Deferred scope::

* full Datadog or Splunk parity for alerting, UI, and ecosystem breadth
* multi-region observability federation

=== E7: Transaction Classes and Durable Cross-Model Commit

ADR summary::
Replace implicit "ACID everywhere" assumptions with explicit transaction classes and durable cross-model commit only where the engines can actually honor it.

Context::
The transaction substrate exists, and some staged participants are real, but live-engine durability is still incomplete. A future-proof solution must distinguish local ACID from same-node durable 2PC and from asynchronous projection workflows.

Decision::
Introduce three transaction classes:

* `LocalStrict` for single-engine strict ACID
* `SameNodeDurable2PC` for same-process or same-node multi-engine durable transactions
* `AsyncProjection` for outbox or saga-driven propagation where strict cross-engine atomicity is not available

Then implement:

* durable coordinator decision logging
* idempotent participant prepare and commit and abort
* prepared handles and recovery state
* outbox and replay path for async projections

Primary owner modules::

* `src/transaction/*`
* `src/storage/multimodel/transaction/*`
* `src/storage/transaction/*`
* vector, document, graph, and observability service modules that own write sets

Deliverables::

* transaction-class selection rules and API exposure
* durable coordinator log and recovery sweeper
* concrete participant adapters where supported
* outbox contract for unsupported strict-atomic combinations

Acceptance criteria::

* Every multi-model write path declares its transaction class explicitly.
* `prepare()` means durable and crash-recoverable for every participant that votes yes.
* Duplicate commit and abort messages are idempotent.
* Unsupported combinations fail or route to `AsyncProjection`; they do not silently masquerade as ACID.

Deferred scope::

* cross-cluster distributed transactions
* broad serializable guarantees for experimental engines

=== E8: Distributed Data Plane and RPC Productization

ADR summary::
When distributed mode is enabled, ProximaDB must use real transport, real apply-before-ack replication, and real snapshot semantics. Handler-based or simulated fallback remains valid only for local development and tests.

Context::
The codebase contains strong distributed foundations, but the public story is still undermined by unified-mode fallback, handler-registry execution, simulated replication paths, and incomplete snapshot installation.

Decision::
Split local simulation from distributed mode clearly:

* local mode may use loopback adapters for development
* distributed mode requires fully wired transport and node registry
* replication uses apply-before-ack semantics
* snapshot installation is staged, checksummed, and atomically promoted
* remote query execution uses real gRPC-backed contracts

Primary owner modules::

* `src/query/distributed/*`
* `src/cluster/rpc/*`
* `src/cluster/replication.rs`
* `src/cluster/consensus.rs`
* `src/network/multi_server.rs`
* graph distributed modules under `src/graph/engines/pulsar/*`

Deliverables::

* explicit local-vs-distributed mode boundary
* real RPC-backed remote execution
* replication and catch-up paths with apply-before-ack
* completed snapshot install and restore semantics
* 3-node cluster reference topology and failure test harness

Acceptance criteria::

* Distributed mode fails startup if transport or registry wiring is incomplete.
* Remote execution no longer depends on registered handler shortcuts on the supported path.
* Replication acknowledgments are issued only after apply succeeds.
* Snapshot install and catch-up replication pass failure-injection tests.

Deferred scope::

* multi-region routing as a supported surface
* making PULSAR or QUASAR the default graph engine

=== E9: Backup, Restore, and Point-in-Time Recovery

ADR summary::
Turn the local backup and restore substrate into an operator-grade checkpoint and PITR system with cloud targets, resumability, manifest versioning, and integrity guarantees.

Context::
Local incremental backup and manifest-based restore exist, but cloud targets are stubs and recovery is not yet a full operator story.

Decision::
Standardize on:

* manifest versioning
* content-addressed or chunked backup parts
* resumable uploads and downloads
* end-to-end checksums
* restore planner by backup ID, LSN, and time
* cluster-aware checkpoint ordering once distributed mode is real

Primary owner modules::

* `src/operations/backup/mod.rs`
* `src/operations/restore/mod.rs`
* WAL and replication owners in `src/storage/*` and `src/cluster/*`
* operational docs under `docs/_internal/operations/*`

Deliverables::

* S3, GCS, and Azure object-store drivers
* manifest v2 with checksums, retention metadata, and dependency chain
* restore planner with point-in-time recovery support
* cluster-consistent backup hooks

Acceptance criteria::

* Backup and restore complete successfully against local filesystem and cloud-emulated targets.
* Interrupted uploads and downloads can resume without data corruption.
* PITR restores to a selected LSN or timestamp on a controlled test dataset.
* Restore verification reports mismatched checksums and partial failures explicitly.

Deferred scope::

* cross-account disaster-recovery orchestration
* managed-service backup UX

=== E10: Verification, Benchmarks, and Release Gates

ADR summary::
Make evidence the promotion gate. Every supported or beta claim must map to a contract suite, a benchmark or fault-injection suite where relevant, and an automated maturity decision.

Context::
The repo now has enough code that documentation drift is a bigger risk than missing modules. The solution is not more prose; it is release gates tied to objective evidence.

Decision::
Establish four persistent verification lanes:

* capability contract tests
* differential correctness tests
* performance and benchmark tests
* failure-injection and recovery tests

Use those lanes to drive maturity promotion and support-matrix generation.

Primary owner modules::

* `tests/*`
* `src/services/tests/*`
* `benches/*`
* `docs/_internal/roadmap/*`
* CI and release automation

Deliverables::

* contract-test suites for vector, graph, document, observability, and transaction behavior
* exact-vs-optimized differential suites
* benchmark baselines for filtered ANN, graph traversal, document pruning, and observability query paths
* release gate definitions for supported, beta, and experimental tiers

Acceptance criteria::

* No supported capability can be promoted without a contract suite and public-path integration coverage.
* Performance-sensitive claims are backed by repeatable benchmark artifacts.
* Recovery-sensitive claims are backed by restart and duplicate-message tests.
* Documentation updates fail CI when they exceed the generated support matrix or verified benchmark envelope.

Deferred scope::

* vanity benchmark comparisons not tied to a release decision
* broad coverage-percentage goals without subsystem-level risk targeting

== Sequencing Guidance

=== First 90 Days

* Finish E1 first and use it to cut unsupported branches from the canonical path.
* Run E2 and E3 immediately after E1; these are the fastest path to a coherent query core.
* Start E10 in parallel with E1 and keep it active through all later epics.

=== Days 90-180

* Land E4, E5, and E6 on top of the canonical plan contract.
* Do not start durable multi-model promotion work from E7 until at least one supported path exists for each of graph, document, and observability writes.

=== Days 180+

* Treat E8 and E9 as a coupled operator-readiness tranche after E7 durability contracts stabilize.
* Keep distributed and cloud claims beta or experimental until E8 and E9 both pass fault-injection and restore tests.

== Promotion Rules

* A feature moves to `Supported` only after E1 capability declaration, E10 contract coverage, and public-path parity are complete.
* A feature remains `Beta` if the core behavior works but operator gaps or recovery gaps remain.
* A feature remains `Experimental` if it depends on simulation, missing transport, placeholder storage, or partial recovery semantics.

== Immediate Next Actions

1. Use E1 to create the capability registry skeleton and generated support-matrix artifact.
2. Open implementation branches or epics for E2 and E3 as the first concurrent engineering stream.
3. Define the E10 contract-test matrix before expanding graph, document, or observability surfaces further.
