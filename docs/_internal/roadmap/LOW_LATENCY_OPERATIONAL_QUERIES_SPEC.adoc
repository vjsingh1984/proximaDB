= Low-Latency Operational Query Engine Specification
:toc: left
:toclevels: 3
:sectnums:

== Executive Summary

This specification defines a low-latency operational query engine for ProximaDB that enables real-time analytics on lakehouse architectures using open formats (Parquet, Delta Lake, Apache Arrow). The system bridges the gap between high-throughput analytical queries and low-latency operational queries without requiring proprietary formats.

**Key Objectives:**

* Sub-second latency for operational queries on Parquet/Delta Lake datasets
* Zero-copy data movement using Apache Arrow memory format
* Vectorized query execution with CPU SIMD acceleration
* Predicate pushdown and column pruning at storage layer
* Integration with existing ProximaDB vector search and graph capabilities
* 100% open format stack - no proprietary lock-in

**Target Use Cases:**

* Real-time dashboards and BI tools (< 1 second response)
* Operational monitoring and alerting
* Interactive data exploration
* High-concurrency API workloads
* Hybrid vector + operational queries

== Background: Lakehouse Operational Queries

=== The Lakehouse Paradigm

Lakehouse architectures combine the best elements of data lakes and data warehouses:

* **Data Lake Benefits**: Low-cost storage, open formats, flexibility
* **Data Warehouse Benefits**: ACID transactions, schema enforcement, fast queries

=== Current Market Landscape

Several commercial solutions address operational queries on lakehouse data:

* **Databricks Photon**: Native C++ query engine with vectorized execution
* **Azure Synapse**: Serverless SQL pools on Delta Lake
* **Google BigQuery**: Anthos and BigQuery Omni for hybrid deployments
* **Snowflake**: Separation of storage and compute with elastic warehouses
* **Starburst/Trino**: Distributed SQL engine with federated queries

=== The "Proprietary Format" Problem

Many vendors create competitive moats using proprietary formats:

* Delta Lake (Databricks) - patent-encumbered transaction log format
* Snowflake - proprietary micro-partition format
* Apache Iceberg - open but complex metadata requirements
* Apache Hudi - complex timeline management

**Our Strategy**: Use Apache Parquet + Apache Arrow + custom Delta-like transaction layer with open specifications, avoiding patent-encumbered formats.

=== Query Processing Pipeline

==== 1. Query Parsing and Validation

* SQL-99 compliant parser with extensions for vector/graph operations
* Semantic analysis and type checking
* Permission verification

==== 2. Logical Plan Generation

* Convert parsed SQL to logical operators (Scan, Filter, Project, Join, Aggregate)
* Apply query rewrites based on rules
* Validate against catalog schema

==== 3. Physical Planning

* Convert logical plan to physical execution plan
* Choose algorithms (e.g., hash join vs. sort-merge join)
* Determine data partitioning strategy

==== 4. Cost-Based Optimization

* Statistics-based cost estimation
* Cardinality estimation using histograms
* Join order optimization using dynamic programming
* Multi-objective optimization (latency vs. throughput)

==== 5. Vectorized Execution

* Operator-at-a-time execution model
* Apache Arrow batches as unit of computation
* CPU SIMD acceleration for arithmetic operations
* Just-in-time compilation for hot paths

=== Storage Layer Integration

==== Parquet Optimization Techniques

===== Predicate Pushdown

* Filter predicates pushed to Parquet reader
* Leverage Parquet statistics (min/max, null counts)
* Skip entire row groups that don't match predicates
* Bloom filter support for equality predicates

===== Column Pruning

* Read only required columns from Parquet files
* Reduce I/O bandwidth requirements
* Lower memory footprint

===== Row Group Selection

* Use partition-level statistics
* Partition pruning based on query predicates
* Co-located reads for spatial locality

===== Adaptive Row Group Size

* Default: 128MB row groups for balanced scan vs. seek
* Configurable based on query patterns
* Small row groups for low-latency queries
* Large row groups for high-throughput scans

==== Delta Lake Transaction Layer

* ACID transactions using optimistic concurrency control
* Snapshot isolation for consistent reads
* Time travel via transaction log replay
* Schema evolution support

**Custom Implementation Strategy:**

* Use Parquet as data file format
* Implement custom transaction log in JSONL format (open specification)
* Atomic file operations via rename (POSIX guarantees)
* No patent-encumbered Delta Lake protocol

==== Apache Arrow Integration

* Zero-copy data movement between storage and execution
* Columnar memory format for efficient vectorization
* Shared memory for inter-process communication
* Arrow Flight for high-throughput data transfer

== Performance Optimizations

=== CPU Vectorization

* SIMD operations for arithmetic, comparisons, string operations
* Compiler auto-vectorization with explicit SIMD intrinsics fallback
* Target architectures: AVX2, AVX-512, NEON (ARM), SVE (ARM)

=== Memory Management

* Arrow memory pool with allocation tracking
* Memory-mapped files for zero-copy access
* Buffer reuse across operators
* Adaptive memory management based on workload

=== Parallel Execution

* Multi-threaded execution using Rayon thread pool
* Work-stealing scheduler for load balancing
* Partition-level parallelism for scans
* Pipeline parallelism for multi-stage queries

=== Caching Strategy

* Query result cache with TTL-based invalidation
* Parquet metadata cache (footers, statistics)
* Filtered page cache for hot data
* Adaptive cache sizing based on workload

=== Adaptive Execution

* Runtime statistics collection
* Re-optimization at runtime based on actual cardinalities
* Choose between hash join and sort-merge join based on data sizes
* Adaptive parallelism degree

== Integration with ProximaDB

=== Hybrid Query Capabilities

==== Vector + Operational Queries

```sql
-- Find products similar to a given vector within a price range
SELECT
    product_id,
    name,
    price,
    VECTOR_DISTANCE(embedding, [0.1, 0.2, ...]) AS distance
FROM products
WHERE
    price BETWEEN 50 AND 100
    AND category = 'electronics'
ORDER BY distance
LIMIT 10;
```

==== Graph + Operational Queries

```sql
-- Find products frequently purchased together
SELECT
    p1.product_id,
    p2.product_id,
    COUNT(*) AS co_purchase_count
FROM purchases p1
JOIN GRAPH_EDGE('purchases', 'customer_id', 'product_id') g
    ON p1.product_id = g.from_id
JOIN purchases p2 ON p2.product_id = g.to_id
WHERE p1.purchase_date > CURRENT_DATE - INTERVAL '30 days'
GROUP BY p1.product_id, p2.product_id
ORDER BY co_purchase_count DESC
LIMIT 100;
```

== Risk Mitigation

=== Technical Risks

==== Risk 1: Complexity of Cost-Based Optimization

**Mitigation**:

* Start with rule-based optimization
* Gradually introduce cost-based optimization
* Leverage Apache DataFusion's optimizer
* Extensive benchmarking and profiling

==== Risk 2: Memory Management Complexity

**Mitigation**:

* Use Arrow memory pool for automatic management
* Implement memory limits and spill-to-disk
* Extensive memory leak testing
* Memory profiling in CI/CD

==== Risk 3: Transaction Serialization Bottlenecks

**Mitigation**:

* Use optimistic concurrency control
* Partition transaction log by table
* Implement transaction batching
* Fallback to serializable isolation only when needed

== Appendix

=== A. Query Examples

==== Simple Filtering

```sql
SELECT product_id, name, price
FROM products
WHERE category = 'electronics' AND price < 100
LIMIT 100;
```

==== Aggregation

```sql
SELECT
    category,
    AVG(price) AS avg_price,
    COUNT(*) AS product_count
FROM products
GROUP BY category
HAVING COUNT(*) > 100
ORDER BY avg_price DESC;
```

==== Join

```sql
SELECT
    p.product_id,
    p.name,
    o.order_id,
    o.order_date
FROM products p
JOIN orders o ON p.product_id = o.product_id
WHERE o.order_date > CURRENT_DATE - INTERVAL '7 days';
```

==== Hybrid Vector Search

```sql
SELECT
    p.product_id,
    p.name,
    p.category,
    VECTOR_DISTANCE(p.embedding, [0.1, 0.2, ...]) AS distance
FROM products p
WHERE
    p.price BETWEEN 50 AND 200
    AND p.stock_quantity > 0
ORDER BY distance
LIMIT 10;
```

==== Time Travel

```sql
-- Query data as of 1 hour ago
SELECT * FROM products
FOR SYSTEM_TIME AS OF SYSTEM_TIMESTAMP - 3600
WHERE category = 'electronics';
```

=== C. Glossary

* **Lakehouse**: Architecture combining data lake and data warehouse features
* **Operational Query**: Low-latency, interactive query (< 1 second)
* **Vectorized Execution**: Process data in batches using CPU vector instructions
* **Predicate Pushdown**: Move filter conditions to storage layer for early pruning
* **Column Pruning**: Read only required columns from storage
* **Time Travel**: Query historical data via transaction log replay
* **Snapshot Isolation**: Consistent read view at a point in time
* **SIMD**: Single Instruction, Multiple Data - CPU parallel processing
