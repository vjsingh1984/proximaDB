== Overview

ProximaDB automatically detects and utilizes available hardware capabilities. This guide helps you optimize your deployment for maximum performance.

=== Hardware Detection at Startup

[source,text]
----
$ RUST_LOG=info proximadb-server

  CPU: AMD EPYC 7763 64-Core (128 threads)
  SIMD: AVX2, AVX-512, FMA
  Memory: 512 GB DDR4
  Storage: NVMe SSD (3.5 GB/s read)
  Cache: L1=32KB, L2=512KB, L3=256MB

[INFO] Optimizations Enabled:
  - AVX-512 distance computation
  - VNNI INT8 acceleration
  - Memory-mapped file I/O
  - NUMA-aware allocation
----

=== Check CPU Capabilities

[source,bash]
----
# Linux: Check CPU flags
grep -E 'avx|sse|neon' /proc/cpuinfo | head -1

# macOS: Check CPU features
sysctl -a | grep -E 'cpu.features'

# Verify ProximaDB detection
RUST_LOG=proximadb::compute=debug proximadb-server 2>&1 | grep -i simd
----

=== CPU Affinity (NUMA)

For multi-socket servers:

[source,toml]
----
[server]
# Pin to specific NUMA node
numa_node = 0

# Or use all nodes with interleaving
numa_policy = "interleave"

# Thread pool sizing
worker_threads = 64        # Match physical cores
background_threads = 8     # For compaction, indexing
----

[source,bash]
----
# Linux: Run on specific NUMA node
numactl --cpunodebind=0 --membind=0 proximadb-server

# Verify NUMA allocation
numastat -p $(pgrep proximadb)
----

=== Thread Pool Tuning

[source,toml]
----
[server]
# Query processing threads (CPU-bound)
worker_threads = 32             # Physical cores (not hyperthreads)

# I/O threads (for async operations)
io_threads = 16                 # Half of worker threads

# Background tasks
compaction_threads = 4
index_build_threads = 4

# Thread stack size (reduce for many threads)
thread_stack_size_kb = 512
----

=== Recommended CPU Configurations

[cols="2,3,3", options="header"]
|===
| Workload | CPU Recommendation | Why
| High QPS (>10K) | Many cores, high clock | Parallel query processing
| Large datasets | High L3 cache | Keep hot data close
| Batch analytics | AVX-512 support | Vector operations
| Mixed workload | Balanced cores + clock | Flexibility
|===

== Memory Optimization

=== Memory Sizing

[source,text]
----
Minimum Memory Formula:
  Base overhead:           ~500 MB
  Per collection:          ~100 MB
  Per million vectors:     Depends on dimension and quantization

Example (10M vectors, 1536 dims, INT8):
  Vectors: 10M × 1536 × 1 byte = 14.3 GB
  Index (HNSW): ~2 GB
  Metadata: ~2 GB
  Working memory: ~4 GB
  Total: ~23 GB (recommend 32 GB)
----

=== Memory Configuration

[source,toml]
----
[storage]
# Memory-mapped files
mmap_enabled = true
mmap_populate = true          # Prefault pages (slower start, faster queries)

# Cache sizes
block_cache_size_mb = 8192    # 8 GB for frequently accessed blocks
metadata_cache_size_mb = 1024 # 1 GB for metadata
index_cache_size_mb = 4096    # 4 GB for HNSW graph

# Memory limits
max_memory_usage_gb = 64      # Hard limit
memory_warning_threshold = 0.8 # Alert at 80%
----

=== Huge Pages

Enable huge pages for large deployments:

[source,bash]
----
# Linux: Enable huge pages
echo 'vm.nr_hugepages=4096' >> /etc/sysctl.conf
sysctl -p

# Verify
grep -i huge /proc/meminfo

# Run with huge pages
MALLOC_ARENA_MAX=2 proximadb-server
----

[source,toml]
----
[server]
use_huge_pages = true
huge_page_size_mb = 2         # 2MB or 1GB pages
----

=== Memory-Mapped I/O

[source,toml]
----
[storage]
mmap_enabled = true

# mmap settings
mmap_read_ahead_kb = 256      # Prefetch size
mmap_advise = "sequential"    # For scans: sequential, random
mmap_lock = false             # Lock pages in RAM (requires privileges)
----

=== NUMA Memory Allocation

[source,toml]
----
[server]
# Allocate memory on local NUMA node
numa_local_alloc = true

# Or use specific node
numa_memory_node = 0

# Interleave for balanced access
numa_interleave = false
----

== Storage Optimization

=== SSD vs HDD

[cols="2,2,2,2", options="header"]
|===
| Metric | NVMe SSD | SATA SSD | HDD
| Random Read | 500K IOPS | 100K IOPS | 150 IOPS
| Sequential Read | 7 GB/s | 550 MB/s | 200 MB/s
| Latency | 10-20 μs | 50-100 μs | 5-10 ms
| Recommendation | Production | Development | Not recommended
|===

=== Storage Configuration

[source,toml]
----
[storage]
data_dir = "/nvme/proximadb/data"

# Multiple storage paths for parallelism
[[storage.storage_locations]]
url = "file:///nvme1/proximadb"
weight = 1

[[storage.storage_locations]]
url = "file:///nvme2/proximadb"
weight = 1

# I/O settings
direct_io = true              # Bypass OS cache (for dedicated DB)
io_uring_enabled = true       # Linux 5.1+ async I/O
read_ahead_kb = 256
write_buffer_size_mb = 64
----

=== NVMe Optimization

[source,bash]
----
# Check NVMe capabilities
nvme list
nvme id-ctrl /dev/nvme0

# Set I/O scheduler (Linux)
echo 'none' > /sys/block/nvme0n1/queue/scheduler

# Increase queue depth
echo 1024 > /sys/block/nvme0n1/queue/nr_requests

# Enable write caching
nvme set-feature /dev/nvme0 -f 0x06 -v 1
----

=== Filesystem Tuning

[source,bash]
----
# XFS (recommended for large files)
mkfs.xfs -f -d su=256k,sw=4 /dev/nvme0n1
mount -o noatime,nodiratime,logbufs=8 /dev/nvme0n1 /data

# ext4 alternative
mkfs.ext4 -E stride=64,stripe-width=256 /dev/nvme0n1
mount -o noatime,nodiratime,data=writeback /dev/nvme0n1 /data
----

=== RAID Configuration

[source,text]
----
Recommended: RAID 10 (for balanced performance + redundancy)
Alternative: RAID 0 (maximum performance, no redundancy)
Avoid: RAID 5/6 (write penalty)

NVMe: Consider software RAID (mdadm) or ZFS
      Enterprise NVMe often doesn't need RAID due to internal redundancy
----

== Network Optimization

=== TCP Tuning

[source,bash]
----
# /etc/sysctl.conf

# Increase buffer sizes
net.core.rmem_max = 16777216
net.core.wmem_max = 16777216
net.ipv4.tcp_rmem = 4096 87380 16777216
net.ipv4.tcp_wmem = 4096 65536 16777216

# Connection handling
net.core.somaxconn = 65535
net.ipv4.tcp_max_syn_backlog = 65535

# Reduce TIME_WAIT
net.ipv4.tcp_tw_reuse = 1
net.ipv4.tcp_fin_timeout = 15

# Enable TCP fast open
net.ipv4.tcp_fastopen = 3

# Apply
sysctl -p
----

== Summary

=== Quick Optimization Checklist

[source,text]
----
□ CPU: Enable AVX-512 if available
□ CPU: Set worker_threads = physical cores
□ CPU: Configure NUMA affinity for multi-socket
□ Memory: Size for dataset + 30% headroom
□ Memory: Enable mmap with populate
□ Memory: Consider huge pages for >64GB
□ Storage: Use NVMe SSD
□ Storage: Enable direct I/O for dedicated servers
□ Storage: Use XFS filesystem
□ Network: Tune TCP buffers
□ Network: Enable keepalive and compression
----
