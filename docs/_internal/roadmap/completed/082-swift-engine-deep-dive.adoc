== Overview

SWIFT is ProximaDB's **ultra-low latency engine** using a three-tier hierarchical architecture. It's optimized for small to medium datasets where sub-millisecond response times are critical.

=== Key Characteristics

[cols="2,3", options="header"]
|===
| Metric | Value
| Query Latency | ~95ms (cold), <1ms (warm cache)
| Optimal Dataset Size | <5K vectors
| Tier Count | 3 (hot, warm, cold)
| Memory Model | Tiered with promotion/demotion
| Best For | Real-time systems, low-latency requirements
|===

== Architecture

=== Three-Tier Hierarchy

[source,text]
----
Tier Architecture:
├── Hot Tier (L1 - In-Memory)
│   ├── Frequently accessed vectors
│   ├── Full precision (no compression)
│   ├── O(1) hash lookup
│   └── Automatic promotion from warm
│
├── Warm Tier (L2 - Memory-Mapped)
│   ├── Recently accessed vectors
│   ├── Light compression (LZ4)
│   ├── Memory-mapped files
│   └── Promotion/demotion tracking
│
└── Cold Tier (L3 - Disk)
    ├── Infrequently accessed vectors
    ├── High compression (ZSTD)
    ├── Block-based storage
    └── Prefetch on access pattern
----

== Tier Management

=== Promotion Policy

[source,rust]
----
pub struct PromotionPolicy {
    // Access count threshold for warm -> hot
    pub warm_to_hot_access_count: u32,      // Default: 3

    // Time-based promotion (recent access)
    pub warm_to_hot_recency_ms: u64,        // Default: 1000

    // Batch promotion for related vectors
    pub enable_batch_promotion: bool,       // Default: true
    pub batch_size: usize,                  // Default: 100
}

impl SwiftEngine {
    fn maybe_promote(&self, vector_id: &str) {
        let access_stats = self.get_access_stats(vector_id);

        if access_stats.count >= self.policy.warm_to_hot_access_count
            || access_stats.last_access_ms < self.policy.warm_to_hot_recency_ms
        {
            self.promote_to_hot(vector_id);
        }
    }
}
----

== Search Pipeline

=== Stage 1: Hot Tier Search (O(1))

[source,rust]
----
pub async fn search_hot_tier(&self, query: &Query) -> Option<Vec<SearchResult>> {
    // Hash-based lookup for exact matches
    if let Some(exact) = self.hot_tier.get_exact(&query.vector) {
        return Some(vec![exact]);
    }

    // Small dataset - brute force is fast
    if self.hot_tier.len() < 1000 {
        return Some(self.hot_tier.brute_force_search(query));
    }

    None // Fall through to warm tier
}
----

=== Stage 2: Warm Tier Search

* Memory-mapped file access
* LZ4 decompression (fast)
* Parallel block scanning
* Results merged with hot tier

=== Stage 3: Cold Tier Search

* Disk-based block reading
* ZSTD decompression
* Prefetch optimization
* Final result merge

== Write Path

=== Flush Process

[source,rust]
----
impl SwiftEngine {
    pub async fn flush(&self, vectors: Vec<VectorRecord>) -> Result<()> {
        // 1. New vectors go directly to warm tier
        let compressed = self.compress_lz4(&vectors);

        // 2. Write to warm tier file
        self.warm_tier.append(compressed).await?;

        // 3. Trigger promotion for hot candidates
        for vector in &vectors {
            if self.is_hot_candidate(vector) {
                self.hot_tier.insert(vector.clone());
            }
        }

        // 4. Check for demotion needs
        self.maybe_demote().await
    }
}
----

== Performance Optimizations

=== Cache-Friendly Design

* Hot tier entries cache-line aligned (64 bytes)
* Contiguous memory layout for hot tier
* Prefetching for warm tier sequential access

=== Lock-Free Hot Tier

* DashMap for concurrent access
* Atomic counters for access statistics
* RCU-style updates for tier changes

=== Adaptive Index

* No index for <500 hot vectors (brute force faster)
* Automatic HNSW construction for larger hot tiers
* Index invalidation on tier changes
