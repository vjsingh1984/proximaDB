**Sorted String Table (SST) - High-Performance OLTP-Optimized Storage**

== Overview

SST is ProximaDB's **write-optimized storage engine** using LSM-tree architecture with sophisticated three-stage filtering. It's designed for real-time applications requiring sub-5ms query latency.

== Architecture

=== LSM-Tree Design

[source,text]
----
Write Path:
WAL → MemTable → L0 (flush) → L1+ (compaction)

Storage Hierarchy:
├── L0: Unsorted flush files
├── L1: Sorted, non-overlapping
├── L2-L6: Exponential size multiplier
└── Background compaction threads
----

==== SSTable Index

* Block-level index with key ranges
* Hierarchical bloom filters (global + per-block)
* Block centroids (FP32 + FP16 quantized)
* Z-Order spatial codes for range pruning
* Optional B+ tree for O(log n) lookups

== Three-Stage Filtering Pipeline

=== Stage 1: Bloom Filter Elimination

* File-level global bloom filter
* Per-block bloom filters for metadata
* **95% unnecessary read reduction**

=== Stage 2: Index Entry Block Filtering

* Block centroid-based distance pruning
* Metadata range filtering
* Z-Order spatial code pruning

=== Stage 3: Full Precision Results

* Complete block decompression
* SIMD-optimized distance computation
* Final metadata filtering

== Flush & Compaction

=== Flush Process

[source,rust]
----
1. Sort vectors for optimal SSTable encoding
2. Atomic operation with staging:
   - Begin atomic operation
   - Write to staging directory
   - Commit to final location
3. PCA model training (if ≥100 vectors)
4. Optional collection-level quantization
----

=== Compaction Strategy

* **Level-Based Compaction**: L0 unsorted → L1+ sorted
* **Zero-Copy Merge**: Blocks passed without decompression
* **Exponential Size Multiplier**: 10x between levels
* **Triggers**: L0 ≥ 4 files OR level_size_ratio > 10
