== Overview

This guide covers query optimization techniques for ProximaDB's vector search, SQL queries, and multi-model operations.

=== Query Processing Pipeline

[source,text]
----
Query Flow:
1. Parse & Validate → 2. Plan → 3. Optimize → 4. Execute → 5. Rerank → 6. Return

Optimization Points:
├── Index selection (HNSW vs IVF vs Flat)
├── Quantization strategy
├── Filter ordering
├── Batch processing
└── Caching
----

== Vector Search Optimization

=== Index Parameter Tuning

==== HNSW Parameters

[source,python]
----
# At collection creation
client.create_collection(
    name="optimized_collection",
    dimension=1536,
    index_config={
        "type": "hnsw",
        "m": 16,                # Connections per node (8-64)
        "ef_construction": 200, # Build-time search width (100-500)
    }
)

# At query time
results = client.search(
    collection="optimized_collection",
    vector=query,
    top_k=10,
    search_params={
        "ef_search": 100       # Query-time search width (50-500)
    }
)
----

==== HNSW Tuning Guide

[cols="2,2,2,3", options="header"]
|===
| Parameter | Low | High | Effect
| `m` | 8 | 64 | Memory ↑, Recall ↑, Build time ↑
| `ef_construction` | 100 | 500 | Build time ↑, Recall ↑
| `ef_search` | 50 | 500 | Latency ↑, Recall ↑
|===

==== IVF Parameters

[source,python]
----
client.create_collection(
    name="ivf_collection",
    dimension=1536,
    index_config={
        "type": "ivf",
        "num_lists": 1024,      # sqrt(n) to 4*sqrt(n)
        "num_probes": 32        # 1-10% of num_lists
    }
)

results = client.search(
    collection="ivf_collection",
    vector=query,
    top_k=10,
    search_params={
        "nprobe": 64           # Override num_probes
    }
)
----

=== Recall vs Latency Trade-offs

[cols="2,2,2,2", options="header"]
|===
| Priority | ef_search | nprobe | Expected Recall
| Speed | 50 | 16 | 90-95%
| Balanced | 100 | 32 | 95-98%
| Quality | 200 | 64 | 98-99%
| Maximum | 400 | 128 | 99%+
|===

== Filter Optimization

=== Filter Ordering

Place most selective filters first:

[source,python]
----
# Good: Selective filter first
filter = {
    "must": [
        {"field": "user_id", "match": "user_123"},  # Very selective
        {"field": "category", "match": "tech"},     # Moderately selective
        {"field": "is_active", "match": True}       # Not selective
    ]
}

# Automatic optimization: ProximaDB reorders internally
----

=== Pre-filtering vs Post-filtering

[source,python]
----
# Pre-filtering (default): Filter before vector search
results = client.search(
    collection="my_collection",
    vector=query,
    top_k=10,
    filter={"must": [{"field": "status", "match": "active"}]},
    search_params={"filter_strategy": "pre"}  # Default
)

# Post-filtering: Search first, then filter
# Use when filter matches most documents
results = client.search(
    collection="my_collection",
    vector=query,
    top_k=10,
    filter={"must": [{"field": "is_public", "match": True}]},
    search_params={"filter_strategy": "post"}
)
----

=== When to Use Each Strategy

[cols="2,4", options="header"]
|===
| Strategy | When to Use
| Pre-filter | Selective filters (<30% match rate)
| Post-filter | Broad filters (>70% match rate)
| Hybrid | Medium selectivity (30-70% match rate)
|===

== SQL Query Optimization

=== EXPLAIN Queries

[source,python]
----
# Analyze query plan
plan = client.execute_sql("""
    EXPLAIN SELECT id, metadata
    FROM my_collection
    WHERE VECTOR_DISTANCE(vector, $1, 'cosine') < 0.5
      AND $.category = 'tech'
    ORDER BY VECTOR_DISTANCE(vector, $1, 'cosine')
    LIMIT 10
""", parameters=[{"vector": query}])

print(plan)
# Output:
# QueryPlan {
#   stages: [
#     VectorSearch { index: "hnsw", ef: 100 },
#     MetadataFilter { field: "category", selectivity: 0.15 },
#     Sort { by: "distance" },
#     Limit { n: 10 }
#   ],
#   estimated_cost: 0.23,
#   estimated_rows: 10
# }
----

=== Query Hints

[source,sql]
----
-- Force index usage
SELECT /*+ INDEX(hnsw) */ id, metadata
FROM my_collection
WHERE VECTOR_SIMILAR(vector, $1, 0.8)
LIMIT 10;

-- Disable quantization
SELECT /*+ NO_QUANTIZATION */ id, metadata
FROM my_collection
WHERE VECTOR_SIMILAR(vector, $1, 0.8)
LIMIT 10;

-- Set search parameters
SELECT /*+ EF_SEARCH(200) */ id, metadata
FROM my_collection
WHERE VECTOR_KNN(vector, $1, 10);
----

=== Batch Queries

[source,python]
----
# Batch multiple searches in one request
results = client.batch_search(
    collection="my_collection",
    queries=[
        {"vector": query1, "top_k": 10},
        {"vector": query2, "top_k": 10},
        {"vector": query3, "top_k": 10}
    ],
    batch_params={
        "parallel": True,       # Execute in parallel
        "share_filter": True,   # Reuse filter results
        "deduplicate": True     # Remove duplicates across queries
    }
)
----

=== Embedding Cache

[source,python]
----
# Cache frequently used embeddings
client.cache_vectors(
    collection="my_collection",
    vector_ids=["popular_1", "popular_2", "popular_3"],
    ttl_seconds=3600
)

# Search with cached query vector
results = client.search(
    collection="my_collection",
    cached_query_id="popular_1",  # Use cached vector
    top_k=10
)
----

=== Warm-up Queries

[source,python]
----
# Warm up cache after restart
def warmup_cache(client, collection, sample_queries):
    """Run sample queries to warm up cache."""
    for query in sample_queries:
        client.search(
            collection=collection,
            vector=query,
            top_k=10,
            search_params={"cache_result": True}
        )

# Run at startup
warmup_cache(client, "my_collection", popular_queries)
----

== Reranking Optimization

=== Two-Stage Search

[source,python]
----
# Stage 1: Fast approximate search
candidates = client.search(
    collection="my_collection",
    vector=query,
    top_k=100,  # Fetch more candidates
    search_params={
        "quantized": True,      # Use quantized vectors
        "ef_search": 50         # Lower ef for speed
    }
)

# Stage 2: Precise reranking
results = client.rerank(
    collection="my_collection",
    query_vector=query,
    candidate_ids=[c.id for c in candidates],
    top_k=10,
    rerank_params={
        "use_full_precision": True,
        "include_scores": True
    }
)
----

=== Automatic Reranking

== Multi-Model Query Optimization

=== Fusion Strategy Selection

[source,python]
----
# Choose fusion based on use case
results = client.unified_search(
    components=[
        {"type": "vector", "collection": "embeddings", "weight": 0.7},
        {"type": "graph", "graph": "knowledge", "weight": 0.2},
        {"type": "text", "collection": "documents", "weight": 0.1}
    ],
    fusion_strategy="rrf",     # rrf | intersection | union | weighted
    limit=10
)
----

=== Fusion Strategies

[cols="2,4,2", options="header"]
|===
| Strategy | Description | Best For
| `intersection` | Only results in all modalities | High precision
| `union` | Any result from any modality | High recall
| `rrf` | Reciprocal rank fusion | Balanced
| `weighted` | Custom weights per modality | Domain-specific
| `learned` | ML-based fusion | Production optimization
|===

=== Parallel Execution

[source,python]
----
# Execute modalities in parallel
results = client.unified_search(

== Best Practices Checklist

=== Vector Search

[source,text]
----
□ Choose appropriate index type (HNSW for most cases)
□ Tune ef_search based on recall requirements
□ Enable quantization for large collections
□ Use reranking for critical accuracy
□ Batch queries when possible
----

=== Filtering

[source,text]
----
□ Place selective filters first
□ Use pre-filtering for selective filters
□ Use post-filtering for broad filters
□ Index frequently filtered fields
□ Avoid NOT filters when possible
----

=== SQL

[source,text]
----
□ Use EXPLAIN to understand query plans
□ Add query hints for complex queries
□ Batch similar queries together
□ Use parameterized queries
□ Limit result sets appropriately
----

=== Caching

[source,text]
----
□ Enable query result caching
□ Warm up cache after restarts
□ Cache popular query vectors
□ Set appropriate TTLs
□ Monitor cache hit rates
----
