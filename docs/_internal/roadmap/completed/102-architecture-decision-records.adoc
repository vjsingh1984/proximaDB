**Documenting significant architectural decisions in ProximaDB development**

== Overview

Architecture Decision Records (ADRs) capture important architectural decisions made during ProximaDB development, including context, decision, and consequences.

=== ADR Format

[source,text]
----
ADR Structure:
├── Title: Short descriptive title
├── Status: Proposed | Accepted | Deprecated | Superseded
├── Context: Why is this decision needed?
├── Decision: What is the change being proposed?
├── Consequences: What are the results of this decision?
├── Alternatives: What other options were considered?
└── References: Related documents or discussions
----

== ADR-001: Unified Storage Engine Architecture

=== Status
**Accepted** - January 2024

=== Context
ProximaDB needs to support diverse workloads with different performance characteristics:
- Real-time search with low latency
- Batch analytics with high throughput
- Time-series data with temporal queries
- Mixed workloads with varying patterns

A single storage engine cannot optimally serve all these use cases. We need a flexible architecture that allows specialized engines while maintaining a unified API.

=== Decision
Implement a `UnifiedStorageEngine` trait that all storage engines must implement, with 6 specialized implementations:

[source,rust]
----
pub trait UnifiedStorageEngine: Send + Sync {
    async fn insert(&self, collection: &str, records: Vec<VectorRecord>) -> Result<InsertResult>;
    async fn search(&self, collection: &str, query: SearchQuery) -> Result<SearchResult>;
    async fn delete(&self, collection: &str, ids: Vec<String>) -> Result<DeleteResult>;
    async fn flush(&self) -> Result<()>;
    async fn compact(&self) -> Result<()>;
}
----

Engine implementations:
- **SST**: LSM-tree for write-heavy workloads
- **HELIX**: Hilbert curve + PCA for locality-optimized search
- **VIPER**: Parquet columnar for analytics
- **SWIFT**: Three-tier for ultra-low latency
- **NOVA**: Progressive hierarchical for exploratory search
- **RAPTOR**: Adaptive for dynamic workloads

=== Consequences

**Positive:**
- Users can choose optimal engine for their workload
- New engines can be added without API changes
- Testing and benchmarking is standardized

**Negative:**
- Increased code complexity
- Users must understand engine tradeoffs
- Cross-engine operations require data movement

=== Alternatives Considered

1. **Single Adaptive Engine**: One engine that adapts to workload
   - Rejected: Too complex, performance compromises
2. **Separate Databases**: Different databases for different workloads
   - Rejected: Operational complexity, no unified API
3. **Plugin Architecture**: Third-party engines
   - Deferred: May implement later for extensibility

== ADR-002: Proto-First Pipeline

=== Status
**Accepted** - January 2024

=== Context
ProximaDB handles high-volume vector operations where serialization overhead significantly impacts performance. We need an efficient data pipeline from API to storage.

Traditional approach: JSON → Internal types → Storage format
This involves multiple conversions and copies.

=== Decision
Use Protocol Buffers as the canonical data format throughout the pipeline:

[source,text]
----
Request → Proto (VectorRecord) → Storage
         (zero copy)           (direct write)
----

Key principles:
1. Proto types are the source of truth
2. Minimal conversions between layers
3. Zero-copy where possible using Arc
4. Proto types have Serde compatibility for JSON REST

=== Consequences

**Positive:**
- 3-5x reduction in serialization overhead
- Single type definition (no duplication)
- Efficient gRPC support out of the box
- Clear API contract

**Negative:**
- Proto syntax learning curve
- Build-time code generation
- Less flexibility in internal representation

=== Implementation
[source,rust]
----
// Proto types used directly
pub use crate::proto::VectorRecord;
pub use crate::proto::SearchRequest;
pub use crate::proto::SearchResponse;

// Arc-based sharing for zero-copy
pub struct VectorBatch {
    records: Arc<Vec<VectorRecord>>,
}
----

== ADR-003: Unified Quantization Engine

=== Status
**Accepted** - February 2024

=== Context
Vector quantization is critical for memory efficiency and search performance. Different quantization methods have different tradeoffs:
- Binary: 32x compression, ~90% recall
- INT8: 4x compression, ~98% recall
- Product Quantization: Configurable compression/recall

We need a unified approach that:
1. Works consistently across all storage engines
2. Leverages hardware acceleration (SIMD)
3. Supports multiple quantization types
4. Enables progressive search with reranking

=== Decision
Create a `UnifiedQuantizationEngine` with:

[source,rust]
----
pub struct UnifiedQuantizationEngine {
    pub binary: BinaryQuantizer,
    pub scalar: ScalarQuantizer,  // INT8
    pub product: ProductQuantizer,
}

impl UnifiedQuantizationEngine {
    pub fn quantize(&self, vectors: &[f32], quant_type: QuantType) -> QuantizedVectors;
    pub fn distance(&self, query: &[f32], quantized: &QuantizedVectors) -> Vec<f32>;
    pub fn progressive_search(&self, stages: Vec<SearchStage>) -> SearchResults;
}
----

All engines use this shared quantization system:
- Codebooks are cached globally
- SIMD acceleration is automatic
- Reranking is built-in

=== Consequences

**Positive:**
- Consistent behavior across engines
- Hardware acceleration everywhere
- Codebook sharing reduces memory
- Progressive cascade search

**Negative:**
- All engines depend on quantization module
- Codebook training adds startup time
- Complex configuration options

== ADR-004: Write-Ahead Log Design

=== Status
**Accepted** - February 2024

=== Context
Durability is essential for a production database. We need:
- ACID guarantees for writes
- Fast recovery after crashes
- Support for cloud storage (S3, Azure, GCS)
- Multi-disk coordination

=== Decision
Implement a global WAL manifest with per-collection WAL segments:

[source,text]
----
WAL Architecture:
├── Global Manifest (manifest/manifest_*.jsonl)
│   ├── Collection registry
│   ├── LSN tracking
│   └── Segment references
└── Per-Collection WAL (collections/{name}/wal/*.wal)
    ├── Append-only segments
    ├── Checksum verification
    └── Configurable sync mode
----

Key design choices:
1. **Manifest per storage location**: Enables multi-disk deployments
2. **JSONL format**: Human-readable, append-only
3. **Parallel recovery**: 10 threads for fast startup
4. **Direct-to-storage**: Cloud-native recovery path

=== Consequences

**Positive:**
- Fast parallel recovery
- Cloud storage compatibility
- Easy debugging (human-readable manifest)
- Multi-disk support

**Negative:**
- Manifest can grow large
- JSONL parsing overhead vs binary
- Complex recovery logic

=== Configuration
[source,toml]
----
[storage.wal_config]
global_manifest_url = "file:///data/manifest"
enable_wal = true
memory_flush_size_bytes = 16777216
sync_mode = "fsync"  # fsync, async, periodic
----

== ADR-005: AXIS Indexing Framework

=== Status
**Accepted** - March 2024

=== Context
Vector similarity search requires efficient index structures. Different algorithms have different tradeoffs:
- HNSW: Fast search, high memory
- IVF: Lower memory, training required
- LSH: Approximate, very fast
- Flat: Exact, slow for large datasets

We need an adaptive framework that:
1. Selects optimal index based on workload
2. Supports index composition
3. Enables background index building
4. Integrates with EventLog for async updates

=== Decision
Create the AXIS (Adaptive indeX Integration System) framework:

[source,rust]
----
pub struct AxisManager {
    indexes: HashMap<String, Box<dyn VectorIndex>>,
    selector: AdaptiveSelector,
    event_consumer: EventLogConsumer,
}

pub trait VectorIndex: Send + Sync {
    fn insert(&mut self, id: &str, vector: &[f32]);
    fn search(&self, query: &[f32], k: usize) -> Vec<(String, f32)>;
    fn build(&mut self);
    fn memory_usage(&self) -> usize;
}
----

Index selection based on:
- Collection size
- Query patterns
- Memory constraints
- Latency requirements

=== Consequences

**Positive:**
- Automatic optimization
- Composable indexes (HNSW + IVF)
- Async index building
- Workload adaptation

**Negative:**
- Complex selection logic
- Index switching overhead
- Multiple index maintenance

== ADR-006: Graph Database Integration

=== Status
**Accepted** - April 2024

=== Context
Many vector use cases benefit from graph relationships:
- Knowledge graphs with embeddings
- Recommendation systems
- Entity linking

We could:
1. Integrate external graph database
2. Build native graph support
3. Use vector relationships as implicit graph

=== Decision
Build native graph support with CSR (Compressed Sparse Row) storage:

[source,rust]
----
pub struct GraphMemoryPool {
    nodes: Arc<DashMap<NodeId, Arc<Node>>>,
    edges: Arc<CsrGraph>,
    indexes: Arc<GraphIndexes>,
}
----

Three graph engines:
- **ORION**: In-memory, fast traversal
- **PULSAR**: Distributed graph
- **QUASAR**: Hybrid vector+graph

Arc-based zero-copy memory sharing for efficiency.

=== Consequences

**Positive:**
- Unified vector + graph queries
- Zero-copy traversal
- Native Cypher-like query language
- Single operational system

**Negative:**
- Increased system complexity
- Memory overhead for graphs
- Graph-specific optimization needed

== ADR-007: Embedded Database Mode

=== Status
**Accepted** - May 2024

=== Context
Some use cases require in-process database access:
- Local development and testing
- Edge deployments
- Language bindings (Python, Java, etc.)

Running a separate server adds:
- Network latency
- Operational complexity
- Resource overhead

=== Decision
Implement embedded mode with language bindings:

[source,rust]
----
pub struct EmbeddedProximaDB {
    storage: Arc<UnifiedStorageEngine>,
    collections: Arc<CollectionService>,
    config: ProximaDBConfig,
}

impl EmbeddedProximaDB {
    pub fn new(config: ProximaDBConfig) -> Result<Self>;
    pub fn create_collection(&self, name: &str, config: CollectionConfig) -> Result<()>;
    pub fn search(&self, collection: &str, query: SearchQuery) -> Result<SearchResults>;
}
----

Language bindings via:
- PyO3 for Python
- JNI for Java
- NAPI-RS for Node.js
- C FFI for Go/C++

=== Consequences

**Positive:**
- Zero network overhead
- Simple deployment
- Native language integration
- Same codebase as server

**Negative:**
- Memory shared with application
- No multi-process isolation
- Build complexity for bindings

== ADR-008: Multi-Protocol API Support

=== Status
**Accepted** - March 2024

=== Context
Different clients prefer different protocols:
- Web applications: REST/HTTP
- High-performance services: gRPC
- Data pipelines: Arrow Flight

Supporting one protocol limits adoption.

=== Decision
Implement multi-protocol support via unified service layer:

[source,text]
----
API Architecture:
├── REST (port 5678)
│   └── OpenAPI spec, JSON
├── gRPC (port 5679)
│   └── Proto definitions
└── Arrow Flight (port 5680)
    └── Zero-copy data transfer
----

All protocols share:
- Same service implementations
- Same authentication
- Same rate limiting
- Same observability

=== Consequences

**Positive:**
- Client choice flexibility
- Protocol-appropriate optimization
- Broad ecosystem compatibility

**Negative:**
- Multiple protocol maintenance
- Testing complexity
- Documentation overhead
