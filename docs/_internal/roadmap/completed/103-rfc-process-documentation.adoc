**Request for Comments (RFC) process for proposing significant changes to ProximaDB**

== Overview

The RFC (Request for Comments) process is used for proposing substantial changes to ProximaDB. It provides a consistent and controlled path for new features, architectural changes, and process improvements.

=== When to Use an RFC

[source,text]
----
RFC Required:
├── New storage engine
├── New API endpoints
├── Breaking changes
├── Cross-cutting features
├── Security-related changes
├── Performance-critical changes
└── Public API modifications

RFC Not Required:
├── Bug fixes
├── Documentation updates
├── Refactoring (internal only)
├── Test additions
├── Dependency updates
└── Minor improvements
----

== RFC Lifecycle

=== States

[source,text]
----
RFC States:
├── Draft       → Initial proposal, gathering feedback
├── Proposed    → Ready for formal review
├── In Review   → Active review by maintainers
├── Accepted    → Approved for implementation
├── Implemented → Feature is complete
├── Rejected    → Not accepted
├── Withdrawn   → Author withdrew proposal
└── Deferred    → Postponed for later consideration
----

=== Process Flow

[source,text]
----
1. Draft RFC
   ├── Author creates RFC document
   ├── Opens draft PR
   └── Gathers initial feedback

2. Propose
   ├── RFC is complete
   ├── PR marked "Ready for Review"
   └── Maintainers assigned

3. Review Period (2-4 weeks)
   ├── Community discussion
   ├── Technical review
   └── Revisions as needed

4. Final Comment Period (1 week)
   ├── Last call for feedback
   ├── Maintainer consensus
   └── Final decision

5. Decision
   ├── Accepted → Merge RFC, begin implementation
   ├── Rejected → Close PR with explanation
   └── Deferred → Label and revisit later
----

== Example RFC

=== RFC-0001: Streaming Insert API

[source,asciidoc]
----
= RFC-0001: Streaming Insert API
:author: Jane Developer
:email: jane@example.com
:date: 2024-12-15
:status: Accepted

== Summary

Add a streaming insert API that allows clients to continuously insert vectors without batching on the client side.

== Motivation

Current insert API requires clients to batch vectors before sending. This creates several problems:

1. **Memory pressure**: Clients must buffer vectors
2. **Latency**: Batches must complete before sending
3. **Complexity**: Clients implement batching logic

A streaming API allows clients to send vectors as they become available.

=== Use Cases

1. **Real-time indexing**: Index documents as they're processed by ML pipeline
2. **IoT data ingestion**: Continuous sensor embeddings
3. **Event streaming**: Kafka/Pulsar integration

== Detailed Design

=== gRPC Streaming API

[source,protobuf]
----
service VectorService {
  // Existing unary insert
  rpc Insert(InsertRequest) returns (InsertResponse);

  // New streaming insert
  rpc StreamInsert(stream VectorRecord) returns (stream InsertAck);
}

message InsertAck {
  string vector_id = 1;
  bool success = 2;
  string error = 3;
}
----

=== Server-Side Buffering

The server buffers incoming vectors and flushes when:
- Buffer reaches `stream_buffer_size` (default: 1000)
- Time since last flush exceeds `stream_flush_interval` (default: 100ms)
- Client closes stream

[source,rust]
----
pub struct StreamBuffer {
    vectors: Vec<VectorRecord>,
    max_size: usize,
    flush_interval: Duration,
    last_flush: Instant,
}

impl StreamBuffer {
    pub fn should_flush(&self) -> bool {
        self.vectors.len() >= self.max_size ||
        self.last_flush.elapsed() >= self.flush_interval
    }
}
----

=== Configuration

[source,toml]
----
[api.streaming]
enabled = true
buffer_size = 1000
flush_interval_ms = 100
max_concurrent_streams = 100
----

=== Python SDK

[source,python]
----
async def stream_insert(client, collection, vector_generator):
    async with client.stream_insert(collection) as stream:
        for vector in vector_generator:
            await stream.send(vector)
            ack = await stream.receive()
            if not ack.success:
                logger.error(f"Insert failed: {ack.error}")
----

== Drawbacks

1. **Complexity**: Server-side buffering adds state
2. **Ordering**: Vectors may be reordered during concurrent inserts
3. **Resource usage**: Long-lived connections consume resources

== Rationale and Alternatives

=== Alternative 1: Larger Batch Size
- **Rejected**: Doesn't solve latency or memory issues

=== Alternative 2: HTTP Chunked Encoding
- **Rejected**: Less efficient than gRPC streaming

=== Why gRPC
- Native streaming support
- Efficient binary protocol
- Existing infrastructure

== Prior Art

- **Milvus**: Supports bulk insert but not streaming
- **Qdrant**: Batch insert only
- **Kafka**: Streaming producer pattern

== Unresolved Questions

1. How to handle stream interruption mid-batch?
2. Should we support ordered delivery?

== Implementation Plan

=== Milestones

2. [x] Phase 2: Server-side buffering
3. [x] Phase 3: Python SDK support
4. [ ] Phase 4: Kafka integration (future)

=== Team

- **Reviewers**: @alice, @bob
----

== Review Process

=== Reviewer Responsibilities

[source,text]
----
Reviewers should evaluate:
├── Technical soundness
├── Alignment with project goals
├── API consistency
├── Performance implications
├── Security considerations
├── Backwards compatibility
└── Documentation quality
----

=== Review Comments

Use structured comments:

[source,markdown]
----
## Technical Concern

**Severity**: Major/Minor/Nit
**Section**: Detailed Design

The proposed buffering strategy may cause memory issues under high load.

**Suggestion**: Add backpressure mechanism when buffer exceeds threshold.
----

=== Consensus Building

Decisions require:
- At least 2 maintainer approvals
- No unresolved major concerns
- Author addressed all feedback

== RFC Amendments

=== Minor Changes

For small clarifications to accepted RFCs:
1. Open PR with changes
2. Reference original RFC
3. One maintainer approval required

=== Major Changes

For significant changes to accepted RFCs:
1. Create new RFC referencing original
2. Follow full RFC process
3. Mark original as superseded if needed

== Governance

=== RFC Team

[cols="2,3", options="header"]
|===
| Role | Responsibilities
| RFC Author | Create and champion proposal
| RFC Shepherd | Guide RFC through process
| Maintainers | Technical review and approval
| Community | Feedback and discussion
|===

=== Decision Making

[source,text]
----
Decision Process:
1. Maintainers discuss in private channel
2. Each maintainer votes: +1, 0, -1
3. Majority +1 required to accept
4. Any -1 must be resolved before acceptance
5. Decision posted publicly with rationale
----

== Quick Reference

=== Creating an RFC

[source,bash]
----
# 1. Create RFC file
cp docs/rfcs/0000-template.adoc docs/rfcs/0XXX-my-feature.adoc

# 2. Fill in template
vim docs/rfcs/0XXX-my-feature.adoc

# 3. Open PR
git checkout -b rfc/my-feature
git add docs/rfcs/0XXX-my-feature.adoc
git commit -m "RFC: My Feature"
git push origin rfc/my-feature

# 4. Create PR with [RFC] prefix
# Title: [RFC] My Feature
----

== Summary

The RFC process ensures that significant changes to ProximaDB are:
- Well-documented before implementation
- Reviewed by multiple stakeholders
- Aligned with project goals
- Communicated to the community

Use this process for any substantial changes to maintain quality and consistency.
