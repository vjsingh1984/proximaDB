= ProximaDB Architectural Review: Vision, Foundations, and Performance Alignment
:toc: left
:toclevels: 3
:icons: font
:docdate: 2026-03-21

[.lead]
A comprehensive review of ProximaDB's vision coherence, multi-model integration maturity, foundational data layer alignment, and performance gap analysis against single-node analytical systems (DuckDB, Polars).

== Executive Summary

ProximaDB's vision as "The Context Database" is **architecturally sound and differentiated**. The specialized-engine-per-workload model under a unified query plane is the right abstraction -- it avoids the "lowest common denominator" problem of generic multi-model databases while maintaining a single operational surface. However, three foundational gaps threaten the credibility of the vision:

[cols="1,3,1"]
|===
| Gap | Impact | Severity

| **Vectorized execution missing**
| Columnar query engine processes row-at-a-time inside Arrow batches; filter pushdown engine returns `true` (unimplemented); adaptive filter executor disabled. Claims of analytical performance cannot be substantiated.
| *CRITICAL*

| **Arrow used for transport, not as native memory format**
| Cross-model query results undergo multiple serialization conversions (JSON parse per row in LATERAL joins). The system pays conversion tax at every model boundary.
| *HIGH*

| **No spill-to-disk mechanism**
| Memory caches reject writes with `CapacityExceeded` when full. No automatic spillover. Larger-than-memory workloads fail rather than degrade gracefully.
| *HIGH*
|===

The storage engine layer (ProximaBlocks codec, Parquet integration, WAL) is **genuinely well-built** -- the SIMD codec with wire-format compatibility across implementations is production-grade engineering. The gap is in the *query execution layer above storage*, not in storage itself.

== Part 1: Vision Strength Assessment

=== What ProximaDB Gets Right

[cols="1,3"]
|===
| Strength | Evidence

| **Specialized engines under unified surface**
| 6 vector engines (SST write-optimized, HELIX locality, VIPER analytics, etc.) + 3 graph engines + document + observability + TST + event sourcing. Each optimized for its workload, not a generic store.

| **Dogfood-driven development**
| ibkrtrading production trading system validates architecture under genuine pressure. This is how PostgreSQL, SQLite, and DuckDB evolved -- production use drives design.

| **Honest maturity tiering**
| The SUPPORTED_SURFACE.adoc contract distinguishes Supported/Beta/Experimental explicitly. This prevents over-promising and builds trust.

| **Cross-model SQL extensions**
| `VECTOR_SEARCH()`, `GRAPH_QUERY()`, `DOCUMENT_QUERY()`, `LOGS()`, `METRICS()` in standard SQL with LATERAL joins. This is the right abstraction for multi-model -- extend SQL, don't replace it.

| **Proto-first architecture**
| API types defined in protobuf with Serde compatibility. Zero-copy principle applied correctly.

| **Wire-format codec compatibility**
| ProximaCodec's Baseline/SIMD/GPU implementations produce identical bytes. This enables mix-and-match decoding and clean benchmarking.
|===

=== Category Definition: Context Database

ProximaDB's positioning as a "Context Database" (not just a vector database) is the right strategic move. The multi-model integration creates a genuine category:

* **Vector databases** (Pinecone, Milvus, Qdrant): Single-model, require external systems for graphs/documents/logs
* **Generic multi-model** (ArangoDB, SurrealDB): Unified but not workload-specialized
* **ProximaDB**: Specialized engines per workload + unified query plane = best of both

The category holds **if and only if** cross-model queries actually work efficiently. Today, the function-backed federated path (VECTOR_SEARCH + DOCUMENT_QUERY via LATERAL) works. But the execution engine underneath is row-at-a-time, which limits the performance claim.

=== The Unified Execution Engine: Honest Assessment

ProximaDB does **not** have a single unified execution engine. It has:

1. **A federated SQL engine** (`src/query/federated/`) that handles function-backed sources well
2. **Separate model-specific engines** called directly (GraphOperationsService, DocumentService, VectorOps, ObservabilityStorage)
3. **A facade** (`src/query/facade/`) that routes between them via a `QueryStrategy` priority system
4. **Fusion strategies** (RRF, WeightedLinear, BordaCount, etc.) that post-process results but are rarely invoked

The graph query executor (`src/graph/query/executor.rs`) is **stubbed** -- only `NodeScan` is partially implemented. Queries fall through to the GraphStrategy which calls ORION directly, bypassing the query planner entirely.

**What this means**: The architecture is a traffic cop, not a true unified engine. Each model's query path is optimized independently, and cross-model queries pay conversion costs at every boundary.

=== Cross-Model Join Overhead

The most critical cross-model performance issue:

[source]
----
SELECT * FROM DOCUMENT_QUERY('profiles') p
  JOIN LATERAL VECTOR_SEARCH('products', p.document.embedding, 10) v ON true
----

**Current execution**:
[source]
----
For each document row:
  1. Extract JSON string from Arrow column
  2. serde_json::from_str() → parse entire document
  3. Navigate nested path to find "embedding" field
  4. Convert JSON array → Vec<f32>
  5. Execute VECTOR_SEARCH with extracted vector
  6. Join result with outer row
----

**Cost**: O(document_size) JSON parsing *per row*. For 10,000 documents with 1KB each, this is ~10MB of unnecessary JSON parsing.

**Fix**: Store embeddings in Arrow `FixedSizeList<Float32>` columns, not inside JSON. Extract directly from the Arrow array without serialization.

== Part 3: Storage & Codec Foundational Analysis

=== What's Genuinely Well-Built

==== ProximaCodec (2,100+ LOC SIMD)

The custom codec is **production-grade engineering**:

* 7 encoding schemes: Raw, BitPacked, Delta, FrameOfReference, PatchedBase, Dictionary, RunLength
* 3 implementation tiers: Baseline (scalar), SIMD (AVX2/AVX512/NEON), GPU (optional)
* Wire-format compatibility: All tiers produce identical bytes
* Platform independence: Scalar fallback always works
* 1-byte marker format with HAS_COUNT flag

**Gap vs. DuckDB**: DuckDB performs **per-segment codec selection** (analyzes data, tries multiple codecs, picks best ratio). ProximaDB's codec is selected at write time but does not appear to do adaptive selection per segment. This is the single highest-impact storage optimization missing.

==== Parquet Integration (VIPER/NOVA)

Real Apache Parquet usage (not just claimed):

* StreamingParquetWriter with row groups (~128MB default, 2048 vectors)
* UnifiedParquetReader with footer caching (70-90% cloud API reduction)
* Bloom filter per row group
* Column projection
* Compression: LZ4/Snappy/Zstd per column

**Gap**: Row group statistics-based pruning only works for string columns. Numeric range pruning is explicitly disabled (TODO comment in code). This means metadata filters on numeric fields (timestamps, scores) scan all row groups.

==== ProximaBlocks (SST/SWIFT/HELIX)

Custom columnar encoding optimized for vector data:

* Dimension-columnar layout: Each dimension stored sequentially for SIMD
* ~65KB default data blocks
* Bloom filter (4KB) + B+ tree index (60KB) per file
* Zero-copy vector serialization via `bytemuck::cast_slice`

==== WAL System

Solid write-ahead log with pluggable serialization:

* 3 strategies: Protocol Buffers, Apache Avro, Bincode
* Memtable manager (configurable limit, default 512MB)
* Multi-disk support with collection affinity
* Crash recovery with parallel recovery

== Part 4: Performance Gap Analysis vs. DuckDB/Polars

=== Critical Pattern Gaps

==== Gap 1: No Vectorized Execution Engine (CRITICAL)

**DuckDB pattern**: Process data in 2048-value DataChunks. Each operator works on entire vectors using tight loops that auto-vectorize to SIMD. One virtual function call per 2048 tuples.

**Polars pattern**: Lazy evaluation with streaming execution in 50K-100K row batches. Morsel-driven parallelism with work-stealing.

**ProximaDB reality**:
[source,rust]
----
// From unified_reader.rs - row-at-a-time filtering inside batches
while let Some(batch) = reader.next() {
    let batch = batch?;
    let batch_records = self.extract_records_from_batch(&batch, ...)?;
    for record in batch_records {
        if self.matches_filter_expression(&record, filter_expr) {
            records.push(record);
        }
    }
}
----

* Arrow batches of 1024 records used for I/O chunking, but filtering is row-by-row
* No selection vector pattern (copies matching rows instead of maintaining index bitvector)
* No late materialization (reads all columns before filtering)

**Impact**: For analytical queries over vector collections (e.g., "find all vectors where metadata.category = 'tech' and score > 0.8"), ProximaDB will be 10-100x slower than DuckDB on the same Parquet files.

==== Gap 2: Filter Pushdown Not Implemented (CRITICAL)

[source,rust]
----
// From filter_pushdown_engine.rs - always returns true
fn row_group_matches(&self, __filters: &[MetadataFilter], __rg: &RowGroupMetaData) -> bool {
    true  // No actual pruning
}
----

[source,rust]
----
// From adaptive_filter_executor.rs - disabled
"BranchedFilterExecutor temporarily disabled due to API changes"
----

**Impact**: Every query scans all row groups regardless of filter selectivity. For a 1M-vector collection with 100 row groups, a filter that matches 1% of data still reads 100% of row groups.

==== Gap 3: No Per-Segment Adaptive Codec Selection (HIGH)

**DuckDB pattern**: For each ~122K-row segment, DuckDB:

1. Samples the data
2. Tries multiple codecs (Dictionary, RLE, BitPack, FOR, FSST, ALP)
3. Picks the codec with best compression ratio
4. Different segments of the same column can use different codecs

**ProximaDB**: ProximaCodec supports 7 encoding schemes but codec selection appears to be manual/static, not adaptive per-segment. A timestamp column that's sorted in one segment and random in another will use the same codec for both.

==== Gap 4: No Spill-to-Disk (HIGH)

**DuckDB**: When memory is exhausted, intermediate results (hash tables, sort buffers) are spilled to temporary files. Queries degrade gracefully, never OOM.

**Polars**: Streaming engine partitions data and processes partitions sequentially, with spill for oversized operations.

**ProximaDB**: `CapacityExceeded` error when L1 cache is full. L2 (NVMe) and L3 (Network) cache backends are defined but **not implemented** (TODO stubs). No automatic spillover.

==== Gap 5: Distance Computation Not Truly Batched (MEDIUM)

**Current pattern** (from engine.rs):
[source,rust]
----
// Unroll factor 4, but still per-vector SIMD
let d0 = self.compute_distance_simd(query, chunk[0], metric);
let d1 = self.compute_distance_simd(query, chunk[1], metric);
let d2 = self.compute_distance_simd(query, chunk[2], metric);
let d3 = self.compute_distance_simd(query, chunk[3], metric);
----

This uses CPU instruction pipelining (good) but not **multi-vector SIMD**. True batched distance would transpose vectors into a matrix and use SIMD across dimensions simultaneously. For 128-dimensional vectors with AVX2, this could yield 2-4x improvement.

=== What ProximaDB Does Well (vs. DuckDB/Polars)

[cols="1,3"]
|===
| Advantage | Details

| **Progressive quantization search**
| Binary -> INT8 -> PQ -> FP32 cascade achieves <5ms for 1M vectors. DuckDB has no equivalent for vector similarity.

| **Predictive cache prefetching**
| Access pattern correlation with <200ns overhead. DuckDB relies on OS page cache; Polars has no prefetching.

| **SIMD codec with wire compatibility**
| Three independent SIMD implementations that produce identical bytes. Clean engineering.

| **Multi-format storage strategy**
| Right engine for right workload. DuckDB has one storage format; ProximaDB matches engine to access pattern.

| **Memory budget with rebalancing**
| 5-way split (vectors 40%, queries 30%, filters 15%, index 10%, metadata 5%) with periodic rebalancing. More sophisticated than DuckDB's single pool.
|===

== Part 5: Recommended Foundational Alignment

=== Priority 1: Vectorized Columnar Execution Engine

This is the single highest-impact improvement. Without it, ProximaDB cannot credibly claim analytical query performance.

**Design**:
[source]
----
DataChunk {
    vectors: Vec<Array>,     // Arrow arrays, one per column
    size: usize,             // 2048 values (L2-cache-sized)
    selection: Option<Bitmap> // Selection vector for filtered rows
}

trait PhysicalOperator {
    fn next_chunk(&mut self) -> Option<DataChunk>;
}

// Example: FilterOperator
impl PhysicalOperator for FilterOperator {
    fn next_chunk(&mut self) -> Option<DataChunk> {
        let chunk = self.child.next_chunk()?;
        // Evaluate predicate on entire array (auto-vectorizes)
        let mask = evaluate_predicate_vectorized(&chunk, &self.predicate);
        // Combine with existing selection (AND)
        chunk.selection = chunk.selection.and(mask);
        Some(chunk)  // No copying -- just updated selection bitmap
    }
}
----

**Key principles from DuckDB/Polars**:

1. Fixed 2048-value chunks that fit in L2 cache
2. Selection vectors instead of copying filtered rows
3. Late materialization -- don't read column values until after filtering
4. Operators process entire arrays, enabling SIMD auto-vectorization
5. Pipeline-based execution with pipeline breakers at sort/aggregate/hash-build

**Files to modify**: `src/storage/engines/core/formats/columnar/columnar_query_engine/`

=== Priority 2: Implement Row Group Pruning for All Types

**Current state**: String-only statistics comparison. Numeric pruning returns `true`.

**Fix**: Use Parquet's typed statistics API properly:

[source,rust]
----
// Instead of binary comparison, use typed statistics
match statistics {
    Statistics::Int64(stats) => {
        let min = stats.min_opt();
        let max = stats.max_opt();
        // Compare with filter value using proper numeric comparison
    }
    Statistics::Float(stats) => { /* same */ }
    Statistics::Double(stats) => { /* same */ }
    // ...
}
----

**Impact**: For a 100-row-group collection with a timestamp range filter, this eliminates 90%+ of I/O.

=== Priority 3: Arrow as Native Memory Format

**Current**: Arrow used for I/O batching and transport. Intermediate processing uses custom types with conversion at every boundary.

**Target**: Arrow RecordBatch as the lingua franca between all engines and the query executor.

**Key changes**:

1. Store document embeddings as Arrow `FixedSizeList<Float32>` columns, not inside JSON metadata
2. Graph query results returned as Arrow RecordBatch, not custom Rust types
3. Observability query results as Arrow RecordBatch
4. Eliminate JSON serialization/deserialization in cross-model LATERAL joins

**Impact**: Eliminates the O(document_size) JSON parsing per row in cross-model joins.

=== Priority 4: Per-Segment Adaptive Codec Selection

**Design** (inspired by DuckDB):

[source]
----
fn select_codec(segment: &[f32], dimension: usize) -> ProximaScheme {
    let stats = analyze_segment(segment);

    // Try each codec on a sample, pick best ratio
    let candidates = [
        (ProximaScheme::Delta, try_delta(sample)),
        (ProximaScheme::BitPacked, try_bitpack(sample)),
        (ProximaScheme::Dictionary, try_dictionary(sample)),
        (ProximaScheme::RunLength, try_rle(sample)),
        (ProximaScheme::FrameOfReference, try_for(sample)),
    ];

    candidates.min_by_key(|(_, ratio)| ratio).0
}
----

**Impact**: 20-40% storage reduction for mixed workloads where different segments have different data distributions.

=== Priority 5: Spill-to-Disk for Larger-than-Memory Queries

**Design**:

1. Implement L2 NVMe cache backend (currently TODO stub)
2. Add spill-to-disk for hash join build tables
3. Add external merge sort for ORDER BY on large result sets
4. Configure via `max_memory_bytes` with automatic spillover

**Impact**: Enables analytical queries over collections that exceed available memory without OOM.

=== Priority 6: Graph Query Executor Implementation

**Current**: Parser creates plan, executor is stubbed, queries bypass to direct engine calls.

**Fix**: Implement the query executor pipeline:

[source]
----
NodeScan → Filter → Traverse → Filter → Project → Sort → Limit
----

Each step should produce Arrow RecordBatches, enabling integration with the federated query engine without format conversion.

== Part 8: Vision Coherence Verdict

=== The Abstraction is Right

ProximaDB's core abstraction -- specialized engines per workload, unified under one query language and data plane -- is the **correct architecture** for a context database. This is validated by:

1. **DuckDB's success**: Single-node, embedded, specialized for analytics = dominant in its category
2. **SQLite's success**: Single-node, embedded, simple surface = ubiquitous
3. **ProximaDB's opportunity**: Single-node, embedded, specialized for multi-model AI context = unique category

=== The Execution Layer Needs Catching Up

The storage engines and codec layer are ahead of the query execution layer. This creates a credibility gap:

* **Storage**: Production-grade (ProximaCodec SIMD, Parquet integration, WAL)
* **Search**: Production-grade (progressive quantization, SIMD distance, hybrid BM25+vector)
* **Query Execution**: Prototype-grade (row-at-a-time, no filter pushdown, graph executor stubbed)

=== Path to Credible Category Leadership

[source]
----
Current state:     "Broad multi-model with narrow depth"
Target state:      "Deep single-node performance with credible multi-model"
Key transformation: Build the vectorized execution engine between storage and API
----

The foundational layers (storage, codec, persistence) are solid. The API surface (REST, gRPC, Arrow Flight, PostgreSQL wire) is comprehensive. The missing piece is the **execution engine in the middle** -- the layer that turns columnar storage into fast analytical queries, that turns Arrow batches into vectorized processing, and that eliminates format conversion at model boundaries.

**Get this layer right, and ProximaDB's category claim becomes credible.**

== Appendix A: DuckDB/Polars Patterns for Reference

=== DuckDB Key Patterns

1. **2048-value DataChunks** fitting in L2 cache
2. **Morsel-driven parallelism** (10K-row morsels assigned to threads)
3. **Per-segment adaptive codec selection** (tries multiple codecs, picks best)
4. **Native Parquet reader** with zone-map pushdown, page-level filtering, dictionary predicate resolution
5. **Buffer manager** with fixed 256KB blocks, LRU eviction, temp directory spillover
6. **FSST** (Fast Static Symbol Table) for string compression
7. **ALP** (Adaptive Lossless floating-Point) for float compression

=== Polars Key Patterns

1. **Arrow2-based memory model** (zero-copy, 64-byte aligned)
2. **Lazy evaluation** with predicate/projection/slice pushdown
3. **Streaming engine** with morsel-driven processing
4. **Async I/O** for cloud Parquet (prefetch row groups concurrently)
5. **Monomorphized kernels** (Rust generics eliminate runtime type dispatch)
6. **Expression-level parallelism** (independent expressions evaluated in parallel)

=== Unique ProximaDB Advantages Over Both

1. **Progressive quantization search**: Binary -> INT8 -> PQ -> FP32 cascade (no equivalent in DuckDB/Polars)
2. **Multi-engine storage selection**: Right engine for right workload (DuckDB has one format)
3. **Predictive cache prefetching**: Access correlation with <200ns overhead
4. **Native graph + vector integration**: CSR graph with vector similarity in one system
5. **Wire-format codec compatibility**: Three independent SIMD implementations, identical bytes
