= TPC gate evidence v3 — sort-on-materialize lights up pruning (2026-07-05)

Completes the v1/v2 evidence arc: with all four chain links landed
(filter pushdown #671, date-literal translation + row-group geometry #680,
TD-OLAP-6 sort-on-materialize this PR), zone-map pruning produces its first
measured skips.

== Results (scale 0.01, `PROXIMADB_MATERIALIZE_ROW_GROUP_ROWS=4096`,
local-tempdir, debug; repeat temperature)

|===
| run | tpch skip | tpcds skip | notes

| v1/v2 (any config, unsorted)
| 0/85 (0%)
| 0/40 (0%)
| whole-domain row groups — structurally unprunable

| sorted baseline (static pruning only)
| **81/422 (19.2%)**
| 0/152 (0%)
| TPC-H date predicates prune directly: Q14/Q15 = 14/16 groups, Q6 = 12/15
  with a 50 ms wall beside multi-second peers. TPC-DS 0% is EXPECTED —
  its date filters sit on `date_dim`, not the fact table (the runtime
  join filter's case).

| sorted + `PROXIMADB_DF_RUNTIME_FILTER_PRUNE=1`
| 81/422 (19.2%) — identical to baseline
| 0/152 (0%) — identical to baseline
| The join dynamic filter added ZERO incremental pruning: no per-query
  delta vs the sorted baseline anywhere. Either DF 54's Post-phase pushdown
  is not delivering the filter to `ProximaScanExec` on our plan shapes, or
  the resolved filter does not translate to prunable predicates here —
  instrumenting the absorption path (absorb/snapshot/translate counters) is
  the follow-up filed under TD-OLAP-3.
|===

Geometry note: the 4,096-row evidence granularity raises `splits_total`
(85 → 422 TPC-H) and adds per-group overhead on unpruned scans; the
production default stays 65,536 (`warehouse_writer_properties`). Row-group
size is the standard granularity/overhead dial — tune per deployment, and
the skip percentages below scale with granularity.

== Decision

* **Static pruning is the proven lever** — 19.2% TPC-H split skip on
  sorted publication, with per-query wins like Q6 at 50 ms (12/15 groups
  skipped) beside multi-second peers. It is already default-ON (Inexact
  filter pushdown, #671) and needs no further gating.
* **`PROXIMADB_DF_RUNTIME_FILTER_PRUNE` stays default-OFF** — measured zero
  incremental benefit (mandate: promote only on a measured win). Next
  actionable: instrument the absorption/snapshot/translate path to learn
  whether the filter arrives at all on our plan shapes.
* **`PROXIMADB_DF_STATS_VALUE_BOUNDS` stays default-OFF** — unchanged since
  v1 (stability-neutral, no measured benefit yet).
* **TD-OLAP-6 sort-on-materialize: proven and shipping** — the regression
  test pins monotone, tight row-group windows; it converted 0% skip into
  19.2% on the same queries and data.
