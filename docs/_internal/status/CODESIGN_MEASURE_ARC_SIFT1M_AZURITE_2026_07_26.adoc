== Decision question

On the cloud-latency regime that actually bills us, does inter-file search parallelism (TD-SEARCH-2 S1,
`PROXIMADB_SEARCH_PARALLEL_FILES`) move the dominant cost term — and is the recall it delivers a recall
property or a compaction artifact?

== What was measured, in the code

The parallelism under test is the inter-file fan-out in
`src/storage/engines/sst/search/mod.rs` — the `tokio::spawn` per file, sized by
`resolve_search_parallelism` from `PROXIMADB_SEARCH_PARALLEL_FILES` (TD-SEARCH-2 S1; `0` means half
the cores).

That pointer is recorded here because the ledger cannot hold it: `bench_source` is
existence-checked as a path, so the original entry's
`"src/storage/engines/sst/search/mod.rs (S2 tokio::spawn + resolve_search_parallelism)"` fails
validation. Naming the mechanism in prose is the only place it survives — dropping the parenthetical
to satisfy the schema would otherwise lose the one detail that says *which* code the number is about.

== Results

[cols="2,2,3",options="header"]
|===
| Quantity | Value | Reading
| recall@10 | **0.98** | Coalesced-RaBitQ cascade over 8 uncompacted L0 files
| Direct-Azurite latency (1 ms GET) | p50 **1 ms**, p95 **11 ms** | **CPU-bound** — the object store is not the constraint at this latency
| 50 ms-GET regime, degree 1 | ~**3458 ms** steady | **I/O-bound** — the regime that resembles cloud
| 50 ms-GET regime, degree 4 | ~**1700 ms** steady | **~2x** from S1 inter-file parallelism
| GETs per query | ~**70–140** across 8 files | The term the co-design mandate says to optimise
|===

== What the numbers mean, and what they do not

* **The ~2x is bounded by `file_count / degree`.** With 8 files at degree 4 there is no more headroom;
  the speedup is a property of the file count, not a ceiling of the technique. More files would show
  more.
* **Compaction did not fire** — 8 L0 segments, zero at L1 or above — so the query was a full scan with
  no IVF pruning. That is a **cloud-latency gap, not a recall gap**: compaction cuts GETs and vectors
  ranked, not recall.
* **recall@10 = 0.98 is therefore full-scan RaBitQ**, i.e. recall-exact for this configuration. An
  earlier reading of **0.23 was an artifact** of a flush-blocked memtable, not a quality regression —
  worth recording precisely because a recall number that low invites a redesign of the wrong layer.
* **The direct-Azurite figure should not be quoted as a latency result.** At a 1 ms GET the system is
  CPU-bound, so it measures the host rather than the design. The 50 ms regime is the one that carries
  information about the dominant cost term.

== Known-bad state observed during the run

== Why this is filed as evidence rather than as a claim in prose

Per the measurement mandate, a performance number is quotable only from the ledger. The corresponding
entry is `codesign_measure_arc_sift1m_azurite_2026_07_26`, and this document is the `artifact` it
requires. The lesson worth carrying past the numbers: **the ledger's validator is what kept this
measurement out of the repository for 25 days** — the entry was written, the run was done, and the
schema was never satisfied. A gate that rejects silently at commit time, on a branch nobody returns to,
loses the evidence it exists to protect.
