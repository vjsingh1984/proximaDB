= TPC gate evidence v4 — I/O attribution fix makes pruning observable (2026-07-05)

Closes the v1–v3 arc. v3 established that STATIC split pruning fires (19.2%
TPC-H skip) but the ledger's `bytes_read` did not move with it, and the
runtime-filter gate measured "zero incremental pruning". Both symptoms had a
single root cause, found here — and it was NOT a second scan execution (the
v3 "double-execution frontier" hypothesis is **disproved** below).

== Root cause: query I/O escaped the per-query trace scope

`ProximaScanExec` reports `UnknownPartitioning(num_cpus)`, so DataFusion
inserts a `CoalescePartitionsExec` that drives each partition's stream on a
**spawned** tokio task. A `tokio::task_local!` does not propagate across
`tokio::spawn`, so the `IO_TRACE` task-local was absent in those tasks and the
row-group data reads — the dominant scan I/O, and exactly the bytes split
pruning saves — recorded into nothing (`try_with` → `Err`, silent no-op).

An in-scope probe at the object-store GET site confirmed it directly
(scale 0.01, `PROXIMADB_DF_RUNTIME_FILTER_PRUNE=1`):

|===
| GETs observed | in `IO_TRACE` scope | attribution

| 84 of 96 | `false` | the per-row-group ranged reads — **uncounted**
| 12 of 96 | `true`  | plan-time `statistics_from_splits` footer/stats reads
|===

So the counted `bytes_read` was only the constant plan-time stats read
(a ~1.76 MB whole-object GET), identical regardless of pruning. That is why
Q1 (1/15 pruned) and Q6 (12/15 pruned) reported byte-for-byte identical
`bytes_read` in v3. The same mechanism silenced the runtime-path
`record_splits` counter (it too runs on the spawned task).

=== The "double execution" hypothesis was a diagnostic artifact

`execute_datafusion` runs **once** per submitted statement (single call site,
`relational_pipeline.rs:339`). The "2–3× per statement" seen while
instrumenting the TPC-DS conformance test was the test itself: `rollup` /
`cube` / `win_rank` each run once in the conformance loop and again (identical
SQL) in the value-correctness checks; `intersect` re-runs plus `except` shares
a 60-char truncated prefix; `q3`/`q52` are two distinct queries the truncation
merged. No product-level double scan exists.

== Fix

Hold the trace behind `Arc<IoTrace>` and capture a handle
(`io_trace::current_handle()`) **while still in the query scope** (table open /
physical planning). `TracingObjectStore` captures at `wrap()`; `ProximaScanExec`
captures at `build()` for its `record_splits`. Reads on spawned tasks now
record through the captured handle. Falls back to the task-local when
constructed outside a scope (behaviour-preserving for non-query paths).

== Result: `bytes_read` now tracks pruning

Controlled within-table comparison — Q1 and Q6 both scan `lineitem` with a
comparable projection (scale 0.02, `PROXIMADB_MATERIALIZE_ROW_GROUP_ROWS=4096`,
local-tempdir, debug, `first` temperature, `PROXIMADB_DF_RUNTIME_FILTER_PRUNE=1`):

|===
| query | splits pruned | `bytes_read` before fix | `bytes_read` after fix | `range_gets` after

| Q1 | 2 / 30  | 1,796,281 | 8,773,979 | 506
| Q6 | 25 / 30 | 1,796,281 | 4,612,767 | 92
|===

Before: byte-identical despite 12× the pruning. After: Q6 reads ~47% fewer
bytes and issues ~6× fewer GETs than Q1, proportional to its higher prune
ratio. The suite corroborates at the extremes — Q21 (0/199 pruned) = 21.1 MB /
1731 GETs, Q14 (29/32 pruned) = 4.3 MB / 33 GETs.

Aggregate TPC-H DF-route skip is now a **measured, attributed** 171/1347
splits = 12.7% (11 of 22 queries prune). Across the full heterogeneous suite
the prune-ratio↔bytes correlation is only −0.29, because `bytes_read` is
dominated by query shape (table count, projection width) — which is why the
controlled same-table comparison, not the cross-query aggregate, is the valid
signal.

== What this unblocks (follow-ups, unchanged posture)

* The runtime-filter gate (`PROXIMADB_DF_RUNTIME_FILTER_PRUNE`) stays
  **default-off**. Its promotion still needs an isolated baseline-vs-gate
  comparison (Slice A static vs Slice B runtime) — now finally measurable,
  since both paths attribute correctly. v3's "zero incremental" reading was
  taken through the broken meter and must be re-measured.
* Faithful-scale datagen + object-store regime (TD-OLAP-4) remains the
  headline evidence target; this fix is its prerequisite.
