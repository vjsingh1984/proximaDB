= SIFT1M coalesced-RaBitQ scan-then-rerank recall + GET cost (2026-07-15)

:toc: macro

toc::[]

== Why this run

ADR-062 / TD-RDSTRAT-6 PR1 hoists the RaBitQ binary tier out of per-block stripes
into a coalesced file-level header region, then **scan-then-reranks**: one ranged
GET scans ALL RaBitQ codes (keep=100%, ~0.99 recall, zero prune loss), and
survivors are reranked via a few coalesced SQ8 block GETs. This is the GET lever
the measured block-centroid-prune ceiling (link:SIFT1M_VOE_COMPACTED_RECALL_PARETO_2026_07_15.adoc[the
2026-07-15 VOE eval]) proved unreachable through block-pruning. This run is the
PR1 bake of the new layout: does it reach the ~0.99 recall regime at GETs/query
≪ today's ~370?

- **Dataset:** TEXMEX SIFT1M, N=100000 subset, 100 queries, top-10, Euclidean

  `PROXIMADB_SIFT_DATASET_DIR=$HOME/sift1m PROXIMADB_SIFT_N=100000 PROXIMADB_SIFT_QUERIES=100 \
   cargo test --release --test sift_pax_recall_ratchet_test sift_coalesced_rabitq_scan_rerank_eval -- --ignored --nocapture`
- **Reviewer PR1 ratchets (both honored):**
  (a) IVF flush opt-in ON (`PROXIMADB_PAX_FLUSH_CLUSTER=ivf`) — rerank coalescing
  assumes `cluster_order_pca_ivf` survivor locality.
  (b) a SINGLE-FILE collection — the entire base is flushed in ONE batch → one
  segment file, so the per-file "~1 RaBitQ GET" win is isolated from the PR2
  GET-budget compaction (the flush→compaction scheduler is unwired).

Recall ratchet floor (asserted in the eval): `PROXIMADB_SIFT_COALESCED_RECALL_FLOOR`
default 0.95 — recall 0.984 clears it; the ratchet only goes up. GET budget floor
`PROXIMADB_SIFT_COALESCED_GET_BUDGET` default 50 — 20 clears it.

== Interpretation

* **The GET lever is moved.** Block-centroid pruning was measured GET-capped at
  ~0.87 recall for any tight-block recall win (the binary tier was read per
  block). Hoisting RaBitQ into one coalesced header region collapses the scan to
  ~1 RaBitQ GET/file; the rerank then fetches cluster-adjacent survivors in a
  handful of coalesced GETs (the `ObjectRangeCoalescePolicy` plan). Net per-query
  GETs drop ~18.5×, moving the dominant cost term (`per_get=20 ≫ per_mib=5`).
* **Recall reaches the ~0.99 regime** at keep=100% (scan all codes, zero prune
  loss) — the regime block-pruning could not enter without shattering GETs. The
  single segment-level RaBitQ centroid (the standard RaBitQ setup — the legacy
  per-block re-fit was the unusual case) lands at 0.984; tuning the survivor pool
  `M` or per-IVF-cell centroids is the follow-up if a tighter 0.99+ is required.
* **Bytes are the deferred lever** (ADR-062 consequence): clustered SQ8/fp32
  statistical compression cuts bytes once the layout is measured in — not v1.

== What is NOT measured here (out of PR1 scope)

* PR2 GET-budget compaction (file-count = GET-count knob) — deliberately isolated
  out by the single-file collection.
* PR3 per-block OID bloom (`vector_by_id` fast path) — the `StatsKind` structure
  is emitted now; population/wiring is PR3.
* Multi-file GET scaling, footer/bloom sizing at scale, schema-evolution — all PR2/PR3/follow-on.

== 2026-07-16 full-scale follow-up

This artifact is intentionally the N=100k PR1 measurement; its `0.984` recall
and `20` GETs/query must not be generalized to N=1M. A verified full TEXMEX
N=1M, 100-query follow-up measured flat SQ8 at recall@10 `0.968`, `61`
GETs/query, and `138,851,704` bytes/query. The deferred-bytes bake-off and the
scale prerequisites it exposed are recorded in
link:RDSTRAT6_BYTES_BAKEOFF_SIFT_2026_07_16.adoc[the 2026-07-16 evidence].
