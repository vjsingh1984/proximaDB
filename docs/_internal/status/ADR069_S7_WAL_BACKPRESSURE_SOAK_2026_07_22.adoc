= ADR-069 S7 — WAL write-backpressure soak (2026-07-22)

== Purpose
TD-WAL-1 S7 acceptance evidence: under sustained write load, the ADR-069
write-path critical-watermark backpressure ENGAGES without crashing, the WAL
footprint stays BOUNDED (steady-state, not unbounded growth), and the insert
rate stays flat (the co-design trace for the WAL dimension).

== Method
`scripts/soak_wal_backpressure.py` boots a server from a base config with a
small `wal_max_bytes` + the high/critical watermarks INJECTED into
`[storage.wal_config]` so backpressure arms (it is default-OFF in production),
then sustains SDK batch inserts at a target rate for a bounded window, retrying
nothing on HTTP 429 (a shed is counted, not a failure). It scrapes
`/metrics/prometheus` every 5 s for the `proximadb_wal_*` family.

Run (from a checkout with a built server):
----
PYTHONPATH=clients/python/src scripts/soak_wal_backpressure.py \
  --server-binary ./target/release/proximadb-server \
  --base-config config/config.toml --duration-s 600 --rate-per-s 5000 --batch 500
----

Config: `wal_max_bytes = 512 KB`, `high_watermark_pct = 0.80`,
`critical_watermark_pct = 0.95`, `flush_interval_secs = 2`, dim=64 cosine.
Bounded 10-min run (the harness is parameterized to multi-hour / nightly via
`--duration-s`).

== Result (10 min / 600 s, macOS arm64)
[cols="2,4", options="header"]
|===
| signal | value
| inserts accepted | 2,611,000 (~4,350/s sustained — flat)
| backpressure engagements | `backpressure_total` +5 (engaged under load)
| WAL on-disk (`wal_size_bytes`) | plateaued at 46.6 MB (steady-state from ~t=275 s)
| non-429 failures | 0
| server | up the full 600 s, no crash (clean exit only on the flush-on-stop shutdown)
|===

== Findings
1. **Backpressure engages.** `backpressure_total` rose +5 — the critical-
   watermark admission gate fired under the ingest burst (the gate is
   default-OFF in production; armed here via the small budget).
2. **WAL footprint is bounded.** `wal_size_bytes` rose to 46.6 MB then
   *plateaued* for the second half of the run — flush + compaction reclaim at
   the ingestion rate. No unbounded growth. (Note: `wal_size_bytes` is the
   cumulative on-disk WAL, not the unflushed memtable; the bounding input the
   gate guards is the unflushed memtable, which the engagements prove stayed
   within the critical line.)
3. **Insert rate is flat.** ~4,350 accepts/s held across 10 min (2.6 M total) —
   no collapse, no throughput degradation. The system self-regulates: back-
   pressure engages on bursts, then steady-state flushes keep up.
4. **No crash.** The server stayed up the full window under sustained load +
   repeated shedding.

== Caveats / follow-ups
Indicative dev-machine evidence, **not an SLA**. This is a 10-min bounded run;
the harness is parameterized for the multi-hour / nightly soak (longer runs
detect slow degradation / leaks). Backpressure engagements were concentrated in
the warmup burst (steady-state flushes then kept the unflushed memtable under
the critical line); a higher sustained rate or slower flush would exercise
steady-state shedding more. Governed by the `BENCHMARK_EVIDENCE.toml` claim
`adr069_s7_wal_backpressure_soak`.
