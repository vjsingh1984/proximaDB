== Migration recipe

For each remaining consumer:

1. Replace `use crate::storage::multimodal::*` → `use crate::storage::multimodel::*` for any symbol that exists in both modules under the same name (ModelType, StoreCapabilities, DocumentStore, GraphStore, ObservabilityStore, RDBMSStore, VectorStore, and the htap/observability/transaction sub-symbols that don't carry `MultiModal` in the name).

2. For symbols that carry `MultiModal*` in the name (`MultiModalStorageFacade`, `MultiModalStorageEngine`, `MultiModalFacadeConfig`), replace with the `MultiModel*` equivalent. Note: `MultiModelFacadeConfig` is not currently re-exported from multimodel — either re-export it from `multimodel/facade.rs` or refactor the consumer to construct it via `MultiModelStorageFacade::new` directly.

3. `cargo check --lib` after each consumer file.

4. Once all 7 are flipped, `cargo check --lib` should still pass even after `pub mod multimodal;` and the multimodal re-exports are removed from `src/storage/mod.rs`. At that point delete `src/storage/multimodal/` entirely.

== Stale doc inside the legacy module

`src/storage/multimodal/mod.rs` has a doc-comment that reads (verbatim):

> This module was previously located at `storage::multimodal` and has been renamed to `storage::multimodal` for consistency with the Multi-Model Overhaul Spec. The old `multimodal` path remains as a compatibility re-export.

That sentence is self-referential (renamed FROM and TO the same path). It should either:

* be deleted (most accurate — the migration target is `multimodel`, not the same name), or
* be rewritten to say "this module is the legacy path; new code should use `storage::multimodel`".

Doing nothing leaves a misleading comment for any future reader.

== Why I didn't do the full migration now

The remaining 5 consumers + facade-config rework + module deletion is roughly 90 minutes of focused mechanical work plus verification (cargo check, cargo test per migrated file). That's the right size for a dedicated session, not a session-end follow-up. The migration is unblocked — there is no design decision pending — it just needs an uninterrupted block of time.
