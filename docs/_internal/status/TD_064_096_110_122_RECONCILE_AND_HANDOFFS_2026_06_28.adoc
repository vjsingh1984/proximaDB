=== 2 — TD-110 S1: recursive ON DELETE cascade (REL, S–M)

`eval "$(scripts/worktree.sh new feat/td110-recursive-cascade)"`

Already landed (do not redo): single-level ON DELETE in
`DmlService::enforce_delete_referential_actions` (`src/services/dml/mod.rs:3958`), invoked from
`execute_delete` (`:3089`). The CASCADE branch (`:4068-4099`) writes child tombstones directly
and does NOT recurse → grandchildren orphaned; the DML lock (`acquire_table_dml_lock`, `:940`)
covers only the parent. Implement: (1) route each cascaded child delete back through the
referential-action engine (recurse) for N-level chains, with cycle detection (visited
`(namespace,table)` set) + a bounded depth guard (default ~16, typed error on trip); (2) before
mutating children, acquire DML write locks on the transitive child set in a deterministic order
(sort by namespace/name) to close the TOCTOU + avoid deadlock; (3) preserve single-level
semantics + tenant scoping; (4) keep child-before-parent commit order. OUT OF SCOPE: ON UPDATE,
composite FK, PK-immutability, object_id/ADR-031, the dead `catalog/internal/enforcement.rs`.
Test: extend `tests/pgwire_fk_referential_actions_e2e.rs` (PgwireTestServer + tokio_postgres) —
3-level CASCADE chain, cyclic-FK rejection, depth-guard trip, and a two-client concurrency test
(child INSERT during parent `DELETE … RESTRICT` must not orphan); extend unit
`delete_enforces_referential_actions` (`:9243`).
