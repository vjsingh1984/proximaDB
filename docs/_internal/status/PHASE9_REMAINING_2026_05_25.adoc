== Task #69 — Phase 9.11 Security integration to runtime

=== Current state

* `proximadb_runtime::SecurityPort` exists with the RBAC / role / audit /
  policy surface (12 RPC-shaped methods).
* gRPC side fully port-backed:
  `proximadb_api::grpc::v1::security::SecurityServiceImpl` holds
  `Option<Arc<dyn SecurityPort>>` and delegates each RPC.
* REST side still uses `Arc<SecurityCoordinator>` directly via
  `src/network/auth/middleware.rs::auth_middleware_unified`.
* Production wiring: `src/network/rest/server.rs:461-476` passes
  `Arc<SecurityCoordinator>` into the axum layer with `from_fn_with_state`.

=== Actual blocker (file:line)

`SecurityCoordinator::authenticate_request` at
`src/security/security_coordinator.rs:329-348` returns
`UnifiedUserContext`, which is a **root-crate concrete type** used in 20+
files (117 references):

* `src/security/auth_service.rs`, `rbac_service.rs`, `rls/service.rs`,
  `auth/mod.rs`, `auth/ldap.rs`, `auth/oidc.rs`
* `src/network/auth/middleware.rs`, `src/network/middleware/tenant.rs`,
  `src/network/grpc/auth.rs`, `src/network/grpc/security_service.rs`
* `src/services/collection/security.rs`, `src/services/operations/secure_operations.rs`
* `src/query/unified/executor.rs`, `src/storage/traits/query.rs`,
  `src/graph/service.rs`

`SecurityPort` deliberately does NOT expose `authenticate_request` because
its return type cannot be moved to the runtime crate without either
(a) duplicating `UnifiedUserContext` as a port-level type and wrapping it
on both ends, or (b) extracting the entire `UnifiedUserContext` graph
(`UnifiedPermission`, `UnifiedAuthMethod`, effective-permissions cache,
session id, capability scopes) into a shared contracts crate.

=== Recommended next step (multi-session)

. Add a minimal `proximadb_runtime::PortUserContext` (string user_id,
  string tenant_id, Vec<String> roles, Vec<String> scopes, JSON-serialized
  effective_permissions).
. Add `SecurityPort::authenticate(AuthenticationData) -> PortUserContext`.
. Implement on `SecurityCoordinator` by lossy projection of
  `UnifiedUserContext`.
. Cut a parallel `auth_middleware_unified_port` that uses the port and
  stores `PortUserContext` in request extensions; consumers in
  `request.extensions` need to read both shapes during transition.

Estimated 3-4 commits across 8-10 files, plus a longer follow-up to
migrate the 20 consumers off `UnifiedUserContext`.  **Not actionable as a
single mechanical pass.**

== Task #76 — Phase 9.10 Service composition to runtime crate

=== Current state

* `proximadb_runtime::composition` is a 52-line stub
  (`ServiceComposer`, `DIContainer`) marked `TODO: Move service
  composition logic from src/services/mod.rs`.
* Real composition is `SharedServices` at
  `src/network/shared_services.rs` (1049 lines), holding 14 `Arc<>`-wrapped
  root-crate concrete services (`CatalogManager`, `SegmentRegistry`,
  `CollectionService`, `VectorOperationsService`, `GraphService`,
  `DocumentService`, `ObservabilityService`, `UnifiedHandlers`,
  `MetricsCollector`, `InternalMetricsUpdater`, `UnifiedQueryFacade`,
  `GraphQueryService`, `GraphExecutionService`, `ApiHandlersPort`).

=== Actual blocker

Of the 14 fields in `SharedServices`, only `ApiHandlersPort` is already a
trait object.  The remaining 13 are concrete root-crate types whose
construction graph deeply uses xCatalog + WAL + metadata + storage
internals that have not been crate-extracted yet.

The convergence work (Phase 1-5 of the workspace refactor) extracted
foundations and modality runtimes but stopped before pulling the
composition layer apart.  Service composition cannot move until each
service either: (a) is itself extracted into a sibling crate, or
(b) exposes a port trait that can live in `proximadb-runtime`.

=== Recommended next step (multi-session)

Pick one service at a time, define a port for it (mirroring the
existing `VectorOpsPort` / `CollectionPort` pattern), and migrate
`SharedServices` to hold `Arc<dyn XxxPort>`.  Estimated 13 such
port-trait + impl pairs.  Not appropriate for a single mechanical pass.

=== Design finding: port impl location (Task #76)

The 5 SharedServices fields where the corresponding port trait already
exists in `proximadb_runtime` split into TWO classes by where the
`impl XxxPort` lives:

[cols="3,3,3"]
|===
| Service | `impl XxxPort` location | Migration shape

| `CollectionService`
| Bare concrete service (`src/services/collection/manager.rs:3039`)
| Mechanical parallel-field swap — done in `89bbe7ec3`.

| `VectorOperationsService`
| Bare concrete service (`src/services/operations/vectors/legacy.rs:4991`)
| Mechanical parallel-field swap — done in `89bbe7ec3`.

| `DocStorageService` (aka `DocumentService`)
| gRPC wrapper `DocumentServiceImpl` (`src/network/grpc/document_service.rs:284`)
| Decision: move impl to bare service (see ADR-015).

| `ObservabilityService`
| gRPC wrapper `ObservabilityServiceImpl:532`
| Same decision.

| `GraphService`
| gRPC wrapper `GraphServiceImpl:1682`
| Same decision.
|===

Decision is recorded in `docs/12-design/adr/ADR-015-port-impl-location.adoc`:
the port impl belongs on the bare concrete service so SharedServices can
hold `Arc<dyn XxxPort>` directly. The gRPC wrapper becomes a thin
proto-conversion shim (which is its actual job).

Design decisions worth remembering (not in the ADR text):

* `PortAuthCredential` covers only `Jwt(String)` + `ApiKey(String)`.
  SSO and mTLS remain on the typed root-crate path until a port-need
  is articulated.
* Impl on `SecurityServiceImpl` (existing gRPC wrapper) not
  `SecurityCoordinator` (per ADR-015's "bare service" recommendation).
  Moving the entire `impl SecurityPort` to `SecurityCoordinator` is a
  separate refactor.
* `auth_middleware_unified_port` deliberately omits `DataPlaneCapability`
  handling — the capability extraction needs `UnifiedUserContext`-typed
  info that the projection loses.
