[.lead]
**v0.2 release evidence for the object-economy vector route (Beta).** Numbers come from the
existing benches under `benches/bench_vector_object_economy{,_e2e}.rs` — no new bench code
was added for this report.

== Why this exists

`MVP_RELEASE_READINESS_RECONCILIATION_2026_05_28.adoc` (P1 #3) requires evidence for the
object-economy route before v0.2 ships. The route is Beta in
link:../../SUPPORTED_SURFACE.adoc[`docs/SUPPORTED_SURFACE.adoc`] — these numbers do not
constitute a cost or recall SLA. They lock in a **non-regression** baseline that future
releases compare against.

== What this report measures

[cols="1,3", options="header"]
|===
| Block | What it answers

| Building-block CPU costs (`bench_vector_object_economy.rs`)
| How much of the strong-route critical path is consumed by directory load,
  delta merge, and tombstone suppression at 100 / 1K / 10K / 100K records.

| End-to-end cold p50/p99 (`bench_vector_object_economy_e2e.rs`)
| Wall-clock latency for the first query against a freshly constructed
  engine — page cache cold, index cold, block cache cold.

| End-to-end warm p50/p99 (`bench_vector_object_economy_e2e.rs`)
| Wall-clock latency for subsequent queries against the same engine — page
  cache populated by the cold query.

| Per-query throughput
| Queries / second under the warm steady state.
|===

== What this report cannot measure (v0.2 limitations)

The benches and this report explicitly do not produce:

* **Object-store GET count + bytes per query.** The local tempfs proxy does not surface
  GET-equivalent metrics. Cold-vs-warm latency differential is reported instead.
* **Recall @ k.** `SearchMode::Exact` is the default; that is 100% recall by definition.
  See `tests/filtered_ann_recall_bands.rs` for the ANN recall envelope at low/medium/high
  selectivity.
* **WAL delta merge cost under concurrent write + read load.** Bench harness drives
  searches against a static dataset; delta scan exits early.

These three gaps are tracked as Beta-graduation requirements for the object-economy route
post-v0.2 (see link:../../10-quality/TECHNICAL_DEBT.adoc[TECHNICAL_DEBT.adoc] —
new TD entry under "external-table/object-store evidence").

== Reproducing

[source,bash]
----
rm -rf /tmp/proximadb-bench-*

# Building-block CPU costs (5–30 s)
cargo bench --bench bench_vector_object_economy

# End-to-end cold/warm at default scale 10 000 vectors (≈ 1–3 min)
cargo bench --bench bench_vector_object_economy_e2e

# Larger e2e scale — opt-in, 5–15 min:
PROXIMADB_BENCH_VECTORS=100000 cargo bench --bench bench_vector_object_economy_e2e
----

Criterion writes HTML to `target/criterion/`; this report cites the textual output.

=== Headroom analysis vs turbopuffer reference (NOT a positioning claim)

From the bench's own analysis section:

* Merge 100K records: **~305 ms** (0.65 M rec/s @ 1.5 µs/record).
* Load 10K-block directory: **~9.7 ms** (payload 2.61 MB).
* Tombstone merge 10K: **~7.7 ms** (2.58 M rec/s).
* Freshness-mode dispatch: **~0.5 ns/call** (2.14 B calls/sec).

Implication: directory load + merge cost is small enough that a cold-query
budget of ~400 ms is dominated by object-store round trips, not local CPU.
The strong-route delta merge adds **< 1 ms per 10K-record set**, leaving the
full turbopuffer-style cold budget available for remote I/O.

== Comparison reference (NOT a positioning claim)

For context only — turbopuffer's published architecture numbers:

* Cold query (1M docs): ~400–500 ms, 3–4 object-store round trips.
* Warm query (1M docs): ~14 ms p50.

ProximaDB v0.2 ships object-economy as Beta and does **not** claim cost or latency parity
with these numbers. The bench above measures the building-block headroom — whether the
shipped code has room to reach those numbers without new architecture, not whether it
does today.
