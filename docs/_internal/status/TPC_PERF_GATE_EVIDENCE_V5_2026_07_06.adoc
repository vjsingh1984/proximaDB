= TPC gate evidence v5 — Slice B (runtime join filter) isolated, proven complementary to Slice A (2026-07-06)

First measurement taken through the FIXED I/O meter (v4 / PR #694). v3 reported
the runtime-filter gate as "zero incremental pruning"; that reading was an
artifact of the broken meter (scan reads on DataFusion-spawned partition tasks
escaped the per-query trace). With attribution fixed, an isolated A/B run shows
Slice B delivers a large, correct fact-table byte reduction on exactly the
star-schema shape it exists for.

== Method

Same generator seed, scale (0.02), row-group geometry
(`PROXIMADB_MATERIALIZE_ROW_GROUP_ROWS=4096`), local-tempdir, debug, `first`
temperature. Only the gate differs:

* *A* — `PROXIMADB_DF_RUNTIME_FILTER_PRUNE` unset (static WHERE pushdown only).
* *A+B* — `=1` (static + runtime join-filter split pruning at stream-open).

Per-query `bytes_read` (attributed) is the ground truth; `splits_*` counters are
secondary (and double-count when the gate is on — see caveat).

== Result: B prunes the fact table where A structurally cannot

The TPC-DS star queries filter on `date_dim` (`d_year=2000 AND d_moy=11`), NOT on
the `store_sales` fact table — so static pushdown prunes nothing on the fact scan:

|===
| query | A: pruned / bytes | A+B: pruned / bytes | fact-scan bytes saved

| tpcds/q3  | 0/17 · 2,577,515 | 11/33 · 1,566,940 | **1,010,575 (−39%)**
| tpcds/q42 | 0/17 · 2,577,515 | 13/33 · 1,370,988 | **1,206,527 (−47%)**
| tpcds/q52 | 0/17 · 2,577,515 | 13/33 · 1,370,988 | **1,206,527 (−47%)**
| tpcds/q55 | 0/17 · 2,577,515 | 13/33 · 1,370,988 | **1,206,527 (−47%)**
|===

The runtime filter builds the `ss_sold_date_sk` key range from the filtered
`date_dim` build side and prunes ~half the fact-table row groups before fetch —
the classic star-schema semi-join lever (Databricks AQE / Snowflake SOS).

TPC-H shows only ±1 KB jitter across all 22 queries: its fact-table predicates
(`l_shipdate` etc.) sit directly in the `WHERE`, so **Slice A already prunes
them** and B adds nothing to fetch. The small ± deltas are footer-read variation
from the extra dynamic-filter plan node, not real I/O.

**Conclusion: A and B are complementary, not redundant.** A covers direct
fact-table predicates (most of TPC-H); B covers dimension-only predicates that
reach the fact table solely through the join (the TPC-DS star case). Suite total
at this scale: A = 213.0 MB, A+B = 208.4 MB (−2.18%), concentrated entirely in
the four dimension-filtered star queries.

== Caveats before promoting the gate to default-ON

. *Small-scale/debug/single-machine.* Direction is unambiguous (B prunes fact
  row groups A cannot), but the absolute figures are scale-0.02 debug. Confirm at
  a larger scale before flipping the default.
. *`wait_complete()` stall-safety.* The stream head awaits each absorbed filter's
  completion (0 ms when resolved; 10 s bounded fallback). Before it is the default
  path, validate no common plan shape leaves a filter unresolved and eats the
  10 s per scan.
. *`splits_*` double-count when gate on.* Static `scan()` records the full
  candidate universe and runtime `execute()` re-records per surviving split, so
  `splits_total` inflates (e.g. 17→33). `bytes_read` is unaffected and remains the
  authoritative signal; the counter pair should be de-duplicated (separate
  static/runtime pairs, or execute() adds to `pruned` only) — filed as follow-up.

== Recommendation

Promotion of `PROXIMADB_DF_RUNTIME_FILTER_PRUNE` to default-ON is now
**evidence-supported** (P2a's stated success criterion — "promote once the ledger
evidences the skip ratio" — is met). Gate the flip on the three caveats above in a
dedicated, correctness-ratcheted PR (conformance stays green with the gate on in
these runs; keep it that way). Until then the gate remains opt-in.
