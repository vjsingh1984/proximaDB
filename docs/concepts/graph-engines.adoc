= Graph Engines
:toc: left
:toclevels: 2
:icons: font

[.lead]
ProximaDB provides 3 graph engines for different scaling challenges. This guide helps you choose the right engine for your graph workload.

== Quick Decision Matrix

[cols="1,2,2,2", options="header"]
|===
| Engine | Scaling Dimension | Best For | Limitation

| **ORION**
| Latency (in-memory)
| Real-time traversal, <1ms queries
| Must fit in RAM

| **PULSAR**
| Capacity (distributed)
| Billion+ nodes across shards
| Network latency for cross-shard

| **QUASAR**
| Cost (tiered storage)
| Large sparse graphs, hot/cold
| Higher latency for cold data
|===

== ORION: In-Memory Engine

**Problem solved**: Real-time graph traversal with sub-millisecond latency.

**Key innovation**: Compressed Sparse Row (CSR) format enables O(1) neighbor lookup with cache-friendly sequential memory access.

=== CSR Format

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
flowchart LR
    subgraph ADJ["Adjacency List"]
        A1["Node 0 → [1,2,3]"]
        A2["Node 1 → [2]"]
        note1["Random access<br/>Cache unfriendly"]
    end

    subgraph CSR["CSR Format"]
        C1["offsets: [0,3,4,4]"]
        C2["targets: [1,2,3,2]"]
        note2["Sequential access<br/>Cache friendly"]
    end

    style ADJ fill:#ffe6e6
    style CSR fill:#e6ffe6
----

**Neighbor lookup**:
1. Read `offsets[i]` and `offsets[i+1]`
2. Slice `targets[start..end]`
3. Cost: O(1) + O(degree)

=== Performance

|===
| Metric | Value

| Node lookup | <1 microsecond
| Edge traversal | 1M+ edges/sec
| Parallel BFS | 10K frontier → 15ms (vs 100ms serial)
| Memory overhead | ~100 bytes/node
|===

=== When to Use

**Choose ORION when**:
- Graph fits in memory (<100GB)
- Sub-millisecond queries required
- Real-time recommendations, social graphs
- Concurrent read/write needed

**Avoid ORION when**:
- Graph exceeds available RAM
- Cold data rarely accessed (waste of memory)

---

== PULSAR: Distributed Engine

**Problem solved**: Graphs too large for a single machine.

**Key innovation**: Consistent hashing distributes nodes across shards with minimal rebalancing on cluster changes.

=== Sharding Strategy

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
flowchart TB
    subgraph NAIVE["Hash Mod N"]
        N1["Add shard → rehash ALL"]
    end

    subgraph CONSISTENT["Consistent Hashing"]
        C1["Add shard → move 1/N data"]
    end

    style NAIVE fill:#ffe6e6
    style CONSISTENT fill:#e6ffe6
----

=== Cross-Shard Traversal

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
sequenceDiagram
    participant C as Coordinator
    participant S1 as Shard 1
    participant S2 as Shard 2

    C->>S1: Get neighbors of node A
    S1-->>C: [B, C, D]
    Note over C: B on Shard 2
    C->>S2: Get neighbors of node B
    S2-->>C: [E, F]
    C-->>Client: Merged results
----

=== Performance

|===
| Metric | Value

| Single-shard query | 5-10ms
| Cross-shard (2 hops) | 20-50ms
| Rebalancing (add shard) | ~1/N data moved
| Max tested | 10B+ edges
|===

=== When to Use

**Choose PULSAR when**:
- Graph exceeds single-machine memory
- Billion+ node scale required
- Can tolerate 10-50ms latency
- Need horizontal scaling

**Avoid PULSAR when**:
- Sub-millisecond latency required
- Graph fits in memory (ORION simpler)

---

== QUASAR: Tiered Storage Engine

**Problem solved**: Large sparse graphs where most data is cold but some is frequently accessed.

**Key innovation**: Three-tier storage (Memory → SSD → Object Store) with automatic promotion/demotion based on access patterns.

=== Storage Tiers

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
flowchart TB
    subgraph HOT["Hot Tier: Memory"]
        H1["Frequently accessed nodes"]
        H2["Latency: <1ms"]
    end

    subgraph WARM["Warm Tier: SSD"]
        W1["Recently accessed"]
        W2["Latency: 1-10ms"]
    end

    subgraph COLD["Cold Tier: S3/GCS"]
        C1["Rarely accessed"]
        C2["Latency: 50-200ms"]
    end

    HOT -->|Evict| WARM
    WARM -->|Evict| COLD
    COLD -->|Promote| WARM
    WARM -->|Promote| HOT

    style HOT fill:#e6ffe6
    style WARM fill:#fff3e6
    style COLD fill:#e6f3ff
----

=== Tiering Policy

|===
| Event | Action

| Access count > threshold | Promote to hotter tier
| No access for TTL | Demote to colder tier
| Memory pressure | Evict LRU to warm
| Query prefetch | Promote neighbors speculatively
|===

=== When to Use

**Choose QUASAR when**:
- Large graph with clear hot/cold separation
- Cost optimization over latency
- Archival queries acceptable at 50-200ms
- S3/GCS storage already in use

**Avoid QUASAR when**:
- Uniform access patterns (no hot/cold)
- All queries need sub-10ms latency

== Configuration Examples

=== ORION (Default)

[source,toml]
----
[graph]
default_engine = "orion"

[graph.orion]
parallel_threshold = 1000  # BFS parallelization threshold
wal_enabled = true
----

=== PULSAR (Distributed)

[source,toml]
----
[graph]
default_engine = "pulsar"

[graph.pulsar]
shards = 8
replication_factor = 3
coordinator_timeout_ms = 5000
----

=== QUASAR (Tiered)

[source,toml]
----
[graph]
default_engine = "quasar"

[graph.quasar]
hot_tier_mb = 4096
warm_tier_path = "/data/ssd/graph"
cold_tier_url = "s3://bucket/graph"
promote_threshold = 10  # accesses
demote_ttl_hours = 24
----

== Hybrid Vector + Graph Queries

ProximaDB's unique capability: combine vector similarity with graph traversal.

[source,python]
----
# Find similar documents AND their citation network
results = db.hybrid_search(
    collection="papers",
    vector=query_embedding,        # Vector similarity
    graph_traversal="citations",   # Graph edges
    hops=2,                        # 2-hop citations
    top_k=10
)
# Returns: similar papers + their citations + shared authors
----
