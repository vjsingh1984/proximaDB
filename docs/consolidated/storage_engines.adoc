== Production Engines (✅ Ready)

=== SST Engine
**Sorted String Table** - Zero-copy LSM with three-stage filtering

* **Implementation**: 26,488 lines of production code
* **Architecture**: Row-based LSM with WAL and MemTable integration
* **Optimization**: Three-stage filtering (Bloom → Quantized → Full), zero-copy compaction
* **Performance**: 200K vectors/sec write, <5ms P99 latency

link:sst.adoc[Full SST Documentation →]

=== VIPER Engine
**Vectorized Intelligence Parquet Engine for Retrieval** - Columnar analytics storage

* **Implementation**: 22,581 lines of production code
* **Architecture**: Apache Parquet-based columnar format
* **Optimization**: Advanced quantization pipeline, predicate pushdown, zone maps
* **Performance**: 500K vectors/sec batch write, 5-10x compression

link:viper.adoc[Full VIPER Documentation →]

=== HELIX Engine
**High-Efficiency Locality-Indexed eXecution** - Similarity-optimized storage

* **Implementation**: 7,783 lines of production code
* **Architecture**: Disk-only LSM with PCA+Hilbert clustering
* **Optimization**: FastLane blocks, liquid clustering, aggressive pruning
* **Performance**: 150K vectors/sec, 70-90% query pruning

link:helix.adoc[Full HELIX Documentation →]

== Production Engines (Continued)

=== RAPTOR Engine
**Row-Aligned Predicated Tensor Optimized Repository** - Graph-optimized storage

* **Implementation**: 18,191 lines of production code
* **Architecture**: Matrix Trinity navigation (P²+K²+P×K) replacing HNSW
* **Optimization**: Artus bloom filters (200x memory savings vs B-tree)
* **Performance**: 100K vec/s, O(1) centroid lookup, <10ms graph traversal

== Migration Guide

=== Switching Engines
[source,bash]
----
# Export from current engine
proximadb-cli export \
  --engine sst \
  --collection my_data \
  --format parquet \
  --output data.parquet

# Update configuration
sed -i 's/default_engine = "sst"/default_engine = "helix"/' config.toml

# Restart and import
systemctl restart proximadb
proximadb-cli import --collection my_data --format parquet
----

= HELIX Storage Engine
:toc: left
:toclevels: 3
:icons: font

[abstract]
**High-Efficiency Locality-Indexed eXecution** - A disk-only LSM engine with 7,783 lines of implementation. Uses PCA dimensionality reduction and Hilbert curve clustering for physical co-location of similar vectors, achieving 70-90% query pruning with 150K vectors/sec throughput.

image::../assets/logos/helix-engine-logo.svg[HELIX Engine Logo, 200, align="center"]

== Overview

The HELIX engine is designed for similarity search workloads where vectors exhibit natural clustering patterns. By combining PCA dimensionality reduction with Hilbert curve space-filling properties, HELIX preserves locality while enabling efficient pruning of irrelevant data during searches.

=== Key Features

* **Disk-Only LSM**: No embedded memtable/WAL - uses global infrastructure
* **PCA + Hilbert Clustering**: Physical co-location of similar vectors
* **FastLane Columnar Blocks**: SIMD-optimized columnar format
* **Liquid Clustering**: Query pattern-based adaptive clustering
* **Parallel Search**: Configurable threads (default: 3 files minimum)
* **EventLog Integration**: Async AXIS indexing support

=== When to Use HELIX

[cols="1,2", options="header"]
|===
| Use HELIX When | Don't Use When

| Similarity search is primary
| Need real-time updates

| Data has natural clusters
| Random access patterns

| Can batch writes
| Ultra-low latency (<2ms)

| Read-heavy workload
| Frequently changing data
|===

=== Component Details

==== PCA Transformation
* Reduces dimensions from original (e.g., 768) to 64
* Preserves 95%+ of variance
* Trained incrementally on data batches
* Cached for query transformation

==== Hilbert Clustering
* Maps 64D space to 1D Hilbert curve
* Preserves spatial locality
* Groups similar vectors in same files
* Enables efficient range queries

==== LSM Tree Structure
* **L0**: In-memory buffer (MemTable)
* **L1**: Small sorted files (4-8MB)
* **L2**: Larger compacted files (32-64MB)
* **Compaction**: Merges and re-clusters periodically

== Configuration

=== Basic Configuration

[source,toml]
----
[storage]
default_engine = "helix"

[engines.helix]
# PCA configuration
pca_dimensions = 64              # Target dimensions after PCA
pca_retrain_interval_hours = 24  # PCA model retrain interval

# Clustering configuration
fastlane_block_size = 1024       # Vectors per FastLane block
hilbert_bits_per_dimension = 16  # Hilbert curve resolution
enable_liquid_clustering = true   # Query-based adaptive clustering

# Search configuration
parallel_search_enabled = true   # Enable parallel search
parallel_search_threshold = 3    # Min files for parallel (default)
max_search_threads = 0           # 0 = CPU cores / 2 (auto)

# LSM configuration
level0_file_num_compaction_trigger = 4  # L0 compaction trigger
max_levels = 7                          # Maximum LSM levels
size_ratio = 10.0                       # Size ratio between levels
storage_quantization = true             # Enable storage quantization
bloom_filter_bits_per_key = 10         # Bloom filter configuration
block_cache_size_mb = 256               # Block cache size
----

=== Key Components

==== FastLane Columnar Blocks
* SIMD-optimized columnar format for vector storage
* Better compression and cache locality than row format
* Direct integration with hardware acceleration

==== Liquid Clustering
* Adaptive clustering based on query patterns
* Reorganizes data during compaction for better locality
* Tracks access patterns to optimize future queries

==== Disk-Only Design
* No embedded memtable or WAL
* Relies on global infrastructure for durability
* Receives flushed data from EventLog system
* Pure disk-based LSM implementation

=== Unique Features

==== Hilbert Curve Mapping
* Maps high-dimensional PCA space to 1D curve
* Preserves locality for range queries
* Configurable resolution (bits per dimension)

==== Zone Maps with Pruning
* Min/max bounds per SSTable
* Hilbert range filtering
* 70-90% file pruning before search

==== Progressive Search Integration
* Uses unified progressive search framework
* Binary → INT8 → PQ → Full precision pipeline
* Shared with other storage engines

== Implementation Details

=== File Format

HELIX files use a custom SST-like format:

```
[Header]
  Magic: "HELIX001"
  PCA Model Reference
  Hilbert Parameters
  Vector Count
  Dimension Info

[Data Blocks]
  Block 1: [Vector Data + Metadata]
  Block 2: [Vector Data + Metadata]
  ...

[Index]
  Hilbert Range Index
  Block Offsets
  Bloom Filter

[Footer]
  Checksum
  Compression Info
```

=== PCA Model Management

The PCA model is:
1. Trained on first 100K vectors (configurable)
2. Stored separately from data files
3. Shared across all HELIX files
4. Updated incrementally if needed

== Troubleshooting

=== Common Issues

==== Poor Pruning Rate
**Symptom**: Less than 50% files pruned

**Causes**:
1. Data lacks natural clusters
2. PCA dimensions too low
3. Hilbert bits insufficient

**Solutions**:
```toml
pca_dimensions = 128      # Increase dimensions
hilbert_bits = 20         # More Hilbert precision
clustering_batch_size = 100000  # Larger clusters
```

==== Slow Compaction
**Symptom**: Compaction takes > 60 seconds

**Solutions**:
1. Reduce file sizes
2. Adjust compaction triggers
3. Use faster compression

```toml
l1_size_mb = 128          # Smaller files
compaction_threads = 4     # More threads
compression = "lz4"        # Faster algorithm
```

==== Memory Usage
**Symptom**: High memory consumption

**Solutions**:
1. Reduce cache size
2. Lower PCA dimensions
3. Disable parallel search

```toml
cache_size_mb = 512       # Smaller cache
pca_dimensions = 32       # Fewer dimensions
parallel_search_enabled = false
```

== Best Practices

=== Data Preparation
1. **Normalize vectors** before insertion
2. **Batch writes** in 50-100K chunks
3. **Pre-sort** by similarity if possible
4. **Remove duplicates** to improve clustering

=== Query Optimization
1. **Use filters** to reduce search space
2. **Cache frequent queries** at application level
3. **Adjust k** parameter based on recall needs
4. **Monitor pruning rates** regularly

=== Maintenance
1. **Schedule compaction** during low traffic
2. **Monitor cluster quality** over time
3. **Retrain PCA** if data distribution changes
4. **Archive old data** to maintain performance

pub struct ZoneMap {
    // Basic statistics
    min_value: Value,
    max_value: Value,
    null_count: u64,
    
    // Advanced statistics
    bloom_filter: BloomFilter,
    distinct_count: u64,
    histogram: Histogram,
    
    // Vector-specific
    centroid: Vec<f32>,
    radius: f32,
    pca_components: Matrix,
}

impl ZoneMap {
    pub fn can_skip(&self, predicate: &Predicate) -> bool {
        match predicate {
            Predicate::Range(min, max) => {
                self.max_value < *min || self.min_value > *max
            }
            Predicate::In(values) => {
                !values.iter().any(|v| self.bloom_filter.contains(v))
            }
            Predicate::VectorSimilarity(query, threshold) => {
                let distance = compute_distance(query, &self.centroid);
                distance - self.radius > threshold
            }
            _ => false
        }
    }
}

pub struct NOVAOptimizer {

    cost_model: CostModel,

impl NOVAOptimizer {
    pub fn optimize(&self, query: &Query) -> ExecutionPlan {
        // Generate candidate plans
        let candidates = self.generate_plans(query);
        
        // Estimate cost for each plan
        let costs: Vec<_> = candidates.iter()
            .map(|plan| self.estimate_cost(plan))
            .collect();
        
        // Select best plan
        let best_idx = costs.iter()
            .position_min()
            .unwrap();
            
        candidates[best_idx].clone()
    }
    
    fn estimate_cost(&self, plan: &ExecutionPlan) -> f64 {
        let io_cost = self.estimate_io(plan);
        let cpu_cost = self.estimate_cpu(plan);
        let memory_cost = self.estimate_memory(plan);
        
        io_cost * 1.0 + cpu_cost * 0.5 + memory_cost * 0.3
    }
}

        let mut current_plan = plan;
        
        loop {
            // Execute next operator
            let result = self.execute_operator(&current_plan.next());
            
            // Collect runtime statistics
            self.runtime_stats.update(&result);

            if self.should_reoptimize() {

                    current_plan,
                    &self.runtime_stats

            if current_plan.is_complete() {

            }
        }

    epoch: Arc<Epoch>,

    vectors: Arc<LockFreeHashMap<VectorId, AtomicVector>>,

impl AtomicVector {
    // Wait-free read
    pub fn read(&self) -> VectorData {
        let ptr = self.data.load(Ordering::Acquire);
        unsafe { &*ptr }.clone()
    }
    
    // Lock-free update with CAS
    pub fn update(&self, new_data: VectorData) -> bool {
        loop {
            let current = self.data.load(Ordering::Acquire);
            let new_ptr = Box::into_raw(Box::new(new_data));
            
            match self.data.compare_exchange(
                current,
                new_ptr,
                Ordering::Release,
                Ordering::Acquire
            ) {
                Ok(_) => {
                    self.epoch.defer(move || {
                        unsafe { Box::from_raw(current); }
                    });
                    return true;
                }
                Err(_) => {
                    unsafe { Box::from_raw(new_ptr); }
                }
            }
        }
    }
}

impl NumaAllocator {
    pub fn allocate_aligned(&self, size: usize, align: usize) 
        -> Result<*mut u8> {
        // Allocate from local NUMA node
        let ptr = unsafe {
            numa_alloc_onnode(
                size,
                self.node_id
            )
        };
        
        // Track usage
        self.used.fetch_add(size, Ordering::Relaxed);
        
        // Prefault pages for lower latency
        if self.prefault_enabled {
            self.prefault_pages(ptr, size);
        }
        
        Ok(ptr)
    }
    
    fn prefault_pages(&self, ptr: *mut u8, size: usize) {
        // Touch every page to prevent page faults
        let page_size = 4096;
        for offset in (0..size).step_by(page_size) {
            unsafe {
                ptr.add(offset).write(0);
            }
        }
    }
}

== Bloom Filter Implementation

=== Design Rationale

RAPTOR uses bloom filters instead of B-trees because:

1. **Memory Efficiency**: 180KB vs 40-60MB for 1M vectors
2. **O(1) Lookups**: Constant time vs O(log n)
3. **Cache Friendly**: Fits in L3 cache
4. **No Rebalancing**: No tree maintenance overhead

=== Implementation

[source,rust]
----
pub struct RaptorBloomFilter {
    filters: Vec<BloomFilter>,    # Sharded filters
    capacity: usize,              # Vectors per filter
    fpp: f64,                     # False positive probability
}

impl RaptorBloomFilter {
    pub fn new(expected: usize, fpp: f64) -> Self {
        // Calculate optimal parameters
        let num_bits = Self::optimal_bits(expected, fpp);
        let num_hashes = Self::optimal_hashes(num_bits, expected);
        
        // Create sharded filters for parallelism
        let num_shards = num_cpus::get();
        let filters = (0..num_shards)
            .map(|_| BloomFilter::new(num_bits / num_shards, num_hashes))
            .collect();
            
        Self {
            filters,
            capacity: expected,
            fpp,
        }
    }
    
    pub fn insert(&mut self, id: &str) {
        let shard = self.hash_to_shard(id);
        self.filters[shard].insert(id);
    }
    
    pub fn contains(&self, id: &str) -> bool {
        let shard = self.hash_to_shard(id);
        self.filters[shard].contains(id)
    }
}

        self.connect_neighbors(id, level);
    }
    
    pub fn search(&self, query: &Vector, k: usize) -> Vec<SearchResult> {
        // Trinity navigation for entry points
        let entries = self.trinity.navigate(query);
        
        // HNSW search from entry points
        let candidates = self.graph.search_from_entries(
            query, 
            entries, 
            k * 2  // Over-fetch for filtering
        );
        
        // Filter and rank
        self.filter_and_rank(candidates, k)
    }
}

impl BlockAllocator {
    fn allocate_block(&mut self, level: u8) -> BlockId {
        match level {
            0 => self.allocate_root_block(),
            1 => self.allocate_directory_block(),
            2 => self.allocate_index_block(),
            3 => self.allocate_data_block(),
            _ => panic!("Invalid level")
        }

    fn should_split(&self, block: &SuperBlock) -> bool {
        block.vector_count > self.max_vectors_per_block ||
        block.radius > self.max_radius_threshold
    }
    
    fn should_merge(&self, blocks: &[SuperBlock]) -> bool {
        let total: u64 = blocks.iter()

        total < self.min_vectors_per_block
    }

=== Query Execution

==== Hierarchical Search
[source,rust]
----
fn search_hierarchical(
    query: &[f32],
    k: usize,
    root: &SuperBlock
) -> Vec<SearchResult> {
    let mut candidates = BinaryHeap::new();
    let mut visited = HashSet::new();
    
    // Start from root
    candidates.push(root);
    
    while let Some(block) = candidates.pop() {
        if visited.contains(&block.block_id) {
            continue;
        }
        visited.insert(block.block_id);
        
        match block.level {
            0..=2 => {
                // Non-leaf: explore children
                for child_ref in &block.children {
                    let distance = compute_distance(
                        query, 
                        &child_ref.centroid
                    );
                    
                    if distance < threshold {
                        let child = load_block(child_ref);
                        candidates.push(child);
                    }
                }
            }
            3 => {
                // Leaf: search vectors
                search_vectors(query, k, &block.vectors);
            }
            _ => {}
        }
    }
    
    get_top_k_results(k)
}

= VIPER Storage Engine
:toc: left
:toclevels: 3
:icons: font

[abstract]
**Vectorized Intelligence Parquet Engine for Retrieval** - A production-ready columnar storage engine with 22,581 lines of implementation. Features advanced quantization pipeline, predicate pushdown, and Apache Parquet integration for 5-10x compression and 500K vectors/sec batch throughput.

image::../assets/logos/viper-engine-logo.svg[VIPER Engine Logo, 200, align="center"]

== Overview

The VIPER engine leverages Apache Parquet's columnar format to provide exceptional compression ratios and analytical query performance. By storing vectors and metadata in columnar format with aggressive compression and quantization, VIPER achieves 5-10x storage reduction while maintaining excellent batch processing throughput.

=== Key Features

* **Shared Columnar Infrastructure**: Uses common columnar module for consistency
* **Progressive Search Pipeline**: 7-phase optimization (Bloom → Binary → INT8 → PQ → Hybrid → FP32 → Cache)
* **Predicate Pushdown**: Returns row indices without reading vectors (60-90% I/O savings)
* **Zero-Copy Serialization**: BinaryArray with bytemuck for optimal performance
* **EventLog Integration**: Async indexing with ~600 line queue system
* **Production Ready**: 2.5-3x search performance, -52% P50 latency

pub struct QuantizationPipeline {
    stages: Vec<QuantizationStage>,

impl QuantizationPipeline {
    pub fn execute(&self, vectors: &[f32]) -> QuantizedVectors {
        // Stage 1: Binary quantization for initial filtering
        let binary = self.binary_quantize(vectors);
        
        // Stage 2: INT8 for intermediate precision
        let int8 = self.int8_quantize(vectors);
        
        // Stage 3: Product Quantization for storage
        let pq = self.pq_quantize(vectors);
        
        QuantizedVectors {
            binary,
            int8,
            pq,
            original_sample: self.sample(vectors),
        }
    }

== Troubleshooting

=== Common Issues

==== Slow Batch Writes
**Symptom**: Batch insertion < 100K vec/s

**Causes**:
1. Small batch sizes
2. Excessive compression
3. Complex quantization

**Solutions**:
```toml
batch_size = 50000           # Larger batches
compression_level = 3        # Faster compression
quantization_level = "int8"  # Simpler quantization
```

==== High Storage Usage
**Symptom**: Storage > 1GB per million vectors

**Solutions**:
1. Enable quantization
2. Increase compression level
3. Run compaction

```toml
quantization_enabled = true
quantization_level = "pq8"
compression_level = 9
compaction_threshold = 0.2
```

==== Poor Query Performance
**Symptom**: P99 latency > 10ms

**Solutions**:
1. Enable statistics
2. Add bloom filters
3. Optimize row group size

```toml
enable_statistics = true
enable_bloom_filters = true
row_group_size = 50000  # Smaller for faster seeks
```
