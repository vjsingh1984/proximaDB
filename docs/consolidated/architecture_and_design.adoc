== 💡 Key Architectural Innovations

=== 1. Proto-First Design

[NOTE]
====
**Zero double serialization** - VectorRecord flows natively through the entire pipeline without conversion overhead.

**Direct memtable access** - Achieves 40-60% latency improvement by bypassing intermediate layers.

**Type safety** - Compile-time guarantees ensure data integrity throughout the system.
====

=== 2. Bloom Filter Optimization

[TIP]
====
**95% metadata scan reduction** - Dramatically reduces the search space before expensive operations.

**180KB vs 40-60MB** memory usage represents a 200x memory savings for 1M vectors.

**Scattered ID handling** - Optimized for HNSW-organized data where IDs are not sequential.
====

=== 3. EventLog Queue System

[IMPORTANT]
====
**Zero write amplification** - Metadata-only queue prevents data duplication during writes.

**Async indexing** - Decouples write acknowledgment from index updates: Flush → EventLog → AXIS processing.

**Queue-aware compaction** - Protects files until AXIS acknowledges processing completion.
====

=== 4. Hardware Acceleration

[CAUTION]
====
**Automatic detection** - Supports SIMD instruction sets: AVX-512, AVX2, SSE, NEON.

**GPU support** - Lazy initialization with graceful fallback to CPU processing.

**Cached backend selection** - Learns optimal performance paths for different workloads.
====

== Performance Summary

This architecture delivers:

* **Sub-microsecond latencies** for vector operations
* **20.8M+ operations per second** sustained throughput  
* **45-65% memory reduction** through optimization
* **Single API simplicity** despite multi-engine complexity

The unified platform provides the performance benefits of specialized engines while maintaining the operational simplicity of a single database system.

 = Hybrid Query Orchestration
 :toc:
 :toclevels: 2

 == Overview
 Hybrid queries combine vector similarity and graph traversal within one plan. ProximaDB supports a federated orchestration path today and a storage-coupled SKS path in progress.

== Federated Orchestration (Current)
 - Parsing: `sql_frontend/{parser,lowering}.rs` map SIMILAR/FOLLOW to internal AST.
 - Planning: `query/execution/planner.rs` emits `ExecutionOperation::{VectorSearch, GraphTraversal, Fusion, Project, Aggregate}`.
 - Execution: `query/execution/executor.rs`
   - Runs vector and graph operations in parallel where possible
   - Optional seed handoff (vector seeds → FOLLOW; graph seeds → SIMILAR)
   - Applies fusion (RRF default) → paginate/stream

== Storage-Coupled SKS (Planned v1)
 - Storage: `storage/entity_store.rs` implements `EntityStore` with shared headers (Arc) and embedding pointers; `CsrRelationsStore` for adjacency.
 - Benefits: Zero-copy headers, unified indexes, lower latency for SIMILAR→FOLLOW.
 - Fallback: Feature flag toggles to federated path.

== ExecutionOperation Contracts
 - VectorSearch { collection_id, query_vector, filters, top_k, distance_metric }
 - GraphTraversal { start_nodes, edge_types, max_depth, filters }
 - Fusion { strategy: RRF|Additive|Adaptive, weights }
 - Project/Aggregate (optional)

== Seed Handoff Patterns
- Vector→Graph: Use vector ids as start_nodes for FOLLOW depth D.
- Graph→Vector: Use visited node ids as SIMILAR seeds (e.g., average embeddings or per-node embeddings).

=== Seeding Strategy Controls
- SQL hints: `-- SEEDING: AVERAGE | PER_SEED | NONE` (or `SEED USING ...`)
- REST field: `seeding: "average" | "per_seed" | "none"` in `/api/v1/sql/execute` body
- Behavior:
  - AVERAGE: Averages up to 32 seeds into one query vector (fast)
  - PER_SEED: Runs per-seed vector queries (higher recall; costlier)
  - NONE: Disables graph→vector seeding (id-only rows)

== Pagination & Streaming
 - Emit paged results from executor; when enabled, stream fused rows incrementally.
 - REST/gRPC surfaces via UnifiedHandlers.

== Acceptance Criteria
 - Deterministic fusion with ties; stable pagination
 - Backpressure-friendly streaming
- Clear EXPLAIN with operations and costs

== Graph Engines (MVP)

- ORION (default): In-memory CSR engine used by `GraphService` for traversal in hybrid queries.
- PULSAR (single-process MVP): Runs as a single shard in-process; can back `GraphService` for larger graphs without network.
- QUASAR (single-process MVP): Hot/cold tiering with ORION as hot tier inside one process; suitable for cost-aware workloads.

Integration: The Hybrid Orchestrator is engine-agnostic; `GraphTraversal` routes through `GraphService`. Engine selection is a construction-time concern (factory/config). Default is ORION; PULSAR/QUASAR can be enabled in single-process deployments.

== Overview

ProximaDB supports a progressive search pipeline that refines candidates across multiple stages (Binary → INT8 → PQ → FP32) to balance latency and recall.

== Stage Flow

[source,mermaid]
----
%%{init: {'theme':'neutral','themeVariables': {'primaryColor':'#0d47a1','primaryTextColor':'#fff','lineColor':'#1565c0'}} }%%
flowchart LR
  Q([Query Vector]) --> P1{{Binary Filter}}
  P1 --> P2{{INT8 Ranking}}
  P2 --> P3{{PQ Ranking}}
  P3 --> P4{{FP32 Rerank}}
  P4 --> R([Top-K Results])

  classDef stage fill:#e3f2fd,stroke:#1565c0,color:#0d47a1;
  class P1,P2,P3,P4 stage;
----

== Stage Sizing

Let k be the final Top-K. With per-stage recalls r₁..rₙ, the candidates for stage i+1 are: k / (Π rⱼ for j≤i).

[source]
----
P1: binary_candidates = k / r1
P2: int8_candidates  = k / (r1 * r2)
P3: pq_candidates    = k / (r1 * r2 * r3)
P4: fp32_candidates  = k
----

== Configuration

The effective recalls and scenario are derived from collection quantization config and runtime hints.

[source,toml]
----
[quantization]
enabled = true
enable_progressive_search = true
quality_threshold = 0.95
binary_filter_selectivity = 0.10
int8_ranking_selectivity  = 0.20
pq_ranking_selectivity    = 0.30
----

== Code Integration

- Stage planning: `ProgressiveSearchConfig` + stage sizing helpers
- Execution: storage engines evaluate candidates per stage (Bloom → Binary → INT8 → PQ → FP32)
- REST: Progressive endpoints return the same envelope as regular search (VectorOperationResponse with SearchVectorRecord items)

== Notes

- Stage execution is designed to be zero-copy and SIMD-aware where possible.
- Caching applies across stages to minimize repeated work.

== Overview

ProximaDB is designed as a high-performance vector database with a focus on hardware acceleration, storage engine specialization, and zero-copy operations.

== Design Philosophy

=== Core Principles

[cols="1,3", options="header"]
|===
| Principle | Description


| *Proto-First*
| All data flows as protobuf messages, eliminating serialization overhead

| *Hardware-Aware*
| Automatic detection and utilization of SIMD, GPU, and cache hierarchies

| *Zero-Copy*
| Minimize data movement through memory-mapped files and direct buffers

| *Engine Specialization*
| Multiple storage engines optimized for specific workloads

| *Progressive Refinement*
| Multi-stage search from coarse to fine-grained matching
|===

// Simplified write path
async fn insert_vector(request: InsertRequest) -> Result<InsertResponse> {
    // 1. Validation
    validate_request(&request)?;
    
    // 2. Select storage engine
    let engine = select_engine(&request.collection)?;
    
    // 3. Transform to internal format
    let record = VectorRecord::from_proto(request.vector);
    
    // 4. Write to memtable (fast path)
    engine.write_to_memtable(&record).await?;
    
    // 5. Async write to EventLog
    event_log.append(Event::Insert(record.clone())).await?;
    
    // 6. Background indexing
    spawn_indexing_task(record);
    
    Ok(InsertResponse::success())
}

=== Read Path

[source,rust]
----
// Simplified search path
async fn search_vectors(request: SearchRequest) -> Result<SearchResponse> {
    // 1. Query planning
    let plan = QueryPlanner::plan(&request)?;
    
    // 2. Progressive search stages
    let candidates = match plan.strategy {
        Strategy::Progressive => {
            // Stage 1: Bloom filter
            let filtered = bloom_filter_check(&request.vector)?;
            
            // Stage 2: Binary quantization
            let binary_matches = binary_search(&filtered, &request.vector)?;
            
            // Stage 3: INT8 refinement
            let int8_matches = int8_refine(&binary_matches, &request.vector)?;
            
            // Stage 4: Full precision
            full_precision_search(&int8_matches, &request.vector)?
        }
        Strategy::Direct => {
            direct_search(&request.vector)?
        }
    };
    
    // 3. Re-rank and return
    let results = rerank(candidates, request.k);
    Ok(SearchResponse::from(results))
}

// Retry logic
async fn with_retry<T, F>(
    operation: F,
    max_retries: u32,
) -> Result<T>
where
    F: Fn() -> Future<Output = Result<T>>,
{
    let mut retries = 0;
    loop {
        match operation().await {
            Ok(result) => return Ok(result),
            Err(e) if retries < max_retries => {
                retries += 1;
                sleep(exponential_backoff(retries)).await;
            }
            Err(e) => return Err(e),
        }
    }
}
