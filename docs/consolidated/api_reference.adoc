= SQL API
:toc:
:icons: font

== Overview

SQL endpoints provide a SQL-first interface over REST, plus EXPLAIN for orchestration plans and vector/graph hints.

Base URL: `http://localhost:5678`

== Execute

- REST: `POST /api/v1/sql/execute`

Seeding strategy controls for hybrid graph→vector:

- SQL hint (inline): `-- SEEDING: AVERAGE | PER_SEED | NONE` (or `SEED USING AVERAGE`)
- REST body field: `"seeding": "average" | "per_seed" | "none"`

Request
----
{
  "query": "-- SEEDING: PER_SEED\nSELECT id FROM my_collection ORDER BY COSINE_DISTANCE(vector, $1) LIMIT 5",
  "parameters": [[0.1,0.2,0.3, ...]],
  "collection": "my_collection",
  "seeding": "per_seed"
}
----

Response (truncated)
----
{
  "success": true,
  "data": {
    "rows": [ { "id": "vec_1", "score": 0.92, ... }, ... ],
    "row_count": 5
  },
  "error": null
}
----

== EXPLAIN

- REST: `POST /api/v1/sql/explain`

Request
----
{
  "query": "SELECT * FROM my_collection ORDER BY COSINE_DISTANCE(vector, $1) LIMIT 10",
  "analyze": false
}
----

Response (fields abridged)
----
{
  "success": true,
  "data": {
    "plan": {
      "orchestration_steps": ["Parse", "Orchestrate", ...],
      "vector_hints": { "pruned_files": 12, "ef_search": 64, ... },
      "graph_hints": { "traversal_algorithm": "BFS", ... }
    },
    "request_id": "..."
  }
}
----

== gRPC (planned)

- gRPC: `proximadb.v1.SqlService/ExecuteSql(ExecuteSqlRequest) returns (ExecuteSqlResponse)`

== Graph Constructs in SQL

SQL can express graph operations using functions/clauses that the SqlService lowers to GraphService calls internally. Examples:

- FOLLOW/TRAVERSE semantics (illustrative):
----
SELECT id
FROM FOLLOW(start => 'user_123', rel => 'FOLLOWS', depth => 2)
WHERE label = 'User';
----

- Hybrid vector + graph (illustrative):
----
SELECT n.id
FROM SIMILAR(table => 'docs', vec => $1, top_k => 10) AS s
JOIN FOLLOW(start => s.id, rel => 'CITES', depth => 1) AS n
WHERE n.label = 'Paper'
LIMIT 20;
----

Note: The above are examples of SQL surface syntax; actual lowering uses the existing planner to call GraphService and VectorService as needed.

[source,json]

----

== gRPC

Service: `proximadb.v1.VectorService`

RPCs:
- `VectorBatch(VectorBatchRequest) returns (VectorOperationResponse)`
- `VectorSearch(VectorSearchRequest) returns (VectorOperationResponse)`
- `VectorGet(VectorGetRequest) returns (VectorOperationResponse)`

Python stub example:
[source,python]
----
import grpc
from proximadb.v1 import vector_pb2_grpc, vector_types_pb2

channel = grpc.insecure_channel('localhost:5679')
stub = vector_pb2_grpc.VectorServiceStub(channel)
req = vector_types_pb2.VectorSearchRequest(
    collection_id='docs',
    queries=[vector_types_pb2.SearchQuery(vector=[0.1,0.2,0.3])],
    top_k=5
)
resp = stub.VectorSearch(req)
for r in resp.results.results:
    print(r.id, r.score)
----

Enums:
- DistanceMetric: COSINE, EUCLIDEAN, DOT_PRODUCT, HAMMING, MANHATTAN, JACCARD, ANGULAR, CHEBYSHEV, CANBERRA, MINKOWSKI, BRAY_CURTIS, HELLINGER, CUSTOM
- StorageEngine: VIPER, SST, NOVA, HELIX, SWIFT

Notes:
- String aliases in SQL and REST may include: "l2" → EUCLIDEAN, "l1" → MANHATTAN, "dot"/"inner_product" → DOT_PRODUCT.
- Default metric is COSINE if unspecified.

= Graph API Reference
:toc:
:icons: font
:source-highlighter: rouge

== Traversal

- REST: POST `/v1/graph/traverse`
- Request body (JSON, TraversalRequest):
  - `start_node_id` (string)
  - `max_depth` (uint)
  - `edge_types` (string[])
  - `node_labels` (string[])
  - `filters` (PropertyFilter[])
  - `algorithm` ("BFS" | "DFS" | "PARALLEL_BFS")
  - `limit` (uint)
  - `timeout_ms` (uint, optional) — server honors if set; default ~500ms
  - `max_frontier` (uint, optional) — cap on frontier size; default ~50k

== Shortest Path

- REST: POST `/v1/graph/shortest_path`
  - Body: `{ start_node_id, target_node_id, max_depth?, edge_types?, algorithm?: "DIJKSTRA"|"ASTAR", k?: number, enable_prefetch?: bool, prefetch_budget?: int }`
  - Response: `{ success, path: string[]?, total_weight?: number }`
- gRPC: `ShortestPath(ShortestPathRequest) returns (ShortestPathResponse)`
  - ShortestPathRequest includes `algorithm` (enum) and `k` (for k-shortest if > 1)
  - Per-call prefetch overrides via gRPC metadata headers:
    - `x-graph-prefetch-enabled: true|false|1|0`
    - `x-graph-prefetch-budget: <int>`

=== Prefetch Controls (REST)
- JSON fields (optional): `enable_prefetch`, `prefetch_budget`
- Alternative headers:
  - `x-graph-prefetch-enabled: true|false|1|0`
  - `x-graph-prefetch-budget: <int>`

== Streaming Traversal (gRPC)

- gRPC: `StreamTraverse(TraversalRequest) returns (stream TraversalChunk)`
  - Streams chunks of nodes; final chunk includes edges, paths, stats, and `done=true`.
  - Use when traversals may return many nodes; respects `timeout_ms` and `max_frontier`.

== Unique Constraints DDL

- REST:
  - POST `/v1/graph/constraints/unique` `{ label, property }` — add constraint
  - DELETE `/v1/graph/constraints/unique` `{ label, property }` — remove constraint
- gRPC:
  - `AddUniqueConstraint(UniqueConstraintRequest)`
  - `RemoveUniqueConstraint(UniqueConstraintRequest)`

== Notes

- Property indexes: equality, numeric ranges (>, >=, <, <=) and prefix (starts_with) are accelerated; others validated via scan.
- Delete modes: default RESTRICT; use `delete_node_detach` server method for detaching edges before delete.

== Pagination & Continuation Tokens

- Node/Edge queries support offset/limit pagination across REST and gRPC.
- Additionally, pass a `continuation_token` as a string of the form `"offset:<n>"` to resume.
- Responses include `next_token` when a full page is returned; pass it as `continuation_token` in the next request.

== Error Codes (REST)

- GRAPH_NODE_CREATE_ERROR — node creation failed (validation, RI, constraints)
- GRAPH_NODE_NOT_FOUND — node not found
- GRAPH_NODE_GET_ERROR — node retrieval failed
- GRAPH_EDGE_* — similar for edges
- GRAPH_SHORTEST_PATH_ERROR — error computing shortest path
- GRAPH_ADD_UNIQUE_ERROR — failed to add unique constraint

All REST errors return `{ error, message, code }` with 4xx/5xx status.
== Graph Analysis

- REST:
  - GET `/v1/graph/components` → `{ success, components: string[][] }`
  - GET `/v1/graph/cycles` → `{ success, has_cycle: boolean }`
 - gRPC: `GetConnectedComponents(GetStatsRequest)`, `HasCycle(GetStatsRequest)`

== TTL / Expiry

- Entities (nodes/edges) with a property `"__expires_at"` (unix millis) are periodically removed by a background sweeper.
- The sweeper runs every `ttl_sweep_interval_seconds` (default 900 = 15 minutes), configured under `[api]` in the server config.
- Edges are removed before nodes (detach semantics) to maintain referential integrity.

== Overview

ProximaDB exposes comprehensive **Unified Intelligence APIs** via gRPC (port 5679) and REST (port 5678) for vector search, graph operations, and semantic knowledge store (SKS) capabilities. The platform features **automated API orchestration** that intelligently routes requests to appropriate engines.

**Three API Categories:**
- **Vector APIs**: Multimodal semantic search (text, image, video, audio)
- **Graph APIs**: Relationship modeling, traversal, and analysis  
- **SKS APIs**: Hybrid vector+graph intelligence with context assembly

**API Benefits:**
- **Serverless-Ready**: Zero infrastructure management required
- **Auto-Orchestration**: Intelligent routing eliminates manual integration
- **Performance Optimized**: gRPC for throughput, REST for compatibility
- **Type-Safe**: Protocol buffer definitions ensure consistency

=== Progressive Search (REST)

.GET query variant (for small vectors)
[source,http]
----
GET /api/v1/progressive/search/{collection_id}?k=10&include_metadata=true&include_vectors=false
----

.POST JSON variant (preferred)
[source,json]
----
POST /api/v1/progressive/search/{collection_id}
{
  "vector": [0.12, 0.03, ...],
  "k": 10,
  "scenario": "high_recall",
  "include_vectors": false,
  "include_metadata": true
}
----

.Explain stages
[source,http]
----
GET /api/v1/progressive/explain/{collection_id}?k=10&scenario=balanced
----

Response returns SearchVectorRecord fields (proto) for results and stage plan for explain. Use the POST variant for larger inputs.
