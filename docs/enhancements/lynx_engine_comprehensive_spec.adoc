## 1. Introduction

### 1.1. Overview

This document specifies the design of "Lynx," a new Log-Structured Merge-Tree (LSM) based storage engine for ProximaDB. The primary goal of the Lynx engine is to accelerate nearest neighbor (ANN) and hybrid queries by physically co-locating similar vectors on disk. This is achieved by clustering vectors based on their position along a space-filling curve and storing them in specialized columnar blocks that can be efficiently pruned during query execution.

### 1.2. Rationale

As vector datasets grow, scanning the entire dataset for a query becomes prohibitively expensive. The Lynx engine addresses this by organizing data on disk in a way that reflects its structure in the high-dimensional vector space. This allows the query planner to skip large portions of the data that are irrelevant to the query, drastically reducing I/O and speeding up response times. This approach is particularly effective for queries that combine vector similarity search with metadata filters.

### 1.3. Key Concepts

*   **LSM Tree:** A data structure that excels at handling high write throughput. It buffers writes in an in-memory **Memtable** and periodically flushes them to immutable on-disk files called **SSTables**. These files are merged in the background through a process called **Compaction**.
*   **SSTable:** A Sorted String Table. An immutable, on-disk file containing data sorted by a key. In Lynx, the primary sort key is the Hilbert Key.
*   **PCA (Principal Component Analysis):** A dimensionality-reduction technique used to project high-dimensional vectors into a lower-dimensional space while preserving as much of the data's variance as possible.
*   **Hilbert Curve:** A continuous space-filling curve that maps a multi-dimensional space onto a 1D line. This mapping largely preserves locality, meaning points that are close in the multi-dimensional space are likely to be close on the 1D line.
*   **Hilbert Key:** The `u64` value representing a vector's position on the 1D Hilbert curve after it has been projected into a lower-dimensional space by PCA.
*   **Tombstone:** A special marker indicating that a record has been deleted. It is used for "soft deletes," with the actual data being purged during compaction.
*   **AXIS:** The central indexing service in ProximaDB. It consumes events from storage engines to build and maintain in-memory indexes (e.g., HNSW, IVF) for fast searching.

## 3. High-Level Architecture

### 3.1. Core Architectural Principles

1.  **Pluggable Storage Backend:** All file I/O within the Lynx engine **must** be performed through the `Filesystem` API. This ensures that Lynx works seamlessly with different storage backends, such as local disk, S3, GCS, and other cloud stores, without any code changes.
2.  **Decoupling from Indexing:** Lynx is a physical storage engine responsible for the layout and retrieval of data. It is decoupled from the logical indexing service, **AXIS**. Lynx produces clustered data files (SSTables) and notifies AXIS of these new files. AXIS is then responsible for consuming this information to update its own in-memory indexes.

### 3.2. LSM-Tree Structure

Lynx adopts a leveled LSM compaction strategy. This structure is fundamental to managing the data lifecycle and enabling efficient, incremental re-clustering.

## 4. Clustering and Data Layout

### 4.1. Clustering Pipeline: PCA + Hilbert Curve

To map the high-dimensional vector space to a one-dimensional line for sorting, the Lynx engine uses a PCA-powered Hilbert curve.

[source, mermaid]
----
graph LR
    A[High-Dim Vector<br/>e.g., 1536D] -- PCA Projection --> B(Low-Dim Vector<br/>e.g., 16D)
    B -- Hilbert Curve<br/>Encoding --> C(u64 Hilbert Key)
    
    style A fill:#ffcccc,stroke:#333,stroke-width:2px
    style B fill:#ffffcc,stroke:#333,stroke-width:2px
    style C fill:#ccffcc,stroke:#333,stroke-width:2px
----

1.  **Dimensionality Reduction**: High-dimensional vectors are projected into a lower-dimensional space using a versioned PCA model.
2.  **Key Generation**: The lower-dimensional projection is used to compute a single `u64` Hilbert curve key.
3.  **Sorting**: Before being written to an SSTable, all records are sorted based on this Hilbert key.

## 5. Core Operations & Workflows

### 5.1. Record Lifecycle

The state of a record (vector) changes as it moves through the Lynx engine.

[source, mermaid]
----

    B -- Flush --> C(In L0 SSTable)
    C -- Compaction --> D(In L1..Lk-1 SSTable)
    D -- Compaction --> E(In Lmax SSTable)
    E -- Re-clustering<br/>Compaction --> F(In Lmax SSTable<br/>with new PCA key)
    
    A2[Delete Operation] --> G{Tombstone<br/>in Memtable}

    H -- Compaction<br/>with Record --> I[Record &<br/>Tombstone Purged]

### 5.2. Ingestion, Flush, and AXIS Integration

1.  A write operation is recorded in the WAL and inserted into the memtable.
2.  When the memtable is full, a flush is triggered.
3.  The active PCA model is used to calculate a Hilbert key for each vector.
4.  Records are sorted by Hilbert key and written to a new SSTable file using the `Filesystem` API.
5.  **AXIS Notification**: Upon successful creation of the new SSTable, an event is published to an internal event log. This event notifies the **AXIS indexing service** that a new file is available. AXIS will then asynchronously process this file to update its in-memory indexes.

### 5.3. Compaction and AXIS Integration

The compaction process merges SSTables and progressively re-clusters data.

1.  One or more SSTables are selected for compaction.
2.  The records are read, re-keyed using the latest active PCA model, and sorted.
3.  New, larger SSTables are written to disk via the `Filesystem` API.
4.  The old input SSTables are marked for deletion.
5.  **AXIS Notification**: Similar to a flush, an event is published upon the successful creation of the new compacted SSTables and the deletion of the old ones. AXIS consumes these events to atomically update its index to reference the new files and remove references to the old ones.

                                                 ▼
┌────────────────────────────────────────────────────────┐

└────────────────────────────────────────────────────────┘
       ▲              ▲              ✗ (pruned)
       │              │

Pruning Strategy:
1. Convert query vector to Hilbert key
2. Select SSTables with overlapping key ranges
3. Within selected SSTables, use block-level metadata for finer pruning
4. Load only relevant blocks into memory
