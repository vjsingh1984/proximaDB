= Design Specification: The Lynx Storage Engine

:toc: left
:toclevels: 3
:source-highlighter: rouge
:icons: font

## 1. Overview

This document specifies the design of "Lynx," a new LSM-based storage engine for ProximaDB. The primary goal of the Lynx engine is to accelerate nearest neighbor and hybrid queries by physically co-locating similar vectors on disk.

This is achieved by clustering vectors based on their position along a space-filling curve (a Hilbert curve) and storing them in specialized columnar blocks (`FastLaneBlock`) that can be efficiently pruned during query execution.

This engine will be implemented as a new `StorageEngineStrategy` within ProximaDB's pluggable storage architecture.

## 2. Rationale

As vector datasets grow, scanning the entire dataset for a query becomes prohibitively expensive. The Lynx engine addresses this by organizing data on disk in a way that reflects its structure in the high-dimensional vector space. This allows the query planner to skip large portions of the data that are irrelevant to the query, drastically reducing I/O and speeding up response times.

This approach is particularly effective for queries that combine vector similarity search with metadata filters.

## 3. File Layout and Core Components

The on-disk representation is critical to the Lynx engine's performance. An SSTable file is composed of a header, multiple `FastLaneBlock`s, and a footer containing all metadata required for pruning.

### 3.2. Clustering Strategy: Hilbert Curve

To map the high-dimensional vector space to a one-dimensional line for sorting, the Lynx engine will use a **Hilbert curve**.

*   **Dimensionality Reduction**: To apply the Hilbert curve, high-dimensional vectors are first projected into a lower-dimensional space (e.g., 8-16 dimensions) using **Principal Component Analysis (PCA)**. The PCA matrix will be trained on a sample of the data when the collection is created.
*   **Key Generation**: The lower-dimensional projection of each vector is then used to compute a single `u64` Hilbert curve key.
*   **Sorting**: Before being written to disk, all records (vectors and their metadata) are sorted based on this Hilbert key.

### 3.3. On-Disk Format: `FastLaneBlock`

The Lynx engine will use the existing `FastLaneBlock` as its fundamental unit of storage. While `FastLaneBlock` may support up to 64 dimensions for certain operations, Lynx will use it as a generic columnar container. The clustering is handled externally by sorting records before they are written into blocks.

The metadata for each `FastLaneBlock` will be extended to include:

*   **Hilbert Key Range**: The minimum and maximum Hilbert key (`(u64, u64)`) of the vectors contained within the block. This is the primary mechanism for data pruning.
*   **Bloom Filter**: A bloom filter on the vector IDs within the block.
*   **Zone Maps**: Min/max values for all other metadata columns in the block.

## 4. PCA Model Management and Drift

The relevance of the PCA model is critical to clustering performance. As new data is written, the data distribution may "drift," making the original PCA model less effective. Lynx will manage this through a process of monitoring, retraining, and re-clustering.

### 4.1. Model Storage

*   **Location**: PCA models will be stored in a dedicated directory for each collection, using the existing `Filesystem` API to ensure compatibility with `file://`, S3, GCS, and ADLS. The proposed location is: `{base_url}/{collection_id}/models/`.
*   **Versioning**: Each model will be versioned (e.g., using a timestamp or UUID) and stored as a separate file (e.g., `pca-1689882605.bin`). The collection's root metadata will be atomically updated to point to the currently active model version.

### 4.2. Drift Detection and Retraining

*   **Trigger**: Retraining can be triggered automatically or manually.
    *   **Automatic**: A background process monitors the collection. After a configurable number of new vectors have been added (e.g., 1 million), it triggers a retraining job.
    *   **Manual**: An administrative command can force retraining at any time.
*   **Process**: The retraining process runs in the background:
    1.  It takes a random sample of recent data from the collection.
    2.  It trains a new PCA model on this sample.
    3.  The new model is validated to ensure it captures a sufficient percentage of the variance.
    4.  The validated model is saved to the `models/` directory with a new version ID.
    5.  The collection metadata is updated to reference the new model. From this point on, all new flushes will use the new PCA model to calculate Hilbert keys.

### 4.3. Re-clustering Data

Data written with an old PCA model is not optimally clustered. To fix this, a special **re-clustering compaction** must be run.

*   This compaction job will read SSTables that were written with an old PCA model version.
*   For each record, it will recalculate the Hilbert key using the **new, active PCA model**.
*   It will then re-sort and rewrite the data into new SSTables, effectively migrating the data to the new clustering scheme.
*   This is an I/O-intensive operation that should be run during periods of low traffic.

## 5. Detailed Workflows

### 5.1. Ingestion and Flush

1.  **Memtable**: New writes are buffered in an in-memory memtable.
2.  **Flush Trigger**: When the memtable is full, a flush is triggered.
3.  **Clustering**:
    *   The engine retrieves the **active PCA model version** for the collection.
    *   For each vector, its lower-dimensional projection is calculated, and a Hilbert key is generated.
4.  **Sorting**: The records are sorted by their Hilbert key.
5.  **Block Creation**: The sorted records are partitioned into `FastLaneBlock`s.
6.  **SSTable Write**: The blocks are written to a new SSTable file, and the file footer is populated with metadata, including the **PCA model version ID** used for this file.

### 5.2. Compaction

*   **Standard Compaction**: Merges SSTables that were created with the **same PCA model version**. This improves locality within the existing clustering scheme.
*   **Re-clustering Compaction**: As described in section 4.3, this special compaction migrates data from an old clustering scheme to the new one.

### 5.3. Query Execution

The query path remains the same, but the query planner must now be aware of PCA model versions. If a query spans data created with multiple PCA models, it may need to adjust its pruning strategy, though the primary benefits will come from querying data that is consistently clustered.

## 6. `UnifiedStorageEngine` Implementation

The `LynxEngine` will be a new implementation of the `UnifiedStorageEngine` trait.

*   **`engine_name()`**: Returns `"LynxEngine"`.
*   **`strategy()`**: Returns `StorageEngineStrategy::Lynx`.
*   **`do_flush()`**: Implements the flush workflow (5.1).
*   **`do_compact()`**: Implements both standard and re-clustering compaction (5.2).
*   **`search_vectors_unified()`**: Implements the query workflow.
*   **`scan_capabilities()`**: Will report `supports_row_group_pruning = true` and `supports_zone_maps = true`.

## 7. Future Work

*   **Incremental Clustering**: To reduce write amplification during re-clustering, a "liquid clustering" approach could be investigated.
*   **Adaptive Dimensionality**: The PCA training process could adaptively choose the optimal number of dimensions to project to based on the data distribution.
