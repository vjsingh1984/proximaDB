## 1. Introduction

### 1.1. Overview

This document specifies the design of "HELIX," a new Log-Structured Merge-Tree (LSM) based storage engine for ProximaDB. The primary goal of the HELIX engine is to accelerate nearest neighbor (ANN) and hybrid queries by physically co-locating similar vectors on disk. This is achieved by clustering vectors based on their position along a space-filling curve and storing them in specialized columnar blocks that can be efficiently pruned during query execution.

### 1.2. Rationale

As vector datasets grow, scanning the entire dataset for a query becomes prohibitively expensive. The HELIX engine addresses this by organizing data on disk in a way that reflects its structure in the high-dimensional vector space. This allows the query planner to skip large portions of the data that are irrelevant to the query, drastically reducing I/O and speeding up response times. This approach is particularly effective for queries that combine vector similarity search with metadata filters.

### 1.3. Key Differentiators from Traditional LSM

The HELIX engine differs fundamentally from traditional LSM implementations:

[cols="2,3,3", options="header"]
|===
| Aspect | Traditional LSM | HELIX Disk-Only LSM

| Memory Management
| Each engine has own memtable & WAL
| Uses global partitioned memtable & WAL

| Write Path
| Writes → Engine Memtable → Engine WAL
| Writes → Global Memtable → Global WAL → Batch Flush to HELIX

| Flush Trigger
| When engine memtable is full
| When global memtable partition flushes

| Level 0 Files
| Sorted by primary key
| Unsorted FastLane blocks (clustering happens in compaction)

| Compaction Focus
| Merge overlapping key ranges
| Cluster similar vectors using PCA + Hilbert keys

| Query Optimization
| Key-based pruning
| Similarity-based pruning with Hilbert ranges
|===

### 1.4. Key Concepts

*   **LSM Tree:** A data structure that excels at handling high write throughput. It buffers writes in an in-memory **Memtable** and periodically flushes them to immutable on-disk files called **SSTables**. These files are merged in the background through a process called **Compaction**.
*   **SSTable:** A Sorted String Table. An immutable, on-disk file containing data sorted by a key. In HELIX, the primary sort key is the Hilbert Key.
*   **PCA (Principal Component Analysis):** A dimensionality-reduction technique used to project high-dimensional vectors into a lower-dimensional space while preserving as much of the data's variance as possible.
*   **Hilbert Curve:** A continuous space-filling curve that maps a multi-dimensional space onto a 1D line. This mapping largely preserves locality, meaning points that are close in the multi-dimensional space are likely to be close on the 1D line.
*   **Hilbert Key:** The `u64` value representing a vector's position on the 1D Hilbert curve after it has been projected into a lower-dimensional space by PCA.
*   **Tombstone:** A special marker indicating that a record has been deleted. It is used for "soft deletes," with the actual data being purged during compaction.
*   **AXIS:** The central indexing service in ProximaDB. It consumes events from storage engines to build and maintain in-memory indexes (e.g., HNSW, IVF) for fast searching.

## 3. High-Level Architecture

### 3.1. Core Architectural Principles

1.  **Disk-Only LSM Structure:** Unlike traditional LSM engines, HELIX **does not maintain its own memtable or WAL**. The global partitioned memtable and WAL provide write throughput guarantees across all storage engines. HELIX only manages the on-disk LSM structure with leveled compaction for efficient data organization.
2.  **Pluggable Storage Backend:** All file I/O within the HELIX engine **must** be performed through the `Filesystem` API. This ensures that HELIX works seamlessly with different storage backends, such as local disk, S3, GCS, and other cloud stores, without any code changes.
3.  **Decoupling from Indexing:** HELIX is a physical storage engine responsible for the layout and retrieval of data. It is decoupled from the logical indexing service, **AXIS**. HELIX produces clustered data files (SSTables) and notifies AXIS of these new files. AXIS is then responsible for consuming this information to update its own in-memory indexes.

### 3.2. Disk-Only LSM-Tree Structure

HELIX receives pre-batched, sorted data from the global memtable flush process. It organizes this data into a leveled LSM structure on disk with columnar FastLane blocks for efficient clustering and query performance.

### 3.4. Sorted Flush Optimization

**Key Innovation:** HELIX sorts vectors by Hilbert key during L0 flush, enabling immediate query pruning even before compaction.

#### Why Sorted L0 Flush?

Traditional LSM engines write unsorted data to L0 and rely on compaction to organize it. HELIX takes a different approach:

1. **Immediate Pruning Benefits**: Small collections that haven't experienced compaction can still benefit from Hilbert-based range pruning
2. **Reduced Compaction Work**: L0 files arrive pre-sorted, making compaction primarily a merge operation rather than sort+merge
3. **Consistent Query Performance**: Query optimization works uniformly across all levels, including fresh L0 files
4. **Better Cache Locality**: Sequential reads during queries due to pre-sorted layout

1.  **Dimensionality Reduction**: High-dimensional vectors are projected into a lower-dimensional space using a versioned PCA model.
2.  **Key Generation**: The lower-dimensional projection is used to compute a single `u64` Hilbert curve key.
3.  **Sorting**: Before being written to an SSTable, all records are sorted based on this Hilbert key.

### 5.2. Flush Integration and AXIS Notification

Since HELIX doesn't maintain its own memtable, the flush process is different from traditional LSM engines:

1.  **Batch Reception**: HELIX receives pre-batched vectors from the global memtable flush process. These batches are already organized and ready for columnar encoding.
2.  **FastLane Block Creation**: The batch is transformed into columnar FastLane blocks with:
    - Columnar vector storage for SIMD operations
    - Metadata columns for IDs and timestamps
    - Bloom filters for efficient lookups
3.  **PCA Projection & Hilbert Key Generation**: Each vector in the batch is:
    - Projected to lower dimensions using the active PCA model
    - Assigned a Hilbert key for clustering
4.  **SSTable Creation**: A new Level-0 SSTable is created with FastLane blocks, initially unsorted by Hilbert key (sorting happens during compaction).
5.  **AXIS Notification**: Upon successful SSTable creation, an event is published to notify AXIS that a new file is available for indexing.

### 5.3. Leveled Compaction with Liquid Clustering

The compaction process is where HELIX's clustering magic happens. Unlike during flush (which just creates FastLane blocks), compaction performs the actual clustering:

#### Level 0 → Level 1 Compaction (Initial Clustering)
1.  **Select L0 SSTables**: Choose unsorted flush files for compaction
2.  **Apply PCA + Hilbert**: For each vector:
    - Project to low dimensions using PCA model
    - Calculate Hilbert key
    - Sort all records by Hilbert key
3.  **Create Clustered SSTables**: Write sorted, clustered data to L1

#### Level i → Level i+1 Compaction (Progressive Refinement)
1.  **Merge Sorted Runs**: Combine multiple sorted SSTables
2.  **Liquid Clustering**: Adaptively reorganize based on:
    - Query patterns (frequently accessed ranges)
    - Data distribution changes
    - PCA model updates
3.  **Optimize Block Boundaries**: Ensure FastLane blocks contain similar vectors
4.  **AXIS Notification**: Publish events for index updates

#### Re-clustering at Lmax
- Periodic re-clustering with updated PCA models
- Maintains optimal clustering as data distribution evolves
- Balances clustering quality vs. compaction cost

### 5.5. Handling Deletes and Updates

Deletes and updates are handled through tombstoning:

1. **Soft Deletes**: Use `expires_at` field in VectorRecord to mark as deleted
2. **Tombstone Propagation**: Tombstones flow through flush and compaction
3. **Physical Removal**: Records are hard deleted during compaction when:
   - Tombstone and record meet in same compaction job
   - Expired records (`expires_at` < current_time) are encountered
4. **Update Handling**: Updates create new version with same ID, old version tombstoned

### 5.6. Simple Recovery Design

HELIX uses a simplified recovery approach since it's a disk-only engine:

1. **No Complex State**: No memtable or WAL to recover (uses global infrastructure)
2. **Atomic Operations**: All file operations are atomic (write + rename)
3. **Simple Initialization**:
   - Scan directory for all .helix files on restart
   - Parse level from filenames (e.g., `L0_timestamp_uuid.helix`)
   - Load PCA model if exists
   - No complex recovery needed - files either exist or don't
4. **Natural Durability**: 
   - Global WAL ensures write durability
   - File system provides operation atomicity
   - No partial states possible with atomic file operations

### 5.7. File Management (SST-Style Approach)

HELIX uses the same file management strategy as the SST engine for simplicity and reliability:

#### File Naming Convention
Files encode level information directly in their names using the unified `FilenameCodec`:
- **Format**: `L{level}_{timestamp}_{uuid}.helix`
- **Example**: `L0_20250814T143052_a7f3c2d1.helix` (Level 0 file)
- **Example**: `L3_20250814T143053_b8e4d3e2.helix` (Level 3 file)

#### Manifest-Free Design
Unlike traditional LSM engines with complex manifest files, HELIX:
1. **File Discovery**: List directory to find all `.helix` files
2. **Level Detection**: Parse level from filename (e.g., `L3_` → Level 3)
3. **File Validity**: File existence indicates validity (no separate manifest)
4. **Atomic Operations**: Rename for atomic file visibility
5. **Compaction Cleanup**: Delete old files after successful compaction

#### Benefits of This Approach
- **Simplicity**: No manifest synchronization complexity
- **Reliability**: File system provides atomicity guarantees
- **Recovery**: Simple directory scan rebuilds state
- **Cloud-Native**: Works seamlessly with object stores (S3, GCS)
- **Debugging**: Human-readable file organization

#### File Extensions and Magic Bytes
- **Extension**: `.helix` (defined in `constants.rs`)
- **Magic Bytes**: `HELX` (0x48454C58)
- **Header**: Contains version, compression, and clustering metadata

### 5.8. Hybrid Search Strategy with Adaptive Quantization

HELIX leverages the unified quantization module for flexible search strategies:

#### Storage Quantization Scenarios

1. **No Storage Quantization + No On-Demand**:
   - Use Hilbert range pruning on collocated row groups
   - Leverage block statistics for filtering
   - Direct FP32 vector comparisons

2. **No Storage Quantization + On-Demand Required**:
   - Apply on-demand quantization first (based on hints)
   - Use quantized vectors for initial filtering
   - Refine with FP32 vectors in final stage

3. **Storage Quantization Enabled**:
   - Use pre-quantized vectors from storage for filtering
   - Progressive refinement: Binary → INT8 → PQ → FP32
   - Leverage `quantized_vector` field in VectorRecord

#### Quantization Integration Points

- **Insert Time**: Via `QuantizationRepresentation` in VectorRecord
- **Search Time**: Via `SearchQuantization` for on-demand quantization
- **Collection Config**: Controls default quantization behavior
- **Hints**: Runtime overrides for quantization strategy
