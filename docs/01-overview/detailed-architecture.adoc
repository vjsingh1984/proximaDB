== Design Principles

=== 1. Proto-First Architecture
ProximaDB eliminates serialization overhead by using protocol buffers natively throughout the system:

[source]
----
Traditional:  API → Convert → Internal Types → Convert → Storage
ProximaDB:    API → Proto Types → Storage (Zero Conversion)
----

**Benefits:**
* Zero serialization overhead
* Direct field access without enum dispatch
* Single source of truth for data structures
* 40-60% latency reduction

=== 2. Single-Server Simplicity
Enterprise capabilities without distributed complexity:

* **One Container**: Complete system in a single deployment
* **No Coordination**: No consensus protocols or leader election
* **Fixed Resources**: Predictable costs and performance
* **5-Minute Setup**: From download to production

=== 3. Hardware-Adaptive Performance
Automatic detection and optimization for available hardware:

* **CPU SIMD**: AVX-512, AVX2, SSE, NEON
* **GPU Acceleration**: CUDA, ROCm, MPS, OpenCL
* **Memory Alignment**: Page-aligned buffers for direct I/O
* **Thread-Local Pools**: Zero-contention resource access

== Core Components

=== API Layer
* **REST API** (Port 5678): JSON-based, HTTP/2 support
* **gRPC API** (Port 5679): Protobuf, 2.1x faster than REST
* **Unified Handlers**: Shared logic, zero-copy marshaling

=== Service Layer
* **VectorOperationsService**: Direct memtable access for 40-60% latency reduction
* **CollectionService**: Schema and lifecycle management
* **SearchService**: Query planning and orchestration
* **EventService**: Async event processing via EventLog

=== Storage Layer

==== Multi-Engine Architecture
Different engines optimized for specific workloads:

[cols="1,2,2", options="header"]
|===
| Engine | Architecture | Optimal Use Case

| **SST**
| Row-based LSM tree
| Real-time updates, OLTP workloads

| **VIPER**
| Columnar Parquet
| Analytics, batch operations, cloud

| **HELIX**
| PCA+Hilbert clustering
| Similarity search with locality preservation
|===

==== Write Path
1. Client request → API handler
2. Write to WAL (durability)
3. Buffer in MemTable
4. Trigger flush (size/time based)
5. Write to storage engine
6. Emit to EventLog for indexing

==== Read Path
1. Search request → SearchService
2. Check cache layers
3. Progressive search pipeline
4. Storage engine retrieval
5. Result aggregation
6. Response marshaling

=== Index Layer (AXIS)

The AXIS engine manages all indexing operations:

* **Asynchronous Updates**: Via EventLog queue
* **Multiple Algorithms**: HNSW, IVF, LSH, PQ, FLAT, ANNOY
* **Quantized Indexes**: Memory-efficient representations
* **Incremental Building**: No full rebuilds required

== Operations

=== Monitoring
ProximaDB exposes a Prometheus endpoint for monitoring key metrics. The endpoint is available at `http://<host>:5678/metrics`.

=== Backup and Restore
ProximaDB supports online backup and restore to and from a variety of storage backends, including local filesystem, S3, GCS, and Azure Blob Storage.

== Security

ProximaDB provides a comprehensive security model that includes authentication, authorization, and encryption.

=== Authentication
ProximaDB supports multiple authentication mechanisms, including:

* **mTLS:** Mutual TLS for secure client-server communication.
* **JWT:** JSON Web Tokens for stateless authentication.

=== Authorization
ProximaDB uses a Role-Based Access Control (RBAC) model to control access to resources. Users can be assigned to roles, and roles can be granted permissions to perform specific actions on specific resources.

=== Encryption
ProximaDB supports encryption at rest and in transit.

* **Encryption at Rest:** Data is encrypted at rest using AES-256.
* **Encryption in Transit:** Data is encrypted in transit using TLS 1.3.

== Performance Optimizations

=== Memory Management
* **Vector Pools**: Pre-allocated, SIMD-aligned buffers
* **Thread-Local Storage**: Zero-contention access patterns
* **Page-Aligned I/O**: Direct kernel bypass
* **Reference Counting**: Automatic resource management

=== Caching Strategy
* **Result Cache**: Complete query results
* **Metadata Cache**: 90% hit rate for cloud storage
* **Disk Cache**: Local caching of remote data
* **Prefetch Buffer**: Predictive read-ahead

=== Zero-Copy Design
* **Direct Proto Access**: No intermediate representations
* **Memory-Mapped Files**: OS-level optimization
* **Shared Buffers**: Cross-component data sharing
* **Lazy Deserialization**: On-demand field access

== Key Architectural Decisions

=== Why Proto-First?
* **Performance**: Eliminates double serialization
* **Consistency**: Single data model throughout
* **Compatibility**: Industry-standard format
* **Evolution**: Built-in schema versioning

=== Why Single-Server?
* **Simplicity**: No distributed complexity
* **Cost**: 90% reduction vs distributed systems
* **Reliability**: Fewer failure modes
* **Performance**: No network overhead

=== Why Multiple Engines?
* **Optimization**: Each engine for specific workload
* **Flexibility**: Choose best fit for use case
* **Evolution**: Add new engines without breaking changes
* **Performance**: Specialized data structures
