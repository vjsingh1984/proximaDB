== Search Implementation

**Why This Matters**: Understand how to achieve sub-millisecond search at scale.

=== Two-Stage Search for Speed

image::two-stage-search.svg[Two-Stage Search, width=900]
_Production pattern: Fast filtering followed by precise ranking_

**The Strategy**:
1. **Stage 1**: Quantized/index search gets 10-100x more candidates than needed
2. **Stage 2**: Full-precision reranking on candidates only

**Result**: 90% of computation saved while maintaining accuracy.

=== Implementation Architecture

==== Search Orchestration (Your Entry Point)
```rust
// VectorOperationsService coordinates everything
impl VectorOperationsService {
    pub async fn search(&self, request: SearchRequest) -> SearchResult {
        // Parallel execution across all sources
        let (wal_results, index_results, storage_results) = 
            tokio::join!(
                self.search_wal(&request),      // Unflushed data
                self.search_indexes(&request),  // AXIS indexes  
                self.search_storage(&request)   // Storage engines
            );
        
        // Smart deduplication and ranking
        self.merge_and_deduplicate(wal_results, index_results, storage_results)
    }
}
```

**Key Benefits**:
- **Stateless design**: No complex state management
- **Parallel execution**: All sources searched concurrently
- **Automatic routing**: Engine selection based on collection metadata

==== Engine-Specific Optimizations

**SST Engine** (Row-based, write-optimized):
```rust
// Three-stage filtering minimizes disk I/O
impl SstEngine {
    fn search(&self, query: &Query) -> Result<Vec<Match>> {
        self.bloom_filter_stage()     // Skip entire files
            .index_filter_stage()     // Skip data blocks
            .row_filter_stage()       // Skip individual records
    }
}
```

**VIPER Engine** (Columnar, analytics-optimized):
```rust
// Predicate pushdown to Parquet level
impl ViperEngine {
    fn search(&self, query: &Query) -> Result<Vec<Match>> {
        self.push_predicates_to_parquet()
            .prune_unnecessary_columns()
            .use_row_group_statistics()
    }
}
```

== Compression & Storage Optimization

=== Two-Tier Compression Strategy

image::unified_quantization_system.svg[Compression Pipeline, width=900]
_Production compression pipeline: Transport + Storage layers_

**ProximaDB uses separate compression tiers**:

1. **Transport Layer** (Protocol compression): Disabled by default for debugging
2. **Storage Layer** (Collection compression): SDK-driven, 50-80% reduction

| Method | Compression Ratio | Accuracy | Best For

| Production systems requiring high accuracy

| **Product Quantization (PQ8)**
| 16x compression  
| 95-99% accuracy
| Large-scale deployments with acceptable accuracy trade-off

=== API Architecture

image::unified-handlers-architecture.svg[API Handlers, width=900]
_Single codebase serves both REST and gRPC with identical performance_

**Implementation Pattern**:
```rust
// Unified handler serves both protocols
pub struct UnifiedVectorHandler {
    vector_service: Arc<VectorOperationsService>,
}

impl UnifiedVectorHandler {
    // REST endpoint
    pub async fn rest_search(&self, req: RestSearchRequest) -> RestResponse {
        let internal_req = self.convert_from_rest(req);
        let result = self.vector_service.search(internal_req).await;
        self.convert_to_rest(result)
    }
    
    // gRPC endpoint  
    pub async fn grpc_search(&self, req: GrpcSearchRequest) -> GrpcResponse {
        let internal_req = self.convert_from_grpc(req);
        let result = self.vector_service.search(internal_req).await;
        self.convert_to_grpc(result)
    }
}
```

== Distance Metrics Selection Guide

**Why This Matters**: Choose the right metric for your similarity requirements.

[cols="2,3,2,2", options="header"]
|===
| Metric | Best Use Case | Range | Performance

| **cosine**
| Semantic similarity, text embeddings, normalized data
| [0, 2] (0=identical)
| Fast, recommended default

| **euclidean**  
| Image embeddings, spatial data, absolute distances
| [0, ∞) (0=identical)
| Fast, hardware-accelerated

| **dot_product**
| Recommendation systems, raw scores
| (-∞, ∞) (higher=similar)
| Fastest available

| **manhattan**
| High-dimensional sparse data, robust to outliers
| [0, ∞) (0=identical)
| Good for sparse vectors

| **hamming**
| Binary data, feature hashes, bit vectors
| [0, n] (0=identical)
| Extremely fast on binary data

| **jaccard**
| Set similarity, categorical data overlap
| [0, 1] (1=identical)
| Good for sparse categorical features
|===

== Index Algorithm Selection

**Why This Matters**: Right index = 100x performance improvement for your workload.

[cols="2,3,2,1", options="header"]
|===
| Algorithm | When to Use | Memory Cost | Search Speed

| **HNSW**
| High accuracy required, medium scale (<10M vectors)
| High (M×N)
| Excellent (log N)

| **IVF**
| Large scale (>10M vectors), balanced accuracy/speed
| Medium (N)
| Good (configurable)

| **FLAT**  
| Perfect accuracy required, small scale (<100K vectors)
| Low (N)
| Exact (linear)

| **LSH**
| Approximate similarity, extremely large scale
| Medium (L×N)
| Very fast (constant)

| **ANNOY**
| Memory-constrained environments
| Medium (trees×N)
| Good (log N)

| **PQ**
| Compression-first, accuracy secondary
| Very low (N/8)
| Moderate (linear)
|===
