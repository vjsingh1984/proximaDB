== SST Engine Architecture

The SST (Sorted String Table) engine is optimized for write-heavy OLTP workloads with row-based storage.

=== SST File Format

image::sst1-format.svg[SST1 File Format, width=900]

Key features:
* **Magic bytes**: SST1 header for format identification
* **Row-based storage**: Optimal for point queries
* **Bloom filters**: 95% reduction in unnecessary reads
* **Compression blocks**: Configurable compression per block

==== Algorithm Complexity Analysis

[cols="3,2,2,3", options="header"]
|===
| Strategy | Insertion | Sorting | Total Complexity

| **BTreeMap (Old)**
| O(log n) per insert
| Pre-sorted
| **O(n log n)** - _High constant factor_

| **Vec + Sort (Small)**
| O(1) per insert
| O(n log n)
| **O(n log n)** - _Low constant factor_

| **K-Way Merge (Large)**
| O(1) per insert
| O(m log m) + O(n log k)
| **O(n log m + n log k)** - _where k << n_
|===

==== Performance Optimizations

**Memory Efficiency:**
* **Immediate Deallocation**: All transient structures are scoped
* **Cache Locality**: Smaller batch sorts improve CPU cache utilization
* **Zero-Copy**: Iterator-based streaming to disk

**Algorithmic Benefits:**
* **Better Complexity**: K-way merge is more efficient when k << n
* **Adaptive Selection**: Automatically chooses optimal strategy
* **Batch Awareness**: Leverages natural batch boundaries from memtable

**Production Characteristics:**
* **10K Record Threshold**: Empirically determined crossover point
* **Heap-Based Merge**: Min-heap for efficient k-way merge
* **Database Optimized**: Designed for multiple collections and frequent flushes

==== Multi-Batch Flush Pipeline

1. **Batch Extraction**: Extract individual vectors from multiple batch entries in global partitioned memtable
   - Each batch entry contains multiple vectors
   - Vectors arrive unsorted across batches (different write times)
   - Flatten all vectors into single stream for processing

2. **Strategy Selection**: Choose Vec+Sort or K-Way Merge based on total vector count and batch count
   - Small datasets (< 10K vectors): Use simple Vec + sort
   - Large multi-batch datasets: Use k-way merge for better cache locality

3. **Efficient Sorting**: Minimize memory allocation and CPU cache misses
   - Group vectors by original batch boundaries when beneficial
   - Sort smaller groups separately for better cache performance

4. **Streaming Write**: Process sorted records directly to SSTable blocks
   - No intermediate BTreeMap storage
   - Immediate deallocation of transient structures

5. **Atomic Flush**: Ensure ACID compliance during write operations

== VIPER Engine Architecture

The VIPER (Vector Indexed Parquet Enhanced Reader) engine uses columnar storage optimized for analytics.

=== Parquet Integration

VIPER leverages Apache Parquet for:
* **Columnar compression**: 50-80% storage reduction
* **Predicate pushdown**: Filter at storage layer
* **Vector quantization**: Optional INT8/PQ compression
* **Batch processing**: Optimized for large scans

=== Quantization Strategy

The key difference between engines:
* **VIPER**: Quantization RECOMMENDED ✓
  - Columnar format benefits from uniform types
  - Better compression ratios
  - Faster SIMD operations

* **SST**: Quantization NOT RECOMMENDED ✗
  - Row format doesn't benefit
  - Added complexity without gains
  - Better to use native FP32

=== Configuration Examples

==== SST for Real-time
[source,python]
----
config = CollectionConfig(
    name="realtime_vectors",
    dimension=768,
    storage_engine="sst",
    compression=CompressionConfig(
        algorithm="lz4",  # Fast compression
        level=1,          # Minimal overhead
        enable_quantization=False  # Not recommended for SST
    )
)
----

==== VIPER for Analytics
[source,python]
----
config = CollectionConfig(
    name="analytics_vectors",
    dimension=1536,
    storage_engine="viper",
    compression=CompressionConfig(
        algorithm="zstd",
        level=6,
        enable_quantization=True,
        quantization_type="pq8"  # Product quantization
    )
)
----

== Advanced Features

=== Multi-Tier Storage
Both engines support tiered storage:
1. **Hot tier**: Memory (Bincode)
2. **Warm tier**: NVMe (Native format)
3. **Cold tier**: HDD/S3 (Compressed)

=== Concurrent Operations
* **SST**: Lock-free reads, sequential writes
* **VIPER**: Batch writes, parallel reads

=== Recovery & Durability
* **WAL**: Write-ahead logging for both engines
* **Snapshots**: Point-in-time backups
* **Replication**: Async replication support
