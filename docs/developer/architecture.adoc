=== Design Principles
* **Proto-first**: Zero double serialization, native proto flow
* **Hardware acceleration**: Auto GPU/SIMD detection
* **Dual storage**: VIPER (columnar) + SST (row-based)
* **SDK-driven**: Client-controlled compression
* **Magic byte validation**: Auto format detection

== System Initialization

image::initialization-sequence.svg[Initialization Sequence, width=900]
_Complete startup sequence showing service creation, dependency injection, and recovery phases_

The initialization follows a careful sequence to avoid circular dependencies:
1. **Core Services Creation**: MetricsCollector and SharedServices
2. **Storage Engine Setup**: Created without CollectionService, then injected
3. **Network Layer**: REST and gRPC servers with unified handlers
4. **Recovery**: Collections from metadata, then vectors from WAL

=== Tiered Storage
```
Memory (bincode) → NVMe (SST/VIPER) → HDD → S3/Cloud
```

* **Memory**: Bincode serialization, <1ms
* **NVMe**: Native formats, bloom filters
* **Cloud**: S3 Express/Standard/Archive
* **Smart promotion**: Only to faster tiers

=== SDK Configuration
```python

config = CompressionConfig(
    algorithm="zstd",     # zstd/lz4/snappy
    level=6,             # 1-22 for zstd
    enable_quantization=True,  # VIPER only
    quantization_type="int8"   # int8/pq8/pq4

```

=== Compression Decision Tree

image::compression-decision-tree.svg[Compression Decision Tree, width=900]
_Decision flow for selecting optimal compression settings based on workload_

=== Two-Stage Search

1. **Index-Based** (AXIS): Quantized index → FP32 rerank
2. **Column-Based** (VIPER): Quantized column → FP32 column
3. **Block-Based** (SST): Bloom filter → Decompress blocks

=== IVF Tiering
```
Centroids (Memory): 1024 centers, ~1.5MB
├── Hot Posting Lists (Memory): Top 100, ~150MB
├── Warm Posting Lists (NVMe): Recent 1hr, ~1.5GB
└── Cold Posting Lists (Disk): Rarely accessed, ~13.5GB
```

== Distance Metrics

**Core**: cosine, euclidean, dot_product
**Extended**: manhattan, hamming, jaccard, chebyshev, canberra, minkowski, angular, bray_curtis, hellinger, custom

== Search Optimization

=== Query Planning
1. Retrieve collection metadata
2. Search WAL/memtable (always first)
3. Execute index or scan strategy
4. Merge and deduplicate results

=== Performance Features
* **Bloom filters**: 95% metadata scan reduction
* **Parallel reading**: 3-5x multi-file speedup
* **Early termination**: Stop at k results
* **Query caching**: LRU repeated queries
* **Predicate pushdown**: 60-90% I/O reduction
