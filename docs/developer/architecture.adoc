**How ProximaDB achieves 17K vectors/sec and sub-millisecond search through innovative architecture.**

== Design Philosophy

**Core Question**: What if we designed every component optimized for vectors from day one?

**Result**: A system where:
* Vectors flow natively without conversion overhead
* Storage engines optimize for vector-specific workloads  
* Hardware acceleration is automatic
* Compression is context-aware

image::technical-architecture-abstract.svg[ProximaDB Architecture, width=900]

== System Architecture

=== Layered Architecture

image::system-data-flow-abstract.svg[System Data Flow, width=900]

The system follows a clean layered architecture:

1. **API Layer**: REST and gRPC endpoints with unified handlers
2. **Service Layer**: VectorOperationsService and CollectionService coordination
3. **Storage Layer**: Dual engines (SST + VIPER) with compression and tiering
4. **Persistence Layer**: WAL, metadata, and multi-cloud storage backends

=== Core Design Principles

[cols="2,2,2", options="header"]
|===
| Traditional Approach | Problem | ProximaDB Solution

| JSON → Proto → Storage
| 4 serialization steps
| Proto native flow (0 conversions)

| Single storage engine
| Suboptimal for all workloads
| Dual engines (VIPER + SST)

| Manual optimization
| CPU/GPU detection manual
| Auto hardware acceleration

| Server-side compression
| One-size-fits-all
| SDK-driven per-collection tuning
|===

== Core Components

=== Storage Architecture

image::storage-components-detail-modular.svg[Storage Components, width=900]

==== Dual Storage Engines

[cols="1,2,2", options="header"]
|===
| Engine | Optimized For | Use Cases

| **VIPER**
| Analytics queries, compression
| Batch analytics, data warehousing, >10K vectors

| **SST**
| High-throughput writes, OLTP  
| Real-time applications, frequent updates, <10K vectors
|===

==== Hierarchical Storage

```
Memory (Bincode) → NVMe (SST/VIPER) → HDD → S3/Cloud
```

* **Memory Tier**: Sub-millisecond access with bincode serialization
* **NVMe Tier**: Native formats with bloom filter optimization
* **Cloud Tier**: Cost-optimized with smart caching

=== Service Architecture

image::service-interactions-abstract.svg[Service Interactions, width=900]

==== VectorOperationsService
**Location**: `/src/services/vector_operations_service.rs`

* Direct memtable access (40-60% latency reduction)
* Unified search orchestration across all storage layers
* Query planning and optimization
* SDK-driven compression routing

==== CollectionService  
**Location**: `/src/services/collection_service.rs`

* Collection metadata management
* Storage assignment embedded in Collection proto
* Compression configuration per collection
* Distance metric and index settings

* GPU acceleration: 10x faster for large batches
* SIMD (AVX-512): 4x faster distance computation
* Automatic fallback for any hardware

== Compression Architecture

image::compression-architecture-abstract.svg[Compression Architecture, width=900]

=== Two-Tier Compression Model

1. **Protocol Level** (Transport)
   - REST/gRPC compression
   - Disabled by default for performance
   - Server-wide configuration

2. **Collection Level** (Storage)
   - Per-collection compression settings
   - SDK-driven configuration
   - 13 supported algorithms
   - Context-aware optimization

=== Quantization System

image::quantization-strategy-abstract.svg[Quantization Strategy, width=900]

* **Scalar Quantization**: 4-8x compression, 99.5% accuracy
* **Product Quantization**: 16-64x compression, 95-99% accuracy  
* **Binary Quantization**: 32x compression, 85-95% accuracy

== Search Architecture

=== Two-Level Search Orchestration

image::vector-search-abstract.svg[Search Architecture, width=900]

**Level 1: High-Level Orchestration** (VectorOperationsService)
```
search()
├── WAL.search()      // Unflushed data
├── Index.search()    // AXIS indexes if available
├── Storage.search()  // SST or VIPER engines
└── Merge Results     // Deduplicate and sort
```

**Level 2: Engine Optimizations**
* SST: Three-stage filtering pipeline
* VIPER: Columnar predicate pushdown
* Cache: Multi-tier with smart eviction
