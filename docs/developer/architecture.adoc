== 🏗️ System Overview

ProximaDB is a **proto-first, hardware-accelerated vector database** designed for enterprise AI applications.

image::storage-architecture-complete.svg[ProximaDB Architecture, align=center, width=900]

=== Core Design Principles

* **Proto-first**: Zero double serialization - VectorRecord flows natively as proto types
* **Hardware acceleration**: Automatic GPU/SIMD detection and usage
* **Dual storage engines**: VIPER (columnar/analytics) + SST (row-based/OLTP)
* **SDK-driven compression**: Client-controlled compression without server defaults
* **Magic byte validation**: Automatic format detection via magic bytes

== 🗄️ Storage Architecture

=== Magic Bytes System

ProximaDB uses magic bytes for automatic format detection and validation:

image::proximadb-unified-architecture.svg[ProximaDB Unified Architecture, align=center, width=900]

[cols="2,1,1,2", options="header"]
|===
| Engine | Magic | Location | Purpose

| **SST Engine**
| `SST1`
| Header (0x0)
| Row-based OLTP storage

| **VIPER Engine** 
| `PAR1`
| Footer (-4 bytes)
| Columnar analytics storage

| **Bloom Filters**
| `BF01`
| Section header
| Fast negative lookups

| **Indexes**
| `IDX1`
| Section header
| B-tree/skip list indexes
|===

=== Storage Engine Selection

**SST Engine** - Optimized for:
* OLTP workloads and real-time ingestion
* Point queries and single-vector updates
* Small to medium batch operations (<10K vectors)
* Low-latency requirements (sub-millisecond)

**VIPER Engine** - Optimized for:
* Analytics workloads and complex queries
* Large batch operations (>10K vectors)
* Columnar scans with metadata filtering
* Maximum compression efficiency (50-80% reduction)

=== File Format Detection Flow

[source]
----
File Access Request
    ├─ Read magic bytes
    │   ├─ Header check: "SST1" → Route to SST Engine
    │   ├─ Footer check: "PAR1" → Route to VIPER Engine
    │   └─ Extension fallback → Use file extension
    └─ Validate sub-components
        ├─ SST: Check BF01, IDX1, BLK1
        └─ VIPER: Validate Parquet schema
----

=== SDK-Driven Compression

All compression is controlled from the client SDK:

```python
from proximadb import ProximaDBClient
from proximadb.models import CompressionConfig

config = CompressionConfig(
    sst_compression_algorithm="zstd",
    sst_compression_level=6,
    sst_block_size=32768,
    viper_enable_dual_columns=True,
    adaptive_compression=True,
    compression_threshold_kb=100
)

collection = client.create_collection(
    name="vectors",
    dimension=1536,
    compression_config=config
)
```

=== Two-Stage Search

For quantized/compressed data:

1. **Coarse Search**: Fast search on quantized vectors
2. **Reranking**: Precise search on decompressed candidates
3. **Result Merging**: Combine and deduplicate results

== 🔧 Development Guidelines

=== Best Practices

1. **Proto-First**: Use proto types directly
2. **Magic Byte Validation**: Always validate file formats
3. **SDK-Driven**: No server-side compression defaults
4. **Cache-Aware**: Utilize decompression cache
5. **Hardware-Aware**: Use capabilities system

=== Common Patterns

```rust
// Compression-aware search
let plan = query_planner.plan_proto_query(&query, &files).await?;
if plan.use_two_stage {
    // Coarse + reranking
} else {
    // Direct search
}

// Magic byte validation
if &data[0..4] != b"SST1" {
    return Err(anyhow!("Invalid SST format"));
}
```
