== 🏗️ System Overview

ProximaDB is a **proto-first, hardware-accelerated vector database** designed for enterprise AI applications.

image::proximadb-unified-architecture.svg[ProximaDB Architecture, align=center, width=800]

=== Core Design Principles

* **Proto-first**: Zero double serialization - VectorRecord flows natively as proto types
* **Hardware acceleration**: Automatic GPU/SIMD detection and usage
* **Dual storage engines**: VIPER (columnar/analytics) + SST (row-based/OLTP)
* **Direct vector service**: Eliminates abstraction layers for 40-60% latency improvement

== 🔧 Core Components

=== DirectVectorService
**Location**: `/src/services/direct_vector_service.rs`

Direct memtable access eliminating abstraction layers:
```rust
// Proto-first pipeline
Proto → DirectVectorService → Memtable → Storage
```

**Benefits**:
* 40-60% latency reduction
* Zero serialization overhead
* Direct memory access patterns
* Integrated WAL recovery using collection metadata

=== CollectionService (Updated 2025-08-06)
**Location**: `/src/services/collection_service.rs`

Manages collection metadata with integrated storage assignment:
```rust
// Storage assignment now embedded in Collection proto
Collection {
    id: String,
    config: CollectionConfig,
    stats: CollectionStats,
    storage_assignment: Option<StorageAssignment>, // NEW
}
```

**Key Changes**:
* Removed separate AssignmentService
* Storage locations managed within collection metadata
* WAL discovery through collection service
* Automatic storage assignment on collection creation

=== Hardware Capabilities System
**Location**: `/src/core/hardware_capabilities.rs`

Centralized hardware detection using `OnceLock` pattern:
```rust
// Initialize once at startup
initialize_hardware_capabilities_default()?;
let caps = get_hardware_capabilities();
```

**Features**:
* GPU detection (CUDA, ROCm, MPS, OpenCL)
* SIMD capabilities (AVX2, SSE4.1)
* Memory and CPU optimization

=== Unified Atomic Coordinator
**Location**: `/src/storage/atomic.rs`

ACID transaction support for all write operations:
* Multi-collection consistency
* Write buffer coordination
* Rollback capabilities

== 🗄️ Storage Engines

=== VIPER Engine (Columnar)
**Optimized for**: Analytics, read-heavy workloads

**Features**:
* Parquet format with ZSTD compression
* Predicate pushdown (60-90% I/O reduction)
* Quantization support
* Adaptive reading strategies

**File Structure**:
```
/src/storage/engines/viper/
├── unified_parquet_reader.rs    # Adaptive reading
├── quantization/               # Compression support
└── tests/                     # Engine tests
```

=== SST Engine (Row-based)
**Optimized for**: OLTP, write-heavy workloads

**Features**:
* SSTable format with bloom filters
* Three-stage filtering (Bloom → Index → Row)
* Bytemuck serialization (5-10x speedup)
* Intelligent compaction

**File Structure**:
```
/src/storage/engines/sst/
├── unified_search_engine.rs     # Search optimization
├── bloom_filter/               # Fast filtering
└── tests/                     # Engine tests
```

== 🚀 Performance Optimizations

=== Search Optimizations
1. **Bloom Filters**: Skip 95%+ irrelevant batches in memtable
2. **Parallel SSTable Reading**: 3-5x speedup for multi-file searches  
3. **Early Termination**: Stop when k results found (unordered queries)
4. **Query Result Caching**: LRU cache at service level
5. **Predicate Pushdown**: Reduce data transfer by 50-80%

=== SQL Engine (High-Performance)
**Location**: `/src/query/sql_engine/`

**Features**:
* Lock-free parser pool (1M+ queries/sec)
* SIMD-accelerated vector parsing (AVX2/SSE4.1)
* Query result caching with DashMap
* GPU-accelerated parsing support

**Architecture**:
```rust
// Lock-free concurrent parsing
LockFreeParserPool → SIMD VectorParser → QueryCache
```

=== Compression System
**Automatic compression** for both REST and gRPC:
* **REST**: deflate, gzip, zstd, brotli via tower-http
* **gRPC**: Native gzip compression  
* **Bandwidth savings**: 50-80% reduction
* **Zero configuration**: Transparent to clients

* **Integration tests**: Cross-component workflows
* **Performance tests**: Benchmark validation
* **Stress tests**: Concurrent load validation

== 🔧 Development Guidelines

=== Code Patterns
* **Proto-first**: Use proto types directly, avoid conversions
* **Atomic writes**: Always use UnifiedAtomicCoordinator
* **Storage-aware**: Let engines select optimal strategies
* **Hardware-aware**: Use capabilities system for optimization
