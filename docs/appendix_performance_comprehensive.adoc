== Executive Summary

This comprehensive performance analysis covers ProximaDB's performance across different protocols (REST/gRPC), storage engines (VIPER/LSM), and quantization levels. Key findings include:

* **gRPC Protocol**: 3-4x faster than REST for batch operations
* **Optimal Batch Size**: 500-1500 vectors for REST, 3000 vectors for gRPC
* **Insert Performance**: Peak at 77,872 vectors/second (gRPC, batch 3000)
* **Search Latency**: Sub-2ms for small datasets, ~110ms for 100K vectors
* **Large Scale**: 79K+ vectors/second for VIPER, 66K+ for LSM with gRPC
* **100K Vector Dataset**: gRPC completes in 1.3s vs REST's 4.7s

=== Performance Characteristics

==== VIPER Engine
* **Strengths**: 
  - Columnar storage with Parquet compression
  - Predicate pushdown for filtered searches
  - ML clustering for large datasets
  - Excellent for analytical workloads
* **Trade-offs**:
  - Batch flush latency (~100ms per 8MB)
  - Requires flush before search visibility

==== LSM Engine
* **Strengths**:
  - Consistent write performance
  - Immediate search visibility
  - Bloom filters for efficient lookups
  - Better for real-time workloads
* **Trade-offs**:
  - Higher storage overhead
  - Write amplification during compaction

== Performance Optimization Guidelines

=== For Maximum Throughput

1. **Use gRPC Protocol**: 3-4x faster for batch operations
2. **Optimal Batch Size**: 
   - REST: 1,500 vectors (~26K vec/s)
   - gRPC: 3,000 vectors (~78K vec/s)
3. **Storage Engine**: 
   - VIPER: Best for batch operations (79K vec/s)
   - LSM: Good balance (66K vec/s)
4. **Parallelization**: Use multiple client connections for >1M vectors

=== For Minimum Latency

1. **Small Batches**: 10-100 vectors
2. **REST Protocol**: Slightly lower latency for search
3. **Keep Datasets Small**: Sub-second search for <100K vectors
4. **LSM Engine**: Immediate visibility for real-time apps

== Conclusion

ProximaDB demonstrates excellent performance characteristics:

* **Protocol Choice Matters**: gRPC provides 3.4x better throughput for inserts
* **Batch Size Optimization**: 
  - REST: 1,500 vectors optimal (~26K vec/s)
  - gRPC: 3,000 vectors optimal (~78K vec/s)
* **Storage Engines**: 
  - VIPER excels at batch operations (79K vec/s)
  - LSM provides consistent performance (66K vec/s)
* **Scalability**: 
  - 100K vectors: 1.3s with gRPC vs 4.7s with REST
  - Search latency ~110ms for 100K dataset
* **Data Persistence**: 
  - 100% data integrity across server restarts
  - 2-4 second recovery time for large datasets
  - Minimal performance impact post-recovery
* **Proto-First Architecture**: Enables unified handling with minimal overhead

The performance metrics confirm ProximaDB is suitable for:
- **High-throughput batch processing**: Use gRPC + VIPER with 3K batch size
- **Low-latency real-time applications**: Use REST/gRPC + LSM with smaller batches
- **Large-scale deployments**: gRPC handles 100K+ vectors efficiently
- **Production systems**: Excellent persistence and recovery capabilities
- **Memory-constrained environments**: PQ-8 provides 4x memory reduction with 90% recall
- **Complex analytical queries**: Advanced metadata filtering with AND/OR/NOT expressions
- **Hybrid workloads**: Automatic flush triggers ensure data persistence without manual intervention
