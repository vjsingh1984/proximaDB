== Status Tiers

|===
| Tier | Meaning | Guidance

| Supported
| Primary product path with coherent API behavior on the canonical single-node surface.
| Safe default for adoption, examples, and positioning.

| Beta
| Implemented and useful, but still has known execution or operator gaps.
| Use with review and explicit scope control.

| Experimental
| Foundations exist, but behavior, transport, or support expectations are still in flux.
| Feature-gate and avoid broad product claims.

| Planned
| Roadmap item without a coherent product surface yet.
| Do not market as implemented.
|===

== Current Matrix

|===
| Capability | Tier | Current Scope | Main Constraints

| Vector CRUD and search
| Supported
| Canonical REST v2 record batch/search/get flows and gRPC `proximadb.v2.ProximaRecordService` record operations. REST/gRPC v1 vector-shaped flows remain compatibility adapters for existing clients and must lower into canonical records.
| Keep hybrid retrieval and distributed search claims separate from the supported vector surface. New clients should not target v1 `VectorRecord`/`SqlValue` payloads.

| Federated SQL over function-backed sources
| Beta
| `VECTOR_SEARCH(...)`, `GRAPH_QUERY(...)`, `DOCUMENT_QUERY(...)`, `LOGS(...)`, and `METRICS(...)` run through the federated engine with cache support. Phase 2.5: pipeline-based execution, morsel-driven parallelism, Arrow-native cross-model format for LATERAL joins, batch SIMD distance.
| Strongest on function-backed sources; generic relational scans and remote distributed execution are still incomplete.

| Document CRUD, query, and aggregation
| Beta
| WAL-backed collections, CRUD, aggregation, change events, and in-memory query execution are implemented. Canonical `ProximaRecord` storage exists as the convergence path.
| Canonical record storage is not yet the default durable authority across all server wiring. Path-filter depth, geo indexes, and deeper block-level pruning/compression are incomplete.

| ORION graph operations
| Beta
| Node/edge CRUD, traversal, neighbors, shortest-path APIs, canonical node/edge mapping, and adjacency projections are usable.
| Declarative graph query execution is still incomplete on the canonical gRPC path. ORION/PULSAR/QUASAR remain projections or compatibility engines unless an ADR promotes additional durable semantics.

| Observability ingestion and query
| Beta
| Logs, metrics, and traces ingestion exist alongside full-text log search, PromQL execution, CHRONO integration, and canonical observability record mapping.
| Canonical observability replay into shared record storage is not yet the default. Alerting, operator workflow depth, and some gRPC query mappings remain incomplete.

| Security runtime
| Beta
| JWT, API key, SSO hooks, mTLS identity, and CRL-backed revocation reload/freshness checks are present.
| Security admin/status APIs and stronger online revocation policy are incomplete.

| Hybrid retrieval
| Beta
| tantivy BM25 integration, RRF/weighted fusion, and compatibility REST `/api/v1/hybrid/search` facade (TD-008 resolved).
| Backend integration improved; REST v1 remains a deprecated compatibility surface and gRPC path parity is still in progress. Projection Fusion is a shared planner contract only until runtime implementation, explain output, and benchmarks are complete.

| PULSAR and QUASAR graph engines
| Experimental
| Distributed and hybrid graph foundations exist in code.
| They are not the canonical product graph path and are not fully wired end-to-end.

| Distributed cluster execution
| Experimental
| Raft internals, shard planning, and routing foundations exist.
| RPC transport and remote execution still contain placeholder or partial implementations.

| Time-series and event foundations
| Beta
| TST engine complete (ASOF joins, downsampling, OHLC; TD-009). Event sourcing engine complete (append-only WAL, temporal queries; TD-010).
| Product packaging, API parity, and production validation at scale still in progress.
|===

== Not Supported in v0.2

The v0.2 release ships **single-node**, **CRUD-only** writes, and **per-request** freshness/route
controls. The items below are out of scope for v0.2; do not document, demo, or release-note them as
supported. The live source of truth for write contract is the
`WriteContractHealth` block in route-health (`src/network/rest/v2/collections.rs:869-880`,
GET `/api/v2/_diagnostics/collections/{collection_id}/route-health`):

|===
| Surface | Status in v0.2 | Live signal

| Optimistic versioning (compare-and-set on insert/upsert)
| Not supported
| No `version` / `if_match` / `if_none_match` field on `InsertRecordsRequest` or
  `UpsertRecordsRequest`. `WriteContractHealth.conditional_write = false`.

| Conditional writes (predicate-gated insert/upsert/delete)
| Not supported
| `WriteContractHealth.conditional_write = false`.

| Update-by-filter / delete-by-filter
| Not supported
| `WriteContractHealth.filter_write = false`. Delete is single-record / batch-of-ids only.

| Patch / partial-record update
| Not supported
| `WriteContractHealth.patch = false`. Full-record upsert is the only mutation shape.

| Collection-default freshness mode
| Not supported (per-request only)
| `FreshnessHealth.collection_level_modes_wired = false`
  (`src/network/rest/v2/collections.rs:1114-1126`). Per-request `freshness_mode`
  (`Strong`/`BoundedStale{max_staleness_ms}`/`StaleOk`) is honored;
  collection-default is not catalog-persisted in v0.2. See TD-074.

| Filtered ANN per-collection policy
| Not supported (default policy only)
| `AnnFilteringPolicy` runs from the default in v0.2; per-collection catalog
  policy plumbing tracked in TD-073. Differential recall envelope across
  selectivity bands is verified by `tests/filtered_ann_recall_bands.rs` but
  no recall SLA is claimed.

| `RecallProbeGate` enforced route selection
| Not supported (diagnostic only)
| Gate state is readable via route-health and EXPLAIN; route selection in
  `AxisManager` does not consult the gate. Quantized-route enforcement
  tracked in TD-075.
|===

If a release note or SDK doc implies any of the above works, file a doc fix before the cut.

== Experimental in v0.2 (do not market as implemented)

These surfaces have code foundations but are not part of the v0.2 product story. Release collateral
must not list them under "supported", "production", or "ready":

* Distributed cluster execution (Raft transport / remote execution placeholders).
* PULSAR and QUASAR graph engines.
* Full SQL parity (ADR-018 Phase 2/3 — Postgres parity).
* External-table execution (Iceberg / Delta / Hudi as Proxima-owned hot authority).
* Arrow Flight / gRPC service multiplexing as a customer-facing transport.
* Trino / Spark compute adapters.
* All "Not Supported in v0.2" items above.

== Positioning Guidance

ProximaDB should currently be positioned as a developer-first context database:

* One system for vectors, operational documents, graph context, and telemetry on the single-node developer path.
* Best fit for integrated semantic + graph + telemetry workflows.
* Not yet a like-for-like replacement for best-in-class distributed vector, graph, document, or observability platforms.

== Near-Term Exit Criteria

The next maturity step is to move from "broad but uneven" to "narrow but reliable":

* One canonical execution path for vector, hybrid, graph, document, and observability queries.
* Canonical `ProximaRecord`/xCatalog/WAL authority is default for document, graph, and observability writes; modality engines are cataloged projections.
* No roadmap or README claims that exceed the supported surface defined here.
* Distributed claims backed by real transport and failover verification.
