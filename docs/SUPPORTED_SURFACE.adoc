== Canonical API Surface

REST `/api/v2` is the **sole canonical surface** for all ProximaDB clients as of 2026-06-17.

[IMPORTANT]
====
* *REST /api/v2* — canonical; all new clients and integrations must target this prefix.
* *REST /api/v1* — deprecated compatibility adapter. Requests are still accepted but must
  lower into v2 handlers internally. The v1 prefix will be retired; do not document or
  advertise it in new collateral.
* *REST /api/v3* — folded back into v2 as a permanent *308 Redirect* alias. `POST
  /api/v3/collections/{id}/documents` redirects to `POST
  /api/v2/collections/{id}/documents`. No additional v3 surface is defined.
* *gRPC v1 (`proximadb.v1.*`)* — deprecated-compat; **OFF by default**. Enable only for
  transitional client compatibility via config flag `enable_grpc_v1_compat: true` or
  environment variable `PROXIMADB_GRPC_V1_COMPAT=1`. This compat layer is scheduled for
  **Sunset 2026-06-30**; clients must migrate to `proximadb.v2.*` before that date.
====

== Status Tiers

|===
| Tier | Meaning | Guidance

| Supported
| Primary product path with coherent API behavior on the canonical single-node surface.
| Safe default for adoption, examples, and positioning.

| Beta
| Implemented and useful, but still has known execution or operator gaps.
| Use with review and explicit scope control.

| Experimental
| Foundations exist, but behavior, transport, or support expectations are still in flux.
| Feature-gate and avoid broad product claims.

| Planned
| Roadmap item without a coherent product surface yet.
| Do not market as implemented.
|===

== Current Matrix

|===
| Capability | Tier | Current Scope | Main Constraints

| Vector CRUD and search
| Supported
| Canonical REST `/api/v2` record batch/search/get/scan flows and gRPC `proximadb.v2.ProximaRecordService` record operations. REST `/api/v1` and gRPC v1 vector-shaped flows are deprecated compatibility adapters for existing clients only (see Canonical API Surface above); they lower into canonical v2 handlers and will be retired. Record metadata filters are enforced on typed `/search` (`filters:[{field,op,value}]`) and `/records/scan` (`filter`) across the supported ops (`eq,neq,gt,gte,lt,lte,in,contains,between,starts_with,ends_with`), including tenant/account scoping; array-valued props support `in`/`contains` membership.
| Keep hybrid retrieval and distributed search claims separate from the supported vector surface. New clients must not target v1 `VectorRecord`/`SqlValue` payloads.

| Federated SQL over function-backed sources
| Beta
| `VECTOR_SEARCH(...)`, `GRAPH_QUERY(...)`, `DOCUMENT_QUERY(...)`, `LOGS(...)`, and `METRICS(...)` run through the federated engine with cache support. Phase 2.5: pipeline-based execution, morsel-driven parallelism, Arrow-native cross-model format for LATERAL joins, batch SIMD distance.
| Strongest on function-backed sources; generic relational scans and remote distributed execution are still incomplete.

| Document CRUD, query, and aggregation
| Beta
| WAL-backed collections, CRUD, aggregation, change events, and in-memory query execution are implemented. Canonical `ProximaRecord` storage exists as the convergence path.
| Canonical record storage is not yet the default durable authority across all server wiring. Path-filter depth, geo indexes, and deeper block-level pruning/compression are incomplete.

| ORION graph operations
| Beta
| Node/edge CRUD, traversal, neighbors, shortest-path APIs, canonical node/edge mapping, and adjacency projections are usable. These core operations are now served on the canonical v2 gRPC surface (`proximadb.v2.ProximaGraphService`, always-registered) and consumed by the Python SDK; the deprecated `proximadb.v1.GraphService` is off by default (`enable_grpc_v1_compat`).
| Declarative graph query execution (Cypher/Gremlin `ExecuteQuery`) and several analytic/batch RPCs are still incomplete on the canonical v2 gRPC path (deferred — TD-124); graph creation/DDL is REST-only (`/api/v2/graphs`). ORION is a rebuildable projection runtime; durable graph authority remains in canonical records, xCatalog, WAL/log/manifest state, policy/RLS, version/time, and provenance.

| Observability ingestion and query
| Beta
| Logs, metrics, and traces ingestion exist alongside full-text log search, PromQL execution, CHRONO integration, and canonical observability record mapping.
| Canonical observability replay into shared record storage is not yet the default. Alerting, operator workflow depth, and some gRPC query mappings remain incomplete.

| Security runtime
| Beta
| JWT, API key, SSO hooks, mTLS identity, and CRL-backed revocation reload/freshness checks are present.
| Security admin/status APIs and stronger online revocation policy are incomplete.

| Hybrid retrieval
| Beta
| tantivy BM25 integration, RRF/weighted fusion, and canonical REST `/api/v2/collections/{id}/search` hybrid path (TD-008 resolved). The former `/api/v1/hybrid/search` facade is a deprecated compat alias only. Request `filters` are enforced on both fusion legs: the vector candidates are filtered server-side, and the text (BM25) candidates are gated to that filtered id set so a scoped filter cannot leak through the text leg.
| Backend integration improved; REST v1 hybrid alias is a deprecated compatibility surface (see Canonical API Surface above) and gRPC path parity is still in progress. A BM25-only match that passes the filter but falls outside the vector leg's `top_k` (or a hybrid request with no query vector) is dropped rather than risk a leak — safe, but it can under-return; keeping that tail needs a resolving metadata fetch (follow-up). Projection Fusion is a shared planner contract only until runtime implementation, explain output, and benchmarks are complete.

| PULSAR and QUASAR graph engine names
| Retired / Not supported
| Separate PULSAR and QUASAR engine code, feature flags, REST routes, and dedicated tests have been removed.
| Use ORION. Former distributed-graph behavior belongs to the relational distributed substrate; former tiered-graph behavior belongs to xCatalog/storage projection policy.

| Distributed cluster execution
| Experimental
| Raft internals, shard planning, and routing foundations exist.
| RPC transport and remote execution still contain placeholder or partial implementations.

| Time-series and event foundations
| Beta
| TST engine complete (ASOF joins, downsampling, OHLC; TD-009). Event sourcing engine complete (append-only WAL, temporal queries; TD-010).
| Product packaging, API parity, and production validation at scale still in progress.
|===

== Not Supported in v0.2

The v0.2 release ships **single-node**, **CRUD-only** writes, and **per-request** freshness/route
controls. The items below are out of scope for v0.2; do not document, demo, or release-note them as
supported. The live source of truth for write contract is the
`WriteContractHealth` block in route-health (`src/network/rest/v2/collections.rs:869-880`,
GET `/api/v2/_diagnostics/collections/{collection_id}/route-health`):

|===
| Surface | Status in v0.2 | Live signal

| Optimistic versioning (compare-and-set on insert/upsert)
| Not supported
| No `version` / `if_match` / `if_none_match` field on `InsertRecordsRequest` or
  `UpsertRecordsRequest`. `WriteContractHealth.conditional_write = false`.

| Conditional writes (predicate-gated insert/upsert/delete)
| Not supported
| `WriteContractHealth.conditional_write = false`.

| Update-by-filter / delete-by-filter
| Not supported
| `WriteContractHealth.filter_write = false`. Delete is single-record / batch-of-ids only.

| Patch / partial-record update
| Not supported
| `WriteContractHealth.patch = false`. Full-record upsert is the only mutation shape.

| Collection-default freshness mode
| Not supported (per-request only)
| `FreshnessHealth.collection_level_modes_wired = false`
  (`src/network/rest/v2/collections.rs:1114-1126`). Per-request `freshness_mode`
  (`Strong`/`BoundedStale{max_staleness_ms}`/`StaleOk`) is honored;
  collection-default is not catalog-persisted in v0.2. See TD-074.

| Filtered ANN per-collection policy
| Not supported (default policy only)
| `AnnFilteringPolicy` runs from the default in v0.2; per-collection catalog
  policy plumbing tracked in TD-073. A deterministic recall-band harness exists
  at `tests/filtered_ann_recall_bands.rs`, but it is intentionally ignored
  while ADR-011 remains Beta; no recall SLA is claimed.

| `RecallProbeGate` enforced route selection
| Not supported (diagnostic only)
| Gate state is readable via route-health and EXPLAIN; route selection in
  `AxisManager` does not consult the gate. Quantized-route enforcement
  tracked in TD-075.
|===

If a release note or SDK doc implies any of the above works, file a doc fix before the cut.

== Experimental in v0.2 (do not market as implemented)

These surfaces have code foundations but are not part of the v0.2 product story. Release collateral
must not list them under "supported", "production", or "ready":

* Distributed cluster execution (Raft transport / remote execution placeholders).
* PULSAR and QUASAR graph engines (retired; use ORION).
* Full SQL parity (ADR-018 Phase 2/3 — Postgres parity).
* PostgreSQL-style OLTP/HTAP parity: full MVCC transactions, FK/PK/unique/check enforcement,
  native row/delta indexes, DataFusion snapshot-plus-delta reads, and distributed consistency gates
  are tracked in TD-110 and are not part of v0.2.
* External-table execution (Iceberg / Delta / Hudi as Proxima-owned hot authority).
* Iceberg v3 interop _write/export_ — `ALTER TABLE … MATERIALIZE` over pgwire emits a
  spec-shaped Iceberg v3 table (`v*.metadata.json` referencing an Avro manifest list + manifest)
  to the warehouse so external Iceberg engines can read it (verified by `tests/iceberg_interop_e2e.rs`).
  One-way publish only; this is distinct from the hot-authority item above (still experimental), and
  external read-back plus multi-writer coordination are unverified.
* Columnar vector quantization (RaBitQ / SQ8) in PAX vector segments — _flag-gated, default OFF_.
  Enabled with `PROXIMADB_PAX_VECTOR_SEGMENTS=1` plus `PROXIMADB_PAX_VECTOR_QUANT=rabitq|sq8|auto`
  (deployment-level env selector; per-collection proto config is the productionization follow-up).
  Reads are mixed-format-safe — existing ProximaBlocks segments still read back when the flag is on.
  Codecs/kernels are tested; no per-collection policy or recall SLA is claimed.
* Arrow Flight / gRPC service multiplexing as a customer-facing transport.
* Trino / Spark compute adapters — _scaffolded_ (Spark JNI bridge per TD-097; Trino Flight per TD-098). Structural contract gates land in 2026-05-30 connector sprint (`tests/connectors_flight_contract.rs`); end-to-end wire impl deferred.
* Hadoop InputFormat / OutputFormat — _write-side wire-true_ (`ProximaRecordWriter::flush_now` posts spec-true `/api/v2/.../records/batch`); read-side blocked on the records-scan endpoint gap tracked under TD-099.
* DuckDB connector — _Rust-side wire-true for bind / search / insert_ (`src/connectors/duckdb.rs`); DuckDB extension binary compilation + scan-via-Flight are separate follow-ups.
* All "Not Supported in v0.2" items above.

== Positioning Guidance

ProximaDB should currently be positioned as a developer-first context database:

* One system for vectors, operational documents, graph context, and telemetry on the single-node developer path.
* Best fit for integrated semantic + graph + telemetry workflows.
* Not yet a like-for-like replacement for best-in-class distributed vector, graph, document, or observability platforms.

== Near-Term Exit Criteria

The next maturity step is to move from "broad but uneven" to "narrow but reliable":

* One canonical execution path for vector, hybrid, graph, document, and observability queries.
* Canonical `ProximaRecord`/xCatalog/WAL authority is default for document, graph, and observability writes; modality engines are cataloged projections.
* No roadmap or README claims that exceed the supported surface defined here.
* Distributed claims backed by real transport and failover verification.
