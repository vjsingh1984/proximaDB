**Why SST exists and how it solves write-heavy vector workloads**

== Design Philosophy

=== The Problem SST Solves

Vector databases face a fundamental tension: **writes are sequential but searches are random**. Traditional approaches force a choice:

* **Row-stores** (PostgreSQL pgvector): Good writes, poor vector search (full table scan)
* **Pure columnar** (Parquet): Good analytics, poor write latency (immutable files)
* **Graph-based indexes** (HNSW): Good search, poor writes (expensive rebalancing)

SST resolves this by combining **LSM-tree sequential writes** with **three-stage progressive filtering** that eliminates candidates before expensive distance computation.

=== Core Design Decisions

[cols="2,3,3", options="header"]
|===
| Decision | Rationale | Trade-off
| **LSM-tree architecture** | Sequential disk writes achieve maximum throughput; immutable files simplify concurrency | Read amplification from multiple levels
| **Three-stage filtering** | Eliminates 99%+ candidates cheaply before distance computation | Additional metadata storage overhead
| **Hybrid columnar format** | SIMD-friendly columnar layout without pure-columnar write penalties | More complex serialization
| **Per-block bloom filters** | O(1) negative lookups skip entire blocks | 1% false positive rate, memory overhead
|===

== Architecture Overview

=== Why LSM-Tree for Vectors?

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
stateDiagram-v2
    [*] --> MemTable: Write Request
    MemTable --> WAL: Durability
    MemTable --> L1: Flush (64MB threshold)

    state "Level 1 (Hot)" as L1 {
        [*] --> SmallFiles: 2MB SSTables
        SmallFiles --> Compact: >10 files
    }

    state "Level 2+ (Cold)" as L2 {
        [*] --> MergedFiles: 20-200MB SSTables
        MergedFiles --> [*]: Long-term storage
    }

    L1 --> L2: Tiered Compaction

    note right of MemTable
        In-memory sorted buffer
        enables batch writes
    end note

    note right of L1
        Small files for fast writes
        Accept some read amplification
    end note

    note right of L2
        Large files minimize space
        Leveled compaction reduces read amp
    end note
----

**Key insight**: Vector workloads are often WORM (Write Once, Read Many). LSM-trees excel here because:

1. **Writes never modify existing data** - New versions append, old versions garbage-collected
2. **Compaction amortizes write cost** - Background merge keeps read amplification bounded
3. **Immutable files simplify caching** - Files never change, aggressive caching possible

=== Three-Stage Filtering: The Core Innovation

**Problem**: Computing L2 distance for 1M 768-dim vectors = 3 billion operations. Brute force is O(n×d).

**Solution**: Eliminate candidates progressively using cheap operations before expensive distance computation.

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
flowchart TB
    subgraph STAGE1["Stage 1: Bloom Filter (O(1) per file)"]
        A[1000 SST Files] --> B{Bloom Filter<br/>+ Zone Maps}
        B -->|Definite No Match| X1[900 files skipped<br/>Cost: 100ns each]
        B -->|Possible Match| C[100 files remain]
    end

    subgraph STAGE2["Stage 2: Index Entry (O(log n) per file)"]
        C --> D{Block Index<br/>Metadata Ranges}
        D -->|Range Mismatch| X2[80 files skipped<br/>Cost: 1µs each]
        D -->|Range Overlap| E[20 files, 5K blocks]
    end

    subgraph STAGE3["Stage 3: Row Filter (O(m) per block)"]
        E --> F{Metadata<br/>Predicate Eval}
        F -->|Filter Fails| X3[4500 vectors skipped<br/>Cost: 10ns each]
        F -->|Filter Passes| G[500 candidates]
    end

    subgraph DISTANCE["Distance Computation"]
        G --> H[L2/Cosine Distance<br/>500 × 768 dims]
        H --> I[Top-K Results]
    end

    style STAGE1 fill:#e6f3ff,stroke:#4a90e2
    style STAGE2 fill:#fff3e6,stroke:#f4a261
    style STAGE3 fill:#e6ffe6,stroke:#93c47d
    style DISTANCE fill:#ffe6e6,stroke:#e06666
----

**Why three stages?**

|===
| Stage | Cost | Eliminates | Key Data Structure

| **Bloom Filter** | O(1), ~100ns | 90% of files | Probabilistic bit array (1% FPR)
| **Index Entry** | O(log n), ~1µs | 80% of blocks | Zone maps (min/max per column)
| **Row Filter** | O(m), ~10µs | 90% of vectors | SIMD predicate evaluation
|===

Total: **99.9% elimination before distance computation**

=== When to Choose SST

[cols="1,4", options="header"]
|===
| Choose SST When | Rationale

| **High write throughput needed**
| LSM-tree achieves 100K+ writes/sec via sequential I/O

| **Real-time query requirements**
| Three-stage filtering provides <1ms p99 latency

| **Metadata filtering is selective**
| Bloom filters + zone maps eliminate 99% before scan

| **Mixed insert/query workload**
| Designed for concurrent writes and reads

| **ACID guarantees required**
| WAL + atomic flush ensures durability
|===

=== When NOT to Choose SST

[cols="1,2,2", options="header"]
|===
| Scenario | Better Choice | Why

| Pure analytics, batch queries
| **VIPER**
| Pure columnar + predicate pushdown

| Spatial clustering queries
| **HELIX**
| Hilbert curves preserve locality

| Ultra-low latency (<10µs), small datasets
| **SWIFT**
| In-memory three-tier hierarchy

| Read-mostly workloads
| **NOVA**
| Progressive columnar, no compaction overhead

| Adaptive access patterns
| **RAPTOR**
| Matrix Trinity learns query patterns
|===

== Data Flow Architecture

=== Write Path State Diagram

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
stateDiagram-v2
    [*] --> Received: Insert Request

    state "Memory Layer" as MEM {
        Received --> Buffered: Add to MemTable
        Buffered --> WALWritten: Persist to WAL
        WALWritten --> Acknowledged: Return Success
    }

    state "Flush Decision" as FLUSH {
        Acknowledged --> CheckThreshold: Background Check
        CheckThreshold --> Buffered: Below 64MB
        CheckThreshold --> Flushing: Above 64MB
    }

    state "Flush Process" as FLUSHPROC {
        Flushing --> Sorting: Sort by ID
        Sorting --> Building: Build Bloom + Index
        Building --> Compressing: Compress ProximaBlocks
        Compressing --> Staging: Write to staging/
        Staging --> Atomics: Atomic rename
        Atomics --> Manifested: Update manifest
    }

    Manifested --> [*]: Flush Complete

    note right of WALWritten
        Write returns BEFORE flush
        WAL ensures durability
    end note

    note right of Staging
        Staging prevents
        partial file visibility
    end note
----

=== Read Path Activity Diagram

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
sequenceDiagram
    participant C as Client
    participant E as SstEngine
    participant B as BloomFilter
    participant I as IndexBlock
    participant D as DataBlock
    participant DC as DistanceCompute

    C->>E: Search(query, top_k=10)

    Note over E: Stage 1: File Selection
    loop Each SSTable
        E->>B: might_contain(query.id)
        alt Bloom says NO
            B-->>E: Skip file
        else Bloom says MAYBE
            E->>E: Add to candidate files
        end
    end

    Note over E: Stage 2: Block Selection
    loop Each Candidate File
        E->>I: Check zone maps
        alt Range mismatch
            I-->>E: Skip block
        else Range overlap
            E->>E: Add to candidate blocks
        end
    end

    Note over E: Stage 3: Row Filtering
    loop Each Candidate Block
        E->>D: Decompress block
        D->>D: SIMD predicate eval
        D-->>E: Filtered candidates
    end

    Note over E: Distance Computation
    E->>DC: Compute distances (500 candidates)
    DC-->>E: Sorted by distance

    E-->>C: Top-K results
----

== File Format Design

=== Why Hybrid Columnar?

**Pure row format** (PostgreSQL): Each vector stored contiguously. Good for point lookups, poor for batch operations.

**Pure columnar** (Parquet): Each dimension stored separately. Good for analytics, poor for reconstructing vectors.

**SST's hybrid approach**: Metadata columnar (for filtering), vectors grouped (for SIMD).

[source,text]
----
┌─────────────────────────────────────────────────────────┐
│ ProximaBlock (Hybrid Columnar)                          │
├─────────────────────────────────────────────────────────┤
│ Columnar Metadata (for filtering):                      │
│   ids[]      → String column, Zstd compressed          │
│   timestamps[]→ i64 column, Delta + LZ4                │
│   metadata[] → Map column, Zstd compressed             │
├─────────────────────────────────────────────────────────┤
│ Grouped Vectors (for SIMD distance):                    │
│   group_0[]  → dims 0-31, all vectors, LZ4             │
│   group_1[]  → dims 32-63, all vectors, LZ4            │
│   ...                                                   │
│   group_23[] → dims 736-767, all vectors, LZ4          │
├─────────────────────────────────────────────────────────┤
│ Block Bloom Filter: 10KB, 1% FPR                        │
└─────────────────────────────────────────────────────────┘

Why grouped vectors?
- 32-dim groups align with AVX2 (8 floats) and AVX-512 (16 floats)
- Distance computation processes groups sequentially
- Better cache utilization than pure columnar
----

=== SSTable Structure

[source,text]
----
┌──────────────────────────────────────────────┐
│ Header (128 bytes)                           │
│   Magic: "SST1", Version: 2                  │
│   Compression, Encoding, Dimensions          │
├──────────────────────────────────────────────┤
│ Data Blocks (ProximaBlocks)                  │
│   Block 0: vectors 0-999, compressed         │
│   Block 1: vectors 1000-1999, compressed     │
│   ...                                        │
├──────────────────────────────────────────────┤
│ Index Block                                  │
│   Per-block: offset, size, count             │
│   Zone maps: id_range, timestamp_range       │
│   Metadata ranges: {field: (min, max)}       │
├──────────────────────────────────────────────┤
│ Footer (128 bytes)                           │
│   Index offset, checksum, magic              │
└──────────────────────────────────────────────┘

Design rationale:
- Index at END enables streaming writes
- Footer magic verifies file integrity
- Zone maps enable Stage 2 pruning
----

== Compaction Strategy

=== Why Two-Phase Compaction?

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
graph TB
    subgraph L1["Level 1: Tiered Compaction"]
        A1[2MB file]
        A2[2MB file]
        A3[2MB file]
        A4[...10 files]
    end

    subgraph L2["Level 2+: Leveled Compaction"]
        B1[20MB file]
        B2[20MB file]
    end

    L1 -->|"Merge when >10 files<br/>(reduce file count)"| L2

    note1[/"L1: Tiered<br/>- Accept overlapping ranges<br/>- Fast writes<br/>- Higher read amp"/]
    note2[/"L2+: Leveled<br/>- Non-overlapping ranges<br/>- Lower read amp<br/>- Higher write amp"/]

    style L1 fill:#ffd966,stroke:#cc9900
    style L2 fill:#93c47d,stroke:#5a8047
----

**Tiered (L1)**: Accept some read amplification for fast writes. Multiple overlapping files merged on compaction trigger.

**Leveled (L2+)**: Ensure non-overlapping key ranges. Point queries touch exactly one file per level.

== Configuration Guide

=== Tuning for Write-Heavy Workloads

[source,toml]
----
[storage.sst]
# Larger buffer = fewer flushes = higher throughput
flush_threshold_mb = 128

# More threads for parallel flush
flush_threads = 8

# Tiered compaction favors writes
compaction_strategy = "tiered"

# Delay compaction for burst writes
l1_max_files = 20
----

=== Tuning for Read-Heavy Workloads

[source,toml]
----
[storage.sst]
# Smaller buffer = fresher data visible
flush_threshold_mb = 32

# Leveled compaction reduces read amp
compaction_strategy = "leveled"

# Aggressive compaction
l1_max_files = 4

# Larger cache for hot blocks
decompression_cache_mb = 512
----

=== Key Health Indicators

| Metric | Healthy Range | Action if Unhealthy

| `stage1_elimination_pct` | >85% | Check bloom filter FPR, add more selective filters
| `stage2_elimination_pct` | >70% | Check zone map coverage, verify metadata indexed
| `cache_hit_rate` | >80% | Increase cache size or reduce working set
| `compaction_lag_seconds` | <60s | Increase compaction threads

== Summary: SST Design Principles

1. **Sequential writes via LSM-tree** - Maximize disk throughput, accept read amplification
2. **Three-stage progressive filtering** - Eliminate 99%+ candidates before expensive distance computation
3. **Hybrid columnar format** - Columnar metadata for filtering, grouped vectors for SIMD
4. **Per-block bloom filters** - O(1) negative lookups eliminate entire blocks
5. **Two-phase compaction** - Tiered for hot data, leveled for cold data
