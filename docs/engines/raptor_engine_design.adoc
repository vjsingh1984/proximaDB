== Executive Summary

RAPTOR (Row-Aligned Predicated Tensor Optimized Repository) is a hybrid storage engine featuring *smart row group sizing*, *hybrid row-columnar architecture*, *semantic accuracy optimization*, and *integrated HNSW graph building during flush/compact operations*.

=== Key Architectural Insight

RAPTOR builds HNSW graphs during flush and compaction for storage locality optimization, while AXIS provides optional additional indexing via EventLog. This separation ensures:

* **Storage Locality**: HNSW graphs are built and stored in RAPTOR format for cache efficiency
* **Optional Indexing**: AXIS only processes collections with configured indexes
* **Non-blocking Compaction**: Collections without indexes don't block on index building
* **Smart Parameters**: HNSW parameters (m, ef_construction) are dynamically selected based on actual data

pub async fn lookup_ids_after_hnsw(
    hnsw_results: Vec<String>,  // IDs from HNSW top-k
    row_groups: &[RowGroupMetadata],
) -> Vec<VectorRecord> {
    // Step 1: Check bloom filters (parallel)
    let candidate_rgs = row_groups.par_iter()
        .filter(|rg| {
            hnsw_results.iter().any(|id| rg.bloom_filter.might_contain(id))
        })

    // Step 2: Scan ID columns in candidate row groups

            id_column.find_ids(&hnsw_results)
        })
        .collect::<Vec<_>>();
    
    // Step 3: Load full records
    load_full_records(found_records).await

=== Optimized Memory-Efficient HNSW Writer Design

==== Current Implementation Analysis

The current implementation stores in `HnswNode`:
- `node_id`: 4 bytes
- `row_location`: 4 bytes (page_id + offset)
- `quantized_vector`: Variable (96 bytes for PQ8, 768 bytes for INT8, 3KB for FP32)
- `edges`: Vec<(u32, f32)> - neighbors with distances

**Memory Issue**: Even with quantization, storing vectors in memory during graph building is expensive.

=== HNSW Integration Strategy

==== Build-Time HNSW Graph Construction

RAPTOR builds HNSW graphs during flush and compaction operations, not during runtime search. This approach optimizes for:

1. **Storage Locality**: Neighboring nodes in the graph are stored together
2. **Memory Efficiency**: Graphs are built transiently, then stored on disk
3. **Adaptive Parameters**: m and ef_construction are selected based on actual data characteristics

==== Smart HNSW Parameter Selection

The HNSW parameters `m` (max connections per node) and `ef_construction` (build-time beam width) are critical for recall optimization. RAPTOR dynamically selects these based on:

/// Smart HNSW parameter calculation based on collection characteristics
pub fn calculate_optimal_hnsw_params(
    num_vectors: usize,
    dimension: usize,
    available_memory_gb: usize
) -> (u32, u32, u32) {
    // Memory estimation per vector (dimension * 4 bytes + metadata overhead)
    let bytes_per_vector = dimension * 4 + 100;
    let total_memory_needed_gb = (num_vectors * bytes_per_vector) / (1024 * 1024 * 1024);
    
    // Select parameters based on dataset size and memory pressure
    let (m, ef_construction, max_level) = match num_vectors {
        // Small collections (<1K vectors): Maximum connectivity for perfect recall
        0..=1000 => {
            // m=48: Each node connects to up to 48 others (near-complete graph)
            // ef=500: Search 500 candidates during construction (exhaustive)
            // Reasoning: Small datasets can afford maximum connectivity
            (48, 500, 4)
        },
        
        // Medium collections (1K-10K vectors): Balanced approach
        1001..=10000 => {
            // m=32: Good connectivity without excessive memory
            // ef=400: High quality construction
            // Reasoning: Balance between recall and memory usage
            (32, 400, 5)
        },
        
        // Large collections (10K-100K vectors): Memory-aware
        10001..=100000 => {
            // m=24: Moderate connectivity to control memory
            // ef=300: Good construction quality
            // Reasoning: Start optimizing for memory efficiency
            (24, 300, 6)
        },
        
        // Very large collections (100K-1M vectors): Memory-optimized
        100001..=1000000 => {
            // Check memory pressure
            if total_memory_needed_gb < available_memory_gb / 2 {
                // Plenty of memory: Use standard parameters
                (16, 200, 7)
            } else {
                // Memory pressure: Reduce connectivity
                (12, 150, 7)
            }
        },
        
        // Massive collections (>1M vectors): Aggressive memory optimization
        _ => {
            // Ultra-large scale requires careful memory management
            let memory_pressure_factor = total_memory_needed_gb / available_memory_gb;
            
            if memory_pressure_factor < 1 {
                // Can fit in memory: Standard parameters
                (16, 200, 8)
            } else if memory_pressure_factor < 2 {
                // Tight fit: Reduce parameters
                (12, 150, 8)
            } else {
                // Doesn't fit: Minimum viable parameters
                (8, 100, 8)
            }
        }
    };
    
    (m, ef_construction, max_level)
}

* **HNSW Reality**: Row groups contain semantically similar vectors with random IDs
* **B-tree Overhead**: 40-60MB index for scattered IDs with no range query benefit
* **Bloom Solution**: 180KB total for 1M vectors, perfect for membership testing

=== 3. Hybrid Row Group + Columnar Architecture

==== The Three-Level Design

RAPTOR combines bloom filters with columnar storage for HNSW-organized data:

**Level 1: Per-RowGroup Bloom Filters** (Fast membership testing)
----
RowGroup 0 Bloom (180 bits) → Skip or Scan decision
RowGroup 1 Bloom (180 bits) → Skip or Scan decision
...
----

**Level 2: Smart Row Groups** (HNSW locality, not ID locality)
----
Row Group 0: [600-2600 vectors] -> Cloud-optimized I/O (1-4MB)
Row Group 1: [dimension-aware]  -> Semantic accuracy optimized
Row Group 2: [query-pattern]    -> High/medium/low selectivity tuned
----

**Level 3: Columnar Within Groups** (FastLanes + SIMD efficiency)
----
Within Row Group 0 (using TransposedVectors):
  Encoding Marker: 0xA1              // FastLanes tensor encoding
  ID Column:       [id_0, id_1, ...]  // Variable length with fixed offsets
  Dimensions[0]:   [v0_d0, v1_d0, ...] // Per-dimension FastLanes encoding
  Dimensions[1]:   [v0_d1, v1_d1, ...] // Chosen optimal scheme per dim
  ...
  Dimensions[d-1]: [v0_dd, v1_dd, ...] // Independent compression
  Metadata:        String/numeric/boolean column families
  
  Quantized Data:  // Progressive search support
    Binary:        [1-bit approximation]
    INT8:          [8-bit quantization]  
    PQ:            [4-8 bit product quantization]
    FP32:          [Full precision for reranking]
----

==== Why This Architecture Works

**Problem with Pure Row Storage:**
- Vectors stored sequentially: [vec0, vec1, vec2, ...]
- To get dimension 0 of all vectors: Must parse through entire dataset
- FastLanes can't work on non-contiguous data

**Problem with Pure Columnar:**
- HNSW neighbors scattered across different I/O units
- Loading 1000 vectors requires 1000 separate reads
- Destroys graph locality benefits

**RAPTOR's Hybrid Solution:**
- Row groups preserve HNSW locality (neighbors stay together)
- Columnar within groups enables SIMD (contiguous dimension arrays)
- Single I/O loads all data needed for local graph traversal

    participant FS as Zero-Copy FS
    participant S3
    
    Query->>Cache: get_rowgroups([1,3,7])
    Cache->>Cache: Check memory (4GB LRU)
    
    alt Cache Hit
        Cache-->>Query: Return cached
    else Cache Miss
        Cache->>Meta: Get file metadata
        Meta-->>Cache: RowGroup offsets
        Cache->>Cache: Optimize read strategy
        
        alt Individual (1-2 RGs)
            Cache->>FS: Range reads
        else Coalesced (adjacent)
            Cache->>FS: Single read
        else Many (>50%)
            Cache->>FS: Full file
        end
        
        FS->>S3: Optimized I/O
        S3-->>Cache: Data
        Cache-->>Query: RowGroups
    end
----

pub enum ReadStrategy {
    Individual,     // 1-2 non-adjacent RGs
    Coalesced {     // Adjacent RGs within 1MB gap
        ranges: Vec<(u64, u64, Vec<u32>)>,
    },
    FullFile,       // >50% RGs needed
}

impl RowGroupCacheManager {
    fn optimize_read_strategy(&self, missing_ids: &[u32]) -> ReadStrategy {
        let missing_ratio = missing_ids.len() as f32 / total_rgs as f32;
        
        if missing_ratio > 0.5 {
            return ReadStrategy::FullFile;
        }
        
        // Coalesce adjacent RGs with <1MB gaps
        let ranges = self.coalesce_adjacent(missing_ids);
        
        if ranges.len() > 10 {
            return ReadStrategy::FullFile;
        }
        
        ReadStrategy::Coalesced { ranges }
    }
}

pub async fn reorganize_by_hnsw_locality(
    &self,
    vectors: Vec<VectorRecord>,
    hnsw_graph: &HnswGraph,
) -> Result<Vec<RowGroup>> {
    let mut row_groups = Vec::new();
    let adjacency = self.build_adjacency_map(hnsw_graph);
    
    // BFS traversal for locality
    for entry_point in &hnsw_graph.entry_points {
        let mut current_group = Vec::new();
        let mut queue = vec![entry_point];
        
        while let Some(node) = queue.pop() {
            current_group.push(vectors[node]);
            
            // Start new group at 1K vectors
            if current_group.len() >= 1000 {
                row_groups.push(RowGroup::from(current_group));
                current_group = Vec::new();
            }
            
            // Add neighbors for locality
            queue.extend(adjacency.get(node));
        }
    }
    
    Ok(row_groups)
}

==== Columnar SIMD Operations

[source,rust]
----
impl HybridRaptorReader {
    /// Efficient distance computation using columnar layout
    fn compute_distances_columnar(
        &self, 
        query: &[f32], 
        rowgroup: &HybridRowGroup
    ) -> Vec<f32> {
        let dimension_count = query.len();
        let vector_count = rowgroup.vector_count;
        let mut distances = vec![0.0f32; vector_count];
        
        // Process each dimension using SIMD
        for (dim_idx, &query_dim) in query.iter().enumerate() {
            let dim_column = &rowgroup.columns.vector_columns.dimensions[dim_idx];
            
            // Decode dimension values (FastLanes → f32 array)
            let dim_values = self.fastlanes_decoder.decode_f32(
                &dim_column.encoded_data,
                dim_column.encoding,
                vector_count
            )?;
            
            // SIMD compute: (query_dim - vector_dim)²
            let squared_diffs = self.simd_squared_diff(query_dim, &dim_values);
            
            // Accumulate into distance array
            self.simd_accumulate(&mut distances, &squared_diffs);
        }
        
        // Final square root for Euclidean distance
        self.simd_sqrt(&mut distances);
        
        distances
    }
    
    /// Hardware-specific SIMD implementations
    fn simd_squared_diff(&self, query_val: f32, column_vals: &[f32]) -> Vec<f32> {
        let hardware = HardwareCapabilities::get();
        
        match hardware {
            _ if hardware.has_avx512() => {
                // Process 16 f32 values at once
                self.avx512_squared_diff(query_val, column_vals)
            },
            _ if hardware.has_avx2() => {
                // Process 8 f32 values at once
                self.avx2_squared_diff(query_val, column_vals)
            },
            _ => self.scalar_squared_diff(query_val, column_vals),
        }
    }
}
