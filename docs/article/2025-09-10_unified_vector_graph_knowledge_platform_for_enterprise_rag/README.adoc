== The ProximaDB Difference: Unified Intelligence

ProximaDB is not just another vector database. It's a comprehensive platform for building enterprise-grade AI applications.

*   **Unified Engine:** Go beyond simple vector similarity. ProximaDB combines vector search with graph traversal and a Semantic Knowledge Store (SKS) in a single, high-performance engine.
*   **SQL-First Approach:** Leverage your existing skills. Query vectors, metadata, and relationships using familiar SQL, supercharged with extensions for hybrid intelligence.
*   **Accelerated Performance:** Don't compromise on speed. ProximaDB is built in Rust and features progressive search, SIMD optimizations, and smart pruning to reduce latency and cost.
*   **Operational Simplicity:** Deploy anywhere, effortlessly. ProximaDB offers serverless deployment patterns, multicloud portability, and built-in observability for easy management.

== Key Capabilities

*   **Vector Search at Scale:** Advanced filtering, hybrid fusion (e.g., Reciprocal Rank Fusion), and pluggable storage backends.
*   **Native Graph Analytics:** Perform complex graph operations like pathfinding, neighborhood analysis, and streaming traversals.
*   **Semantic Knowledge Store:** Enrich your data with entities, provenance, and temporal context for more trustworthy and accurate answers.
*   **One API Surface:** Interact with ProximaDB through a unified API supporting REST and gRPC with typed results.

== Spotlight Use Case: Enterprise RAG You Can Trust

**Challenge:** A global services company needs to answer internal questions from over 100,000 documents across various departments. Pure vector search returns plausible but often incomplete or inaccurate answers. Traditional knowledge graphs are too slow to build and maintain at this scale.

**Solution with ProximaDB:**

1.  **Ingest & Enrich:** Documents are ingested as entities into the Semantic Knowledge Store (SKS) with embeddings and rich metadata (e.g., department, version, effective dates).
2.  **Connect the Dots:** Relationships between documents (e.g., dependencies, ownership, policy lineage) are captured in the native graph engine.
3.  **Query with Confidence:** A single SQL query is all it takes to:
    *   Find semantically similar passages using vector search.
    *   Traverse the graph to discover authoritative sources and owners.
    *   Apply temporal and provenance filters to ensure the information is current and reliable.
    *   Fuse the results into a compact, cited context window.

**Outcome:**

*   **Higher Accuracy & Explainability:** Answers are not just accurate, they're also explainable, with clear citations to sources and owners.
*   **Lower Latency & Cost:** A unified system means lower operational overhead and faster query performance compared to multi-system stacks.
*   **Simplified Operations:** A single data plane to operate and secure across multiple clouds.

== Cross-Collection Retrieval (Docs + Media)

[source,sql]
----
-- Search in two collections (docs + media), then follow graph
WITH candidates AS (
  SELECT id AS item_id, 'docs' AS source, _similarity
  FROM docs
  WHERE SIMILAR(embedding, $query_vec, 'cosine')
    AND department = $dept
  LIMIT 20

  UNION ALL

  SELECT id AS item_id, 'media' AS source, _similarity
  FROM media
  WHERE SIMILAR(embedding, $query_vec, 'cosine')
    AND media_type IN ('image','video')
  LIMIT 20
)
SELECT g.title, g.url, g.owner, c.source
FROM candidates c
JOIN FOLLOW(c.item_id, 'references', 2) AS g ON g.seed_id = c.item_id
ORDER BY _similarity DESC
LIMIT 10;
----

Notes:

* The engine applies hybrid fusion (e.g., RRF/Adaptive) over multi‑collection candidates.
* Graph expansion adds authority and context; apply temporal/provenance filters as needed.

== Example Conceptual SQL

[source,sql]
----
SELECT
    passage,
    source_url,
    owner
FROM
    docs
WHERE
    SIMILAR(embedding, $query_vec, 'cosine')
AND
    FOLLOW(doc_id, 'references', 2)
AND
    temporal.valid_from <= NOW()
ORDER BY
    _similarity DESC
LIMIT 8;
----
