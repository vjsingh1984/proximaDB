**ProximaDB implements a sophisticated multi-tier caching system with a global `CrossCacheOrchestrator` for coordinating multiple specialized caches.**

toc::[]

== Executive Summary

ProximaDB's caching system provides intelligent memory management across 11 distinct cache types, with automatic eviction, warming, and rebalancing services. The architecture supports multi-tenant isolation, hardware-accelerated operations, and configurable policies for optimal performance.

[NOTE]
====
All critical issues have been resolved as of Phase 5 completion. The cache system now features:
* ✅ Dedicated VectorCache implementation
* ✅ Automatic eviction and memory management
* ✅ Configurable policies via `config.toml`
* ✅ Unified metrics collection
====

=== Specialized Cache Implementations

==== VectorCache

[IMPORTANT]
====
VectorCache was newly implemented in Phase 1 to resolve type mismatch issues where storage engines incorrectly used QueryCache for individual vectors.
====

.VectorCache Specifications
[cols="1,3"]
|===
|Property |Description

|**Location**
|`src/storage/cache/specialized/vector_cache.rs`

|**Key Type**
|`VectorCacheKey` (string wrapper)

|**Value Type**
|`CachedVector` (VectorRecord, cached_at, access_count)

|**Key Format**
|`"vector:{collection_id}:{vector_id}"`

|**Backend**
|`BaseCacheImpl` with memory backend
|===

=== Rebalancing Service

The memory rebalancer runs every 5 minutes to optimize allocation based on actual usage patterns:

[source,rust]
----
// Automatic rebalancing based on hit rates
if cache_stats.hit_rate > 0.8 && cache_stats.memory_usage > 0.9 {
    // Increase allocation for high-performing cache
    allocator.increase_budget(cache_type, 10);
} else if cache_stats.hit_rate < 0.2 {
    // Reduce allocation for underutilized cache
    allocator.decrease_budget(cache_type, 10);
}
----

=== Implementation Example

[source,rust]
----
// Standardized cache integration across all engines
let cache_key = format!("vector:{}:{}", collection_id, vector_id);
if let Some(orchestrator) = CrossCacheOrchestrator::global() {
    if let Some(vector_cache) = orchestrator.get_vector_cache() {
        // Check cache first
        if let Some(cached_vector) = vector_cache.get(&cache_key).await {
            return Ok(Some(cached_vector));
        }

        // Load from storage if not cached
        let vector = self.load_from_storage(vector_id).await?;

        // Cache for future use
        vector_cache.put(cache_key, vector.clone()).await;
        return Ok(Some(vector));
    }
}
----

== Best Practices

=== Cache Warming Guidelines

[WARNING]
====
Cache warming is **disabled by default** for resource efficiency. Only enable for predictable workloads with stable access patterns.
====

.When to Enable Cache Warming
[cols="2,3"]
|===
|Scenario |Recommendation

|**Stable Workloads**
|Enable with popularity-based strategy

|**Known Hot Data**
|Enable with explicit item list

|**After Pattern Analysis**
|Enable with correlation-based prefetch

|**Development/Testing**
|Keep disabled to test cold-start performance
|===

== Conclusion

ProximaDB's cache architecture provides a robust, scalable foundation for high-performance vector operations. With all critical issues resolved and comprehensive configuration options available, the system delivers:

* **Intelligent memory management** with automatic rebalancing
* **Multiple eviction policies** for different workload patterns
* **Type-safe cache implementations** for all data types
* **Unified metrics and monitoring** for operational visibility
* **Full configurability** without code changes

The architecture is production-ready and designed for future enhancements including distributed caching and advanced prefetching algorithms.
