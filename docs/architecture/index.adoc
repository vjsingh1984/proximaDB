== Overview

ProximaDB is a high-performance vector database with zero infrastructure tax, designed for sub-millisecond search at scale. It is built in Rust and features a modern, asynchronous, and modular architecture.

=== Service Layer
The service layer contains the core business logic of the database.

- *VectorOperationsService*: Handles all CRUD (Create, Read, Update, Delete) operations for vectors, as well as search coordination.
- *CollectionService*: Manages the lifecycle of collections, including creation, deletion, and schema management.
- *EventLogService*: Provides a log of all events in the system, which can be used for auditing and recovery.

=== Storage Layer
The storage layer is responsible for persisting data to disk. It is designed to be highly performant and scalable.

- *StorageEngine*: The main component of the storage layer. It manages the different storage engines and provides a unified interface for accessing data.
- *MemTable*: An in-memory table that stores recently written data.
- *Write-Ahead Log (WAL)*: A log that records all write operations before they are applied to the database. This ensures data durability in case of a crash.
- *Metadata Store*: Stores all the metadata about collections, indexes, and other system components.

== Key Design Decisions

=== Proto-First Architecture
ProximaDB uses a "proto-first" architecture, where all data structures and APIs are defined in Protocol Buffers. This has several advantages:
- *Zero-copy serialization*: Data can be passed between components without the need for expensive serialization and deserialization.
- *Type safety*: The protobuf compiler generates type-safe code in multiple languages.
- *Efficient wire format*: Protocol Buffers provide a compact and efficient wire format for gRPC.

=== Pluggable Storage Engines
ProximaDB has a pluggable storage engine architecture, which allows for different storage engines to be used for different workloads. The two main storage engines are:
- *SST*: Optimized for real-time OLTP workloads.
- *VIPER*: Optimized for analytical OLAP workloads.
The `StorageEngine` component automatically selects the best engine based on the workload.

=== Hardware-Adaptive Compute
The compute layer is designed to be hardware-adaptive. It can automatically detect and use the best available hardware for a given task, whether it's SIMD instructions on the CPU or a dedicated GPU. This allows ProximaDB to achieve the best possible performance on a wide range of hardware.

== Deployment Architecture

=== Single Server
[source,yaml]
----
# docker-compose.yml
services:
  proximadb:
    image: proximadb/proximadb:latest
    ports:
      - "5678:5678"  # REST
      - "5679:5679"  # gRPC
    volumes:
      - data:/data
----

=== High Availability
- Active-passive failover
- Shared storage backend (S3/Azure/GCS)
- Metadata replication

=== Scaling Strategy
- Vertical: Up to 1TB RAM, 128 cores
- Horizontal: Sharding by collection
- Tiering: Hot/warm/cold data separation

== Configuration

Key configuration in `config/config.toml`:

[source,toml]
----
[server]
http_port = 5678
grpc_port = 5679

[storage]
default_engine = "sst"  # or "viper"
data_dir = "/data"

[compute]
enable_gpu = true
enable_simd = true

[cache]
total_memory_mb = 4096
----
