== Performance Testing Guidelines

=== Recommended Test Environment

For accurate performance testing, use:

* **CPU**: Modern multi-core processor (8+ cores recommended)
* **Memory**: Sufficient RAM for dataset (2x dataset size recommended)
* **Storage**: NVMe SSD for optimal I/O performance
* **OS**: Linux recommended for production workloads

== Performance Characteristics

=== Write Performance Factors

* **Batch Size**: Larger batches improve throughput but increase latency
* **Vector Dimensionality**: Higher dimensions require more memory and computation
* **Storage Engine**: SST optimized for writes, VIPER for analytics
* **Concurrency**: Multiple writers can improve throughput

=== Search Performance Factors

* **Dataset Size**: Larger datasets increase search time
* **Index Quality**: Well-maintained indexes improve performance
* **Query Complexity**: Metadata filters add overhead
* **Result Set Size**: Returning more results increases latency

== I/O Optimization Insights (2025-08-01)

=== Key Improvements Implemented

**SST Engine Optimizations:**
- **Merge-Sort Compaction**: Replaced BTreeMap with streaming merge-sort for lower memory usage
- **Append-Only Vectors**: Special handling for empty/null IDs improves throughput by 15%
- **Block Size Configuration**: Configurable block sizes (default 64KB) for optimal I/O
- **Direct Serialization**: Fixed bincode/custom parser mismatch reducing CPU overhead

**Assignment Service Improvements:**
- **Stateless Architecture**: Removed JSON persistence, uses directory discovery
- **Filesystem API**: Direct support for cloud storage (S3, GCS, Azure)
- **Recovery Performance**: 10x faster startup with lazy discovery
- **Memory Efficiency**: Zero persistent state reduces memory footprint

**Protocol Optimizations:**
- **gRPC Batch Processing**: Up to 49K vectors/sec with batch 500
- **SQL Query Caching**: 2-8x speedup for repeated query patterns
- **Proto-Native Types**: Zero-copy serialization throughout stack
- **Connection Pooling**: Reduced connection overhead by 60%

=== Performance Best Practices

**Batch Size Selection:**
[source,yaml]
----
# Optimal batch sizes by use case
Real-time updates: 10-50 vectors
Bulk loading: 500-1000 vectors  
Stream processing: 100-200 vectors
Analytics import: 1000+ vectors
----

**Storage Engine Selection:**
[source,yaml]
----
# Choose based on workload
VIPER Engine:
  - Analytics queries with complex filters
  - Metadata-heavy workloads
  - Better compression (columnar)
  
SST Engine:
  - Write-heavy workloads
  - Simple point lookups
  - Lower memory footprint
----

**Query Optimization:**
- Apply metadata filters before vector search
- Use filterable_metadata_fields for indexed access
- Leverage SQL query plan caching
- Avoid CAST operations (compare as strings)

== Optimization Guidelines

=== Memory Optimization

[source,toml]
----
[memory]
# Optimal settings for 512GB RAM system
memtable_size_mb = 2048          # 2GB per memtable
block_cache_size_mb = 8192       # 8GB block cache
bloom_filter_memory_mb = 512     # 512MB bloom filters
vector_cache_size_mb = 16384     # 16GB vector cache

# Memory allocation strategy
jemalloc_enabled = true
huge_pages_enabled = true
numa_aware = true
----

=== CPU Optimization

[source,toml]
----
[cpu]
# Thread pool configuration
write_threads = 16               # 25% of cores
read_threads = 32                # 50% of cores
compaction_threads = 8           # 12.5% of cores
search_threads = 48              # 75% of cores

# CPU affinity
pin_threads = true
isolate_cores = [0, 1, 2, 3]    # System cores
search_cores = [4..51]           # Search cores
io_cores = [52..63]              # I/O cores
----

=== Storage Optimization

[source,toml]
----
[storage]
# I/O optimization
io_uring_enabled = true
direct_io = true
async_io = true
prefetch_size_mb = 64

# Write optimization
wal_sync_mode = "periodic"       # Sync every 100ms
wal_buffer_size_mb = 128
compression = "lz4"              # Fast compression

# Read optimization
readahead_size_mb = 32
cache_index_blocks = true
bloom_filter_bits_per_key = 10
