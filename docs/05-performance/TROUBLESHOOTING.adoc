== Overview

This guide documents common issues encountered during benchmark execution and their resolutions, particularly focusing on the singleton engine architecture transition and path resolution issues.

== Singleton Engine Architecture Issues

=== Problem: Constructor Pattern Mismatch

The storage engines were refactored to use a **singleton pattern** (parameter-less constructors), but benchmarks may still attempt to use the old parametrized constructors.

==== Symptoms
* Compilation errors about wrong number of arguments
* Engines not finding data after flush operations
* Inconsistent search results

==== Key Changes

.Old Pattern
[source,rust]
----
// Old: Parametrized constructor
let engine = SstEngine::new(config, filesystem, distance_compute);
----

.New Pattern
[source,rust]
----
// New: Parameter-less constructor
let engine = SstEngine::new().await?;
// Configuration comes from FlushParameters and StorageQueryContext at runtime
----

==== Resolution

1. Update all engine initialization to use parameter-less constructors
2. Pass configuration through `FlushParameters` for write operations
3. Pass configuration through `StorageQueryContext` for read operations

== Path Resolution Issues

=== Problem: Collection-Specific Storage Paths

Singleton engines initialize with empty collection_id, causing path resolution issues between flush and search operations.

==== Root Cause

[source,rust]
----
// In SstEngine::new_with_config
let unified_fs = Arc::new(UnifiedCachingFilesystem::new(
    base_fs,
    String::new(), // Empty collection_id for singleton
    "sst".to_string(),
));
----

==== Impact
* Files written to unexpected locations
* Search operations not finding flushed data
* Directory cleanup failures after benchmarks

==== Solution

Ensure collection-specific paths are provided in operation parameters:

[source,rust]
----
let collection = Arc::new(Collection {
    storage_assignment: Some(StorageAssignment {
        primary_path: base_path.clone(),
        base_location: base_path.clone(),
        ..Default::default()
    }),
    ..Default::default()
});

// For flush operations
let params = FlushParameters {
    collection_id: Some(collection_id.clone()),
    collection_config: Some(collection),
    ..Default::default()
};

// For search operations
let ctx = StorageQueryContext {
    collection,
    ..Default::default()
};
----

== Search Result Accuracy Issues

=== Problem: Empty or Incorrect Results

All engines showing similar timing (~7.6-7.9μs) regardless of engine type, compression, or data size suggests engines are returning empty results.

==== Diagnostic Steps

1. **Validate Flush Operation**
+
[source,rust]
----
assert!(result.success, "Flush should succeed");
assert!(result.vectors_written > 0, "Vectors should be written");
assert!(result.bytes_written > 0, "Bytes should be written");
----

2. **Verify File Creation**
+
[source,rust]
----
let fs = filesystem_factory.get_filesystem(&format!("file://{}", base_path))?;
let files = fs.list(&base_path).await?;
assert!(!files.is_empty(), "Files should be created");
----

3. **Check Search Results**
+
[source,rust]
----
assert!(!results.results.is_empty(), "Search should return results");
assert!(results.results.len() <= top_k, "Result count should respect top_k");
----

== Metadata Filter Issues

=== Problem: Filters Not Applied

Metadata filters constructed correctly but not reducing result sets.

==== Verification

[source,rust]
----
// After filtered search
for result in &results.results {
    if let Some(category) = result.metadata.get("category") {
        assert_eq!(category, &expected_value, "Filter should be applied");
    }
}
----

==== Common Causes

1. Data not properly indexed with metadata
2. Filter expression syntax errors
3. Engine not loading metadata during search

== Compression Impact Analysis

=== Unexpected Performance Patterns

Some engines show **better** performance with compression, which may indicate:

1. **Cache Locality**: Compressed data fits better in CPU cache
2. **I/O Reduction**: Less data to read from disk
3. **Empty Results**: Not actually processing data

==== Validation

Compare compressed vs uncompressed file sizes:

[source,bash]
----
# Check actual compression achieved
du -sh /tmp/proximadb-bench/*/
----

Expected compression ratios:
* ZSTD: 3-4x
* LZ4: 2-3x
* Snappy: 2-3x
* GZIP: 3-5x

== Performance Validation

=== Suspicious Uniform Timing

When all engines show nearly identical performance:

[cols="2,2,3", options="header"]
|===
|Symptom |Possible Cause |Validation

|All ~7.6-7.9μs
|Early exit path
|Add logging in search path

|No variance with size
|Not loading data
|Check file I/O operations

|No compression impact
|Using cached empty results
|Clear caches between tests
|===

== Recommended Benchmark Validation

=== Complete Validation Checklist

[source,rust]
----
// 1. Validate flush
assert!(flush_result.success);
assert!(flush_result.vectors_written == expected_count);
assert!(flush_result.bytes_written > 0);

// 2. Validate files created
let files = fs.list(&base_path).await?;
assert!(files.len() > 0);

// 3. Validate search results
assert!(!search_results.results.is_empty());
assert!(search_results.results[0].score > 0.0);

// 4. Validate filter application
let filtered_count = search_results.results.iter()
    .filter(|r| matches_filter(r))
    .count();
assert_eq!(filtered_count, search_results.results.len());

// 5. Validate compression
let compressed_size = measure_directory_size(&base_path)?;
let ratio = uncompressed_size / compressed_size;
assert!(ratio > 1.5); // At least 1.5x compression
----

== Quick Fixes

=== Common Solutions

[cols="1,3", options="header"]
|===
|Issue |Fix

|Compilation errors
|Update to parameter-less constructors

|No data after flush
|Verify collection paths in parameters

|Empty search results
|Check collection config matches between flush and search

|Filters not working
|Ensure metadata is properly serialized

|Uniform performance
|Add result validation and logging
|===
