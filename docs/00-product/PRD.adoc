== Product Overview

=== Vision

ProximaDB v0.2.0 is *The Context Database* -- a unified engine purpose-built for the AI era that natively combines vectors, documents, graphs, time-series, and events in a single deployable binary. Rather than stitching together five specialized databases with brittle ETL pipelines, ProximaDB provides a single SQL-compatible query interface that can join across all data models in one query.

=== Positioning Statement

For AI/ML engineers, platform engineers, data engineers, and trading system developers who need to store and query contextual data across multiple modalities, ProximaDB is a unified multi-model database that eliminates the operational complexity of managing separate vector, document, graph, time-series, and event stores. Unlike Pinecone (vectors only), Neo4j (graphs only), or TimescaleDB (time-series only), ProximaDB provides cross-model SQL joins, embedded deployment, and sub-millisecond latency in a single Rust binary.

==== Hybrid Search (BM25 + Vector)

[cols="1,3", options="header"]
|===
| Field | Detail

| Feature
| Hybrid Search combining BM25 keyword search with vector similarity search

| User Story
| As a developer building RAG pipelines, I want to combine keyword and semantic search in a single query so that retrieval accuracy doubles compared to vector-only search, reducing hallucination rates in LLM applications.

| Acceptance Criteria
a|
* BM25 full-text index implemented via tantivy integration
* Reciprocal Rank Fusion (RRF) score combination with configurable `k` parameter
* Less than 20ms additional overhead compared to vector-only search at 10K documents
* SQL syntax: `SELECT * FROM HYBRID_SEARCH('collection', 'keyword query', '[0.1, 0.2, ...]', 10)`
* Automatic index creation for text fields when hybrid search is enabled
* Filter support combined with hybrid search
* Python SDK support via `client.hybrid_search(collection, text, vector, top_k)`

| Dependencies
| tantivy crate integration, Python SDK update, query engine extension

| Effort Estimate
| 2 months (1 month core + 2 weeks SDK + 2 weeks testing/polish)
|===

* Ingest rate: >100K bars/second sustained
* Compression ratio: >10:1 for typical OHLCV data

| Dependencies
| New storage engine module, query engine extension, WAL integration

| Effort Estimate
| 3-4 months (2 months engine + 1 month query integration + 1 month testing/optimization)

=== Won't Have (Now)

The following capabilities are explicitly out of scope for the foreseeable roadmap. They either conflict with ProximaDB's architecture, are better served by dedicated systems, or represent insufficient ROI for the engineering investment required.

* *Warehouse-Scale OLAP Replacement in v0.2* -- Use Snowflake, BigQuery, ClickHouse, or Databricks for warehouse-scale analytics today. ProximaDB's roadmap uses DataFusion plus Parquet/Iceberg publications for an owned OLAP/MPP path, but that is post-MVP.
* *Blockchain / Distributed Ledger* -- Cryptographic hash chaining in the event sourcing engine provides tamper evidence without the overhead of consensus-based distributed ledgers.
* *Real-Time ML Model Training* -- ProximaDB stores and serves data for ML; training belongs in dedicated frameworks (PyTorch, JAX). The integrated inference feature (P1) covers serving only.
* *Message Queue Functionality* -- Use Kafka, Redpanda, or NATS for message brokering. ProximaDB's CDC and streaming subscriptions provide change feeds, not general-purpose messaging.
* *General-Purpose RDBMS Replacement in v0.2* -- ProximaDB supports pgwire for the narrow SQL surface, but PostgreSQL-style OLTP with full MVCC transactions, FK/PK/unique/check enforcement, triggers, stored procedures, and cross-shard consistency is post-MVP. The storage/constraint foundation is tracked in TD-110.

=== ibkrtrading Integration Dependencies

The ibkrtrading dogfood application (algorithmic trading system at `/Users/vijaysingh/code/ibkrtrading`) currently uses three separate databases:

* *PostgreSQL* -- Historical OHLCV bars (requires Time-Series Engine)
* *SQLite* -- Application state and order management (requires Event Sourcing Engine)
* *JSONL files* -- Event logs at 119MB/day (requires Event Sourcing Engine)

Full database consolidation into ProximaDB embedded mode requires all three P0 features: Time-Series Engine, Event Sourcing Engine, and Hybrid Search (for semantic search over trade rationale and market commentary).
