This document defines the organization, canonical sources, and authoring conventions for ProximaDB documentation. Its goal is to reduce duplication, keep content aligned with the implementation, and make navigation obvious.

The `docs/09-roadmap` directory is authoritative for roadmap content and must not be edited as part of routine doc cleanup.
====

== Duplication Policy

- Single source per topic. When another doc needs the same content:
  - Link to the canonical doc using `link:path/to/doc.adoc[Title]`
  - If a small subset is needed, summarize and link back to the source.
- Design deep dives (technical/*, architecture/*) must not duplicate API shapes. Reference the API docs instead for endpoints, request/response formats, and stability notes.
- When implementation changes: update the canonical doc first, then adjust any dependent links.

== Alignment With Implementation

- API paths, request/response shapes, and supported operations must reflect the implemented clients and server.
- As of this revision, the Graph REST endpoints implemented are:
  - `POST /api/v1/graph/graphs/{graph_id}/nodes` with body `{ "node": { ... } }`
  - `POST /api/v1/graph/graphs/{graph_id}/edges` with body `{ "edge": { ... } }`
  - `POST /api/v1/graph/graphs/{graph_id}/traverse`
  - `POST /api/v1/graph/graphs/{graph_id}/query/nodes`
- Graph collection management endpoints exist for create/get/list/delete/stats under `/api/v1/graph/graphs`.
- Prefer including concrete examples that can be validated with the Python SDK (`clients/python/src/proximadb`), especially `unified_client.py` and `protocols/rest_sync.py`.

== Mermaid Diagrams

- Use standard fenced blocks and initialization:

  [source,mermaid]
  ----
  %%{init: {"theme": "neutral"}}%%
  graph LR
    A --> B
  ----

- Avoid custom themes or extra braces in the `init` directive.
- Keep diagrams descriptive but compact. Prefer one diagram per concept.

== Change Workflow

1. Update the canonical doc for the topic.
2. Remove or trim duplicated sections in secondary docs; replace with a link to the canonical source.
3. If an API changes, verify examples against the Python SDK or REST endpoints.
4. Keep `docs/09-roadmap` unchanged; cross-link to it for future items.
