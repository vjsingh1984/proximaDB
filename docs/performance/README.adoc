==== Interpretation & Insights

- Engine strengths by workload
  - ORION excels at point lookups and property scans (2.0–2.4M elem/s), and delivers consistently low traversal latency (BFS ~32µs / DFS ~40µs), reflecting fast in‑memory indexes and compact CSR structures.
  - QUASAR leads in edge insertion throughput at small/medium scales (128/1024) due to hot‑tier, in‑memory ingestion and deferred cold‑tier work; it also shows the lowest traversal latencies (BFS ~24µs, DFS ~33–34µs) when operating in hot tier.
  - PULSAR exhibits balanced edge throughput (≈200K elem/s) with predictable scaling and slightly higher traversal latency, consistent with sharded replication and cross‑shard coordination overheads.

- Scaling behavior
  - Node inserts scale roughly linearly; ORION retains the lead as batch size grows (4096), while QUASAR’s node insert throughput drops earlier due to hot‑tier thresholds and synchronous stats updates. Adjust tier limits and background tasks for sustained large‑batch performance.
  - Edge inserts: QUASAR dominates at 128/1024, but falls off at 4096, suggesting hot‑tier saturation or CSR update backpressure; consider batching CSR updates and tuning tier thresholds.

- Traversal characteristics
  - QUASAR’s BFS/DFS lead in these tests indicates better frontier management and cache locality in the hot tier. ORION remains competitive and very stable; PULSAR’s overhead tracks shard coordination.
  - For deep traversals or large graphs, prefer ORION/QUASAR with tuned CSR caches and partitioning; consider PULSAR for distributed workloads where consistency and replication are desired.

- Property queries
  - ORION’s property scans are ~4x of PULSAR/QUASAR in these runs, reflecting tighter in‑memory indexing and lower indirection. For heavy metadata scans, ORION is the default choice.

- Benchmark hygiene
  - Some benches reported "Unable to complete 30 samples"; increase measurement time or reduce sample count for CI stability on heavier inputs.
  - Plotters backend was used (gnuplot not found); results are unaffected, but enabling gnuplot improves chart rendering.

=== Performance Recommendations

**For High-Throughput Applications**:

- Prefer label-based queries over property filters when possible
- Use BFS for shallow traversals (depth ≤ 3)
- Edge creation is 2× faster than node creation - batch edges separately

**For Low-Latency Applications**:

- All query types deliver sub-millisecond latency
- Single-path algorithms (Dijkstra, A*) deliver sub-10μs latency
- Traversal operations complete in <20μs for moderate graphs

**Scaling Considerations**:

- Node/edge creation throughput stable at 75-140K elem/s
- Connected components analysis scales linearly
- For graphs >10K nodes, consider partitioning for parallel analysis

== Storage Engine Flush/Compaction (engine_performance_reporter)

This bench exercises end‑to‑end flush and (best‑effort) compaction for SST and VIPER using a self‑contained proto `Collection` (no external services).

Latest indicative numbers (128‑dim vectors, small batches; plotters backend):

- SST
  - Flush time: ~30–41 ms across sparsity 10/50/90% and compression none/zstd/lz4/snappy
  - Compaction time: ~0 ms in this configuration (compaction manager returns default metrics in current code path)
  - Reported compression ratio: 0.000 (placeholder computation; see notes)

- VIPER
  - Flush time: ~23–28 ms across sparsity and algorithms (consistently faster than SST in these runs)
  - Compaction time: ~68–81 ms (non‑zero; columnar compaction performs real work)
  - Reported compression ratio: 0.000 (placeholder computation; see notes)

Throughput summary from latest CSV (`target/benchmark_report_20251022_001615.csv`):

- SST
  - TotalVecsPerSec: ~24.0K → 31.3K (higher at 90% sparsity due to faster flush)
  - TotalMBps (uncompressed): ~73.9 → 96.0 MB/s
  - Algorithm choice (none/zstd/lz4/snappy) had marginal effect in this small‑batch setting

- VIPER
  - TotalVecsPerSec: ~34.2K → 42.7K (best at 90% sparsity); AvgBatchVecsPerSec ~40.0K–43.5K
  - TotalMBps (uncompressed): ~105.2 → 130.2 MB/s (zstd/lz4/none performed similarly on flush)
  - Compaction cost observed: ~68–78 ms after 5 batches of 1000 vectors (768D)

Notes and caveats:

- Compression ratio in this reporter is currently a placeholder (compressed_size == uncompressed_size). To produce meaningful ratios:
  - SST: sum actual `.sstable` file sizes from the temp directory after flush.
  - VIPER (Parquet): sum Parquet file sizes, or extract compressed vector column size from metadata and compute `1 − compressed/uncompressed` (as in the streaming writer stats).
- SST compaction path in this run reports 0 ms because the compaction manager returns a default `CompactionResult`. Once compaction orchestration is fully wired, expect non‑zero times reflecting input/output file counts.
- VIPER’s flush advantage reflects the Parquet writer’s efficient batched I/O. Compaction incurs expected overhead from row group merges/statistics.
 - Compression algorithms (zstd/lz4/snappy) showed little difference at this micro scale; with larger datasets and real compressed size accounting enabled, expect on‑disk MB/s and ratios to diverge meaningfully.

How to run:

```
cargo bench --bench engine_performance_reporter
# Comprehensive grid (writes CSV):
RUN_BENCHMARKS=true cargo run --release --bin comprehensive_engine_report
```

Recommendations:

- Enable real compression accounting in the reporter to compare algorithms (zstd/lz4/snappy) credibly.
- Calibrate `batch_count` and `vectors_per_batch` to match production volumes; flush/compaction scale with total bytes written and row group sizing.
- For VIPER, tune row group size and filterable columns to balance flush throughput vs. analytical read performance.

CSV columns (derived):

- Batches, VecsPerBatch, TotalVectors, Dimension
- UncompressedSizeB, CompressedSizeB, CompressionRatio, SavingsPercent
- TotalFlushMs, AvgFlushMs, CompactionMs
- InputFiles, OutputFiles, CompactionRatio
- TotalVecsPerSec, AvgBatchVecsPerSec, TotalMBps, AvgBatchMBps

Interpretation:

- TotalVecsPerSec vs AvgBatchVecsPerSec can diverge if compaction or coordination overheads amortize across multiple batches; compare both for holistic throughput.
- TotalMBps uses uncompressed bytes by default (dimension × 4 × vectors); for Parquet, prefer compressed byte accounting for on‑disk throughput once compression measurement is enabled.

Traversal & shortest paths:

- BFS/DFS timings in this bench are ms‑level (0–2ms for 1K, ~0–2ms for 5K), higher than the µs‑level timings from bench_17. This reflects end‑to‑end service overhead (async plumbing, allocations) rather than raw traversal kernel cost.

- QUASAR shows similar Dijkstra/A* timings at 5K (~85/84ms), implying the heuristic provides no advantage on this synthetic topology.

- Connected components cost grows (≈63–76ms → 1506–1897ms) as expected with increased nodes/edges. This aligns with near‑linear scaling in prior component scaling analysis.

Actionable guidance:

- Choose ORION for heavy property scans and consistent throughput at larger scales; expect strong A* on spatial/topology‑friendly graphs.
- Use QUASAR for hot‑tier edge ingestion and low‑latency traversals at small/medium scales; tune tier thresholds and CSR batching for larger batches.
- Use PULSAR for distributed robustness; anticipate slightly higher traversal latency from shard coordination.
