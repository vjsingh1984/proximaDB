= RAPTOR Storage Engine
:toc: left
:toclevels: 3
:icons: font

[abstract]
**Rapid Adaptive Precision Tensor Operations Runtime** - A hybrid storage engine combining row-aligned storage with HNSW indexing and bloom filter optimization for graph-based similarity search.

image::../assets/logos/raptor-engine-logo.svg[RAPTOR Engine Logo, 200, align="center"]

== Overview

The RAPTOR engine implements a unique Matrix Trinity architecture (P²+K²+P×K) that combines the benefits of row-based storage with graph-based HNSW indexing. By using bloom filters instead of B-trees for ID lookups, RAPTOR achieves 200x memory savings while maintaining O(1) lookup performance for up to 107 million vectors.

=== Key Features

* **Matrix Trinity Navigation**: P²+K²+P×K optimization for search
* **HNSW Integration**: Hierarchical graph-based similarity search
* **Bloom Filter Optimization**: 180KB vs 40-60MB for 1M vectors
* **Row-Aligned Storage**: Efficient for graph traversal
* **Adaptive Precision**: Dynamic quantization based on graph level
* **Memory Efficient**: Optimized for large-scale deployments

== Matrix Trinity Optimization

=== P² Matrix (Primary Centroids)

The P² matrix identifies primary cluster centers:

[source,rust]
----
pub struct P2Matrix {
    centroids: Vec<Vector>,      // 256 primary centroids
    radius: Vec<f32>,           // Cluster radius
    density: Vec<u32>,          // Points per cluster
}

impl P2Matrix {
    pub fn navigate(&self, query: &Vector) -> Vec<ClusterID> {
        // Find nearest P centroids
        let distances = self.compute_distances(query);
        let top_p = self.select_top_k(distances, self.p);
        
        // Return cluster IDs for HNSW entry
        top_p.iter()
            .map(|i| self.centroids[*i].cluster_id)
            .collect()
    }
}
----

=== K² Matrix (Secondary Clusters)

The K² matrix provides fine-grained clustering:

[source,rust]
----
pub struct K2Matrix {
    sub_clusters: HashMap<ClusterID, Vec<Vector>>,
    connections: HashMap<ClusterID, Vec<ClusterID>>,
}

impl K2Matrix {
    pub fn refine(&self, 
                  primary: Vec<ClusterID>,
                  query: &Vector) -> Vec<NodeID> {
        let mut candidates = Vec::new();
        
        for cluster_id in primary {
            let sub = &self.sub_clusters[&cluster_id];
            let nearest = self.find_nearest_k(sub, query);
            candidates.extend(nearest);
        }
        
        candidates
    }
}
----

=== P×K Cross-Product

The cross-product optimization:

[source,rust]
----
pub struct PKMatrix {
    cross_products: Array2<f32>,  // P×K dimensional
    lookup: HashMap<(P, K), Vec<NodeID>>,
}

impl PKMatrix {
    pub fn optimize(&self,
                    p_clusters: Vec<ClusterID>,
                    k_clusters: Vec<ClusterID>) -> Vec<NodeID> {
        let mut nodes = HashSet::new();
        
        for p in &p_clusters {
            for k in &k_clusters {
                if let Some(node_list) = self.lookup.get(&(*p, *k)) {
                    nodes.extend(node_list);
                }
            }
        }
        
        nodes.into_iter().collect()
    }
}

== Bloom Filter Implementation

=== Design Rationale

RAPTOR uses bloom filters instead of B-trees because:

1. **Memory Efficiency**: 180KB vs 40-60MB for 1M vectors
2. **O(1) Lookups**: Constant time vs O(log n)
3. **Cache Friendly**: Fits in L3 cache
4. **No Rebalancing**: No tree maintenance overhead

=== Implementation

[source,rust]
----
pub struct RaptorBloomFilter {
    filters: Vec<BloomFilter>,    // Sharded filters
    capacity: usize,              // Vectors per filter
    fpp: f64,                     // False positive probability
}

impl RaptorBloomFilter {
    pub fn new(expected: usize, fpp: f64) -> Self {
        // Calculate optimal parameters
        let num_bits = Self::optimal_bits(expected, fpp);
        let num_hashes = Self::optimal_hashes(num_bits, expected);
        
        // Create sharded filters for parallelism
        let num_shards = num_cpus::get();
        let filters = (0..num_shards)
            .map(|_| BloomFilter::new(num_bits / num_shards, num_hashes))
            .collect();
            
        Self {
            filters,
            capacity: expected,
            fpp,
        }
    }
    
    pub fn insert(&mut self, id: &str) {
        let shard = self.hash_to_shard(id);
        self.filters[shard].insert(id);
    }
    
    pub fn contains(&self, id: &str) -> bool {
        let shard = self.hash_to_shard(id);
        self.filters[shard].contains(id)
    }
}
----

== HNSW Integration

=== Graph Construction

[source,rust]
----
pub struct RaptorHNSW {
    graph: HNSWGraph,
    trinity: MatrixTrinity,
    bloom: RaptorBloomFilter,
}

impl RaptorHNSW {
    pub fn insert(&mut self, id: String, vector: Vector) {
        // Update bloom filter
        self.bloom.insert(&id);
        
        // Update Matrix Trinity
        let cluster = self.trinity.assign_cluster(&vector);
        self.trinity.update(cluster, &vector);
        
        // Insert into HNSW
        let level = self.select_level();
        self.graph.insert(id, vector, level);
        
        // Connect to neighbors
        self.connect_neighbors(id, level);
    }
    
    pub fn search(&self, query: &Vector, k: usize) -> Vec<SearchResult> {
        // Trinity navigation for entry points
        let entries = self.trinity.navigate(query);
        
        // HNSW search from entry points
        let candidates = self.graph.search_from_entries(
            query, 
            entries, 
            k * 2  // Over-fetch for filtering
        );
        
        // Filter and rank
        self.filter_and_rank(candidates, k)
    }
}

== Troubleshooting

=== Common Issues

==== Poor Recall
**Symptom**: Recall < 95%

**Causes**:
1. Low M parameter
2. Insufficient ef_search
3. Imbalanced Trinity

**Solutions**:
```toml
hnsw_m = 32
hnsw_ef_search = 200
p_dimension = 512
rebalance_interval = 10000
```

==== High Memory Usage
**Symptom**: Memory > 3GB per million vectors

**Solutions**:
1. Reduce M parameter
2. Enable quantization
3. Shard bloom filters

```toml
hnsw_m = 12
quantization = "int8"
bloom_filter_shards = 16
```

==== Slow Insertions
**Symptom**: Insert rate < 50K vec/s

**Solutions**:
1. Batch insertions
2. Async indexing
3. Reduce ef_construction

```toml
batch_size = 1000
async_indexing = true
hnsw_ef_construction = 100
```

== Best Practices

=== Data Preparation

1. **Normalize Vectors**: L2 normalization improves clustering
2. **Remove Outliers**: Improves Trinity balance
3. **Batch Operations**: Minimum 1000 vectors per batch
4. **Pre-cluster**: If possible, pre-sort by similarity

=== Index Maintenance

1. **Periodic Rebalancing**: Rebalance Trinity monthly
2. **Graph Optimization**: Prune weak connections
3. **Bloom Filter Sizing**: Plan for 2x expected growth
4. **Monitor Recall**: Track recall metrics continuously

=== Query Optimization

1. **Tune ef_search**: Balance speed vs recall
2. **Use Filters Early**: Apply metadata filters first
3. **Cache Entry Points**: Cache Trinity navigation
4. **Parallel Search**: Enable for large graphs
