= Dedicated Storage Engines for Document, Graph, and Observability
:toc: left
:toclevels: 3
:icons: font

== Overview

ProximaDB's existing storage engines (SST, HELIX, VIPER, NOVA) are all *vector storage engines* optimized for different workload profiles (OLTP, spatial, columnar analytics). None are designed for document, graph, or time-series/observability workloads.

This document designs three new LSM-based storage engines, each purpose-built for its data model using proven patterns from industry-standard systems.

[IMPORTANT]
====
**Design Principle**: All three engines share the same LSM-tree foundation (WAL -> MemTable -> Flush -> Compaction) that SST uses, but specialize the *on-disk format*, *MemTable structure*, *index types*, and *compaction strategy* for their data model.
====

== Architecture: Shared LSM Foundation

All three engines reuse ProximaDB's existing infrastructure:

[source,text]
----
                     Shared Infrastructure
     ┌─────────────────────────────────────────────────┐
     │  WriteAheadLogManager (existing)                │
     │  TransactionCoordinator (existing)              │
     │  UnifiedCachingFilesystem (existing)            │
     │  UnifiedStorageEngine trait (existing)           │
     └───────────────┬─────────────────────────────────┘
                     │
         ┌───────────┼───────────────┐
         ▼           ▼               ▼
    ┌─────────┐ ┌─────────┐   ┌──────────┐
    │  CEDAR  │ │  TITAN  │   │  CHRONO  │
    │  Docs   │ │  Graph  │   │  TSDB    │
    └─────────┘ └─────────┘   └──────────┘
----

**Engine naming**: CEDAR (Columnar Extensible Document Archive), TITAN (Traversal-Indexed Topology and Adjacency Network), CHRONO (Chronological Hierarchical Record and Observation store).

== Engine 1: CEDAR -- Document Storage Engine

=== Prior Art

[cols="1,2,3"]
|===
| System | Architecture | What We Take

| MongoDB (WiredTiger)
| B-tree + LSM hybrid, BSON format, document-level concurrency
| Document-level locking, secondary index patterns, BSON-like encoding

| CouchDB
| Append-only B-tree, MVCC, map-reduce views
| MVCC for document versioning, materialized views

| RethinkDB
| LSM-tree, changefeeds, JSON path indexes
| JSON path index design, real-time change notifications

| RocksDB (MyRocks)
| LSM-tree, prefix bloom filters, column families
| Column family separation of indexes vs data, prefix-based filtering
|===

=== Data Model

[source,text]
----
Document = {
    _id:       String (primary key, auto-generated UUID if absent)
    _rev:      u64    (MVCC revision counter)
    _ts:       u64    (last-modified timestamp ms)
    _ttl:      Option<u64> (expiry timestamp ms)
    body:      BSON   (arbitrary nested JSON, stored as BSON for efficiency)
}
----

=== MemTable Structure

[source,text]
----
CedarMemTable {
    // Primary data: ordered by (_id) for range scans
    documents: BTreeMap<DocumentId, VersionedDocument>

    // Secondary indexes (maintained in-memory, flushed alongside data)
    // Each index is a BTreeMap from extracted field value -> set of _ids
    indexes: HashMap<IndexName, BTreeMap<IndexKey, BTreeSet<DocumentId>>>

    // Approximate size tracking for flush trigger
    size_bytes: AtomicU64

    // Write lock per document (not per memtable) for concurrency
    locks: DashMap<DocumentId, ()>
}
----

**Flush trigger**: Same as SST -- size threshold (default 256MB for documents, smaller than SST's 512MB because documents are typically smaller than vectors).

=== On-Disk SSTable Format

[source,text]
----
CEDAR SSTable Layout:
┌──────────────────────────────┐
│  Header (64 bytes)           │ magic, version, doc_count, min_id, max_id
├──────────────────────────────┤
│  Bloom Filter                │ Key-level bloom (document _id)
│  (variable)                  │ 10 bits/key, same as SST
├──────────────────────────────┤
│  Data Blocks                 │ Documents sorted by _id
│  (multiple, 64KB each)       │ Each block: [doc_count:4][offsets:N*4][bson_data:...]
│                              │ BSON encoding (30-40% smaller than JSON)
│                              │ LZ4 block compression
├──────────────────────────────┤
│  Secondary Index Blocks      │ One block per index
│  (optional)                  │ Format: [field_value -> [doc_ids...]]
│                              │ Sorted by field value for merge-join
├──────────────────────────────┤
│  Block Index                 │ block_offset, min_id, max_id per block
├──────────────────────────────┤
│  Field Statistics            │ Per-field: type distribution, min/max,
│                              │ null count, cardinality estimate (HLL)
└──────────────────────────────┘
----

=== Index Types

[cols="1,2,2"]
|===
| Index Type | Use Case | Implementation

| Primary (_id)
| Point lookups, range scans
| B-tree in SSTable block index (same as SST)

| Secondary (field path)
| `WHERE $.status = 'active'`
| Inverted index: field_value -> doc_id list, stored in secondary index blocks

| Compound
| `WHERE $.category = 'x' AND $.price < 100`
| Concatenated key prefix (category + price) in single index

| JSON Path
| Nested field access `$.address.city`
| Flattened dot-notation keys in secondary index

| Text (optional)
| Full-text search within documents
| BM25 inverted index with term frequencies
|===

=== Compaction Strategy: Leveled with Document Dedup

Same leveled compaction as SST (L0 threshold=4, levels 0-6) with one addition:

**Document-level MVCC resolution during compaction**: When merging SSTables, if multiple versions of the same `_id` exist, keep only the latest `_rev` (unless the query requests historical versions). This is identical to how WiredTiger handles it.

**TTL cleanup during compaction**: Documents past their `_ttl` are dropped during merge, providing free garbage collection.

=== Query Path

[source,text]
----
Document Query Flow:
1. Check MemTable (BTreeMap lookup by _id or index scan)
2. Check block bloom filter (skip blocks that can't contain _id)
3. If secondary index query:
   a. Scan secondary index blocks across levels
   b. Intersect doc_id sets for AND conditions
   c. Fetch full documents by _id from data blocks
4. If full scan with filter:
   a. Stream data blocks with predicate pushdown
   b. Evaluate JSON path expressions against BSON
5. MVCC: filter by _rev visibility (read snapshot)
----

== Engine 2: TITAN -- Graph Storage Engine

=== Prior Art

[cols="1,2,3"]
|===
| System | Architecture | What We Take

| Neo4j (native store)
| Fixed-size records, pointer-based traversal, relationship chains
| Index-free adjacency (O(1) neighbor lookup), fixed-record layout

| JanusGraph
| LSM-tree backend (HBase/Cassandra/BerkeleyDB), wide rows for adjacency
| LSM-tree adjacency storage, wide-row pattern

| DGraph
| Posting lists per predicate, Raft consensus, Badger LSM
| Predicate-based storage, sorted posting lists

| TigerGraph
| Compressed sparse row (CSR), parallel graph algorithms
| CSR for read-heavy traversal, delta encoding for edge lists
|===

=== Data Model

[source,text]
----
Node = {
    node_id:    u64    (dense, auto-incrementing for CSR locality)
    labels:     Vec<String>
    properties: HashMap<String, PropertyValue>
    _ts:        u64
}

Edge = {
    edge_id:    u64
    source:     u64    (node_id)
    target:     u64    (node_id)
    edge_type:  String
    properties: HashMap<String, PropertyValue>
    _ts:        u64
}
----

=== MemTable Structure: Adjacency-First

[source,text]
----
TitanMemTable {
    // Nodes: ordered by node_id for range scans
    nodes: BTreeMap<u64, Node>

    // Adjacency lists: the core graph structure
    // Key = (source_node_id, edge_type) for O(1) neighbor traversal
    // Value = sorted vec of (target_node_id, edge_id, edge_properties)
    outgoing: BTreeMap<(u64, String), Vec<AdjacencyEntry>>
    incoming: BTreeMap<(u64, String), Vec<AdjacencyEntry>>

    // Label index: label -> set of node_ids
    label_index: HashMap<String, BTreeSet<u64>>

    // Edge type index: edge_type -> count (for query planning)
    edge_type_stats: HashMap<String, u64>

    size_bytes: AtomicU64
}

AdjacencyEntry {
    target_id: u64,
    edge_id:   u64,
    weight:    Option<f64>,
    _ts:       u64,
}
----

**Key insight from Neo4j**: Index-free adjacency. The adjacency lists are stored *with* the node, not in a separate index. This gives O(k) traversal where k = number of neighbors, independent of total graph size.

=== On-Disk SSTable Format

[source,text]
----
TITAN SSTable Layout:
┌──────────────────────────────┐
│  Header (64 bytes)           │ magic, version, node_count, edge_count
├──────────────────────────────┤
│  Node Bloom Filter           │ node_id bloom
├──────────────────────────────┤
│  Node Data Blocks            │ Nodes sorted by node_id
│  (64KB each)                 │ Properties: BSON-encoded
│                              │ LZ4 compressed
├──────────────────────────────┤
│  Adjacency Blocks            │ THE CORE OF THE ENGINE
│  (variable size)             │ Key: (source_id, edge_type)
│                              │ Value: delta-encoded target_id list
│                              │   Delta encoding: [base_id:8][deltas:varint...]
│                              │   Typical compression: 60-80% for power-law graphs
│                              │ Sorted by (source_id, edge_type) for merge-join
├──────────────────────────────┤
│  Reverse Adjacency Blocks    │ Same format, keyed by (target_id, edge_type)
│  (variable size)             │ Enables efficient incoming edge traversal
├──────────────────────────────┤
│  Label Index Block           │ label -> sorted node_id list (delta-encoded)
├──────────────────────────────┤
│  Edge Type Statistics        │ Per edge_type: count, avg_degree, max_degree
├──────────────────────────────┤
│  Block Index                 │ Standard block offset index
└──────────────────────────────┘
----

**Delta encoding rationale**: In real-world graphs (social, knowledge), target_ids in adjacency lists tend to cluster. Delta encoding (storing differences between consecutive sorted IDs) gives 2-4x compression. DGraph uses exactly this pattern.

=== Compaction Strategy: Edge-Aware Leveled

Standard leveled compaction with graph-specific optimizations:

1. **Adjacency list merging**: When the same (source_id, edge_type) appears in multiple levels, merge the target lists and deduplicate by edge_id. This maintains adjacency locality across levels.

2. **Tombstone propagation for edge deletes**: Edge deletions write tombstones that must propagate through all levels (since an edge appears in both forward and reverse adjacency blocks).

3. **Degree-based block sizing**: High-degree nodes (> 10K edges) get their own dedicated adjacency blocks to avoid amplifying reads for popular nodes.

=== Query Path

[source,text]
----
Graph Traversal Flow:
1. Start at source node (MemTable -> SSTable bloom -> node data block)
2. Read adjacency block for (source_id, edge_type)
   - MemTable: BTreeMap lookup
   - SSTables: Binary search in adjacency blocks (newest level first)
   - Merge adjacency entries across levels
3. For each neighbor:
   a. Check property filters (if WHERE on edge properties)
   b. Recurse for multi-hop (BFS or DFS, configurable)
4. For pattern matching (Cypher MATCH):
   a. Build worst-case-optimal join plan
   b. Use label index for starting node selection
   c. Intersect adjacency lists for multi-pattern joins

Key performance property:
  Traversal is O(k * L) per hop where k=neighbors, L=levels
  NOT O(E) where E=total edges in graph (index-free adjacency)
----

== Engine 3: CHRONO -- Observability/Time-Series Engine

=== Prior Art

[cols="1,2,3"]
|===
| System | Architecture | What We Take

| InfluxDB (TSM-tree)
| Time-Structured Merge tree, series-key organization, columnar blocks
| TSM layout (time-partitioned SSTs), series-key concept

| Prometheus TSDB
| Time-partitioned blocks (2h default), chunk-based compression
| Time-partitioned compaction, Gorilla timestamp/value encoding

| VictoriaMetrics
| LSM-tree (mergeset), inverted index for labels, per-series blocks
| Label inverted index, per-series blocking

| ClickHouse (MergeTree)
| Columnar LSM, min/max index per granule, partition pruning
| Columnar encoding, granule statistics for time range pruning

| Grafana Loki
| Chunk-based log storage, label-indexed, compressed chunks
| Label-based organization, chunk compression for logs
|===

=== Data Model

[source,text]
----
// Metrics (time-series)
MetricPoint = {
    series_key:  SeriesKey    // (metric_name, sorted label set)
    timestamp:   u64          // nanosecond precision
    value:       f64          // gauge, counter, histogram bucket
}

SeriesKey = {
    name:   String            // e.g. "http_requests_total"
    labels: BTreeMap<String, String>  // e.g. {method: "GET", status: "200"}
}

// Logs
LogEntry = {
    timestamp:   u64
    level:       LogLevel     // TRACE, DEBUG, INFO, WARN, ERROR
    labels:      BTreeMap<String, String>  // structured labels
    message:     String       // log line
    trace_id:    Option<String>
    span_id:     Option<String>
}

// Traces
Span = {
    trace_id:    String
    span_id:     String
    parent_id:   Option<String>
    operation:   String
    start_time:  u64
    duration_us: u64
    labels:      BTreeMap<String, String>
    events:      Vec<SpanEvent>
}
----

=== MemTable Structure: Time-Partitioned

[source,text]
----
ChronoMemTable {
    // Metrics: organized by series key for compression efficiency
    // Key = series_key_hash, Value = sorted (timestamp, value) pairs
    metric_series: HashMap<u64, TimeSeries>

    // Logs: organized by time for sequential scan efficiency
    // Key = timestamp_bucket (1-minute granularity), Value = log entries
    log_buckets: BTreeMap<u64, Vec<LogEntry>>

    // Traces: organized by trace_id for assembly
    traces: HashMap<String, Vec<Span>>

    // Label inverted index (shared across all data types)
    // Key = (label_name, label_value), Value = set of series_key_hashes
    label_index: HashMap<(String, String), RoaringBitmap>

    size_bytes: AtomicU64
    time_range: (u64, u64)  // min/max timestamp in this memtable
}

TimeSeries {
    series_key: SeriesKey,
    samples:    Vec<(u64, f64)>,  // (timestamp, value) sorted by time
}
----

**Key insight from InfluxDB/Prometheus**: Time-series data is *append-mostly* (writes are almost always at the current time). The MemTable is therefore a write buffer for the most recent time window, and flushes create time-partitioned SSTables.

=== On-Disk SSTable Format

[source,text]
----
CHRONO SSTable Layout (time-partitioned):
┌──────────────────────────────────┐
│  Header (64 bytes)               │ magic, version, time_range (min, max),
│                                  │ series_count, point_count, data_type
├──────────────────────────────────┤
│  Label Inverted Index            │ (label_name, label_value) -> series_ids
│  (compressed)                    │ Roaring bitmap for series IDs
│                                  │ Enables O(1) label matching
├──────────────────────────────────┤
│  Series Index                    │ series_key_hash -> block_offset
│  (sorted)                        │ Binary-searchable for series lookup
├──────────────────────────────────┤
│  Data Blocks (columnar)          │ One block per series (or series group)
│  (multiple)                      │
│  ┌────────────────────────┐      │
│  │ Timestamps column      │      │ Gorilla delta-of-delta encoding
│  │ (delta-of-delta + VBR) │      │ Typical: 1.37 bits/timestamp
│  ├────────────────────────┤      │
│  │ Values column          │      │ XOR encoding (Gorilla) for floats
│  │ (XOR float encoding)   │      │ Typical: 1.7 bits/value for gauges
│  ├────────────────────────┤      │
│  │ Log messages column    │      │ Dictionary + LZ4 for log strings
│  │ (dict + LZ4, logs only)│      │ 10-20x compression typical
│  └────────────────────────┘      │
├──────────────────────────────────┤
│  Time Range Statistics           │ Per-block: min_ts, max_ts, point_count
│  (for partition pruning)         │ Per-series: min/max/avg value
├──────────────────────────────────┤
│  Block Index                     │ Standard block offset index
└──────────────────────────────────┘
----

**Gorilla encoding** (from Facebook's paper): Timestamps in time-series are often regular (e.g., every 15 seconds). Delta-of-delta encoding exploits this: first delta might be 15000ms, second delta-of-delta is 0 (encoded as single bit). Achieves ~1.37 bits/timestamp vs 64 bits raw. Values use XOR encoding (consecutive float values often share exponent bits).

=== Compaction Strategy: Time-Window with Downsampling

[source,text]
----
Level 0: Recent data (< 2 hours), individual flush files
Level 1: Short-term (2h - 24h), merged to 2-hour blocks
Level 2: Medium-term (1d - 7d), merged to 6-hour blocks, 1-minute downsampled
Level 3: Long-term (7d - 30d), merged to 24-hour blocks, 5-minute downsampled
Level 4: Archive (30d+), merged to 7-day blocks, 1-hour downsampled

Downsampling preserves: min, max, sum, count, last
(enables avg, rate, percentile approximation from summary stats)
----

**Key insight from Prometheus**: Time-series queries almost always have a time range predicate. Time-partitioned SSTables enable *partition pruning* -- if the query asks for the last hour, only L0 and L1 files need to be read. Combined with the time range statistics in the SSTable header, this eliminates >90% of I/O for typical monitoring queries.

**Retention-based deletion**: Unlike document/graph engines where deletion is explicit, CHRONO drops entire SSTables when they fall outside the retention window. No tombstones needed -- the oldest time-partitioned files are simply deleted.

=== Query Path

[source,text]
----
Metric Query Flow (e.g., PromQL "rate(http_requests_total{status=200}[5m])"):
1. Parse label matchers: {__name__="http_requests_total", status="200"}
2. Label index lookup: intersect roaring bitmaps for matching series
3. Time range pruning: skip SSTables outside [now-5m, now]
4. For each matching series:
   a. Read timestamps + values columns from data blocks
   b. Decompress (Gorilla decode)
   c. Apply PromQL function (rate = delta/time_delta)
5. Aggregate across series if needed

Log Query Flow (e.g., Loki-style "{app=api} |= error | json"):
1. Label index lookup: find series matching {app=api}
2. Time range pruning: focus on relevant time buckets
3. Stream log messages through pipeline:
   a. String match (|= "error")
   b. JSON parse (| json)
   c. Field extraction
4. Return in reverse chronological order (most recent first)
----

== Implementation Plan

=== Phase 1: CEDAR (Document Engine)

Estimated complexity: Medium. Most similar to SST -- same LSM flow, different encoding.

1. Create `src/storage/engines/impls/cedar/` module
2. Implement `CedarMemTable` with BTreeMap + secondary indexes
3. Implement BSON SSTable writer (reuse existing block I/O infrastructure)
4. Register in `factory.rs` as `StorageEngine::CEDAR`
5. Wire into `DocumentService` as the backing store

=== Phase 2: TITAN (Graph Engine)

Estimated complexity: High. Adjacency-first storage is a different paradigm.

1. Create `src/storage/engines/impls/titan/` module
2. Implement `TitanMemTable` with adjacency-first BTreeMaps
3. Implement delta-encoded adjacency block writer
4. Implement adjacency merge during compaction
5. Register in `factory.rs` and wire into graph query engine

=== Phase 3: CHRONO (Observability Engine)

Estimated complexity: High. Gorilla encoding and time-window compaction are specialized.

1. Create `src/storage/engines/impls/chrono/` module
2. Implement Gorilla timestamp/value encoding
3. Implement `ChronoMemTable` with series-key organization
4. Implement time-window compaction with downsampling
5. Register in `factory.rs` and wire into observability subsystem
