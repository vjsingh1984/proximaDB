== Columnar Engines

=== VIPER Engine: Parquet-Based Columnar Storage

**Location**: `src/storage/engines/impls/viper/`

The VIPER engine leverages the Apache Parquet format for high-performance columnar storage with advanced compression and encoding capabilities.

**Key Features**:
- **Parquet Integration**: Native Parquet format support with Arrow integration
- **Advanced Compression**: LZ4, GZIP, Snappy, BROTLI, ZSTD compression algorithms
- **Dictionary Encoding**: Automatic categorical data optimization
- **Column Pruning**: Read only required columns for query processing
- **Predicate Pushdown**: Filter data at storage level before retrieval

**Architecture Components**:
```rust
pub struct ViperEngine {
    pub config: ViperConfig,
    pub filesystem: Arc<dyn UnifiedCachingFilesystem>,
    pub distance_compute: Arc<UnifiedDistanceCompute>,
    pub quantization_engine: Arc<UnifiedQuantizationEngine>,
    pub compression_engine: Arc<CompressionEngine>,
}
```

**Optimal Use Cases**:
- Analytics workloads with columnar access patterns
- Batch processing operations
- Data warehousing scenarios
- Time-series data with high compression requirements

=== NOVA Engine: Progressive Columnar Storage

**Location**: `src/storage/engines/impls/nova/`

The NOVA engine provides progressive search capabilities with hierarchical statistics and multi-level quantization.

**Key Features**:
- **Progressive Search**: Multi-stage refinement from coarse to fine-grained results
- **Hierarchical Statistics**: Zone maps and column statistics for efficient pruning
- **Multi-Level Quantization**: Binary, INT8, PQ4/8/16/32 quantization levels
- **Adaptive Thresholds**: Dynamic optimization based on query patterns

**Operations Architecture**:
- **Flush Operations** (`flush.rs`): Hierarchical data organization during writes
- **Compaction Operations** (`compaction.rs`): Progressive file merging and optimization
- **Search Operations** (`search.rs`): Multi-stage progressive query execution

**Progressive Search Flow**:
1. **Coarse Filter**: Binary quantization for rapid elimination
2. **Intermediate Filter**: INT8 quantization for refinement
3. **Fine Filter**: PQ quantization for accuracy
4. **Exact Search**: Full precision for final results

=== HELIX Engine: Locality-Optimized Storage

**Location**: `src/storage/engines/impls/helix/`

The HELIX engine uses Hilbert curve clustering and locality-optimized storage for spatial and range query optimization.

**Key Features**:
- **Hilbert Curve Clustering**: Space-filling curves for locality preservation
- **Spatial Indexing**: Optimized for range and spatial queries
- **Cache-Friendly Layout**: Data organization for optimal cache utilization
- **Adaptive Partitioning**: Dynamic partitioning based on data distribution

**Predicate Pushdown**:

- Automatic reordering based on selectivity estimates

- Cost-based optimization for complex filter expressions

== Quantization Integration

=== Columnar Quantization Strategy

All columnar engines use the unified quantization system with columnar-specific optimizations:

**Column-Specific Quantization**:
```rust
pub enum ColumnarQuantizationLevel {
    Binary,    // 1 bit per dimension - stored in separate columns
    INT8,      // 8 bits per dimension - columnar layout
    PQ4,       // 4-bit Product Quantization
    PQ8,       // 8-bit Product Quantization
    PQ16,      // 16-bit Product Quantization
    PQ32,      // 32-bit Product Quantization
}
```

**Storage Layout**:
- **Separate Columns**: Each quantization level stored in dedicated columns
- **Batch Access**: Optimized for reading entire columns at once
- **Compression**: Quantized columns compressed using engine-specific algorithms

=== Progressive Quantization Workflow

1. **Data Ingestion**: Full precision vectors stored in primary columns
2. **Quantization Pass**: Multiple quantization levels computed
3. **Column Storage**: Each level stored in separate columnar format
4. **Query Optimization**: Automatic selection of appropriate quantization level

== Usage Examples

=== VIPER Engine Analytics Query

```rust
use proximadb::storage::engines::impls::viper::ViperEngine;
use proximadb::query::unified_query_optimizer::SearchParams;

let viper = ViperEngine::new(config, filesystem, distance_compute).await?;

// Analytical query with column pruning
let search_params = SearchParams {
    vector: None,  // Analytics query without vector search
    filter_expression: Some(FilterExpression {
        clauses: vec![
            FilterClause {
                field: "category".to_string(),
                operator: ComparisonOperator::Equal,
                value: FilterValue::String("electronics".to_string()),
            },
            FilterClause {
                field: "price".to_string(),
                operator: ComparisonOperator::GreaterThan,
                value: FilterValue::Number(100.0),
            }
        ],
        op: LogicalOperator::And,
    }),
    top_k: Some(1000),
    include_metadata: Some(true),
    include_vectors: Some(false),  // Don't load vector columns
    ..Default::default()
};

let results = viper.search_vectors_unified(&search_params).await?;
```

=== NOVA Engine Progressive Search

```rust
use proximadb::storage::engines::impls::nova::NovaEngine;

let nova = NovaEngine::new(config, filesystem, distance_compute).await?;

// Progressive search with multiple quantization levels
let search_params = SearchParams {
    vector: Some(query_vector),
    top_k: Some(10),
    quantization_level: Some("progressive".to_string()),  // Enable progressive search
    distance_metric: Some(DistanceMetric::Cosine),
    ..Default::default()
};

// NOVA will automatically use:
// 1. Binary quantization for initial filtering
// 2. INT8 quantization for intermediate results
// 3. PQ8 quantization for refinement
// 4. Full precision for final top-k
let results = nova.search_vectors_unified(&search_params).await?;
```

=== HELIX Engine Spatial Query

```rust
use proximadb::storage::engines::impls::helix::HelixEngine;

let helix = HelixEngine::new(config, filesystem, distance_compute).await?;

// Spatial range query optimized with Hilbert clustering
let search_params = SearchParams {
    vector: Some(query_vector),
    filter_expression: Some(FilterExpression {
        clauses: vec![
            FilterClause {
                field: "location_lat".to_string(),
                operator: ComparisonOperator::Between,
                value: FilterValue::Range(37.0, 38.0),
            },
            FilterClause {
                field: "location_lng".to_string(),
                operator: ComparisonOperator::Between,
                value: FilterValue::Range(-122.0, -121.0),
            }
        ],
        op: LogicalOperator::And,
    }),
    top_k: Some(50),
    ..Default::default()
};

let results = helix.search_vectors_unified(&search_params).await?;
```

== Integration with Other Systems

=== Unified Cache Integration

All columnar engines integrate with the unified caching system:

```rust
use proximadb::storage::cache::CacheOrchestrator;

let cache = CacheOrchestrator::new(cache_config).await?;

// Engine automatically uses unified cache
let viper = ViperEngine::new_with_cache(config, filesystem, distance_compute, cache).await?;
```

**Cache Optimizations**:
- **Column Caching**: Entire columns cached for analytical workloads
- **Quantization Caching**: Precomputed quantized columns cached
- **Metadata Caching**: Zone maps and statistics cached for rapid access
- **Compression Caching**: Decompressed data cached for repeated access

=== AutoML Integration

Columnar engines integrate with the AutoML framework for automatic optimization:

```rust
use proximadb::automl::{AutoMLCoordinator, OptimizationGoal};

let automl = AutoMLCoordinator::new(automl_config).await?;

// AutoML optimizes columnar engines for workload patterns
automl.optimize_engine("viper", OptimizationGoal::MaximizeThroughput).await?;
automl.optimize_engine("nova", OptimizationGoal::BalancePerformance).await?;
```

**AutoML Optimizations**:
- **Compression Algorithm Selection**: Based on data characteristics
- **Quantization Level Selection**: Based on accuracy requirements
- **Partitioning Strategy**: Based on query patterns
- **Cache Configuration**: Based on memory usage patterns

== Best Practices

=== Data Modeling for Columnar Storage

1. **Schema Design**: Organize data with columnar access patterns in mind
2. **Partitioning Strategy**: Partition data based on query patterns
3. **Compression Selection**: Choose compression based on data characteristics
4. **Quantization Planning**: Balance accuracy vs. performance requirements

=== Query Optimization

1. **Column Pruning**: Select only required columns in queries
2. **Filter Pushdown**: Apply filters at storage level when possible
3. **Batch Operations**: Process data in batches for optimal performance
4. **Progressive Search**: Use NOVA for latency-sensitive applications

=== Performance Tuning

1. **Memory Management**: Configure appropriate cache sizes for workload
2. **Compression Tuning**: Balance compression ratio vs. decompression speed
3. **Quantization Selection**: Use AutoML for optimal quantization levels
4. **Partitioning Optimization**: Align partitioning with query patterns

== Conclusion

ProximaDB's columnar storage architecture provides a comprehensive solution for analytical and batch processing workloads. Through specialized engines (VIPER, NOVA, HELIX), advanced filtering, and intelligent quantization, the system delivers exceptional performance across diverse use cases while maintaining flexibility and ease of use.

The modular design allows for engine-specific optimizations while providing a unified interface for application development. Integration with AutoML ensures automatic optimization and adaptation to changing workload patterns.
