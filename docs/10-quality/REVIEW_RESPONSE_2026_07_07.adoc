This document is the durable response to Antigravity's architectural review and follow-up
recommendation matrix. It verifies the claims against the repository, corrects stale or miscited
items, maps real issues to existing ADR/TD trackers, and defines the critical trajectory for
ProximaDB as a multimodal context database.

[IMPORTANT]
====
The review is directionally useful: handler monoliths, DataFusion/Volcano drift, SaaS catalog
isolation, bounded cross-modal execution, and evidence-gated claims are real concerns. Its
citations and priorities needed correction: several items were already tracked, some were stale,
and the original text under-specified the product architecture. This is the corrected action plan.
====

== 1. Executive Summary

* The top risks are real in theme, but mostly already tracked: TD-104, TD-151, TD-186/ADR-043,
  TD-168/ADR-034, TD-123, TD-ENGINE-1, TD-078, ADR-018, ADR-032, and the measurement ledger.
* `TD-CAT-2` is **real**, not phantom: it is the tenant-prefixed catalog-path slice of ADR-032.
  The correct SaaS blocker is ADR-032 / TD-CAT-1/2/3, not a new ticket.
* The one confirmed new correctness item is TD-FILT-1: v2 metadata filters silently drop rows on
  unresolved fields. Slice 1 added strict evaluators; this PR wires one live hybrid metadata-gating
  seam behind `PROXIMADB_FILTER_FAIL_LOUD`.
* The cross-modal resource-bound finding is TD-XMODAL-9. The current state is partial: one
  graph-fusion path can use the canonical bounded `Fuser`, but residual v2 paths still need the
  same cap/fail-loud contract.
* The development path is: structural isolation and correctness first, bounded multimodal fabric
  second, decomposition and PAX/DataFusion cost work third, distributed MPP and warehouse parity
  later.

== 2. North-Star Architecture Lens

ProximaDB should not be developed as "a vector database plus extra APIs" or "a warehouse clone with
embeddings bolted on." The defensible target is a **multimodal context database** with one durable
identity, type, storage, freshness, and tenancy spine:

* **One canonical record spine.** `ProximaRecord` / `ProximaType` / `ProximaValue`, stable `oid`,
  tenant id, namespace id, and WAL LSN are the authority. Vector, document, graph, event, and
  relational views are projections over that spine, not separate durable truths.
* **One physical locality substrate.** PAX is the native random-access / vector / multimodal
  substrate; Parquet and Iceberg are interop and lakehouse surfaces. The advantage is co-designing
  ANN, metadata filters, graph expansion, and analytical scans over one geometry.
* **One query-lowering contract.** SQL and UQL converge through typed logical plans and shared
  expression/function semantics. DataFusion owns analytical operators; native execution serves
  OLTP/point lookup and the PAX-native scan bridge, not a parallel OLAP engine.
* **One cross-modal fabric.** Retrieval should be `seed -> expand -> calibrate -> fuse-by-oid ->
  rank`, with bounded resource controls and evidence-carrying traces at every stage.
* **Structural isolation and freshness.** Tenant isolation is a path/catalog/edge property, never
  a predicate added late to a query. Strong read-after-write remains the default and is made cheap
  with LSN-aware cache eligibility.
* **Evidence-gated claims.** Product language follows `SUPPORTED_SURFACE.adoc`; performance
  language follows `BENCHMARK_EVIDENCE.toml`. Everything else is roadmap, not a claim.

== 3. Corrections

=== 3.1. TD-CAT-2 is real, but not new

*Review claim:* "Treat TD-CAT-2 as a P0 release blocker for SaaS multi-tenant."

*Actual state:* `TD-CAT-2` exists in `TECHNICAL_DEBT.adoc` and is referenced by ADR-032. It is the
tenant-prefixed catalog-path slice, not a new Antigravity discovery:

* ADR-032 D1 / TD-CAT-1: persist the native catalog through `FilesystemFactory`.
* ADR-032 D2 / TD-CAT-2: route catalog metadata through tenant-prefixed physical paths.
* ADR-032 D3 / TD-CAT-3: make request tenant resolution explicit and fail-closed at edges.

*Action:* Do not open a duplicate catalog-isolation TD. Drive TD-CAT-1/2/3 to completion and do not
make SaaS multi-tenant claims until catalog paths and all protocol edges are fail-closed.

=== 3.2. Performance claims are mostly already gated

The README already caveats benchmark-style figures; the 100K QPS figure lives in the internal
`BENCHMARK_EVIDENCE.toml` ledger as unverified. The remaining work is wording discipline in
product docs: aspirational "sub-ms" phrases should either be measured ledger entries or softened to
"low-latency single-node."

=== 3.3. v1 removal is not a small task

Hard-deleting v1 surfaces is the staged TD-123 ratchet plus TD-ENGINE-1. Treating it as a small
cleanup would create unnecessary blast radius.

=== 3.4. Strategic items stay strategic

Distributed MPP (TD-078), multi-table ACID (ADR-018), and broad warehouse parity are valid future
directions, but they should not pull capacity from the single-node multimodal core before P0/P1/P2
are stable.

== 5. Critical Trajectory

* **P0a — structural SaaS isolation.** Finish ADR-032 in order. TD-CAT-1 cloud catalog root
  injection is present but needs backend smoke/failure tests. TD-CAT-2 is partial and must route
  physical catalog object keys through `DrPathBuilder`. TD-CAT-3 now has
  `proximadb_tenant::TenantDeploymentMode`, `[server.tenant]` startup resolution, and REST
  extraction from that mode. Remaining edge work is gRPC/pgwire/Flight.
* **P0b — fail-loud correctness seams.** Continue TD-FILT-1 from the strict evaluator and
  `PROXIMADB_FILTER_FAIL_LOUD` hybrid gate into lower-level vector/storage predicates once those
  interfaces can return `Result` instead of bare `bool`.
* **P0c — bounded cross-modal execution.** Complete TD-XMODAL-9 by making all live v2 fusion paths
  use the bounded/fail-loud contract, with saturation telemetry and byte/cancellation caps where
  row caps are insufficient.
* **P1 — engineering velocity.** Continue TD-104 decomposition so REST, gRPC, pgwire, and Flight
  call bounded ports without modality-specific god-object reach-through.
* **P2 — PAX/DataFusion cost spine.** Prioritize TD-151, TD-OLAP-1, and ADR-042 after correctness.
  Any claimed performance win must land in `BENCHMARK_EVIDENCE.toml`.
* **Deferred by design.** TD-078 distributed MPP, full multi-table ACID, and warehouse parity wait
  until the single-node multimodal context database foundation is solid.

== 7. Acceptance Criteria

The path is on track when:

* Two tenants can create the same namespace/table name with distinct catalog rows and object paths.
* `multi_tenant` mode rejects REST/gRPC/pgwire/Flight requests without a tenant signal.
* `single_tenant` mode injects the configured default tenant everywhere.
* Every tenant id is structurally validated before becoming a catalog key or object-store segment.
* Strict metadata filtering can fail a query rather than silently narrowing results.
* Every live cross-modal fusion path has row caps, saturation telemetry, and a fail-loud mode.
