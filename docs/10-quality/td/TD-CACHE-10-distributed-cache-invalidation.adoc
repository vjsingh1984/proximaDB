= TD-CACHE-10: Cross-Pod Cache Coherence — Rescoped to the Smallest Correct Mechanism
:toc:
:toclevels: 3
:date: 2026-08-25
:status: SHIPPED (rescoped 2026-08-29 — original PubSub premise replaced by the co-design audit; S2 bus seam landed default-off)

== Context

ProximaDB currently implements single-pod cache invalidation via `CacheInvalidationCoordinator`. However, multi-pod deployments lack distributed cache coherence, creating stale read risks.

== The 2026-08-28 co-design audit (three explorations) — findings that RESCOPE this TD

The original filing premised a PubSub system (SNS/PubSub/Event Grid; <10 ms
propagation; 99.9% delivery) for cross-pod invalidation of "the caches".
Pressure-testing from first principles refutes the premise at three levels:

1. **Multi-pod is not real today.** Single binary is the operative deployment:
   the inter-node gRPC services exist but `start_with_cluster` has zero
   callers, `cluster_port: None` is hardcoded, `NodeRegistry` is an in-process
   HashMap, and the `cluster` cargo feature is not default. Process-local
   invalidation is therefore COMPLETE — every cache-mutating event happens in
   the one process holding the caches. The propagation-latency criteria are
   unmeasurable without the topology they assume.
2. **The byte-level segment caches need NO invalidation, ever.**
   `SegmentInvariantsCache`, `SurvivorRangeCache` (module doc: "**No
   invalidation for v1** … no coherence risk"), and `OidResolverCache` are
   safe-by-immutability: segment paths are immutable and content-unique, so
   stale entries only exist for dead segments (harmless LRU waste). Deletion
   vectors are consulted AFTER cache hits (`is_deleted_as_of` downstream on
   both read paths), so they are also safe-by-construction. A PubSub system
   invalidating these caches solves a problem they do not have.
3. **Query result caches are LSN/TTL-gated by contract** (mandate #16c):
   Strong freshness bypasses/gates all three result caches; weaker modes
   contractually accept TTL staleness. The cross-pod caveat — LSNs from the
   per-pod `GlobalLsnAllocator` — is subsumed by the shipped
   single-writer-per-collection model (`PrimaryPodRegistry` hard write
   affinity + `cache_affinity` read hints).

=== What the audit found as GENUINE stale-risk (and what shipped)

[cols="2,3,2", options="header"]
|===
| Surface | Risk | Resolution
| `VectorObjectEconomyDirectoryCache` | Per-collection OnceCell, NO TTL, invalidated only by LOCAL writes — pod B serves pod A's stale segment list (missing new segments, referencing deleted ones) indefinitely until restart | **TTL re-check shipped** (`PROXIMADB_DIRECTORY_CACHE_RECHECK_MS`, default 30 s, `0` kill): expired handles are replaced on `handle_for`, bounding cross-pod staleness without any transport; same-pod writer invalidation stays immediate
| DV resident map (`DeletionVectorStore`) | Under `cold-deletion-vectors` + multi-pod deletes: the resident map never re-reads the shared `.dv` sidecar | **Sidecar re-check shipped**: `load()` re-confirms entries older than `DV_SIDECAR_RECHECK` (30 s) against the shared sidecar — disk-authoritative replacement loses nothing (local marks persist under the same lock; earliest-generation-wins idempotent). Pinned by `sidecar_recheck_sees_cross_pod_deletes_after_ttl`
| Query/result caches cross-pod | Strong is LSN-gated but LSNs are per-pod | Covered by single-writer routing today; when multi-pod lands, the S2 bus (below) carries the version-propagation signal |
|===

== S2 seam (shipped default-off): invalidation events over the segment queue

`src/query/cache/invalidation_bus.rs`:

* `CacheInvalidationEvent` — serde JSON payload
  `{schema_version, pod_id, tenant, collection, kind: Write|Ddl|Flush|
  Compaction|DeleteVector, lsn}` on topic `cache-invalidation` over the
  **landed** `proximadb-queue` consumer-group primitive (ADR-079 Q1;
  process-wide `QueueClient` at boot, `src/database.rs`). Zero new
  dependencies — the original SNS/Event Grid recommendation is replaced by
  the in-house transport, and the etcd-watch alternative by the
  shared-object-store topic.
* `EventDedup` — per-pod high-water admission: `(pod_id, lsn)` strictly
  increasing admits; duplicates and older-LSN replays drop. Per-pod LSNs are
  NOT globally comparable (per-pod `GlobalLsnAllocator` atomics); the
  single-writer-per-collection routing model is what makes per-pod
  sub-sequences the correct ordering domain.
* `drive_once(consumer, dedup, handler)` — poll/decode/admit/drive/ack;
  unknown schema versions and malformed payloads skip durably.
* Default-off: `PROXIMADB_CACHE_INVALIDATION_BUS=1` plus a queue root
  activates the bus. Publish failure must never fail the write (log +
  counter at call sites).
* Tests (all executed): wire round-trip incl. all kinds; dedup admits
  strictly-increasing per-pod; the in-process multi-pod proof — pod A
  publishes, pod B's `drive_once` admits and drives the invalidation
  handler, and the replayed duplicate `(pod_id, lsn)` is deduped.

=== Multi-pod activation precondition

The bus is wiring-complete, but activating it in a deployment requires
multi-pod to be REAL: `start_with_cluster` wired into server boot, peer
discovery beyond the in-memory `NodeRegistry`, and cross-pod LSN semantics
revisited (or the Raft free-rider adopted — see below). Until then the bus is
test-proven dormant scaffolding.

== Original premise — recorded for the record, superseded

The original filing recommended PubSub (SNS/PubSub/Event Grid) over consensus
(etcd watch) and gossip. Superseded: (a) most caches need no invalidation
(structural safety); (b) the transport is the in-house segment queue (zero
deps, shared-store backed); (c) a Raft `Command::BumpCorpusVersion
{tenant, collection}` applied on every pod is the natural free-rider IF the
`cluster` feature ships — recorded for that future, not built now.
Conformance: mandate #16b semantics unchanged (local invalidation on every
write remains the coherence mechanism; this TD adds the cross-pod signal
layer only when a topology needs it).
