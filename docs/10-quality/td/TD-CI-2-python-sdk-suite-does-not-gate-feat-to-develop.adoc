= TD-CI-2: The Python SDK unit suite does not gate feat→develop, so SDK breakage lands and waits

[cols="1,3",options="header"]
|===
| Field | Value
| Status | **Open — filed 2026-08-20**, from a live instance: two tests were red on `develop` and no PR had reported it. The break itself is fixed in the same change; this entry is about why nothing caught it.
| Dim | D5 (governance) — a gate whose tier lets a known-testable regression reach the shared branch
| Pillar | OE — secondary REL
| Blocks | Nothing directly. It converts every Python SDK regression into a **develop→qa promotion blocker** discovered by whoever happens to promote, rather than by whoever introduced it.
| Depends on | Nothing. Adjacent to TD-CI-1 (compile bottleneck), which is about cost; this is about coverage.
|===

== The finding

`python-test` — "Python SDK Tests", the whole `clients/python/tests/unit` suite, ~4,500 tests across
three interpreter versions — is gated on:

[source,yaml]
----
if: ${{ !inputs.skip_tests && needs.changes.outputs.medium_tier == 'true' }}
----

`medium_tier` is true for **develop→qa** and **qa→main**. It is false for **feat→develop**. So the
Python unit suite never runs on the PR that introduces a Python change.

This is a deliberate tier choice, and the job's own comment explains the reasoning — the suite runs at
develop→qa "so SDK regressions block one stage earlier instead of only surfacing at the qa→main
boundary". The gap is that *one stage earlier* is still one stage too late: the regression is already
on the shared branch by then, and the person who has to diagnose it is the promoter, not the author.

**Measured on PR #1679**, which rewrote large parts of the Python SDK:

[cols="2,1",options="header"]
|===
| Check | Result
| Python Lint | ran
| Python SDK Codegen Drift | ran
| Python SDK round-trip | ran
| SDK Coverage Ratchet | ran
| Chunking Conformance + Quality Evals | ran
| **Python SDK Tests** | **SKIPPED**
|===

Five Python gates ran and the one that executes the tests did not.

== The incident that surfaced it

`tests/unit/test_embedded_record_http.py` had two tests failing on `develop` with
`'EmbeddedProximaDB' object has no attribute '_shared_http_client'`.

Cause: both tests built the object with `EmbeddedProximaDB.__new__(EmbeddedProximaDB)` to skip socket
setup, then set only `config`. When HTTP-client pooling later added `self._shared_http_client = None`
to `__init__`, the half-built object stopped carrying an attribute `_http_client` reads.

Two things are worth separating. The **test was fragile** — skipping initialisation breaks every time
initialisation grows, and it fails as a defect in the code under test rather than in its own setup;
that is fixed here by constructing normally with `transport="tcp"`, which needs no socket. But the
**reason it sat broken** is this TD: the suite that would have caught it on the introducing PR does not
run on the introducing PR.

== Why this is not just "add the job to feat→develop"

The suite is ~5 minutes × 3 interpreter versions, and the runner pool is demonstrably contended — a
`develop` CI run was observed queued for 25 minutes with only two runs in flight org-wide. Turning it
on unconditionally for every PR is a real cost, and CLAUDE.md's CI-tiering mandate exists precisely to
keep feat→develop light.

The targeted form is cheaper and already computed. The `changes.outputs.python` filter exists and is
what `Python Lint`, `Codegen Drift` and `SDK Coverage Ratchet` already use, so:

[source,yaml]
----
if: ${{ !inputs.skip_tests && (needs.changes.outputs.medium_tier == 'true' || needs.changes.outputs.python == 'true') }}
----

runs the suite **only when Python actually changed**, which is exactly the population that can break
it. A PR touching only Rust or docs pays nothing.

Whether to also trim the interpreter matrix on the feat→develop path (one version instead of three) is
the cost/coverage dial, and is the part worth an explicit decision rather than a default.

== Acceptance

* A PR that breaks a Python SDK unit test fails on that PR, not at develop→qa — demonstrated by
  breaking one deliberately and observing the red, per the same standard TD-PROTO-1 used. A gate that
  has never been seen to fail is not known to work.
* A PR touching no Python still does not run the suite.
* The runner-cost delta is stated in the PR that makes the change, measured rather than estimated.

== Co-design note

The cost term here is **engineering latency, not compute**. A regression caught on its own PR costs the
author a re-push; the same regression caught at promotion costs a bisect by someone who did not write
it, on a branch other people are building on. That asymmetry is the argument, and it is why the fix
should be scoped by *what changed* rather than by promotion stage.
