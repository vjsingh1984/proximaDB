== The finding

The WAL is the per-write hot path, and its physical placement sets the cost + latency floor. Pointed at object
storage it bills `O(write ops)` — unbounded and workload-driven (measured ~9M flat-Blob ops/day on a Spot
testbed). The engine can already *place* the WAL on a local reattachable disk (the FilesystemFactory selects
per tier; the queue already uses `file://`), and already has fsync (`PerBatch`) + a truncation routine — but
it lacks the **adaptive flush control, backpressure, and guaranteed truncation cadence** that make a bounded
local WAL + coalesced object-store durability safe. Without those, a local WAL either loses data (no time
flush ⇒ unbounded RPO on volume loss) or crashes the node (no backpressure ⇒ ENOSPC).

== Direction (per ADR-069)

Tier by write-frequency: **WAL on local reattachable disk; object store as the coalesced durable tier for
SST/VIPER/metadata/checkpoints.** Flush on `min(size, time, capacity-budget)`; two watermarks + backpressure;
guarantee post-flush truncation keeps pace; make the `PerBatch` fsync a tested contract; wire the
object-store-write-op *canary* metric so the regression can't recur silently.

== Slices

S1 — **WAL tier-split plumbing + `file://` guardrail.** New `[storage.wal_config]` keys parsed into
`WalPerformanceConfig`: `flush_interval_secs`, `wal_max_bytes`, `high_watermark_pct`, `critical_watermark_pct`
(safe defaults). Startup validation: warn/config-error when `write_buffer_directory` resolves to an
object-store scheme in a durability-sensitive deployment (the "WAL should be `file://`" nudge). No behavior
change beyond config surface. (Per-tier selection already works — this is config + validation only.)

S2 — **Time-based flush.** A per-collection periodic trigger (`flush_interval_secs`) alongside the existing
size trigger in the post-write path (`bincode_serialization_strategy.rs:279` / `memtable_manager.rs`). Fires
on `min(size, time)`. This is the **RPO floor** (ADR-069 D2). Off (=0) preserves today's behavior.

S3 — **Capacity-budget watermark flush + guaranteed truncation cadence.** Track per-collection WAL bytes
against `wal_max_bytes`; at `high_watermark_pct` force a flush and drive
`truncate_through_canonical_marker` — ensuring the `CanonicalEmission` marker advances on *every* durable SST
flush so truncation keeps pace (ADR-069 D4). Budget %, not raw disk %, so a shared volume's data growth
doesn't pollute the trigger (D6).

S4 — **Two-watermark backpressure.** At `critical_watermark_pct`, return a retryable
`ResourceExhausted`/`Unavailable` from the write path instead of writing into an ENOSPC crash; flush runs
async so writes are only shed at the ceiling (ADR-069 D3).

S5 — **fsync durability contract + crash test.** Document each `SyncMode`'s guarantee; add a
crash-consistency test: write N `PerBatch` batches, `SIGKILL`, remount the volume, assert all N replay (RPO 0)
(ADR-069 D5).

S6 — **Metrics + canary.** Add per-collection WAL-util % (vs budget), flush-count-by-trigger (size/time/
capacity/manual), truncation-segments-reclaimed, WAL-replay-time-on-boot, and the **object-store
write-operation rate** (the regression canary). Extend `metrics/updater.rs` / `eventlog_metrics.rs`.

S7 — **Soak + acceptance.** Multi-hour sustained-write soak: WAL-util stays bounded (no monotonic growth);
backpressure engages past critical without crash; object-store write-op rate stays flat (only coalesced
SST/checkpoint ops) — the ADR-069 §6 pressure test.

== Shipped vs residual (2026-07-21, PR #1117 + PR #1118 — live-verified)

**Shipped.**

* **S1 config surface** — the four knobs end-to-end on the LIVE server path:
  `WriteBufferUserConfig` (`src/core/config.rs`, serde back-compat defaults) wired at BOTH
  conversion sites (`shared_services.rs::convert_toml_to_wal_config` + `config.rs::to_engine_config`)
  → `WalPerformanceConfig`; plus the foundation-crate `WalStorageConfig` mirror. Caught en route:
  the `From<&WalStorageConfig>` path is test-only — `WriteBufferUserConfig` is the live surface.
* **S2 + S3 decision core** — `write_ahead_log/flush_policy.rs`: pure
  `FlushPolicy::evaluate(mem_bytes, age) → {reason, backpressure}`; envelope
  `time ≤ size ≤ high < critical`, precedence `capacity-critical > capacity-high > size > time`,
  envelope-reconciliation warnings. 7 unit tests.
* **S2 + S3 execution** — `src/storage/auto_flush_driver.rs`: policy-gated scheduler
  (spawned from `StorageEngine::start()` only when a time/capacity trigger is armed;
  default config = no task). Calls the proven `materialize_collection(free_wal=true)` recipe
  per due collection. WAL reclamation on the live path is **manifest-deletion inside
  `materialize_collection`** (`mark_flushed_and_delete_files`), not the marker-gated
  `truncate_through_canonical_marker` (that path stays feature-gated for canonical replay scope);
  the S3 goal (reclamation keeps pace with every flush) is met by construction.
* **S6 core** — `proximadb-metrics::wal_flush_metrics` (private registry appended to
  `/metrics/prometheus`): `proximadb_wal_flush_total{collection,reason,result}`,
  `_bytes_total`, `_vectors_total`, `_duration_seconds{reason}`; gauges `wal_size_bytes`,
  `budget_bytes`, `high/critical_watermark_bytes`, `last_flush_timestamp_seconds`,
  `backpressure_active/total`. Trigger attribution ships; object-store flush writes were already
  metered (`record_object_store_op("flush_write")` in the materializer).
* **Two latent live-path bugs found by the live verification** (would have silently defeated
  the whole mechanism):
  1. `WALVectorBatch.total_size_bytes` was constructed as `0` on the live ingest path
     ("calculated by strategy" — the strategy never runs live), blinding the pre-existing
     memtable backpressure AND all size/capacity evaluation. Fixed with the canonical,
     precision-aware `WALVectorBatch::estimate_records_size` (dedup of the `BulkWriteRouter`
     copy tracked in TD-WAL-2).
  2. `materialize_collection(free_wal=true)` cleared the inner memtable but never retired
     batches in the **batch coordinator** (the store `get_unflushed_batches` reads) — harmless
     on the terminal shutdown flush, an infinite re-flush loop for any periodic caller
     (pre-fix evidence: 94 × 810-vector duplicate flushes, one per tick). Fixed with
     `mark_batch_flushed` + `clear_flushed_batches` in the `free_wal` block.

**Live acceptance evidence** (local server, 3 s time floor / 100 KB budget):
time flush fired once on an idle small burst (10 vectors), capacity flush once on a large burst
(800 vectors), backpressure counted, flush counters froze after ingest stopped (loop terminates),
and recall passed BOTH post-flush (WAL freed → served from SST) and post-restart
(`No collections found in WAL to restore` → search + record GET still return all records).

**Residual (open).**

* *S1 guardrail nudge* — startup warn/error when `write_buffer_directory` resolves to an
  object-store scheme in a durability-sensitive deployment. Not shipped.
* *S4* — **core shipped.** Write-path admission control unified onto `critical_watermark_pct`:
  `FlushPolicy::write_admission_reject_pct(mem_bytes)` computes the reject decision at the same
  `>= critical` line `FlushDecision::backpressure` uses; the client WAL-append path
  (`WriteAheadLogManager::admit_write`, called from `insert_record`/`insert_vectors`) returns a
  retryable `WalBackpressure` and meters `inc_backpressure` instead of driving the bounded local
  WAL disk into an ENOSPC crash. **Default-OFF** (inert when `wal_max_bytes == 0`); **recovery
  replay is never gated** (it materializes SST directly, not via the insert methods). The ingest
  boundary (`ApiError::from_write_error`) chain-walks the error and promotes a `WalBackpressure`
  to a retryable status (HTTP 429 / gRPC `RESOURCE_EXHAUSTED`). *Residual:* the **primary REST
  batch path** reports WAL-lane rejections as `Ok(success=false)` (per #951), so end-to-end 429
  there needs the backpressure discriminant threaded through `BatchOperationResult` →
  `batch_failure_to_api_error`; the `Err`-propagating paths (gRPC / Arrow Flight / bulk / any
  `?`-propagation) already surface 429. *Second follow-up:* `update_record`/`delete_record` route
  through `insert_record`, so tombstone/DELETE writes are gated like any write. Acceptable under
  default-OFF + the high-watermark force-flush (which drains regardless of op type), but a
  theoretical wedge if flush stalls — consider exempting DELETE/tombstone from admission so ingest
  backpressure can never block the operation that relieves it.
* *S5* — fsync contract doc + SIGKILL crash-consistency test.
* *S6 residual* — truncation-segments-reclaimed and WAL-replay-time-on-boot metrics.
* *S7* — multi-hour soak (bounded WAL util, flat object-store write-op rate).

== Resolved decisions / current caveats

* **Placement needs no engine change** — the FilesystemFactory already selects WAL and SST backends
  independently; S1 is config + a guardrail, not new plumbing.
* **Truncation exists but is marker-gated** (`truncate_through_canonical_marker`) — S3's real work is
  *guaranteeing the marker advances every flush* so it keeps pace, not writing truncation from scratch.
* **WAL is per-collection** — triggers, budget, and truncation are per-collection; a global budget (if added)
  is a sum-across-collections guard, not a replacement.
* **RTO tradeoff is a deployment choice, not an engine constraint** — local WAL ⇒ fresh node waits for volume
  reattach; low-RTO tiers keep the WAL on object storage or run on non-evictable nodes.

== Gate

Ship S1–S3 before any deployment flips its WAL to `file://` (without S2's time flush, a local WAL has
unbounded RPO on volume loss; without S3, it can fill). S4–S7 harden and prove it.
**Gate CLEARED 2026-07-21** — S1–S3 landed + live-verified (PR #1117/#1118); the AnvaiOps
`write_buffer_directory`→`file:///var/lib/proximadb/wal` flip + "WAL must be `file://`" ratchet is
now unblocked (applies at its next ephemeral drill / go-live per its cost posture).

== Non-goals

Cross-region WAL replication; a replicated/consensus WAL (this is the local single-writer WAL, not the Raft
log); changing the SST/VIPER/metadata durable tier (stays object store); automatic hot→cold tiering of the
WAL itself (the flush *is* the tiering).

== Sequencing

S1 (config + guardrail) → S2 (time flush = RPO floor) → S3 (capacity + guaranteed truncation) — this trio is
the minimum safe set. Then S4 (backpressure), S5 (fsync contract + crash test), S6 (metrics/canary), S7
(soak/acceptance). Downstream AnvaiOps config flip after S1–S3.
