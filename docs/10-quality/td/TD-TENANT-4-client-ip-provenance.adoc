= TD-TENANT-4: the client IP is never observed, only asserted
:icons: font

**Status:** S1 + S2 shipped with this TD — D1 and D2 both closed.

**Surface coverage is complete.** Three sites classify a client for KOU egress,
and only one was defective:

* REST (`network/middleware/metrics.rs:46`) — was header-derived; **fixed here**.
* Arrow Flight (`network/arrow_ipc/service.rs:1564`) — already used tonic's
  `request.remote_addr()`, a real peer address. No change needed.
* pgwire (`network/postgres/protocol.rs:5367`) — already used `self.peer_ip`.
  No change needed.

The only other axum TCP listener (the OTLP ingestion adapter,
`observability/ingestion/adapters/otlp.rs:531`) does not classify a client at
all — it is an inbound ingestion endpoint, not a result-egress surface — so it
is deliberately left without `ConnectInfo`.
**Origin:** TD-TENANT-3 S4 item 2 flagged the ungated `X-Forwarded-For` read at
`rate_limit.rs:327` as "the same trust-a-bare-header shape TD-TENANT-1 closed
for tenancy". Investigating it to fix it showed that framing was **wrong about
which surface is affected**, and that the underlying defect is larger and more
interesting than a missing trust gate.

== Correction to TD-TENANT-3 S4

TD-TENANT-3 recorded the concern as *"a client-supplied header trusted for
rate-limit keying"*. Two facts falsify that:

. **The REST rate limiter is not mounted.** `rate_limit_middleware`
  (`crates/platform/proximadb-network-middleware/src/rate_limit.rs:285`) has
  **zero** non-test references. The header-based IP never reaches a rate-limit
  decision.
. **pgwire — the one live rate-limited path — already does the right thing.**
  It keys on `self.peer_ip` (`src/network/postgres/protocol.rs:1375`), a real
  socket peer address, and pgwire has no headers to spoof anyway. It is
  env-gated by `PROXIMADB_PGWIRE_RATE_LIMIT_RPM` (default off).

So there is no rate-limit bypass. The header **is** consumed on a live path,
but a different one, and the consequence is not throttling.

== The actual defect

`get_client_ip` (`rate_limit.rs:326`) resolves the client address in three
steps: `X-Forwarded-For` → `X-Real-IP` → **a hardcoded `127.0.0.1`**, carrying
the comment `"This would need to be set by the server, for now use localhost"`.

That comment names the root cause. **The real peer address is never available**:
nothing in the tree calls `into_make_service_with_connect_info`, so axum never
supplies `ConnectInfo`. Lacking an observation, the code substitutes a
client-controlled assertion and, failing that, a constant.

The live consumer is **KOU egress metering**, not rate limiting. The metrics
middleware is mounted unconditionally on the REST router
(`src/network/rest/server.rs:609`, a `route_layer`) and calls
`get_client_ip` → `EdgePolicyContext::classify`
(`src/network/middleware/metrics.rs:47`) to decide `is_chargeable_egress`.

Two consequences follow, and the second is the one that matters:

=== D1 — a client can choose its own billing classification

`classify` maps an unmatched **private** address to `KouLocality::Unknown`
(`consumption_metrics.rs:497`), and `Unknown` is **not chargeable**
(`is_chargeable_egress`, :268 — only `CrossRegion`, `CrossCloud`, `OnPrem`, and
`Internet` are). A remote client that sends `X-Forwarded-For: 10.0.0.1`
therefore classifies as unchargeable and its result-egress is not metered.

No authentication is required to set a header, so this is available to any
caller that can reach the port.

=== D2 — result-egress metering is inert by default, everywhere

This is the larger finding. With **no** proxy in front and **no** header set —
the default single-node and embedded deployments — every request falls to the
hardcoded `127.0.0.1`. Loopback is not public, matches no scope-map rule, and
so classifies `Unknown` ⇒ **not chargeable**.

The KOU result-egress meter therefore records nothing in any deployment that
does not happen to sit behind a header-setting proxy. The meter does not meter.

== Co-design framing

Per the co-design mandate, **network outgress (KOU) is one of the five metered
TAM surfaces**, and result-egress is named as *"the dominant result-egress
term"* for the Internet locality (~$0.09–0.12/GB). D2 means that dimension is
structurally unobservable in the default configuration — not mis-weighted, but
absent. A dimension you cannot measure cannot be co-designed against, which is
the mandate's own premise ("trace before you tune").

This TD claims no revenue number. The observable is the KOU result-egress
counter being non-zero for a genuinely remote client, which today it is not.

== Design

The two defects share one root cause, so the fix is one capability plus one
gate — deliberately in that order, because the gate is meaningless without the
observation.

=== S1 — observe the peer address (closes D2)

Wire `ConnectInfo` at the TCP serve sites so the middleware can read the real
peer address. Two transports need different treatment and the difference is
load-bearing:

* **TCP** (`multi_server.rs`, `rest/server.rs`) — `ConnectInfo<SocketAddr>`
  carries the true remote address.
* **UDS** (`rest/server.rs`, portless/embedded mode) — a Unix socket has no
  `SocketAddr`. `ConnectInfo<SocketAddr>` must not be demanded there; doing so
  is the trap that makes this look like a one-line change.
+
A UDS peer is by construction on the same host, so it resolves to loopback —
the *correct* classification, not a fallback. But "no `ConnectInfo`" is also
what a TCP surface that forgot the wiring looks like, so the two must not
collapse into one state. The UDS serve path therefore inserts a
`LocalSocketPeer` marker extension, and the resolver checks it first. That
keeps `ClientAddrSource::Unobserved` meaning *"a wiring regression"*, which is
the only thing that variant is good for.
+
This is deliberate: an earlier cut of this change had a `local_socket_client_addr`
helper that nothing called, so the `LocalSocket` state was unreachable and UDS
requests read as `Unobserved`. A variant nothing can produce is indistinguishable
from one left unimplemented — wiring it is part of the item, not a follow-up.

=== S2 — gate the forwarded headers (closes D1)

Honor `X-Forwarded-For` / `X-Real-IP` only when the **immediate peer** is a
trusted proxy, declared as a CIDR allowlist. Otherwise ignore them and use the
observed peer address.

This is the same shape as `HeaderTrustPolicy` (TD-TENANT-1) — a bare
client-supplied assertion is honored only from a caller entitled to make it —
but the entitlement here is *network position*, not a credential, so it is
expressed as CIDRs rather than reusing the enum. Default is **empty**: trust no
proxy, ignore the headers entirely. That is safe for direct exposure and
correct for the default single-node deployment; operators who front the engine
with a load balancer declare its CIDR.

Deliberately **not** a 4xx: an untrusted forwarded header is dropped, matching
the drop-not-reject semantics of ADR-0053 W8 and TD-TENANT-3.

=== Ordering note

S1 alone already fixes D2 and *narrows* D1 (an observed peer address exists to
prefer). S2 alone would fix nothing, because with no observation there is
nothing to fall back to. They ship together; S1 is the load-bearing half.

== Non-goals

* **Reviving the REST rate limiter.** `rate_limit_middleware` is unmounted dead
  code. Whether to mount it is a separate decision with its own blast radius;
  this TD only stops the IP it would key on from being fiction. Noted so the
  dead code is not mistaken for a live control.
* **The full `Forwarded` (RFC 7239) header.** `X-Forwarded-For` / `X-Real-IP`
  are what the code reads and what cloud load balancers emit.
* **Trusting a proxy chain depth > 1.** The leftmost XFF entry is taken, as
  today; multi-hop chain validation is out of scope.
