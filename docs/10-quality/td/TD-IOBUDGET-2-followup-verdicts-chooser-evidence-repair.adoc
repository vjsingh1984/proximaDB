== Verdict 1 — plumb the destination URL (SHIPPED, closes TD-IVF-4)

The TD-IVF-4 premise ("destination unknown at clustering time") was narrower than filed.
The default flush never reaches `ivf_fine_cell_count` (flush IVF clustering is the eval
knob `PROXIMADB_PAX_FLUSH_CLUSTER=ivf`, default OFF); the live path is compaction, which
always knew its output object (`SstCompactionTask.output_file`). The fix threads
`destination_url` from the seven production writer call sites into
`write_target_block_bytes(destination)`, so writer cell geometry resolves the SAME
per-location budget (TD-IOBUDGET-1 registry) the reader resolves for that path — the
ADR-065 "one cell ≈ one IOP" premise now holds on both sides of the storage boundary.
Details in the TD-IVF-4 Resolution section. Red→green:
`destination_url_resolves_the_iop_target` (block_cluster).

Co-design note: this also removes a silent divergence — with an empty registry the writer
now derives the SCHEME default (s3:// → S3 8 MiB; **file:// → LOCAL 1 MiB — the DEFAULT
deployment's k ×4 on new compaction segments, reader nprobe ≈ ×2, self-adapting via each
segment's stored k_c**) where it previously hard-coded CLOUD (4 MiB), which is exactly
what the reader already assumed for that path. Intended but UNMEASURED at the new
operating point: the SIFT-1M acceptance geometry was measured at the OLD k. Rollback
levers today: `PROXIMADB_DISK_CLASS=hdd` (pod-wide) or per-location TOML
`io_budget.disk_class = "hdd"`. **Required follow-up before qa promotion:** a local-bed
compaction A/B (old-CLOUD-k vs new-LOCAL-k, acceptance pair first) — full narration in
the TD-IVF-4 Resolution. New segments only; cell counts are per-segment
self-describing metadata (no format change, mixed-read-safe by construction); cross-host
byte-determinism is a pre-existing config-driven class (cf. `PROXIMADB_IVF_K`).

== Verdict 2 — the chooser default flip is REFUSED on evidence; the supporting A/B is INVALIDATED

The only chooser A/B ever run (TD-RDSTRAT-13 campaign, 2026-08-31, Mac→dataserver2 MinIO)
is invalid:

* The bench harness (`scripts/bench/sift1m_get_reduction.py`) POPS
  `PROXIMADB_STORAGE_READ_STRATEGY_CHOOSER` from the spawned server's env and re-sets it
  only via the `adaptive_read_strategy` constructor parameter — which had **no CLI flag
  and no caller**. The "ON" arm ran chooser-OFF.
* Corroborating evidence: both arms reported byte-identical GET/q (20.05) and bytes/q
  (62,087,166.41); zero `pax.range_estimator` observe lines in either server log; the
  p50 delta (4271→4194 ms, −1.8%) is noise-consistent.
* Both arms also FAILED the harness's own `object_cold GET/q ≤ 20.00` gate; the campaign
  never produced a gate-passing pair at any arm.

An earlier session recorded the A/B as "evidence-backed" for a default flip. That record
was wrong; this TD supersedes it. The invalidation also means TD-RDSTRAT-13's Chooser A/B
section (unmerged worktree commit 188787302) must NOT be cherry-picked to develop as-is.

**Enablement shipped in this batch:** `--adaptive-read-strategy` now exists as a real CLI
flag wired to the constructor param at all three harness construction sites, and the
OFF arm now FAILS FAST if the gate leaks into its server env (the original defect class —
an operator-exported gate silently engaging the "baseline").

== Verdict 3 — the AZURE profile default raise (4→16 MiB) is REFUSED on guard strikes

TD-SEARCH-3's committed wire sweep says 8 MiB is the latency knee and 16 MiB the GET knee
at recall parity, and TD-IOBUDGET-1 lets an operator opt in per location via TOML. But the
ledger's own note keeps the estimator default-OFF pending cache-tier evidence, and the
3.3M RSS guard struck. A const flip changes writer AND reader geometry for every Azure
deployment at once — it waits for the named evidence, not for enthusiasm.

== Consumers/interplay recorded for the flip decision

* With the chooser OFF, a registered per-location budget still applies — as the fixed
  default policy (`defaults` derives from `IopsBudget::for_path(path).target_block_bytes()`).
* The chooser only enumerates ADDITIONAL caps above that default
  (`read_range_cap_candidates` = multiples of budget.target up to scheme ceilings), so
  chooser-ON + a small registered budget can legitimately RAISE an effective cap — GET-count
  gates can move either direction and the flip A/B must run both budgets explicitly.
* The SST scan path (`sst_query_engine.rs`) is budget-blind (hard-coded
  `ObjectRangeCoalescePolicy::default()`) — a pre-existing divergence, out of scope here.
