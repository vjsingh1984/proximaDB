|===

== The seam (the actual enabler)
`FilesystemPort` ALREADY existed in `proximadb-storage-ports` (Slice D port-inversion) with
`get_filesystem` — and root's `FilesystemFactory` already implements it. The metadata
serializers were blocked only because their FIELDS named the concrete `Arc<FilesystemFactory>`.
This lands the inversion:

* `SstMetadataSerializer`/`SwiftMetadataSerializer` fields + ctors → `Arc<dyn FilesystemPort>`.
* Callers (`zero_copy/orchestrator.rs::with_all_engines`, `config.rs::register_*`) coerce
  `Arc<FilesystemFactory> → Arc<dyn FilesystemPort>` at the two `Arc::clone` sites (explicit
  `as` cast — unsized coercion isn't applied through `Arc::clone(&T)` generics).
* Both files move to `proximadb-engine-core` (sst 660 + swift 733 LOC, 3 swift tests).
  Imports rewritten: zero_copy traits → `storage-common::zero_copy_traits`, bloom → foundation.

== Test stub (honest scope)
The swift serializer's `extract_metadata` is a PLACEHOLDER (never reads the filesystem —
synthesizes a 10-segment header). The 3 tests only round-trip the serialization format, so
they now inject a no-op `FilesystemPort` (`test_fs_port::noop_port`) instead of constructing
a real `FilesystemFactory`. When `extract_metadata` gains a real read path, these tests must
switch back to a real filesystem (the stub's `get_filesystem` returns `NotFound`).

== Follow-ons now unblocked (TD-DECOMP-76+)

rewrite refs, move, shim.
