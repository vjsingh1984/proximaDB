= TD-REL-LOWER-1: Comma-join / derived-table SELECTs fall through to the legacy single-table parser on the native route

[cols="1,3", options="header"]

== The finding

On the native (pre-MATERIALIZE) route, TPC-H's comma-separated FROM lists
(`FROM customer, orders, lineitem WHERE …`) and derived tables
(`FROM (SELECT …) t`) fail with `Table 'customer,' does not exist` — the comma
*inside* the quoted table name is the tell. The relational lowering declines
the shape, the query falls through to the **legacy single-table path**, and its
naive whitespace FROM tokenizer takes `customer,` verbatim as a table name.

The pgwire conformance ratchets (TPC-H 22/22) do not see this because they run
the materialized/DataFusion route; the ledger's native sweep is what exercises
the fallthrough. Consequences:

* Native-route TPC-H coverage is impossible for comma-join queries (8 of 22 use them).
* `olap/native` cost cells for join shapes never warm — the router's evidence
  for the Volcano floor on joins comes only from explicit-JOIN queries.
* The error message misleads (the table exists; the parse is wrong).

Separately, TPC-H Q19 fails on the native scan with
`operator - is not defined for Int64 and Float64` (`1 - l_discount`, integer
literal vs Float64 column) — a numeric-coercion gap in the native expression
evaluator, likely TD-186 territory.

== Direction

1. **Lower comma-joins as cross joins** in the relational frontend (ANSI
   semantics; `FROM a, b WHERE …` ≡ `CROSS JOIN` + filter) so the shape engages
   PATH B instead of declining — per the full-ANSI-over-pgwire mandate, prefer
   real semantics over the legacy fallthrough.
2. **Derived tables already engage** (`set_expr_engages` checks
   `table_with_joins_has_derived`) — the decline is later, in lowering; extend
   lowering or make the decline fall through to a *helpful* error, never to the
   legacy tokenizer.
3. At minimum, the legacy path must reject multi-table FROM with a clear
   "unsupported on this route" error instead of parsing `customer,` as a name.
4. Q19 coercion: int→float promotion for arithmetic over Float64 columns in the
   native expression evaluator (or route such filters to DataFusion by
   eligibility until fixed).

== Progress (2026-07-13)

Bisected and fixed the dominant decline class plus the two hardening directions:

* **Root cause of the join/comma-join fallthrough was neither the join nor the comma** — the
  frontend already lowers comma-joins as cross joins and handles derived tables. The decliner was
  a **qualified ORDER BY key** (`ORDER BY t.col` / `alias.col`): `apply_order_by` resolves against
  the post-projection scope, which carries no table qualifiers (`Scope::from_schema`), so the key
  hit `ColumnNotFound` and the whole query fell to the legacy tokenizer. Fixed: a qualified sort
  key that names a projected output column now resolves by its bare column name (ANSI: sort keys
  designate output columns); an unknown column still errors. Aliased explicit-JOIN, aliased
  comma-join, unaliased comma-join, and derived-table SELECTs now execute correctly on the native
  route (`tests/rel_lower_native_join_e2e.rs`), and the geometry-calibration ratchet battery runs
  its join shapes on BOTH seams.
* **Direction 3 (clear error):** the legacy pgwire SELECT path now rejects a multi-table /
  derived-table FROM with a specific `0A000` error (`legacy_unsupported_from_shape`) instead of
  misparsing `customer,` / `(select` as table names — any residual decline reads as "unsupported
  on this route", never a phantom missing table/column.
* **Direction 4 (Q19 coercion):** mixed numeric arithmetic (`1 - l_discount`, Int64 vs Float64)
  now widens both sides to f64 in `eval_arithmetic` — the same promotion `values_equal`/
  `compare_ord` already applied — and `Expr::result_type` agrees (`Float64`).

Historical residuals (split into their own TDs rather than keeping this finding open): full TPC-H native-route coverage — residual per-query lowering
declines (e.g. CASE/EXTRACT/INTERVAL frontend gaps) now fail loudly with the 0A000 message; fix
incrementally per the pgwire mandate.

**Re-measured taxonomy (2026-07-14 native sweep, SF 0.01, post-#953):** the mangled-error class
collapsed from 72 ledger ERRs to 3 single-table queries (TPC-H Q1/Q4/Q6 — declines the
multi-table 0A000 guard cannot see; date/interval frontend gaps). TPC-H: **14/22 now lower and
execute** (Q9–Q22 — then grind the un-normalized cross product, filed as TD-REL-LOWER-2), 3
comma-join + 2 derived-table clean 0A000 declines (Q2/Q3/Q5, Q7/Q8). TPC-DS: **24 native passes**,
15 clean 0A000 declines, 8 cross-product grinders, 2 `rebind_columns` internal planner errors on
alias-named sort keys (q3/q52 — pre-existing pushdown bug newly reachable, filed as
TD-REL-LOWER-3). Follow-up guard candidate: extend the specific-error treatment to single-table
relational declines so Q1/Q4/Q6 stop mangling.

**Re-measured again (2026-07-14, post-`1a424f3c6` + this PR's DATE-literal fix):** develop's
`1a424f3c6` landed the cross→equi-join rewrite in `push_predicates` (the TD-REL-LOWER-2 core) and a
`plan_has_raw_cross_join` fail-fast decline, so the grinders are GONE. Native TPC-H then measured
**4/22 OK** — and the dominant remaining blocker was NOT the join at all: the frontend declined
every `DATE 'YYYY-MM-DD'` typed literal (`Unsupported("typed string literal")`), so ~8 date-filtered
queries fell through to the legacy path and surfaced the misleading "comma-separated table list"
`0A000` (a red herring). Lowering typed DATE literals to the canonical `ProximaValue::Date`
(days-since-epoch, shared `proximadb_data_model::parse_iso_date_to_days`) took native TPC-H to
**12/22 OK** (Q1/Q3/Q4/Q5/Q6/Q7/Q10/Q12 flipped). The residual 10 are now diverse, separate
mechanisms: scalar/IN subqueries (Q2/Q11/Q17/Q18/Q20), `CASE` (Q14), a derived table (Q8), two
genuine non-equi cross-joins (Q9/Q19), and one `rebind_columns` alias error (Q15 — see
TD-REL-LOWER-3). Each is its own frontend/planner coverage item; none share a single fix.
