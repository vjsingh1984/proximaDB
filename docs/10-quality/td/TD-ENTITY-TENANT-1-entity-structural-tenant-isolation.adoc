== Context (the gap)

The other modalities moved from `{tenant}::{id}` folding to structural isolation composed once at
the boundary (per-tenant engines for timeseries; a `{tenant}/{graph_id}` scoped handle for graph).
The entity surfaces still fold `{tenant}::{collection}` (`effective_collection` in
`entities.rs:166`, `effective_collection_id` in `entity_service.rs:88`).

Converting entities revealed that this single fold is **load-bearing for THREE modalities at once**,
each with a *different* correct isolation mechanism — so it cannot be de-folded as a bolt-on
without risking a cross-tenant vector leak or breaking fusion search:

. **Graph (authoritative entity node).** Cleanly isolatable via the landed `for_tenant` facade
  (clean name → `{tenant}/{graph_id}`). Low-risk; this part alone is ready.

. **Vector (entity embeddings + the fusion *seed* leg).** The fold isolates vectors by folding the
  collection **name** (`insert_batch(folded)` / `unified_search_native(folded)`). But:
  * `unified_search_native(collection_id, query, k, filter, config)` has **no tenant parameter**,
    and `get_or_load_collection` **requires the collection to pre-exist** (loads from the
    collection service). So de-folding two ways both fail:
    - keep the name **clean** ⇒ tenant A's and B's entity vectors land in the **same** vector
      collection — a storage-isolation regression and muddied per-tenant KRU/KOU billing, and the
      fusion seed leg over-returns cross-tenant hits;
    - **scope** the name `{tenant}/{collection}` ⇒ the (pre-existing) collection is not found and
      fusion's `retry_vector_search(...)?` **hard-fails** the search.
  * The co-design-correct mechanism EXISTS but fusion does not use it:
    `insert_batch_with_tenant_context` → `validate_tenant_collection_access` (vectors are
    **`TenantContext`-partitioned with a CLEAN name**, not name-folded — the co-design rule). There
    is **no tenant-aware `unified_search_native`** yet, so the fusion read leg has no clean path.
  * Entity *search results* would still be result-isolated (the orchestrator re-fetches each hit
    via a scoped `for_tenant(tenant).get_node`, dropping cross-tenant seeds), BUT the vector
    **storage** leak/break above is real, and the general `fusion_search_v2` path has **no such
    re-fetch backstop**.

. **Document (provenance).** Already deferred — see [[TD-DOC-TENANT-1]] (same store/lifecycle
  entanglement).

The entity vector/fusion path also appears **untested end-to-end**: embedding insert is
best-effort (`warn`-on-fail), and no collection-creation path exists in the entity
handlers/orchestrator — collections are assumed pre-created out-of-band under the folded name.

== Why deferred (not band-aided)

The `{tenant}::{collection}` fold is no worse than today; deferring regresses nothing. A partial
de-fold would either **leak entity vectors across tenants** (clean name, shared collection) or
**break fusion/entity search** (scoped name, missing collection). Delivering coherent entity
isolation requires the vector/fusion/collection-lifecycle rework below, not a bolt-on.

== Proposed resolution (when picked up — a meaty, careful PR of its own)

. **Graph leg:** route the orchestrator/entity-service graph ops through `for_tenant` with clean
  names (trivial, already possible).
. **Vector leg (the crux):** move fusion + entity embedding onto the `TenantContext`-partitioned
  path — `insert_batch_with_tenant_context` for writes, and add a **tenant-aware
  `unified_search_native`** (thread `TenantContext` / a tenant param, `validate_tenant_collection_access`)
  for the fusion seed read. Keep vector collection **names CLEAN** (co-design: vectors isolate by
  `TenantContext`, never by name-fold). Thread the tenant into `GraphFusionParams` so both the
  graph-oid and vector legs scope from one source.
. **Collection lifecycle:** define/where entity + fusion vector collections are created and ensure
  creation is tenant-consistent with the read path (resolve the "collections pre-exist" assumption).
. **Backstop + evals:** add an entity/fusion isolation test (two tenants, same clean collection, no
  cross-tenant seed or result; vector storage physically separated); gate `fusion_search_v2` with
  the same rubric.

== Constraints

* Keep net `proximadb_v1` references non-increasing (TD-123 ratchet, baseline 2917) — prefer v2
  proto types in any new code/tests.
* Vector-format / partition-key changes must be mixed-read-safe (no flag-day), per the
  storage-format-migration mandate.
