== Summary

The TD-151 / TD-RDSTRAT-1 read-coalescing + cost-driven, tier-aware read-strategy chooser
**cannot engage on real (PAX) vector-search data**. They were wired into the reader for the
**ProximaBlocks `.sst`** format, which the write path **no longer produces** (ADR-049 M1-3 folds
every non-Arrow flush to `.pax`). The live PAX read path reads each segment **whole in one physical
`fs.read()`** and never consults the chooser. The chooser's observe→flip gate is therefore moot:
there is nothing to observe.

This was found by *measurement + a backtrace probe*, per the "verify, don't assert" mandate — not by
reading the wiring, which looks plausible in isolation.

== The verified read path

For a non-Arrow SST collection (`storage_engine = Sst`, default config), a vector search takes:

[source]
----
SstEngine::search_vectors_unified                         (search/mod.rs)
  → execute_direct_search
    → try_pax_cascade                                      (search/mod.rs:1008, for `.pax` + L2/Cosine)
        → fs.read(WHOLE segment file)                      (search/mod.rs:271)   ← ONE physical GET/segment
        → rabitq_search_segment                            (segment_format.rs)
----

Two facts make the chooser irrelevant here:

1. **The physical read is whole-segment** (`search/mod.rs:271`) — already maximally coalesced
   (1 GET/segment). There is no per-block GET fragmentation on this path to coalesce.
2. **The per-block `io_trace::record_range_gets(1)` at `segment_format.rs:424` are LOGICAL cost
   projections**, not physical GETs. The code says so:
   `// Trace the cascade's logical reads for this kept block`. They model a *future* selective
   striped-read (RaBitQ codes stripe + SQ8 candidate bytes per surviving block) that is **not yet
   built** — the reader unconditionally reads the whole segment.

== Why the chooser/coalescing are off this path

* **Write side (ADR-049 M1-3):** `flush/mod.rs:168` maps `BlockFormat::ProximaBlocks |
  BlockFormat::PaxBlock ⇒ (PaxBlock, "pax")`. The legacy ProximaBlocks `.sst` streaming write is
  retired; every non-Arrow collection flushes `.pax`.
* **The coalescing lives on the ProximaBlocks reader:** `ModularBlockReader::read_blocks_by_range_plan`,
  selected in `read_selected_block_set` (`sst_query_engine.rs:6152`) by `route_options.enabled` — a
  `.sst`-reader gather the PAX cascade never calls.
* **The slice-3b chooser is wired into two never-called sites:**
  `sst_io_layer::batch_read_with_filtering` (no non-test caller) and
  `sst_query_engine::traditional_search` (reached only via `progressive_search`, disabled in
  `search/coordinator.rs:380`).
* **A second, smaller gap on the `.sst` path itself:** even if that reader ran,
  `search_with_filter_and_pruning` (`sst_query_engine.rs:2353`) reconstructs `SearchParams` and drops
  `custom_hints` (and sets `io_optimization_hints: None`), so the `object_economy_enabled` hint that
  flips `route_options.enabled` never arrives.

== Evidence (measured)

`tests/rdstrat_get_count_measurement_test.rs` builds a synthetic SST collection, runs searches through
`SstEngine::search_vectors_unified` under an `io_trace::scope`, and snapshots `range_gets` /
`bytes_read` across four arms: `default`, `obj-economy` (hint), `chooser-env`
(`PROXIMADB_READ_STRATEGY_CHOOSER=1`), `scan-kill-env` (`PROXIMADB_DISABLE_SST_SCAN_COALESCE=1`).

Result (N=200k, 8 queries): **all four arms identical — 640 logical `range_gets`, 110 MB `bytes_read`,
byte-identical top-k.** No read-strategy lever moves the trace. A backtrace probe at the `io_trace`
funnel confirmed the reads originate at `segment_format.rs:424` (PAX cascade), not the
`ModularBlockReader` path. The test asserts this inertness so a future re-wire flips it red.

== The real fix (follow-up — not this TD)

A read-strategy chooser that helps real workloads must live in the **PAX cascade**, deciding between:

* **whole-segment read** (today's `fs.read` at `search/mod.rs:271`) — 1 GET, but over-fetches the
  whole segment when the query is selective; and
* **selective striped read** — fetch only the RaBitQ codes stripe + the SQ8 candidate-row bytes per
  surviving block (the reads `segment_format.rs:424` currently only *projects*).

The crossover is exactly ADR-052's cost model (`per_get·n_gets + per_mib·n_bytes`, tier-aware): on cold
object storage a selective read of a low-selectivity query wins; on hot NVMe or a high-selectivity
query the single whole-segment GET wins. Notably the selective read is **already modelled** — the
cascade's two stages (RaBitQ codes stripe → SQ8/f32 candidate rerank) are exactly what
`segment_format.rs:424` logically traces — and the read substrate **already exists**
(`proximadb-block-format::ranged` stripe reads + `FileSystem::read_ranges` + `PaxSplitReader`), so the
work is *routing + a chooser at one call site*, not a from-scratch build. The existing
`choose_read_strategy` (`coalesce_strategy.rs`, pure + unit-tested) is reusable as the decision core.

**This follow-up is now specified in
link:../../12-design/adr/ADR-057-pax-cascade-selective-striped-read-and-chooser.adoc[ADR-057]** (PAX
cascade selective striped read + chooser; Proposed), tracked under a to-be-filed TD-RDSTRAT-3.

== Recommendation

* **Now:** record this state (this TD) + land the inertness measurement test as the ADR-034 evidence
  artifact. Do NOT flip `PROXIMADB_READ_STRATEGY_CHOOSER` default-on — it is a no-op on real data.
* **Consider retiring** the dead `.sst`-path coalescing/chooser sites (or explicitly gating them as
  legacy-`.sst`-only) so they stop reading as live capability.
* **Follow-up:** link:../../12-design/adr/ADR-057-pax-cascade-selective-striped-read-and-chooser.adoc[ADR-057]
  (the PAX-cascade selective-striped-read + chooser — the real co-design lever), tracked under TD-RDSTRAT-3.

== Non-goals

* Re-wiring the chooser onto the PAX cascade in this TD — that needs the selective striped read built
  first (separate, larger effort).
* Any change to the whole-segment read's correctness or recall (the cascade is unchanged).
