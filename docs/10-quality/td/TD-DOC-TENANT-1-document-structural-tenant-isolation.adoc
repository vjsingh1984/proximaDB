= TD-DOC-TENANT-1: Structural per-tenant isolation for the document modality (deferred behind store-coherence reconciliation)

[cols="1,3"]
|===
|Status|Open
|Priority|MED
|Scope|FEAT
|Date|2026-07-05
|Relates to|The coherent structural tenant-isolation program (Phase 0 unified resolution; Phase 1a timeseries per-tenant engines; Phase 1b graph `TenantGraphOps` facade; Phase 1c graph_traverse UDTF). This TD is the deferred **document** slice of that program. Backing: `src/storage/document/service.rs` (`DocumentService`), `src/network/grpc/v2/document_service.rs` (the `{tenant}::{collection}` fold), `src/network/postgres/protocol.rs` (`create_document_collection`), `src/network/rest/v2/documents.rs` (a *different* store path).

== Context (the gap)

The other modalities moved from `{tenant}::{id}` string-folding at the network handler to
**structural** isolation composed once at the storage boundary (per-tenant engines for
timeseries; a `{tenant}/{graph_id}` scoped handle for graph). The document gRPC handler still
folds `{tenant}::{collection}` via `effective_collection_id`
(`src/network/grpc/v2/document_service.rs:71`).

Attempting the same `for_tenant`/`scoped_collection` facade for documents surfaced that the
document modality has a **deeper pre-existing coherence problem** than tenant folding, and that
bolting scoping onto it now would be unsafe and incomplete:

* **Collections must pre-exist (hard-fail, not lazy).** `DocumentService::insert_document_record`
  calls `get_collection(collection)` and errors `Collection '{}' not found`
  (`service.rs:~900`). Unlike graph's `get_or_create_graph_engine` (lazy provisioning),
  scoping the write to `{tenant}/{collection}` **breaks create/insert unless collection
  creation is scoped in lockstep** with the same key.

* **Collection creation is split and inconsistent today.** pgwire
  `create_document_collection` (`protocol.rs:~3365`) creates a **bare** collection name (no
  tenant); the gRPC read/write handler folds `{tenant}::{collection}`. So the surfaces are
  **already incoherent**: a pgwire-created bare `docs` is invisible to a gRPC call that folds
  to `{tenant}::docs` (`get_collection` → not found). The gRPC fold appears untested
  end-to-end against real collections.

* **The gRPC and REST document surfaces do not share a store.** `src/network/rest/v2/documents.rs`
  does **not** use `DocumentService` at all — it writes through a different tenant-aware path
  (the Flight/record-store path, records stamped with `tenant_id`). Scoping only the gRPC
  `DocumentService` would not make the document surfaces cross-surface coherent.

* **Response-field vs storage-key mismatch risks recovery.** `conv::record_to_v2` returns
  `collection_id: record.collection_id` (clean). Storing under a scoped key while keeping the
  record's `collection_id` clean (to avoid leaking the scoped name in responses) creates a
  key/field split: `insert_document_record` keys by the `collection` **param**, but WAL replay
  rebuilds `DocumentRecordKey::new(collection_id, document_id)` (`service.rs:~3208`). If
  recovery keys off the clean `record.collection_id` rather than the scoped param, **scoped
  documents are lost on replay**. This must be proven before scoping.

The gRPC `DocumentService` is wired in production (`multi_server.rs:192`), so correctness matters.

== Why deferred (not band-aided)

The document fold is **no worse than today** (it is already incoherent and untested), so leaving
it in place regresses nothing. Scoping the gRPC fold alone would *not* deliver cross-surface
coherence (the REST surface is a separate store) and would risk breaking recovery. The
principled sequence is to **reconcile document store/creation coherence first**, then apply the
structural tenant scope on the reconciled foundation — rather than scoping two incoherent stores
separately.

== Proposed resolution (when picked up)

. **Reconcile the document store + creation path.** Decide the single canonical document store
  for the v2 surfaces (gRPC `DocumentService` vs the REST Flight/record-store path) and route
  both through it, or explicitly document the split. Make collection creation tenant-scoped in
  ONE place — pgwire `create_document_collection` and any REST/gRPC create compose
  `{tenant}/{collection}` via a shared `scoped_document_collection(tenant, collection)`
  (validating the tenant with `proximadb_tenant::validate_request_tenant`, path-style `/`,
  never `::`), so create and read agree.
. **Add the `TenantDocumentOps` scoped handle** over read/write (mirroring the graph
  `TenantGraphOps` facade — additive, raw methods untouched so internal callers are unaffected).
  Delete `effective_collection_id` in the gRPC handler; resolve the tenant via
  `grpc_auth::resolved_tenant_id` and route through the handle with a tenant-CLEAN
  collection name.
. **Resolve the `collection_id` field policy:** store the scoped key internally, strip back to
  the clean name in the response mapper, and **confirm WAL replay keys off the scoped
  param/WAL collection, not the clean `record.collection_id` field** (add a recovery round-trip
  test under a tenant scope).
. Gate with a documents isolation test: two tenants, same clean collection name, no cross-read;
  no `::` in any composed key; recovery preserves scope.

== Constraints

* Keep net `proximadb_v1` references non-increasing (TD-123 ratchet, baseline 2917) — prefer v2
  proto types in any new code/tests.
* Mixed-read-safe / no flag-day for any on-disk key-shape change (document keys, WAL replay).
