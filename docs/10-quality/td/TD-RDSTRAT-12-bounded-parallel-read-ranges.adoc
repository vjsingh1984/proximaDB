== Problem statement

TD-RDSTRAT-8 §"Bounded-parallel `read_ranges`" (rev 2.1) identifies that cold query latency follows a **waves-not-sums model**: `latency ≈ rounds × RTT + Σ ceil(GETs_in_round / pool) × RTT + compute`. The sequential `read_ranges` loop (1 GET at a time) makes the first term dominate. A bounded concurrent executor (issue ranges in parallel, complete into the decode pipeline) turns cold latency from `GETs × RTT` into `rounds × RTT`.

The TD specifies two env knobs, acceptance criteria, and io_trace additions.

== Remaining work

=== 1. Add `PROXIMADB_READ_RANGES_INFLIGHT` prefetch cap

The TD specifies **two independent bounds**:

* `PROXIMADB_READ_RANGES_PARALLEL` (renamed in code to `PROXIMADB_FS_READ_RANGES_PARALLEL`) — the **decode-bound** concurrency cap (~40% of cores)
* `PROXIMADB_READ_RANGES_INFLIGHT` — the **pure prefetch cap**, for I/O-bound work that doesn't decode (zstd, SQ8 parse, distance kernels)

Current implementation has one cap (`PARALLEL`). Add `INFLIGHT` as a separate env var that:

* Defaults to a higher value than `PARALLEL` (e.g., 2× `PARALLEL`, or a fixed sensible default like 32)
* Is parsed + cached in `read_ranges_buffered` or its caller
* Controls the `buffered(N)` concurrency when prefetch is safe (caller can annotate "pure prefetch" via a separate method or flag)

Note: The TD text is ambiguous on **how** the caller signals "pure prefetch". Two options:

* **Option A:** Add a `FileSystem::read_ranges_prefetch` method that uses `INFLIGHT` (only for metadata/footer prefetch paths)
* **Option B:** Pass a "decode cost" hint to `read_ranges`; use `INFLIGHT` when decode is cheap/none

Decision gate: file a sub-TD or ADR to resolve the API shape before implementing.

=== 2. Add `fetch_rounds` + `max_inflight` to general io_trace

Today `fetch_rounds` exists only for IVF probe metrics (`src/storage/engines/sst/metrics.rs:46`). The TD requires these fields for **general `read_ranges` telemetry**, so the concurrency benefits are observable across all paths (footer fetches, Region-A/B reads, not just IVF).

Required:

* Extend the `io_trace` mechanism with `fetch_rounds` (count of parallel rounds issued) and `max_inflight` (peak in-flight reads in a round)
* Emit in `read_ranges_buffered` or its caller
* Surface in Prometheus metrics (`proximadb_read_ranges_fetch_rounds_total`, `proximadb_read_ranges_max_inflight`)

=== 3. Collect SIFT1M evidence

⚠️ **COMPLETE (2026-08-26) — HYPOTHESIS FALSIFIED**

**Acceptance criteria (from TD-RDSTRAT-8):**

* "SIFT1M cold p50 improves ≥2× at equal GETs"

**Actual result:** NO MEASURABLE EFFECT — hypothesis falsified by measurement.

*Measured baseline (`INFLIGHT=0`) vs treatment (`INFLIGHT=32`):*
* **object_cold p50:** 49.02ms vs 49.11ms (<1% difference)
* **GETs/query:** 13.80 vs 13.80 (identical)
* **bytes/query:** 46.18MB vs 46.18MB (identical)
* **fetch_rounds/query:** 4.61 vs 4.61 (identical)
* **recall@100:** 0.9874 vs 0.9874 (identical)

**Root cause:** The `PROXIMADB_READ_RANGES_INFLIGHT` env gate is **inert** for the SIFT1M IVF probe workload:

1. **IVF probe path does not use `read_ranges_prefetch()`** — The env gate only exists in `proximadb-storage-filesystem-types/src/lib.rs:795` inside the `read_ranges_prefetch()` function
2. **IVF probe has its own fetch mechanism** — `src/storage/engines/sst/segment_format.rs:coarse_probe_survivors()` (lines 2487-2701) issues sequential `fs.read_range()` calls in a for loop (lines 2619-2669)
3. **Zero production callers** — `grep` confirmed `read_ranges_prefetch()` has zero production callers outside its own test file

The IVF probe calculates its own `fetch_rounds` metric independently (line 2697: `fetched.len() as u64`) and never touches the `read_ranges_prefetch()` code path gated by `PROXIMADB_READ_RANGES_INFLIGHT`.

**Evidence recorded:**
* `BENCHMARK_EVIDENCE.toml` entry: `rdstrat12_sift1m_inflight_inert`
* Status artifact: `docs/_internal/status/RDSTRAT12_SIFT1M_INFLIGHT_INERT_2026_08_26.adoc`
* Binary: SHA-256 `29ed454bf049671ba6f78a9402d057b4f03163267045206c55c9bcb7b2fc599e` (git revision `64a29ec5604903aadb2502db6abaab8b18b84164`)

**Next steps (choose one):**

1. **Rewire IVF probe to use `read_ranges_prefetch()`** — Modify `coarse_probe_survivors()` to batch its ranged reads and call `fs.read_ranges_prefetch()` instead of the current for loop, then re-measure

Per "Measure, Don't Assert" (mandate #6), this falsified hypothesis is itself valuable data — the mechanism compiles and ships but is unreachable from the measured workload.

== Historical context

The TD-RDSTRAT-8 §"Bounded-parallel `read_ranges`" text:

```
Add a bounded concurrent executor: issue the ranges of a round in parallel, completing into the decode pipeline. Sizing: the GETs themselves are I/O-bound (async in-flight may exceed core count; the real ceilings are store throttles — S3 ~5,500 GET/s/prefix, Azure per-partition limits — and NIC bandwidth); the ~40%-of-cores bound applies to the decode-coupled completion work (zstd, SQ8 parse, distance kernels), with pure prefetch allowed a higher in-flight cap. Env: PROXIMADB_READ_RANGES_PARALLEL (0 = sequential, default until measured), PROXIMADB_READ_RANGES_INFLIGHT (prefetch cap). Benefits PXH1 segments equally; lands independently of the successor layout. Acceptance: SIFT1M cold p50 improves ≥2× at equal GETs; io_trace gains fetch_rounds + max_inflight fields.
```
