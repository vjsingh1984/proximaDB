= TD-CACHE-4: The ADR-065 warm-tier caches were never armed on the live path — every novel query re-paid the full GET chain

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Resolved (in the same PR that found it; budgets finalized 2026-07-24).** The engine constructor arms both caches config-first (`SstConfig.segment_invariants_cache_mb` default **256 MB** — pins Region A for ~10× 1M-vector collections @128d, ~1.2× @1536d since Region A = (d/8+8)·N; `SstConfig.survivor_cache_mb` default **1024 MB** — DEFAULT-ON, an explicit update of ADR-065's default-OFF now that eviction policy is sound (TD-CACHE-2) and the OFF state was proven never-armed anyway). Env overrides win (`PROXIMADB_SEGMENT_INVARIANTS_CACHE_MB` / `PROXIMADB_SURVIVOR_CACHE_BUDGET_MB`); 0 disables. Micro/free-tier profiles set both small via config.
| Priority | **P1 (was silently costing GETs on every novel query).**
| Component | `src/storage/engines/sst/core.rs` (constructor set both caches to `None`; the `with_segment_invariants_cache` / `with_survivor_cache` builder setters had ZERO production callers).
| Evidence | TD-METRICS-1's new hit/miss counters scraped **0** for both caches across a 920-query 1M SIFT run in which `proximadb_queries_total` advanced normally and hot repeats served at 2,455 QPS — proving hot traffic was the QUERY-RESULT cache (exact repeats only) and the warm tier never executed. `grep -rn "with_segment_invariants_cache\|with_survivor_cache"` → definitions only. The mechanism itself was proven by unit/bench tests (`survivor_cache_reduces_gets_on_hot_repeat_query`, the ADR-065 PR3 hot-query eval) — the wiring from `SharedServices`/engine init was simply never added.
|===

== Why it mattered

Without the warm tier, only byte-identical repeat queries are cheap (result
cache). Any *novel* query — the realistic hot workload — paid the full ~36
GETs/query even against fully warm segments, i.e. the billed/latency profile
assumed "cold" for everything but exact repeats. The hot-cache product tier
($0.15/GB-mo) had no serving mechanism enabled. All of TD-CACHE-1/2/3 build on
these caches; they must exist to be warmed, policied, or tenant-floored.

== Lessons

1. **A cache that exists only behind an unused builder setter is dead code** —
   arming belongs at construction with an env/config gate, not in a setter
   waiting for a caller nobody wrote.
2. **The absent-vs-zero metrics distinction found this** (`touch()` at boot +
   counters at the lookup boundary): a scrape showing `0` after a 920-query
   run is a wiring alarm; an absent family hides it. Instrument-first pays
   again.
3. Documented env vars need a grep-able read site; `PROXIMADB_SURVIVOR_CACHE_BUDGET_MB`
   existed in docs/memory only.

== Verification
- Live: 100k ingest + repeat-novel-query pass → `segment_invariants_cache_{hits,misses}_total`
  both advance; with `PROXIMADB_SURVIVOR_CACHE_BUDGET_MB` set, survivor
  hits/misses advance and repeat-novel queries show reduced `object_store_gets`.
- The existing `survivor_cache_reduces_gets_on_hot_repeat_query` +
  `invariants_cache_evicts_priority_then_recency` unit tests cover mechanism +
  policy.
