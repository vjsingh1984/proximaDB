= TD-DECOMP-82: Seed the `proximadb-sst-engine` crate + three supporting hoists
:id: TD-DECOMP-82
:status: implemented
:date: 2026-08-16
:phase: root-crate decomposition — phase 6, PR C

== Problem

The SST engine dir (`src/storage/engines/sst/`, ~60K LOC) is the largest
remaining root-crate block. Whole-dir extraction needs an engine-port surface
that doesn't exist yet, but the phase-6 survey found five leaf files whose
coupling was already dissolved — enough to start the destination crate the
right way rather than extracting into a grab-bag.

== Change

1. **New crate** `crates/storage/proximadb-sst-engine` (all three Cargo.toml
   wirings: workspace member, `[workspace.dependencies]`, root `[dependencies]`).
   Seed modules (moved via `git mv`):
   - `error.rs` (59) — `SstError`/`Result`; the FilesystemError variant re-points
     at `proximadb-storage-filesystem-types` (same enum via the root re-export).
   - `row_filter.rs` (418) + `row_filter_tests.rs` — zero root deps after the
     survey rewrites (ProximaDataBlock ← engine-core, metadata helpers ← the
     hoist below, `evaluate_filter_proxima` ← search-types shim target).
   - `staged_write.rs` (420) — `Arc<FilesystemFactory>` →
     `Arc<dyn FilesystemPort>`; its API (`StagedSegmentWrite`,
     `LocalizedSegment`, `read_object_bytes`) widened `pub(crate)` → `pub`
     (cross-crate consumers in root sst compaction/search/flush).
   - `deletion_vector_store.rs` (422) — fs port swap; tests use the new
     `test_local_port` (tokio::fs-backed `FilesystemPort`, same shape as
     engine-core's TD-78 stub).
   - `decompression_cache.rs` (736) — cache-stats refs resolved by the hoist below.
2. **Hoist `write_strategy.rs`** (66 LOC) → `proximadb-storage-common`
   (`WriteStrategyFactory`/`MetadataWriteStrategy`; only deps are
   filesystem-types). Root `persistence/filesystem/` keeps a `pub use` shim;
   its 7 consumers (transaction_coordinator, WAL ×4, sst ×2) unchanged.
3. **Hoist `UsageStats` + `CacheStatsProvider`** (orchestrator.rs:622–630) →
   `proximadb-storage-ports` (beside `CacheAccessPatternPort`); the root
   orchestrator re-exports back. Graph service, viper, and sst implementers
   unchanged.
4. **Hoist `proto_metadata_helper.rs`** (186 LOC) → `proximadb-storage-common`
   — row_filter's last root dep; `proto` + `serde_json` only (both already
   storage-common deps). Root `src/core/` keeps the re-export shim.
5. **Root call-site coercions** (9 sites across compaction/search/flush):
   `self.filesystem()` / `&self.filesystem_factory` → new
   `filesystem_port()` accessors on `SstEngine` (core.rs) and `Compaction` —
   `FilesystemFactory` impls the port root-side, callers coerce at the boundary.
6. Root `sst/mod.rs` shims: `pub use proximadb_sst_engine::{error, row_filter,
   staged_write, deletion_vector_store, decompression_cache}`.

== Manifest note (recurring hazard)

The root `Cargo.toml` has an entry for `proximadb-engine-core` under
`[dependencies]` at the file tail (beside the raptor NAPI-RS block) — an edit
that relocates "the duplicate-looking" line silently removes the root's dep and
breaks ~40 `proximadb_engine_core::` shims. This PR restored it after hitting
exactly that. Future manifest edits: verify each section header, never delete
by name-match alone.

== Deviation notes

- `row_filter`'s `get_or_convert_vector_metadata` deleted: dead code with zero
  callers workspace-wide, flagged by the crate clippy gate (root's crate-level
  allows suppressed it — the recurring "allows don't travel" class).
- `staged_write`/`deletion_vector_store` tests now exercise the port seam via
  `test_local_port` instead of constructing the real `FilesystemFactory` —
  the production path keeps the port, tests keep real files on disk.
- `multi_stage_filter.rs` deferred (needs `ReadStrategy` from
  sst_query_engine — pull that whole file with its reader in a later wave).

== Impact

~2,545 LOC out of the root crate; the sst-engine crate is live with the
correct dependency posture (ports + extracted siblings only — zero root deps),
so later waves (segment_format, compaction, query engine) peel into it without
re-plumbing. Three cross-cutting vocabulary types (`WriteStrategyFactory`,
`CacheStatsProvider`/`UsageStats`, proto metadata helpers) now live where
storage-tier consumers can name them.
