== Context

After the data-structure-efficiency program (TD-DSEFF-1, #1735/#1737/#1738)
and the embedded engine-routing fix (#1743) landed, an adversarial re-review
of all four PRs' already-merged code was run at the user's request (in
conjunction with the ADR-093 VIPER-retirement re-check). Three independently
dispatched review passes (one per PR group) surfaced six findings. This TD
tracks the ones not folded into ADR-093 or fixed inline.

== 1. CatalogCache shared eviction ring — FIXED

See link:TD-CAT-5-catalog-cache-eviction-scan.adoc[TD-CAT-5]'s follow-up
section. High confidence, high severity (defeated the cache's own capacity
bound under realistic multi-family traffic). Fixed same day by splitting the
ring per map family; regression test added.

== 2. NOVA `vector_by_id` lacks MVCC version resolution and tombstone filtering — FIXED

`src/storage/engines/nova/engine.rs` (`vector_by_id`): #1743 replaced a
hardcoded `Ok(None)` stub (which silently made every upsert re-insert as a
duplicate) with a real point-read that resolved by
first-match-in-file-listing-order and did not filter tombstoned/expired
records at all.

Fixed by rewriting `vector_by_id` to scan the raw Arrow columns per file/row
(mirroring the `(version, timestamp)` best-match comparator VIPER's own
point-read and the shared compaction dedup
(`columnar_compaction.rs::deduplicate_arrow_batches`) already use), resolving
the MVCC winner across *all* candidate rows in *all* files before any
liveness check — a tombstone is itself a newer version and must be able to
shadow an older live one (CLAUDE.md invariant 16d). The winning row converts
to `ProximaRecord` via the existing `From<VectorRecord> for ProximaRecord`
(`conversions.rs`), which already correctly derives `valid_to_ns` (ns) from
the on-disk millisecond `expires_at` column, preserving the `Some(0)`
tombstone sentinel; the canonical `ProximaRecord::is_dead(now_ns)` then gates
the return.

Two byproduct findings surfaced while implementing this, both about
already-merged VIPER code (not fixed — VIPER isn't in this TD's scope):

* VIPER's point-read compares the millisecond `expires_at` column against
  `chrono::Utc::now().timestamp_micros()` — a 1000x unit mismatch that makes
  any record with a real future expiry read as already-expired.
* VIPER's point-read also skips liveness mid-scan (`continue` on an
  expired/tombstoned row) *before* MVCC resolution, so a stale live version
  can win over a newer tombstone instead of being shadowed by it — the fix
  here deliberately resolves MVCC first, then checks liveness once on the
  winner, to avoid reproducing this.
* NOVA's `FIELD_VERSION` Parquet column is `UInt32` (`schema_builder.rs`),
  while VIPER's own factory schema (`viper/factory.rs`) declares the same
  logical column `Int8` — a third VIPER-side type/unit inconsistency in this
  code family, also not fixed here.

Tests: `tests/integration/nova_engine_test.rs` —
`test_nova_vector_by_id_returns_latest_version_across_flushes`,
`test_nova_vector_by_id_hides_tombstoned_record`,
`test_nova_vector_by_id_filters_ttl_expired_and_returns_live`.

== 3. Embedded migration risk from the #1743 routing fix is undocumented — FIXED

`crates/binding/proximadb-embedded/src/lib.rs` (`EmbeddedProximaDB::new`)
previously had no detection for the case where a pre-existing embedded
deployment's non-SST-declared collection has old SST-formatted data
(residue of the bug #1743 fixed) that its declared engine's
extension-filtered reader can never see — a mixed-read-safety gap against
CLAUDE.md directive 8 (format transitions must be detectable, never
flag-day).

Fixed with a one-shot, best-effort, log-only scan at the end of
`EmbeddedProximaDB::new`: for every collection whose declared engine isn't
SST, list its data directory and — if non-empty and every file carries the
legacy `.sst` extension — emit a `tracing::warn!` naming the collection, its
declared engine, and re-ingest as the remediation. The decision logic is
factored into a pure `engine_data_mismatch(&[String]) -> bool` helper for
direct unit testing; never blocks or fails startup (all internal errors are
swallowed, matching the no-`.unwrap()`/`.expect()`/`panic!()` mandate).

Tests: `crates/binding/proximadb-embedded/src/tests.rs` —
`engine_data_mismatch_detects_sst_only_directory`,
`engine_data_mismatch_ignores_empty_directory`,
`engine_data_mismatch_ignores_directory_with_declared_engine_files`,
`reopen_does_not_fail_on_mismatched_pre_fix_collection_data` (end-to-end:
plants real pre-fix-shaped residue via the filesystem, reopens against it).

== 4. raptor `select_nth_unstable_by` — nondeterministic tie-break vs. old stable sort

`src/storage/engines/raptor/` (matrix_builder / writer.rs partial-sort sites
from #1737): `select_nth_unstable_by` does not guarantee the same tie-break
order as the previous `sort_by` at exact float ties. Low severity (raptor is
`experimental-engines`-gated, not on the GA path) and narrow (only affects
ordering among exactly-tied distances, not correctness of the top-k set
itself). Recorded for completeness; not scheduled.

== 5. Skiplist memtable `clear_up_to` two-phase unlocked-gap race

`src/storage/memtable/implementations/skiplist.rs` (~lines 164-187, from
#1738): removal from the `key_index` BTreeSet and removal from the DashMap
happen as two separate un-atomic phases, leaving a window where a concurrent
reader could observe a key present in one structure but not the other.
Self-healing (both removals do complete) and narrow (only visible mid-clear
under concurrent access to the range being cleared). Not scheduled; revisit
if a range-scan-during-clear bug report ever surfaces.

== 6. gRPC BatchWriteStream — un-type-enforced all-or-nothing assumption

`src/network/grpc/v2/record_service.rs` (~lines 1723+, 1830-1840, from
#1738): batching groups consecutive same-write-mode records into one
pipeline call with per-record retry-on-failure, relying on the batch write
path being atomically all-or-nothing. `BatchOperationResult::partial()`
(`crates/platform/proximadb-runtime/src/batch_result.rs:81-93`) exists but
has zero callers in this path today — if a future change to the underlying
batch write ever returns a partial result, this call site would silently
mishandle it. Latent landmine, not a live bug. Candidate fix: either wire
`partial()` handling defensively now, or add a debug-assert that the
underlying result is never partial, so a future violation fails loudly
instead of silently. Not scheduled — no current caller returns partial.

== 7. Cosmetic — not tracked further

* `src/index/axis/management/manager.rs::query_hnsw_with_predicate`
  (~lines 1986-2059, from #1735) holds a read-lock guard across the full
  HNSW search await — contention/latency concern only, not correctness.
* `src/storage/flush_materializer.rs`'s
  `adr081_engine_instance_is_canonical_per_format` test (~lines 1506-1542,
  from #1743) was mechanically weakened during the fallback→register_engine
  rewiring and is now trivially true rather than exercising real contention
  resolution. Worth tightening next time that test file is touched; not
  worth a standalone PR.
