= TD-PATH-1: cwd-relative default paths cross-contaminate server instances (`-d` does not move storage/metadata)
:status: S1 shipped (2026-07-25, this PR — `-d` rebases built-in defaults)
:filed: 2026-07-25
:priority: P1 before any multi-node topology (ADR-073 prerequisite)

== The finding (observed 2026-07-25 during the recall adjudication)

`-d/--data-dir` sets ONLY `config.server.data_dir` (main.rs). The storage
location (`file://./data`), catalog root (`metadata_url = file://./metadata`),
WAL dir (`./data/write_buffer`) and viper dir (`./data/viper_data`) are
SEPARATE relative defaults resolved against `std::env::current_dir()` at
config-load (`config_loader.rs:249,311-316`). Every server launched from one
working directory therefore shares `<cwd>/data` (all collection UUID dirs,
via `collection_*_path` in `services/collection/manager.rs:2066-2118`) and
`<cwd>/metadata` (ONE catalog — the collection-id allocator floor is
recovered by scanning it, `shared_services.rs:766-784`, which is why a
"fresh" `-d` datadir minted collection_id 2). Observed blast radius:
cross-instance catalog pollution between concurrent benchmark sessions, and
a violation of the path-isolation mandate (all writes under DrPathBuilder /
configured roots).

== S1 (shipped): `-d` rebases built-in defaults

`rebase_default_relative_paths` in `apps/proximadb-server/src/main.rs`: when
`-d <dir>` is given, any of the four locations still at its BUILT-IN
cwd-relative default is rewritten under `<dir>` (logged at info). Explicitly
configured URLs are never touched — zero behavior change for deployments
that set their paths, mixed-safe by construction.
