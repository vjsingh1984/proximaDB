= TD-DECOMP-64: Rename document-field geo-index crate to resolve duplication

[cols="1,3", options="header"]
|===
| Field | Value
| Status | Landing

| Component | `crates/horizontal/proximadb-document-geo-index`; root `src/storage/document/indexes/mod.rs`

== Problem
TD-DECOMP-39 extracted the document-field geohash index as `proximadb-geo-index`. TD-DECOMP-62
extracted the index/geo spatial search index as `proximadb-geo-spatial-index`. Both define a
geohash-based `GeoIndex` struct — a competing-abstraction quality concern and naming confusion.

== Fix
Renamed `proximadb-geo-index` → `proximadb-document-geo-index` (making its document-field role
explicit). The crate serves the document-storage indexes subsystem (TD-39); `proximadb-geo-spatial-index`
(TD-62) serves the index/geo spatial-search subsystem. The naming is now unambiguous.

== Future work (algorithm dedup)
TD-39's `geo_index.rs` has its OWN inline geohash encoder/decoder. It should depend on the shared
`proximadb-geohash` crate (TD-60) instead of duplicating the algorithm. File as a follow-up TD.
Also, TD-39's `GeoPoint { lat, lon }` vs geo-types' `GeoPoint { latitude, longitude }` — field-name
unification when the inline geohash is replaced.

== Verified
Standalone check ✓. Root lib check pending. Behavior-neutral rename (crate name + lib name + shim
path updated; no code logic changes).
