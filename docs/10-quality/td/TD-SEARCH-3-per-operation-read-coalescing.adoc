== Cost model: operations and bytes are different axes

For the Azure Blob **flat Blob endpoint** used by active PAX segments, every
HTTP ranged GET is a read transaction. Hot-tier pricing has no separate
per-GB *data retrieval* fee, so a 72-byte and a 24-MiB range each contribute
one read operation. The exact transaction rate is region, redundancy, and
account dependent; `$0.005/10K` must not be described as a universal Azure
price.

That does **not** make bytes free:

* larger ranges consume network/NIC and memory bandwidth and can increase
  tail latency;
* cross-region/public transfer can incur bandwidth/egress charges;
* ProximaDB's own scanned-byte KRU term still meters bytes;
* Cool/Cold/Archive tiers add data-retrieval charges;
* hierarchical-namespace/Data Lake endpoints can have different transaction
  categorization and must not be conflated with the flat Blob endpoint.

Therefore a merge is admissible only when the saved round trip is worth its
bounded gap over-read. Optimizing GET count without a byte cap merely moves
the cost.

== Actual v3 layout and dependency chain

The persisted order is:

[source,text]
----
[fixed header, 72 B]
[A0 coarse model + cell directory, variable]
[Region A: RaBitQ header + presence bitmap + cell-major codes]
[Region B: SQ8 params/codes]
[optional OID-position resolver]
[Region D blocks: OIDs, metadata, optional f32 stripes]
[footer index, variable][footer_len][magic]
----

The fixed header is at byte zero and mirrors all region offsets, including
`footer_off/footer_len`. This is deliberate: the reader can discover the
footer with the first ranged GET and does **not** need an object-store `HEAD`
plus tail seek.

The footer is variable because it contains the block table, schema/encoding
map, and optional resolver metadata that are known only after blocks are
written. Keeping it at the tail preserves streaming assembly and mixed-version
readability. Moving it beside the header would require a second-pass rewrite
or a bounded reserved hole and would not eliminate the need for the fixed
header. Duplicating the entire footer in a prefix would also make format
evolution and integrity reconciliation harder.

The efficient policy is:

* keep the fixed routing header at byte zero;
* keep the authoritative variable footer at the tail;
* retain both in `SegmentInvariantsCache` and persistent L2;
* populate them from writer-owned bytes only after atomic publication.

Thus header/footer placement is not the steady-state GET problem. A working
warm tier makes their steady-state object GET count zero.

== Correct adjacency analysis

The prior version made three incorrect assumptions.

. **A0 is not always “a few KB.”** Its exact size is
  `fixed + 4*dim + 4*ncomp*dim + 4*k*ncomp + 4*k + 72*k + checksum`.
  It grows with dimension and cell count.
. **A0 is not generally adjacent to the first selected cell.** Region A has
  its own header and presence bitmap, and the nearest probed cell may occur
  after codes for unselected cells. Joining them can require gap over-read.
. **The footer is not adjacent to the last Region-B survivor range.** The
  optional resolver and Region-D blocks lie between Region B and the footer.
  A `B+footer` merge would read most of Region D and is rejected.

Adjacent *selected cell extents* can still be coalesced, and non-adjacent
extents can be joined when both `max_gap_bytes` and `max_range_bytes` admit the
over-read. Logical selected slices remain unchanged, so recall is invariant.

== Implemented remediation

=== S1: physical GET accounting

`CountingFileSystem::read_ranges(path, ranges)` now adds `ranges.len()` physical
range operations because the trait's default implementation issues exactly
that many `read_range()` calls. The recorder receives the physical count too.
This fixes benchmark/metering under-counting; a future backend that implements
a true one-request multi-range API must override both the I/O method and its
physical-operation report.

The invariant is:

[source,text]
----
physical ranged HTTP requests == counted range operations
----

A Rust function call named `read_ranges` is not evidence of one cloud request.

=== S2: bounded prefix read

On a cold invariants miss, the reader now fetches a bounded prefix:

* default: 1 MiB;
* `PROXIMADB_PAX_PREFIX_PREFETCH_BYTES=0`: kill switch;
* explicit values are clamped to 8 MiB.

The same byte buffer supplies the fixed header and, when fully covered, A0,
the RaBitQ control header, and early selected-cell ranges. No bytes are
reinterpreted: every consumer takes its original exact logical slice.

This speculative prefix is intentionally bounded. If A0 or a selected cell
does not fit, the reader performs the normal exact ranged read. The expected
cold saving is workload/layout dependent and must be measured; it is not
asserted as “one GET per segment” for every segment.

=== S3: existing selected-range coalescer

`plan_probe_cell_ranges()` remains the correct cell-data seam. It sorts extents
in file order and merges only under `ObjectRangeCoalescePolicy` gap/range
bounds. It never changes `nprobe`, selected rows, or ranking inputs.

== Remaining inefficiencies

* The filesystem trait's generic `read_ranges()` is bounded-concurrent but
  still N physical GETs. Concurrency reduces latency waves, not billable
  operations.
* Concurrent identical misses can race through the cache and issue duplicate
  object GETs. Singleflight by immutable `(path, offset, len)` is the next
  operation-only reduction.
* Exact range keys miss when one request asks for a subrange of a cached parent.
  The write-time SQ8 seed now has an explicit parent-range lookup; the general
  cache can later grow interval containment if evidence warrants it.
* `nprobe` multiplies both Region-A and Region-B work. A recall-ratcheted
  nprobe reduction is potentially larger than all control-read coalescing.
* Segment count remains the outer multiplier. Coalescing does not substitute
  for higher-level consolidation.

== Verification gate

Close this TD only with a benchmark that records, for the same fully
materialized segment geometry:

. physical GETs/query by PAX region/tier;
. bytes/query;
. cold and NVMe-warm p50/p95;
. segment count and level distribution;
. recall@10 (must not regress below the ratchet);
. prefix disabled (`0`) versus 1 MiB versus a justified alternative.

The benchmark must wait for flush/compaction quiescence and prove that all
1M vectors are searchable from materialized segments before restarting.
