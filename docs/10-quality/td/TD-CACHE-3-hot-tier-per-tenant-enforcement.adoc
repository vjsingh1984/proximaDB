= TD-CACHE-3: Hot-cache tier has no per-tenant enforcement — the $0.15/GB-mo pinning contract is unenforceable in v1

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Proposed.** Filed from the 2026-07-24 capacity/pricing session: the hot-cache product tier is the single best margin-per-dollar item on the price card (sells RAM at $0.15/GB-mo that costs ~$0.04/mo per pinned 1M-vector tenant, and converts a tenant from the ~6–10 QPS cold regime to the 2,700 QPS hot regime) — but the serving cache cannot enforce it.
| Priority | **P1 before the hot tier is SOLD** — until then P2. Selling a pinning contract the cache can evict arbitrarily (by another tenant's churn) is a latent SLA breach.
| Component | `src/storage/engines/sst/survivor_range_cache.rs` (`TENANT = "survivor-cache"` — a single shared pseudo-tenant, noted in-code as v1), `crates/foundation/proximadb-cache` (`TenantCache` — already multitenant-capable: per-tenant budgets/stats exist and are UNUSED by this caller), the search path (does not thread `tenant_id` to the cache today).
| Evidence | `survivor_range_cache.rs` comment: "v1 uses a single shared tenant (one elastic pool); per-tenant fair-sharing is a follow-up that threads the real tenant_id into the search path." `TenantCache` already supports `CacheBudget` per tenant + per-tenant `tenant_stats()` — the mechanism exists, the caller collapses all tenants into one.
|===

== The finding

The commercial hot tier is a *contract*: a paying tenant's working set stays
resident. Today all tenants share one elastic pool under one pseudo-tenant id,
so any tenant's churn can flush any other tenant's survivor ranges — including
a tenant paying for pinning. The multitenant cache underneath already has the
budget machinery; only the wiring is missing.

== Direction

S1 — **Thread the real `tenant_id`** from the search path into
`SurvivorRangeCache::get_or_fetch` (the `CacheKey` already carries a tenant
field). Per-tenant hit/miss/bytes fall out of the existing `tenant_stats()`
(and fix the TD-METRICS-1 gauges from sums to labeled per-tenant series when
cardinality allows).

S2 — **Pinned floors from entitlements**: map the hot-tier purchase (control
plane / tiers.json entitlement) to a per-tenant `CacheBudget` floor — the
tenant's pinned GB is *reserved* (never evictable by other tenants' pressure),
while unpinned tenants share the remaining elastic pool, work-conserving.

S3 — **Enforcement metering**: emit per-tenant pinned-bytes vs entitled-bytes
so billing can true-up (charge for what is entitled, alert when residency
cannot be honored — that is a capacity signal to move B4ms → E-series, per the
2026-07-24 instance-family analysis).

== Verification
- Two-tenant test: tenant A pinned (floor = its working set), tenant B churning
  a larger-than-pool set → A's hit rate stays 100%, B evicts only its own.
- Hot-tier QPS contract: A's measured latency stays in the hot regime
  (sub-ms, 0 GETs) throughout B's churn.
