== Why

Continues the cluster extraction after the rpc moves (TD-DECOMP-3/4). A full coupling scan
of `src/cluster/` found four **fully self-contained** subsystem files — zero `crate::`/`super::super::`
climb-out, deps only `proximadb-config` + external crates — that move verbatim with no rewrites:
`shard` (23 tests), `cache_affinity` (9), `node_registry` (3), `metadata_service` (3) = **38
tests** out of the root lib binary. They move to the platform-tier `proximadb-runtime` (legal:
platform depends on every layer except root/app/binding).

== What moved (behavior-neutral)

* `src/cluster/{shard,cache_affinity,node_registry,metadata_service}.rs` →
  `crates/platform/proximadb-runtime/src/cluster/` (verbatim — zero path rewrites; all four
  have no `crate::`/`super::super::` code refs).
* `proximadb-runtime/src/cluster/mod.rs` declares the four modules; `src/lib.rs` declares
  `pub mod cluster;`.
* `proximadb-runtime/Cargo.toml` gains `chrono` + `dashmap` (workspace; `proximadb-config`,
  `serde`, `tokio`, `anyhow` already present).
* Root `src/cluster/mod.rs` drops the four `pub mod X;` and adds
  `pub use proximadb_runtime::cluster::{cache_affinity, metadata_service, node_registry, shard};`
  — so the remaining root-side cluster files (`distributed_ops`/`replication`/`consensus`/etc.)
  and all external callers resolve unchanged.

== Verification

* `cargo check -p proximadb-runtime` green (moved files + chrono/dashmap deps compile).
* `cargo check -p proximadb` green (root compiles through the re-export).
* `cargo nextest run -p proximadb-runtime --lib` — runtime gains the 38 tests (54→92 on this
  base; 111 once TD-DECOMP-4's rpc-client lands).
* `cargo nextest run -p proximadb --lib` green — root lib test binary shed the 38 tests.
* `python3 scripts/check_workspace_boundaries.py` + `scripts/check-layering.sh` green.
* `cargo build -p proximadb-server` + `cargo clippy --lib --bins -- -D warnings` +
  `cargo fmt --check` + `make work-commit-check` green.

== Follow-ups (out of scope here)

* `consensus` (17 tests) is the next clean cluster file — it imports `ConnectionManager`/
  `ConnectionPoolConfig` from `rpc/connection`, so it moves once TD-DECOMP-4 (#1371, the
  tonic rpc-client) lands. Its only rewrite is `super::rpc::`/`super::super::rpc::` →
  `crate::cluster_rpc::`.
* `distributed_ops`/`replication` are tangled with the climbers (`distributed_ops`→`routing`,
  which couples to `crate::catalog`) — they need `catalog`/`network`/`storage` extracted to
  crates (the structural enabler) before they can move.
