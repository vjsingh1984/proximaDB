= TD-IOBUDGET-1: TOML-driven per-location I/O budgets — operator-configurable ranged-GET geometry without a redeploy
:icons: font

**Status:** RESOLVED. Shipped 2026-09-02: `[[storage.storage_locations]] io_budget`
(disk_class + explicit byte bounds), fail-closed validation at config load,
authoritative boot registration + audit dump in `ProximaDB::start`, and the
storage-common longest-prefix registry.
**Origin:** ADR-073 shipped `PROXIMADB_DISK_CLASS` as a stopgap and said so —
"per-location tags don't reach this leaf crate." This TD executes the full seam.

== The problem (all three legs measured)

`IopsBudget` (crates/storage/proximadb-storage-common/src/iops_budget.rs) sizes
every ranged GET the engine issues. Before this TD it resolved from **hardcoded
per-URL-scheme constants** plus one env hint, which has three measured defects:

. **The default planner is measured-suboptimal on Azure.** TD-SEARCH-3's
committed wire sweep shows the 8 MiB latency knee (−29% p50) and the 16 MiB
GET knee (−24% GETs) at recall parity — but the default Azure planner stays at
4 MiB unless an operator knows an env var exists.
. **The disk-class hint is scheme-scoped and pod-wide.** `PROXIMADB_DISK_CLASS`
covers `file`/`minio` paths for the whole process. It cannot express "this SAS
RAID10 location is HDD, that NVMe location is SSD" in a multi-location
deployment — which is the ADR-073 motivating deployment (dataserver2's PERC
H710P: random-1MiB 99.8 MiB/s vs random-128k 16.9 MiB/s; the coalescing profile
is the difference between ~2.6 and ~12 QPS).
. **The effective budget is unauditable.** No boot dump, no validation, no
record of what geometry a location actually ran with. Operator errors surface
only as latency.

== Consumer inventory (what the budget influences — verified 2026-09)

[cols="2,3,3", options="header"]
|===
| Site | What it resolves | Notes

| `sst/segment_format.rs` (4 coalescing-policy sites)
| `IopsBudget::for_path` per read-policy decision
| Per-call, uncached → config effective on restart

| `resolve_adaptive_range_policy` (chooser cap enumeration)
| `read_range_cap_candidates`
| A registered budget tightens the enumeration to its own `max` (never below
its own `target` — an explicit target ABOVE a scheme ceiling is deliberate
operator intent and is honored; scheme ceilings bound unregistered paths)

| `filesystem/mod.rs` `range_coalesce_policy_for`
| `budget.max` ceiling on merged ranges
| Same resolution, per call

| `sst/block_cluster.rs` `ivf_fine_cell_count` (writer)
| `write_target_block_bytes` → `for_path`
| NOT registry-reachable today: the sole call site passes `None` (destination
unknown at clustering time), so writer geometry stays the CLOUD constant.
Plumbing the destination URL from the flush/compaction caller is the TD-IVF-4
follow-up

|===

Explicitly NOT influenced: PAX block byte geometry (the PAX writer's own
constants + `PROXIMADB_PAX_BLOCK_SIZE` + `SstConfig.block_size_kb`) — mixing
that into this budget would silently change flush output. Also out of scope:
the chooser default flip (a separate measured decision; TD-SEARCH-3/ADR-052
evidence) and hot reload (the repo is restart-to-apply; `ConfigReloader` stays
dormant).

== Design

=== Operator surface (TOML)

[source,toml]
----
[[storage.storage_locations]]
url = "file:///mnt/sas-raid/data"
tags = ["durable"]
[storage.storage_locations.io_budget]
disk_class = "hdd"        # "ssd" | "hdd" | "cloud"; optional
# min_bytes / target_bytes / max_bytes override the profile per-field.

[[storage.storage_locations]]
url = "s3://bucket/"
[storage.storage_locations.io_budget]
target_bytes = 16777216   # the measured TD-SEARCH-3 16 MiB GET knee
max_bytes = 16777216
----

=== Layering (the ADR-073 seam, done)

Foundation may depend only on foundation
(`check_workspace_boundaries.py`: "foundation crates may only depend on other
foundation crates"), and storage→foundation is the blessed downward edge (the
ADR-024 comment in storage-common's Cargo.toml). Therefore:

* `IoBudgetConfig` + `DiskClass` (serde) live in **proximadb-config**
  (foundation, next to `StorageLocation`).
* The leaf (storage-common) gains **zero new dependencies**: a registry of its
  OWN type — `register_location_budget(url_prefix, IopsBudget)` +
  `location_budget_for(path)` (longest matching prefix, `/`-boundary-checked,
  insert-overwrite per TD-COMPACT-9).
* The root crate converts (config → budget) and seeds at boot.
* `for_path` = registry → `for_scheme_and_env` (the old scheme + env logic,
  unchanged); **zero changes at the consumer sites**.

=== Precedence (specific beats general)

Within one `io_budget`: explicit `*_bytes` fields override the `disk_class`
profile, which overrides the scheme default. The `PROXIMADB_DISK_CLASS` env
var (file/minio/bare paths) supplies the device CLASS wherever `disk_class`
is UNSET — including inside a partial io_budget: env is the pod-level
hardware-truth signal and bytes are refinements, so a pod-wide
`PROXIMADB_DISK_CLASS=hdd` composes with a per-location `max_bytes` cap.
`cloud` is scheme-aware (`IopsBudget::scheme_cloud_budget`): a `file://`
location gets CLOUD; `s3://` keeps the S3 profile.

=== Fail-closed + auditable

* Unknown `disk_class` value or unknown key inside `[io_budget]`
  (`deny_unknown_fields` — a `target_byets` typo) **fails config load**.
* Bad bounds (`min` below the 64 KiB floor, `min > target`, `target > max` —
  including a per-field override that breaks its profile's own invariant)
  **fail startup** via `validate_config` and `register_io_budgets`.
* `ProximaDB::start` INFO-dumps the resolved table: every location →
  registered min/target/max, or "scheme default" — the audit artifact.
* Duplicate location URLs with CONFLICTING resolved budgets fail startup
  (`validate_io_budget_conflicts`, checked at load AND boot): the registry is
  URL-keyed, so insert-overwrite would silently let the last entry win.
  Identical budgets and budget-less duplicates stay allowed.
* Boot seeding is authoritative-REPLACE (`clear_location_budgets` drains the
  registry before re-registering): a location dropped from a later config
  stops serving its stale budget to an in-process re-boot (embedded re-init,
  test suites).

== Verification

Leaf + root unit tests: profile mapping, per-field overrides (including the
16 MiB S3 opt-in), bounds failures, TOML typo rejection (bad enum value,
unknown key), `StorageLocation` round-trip, registration fail-closed with the
URL named in the error, longest-prefix + `/`-boundary + overwrite semantics,
and the cap-enumeration tightening. Unregistered paths keep byte-identical
behavior (the existing Azure `[4, 8, 12, 16, 24] MiB` ratchet test is untouched
and green).
