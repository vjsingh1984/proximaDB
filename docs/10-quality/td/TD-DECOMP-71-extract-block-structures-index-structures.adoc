== What moved
Phase 3 Step 3 — the largest single-file extraction of the engines program:

* `block_structures.rs` (5,711 LOC, 29 tests via `#[path]`-included `block_structures_tests.rs`)
  — `ProximaDataBlock` (used 358× codebase-wide) and 32 sibling pub types: the PAX block
  container, encode/decode via ProximaCodec, adaptive bloom integration, JSON/metadata serde.
* `block_structures_tests.rs` (830 LOC).
* `index_structures.rs` (791 LOC) — block-level index types (BlockLocation etc.).

== Dependency analysis flipped the planned order
The plan ordered by raw `crate::` ref count (block_reader 4 first). The real analysis showed
*what the refs point at* matters more: every one of block_structures' 31 refs resolves to an
already-extracted crate via root re-export shims — `crate::core::bloom` → `proximadb-bloom`,
`crate::core::compression` → `proximab-compression`, `...ops::proximacodec` → `proximadb-codec`,
`crate::core::search::json_value_serde` → `proximadb-search-types`, `crate::proto` →
`proximadb-proto`, `super::engine_profile` → `proximadb-storage-common`. Meanwhile the
"low-coupling" files (block_reader/sst_metadata/swift_metadata) are blocked by UNEXTRACTED root
`FileSystem`/`FilesystemFactory` — they wait on the filesystem port.

New engine-core deps: bloom, codec, search-types, proto, data-model, quantization-model (all
`{workspace=true}` except bytemuck — root-package-only, inline spec), bincode, rayon, tokio,
tracing; dev: rand.

== Shims
Root `proximablocks/mod.rs`: the two `pub mod` decls → `pub use
proximadb_engine_core::proximablocks::{block_structures, index_structures};` — the parent's
`pub use block_structures::{...}` / `pub use index_structures::{...}` re-export blocks are
unchanged, so every consumer path in root/crates keeps resolving.
