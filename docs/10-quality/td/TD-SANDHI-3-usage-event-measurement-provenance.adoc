== Context

The 0.1.5 schema sync added measurement-provenance fields to the local `usage-event.v1` mirror —
`duration_ms`, `time_to_first_token_ms`, `usage_completeness`, `usage_basis` (plus
`attempts` / `outcome` / `upstream_request_id`). Round-trip tests parse them against the
authoritative `sandhi_core::UsageEvent`, but **no emit site populated any of them**: every event
serialized without the keys, so downstream consumers saw only schema defaults. That is actively
wrong for `usage_completeness`, whose default is `Unavailable` — every event ProximaDB emits
carries a complete accounting for its logical call. And with no `duration_ms`, latency-minded
consumers had to infer timing from log timestamps.

The emit seam itself "didn't measure latency": the generation providers *do* measure
`response_time_ms` at the adapter boundary, but nothing flowed it into the event — and the
embedding path measured nothing at all (no bracket existed anywhere in it before this change;
the bracket this change adds lives in the embedding service's scheduler worker, not the
drainer).

== Change

. **Generation path** (`emit_generation_usage` / `build_generation_event`): a new `duration_ms`
  parameter — the provider adapter's measured `response_time_ms`, already in scope at all 7
  provider emit sites — plus provenance stamps mirroring sandhi-core `ParsedUsage::apply`'s
  fill-if-empty semantics: `usage_completeness = Final`, `usage_basis = ProviderReported`, and
  `outcome = "success"` (emit sites are success-path only — verified per provider — and unlike
  the other measurement fields an omitted `outcome` decodes to *no default*, so a
  `outcome == "success"` filter — natural against the reference producer, which always stamps
  one — would drop every ProximaDB event).
. **All-zero usage is no measurement (adversarial-review guard).** `{"usage":{}}`, `"usage":null`,
  wrong-typed values, and explicit zeros (Ollama reports `prompt_eval_count: 0` on cached prompts)
  all parse to zero counts — the guard drops an event only when *every* count is zero
  (tokens_in/out, both cache splits, and reasoning tokens, which count as billable signal).
  sandhi-core's own Cohere parser drops these ("rather than fabricate a zero-token event — a
  silent, wrong measurement"); we guard at our parser dispatch so every arm gets it. Deliberately
  *stricter* than sandhi's own producers (which stamp `Final` zeros): dropping only loses a
  zero-token billing signal, while certifying a zero as final + provider-reported poisons the
  very trust filter `usage_completeness` exists to enable. Same guard added to the OpenAI/Azure
  *embedding* parsers, where the pre-existing hole was worse: `Some(EmbedUsage{0,0})` certified a
  provider-reported zero **and bypassed the count×512 fallback** (real work billed as 0 tokens).
  The Azure DTO was additionally made *lenient* for usage (wrong-typed values coerce to "no
  usage") — previously a string-typed `prompt_tokens` failed the entire response parse, failing
  the embed call itself.
. **Embedding path**: a `with_provenance(usage_basis, duration_ms)` fluent setter. The wall clock
  is measured **inside the scheduler worker** around `models.embed_batch_with_usage` and carried
  on `EmbedResult::provider_duration_ms` — the schema contract is "adapter boundary … **excludes
  host-side queueing**", and a submit-side bracket smears scheduler backlog (bounded queue of 8)
  into provider latency (up to ~8× under load). The batch's duration is stamped on **exactly one
  designated carrier event per route group** (the first payload): N events × full duration makes
  any `SUM(duration_ms)` rollup report N× provider occupancy (utilization >100%), while
  proportional splitting fabricates per-tenant precision and understates each tenant's real
  latency experience by N×; sum-over-events stays exact and the single honest sample survives.
  Basis: `ProviderReported` for measured input tokens, `Estimated` for the count×512 heuristic
  (local BGE / usage-less BYO contracts); `Final` in both cases — the call is complete,
  estimated-ness is exactly what the basis discriminator expresses.
. **At-least-once redelivery dedupe**: the drainer acks only after every route group succeeds,
  so a failed batch is redelivered and re-embedded — re-emitting every event (and re-accruing
  KEU). Each event now carries the queue `MessageId` (`{partition}:{segment}:{offset}` — stable
  across redeliveries) as its `idempotency_key`, the schema's at-most-once hook. Metering was
  also hoisted **above all shape validation** (per-payload dimension checks and the whole-batch
  vector-count check alike): the provider already consumed the tokens even when the returned
  vectors can't be inserted. A measured batch additionally clamps every record-carrying
  payload's share to a minimum of 1 token (`measured_share`): a floored-to-zero share is
  indistinguishable, on the wire, from the gateway-bug zeros Change §2 refuses to certify, and
  would drop the entire measurement from KEU in the tiny-batch regime (2 tokens / 3 payloads);
  the clamp over-counts by at most one token per floored payload (≤ `batch_size` ≈ 32
  tokens/batch).
. **`time_to_first_token_ms` stays omitted, by design.** The schema scopes it to streams
  ("milliseconds from request start to the first delivered item"); ProximaDB's LLM integration is
  non-streaming only — four of the seven provider request DTOs pin `stream: false` and the rest
  omit the flag entirely (the API default is non-streaming). Fabricating TTFT ≈ duration on
  non-streaming calls would poison the field. Revisit when a streaming provider path lands
  (InferFlux I3's server-side `duration_ms`/TTFT-in-usage is a separate, future parser surface —
  provider-reported timing, not adapter measurement).
. **Seam hygiene**: `UsageBasis` / `UsageCompleteness` are re-exported from
  `proximadb_usage_event::usage_event` so emit sites stamp provenance through the stable crate
  path (SOLID 17a), not the `sandhi_core` internal path. The setter is named `with_provenance`,
  NOT `with_measurement`: sandhi-core's own `UsageEvent::with_measurement(completeness, attempts,
  outcome, upstream_request_id)` sets different fields — the near-collision on the mirrored type
  invited exactly that mixup.

**Non-goal:** `attempts` / `upstream_request_id` stay omitted — the omitted-key defaults decode
correctly for every current emit site. Scope of "no retries", precisely: no provider adapter
retries *within one invocation* (providers are single-shot HTTP calls; the embedding service makes
one attempt per batch; the engine's fallback chain iterates *different* providers, each of which
emits only its own success). The drainer's at-least-once **redelivery** (restart/lease takeover of
a batch whose route group failed) is a queue-level retry of the whole logical call — which is
exactly why events carry `idempotency_key` — and each emitted event still truthfully describes
its own invocation with `attempts` defaulting to 1. No provider DTO surfaces an upstream request
id.

**A note on `Estimated`:** sandhi-core 0.1.6's variant doc scopes `Estimated` to "a stream ends
before the family had reported that category — never on a completed call" — that is *sandhi's own
gateway* semantics (its only `Estimated` producer is interrupted-stream `partial_usage`). The
field's primary definition (and this mirror's doc) is broader: whether the number was
provider-measured or derived. Stamping `Estimated` on a *completed* BYO/local-heuristic embedding
call is the honest signal — the alternative falsely claims the provider measured the count×512
heuristic. Known trade-off: a consumer written to the narrow doc rule (exclude `estimated` from
billing) would unmeter BYO tenants; the pre-change wire was worse in the opposite direction
(absent key decoded `provider_reported` — a heuristic *mislabeled* as measured). **Upstream
follow-up filed:** widen the enum doc, or add an explicit `derived`-vs-`interrupted` distinction
(`anvai-labs/sandhi#184`).

**Inert-by-default preserved:** an event that sets none of the optional fields still serializes
byte-identically to the pre-sync shape (`pre_sync_shape_serializes_byte_identically` keeps
proving it). Note this is now a serde/back-compat property rather than a live emitted shape —
both production emit paths stamp provenance unconditionally; the guarantee that matters is that
*emission itself* stays fully inert without `PROXIMADB_EMIT_USAGE_EVENTS`. The env gate's truthy
spellings (`1`/`true`/`yes`/`on`) and read-once semantics are now documented in
`docs/12-design/ENV_GATE_REGISTRY.adoc` (whose emit-site path had gone stale).

== Known limitations / follow-ups

* **Batch-mate grouping needs an upstream field.** N per-payload events share one provider call,
  but `usage-event.v1` has no batch identifier; overloading `idempotency_key` (would make
  consumers drop N−1 events as retries), `run_id`/`step_id` (agent-tree pollution), or
  `trace_context` (attribution field, grouping not a contract) are all wrong. Filed as
  `anvai-labs/sandhi#183` (additive `batch_id` on `usage-event.v1`). Trap for the implementer:
  the local mirror has no `deny_unknown_fields`, so a local-only field would serialize fine and
  be **silently dropped** by any consumer deserializing into the authoritative type — the field
  must land upstream first.
* **Carrier selection is systematically lopsided per tenant.** The carrier is `group[0]` — the
  lowest partition id present, and partitioning is a stable tenant hash — so in steady multi-tenant
  batches one tenant systematically absorbs the whole batch's `duration_ms` (including other
  tenants' work) and its batch-mates carry none. `SUM(duration)` and global percentiles stay
  exact; per-`group_id` latency dashboards see samples only for carrier tenants. Inherent to
  "one carrier" without a `batch_id`; dissolves when the upstream field lands.
* **Measured-share clamping trades a bounded over-count for zero-elimination.** `measured_share`
  rounds a floored share up to 1, so `SUM(tokens_in)` over a route group can exceed the measured
  batch total by up to one token per floored payload (≤ ~32 tokens/batch, sub-cent at any
  embedding price) — and the tiny-batch regime (`input_tokens < payload_count`) over-counts most.
  The alternative (floor to 0, `provider_reported`) emits a wire shape indistinguishable from the
  gateway-bug zeros Change §2 calls poison, and drops 100% of the measurement from KEU there;
  the heuristic fallback over-counts ~700×. Pinned by
  `measured_share_never_certifies_a_zero` / `split_input_tokens_attributes_by_record_share`.
* **`idempotency_key` uniqueness is queue-scoped.** `MessageId` = `{partition}:{segment}:{offset}`
  is stable across redelivery, but carries no topic/deployment/instance component. Residual
  collision paths: a queue-root wipe (or archive truncation) with a persistent downstream store
  restarts offsets and mints reused ids — first-wins dedupe then drops **real** new events
  (under-billing); a producer retry after disk-append-but-memory-rejection appends at a new
  offset — two events for one logical ingest, not dedupable (at-least-once producer semantics).
* **KEU has no idempotency.** The event dedupes redelivery; `record_keu_units` still re-accrues
  (server-side meter, AnvaiOps ADR-0020 D6). Acceptable while redelivery is rare (it requires a
  restart or lease takeover, not an in-process failure — the read cursor advances on delivery);
  revisit if it is observed. Related half-case: if redelivery regroups payloads differently, the
  surviving (first-wins) event set's carrier may differ from the second attempt's, so the batch's
  `duration_ms` sample can be deduped away — the token accounting is unaffected.
* **`duration_ms` has no ceiling.** sandhi-core clamps token counts at 50e9 against adversarial
  upstreams; our duration is self-measured `Instant` arithmetic, not provider-parsed, so the
  adversarial-input class does not apply. Revisit if a provider-reported duration is ever adopted
  (InferFlux I3).
* **Success-only emission biases latency percentiles** (timeouts/failures emit nothing, so p99
  excludes the slowest population) and the event `duration_ms` can diverge from the
  caller-visible `LLMResponse.response_time_ms` on engine fallback chains (the event carries the
  winning provider's call; the response carries the whole chain — each is correct at its own
  boundary).
* **HuggingFace's generation emit site is dead code** (its body is a JSON array with no `usage`
  object, so the parser always returns `None`) — pre-existing from TD-SANDHI-2, noted here so it
  is not mistaken for coverage. Ironically HF is the one generation provider that computes an
  explicit estimate and would legitimately warrant `usage_basis=Estimated`.
* **Unmetered embedding surfaces:** `EmbeddingService::embed_sync` is also called from
  gRPC `entity_service`, Arrow IPC `service`, and `agent_memory` — no KEU, no event. Pre-existing
  coverage gap, out of scope here.

== Verification

*Pinned by test:*
* `proximadb-usage-event` unit tests: generation events assert `duration_ms` /
  `usage_completeness=final` / `usage_basis=provider_reported` / `outcome=success`, the omitted
  `time_to_first_token_ms`, the all-zero guard (empty/null/wrong-typed/zero bodies emit nothing
  for the openai + anthropic arms) **and its non-over-blocking direction** (cache-only, DeepSeek
  `hit > prompt`, and reasoning-only bodies all still emit); an embedding test stamps both bases
  and the non-carrier `None` duration, round-tripping through the authoritative
  `sandhi_core::UsageEvent`.
* `proximadb-embedding` model tests: all-zero/wrong-typed/total-only/non-object embedding usage
  parses as `None` on **both** the OpenAI (`parse_embed_response`) and Azure (`usage_from_dto` +
  the lenient DTO) paths; the Azure test also pins that no malformed `usage` shape — wrong-typed
  fields or a non-object value — may fail the response parse.
* Drainer unit tests: `build_external_embedding_event` carries the idempotency key, both bases,
  and the passthrough duration; `carrier_duration_is_first_payload_only` pins the one-carrier
  selection policy; `measured_share_never_certifies_a_zero` pins the minimum-1 clamp;
  `route_labels` maps BYO (external) vs BGE (not);
  `split_input_tokens_attributes_by_record_share` pins the floor arithmetic.
* `cargo check --all-targets`, `cargo fmt --check`, `cargo clippy --lib --bins -- -D warnings`,
  `make work-commit-check` in this PR.

*Enforced by placement, not by test (documented so a future "cleanup" doesn't silently break
them):*
* Queue-wait exclusion of `provider_duration_ms` — the `Instant::now()` brackets sit **inside**
  the scheduler worker closures around `models.embed_batch_with_usage` (`service.rs`, both the
  sync and async paths). Moving them above `submit_sync` reintroduces queue-wait smearing with
  every test green; do not move them without adding a saturation test.
* The event-env gate is read-once (`OnceLock`) — no test exercises the enabled path (setting
  the env var in-process would poison the cache for the whole test binary); emission behavior is
  covered at the `build_*` seam instead.

*Process:*
* Pre-merge adversarial review, round 1 (3 independent reviewers: wire-contract/consumer,
  attribution math, runtime/edge) — findings folded into Change §2–§4; the wire shape itself
  validated against the sandhi `usage-event.v1` JSON Schema (Draft 2020-12) with negative
  controls. Round 2 (fix-breaker + tests/docs) — findings folded into this revision (reasoning
  tokens in the zero guard, Azure lenient-usage parity, carrier policy extraction + tests,
  TD truth corrections, split-loop metering). Round 3 (re-attack + fresh-eyes mechanical) —
  metering hoisted above the vector-count check, Azure value-leniency, `measured_share`
  minimum-1 clamp, two TD sentence corrections. Round 4 (final verification, incl. an
  independent run of every gate above): **CLEAN**.
