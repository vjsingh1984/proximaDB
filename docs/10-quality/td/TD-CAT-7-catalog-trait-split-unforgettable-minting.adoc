= TD-CAT-7: split the `Catalog` trait and make identity minting unforgettable
:status: In Progress
:dim: D5
:pillar: SEC

[cols="1,3", options="header"]
|===
| Field | Value
| Status | In Progress — items 1-3 shipped; internal-impl collapse deferred
| Severity | High — this is the STRUCTURAL fix for a defect class that has now cost three PRs
| Component | `crates/control/proximadb-catalog/src/lib.rs` (the `Catalog` trait), all impls
| Relates to | [[TD-AUTHZ-2]] (the instance), [[TD-RECALL-2]] (the re-land), ADR-0083, ADR-077
|===

== Problem

The `Catalog` trait has **40 methods, 18 with default bodies**, and the defaults are *not neutral*:

* `max_object_id` → `Ok(None)`
* `mint_collection_typed_identity` → `Ok(None)`
* `get_table_by_object_id` → `Ok(None)`

An implementation that implements **nothing** still compiles and answers successfully. That is
how "a catalog which does not mint identity" became a *representable state* — and identity is not
bookkeeping: **authorization depends on it.** `dml/mod.rs:1466` gates relational ABAC on
`stable_namespace_id` AND `object_id`.

=== Evidence this is structural, not incidental

The same gap has now been fixed by hand three times, and each fix left the next instance alive:

. **#1607** minted `object_id` on `SystemCatalog` → the introspection view stopped rendering empty.
. **#1636** minted `stable_namespace_id` → ABAC finally *enforced*. Only found because the e2e
  failure **moved** rather than disappearing.
. Three further live defects existed simultaneously, all from the same silent-`None` defaults —
  the ADR-031 anti-collision floor raise was a no-op (`shared_services.rs:1049`), vector
  collections silently stayed on the legacy data path (`collection/manager.rs:2039`), and
  `SystemCatalog` never called `normalize_identity` (ADR-077 violation). All three were closed
  *incidentally* by #1636, which is precisely the problem: nothing structural prevented them, and
  nothing structural prevents the next one.

Fixing instances is demonstrably not converging. The trait itself must stop making the broken
state expressible.

== Why the trait is currently unenforceable

`Catalog` demands identity minting from HTTP shims (Unity, Polaris) and external metastores
(Hive, Iceberg, Glue) that **structurally cannot provide it** — they do not own an allocator. That
is *why* every identity invariant was made optional. A contract two implementations cannot meet
gets weakened until it constrains nobody.

== Proposed change

. **Split by what is honourable.**
  * `CatalogAuthority` — internal, owns identity: minting, allocator floors, tenancy. Every
    identity method **required**; no silent-`None` defaults.
  * `FederatedCatalog` — narrow, read-mostly, for external metastores. No identity obligations,
    so none to fake.
. **Make minting unforgettable, not merely implemented.** Mint in ONE place the manager applies (a
  wrapper, or a sealed default), plus a **post-condition that rejects** any schema leaving
  `create_table` with `object_id: None`. A non-minting authority must fail loudly, not answer.
. **Teeth-proven tests** (revert only the impl line; the test must fail): no-reissue-across-restart,
  adopt-don't-overwrite, and a post-condition test asserting a non-minting impl is **rejected**
  rather than silently accepted.

== Shipped

The split landed as one PR, alone, gated on the recall e2e (per the sequencing
note below).

=== `CatalogAuthority` — the identity half, with no escape hatch

`crates/control/proximadb-catalog/src/lib.rs` now carries a second trait whose
**every method is required**: `max_object_id`, `allocate_object_id`,
`mint_collection_typed_identity`, `account_id_u32`, `account_id_u32_lookup`,
`get_table_by_object_id`, `get_namespace_by_object_id`. A backend that claims
authority cannot forget one — the compiler will not let it. `NativeCatalog` and
`SystemCatalog` implement it; the external/federated adapters do not, which is
the honest answer for a backend that owns no allocator.

`allocate_object_id` returns `u64` rather than `Option<u64>` on this trait: an
authority always can, so the `None` arm no longer exists to be inherited.

=== `Catalog::identity_authority()` — the distinction that did not exist

[source,rust]
----
fn identity_authority(&self) -> Option<&dyn CatalogAuthority> { None }
----

`None` from a federated catalog and `None` from an authority that forgot used to
be the *same value*. They are now different states, and `Catalog`'s identity
methods are thin delegations through this probe rather than answers of their
own — so an authority's own implementation is what answers, or nothing does.

=== The sealed `create_table`

Backends implement `create_table_inner`. `Catalog::create_table` is a provided
method that calls it and then applies the post-condition: **an identity
authority may not return a table with `object_id: None`**. Rust has no `final`,
so `scripts/check_catalog_seal.py` is the seal — it fails the build if any
`impl Catalog for ...` defines `create_table`. Wired into `make
work-commit-check` and the CI layering-check job. The guard was verified by
sabotage (adding an override to `HiveCatalog` makes it exit 1).

Call-site cost of the whole split: **zero**. The ~150 `create_table` callers and
the `dyn Catalog` identity callers are untouched.

=== Three defects the split forced into the open

* **`SystemCatalog::get_namespace_by_object_id` did not exist.** The DEFAULT
  backend was inheriting `Ok(None)`, so a namespace object_id resolved to "no
  such namespace" rather than to its namespace. It has no production caller
  today, so this was latent rather than live — but it is the *fourth* instance
  of the same omission, found by the compiler in the first minute rather than by
  a bisect. It is now implemented (`SystemCatalogState::get_namespace_by_object_id`).
* **`shared_services.rs` collapsed three outcomes into one.** The ADR-031
  collision floor-raise read `cat.max_object_id().await.unwrap_or(None)`, which
  made *no authority*, *nothing minted yet*, and *the authority failed* the same
  value — so a broken floor recovery was indistinguishable from a federated
  catalog and the guard silently did nothing. The three are now named apart and
  the failure warns.

* **The default backend mints no namespace `object_id`.** `NativeCatalog` does
  (ADR-031 / TD-181 P0); `SystemCatalog` does not, and both report the same
  `catalog_type`. Filed as [[TD-CAT-9]] rather than fixed here: it changes what
  draws from the shared id sequence, and the recovery floor folds tables only,
  so closing it needs its own no-reissue-across-restart proof. The current
  behaviour is now pinned by a test that says what must land with any change to
  it, instead of being assumed.

=== Teeth

`crates/control/proximadb-catalog/src/authority_seal_tests.rs`. Each test was
proven by neutering **only** the mechanism it covers:

[cols="2,3", options="header"]
|===
| Neutered | Result
| post-condition removed from `create_table`
| `authority_that_does_not_mint_is_rejected` FAILS
| `max_object_id` default restored to `Ok(None)`
| `catalog_identity_defaults_delegate_to_the_authority` FAILS (`left: None`, `right: Some(42)`)
| `create_table` override added to `HiveCatalog`
| `check_catalog_seal.py` exits 1
|===

`federated_catalog_without_object_id_is_accepted` guards the other direction —
the seal must not fire on backends that never claimed to mint, or they would be
forced to fake an id, which is how the invariants became optional in the first
place.

== Still open

Item 4 of the proposed change — **collapsing the internal impls** (Native /
System / Oltp / Delta differ only in where bytes land) and retiring
`PROXIMADB_DISABLE_SYSTEM_CATALOG`, which has no stated exit criterion — is not
done. It is a persistence-strategy refactor with a different risk profile from
the trait contract, and bundling it here would have put a storage change in an
identity PR, which is the mistake this TD's sequencing note exists to prevent.

The `unwrap_or_default()` rendering at
`crates/binding/proximadb-catalog-introspection/src/lib.rs:424` also remains: it
turns a missing `object_id` into an empty string. The post-condition now makes
that state unreachable through `create_table`, so the rendering is a
defence-in-depth gap rather than a live defect.

== Related but deliberately separate

* The `unwrap_or_default()` rendering at `crates/binding/proximadb-catalog-introspection/src/lib.rs:424`
  turns a missing `object_id` into an empty string — indistinguishable from a legitimately empty
  column. Hardening it belongs with this TD's post-condition work, not with an identity PR.
* The configuration-reachable external adapters are [[TD-CAT-8]].

== Sequencing note

Do NOT bundle this with an authorization change. #1406 was an ABAC PR that carried identity
minting and caused a silent cross-tier recall collapse (`mean=0.000`) that took a bisect and a
revert to unwind (see [[TD-RECALL-2]]). Identity changes ship on their own, gated on
`vector_ann_recall_e2e`.
