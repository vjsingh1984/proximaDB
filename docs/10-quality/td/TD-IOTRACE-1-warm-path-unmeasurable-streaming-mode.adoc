== Symptom

(a) Warm per-query GETs = 0 for all 4 engines — but this is an **artifact of TD-FLUSH-1** (the
unreaped memtable serves everything from memory; the SST files are never touched). Until TD-FLUSH-1
is fixed, the warm-path I/O is unmeasurable.

(b) Even after TD-FLUSH-1, the embedded engine is **in-memory** — it loads the full corpus into
memory on (re)start. To measure the **other side** of the in-memory-vs-streaming tradeoff (per-query
object-store reads, no full in-memory load), a **streaming/lazy-read mode** is needed.

== Fix approach

1. **After TD-FLUSH-1**: re-run the warm bench → warm GETs > 0 (real per-query I/O, measured by
   `CountingFileSystem`). Record the valid warm-path numbers.
2. **Add a streaming mode** to `bench_25`: force per-query reads from the FileSystem (no full
   in-memory load) — e.g., a mode where the engine serves each query by reading blocks on-demand
   from the SST files (no `collection_vectors`, no block cache). Measure the streaming side's
   GET/latency vs the in-memory side.
3. **Compare**: in-memory (fast warm, expensive restart) vs streaming (slower warm, cheap restart).
   The measured numbers are the evidence for the in-memory-vs-streaming tradeoff decision.

== Dependencies

- **Depends on**: TD-FLUSH-1 (warm GETs measurable after memtable reaped) + PR #553
  (`CountingFileSystem` → `IoTrace` composition landed).
- Related: the framework doc documents the in-memory-vs-streaming tradeoff with the cold-start
  numbers as evidence; this TD adds the streaming-side measurement.
