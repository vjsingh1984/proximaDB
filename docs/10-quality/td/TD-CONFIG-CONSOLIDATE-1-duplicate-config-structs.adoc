= TD-CONFIG-CONSOLIDATE-1: retire duplicate/dead config structs stranded by decomposition
:status: S1 shipped (#1314, 2026-07-29); tripwire assessed + declined (see below)
:owner: platform
:relates: ADR-069 S1, Core Directive #19 (CLAUDE.md) / #32 (GEMINI.md)

== Problem
The root-crate decomposition (leaf types → `crates/foundation/proximadb-config`, re-exported so
decomposed crates depend on a stable seam) has stranded **duplicate config structs**: a type is
extracted into the foundation crate, but the assembled compound config keeps a separately-authored
**core twin**, and the two drift as fields are added in parallel. Concurrent worktrees amplify it.
The drift is not hypothetical: while wiring ADR-069 S1 (`wal_local_dir`) we nearly edited the DEAD twin.

== Confirmed inventory (2026-07-28)
* **WAL config (the lone genuine duplicate):**
** Canonical/live: `WriteBufferUserConfig` (`src/core/config.rs:1010`). TOML `[storage.wal_config]`
   → `CoreStorageConfig.wal_config` (`config.rs:848`); consumed on every serving path
   (`shared_services.rs:2870/2952`, `database.rs:351`, `storage/engine.rs:223`).
** Dead: `WalStorageConfig` (`crates/foundation/proximadb-config/src/lib.rs:1060`) — only consumer is a
   **test-only** `impl From<&WalStorageConfig> for WALConfig` (`write_ahead_log/config.rs:~431`, called
   only by unit tests). Stranded by `a63febcbf "Extract config contract crate"`; reflects the
   pre-ADR-069 multi-disk design (no `write_buffer_directory`; hardcodes `data_directories`).
* **Drifted converters (secondary):** `WriteBufferUserConfig::to_engine_config()` (`config.rs:1125`) and
  `SharedServices::convert_toml_to_wal_config()` (`shared_services.rs:2870`) both build the same
  `WALConfig` and have drifted — fold into one.
* Scan of all other `src/core/config.rs` structs vs foundation twins: the rest are healthy re-exports
  (`pub use`) or core-only compounds (`SstConfig`, `ViperConfig`, `CoreStorageConfig`). WAL is the only
  offender among config structs.

== Plan (small, mixed-safe, sequential PRs)
1. ✅ **S1 shipped (#1314, 2026-07-29):** retired `WalStorageConfig` +
   `WalDistributionStrategy` (dead) + the test-only `From<&WalStorageConfig> for WALConfig` impl +
   its test + the `wal_storage_defaults` foundation test + the `core/config.rs` re-export. Each site
   carries a RETIRED note. Verified: 7427/7427 lib tests, fmt, clippy (`-D warnings`),
   work-commit-check. Canonical WAL config remains `WriteBufferUserConfig`.
2. ✅ **S2 shipped (#1323, 2026-07-30):** folded the two WAL converters — `to_engine_config` is the
   single canonical conversion; `convert_toml_to_wal_config` delegates + applies server-only bits.
   Fixed the latent embedded-path bug (it ignored sync_mode/memtable/flush-thresholds). Safe because
   `multi_disk.data_directories` is overwritten by both callers. 7427/7427 tests green.
3. Dead-symbol sweep — **S3 partial (sweep DONE, this PR; retirements incremental).** A two-agent
   audit (foundation/config/control + storage engines) reduced ~200 naive candidates to a verified
   inventory. **Retired in this PR:** the 2 already-`// MARKED FOR REMOVAL` WAL module files
   (`optimized_path_resolver.rs`, `atomic_write_buffer_sync.rs` — finishes #1270; zero-risk, already

     live same-named twin in `gcs_store.rs`); `ProviderHealthStatus` (llm_config, test-only).
   * storage (CONFIRMED-DEAD): `OptimizedWriteBufferWriter`, `ParallelWALSearch` (next in the #1270
     stack), `SstEntry`, `ModularBlockReader`, `CompactionExecution<E>`, `StreamingFlushResult`,
     `ZeroCopyFlushResult`, `CloudBackupStrategy`, `CollectionEffectiveConfig`.
   * CANDIDATE-NEEDS-VERIFY: `TransactionalOperationsConfig`, `DeprecationWarning`/`VersionInfo`,
     `FlushCycleState`, the `CloudBackupConfig` cluster.
   * Orphaned modules (module-level decision, not per-type): `src/llm`, `src/cdc` (zero server wiring).
4. **Tripwire — ASSESSED + DECLINED.** A name-collision guard (`pub struct` defined in BOTH
   `src/core/config.rs` and `crates/foundation/proximadb-config/`) was prototyped + tested
   (zero false positives on the current tree) but is too NARROW: the original incident was two
   *differently-named* structs (`WalStorageConfig` vs `WriteBufferUserConfig`) for the same concept,
   which a name check cannot catch. The signal that *would* catch it — a foundation struct whose
   only consumers are `#[cfg(test)]` — is a heuristic with false-positive risk unsuitable as a hard
   `work-commit-check` gate. Per mandate #12 (keep the harness lean; avoid low-value CI creep), the
   rule (Core Directive #19, reviewed every PR) + the RETIRED site notes + this TD remain the
   primary defense against concept-drift. Do NOT re-attempt a name-collision tripwire without
   addressing this gap.

== Guardrails
Trace the live path before deleting (the dead twin is usually the *foundation extract*, not the core
struct); build the **server binary**, not just `--lib`. Retiring a test-only *struct* is safe; retiring
a *field* obeys the format-migration discipline (Core Directive #8). See Core Directive #19.
