= TD-CAT-9: the default catalog does not mint namespace object_ids
:status: Open
:dim: D5
:pillar: SEC

[cols="1,3", options="header"]
|===
| Field | Value
| Status | Open
| Severity | Medium — latent today (no consumer), but it is a divergence between two backends that report the same `catalog_type`
| Component | `src/services/system_catalog.rs` (`create_namespace_inner`), `src/services/system_catalog_state.rs` (`max_object_id`)
| Relates to | [[TD-CAT-7]] (found it), ADR-031 / TD-181 P0
|===

== Problem

`NativeCatalog::create_namespace_inner` mints a stable catalog `object_id` for
every namespace from the single system-wide sequence — ADR-031 / TD-181 P0, with
the reverse index (`namespace_object_id_index`) maintained on
create/rename/drop. `SystemCatalog::create_namespace_inner` — **the default
backend** — sets `namespace_id` and `tenant_id` and leaves `object_id` at `None`.

Both report the same `catalog_type()` (deliberately, "so downstream
behaviour/introspection" matches), so a namespace created through the default
server path carries no catalog surrogate while the same call on `NativeCatalog`
does. Nothing consumes namespace object_ids today, which is why this has stayed
invisible.

=== How it surfaced

A TD-CAT-7 test asserted the newly-required `get_namespace_by_object_id` could
resolve an id the catalog had just minted. It failed on the *premise*: there was
no id to resolve. That is the fifth instance of the same defect class the trait
split was filed against — with the difference that this one is a divergence from
an accepted ADR rather than an inherited trait default.

== Why it was NOT fixed in the TD-CAT-7 PR

Minting namespace ids changes **what draws from the shared object-id sequence**,
and the recovery floor does not currently account for them:
`SystemCatalogState::max_object_id` folds `tables` (and the columns/indexes they
carry) only. Mint namespace ids without extending that fold and a restart can
recover a floor *below* a persisted namespace id — re-issuing a live namespace's
identity to a new object.

That is precisely the hazard the surrounding code calls out: object ids are
authorization-critical, "so re-issuing one after a restart would hand a NEW
table the DEAD table's permissions." Bundling it into a trait-contract PR would
have put an id-sequence change inside an identity refactor, which is the mistake
[[TD-RECALL-2]] records.

== Proposed change

. Mint `object_id` in `SystemCatalog::create_namespace_inner` from the same
  sequence `create_table` uses.
. Extend `SystemCatalogState::max_object_id` to fold namespace ids, so the
  derived floor covers everything the sequence issued.
. **Teeth**: a no-reissue-across-restart test — create namespaces and tables,
  reopen from WAL, assert the next minted id exceeds every persisted id
  *including* namespace ids. Neutering step 2 alone must fail it.
. Ship alone, gated on `vector_ann_recall_e2e`.

== Current state is pinned, not assumed

`system_catalog_namespaces_carry_no_object_id_yet`
(`src/services/system_catalog.rs`) asserts the `None`, and says in its failure
message what must land alongside a change to it. The divergence is a stated fact
rather than a surprise for the first consumer that keys on it.
