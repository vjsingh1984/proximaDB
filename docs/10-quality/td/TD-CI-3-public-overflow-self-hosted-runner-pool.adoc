= TD-CI-3: Isolated "public-overflow" self-hosted runner pool for public-repo CI

[cols="1,3",options="header"]
|===
| Field | Value
| Status | **Open — rolled out portfolio-wide to all 18 public anvai-labs repos (2026-08-30); first live verification found and fixed a real bug in the smoke test itself (see below).** No real (non-smoke) job routed to the pool yet.
| Dim | D5 (governance) -- self-hosted runner exposure on a public repo
| Pillar | Security, secondary OE (CI throughput)
| Blocks | Nothing directly. Extending real CI jobs onto this pool, or onboarding more public repos, should wait on the acceptance criteria below.
| Depends on | The existing private-repo self-hosted pool (`anvaiops` Default group, `anvai-labs` `dataserver-private-only` group) -- this TD only covers the public-facing extension.

== The problem

`anvaiops` and `anvai-labs` got dedicated self-hosted runner capacity (dataserver2/dataserver3,
Docker-based, `myoung34/github-runner`) to supplement GitHub-hosted CI minutes. 18 of `anvai-labs`'s 19
repos are **public**. Self-hosted runners on a public repo are a well-documented attack path: anyone
can open a pull request from a fork, and if a workflow triggered by `pull_request` runs on a
self-hosted runner, the fork's code executes directly on that machine. The initial rollout (private
repos only: `anvaiops`'s 4 repos + `anvai-labs`'s one private repo, `agentbrowser`) sidestepped this
entirely by scope. This TD covers the design for extending capacity to public repos *without*
reopening that exposure.

== Design: structural unreachability, not policy

The guiding principle is that the runner must be **structurally unreachable** by fork-controlled input,
not just discouraged by convention that a future PR could quietly violate.

1. **Event allowlist enforced by trigger choice, not review discipline.** Self-hosted jobs live only in
   workflows triggered by `push`, `workflow_dispatch`, or `schedule` -- never `pull_request` or
   `pull_request_target`. A fork PR cannot cause a `push` event on the base repo at all, so this isn't
   a rule that can be socially engineered around; it's a gap in what GitHub will even dispatch.

2. **`push` is scoped to branches with enforced review, not just any protected branch.** Branch
   protection can mean different things -- checked on proximaDB (2026-08-29):
+
[cols="1,1,1",options="header"]
|===
| Branch | Required review | Direct push by collaborator
| `main` | Yes (1 approval, `enforce_admins` on) | Blocked
| `develop` | No (`required_status_checks` only) | **Allowed**
|===
+
   `required_status_checks` gates PR *merges*, not direct pushes. A collaborator with push access can
   push straight to `develop` with zero review, and that push would trigger any `push`-gated workflow.
   The pilot workflow's `push` trigger is therefore scoped to `main` only. `workflow_dispatch` (also
   collaborator-only, same trust boundary as push access generally) is used to exercise the pool
   against `develop` on demand instead.

3. **Separate runner group per org, `visibility: selected`, `restricted_to_workflows: true`, pinned to
   the exact workflow file + ref.** Mirrors the org's own pre-existing `inferflux-gpu-trusted-staging`
   pattern. Closes the case where a future PR adds a *new* workflow file that happens to target the
   same runner labels.

4. **Separate, more restricted runner containers than the private-repo pool.** The public-overflow
   containers (`*-public-overflow-1` on dataserver2/dataserver3) do **not** mount
   `/var/run/docker.sock` -- unlike the private-repo pool, which accepts that as a calculated tradeoff
   for trusted-only code. No host Docker socket means no straightforward root-equivalent host
   escalation path from inside a job on this pool.

5. **Ephemeral runners** (`EPHEMERAL=true` + `--restart always`): one job, then the container exits and
   Docker relaunches it with a fresh registration. Nothing persists between jobs.

6. **Small resource caps** (2 cores / 4GB per container currently), enforced and *asserted* (not just
   logged) by the smoke workflow, to bound the cost of a misbehaving job even within the trusted-event
   lane.

7. **"Require approval for all outside collaborators" for Actions** is enabled per onboarded repo. This
   is a human-approval gate before *any* workflow -- GitHub-hosted or self-hosted -- runs for a fork PR.
   Contrary to this TD's original filing, this **is** settable via REST:
   `PUT /repos/{owner}/{repo}/actions/permissions/fork-pr-contributor-approval` with
   `approval_policy=all_external_contributors` (the org/repo `actions/permissions/access` endpoint this
   TD originally tested is a *different* setting -- external-workflow access for internal/private repos
   -- and 422s on public repos, which is what caused the original "UI-only" conclusion). Applied to all
   18 public anvai-labs repos 2026-08-30.

== What this does NOT cover

* Jobs that need Docker (image builds, container smoke tests) stay on GitHub-hosted or the
  private-repo pool -- the public-overflow pool structurally cannot run them without reintroducing the
  socket-mount risk.
* This TD only establishes the pool and proves the isolation properties via a smoke test. No real CI
  job has been moved onto it yet -- see Acceptance.

== Real finding from first live verification (2026-08-30): the cgroup check itself was wrong

The smoke workflow shipped in the introducing PR asserted cgroup caps by computing a nested host-side
path from `/proc/self/cgroup` (`awk -F: '$1 == "0" { print $3 }'`) and reading
`/sys/fs/cgroup${RUNNER_CGROUP}/cpu.max`. This pattern was carried over from `anvaiops`'s
`ci-runner-smoke.yml`, which runs on a macOS/Docker-Desktop-backed runner.

The first real `workflow_dispatch` run (on `victor`, dispatched from `dataserver2-public-overflow-1`)
failed at that step. Investigation (SSH into dataserver2, `docker exec ... cat /proc/self/cgroup`)
found the actual cause: **Docker on native Linux gives each container a private cgroup namespace by
default.** From inside the container, `/proc/self/cgroup` reads `0::/` and `/sys/fs/cgroup` is already
the container's own cgroup root -- there is no nested path to compute, and the check's own
`test "$RUNNER_CGROUP" != "/"` assertion was guaranteed to fail before ever reading the actual values.

Confirmed from the host side (`docker inspect --format '{{.State.Pid}}'` + reading
`/sys/fs/cgroup/<container-scope>/cpu.max` directly) that the **provisioning was correct the whole
time** -- `cpu.max = 200000 100000`, `memory.max = 4294967296`, exactly as configured. Only the
in-container verification script was wrong, because it assumed the macOS/Docker-Desktop runner's cgroup
visibility model applies to native Linux dockerd too. It does not: the two backends handle cgroup
namespacing differently, and a check pattern is not portable between them without verification.

Fixed to read `/sys/fs/cgroup/cpu.max` and `/sys/fs/cgroup/memory.max` directly (no path computation),
and re-verified green. This is the exact failure mode TD-126/mandate-12's "review generated code for
hallucinated dependencies/APIs, plausible-but-wrong logic" warns about -- the original check was
plausible, consistent with an existing in-repo pattern, and wrong for the environment it actually ran
in. It was only caught because this TD's acceptance criteria required an actual execution, not just a
green merge.

== Residual risk (accepted, tracked)

Every onboarded repo's `main`/`develop`/`qa` (or `master`) branches now require 1 approving review
(admin-bypassable), applied portfolio-wide 2026-08-30 -- so the "push only fires on reviewed code"
precondition this design depends on holds structurally, not just for proximaDB. The remaining residual
risk is the admin-bypass itself: `enforce_admins: false` lets the repo owner merge past both the review
requirement *and* the required status check in one action (classic branch protection has no finer-grained
split). This is intentional (there is exactly one collaborator across every onboarded repo as of this
filing, so requiring a second-party review would create a permanent deadlock), but it means the actual
safety property is "the owner chooses not to bypass carelessly," not "the platform prevents unreviewed
code from landing." The moment any onboarded repo gets a second collaborator with push access, this
should be revisited for that repo specifically.

  promoted through develop -> qa -> main, or its `push` trigger (currently `main`-only, see point 2
  above) can be exercised by an actual push once promoted.

== Co-design note

The cost term here is dual: CI throughput (the reason for extra capacity at all) versus blast radius on
real infrastructure (dataserver2/dataserver3 sit on the operator's home LAN alongside other live
services -- nextcloud, minio, ollama). The design optimizes for the second by construction (structural
unreachability) rather than by process discipline, because process discipline on a public repo is
exactly the thing a hostile actor doesn't have to respect -- only GitHub's own event semantics do.
