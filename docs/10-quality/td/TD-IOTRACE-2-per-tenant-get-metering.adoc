== Symptom

`metering_event.rs::build_kru` reads `SearchPlanTrace.index_stats` (cache hits/misses, vectors
scanned) but **NOT** the GET count from `IoTraceSnapshot.get_ops`. So the co-design KOU dimension
(object-store GET requests per query, the dominant cloud cost term) is not surfaced in the per-tenant
metering event — even though the io-trace now captures it via the `CountingFileSystem` → `IoTrace`
composition (PR #553's `IoRecorder` DIP hook).

== Root cause

`build_kru` was written before the `CountingFileSystem` → `IoTrace` composition landed (PR #553).
It reads `SearchPlanTrace.index_stats` (the pre-existing scan/cache stats) but not the new
`IoTraceSnapshot.get_ops` / `bytes_read` fields.

== Fix approach

Extend `build_kru` to:
1. Read `IoTraceSnapshot.get_ops` / `bytes_read` (now available per-query via the `IoRecorder`
   composition).
2. Emit them in the KRU metering event JSON (e.g., `object_store_gets`, `object_store_bytes_read`).
3. Wire the KRU event to drain the IoTrace snapshot (the `BillingObserver` already drains the
   io-trace; the KRU builder needs to consume it).

== Dependencies

- **Depends on**: PR #553 (`CountingFileSystem` → `IoTrace` composition — the `IoRecorder` DIP hook
  that makes GET counts a per-query signal). Independent of TD-AXIS-1 / TD-FLUSH-1 (the metering
  works regardless of whether the GETs are warm 0 or > 0 — it reports whatever the io-trace captured).
