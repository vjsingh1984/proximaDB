= TD-FPRUNE-1: filter-aware PAX cascade — phased arc (ADR-089)
:status: P2 implemented end-to-end; FILTERED_CASCADE flipped default-ON (2026-08-31, adversarially-reviewed evidence); FOOTER_STATS default-OFF pending its own evidence — corridor-benchmark gate open
:dim: D3/D5 (compute-per-modality, object storage)
:pillar: PERF

Problem: filtered vector search on the PAX path is a whole-object brute-force
scan — the coalesced cascade declines any query with a filter
(`src/storage/engines/sst/search/mod.rs:420`) and falls to
`search_pax_file_exact` (whole-object read, decode-all, per-record post-filter,
`mod.rs:2448-2553`). Measured vs Qdrant on identical data (TD-CTXCORR-1
harness): filtered p50 8.0→52.3 ms from 20k→80k rows (O(N)) vs 1.2→1.4 ms
(flat); **38x at 80k and widening**. Recall parity — the brute force buys
nothing. ADR-089 decides the fix: metadata-first cell/block pruning (Region-D
columnar stats) composed with the geometric A0 probe, one pipeline, residual
filter as the correctness backstop. This TD tracks the phases.

== Phases (each evidence-gated; mixed-read-safe; default-OFF until baked)

* **P1 — wire what exists (no format change): IMPLEMENTED (engine level).**
  Landed as: `RowAllow` bitset + allow-aware ranking (`rank_allowed`,
  `rank_probed_rows_allowed`) in `proximadb-block-format`; Stage-F builder
  `pax_filtered_row_allow` (header/footer → coalesced D-block fetch →
  conservative `evaluate_block` stats prune (skips DECODE; fetch pruning is
  P2) → row-accurate `evaluate_filter_proxima` per row — the SAME evaluator as
  the exact path, so match semantics are identical by construction);
  `rabitq_search_segment_coalesced_allowed` (pool sized on the allowed count;
  geometric probe bypassed under a filter — probe∩filter nprobe policy is P3);
  the `mod.rs:420` gate now routes filtered queries through Stage-F + the
  restricted cascade behind default-OFF `PROXIMADB_PAX_FILTERED_CASCADE`
  (fail-safe: any stage-F failure or non-coalesced segment falls back to the
  exact path; a provably-empty allow-set short-circuits to an empty per-file
  result). TDD: allow-aware rank equivalence tests (block-format), Stage-F
  exactness vs an independent decode, filtered-cascade recall vs filtered
  brute force, gate default-off. Evidence: the engine-level A/B harness
  (`p1_evidence_filtered_exact_vs_cascade`, ignored — run in release).
  **P1 residual scope:** P-Shred arming for `filterable` schema columns (user
  tags live in opaque PROPS msgpack, so stats pruning currently helps only
  canonical columns — row accuracy comes from the per-row eval either way),
  and the D-resolve residual check (defense-in-depth; the P1 row set is
  already row-accurate). **End-to-end server evidence is BLOCKED by
  TD-FLUSH-8** (auto-flush cannot resolve REST-created collections in the
  catalog — segments are never produced from the public API, so all corridor
  measurements to date were memtable-scan measurements).
* **P2 — footer-resident block stats (zero-GET pruning). IMPLEMENTED end-to-end
  (this branch, gates default-OFF; see P2 completion below).**
  Populate the reserved `StatsKind::MinMax` slot in the segment footer block
  table (`segment_layout.rs:222-262`; today always `StatsKind::None`,
  `pax_block.rs:2104` — the ADR-062 D5 deferral, now lifted) for filterable
  columns. Pruning then costs nothing beyond the footer the cascade already
  reads. Mixed-read-safe by the stats_kind marker AND the footer's existing
  per-entry `stats_len` framing (readers already skip an unknown-length stats
  payload — `segment_layout.rs:595-603`).
  ** **Keystone DONE (this slice):** `proximadb-block-format::FooterBlockStats`
     — the filterable columns' `ColumnMeta` (min/max hash bounds, the SAME
     bounds P1 prunes on in-body) lifted into a compact `[n u16][ColumnMeta×n]`
     payload, implementing the existing `BlockZoneSource` so `evaluate_block`
     runs unchanged against a footer-backed source. Round-trip + empty-payload
     (all-"may-match", mixed-read-safe) + **footer-prune == body-prune parity**
     are TDD-proven (5 tests). No new pruning logic; reuses the P1 kernel.
  ** **Wiring DONE:** (a) storage-common footer ser/de — `FooterBlockEntry`
     carries an optional `stats: Option<Vec<u8>>` on the existing `stats_len`
     frame; `write_block_entry`/`read_blocks` round-trip it (test
     `footer_index_round_trips`); dropped `Copy`. (b) writer — at flush, behind
     default-OFF `PROXIMADB_PAX_FOOTER_STATS`, lifts each block's bounded-column
     `ColumnMeta` into `BlockIndexEntry.footer_stats` → footer (`stats_kind =
     MinMax`). (c) Stage F (`pax_filtered_row_allow`) — decodes each block's
     footer `FooterBlockStats` and runs `evaluate_block` to drop provably-empty
     blocks from the coalesced FETCH plan BEFORE any body GET; counts them in
     `FilteredRowAllowStats.blocks_pruned_footer`. Test
     `stage_f_footer_stats_prune_blocks_from_fetch` asserts ≥1 block (and not
     all) pruned-from-fetch on a canonical `created_at_ns` filter.
  ** **⚠️ FIELD-NAMESPACE GAP (found during P2 c; the true blocker to the
     benchmark win):** footer-prune resolves fields via `pax_field_to_col`,
     which today maps ONLY canonical columns (`id`, `tenant_id`, `created_at`,
     `valid_to`, …) → `None` for any user tag. The row-accurate match runs
     `evaluate_filter_proxima` over **props**. So the two stages read *disjoint
     field namespaces*: footer-prune engages for canonical-field filters, while
     the benchmark's user-tag filters (`partition`, `lang`) prune nothing
     (conservative — correctness preserved, but zero GET saved). Making
     footer-prune deliver end-to-end for user tags is SMALLER than first
     thought — scoped by investigation (2026-08-12):
     *** ✅ **Shredding already works.** P-Shred (ADR-055) already shreds
         `filterable` props into typed PAX column stripes with `ColumnMeta`
         min/max bounds at their catalog col-id (≥100), driven by
         `schema.props_auto_promotion.promoted_keys` →
         `PaxSegmentWriter::with_shred_spec` (`record_store.rs` write_mutations;
         `writer.rs:454-464,672-679`). The value STAYS in props (duplicate index,
         not extraction), so my P2 writer already lifts these bounds into the
         footer. NOTE: the `write_pax_segment` TEST helper does NOT set a shred
         spec, which is why the P2 unit test uses a canonical field.
     *** ✅ **Row-match already works.** Because the shredded value stays in
         props, `evaluate_filter_proxima` finds it — no change needed.
     *** ❌ **Only gap: field resolution.** `pax_field_to_col`
         (`segment_format.rs:730`) is a stateless fn that maps only canonical
         names; it returns `None` for user tags because segments store physical
         col-ids, not names. Fix = resolve a `name→col-id` map for the segment's
         shredded columns and use it (canonical first, then the user map) in the
         two `evaluate_block` calls in `pax_filtered_row_allow`.
     *** **Follow-up design choice for the map source (the real decision):**
         (i) *Catalog lookup* — `ctx.collection` (`Arc<Collection>`) is in scope
         at `fallback_to_direct_search`, but the proto `FilterableColumnSpec`
         carries only the column NAME, not its PAX col-id (that lives in the
         catalog `CatalogTableSchema.columns[].id`, which the WRITER used via
         `promoted_keys`). So this path needs a catalog-schema lookup, and one
         caller (`scan_single_file`, `search/mod.rs:1651`) has no collection
         context to thread. (ii) *Self-describing segment (preferred, co-design)*
         — embed the shred `name→col-id` map in the segment footer/A0 at write
         (the writer already has the shred spec), so the reader resolves user
         fields with ZERO catalog dependency and no hot-path plumbing; a small,
         mixed-read-safe footer section. Recommend (ii). This is the P2-engagement
         follow-up slice (own PR + benchmark evidence), default-OFF, no writer
         behavior change beyond the additive footer section.
     *** ✅ **DONE — engagement slice landed (self-describing segment, option
         ii).** New optional footer section `SECTION_SHRED_FIELD_MAP` (tag 5)
         carries the writer's P-Shred `(name, col-id)` pairs
         (`segment_layout.rs`; gated with `PROXIMADB_PAX_FOOTER_STATS`, absent ⇒
         byte-unchanged). `pax_filtered_row_allow` builds a `resolve_field`
         closure (canonical via `pax_field_to_col`, else the footer map) used at
         both `evaluate_block` calls, so a USER-TAG filter (`partition`) now
         footer-prunes with ZERO catalog lookup. Tests:
         `footer_index_round_trips` (map round-trip),
         `stage_f_user_tag_footer_prune_via_self_describing_segment` (partition
         filter prunes ≥1 block AND allow-set stays exact). `write_pax_segment_ordered`
         gained a `shred_spec` param so the write path can shred.
     *** ✅ **RESOLVED (M1 + Gap-B, this branch): the SST vector-flush path now
         shreds.** The 2026-08-14 finding (flush materializer passed an EMPTY
         shred spec, so user-tag footer-pruning was DARK end-to-end for
         `engine=sst` vector collections) is closed: `CollectionFlushPlan`
         carries `filterable_columns` from the collection schema, and the SST
         flush materializer forwards the shred spec into the `_shredded`
         `write_pax_segment` variants — declared filterable tags become typed
         PAX stripes with footer stats at flush.
  ** **P2 completion (this branch):**
     *** **M1/Gap-B — flush shredding:** filterable columns propagate
         catalog→`CollectionFlushPlan`→SST flush→shredded write (above).
     *** **Gap-A — REST mapping:** a filterable short-`text` column maps to
         `FilterableString` (internal mapping only; `data_type`/`filterable`
         were already in the OpenAPI spec — no spec/SDK drift).
     *** **A1 — compaction preserves shredded columns**
         (`extract_shred_spec_from_inputs`; compacted segments keep pruning).
     *** **M3 — filtered coarse probe re-armed:** the geometric A0 probe
         composes with the filter allow-set instead of bypassing.
         `filtered_coarse_probe_holds_recall_and_cuts_bytes` proves recall
         parity with a byte cut as a measured fact.
     *** **M2/C2 — tag-aware two-level compaction layout:** per-partition
         k-means over a shared global PCA makes A0 cells partition-homogeneous,
         so an UNCORRELATED filterable tag prunes. Default-ON per-collection
         (engages structurally only when a segment carries a shredded tag;
         `PROXIMADB_PAX_PARTITION_LAYOUT=0` kill-switch; same A0 format —
         mixed-read-safe). C1 evidence: integrated filtered-stack GET/byte
         breakdown = **4.2× byte cut**; C2 evidence: unfiltered recall
         neutral **Δ=0.000** vs global layout.
  ** **Gate policy:** `PROXIMADB_PAX_FILTERED_CASCADE` landed default-OFF
     (2026-08-30, honoring the 2026-08-20 promotion criterion) and was
     **FLIPPED default-ON 2026-08-31** in the follow-up flip PR — after an
     adversarial review established that the original criterion was
     *vacuously dischargeable* (the SIFT ratchet is unfiltered; the gate is
     only consulted under a filter) and that the cascade returned id+score
     with NO metadata while the exact path it replaces returns full props.
     The flip PR therefore carries: (1) top-k metadata REHYDRATION
     (`read_records_by_positions` — position-selective, bounded by the hit
     set) so filtered responses keep the exact path's shape; (2) a NEW
     filtered SIFT ratchet leg through the REAL dispatch — the first test
     anywhere to exercise the gated `search/mod.rs` arm — measuring filtered
     recall@10 = **0.996** vs filtered brute-force GT (floor 0.90, 100
     queries, N=10k, 8 partitions) with predicate satisfaction and metadata
     rehydration asserted per hit. `PROXIMADB_PAX_FOOTER_STATS` stays
     default-OFF (adversarial verdict: no promotion criterion of its own,
     read-inert while the cascade was off, unmeasured footer byte cost paid
     by every collection) until the cascade records io_trace evidence that
     the D-block fetch dominates and a footer byte-delta measurement lands.
  ** **Attribution wired (this branch):** `record_pax_footer_prune(total,
     pruned)` lands in the query-scoped `IoTraceSnapshot`
     (`pax_footer_total_blocks`/`pax_footer_pruned_blocks`), mirroring the
     centroid-prune counters — `pruned > 0` proves engagement; the physical
     savings surface in the universal `get_ops`/`bytes_read` as unfetched reads.
  ** **Evidence gate (OPEN — deferred with rationale):** the corridor
     benchmark (filtered p50/p99 at 20k/80k/1M vs the recorded Qdrant 8.0/52.3
     ms baseline, synthetic partition + Wikipedia `lang`, io_trace
     `object_gets`/`bytes_read` per filtered query) has NOT been run on this
     branch — it needs the corridor harness + corpora and belongs in the
     flip-ON decision, not this code PR. The in-module C1 measurement (4.2×
     byte cut at recall parity on correlated data) is the interim evidence.
* **P3 — per-cell stats (prune before any Region-A byte).** Optional
  footer/A0 section with per-cell dictionary/zone summaries for filterable
  columns; intersect with the geometric nprobe cut
  (`coarse_probe_survivors`, `segment_format.rs:2130-2204`) so metadata-dead
  cells are never fetched. Strongest when metadata correlates with clustering
  (tenant/lang); measure the uncorrelated case honestly — P2 block stats carry
  it. Budget-check against A0's ~120-300 KB envelope.
* **P4 — stats-driven selectivity policy.** Distinct-hint HLL + null counts +
  dictionary domains → per-segment selectivity estimate → route: ultra-selective
  ⇒ direct row fetch + exact rank (no ANN); moderate ⇒ pruned cascade;
  unselective ⇒ cascade + residual only. This is the real auto
  `AnnFilteringMode` (closes the TD-073 deferral) and subsumes the AXIS
  PreFilter/Inline/PostFilter modes as policy over capability.

== Gates (per phase)

* `filtered_recall_at_10` vs exact ground truth (TD-CTXCORR-1 harness) —
  pruning is conservative; recall must match the unpruned path.
* Filtered p50/p99 at 20k/80k/1M vs the recorded Qdrant baseline
  (8.0/52.3 ms → target flat-ish scaling), synthetic partition (uncorrelated)
  AND Wikipedia lang filter (correlated).
* `io_trace` `object_gets`/`bytes_read` per filtered query — the pruning win
  must be visible in the physical-cost counters (feeds TD-CTXCORR-1 Slice 4
  economics).
* Mixed-read: new-stats segments and legacy segments coexist in one
  collection; recovery/readers default to legacy when markers absent.

== Related (non-goals here)

* AXIS REST `ann_filtering_mode` override: SUPERSEDED (2026-08-29 review).
  Mode selection is now catalog-`AnnFilteringPolicy`-driven with selectivity
  routing (`query_optimizer.rs` — "policy as the single source of truth"), and
  a post-hoc plan-field stomp would be overridden by the policy path. The
  former WIP branch was discarded; if a diagnostic lever is still wanted, wire
  a request field through to the existing `AnnFilteringPolicy.force_mode`
  (~30 lines + spec/SDK regen per mandate #15) — do not revive the old
  plan-stomp approach.
* WAL/unflushed side already filters at scan time
  (`search_unflushed_vectors`: bloom pre-filter + per-record eval before
  scoring) — no work needed there.
* In-memory per-tag payload indexes (Qdrant-style): possible future cache
  layer above this design; not the foundation (ADR-089 Alternatives).
