= TD-TENANT-3: one claim vocabulary across all four ingress surfaces
:icons: font

**Status:** S1–S3 shipped. S4 item 2 closed (TD-TENANT-4). S4 item 1: alias honoring REMOVED (#1773); names + detection delete at the next release boundary.
**Origin:** review question raised while landing ADR-0053 W8 (the
`X-Tenant-Tier` trust gate): "why are the headers different in gRPC vs REST —
should they not be standardized?" Pressure-testing that question found the
naming premise mostly false and three *real* defects underneath it.

== Working backwards: the outcome we want

**A tenant claim means exactly one thing, no matter which port it arrives on.**

Concretely, the end-state a client and an operator should be able to rely on:

. The same request, replayed across REST / gRPC / Arrow Flight / pgwire, resolves
  to the **same tenant** and the **same entitlement** — or is rejected on all of
  them. No surface silently ignores a claim another surface honors.
. An entitlement claim has **one canonical spelling internally**, so an operator
  writes one `cache_tiers.json` and it binds identically regardless of which
  alias the control plane happens to stamp.
. Adding a fifth ingress surface means *wiring* the shared vocabulary, not
  *re-deriving* it — the failure mode that produced this TD.

Everything below is the shortest path from today's state to those three
properties.

== First-principles review: the premise is half wrong

The question assumed REST and gRPC read *different header names*. They do not.

REST reads through `http::HeaderMap`, whose keys are `HeaderName` — lowercased
at parse and compared case-insensitively. `X-Tenant-ID`
(`src/network/middleware/tenant.rs:54`) and `x-tenant-id`
(`src/network/grpc/auth.rs:234`) are **the same key**; HTTP/2 additionally
mandates lowercase on the wire, so gRPC could not spell it otherwise. The
casing difference is a source-literal artifact, worth a shared `const`, not an
ADR.

The *decision* layer is already standardized, twice over: every surface calls
the one tenant primitive `resolve_tenant_assertion` (TD-TENANT-1) through the
one identity orchestrator `resolve_request_identity` (TD-ABAC-6), and — as of
ADR-0053 W8 — the one tier primitive `resolve_tier_claim`.

What was never standardized is the **vocabulary**: the set of wire names each
surface reads *before* handing a value to those primitives. That layer is
hand-rolled per surface, and that is where the defects are.

== The three real defects

=== D1 — the accepted alias set diverges per surface (silent, not loud)

[cols="1,3,1", options="header"]
|===
| Surface | Tenant claim names accepted | Tier claim

| REST
| `X-Tenant-ID` (one spelling)
| `x-tenant-tier`

| gRPC
| `x-tenant-id` (one spelling; three duplicate literals at `auth.rs:234`,
  `:506`, `:585`)
| `x-tenant-tier`

| Arrow Flight
| **four**: `x-proximadb-tenant-id`, `x-tenant-id`, `tenant-id`, `tenant_id`
  (`arrow_ipc/service.rs:573-586`)
| **none**

| pgwire
| `database` startup parameter
| `proximadb_tier` startup parameter
|===

A client that sends `x-proximadb-tenant-id` is honored on Flight and **silently
ignored** on REST and gRPC — no error; the request falls through to the
credential tenant or `default_tenant`. That is the "same request, two answers"
class: cross-surface tenant divergence with no diagnostic. It is worse than a
403, because nothing is observable at the boundary.

pgwire's `database`-as-tenant is **not** a defect — the PG startup packet has no
header channel and `database` is how a PG client addresses a database before
auth. That one is protocol-forced and stays.

=== D2 — Arrow Flight has no tier-claim surface at all

`authenticated_flight_context` (`arrow_ipc/service.rs:650-698`) resolves
identity through the shared orchestrator but never reads a tier claim, so a
Flight client always runs at the default tier.

This is the *inverted* priority: Flight is the bulk/columnar zero-copy path —
the highest cache-pressure surface in the system — so it is precisely where
per-tenant cache floors and weights matter most.

=== D3 — the tier claim means two different things downstream

`set_tenant_tier` (`services/record_store.rs:4555`) stores the **raw
client-supplied string**. Four consumers then read it in two incompatible
vocabularies:

* **raw-string** (3 sites): `network/shared_services.rs:780`,
  `storage/engines/sst/core.rs:688`, `storage/engines/sst/warming.rs:224` —
  each matched as a *literal key* against the operator's `cache_tiers.json` via
  `TierPolicy::limits(&str)`.
* **canonical** (1 site): `record_store.rs:4572` `tenant_tier_resolved` →
  `Tier::from_claim`, which is alias-aware (`pro` → `Tier3`).

So `X-Tenant-Tier: pro` and `X-Tenant-Tier: tier3` — the *same* entitlement —
resolve identically for cost multipliers but land in **different cache
buckets**; one of them misses and silently falls back to `default_tier`.

Secondary: the process-global registry stores an unvalidated,
attacker-influenced string as a value, so garbage claims persist verbatim.

== Co-design rigor: which dimensional cost term does this move?

Per the co-design mandate, a change must name the dimensional cost term it
moves, not a local optimum.

The tier claim is the **only per-tenant input** to cache floor / ceiling /
weight (`LimitsResolver`, `proximadb-cache/src/lib.rs:321`). A claim that
silently misses its bucket does not merely mis-label a metric — the tenant
drops to the default share, its working set is evicted sooner, and the misses
become **GET requests against object storage**. That is Dimension 1
(object-storage round-trips), the *dominant* cost term for this system, reached
through Dimension 3 (local disk/cache) and Dimension 5 (governance/entitlement).

So D3 converts a paid entitlement into extra object-store round trips, and D2
withholds the entitlement entirely from the surface that generates the most of
them. Neither is cosmetic; both are billable.

This TD asserts no performance number. The observable is cache-hit-rate and GET
count per tenant, already emitted per the I/O-trace requirement — measurement
belongs to whoever tunes tier shares, not to this convergence work.

== Design: three decoupled workstreams

The three defects are deliberately kept separable — each lands and reverts
independently, and none depends on another's internals.

=== S1 — one claim vocabulary, expressed as data (D1)

Add a vocabulary module to `proximadb-tenant`, the foundation crate that
already owns both trust primitives. It exposes the canonical wire names as
constants plus the deprecated Flight aliases, and a lookup helper generic over
a `Fn(&str) -> Option<&str>` accessor — so it serves `http::HeaderMap`,
`tonic::MetadataMap`, and pgwire's parameter map **without any of those types
leaking into foundation**. Each surface's alias list becomes data the shared
module owns, not code the surface re-derives.

**Convergence direction: narrow, do not widen.** Adding Flight's three extra
aliases to REST and gRPC would make previously-ignored headers newly effective
on two surfaces — a behaviour change in the riskier direction, even though the
same trust gate governs them. Instead `x-tenant-id` / `x-tenant-tier` are
canonical everywhere; Flight keeps accepting its three legacy aliases, now
**deprecated and warned once per alias** so the migration is observable before
anything is removed. Removal is S4, gated on those warnings going quiet.

**One behaviour change ships with S1.** Flight previously preferred
`x-proximadb-tenant-id` *over* `x-tenant-id` — precedence pointing away from
the standard spelling, so a client sending both converged on the alias slated
for removal. That precedence is inverted: the canonical name now wins. Only a
client sending **both** headers with **different** tenant values is affected,
and the resolved tenant remains subject to the same `HeaderTrustPolicy` gate
either way. The test that pinned the old precedence
(`test_tenant_id_from_flight_metadata_prefers_proximadb_header`) is inverted
and renamed rather than deleted, so the change is recorded where it happened.

=== S2 — Flight tier hook (D2)

Mirror the gRPC gate exactly in `authenticated_flight_context`: derive the
`AuthenticatedTenantBinding` from the resolved user context, call the same
`resolve_tier_claim`, stamp the acting tenant, drop-and-warn on rejection with
`surface = "flight"`. No new primitive — this is pure wiring of an existing
one, which is the point: S1 makes the wiring the only work.

=== S3 — normalize the tier claim once, at the stamp (D3)

Resolve through `Tier::from_claim` **at `set_tenant_tier`**, and store both
projections: the canonical `Tier` and the operator's raw spelling. Readers then
take what they need — `tenant_tier_key()` for the canonical id, the raw string
preserved for the cache probe.

The cache-resolver closure probes **canonical first, then raw**. That keeps an
operator's alias-keyed `cache_tiers.json` working unchanged (mixed-read-safe,
no flag day) while guaranteeing that two spellings of one entitlement land in
one bucket.

Normalizing at the stamp also bounds the registry's value space to the known
tier set, so an unrecognized claim resolves to the default tier instead of
persisting as an arbitrary string.

`proximadb-cache` stays a pure leaf with **zero** ProximaDB dependencies. Its
string-keyed `TierPolicy` is deliberately generic (operator-supplied key space,
mechanism-not-policy per TD-OSS-1) and this TD does not compromise that — the
normalization happens on the *caller* side of the seam.

== Non-goals

* **pgwire `database`-as-tenant** — protocol-forced, stays as-is.
* **Renaming `proximadb_tier`** — the PG parameter grammar forbids `-`, so it
  cannot be spelled `x-tenant-tier`; it is mapped by the shared vocabulary
  instead.
* **Hot reload of tier config** — `OnceLock` by design; restart-required is
  documented, not changed (ADR-037 amendment, 2026-08-19).
* **Removing Flight's legacy aliases** — S4, after the deprecation warnings go
  quiet.

== S4 — open follow-ups

. Flight alias retirement — **honoring REMOVED 2026-08-29** (S4 item 1,
  evidence-closed early): the aliases no longer grant a tenant on any surface;
  presence is still detected (warn once per process + the
  `proximadb_deprecated_claim_uses_total` counter, now counting attempts).
  Residual for the next release boundary, then delete: the
  `DEPRECATED_TENANT_CLAIM_ALIASES` const, the three names, the warn, the
  counter, and their tests. Closure basis: integrator exhaustion (no SDK or
  AnvaiOps reference ever sent an alias) — the counter window could not have
  accumulated (no release shipped since it landed); honoring-removal had to
  precede that release regardless.

[NOTE]
====
**Retirement gate made measurable (2026-08-27).** "Warning silent" was
originally a log observation — but the warn fires **once per process**, so a
long-lived pod goes log-silent while clients keep using an alias every second,
and "quiet logs" would falsely read as "clients migrated". Every use now
increments the cumulative counter
`proximadb_deprecated_claim_uses_total{surface,name}` (per use, not per
process; the warn stays once-per-process to avoid log spam). **The gate is a
query: retire when `increase(proximadb_deprecated_claim_uses_total[7d]) == 0`**
on the serving fleet, evaluated across a release boundary. The same change
added `proximadb_tier_claims_dropped_total{surface,reason}` so ADR-0053 W8
drops (previously warn-once-per-tenant, invisible in aggregate — and fully
silent on pgwire) are countable per surface and rejection reason.

  `crates/platform/proximadb-network-middleware/src/rate_limit.rs:327`.

[NOTE]
====
**Superseded by TD-TENANT-4 (2026-08-21), which corrects this framing.** The
item above says the header is "trusted for rate-limit keying". It is not: the
REST rate limiter is unmounted dead code, and pgwire — the one live
rate-limited path — already keys on the real socket peer address. The header
*is* consumed on a live path, but it is KOU egress metering, and the root
cause is that the real peer address is never observed at all (no `ConnectInfo`
is wired), not merely that a header is ungated. See
`TD-TENANT-4-client-ip-provenance.adoc`.
