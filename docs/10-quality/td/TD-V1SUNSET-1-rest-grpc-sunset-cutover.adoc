== Reconciliation (2026-08-28 census)

A deprecation-promises census re-verified the "Current state" section against
`develop` and found it stale in both directions:

* **The gRPC v1 opt-in no longer exists.** `enable_grpc_v1_compat` /
  `PROXIMADB_GRPC_V1_COMPAT` have zero references in the workspace; the cited
  `src/core/config/bootstrap_config.rs` moved to
  `crates/platform/proximadb-runtime/src/bootstrap_config.rs` *without* the
  flag, and the three `multi_server.rs` registration sites are gone. The v1
  gRPC surface under `crates/platform/proximadb-api/src/grpc/` is deleted
  (only `v2/` remains). **The gRPC sunset therefore completed as a hard
  removal**, not as the flag-gated retirement this TD's "Current state"
  describes. `SUPPORTED_SURFACE.adoc` still documented the flag as a live
  mechanism until this same census corrected it.
* **Residual (regen item) — DONE 2026-08-29:** the generated
  `proximadb-proto/src/proto/proximadb.v2.rs` doc comments said some v2 RPCs
  were "gated behind `enable_grpc_v1_compat`" (2 sites). Verified during the
  follow-up that those RPCs were never IN the v2 service definition — the
  comment described absent surface as deferred surface. The proto source
  comment now states they were not carried into v2 (their v1 home is removed;
  definitions remain in `v1/graph.proto` as internal, ratchet-tracked types),
  regenerated via `PROXIMADB_PROTO_REGEN=1` — a comment-only diff. The two
  remaining flag mentions are the deliberate historical quote.
* **Step 5's gate was unobservable.** "Sunset-window verification" requires
  counting `/api/v1` 410 responses, but the REST metrics middleware is a
  post-routing `route_layer` — unmatched `/api/v1/*` paths never reach it, so
  the 410s were not metered anywhere. Same class as the TD-TENANT-3 S4 gate
  fixed in #1757. Fixed the same way here: the `v1_sunset` middleware itself
  now counts every decision it makes
  (`proximadb_v1_sunset_responses_total{outcome}`), so the window is verified
  with `increase(proximadb_v1_sunset_responses_total{outcome="gone"}[Nd])`
  against the traffic baseline, and any residual compat opt-in usage is
  visible as `outcome="compat_served"`.
* **A suspected fourth defect was tested and REFUTED.** The census questioned
  whether `.layer()` fires for UNMATCHED paths (production registers no
  `/api/v1` routes; axum's `fallback_layer` distinction suggests it might
  not), which would have made the 410 dead-in-production. Probed empirically:
  **unmatched `/api/v1/*` returns 410** — the property holds and is now
  pinned by `unmatched_v1_path_still_gets_410_not_404` so an axum upgrade
  cannot silently break it.
* **Live conflict found — RESOLVED 2026-08-29 by clean relocation.** The
  `enterprise-catalogs` feature nested its API under `/api/v1/catalogs` —
  squarely inside the prefix this middleware 410s when compat is off (the
  default), leaving the enterprise surface dead-on-arrival. Moved to
  `/api/v2/catalogs` with NO alias: the surface was never reachable in a
  default deployment (double-prefix bug until TD-CAT-8, then 410), and no
  SDK or client referenced the path. A serving test now pins both properties
  (reachable at v2 under default config; the v1 home still 410s), and the CI
  feature-matrix lane now RUNS the catalog tests rather than only compiling
  them.
+
**Correction to this census's own text:** it said "CI never builds the
feature." Stale — ci.yml has an `enterprise-catalogs` feature-matrix lane;
the lane *compiles* the feature but never *serves* it, which is precisely
why the collision survived a green lane. The fix is serving teeth, not a new
lane.

== Resolution (2026-08-29): Step 5 executed early, on integrator evidence

The v1_sunset middleware (and with it `PROXIMADB_REST_V1_COMPAT`,
`PROXIMADB_REST_V1_SUNSET`, the counter, and their tests) is **deleted**;
both env gates moved to the registry's Retired-names section.

**Closure basis — recorded honestly:** NOT the counter window (it never
accumulated: no release shipped after the counter landed). The gate was
satisfied by stronger evidence: (1) every known client is accounted for —
our SDKs never called ProximaDB v1, and AnvaiOps (the only known gateway
integrator) makes zero ProximaDB `/api/v1` calls and sets no compat opt-in;
(2) `/api/v1` has been 410-by-default since #814 (2026-07-09) — ~7 weeks, so
every working client is already off v1; (3) the migration affordance
SURVIVES the removal: `not_found_fallback` + `v1_replacement_for` answer
removed v1 paths with 404 + the exact `/api/v2` replacement + docs link
(pinned by `removed_v1_paths_404_with_the_v2_replacement_named`). Only the
machine-readable RFC 8594 headers are lost. Worst case for a hypothetical
hand-rolled v1 caller: an equally actionable 404 instead of a 410.

== Why this exists

Both v1 kill-switches already ship (verified 2026-07-08, see the roadmap §"Current
state"). What remains is the **cutover** — flip the REST default off, then hard-delete
the v1 surfaces. The roadmap stages this but does not enumerate the exact files,
the live-vs-deprecated boundary, or the one prerequisite that is easy to miss (the
deprecation-header utility imported by *live* handlers). This TD captures that
execution detail so the cutover is mechanical once the sunset window closes.

== Reconciliation (2026-07-09) — original premise partially invalidated

A fresh `origin/develop` worktree audit (the prompt's "don't trust this blindly"
step) found the deletion targets are NOT the dead surface this TD assumed:

* **Step 4 (gRPC v1 api-crate) — already complete.**
  `crates/platform/proximadb-api/src/grpc/v1/` (11 files), `grpc/builder.rs`, and
  the `lib.rs` `grpc::v1` re-export are all gone; `grpc.rs:5-8` documents the
  removal. The sole residual `grpc::v1` reference workspace-wide is that
  historical doc comment. Nothing to land.

* **Step 3 (REST v1 api-crate) — INVALIDATED, do not execute.**
  `crates/platform/proximadb-api/src/rest/v1/` is **LIVE `/api/v2` code**, not
  deprecated. `src/network/rest/v1/handlers.rs:1460-1542` wires its
  `create_{graph,document,observability,multimodal,hybrid_search}_router`
  builders into production `/api/v2/*` routes (each guarded only by a runtime
  `if let Some(port)` check — the `use proximadb_api::rest::{...}` imports are
  compiled unconditionally). The `v1` path segment is a historical misnomer;
  these are canonical port-backed routers. A blanket `git rm -r` would fail to
  compile AND delete `/api/v2` routes. Relocating/renaming the module is TD-104
  (root-crate decomposition) work, out of scope for the v1 sunset.

* **Consequence — the REST v1 sunset is effectively already complete.** The
  legacy `/api/v1/collections`, `/api/v1/search`, `/api/v1/sql`, and
  `/api/v1/graph` routes were removed in the "API standardization hard-rename"
  (see comments at `handlers.rs:1463-1479,1545`), and step 1's `v1_sunset`
  middleware now `410`s any residual `/api/v1` traffic. No deprecated REST v1
  *route handlers* remain; only the misnamed live `rest::v1` module dir.

* **Step 2 — landed.** The deprecation-header utility was relocated to a neutral
  `proximadb_api::rest::deprecation` module (decoupling the live `handlers.rs`
  from the `rest::v1` namespace). Valid, non-breaking, independent of step 3.

* **Step 5 — unchanged.** Remove `v1_sunset` middleware + mounts only after the
  flip is proven safe through a sunset window (metrics/access-log/SDK audit).
  This remains the sole outstanding REST-side action.

== Prerequisite (easy to miss) — relocate the deprecation-header utility

`crates/platform/proximadb-api/src/rest/v1/mod.rs` defines
`add_rest_v1_deprecation_headers` / `with_v1_compatibility_headers`, but these are
imported by **live** root-crate handlers:

* `src/network/rest/v1/handlers.rs:13` —
  `use proximadb_api::rest::v1::add_rest_v1_deprecation_headers;` (applied at
  `:1741`, `:1877`).

Deleting the api-crate `rest/v1/` dir would break that import. **Before deleting**,
move the deprecation-header helpers to a non-v1 location (e.g.
`crates/platform/proximadb-api/src/rest/deprecation.rs`, re-exported at
`rest/mod.rs`) and repoint `handlers.rs:13`. (The `with_v1_compatibility_headers`
call sites at `rest/v1/{hybrid,observability,analytics}.rs` are *inside* the
deleted dir, so they go away with it.)

== Sunset-window verification (the gate to actually executing)

Before flipping the REST default off / hard-deleting, confirm no live `/api/v1`
traffic:

. **Metrics** — the `/metrics` endpoint; watch `/api/v1/*` request rate to ~0 over
  the window.
. **Access logs** — grep `/api/v1/` in server logs.
. **Clients/SDKs** — confirm generated SDKs (Python/Go/TS/Rust) target `/api/v2`
  (they are spec-driven from the canonical OpenAPI; verify no hand-rolled `/api/v1`
  callers).
. **Deprecation-signal** — the middleware already emits `deprecation: true` +
  `Link: </api/v2>; rel="successor-version"` + optional `Sunset` (from
  `PROXIMADB_REST_V1_SUNSET`). Monitor for clients that do **not** honor these.
. **gRPC** — confirm no deployment sets `PROXIMADB_GRPC_V1_COMPAT=1` (it's already
  default-off; a deployment metric/env audit).

== Risks

* **Breaking** — step 1 returns `410` for any in-flight `/api/v1` client. Mitigation:
  the sunset-window checks above + one-line revert.
* **Deletion of live code by mistake** — the `rest/v1` name collision is the trap;
  this TD's boundary table is the safeguard. The root-crate `src/network/rest/v1/`
  is live and must not be touched.
* **gRPC v1 escape-hatch removal** — step 4 removes the compat feature; confirm no
  deployment relies on `PROXIMADB_GRPC_V1_COMPAT=1` first.
