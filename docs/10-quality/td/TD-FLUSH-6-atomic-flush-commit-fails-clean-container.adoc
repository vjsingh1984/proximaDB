= TD-FLUSH-6: Atomic flush commit fails against a clean object-store container — ingest stalls at record_count 0 under permanent backpressure
:status: Open
:dim: D1
:pillar: REL

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Open — UNDIAGNOSED.** Filed to stop the symptom being attributed to unrelated log noise (see "Ruled out"). The mechanism is not yet known; this TD scopes the diagnosis, it does not claim a cause.
| Priority | **P0 for the object-store bench posture** — SIFT-1M ingest against Azurite cannot complete, so every object-store-backed measurement (recall, GETs/query, flush timing) is blocked.
| Component | `src/storage/transaction_coordinator.rs:531` (`finalize_atomic_operation`), reached via `src/storage/engines/sst/flush/mod.rs:608` and `src/storage/engines/sst/flush/operations.rs:131`.

== Symptom chain

Flush cannot commit ⇒ the memtable never drains ⇒ backpressure never lifts ⇒
writes are rejected indefinitely ⇒ `record_count` never leaves 0. The
user-visible failure is "ingest is dead"; the actionable failure is the commit.

== Ruled out (with evidence)

* **Not the warm-cache path error.** The adjacent
  `az://…/data/default///manifests/warm_cache.json: Invalid path` log line was
  initially read as the root cause. It cannot be: both the write and read sides
  of that path are best-effort and swallow errors
  (`warming.rs:91`, `warming.rs:114-115`). Tracked separately as
  link:TD-CACHE-5-warm-manifest-invalid-path.adoc[TD-CACHE-5].
* **Not an empty `namespace_id`.** `DrPathBuilder` is fail-closed on empty
  segments (`validate_id`, `path_resolver.rs:922`); a missing namespace yields
  an error, not a malformed path, and the flush path does not depend on the
  namespace-identity gap at all (that gap is real and separate — ADR-074).
* **Not a code regression** — the older binary fails identically on a clean
  container.
* **Not** disk capacity (161 GiB free), Azurite writability (probe upload
  succeeded), or env-gate configuration.

== Diagnosis plan (in order)

The commit path after the metadata lookup does three object-store operations,
each with a plausible clean-container failure mode:

1. **`list(&metadata.staging_url)`** (line 571) — on a clean container the
   staging prefix may not exist. Object stores return an empty listing for a
   missing prefix, but a backend that errors instead (or a
   `create-then-immediately-list` consistency window on Azurite) would surface
   exactly here. Check whether the failure is the `Failed to list staging
   directory` context or the outer one.
2. **`move_atomic(staging → final)`** (line 597) — object stores have no
   rename; this is copy+delete underneath. A clean container means the
   destination prefix has never been written, so any implicit
   parent-prefix/`AlreadyExists` assumption differs from the warm-container
   case that previously succeeded. This is the leading suspect because it is
   precisely the axis on which clean and warm containers differ.
3. **`Operation not found: {id}`** (line 539) — the metadata lookup fails if
   `begin_atomic_operation` never registered, e.g. because `begin` itself
   failed earlier and the error was swallowed upstream. Confirm `begin`
   succeeded before assuming the fault is in `finalize`.

Fastest discriminator: re-run with `RUST_LOG=proximadb::storage::transaction_coordinator=trace`
— the body already emits the staging URL, the entry count, and each
`Moving file: {src} -> {dst}` at `trace!`, which distinguishes all three
without adding instrumentation. Capture the full `anyhow` context chain, not
just the outermost `Failed to commit atomic flush operation` string; the
proximate error is one or two `.context()` layers down and has been lost in
every report so far.

== Why it escaped CI

The recall/flush ratchet added in #1208 exercises flush in-process
(`do_flush`), bypassing the REST → WAL → flush write path, and the
object-store-emulator suite does not run a full ingest to flush against a
freshly created container. A regression test for this belongs on the
clean-container axis specifically — a warm container masks it.

== Verification

* SIFT-1M (or a reduced N) ingest against a **freshly created** Azurite
  container completes, `record_count` advances, and `.pax` segments land at the
  final prefix.
* Same run against a container that already holds prior-session state (the
  historically passing case) still succeeds — the fix must not trade one state
  for the other.
* Add the clean-container ingest→flush case to the object-store-emulator job.
