= TD-BENCH-2: Azure-geometry settle loses a materialize-vs-deadline race at high RTT

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Open — reproduced 2/2 high-RTT arms; direction sketched, fix not started**
| Priority | P2 — blocks high-RTT benchmark beds (the §3-style verdict methodology), not production paths
| Severity | Measurement-infrastructure: silently discards otherwise-valid arms after up to 60 min each
| Component | `scripts/bench/sift1m_get_reduction.py` — `AzureCliPaxGeometry` (`inventory`/`materialize`), `wait_for_materialization`
| Discovered | TD-RDSTRAT-12 §3 round-4 RTT-ladder (2026-08-30); arms a1@RTT-100 and a0@RTT-150 both failed identically while the 50 ms pair passed
|===

== Problem

`wait_for_materialization`'s settle loop requires, inside one `timeout_seconds`
budget: quiescent layout (names + segment count) → a stable etag-signature
window → THEN `AzureCliPaxGeometry.materialize()`, which downloads EVERY PAX
segment in full (`az storage blob download` per segment — ~267 MB on SIFT1M)
through the measured network before any row can be verified.

At 50 ms injected RTT the download fits the remaining budget. At 100–150 ms —
with per-call latency also multiplying each `az` spawn — the loop exhausts its
deadline while `materialize` is still downloading (or before the stable window
even opens), and raises:

----
materialization/compaction did not quiesce: rows=not-snapshotted/1000000,
segments=2 (max 3), last_parse_error=None
----

`last_parse_error=None` is the tell: nothing failed — the work simply did not
fit. Both ladder arms failed this way on a healthy daemon (the earlier wedged
daemon was force-restarted and ruled out), while the 50 ms pair passed
identically configured.

Secondary hazard: `materialize` runs AFTER the stable window, so its results
(footers → `layout_candidate_is_ready(azure_inventory=False)`) can invalidate
the stable window and force another full cycle — another full re-download.

== Direction (not started)

. Decouple row verification from the deadline: fetch ONLY footer bytes
  (range request per segment: footer offset+len are known once segment sizes
  are listed) instead of whole-segment downloads — reduces materialize from
  ~267 MB to ~KBs and removes the race class entirely.
. Account time honestly: give `materialize` its own budget and check the
  deadline only after it returns (the loop currently can also re-enter the
  stable window on post-materialize layout checks that reread the same
  etag-gated bytes — deterministic, so a second full cycle is pure waste).
. Optional: parallelize per-segment downloads (bounded, e.g. 4) — same
  spirit as the storage layer's wave.
