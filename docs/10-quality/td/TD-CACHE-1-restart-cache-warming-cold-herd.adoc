= TD-CACHE-1: Restart cache warming — defuse the post-eviction cold herd at its source

== The finding

Cold-vs-hot is a ~150× QPS gap and a ~500× $/QPS gap (RAM at ~$2.50/GB-mo pinning 4 tenants/GB vs cold CPU at ~$30/QPS-mo). All the supply-side levers (TD-SEARCH-2 S2 raising the cold ceiling, #1175 shortening L0 windows) still leave the demand spike itself: a restart converts the ENTIRE working set to cold simultaneously. The cheapest fix is to not have the herd — re-warm the caches before (or as) traffic lands.

== Direction

S1 — **Invariants prefill on collection load (no new state, biggest win/LOC).**
At engine collection registration, for each discovered segment, issue the 3
coalesced control reads (header-prefix + footer + A0 region) and `put` them
into `SegmentInvariantsCache` — exactly the bytes the first query would fetch,
~tens of KB per segment, done concurrently. Converts the first-query 3-GET
penalty per segment into boot-time background I/O measured in tens of ms.
Bounded by the existing cache byte budget; no format change; no config beyond
an on/off env (default ON — it is strictly work the first queries would do).
NOTE: prefill retention assumes priority-aware eviction — see TD-CACHE-2 (the
invariants cache currently evicts arbitrary victims when over budget, which
could shed warmed Region A entries first).

S2 — **Survivor-range warm-set manifest (small persisted artifact, opt-in).**
The survivor cache's keys `(path, off, len, kind)` describe the hot set
compactly (~100 B/entry). Periodically (and on graceful shutdown / Spot
eviction notice — Azure gives 30 s) persist the top-K keys per tenant by hit
count to a `warm.manifest` object next to the collection (via `DrPathBuilder`,
`TenantContext` attached). On boot, replay the manifest: coalesced ranged GETs
re-populate the cache before/while serving. Mixed-read-safe by construction:
the manifest is advisory; absent/stale/corrupt ⇒ ignore (cold start as
today); entries referencing compacted-away segments fail the existence check
and are dropped. Billing: replay GETs are metered exactly like the cold
queries they replace — net ≤ 0 new GETs, strictly better latency shape.

S3 — **Tenant-priority warming.** Warm in tier order (Enterprise/pinned
first — the hot-cache tier at $0.15/GB-mo is a *contract* to be warm), then
recently-active tenants from the manifest's hit counts. A free/idle tenant
stays cold-on-first-touch by design.

S4 — **Eviction-notice fast-drain hook.** On the Spot 30 s notice: flush
memtable (existing), snapshot the warm manifest (S2), and pre-signal the
replacement node (when the control plane orchestrates one) so warming starts
before DNS/LB cutover.

== Non-goals
Whole-corpus RAM residency (the Qdrant model — surrendered cost advantage);
warming cold tenants nobody queries; any read-path format change.

== Verification
- Restart-under-load harness (extend #1172 T5): kill -9 with c=8 sustained
  mixed-tenant load → with S1+S2, p95 within 2× steady-state within 10 s of
  healthy, and post-restart GET count ≤ the manifest replay budget (vs the
  unbounded herd today). Recall unchanged (warming is byte-identical data).
- Free-tier profile: post-restart free-op consumption bounded (≤ manifest
  size), verified against the 20k-ops budget.
