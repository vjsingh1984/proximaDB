= TD-STACK-1: Latent ~2 MB-deep recursion on the document/JSON pgwire path overflows default tokio worker stacks

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Proposed (mitigated).** `RUST_MIN_STACK=16 MiB` on the pgwire-accuracy CI step makes both failing tests pass (tokio workers are std threads and honor it when no explicit stack size is configured). The recursion itself is UNFIXED and the mitigation must be removed when it is.
| Priority | **P2 (downgraded 2026-07-24)** — the production server runtime was ALREADY hardened: `apps/proximadb-server/src/main.rs:132` sets `thread_stack_size(32MiB)` on the sole query-serving multi-thread runtime (added for TD-XMODAL-7 DataFusion planner recursion), so the crash class only ever threatened the 2MB-default TEST harness (mitigated via the CI `RUST_MIN_STACK` env in #1179). The recursion itself remains unfound/unfixed; S1 backtrace capture stands. Previous assessment: **P1** — production risk, not just CI: server runtimes also default to ~2 MB worker stacks, so a sufficiently nested document/JSON workload can SIGABRT a live worker (crash, not error). The failing tests use only 3 small documents — the depth is structural, not data-proportional in any obvious way.
| Component | The pgwire → materialize → document/JSON serving path exercised by `tests/document_json_pgwire_e2e.rs` and `tests/events_tsbs_pgwire_e2e.rs`. Recursion site UNKNOWN — candidates: `ProximaTreeNode` (recursive enum) serde/traversal/Drop, DataFusion logical/physical plan recursion over JSON expressions, arrow nested-schema builders.
| Evidence | Both tests SIGABRT ("thread 'tokio-rt-worker' has overflowed its stack") immediately after `materialize: 1/1 tables`, deterministic, 3× nextest retries. `git bisect` (good 4f0b598cf / bad 5707002c0 = #1169) lands on a **pure function with no recursion** — a code-layout/inlining straw proving the depth sat just under the 2 MB boundary before it. `RUST_MIN_STACK=16 MiB` ⇒ both pass ⇒ bounded (2–16 MB) recursion, not runaway. Failure predates and is independent of #1175/#1179 content (reproduced on bare develop at multiple commits).
|===

== Direction

S1 — **Capture the overflowing backtrace**: run the test binary under lldb with
the nextest filter (batch-mode attempt timed out under the CI-investigation
time-box; rerun interactively or with `--test-threads=1` and a breakpoint on
`abort`), or instrument with a stack-depth probe. Identify the recursive
frames.

S2 — **Fix the recursion**: iterative rewrite (explicit stack) or bounded-depth
guard with a proper error, per the site. Then REMOVE the `RUST_MIN_STACK`
mitigation from `ci.yml` and add a regression test asserting the path serves
under default stack sizes.

S3 — **Server hardening decision**: whether production runtimes should set an
explicit `thread_stack_size` (defense against the whole class) or stay at
defaults with the recursion fixed — decide with the S1 findings.
