= TD-FLUSH-1: In-memory data not reaped after flush (OOM risk + masks warm I/O)
:toc: macro

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Open**
| Severity | Critical — unbounded memory growth → OOM for large/long-running workloads; also masks the warm-path I/O measurement (warm GETs = 0 because the unreaped memtable serves everything).
| Component | Flush path — `src/storage/flush_materializer.rs`; AXIS `collection_vectors` — `src/index/axis/management/`
| Tracked-by | link:../../12-design/STORAGE_FORMAT_DECISION_FRAMEWORK_2026_06_29.adoc[Storage-Format Decision Framework] (PR #553)

== Symptom

After `db.flush()` (with `free_wal=true`), Stage 1 of the search path
(`wal_manager.search_unflushed_vectors`) **still returns ALL vectors** from memory:
```
Stage 1 complete: 1000 WAL results   ← ALL vectors still in memory after flush
```

This means the in-memory data was **not fully reaped** after flush. Two consequences:

1. **OOM risk**: the in-memory store grows unbounded — every insert accumulates, flush doesn't clear
   it all. Large/long-running workloads will exhaust memory.
2. **Warm GETs = 0**: the unreaped in-memory copy serves every warm query → the SST files are never
   read → `CountingFileSystem` measures 0 warm GETs → the warm-path I/O is unmeasurable.

== Root cause

`clear_flushed` (`flush_materializer.rs:196`, `free_wal=true` path) reaps:
- **WAL write-buffer batches** (`write_buffer.clear_flushed(&plan.wal_key)`) — ✓ cleared.
- **WAL log files** (`mark_flushed_and_delete_files`) — ✓ deleted.

BUT it does NOT reap:
- **`AxisManager::collection_vectors`** — a separate in-memory `ProximaRecord` map used by the AXIS
  index for exact-filtered fallback + MVCC expiration lookup. This map retains ALL vectors after flush.
- **Block-cache entries** for the flushed collection (the 1 GiB DashMap/moka cache).

So the vectors live in memory in 3+ places; flush clears only 1 (the WAL batches).

== Fix approach

After a successful flush (`free_wal=true`), reap ALL in-memory copies:

1. WAL batches — existing (`clear_flushed`). ✓
2. `AxisManager::collection_vectors` for the flushed collection — **new**: add a
   `clear_collection_vectors(collection_id)` method to the AxisManager + call it from the flush path.
3. Block-cache invalidation for the flushed collection — **new**: invalidate (or selectively evict)
   the collection's entries from the block cache.

After the fix, warm queries must read from SST (Stage 3) → **warm GETs > 0** (real per-query I/O,
measurable via `CountingFileSystem`).

== Dependencies

- **Unblocks**: TD-IOTRACE-1 (warm-path GET measurement meaningful only after the memtable is reaped).
- Related: TD-163 (PR #393, `free_wal=true` for the server flush) — the server path already sets
  `free_wal=true`; the embedded path does too, but the `collection_vectors` reap is missing in both.
