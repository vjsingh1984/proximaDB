= TD-LIFECYCLE-1: process exit after SIGTERM blocked by leaked background shutdown senders
:status: Open (mitigated)
:filed: 2026-07-24
:priority: P2

== Symptom (measured)

Restart-under-load verification for the production-resilience package
(feat/restart-resilience, 100k SIFT bed): after SIGTERM the server logs the
full clean shutdown sequence — flush, compaction stop, warm-manifest emit,
`Server shutdown complete`, `ProximaDB server stopped` — but the **process
never exits** (observed >2 min, state R). `sample` shows the main thread stuck
in `drop_in_place<tokio::Runtime>` → `BlockingPool::shutdown` → `park`, while a
blocking-pool worker is still executing
`services::discovery::passes::run` under
`DiscoveryJobExecutor::execute` / `spawn_discovery_executor`.

== Root cause

`src/network/shared_services.rs` (discovery executor spawn block, and the
recall observer that documents itself as "matching the discovery executor")
**intentionally leaks the shutdown watch sender**:

[source,rust]
----
let (shutdown_tx, shutdown_rx) = tokio::sync::watch::channel(false);
std::mem::forget(shutdown_tx);
----

The executor's `watch`-based cooperative shutdown therefore never fires, and
its drain loop (`while executor.run_once().await.is_some() {}`) also does not
re-check shutdown between jobs. `Runtime::drop` waits for in-flight blocking
tasks, so one long/looping discovery pass at teardown blocks exit forever.
Under systemd/K8s the supervisor's grace-period SIGKILL masks it; on a bare
Spot instance the process wastes the eviction notice window doing nothing.

== Mitigation (shipped with feat/restart-resilience)

`apps/proximadb-server/src/main.rs`: `runtime.shutdown_timeout(5s)` after
`block_on(run())` returns — durable state is persisted by
`ProximaDB::shutdown` before this point, so bounding teardown is safe. The
process now exits deterministically ≤5 s after a clean shutdown.

== Durable fix (open)

1. Register the leaked senders in a process-level shutdown registry
   (discovery executor, recall observer, drift watch) and flip them from
   `ProximaDB::shutdown` before server stop.
2. Re-check the shutdown receiver inside the drain loop
   (`spawn_discovery_executor`) so a queued backlog cannot extend teardown.
3. Audit for other `std::mem::forget(<shutdown sender>)` /
   dropped-JoinHandle always-on loops (mandate #11: no non-daemon background
   work that outlives shutdown).
