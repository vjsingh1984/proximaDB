== Finding (2026-07-12)

The engine taxonomy is told four different ways:

1. **`StorageEngineStrategy` enum** (canonical type after #906/#910): `Sst`, `Viper`,
   `Helix`, `Nova`, `Swift`, `Raptor`, `Hybrid`, `TimeSeries` (TST), `Cedar`, `Chrono`
   — 10 variants. Until this filing's PR, `Helix` was doc-commented "time-series
   optimized storage" (copy-paste of the TST line) while the engine's own header
   (`src/storage/engines/helix/mod.rs`) describes a spatial-locality vector engine
   (Hilbert-curve clustering, zone maps).
2. **Engine module tree** (`src/storage/engines/`): `sst`, `viper`, `helix`, `nova`,
   `swift`, `raptor`, `cedar`, `chrono`, `tst`, plus `sequoia`, `titan`, `universal` —
   the last three have **no enum variant**; graph's ORION lives separately under
   `crates/modalities/proximadb-orion-engine`.
3. **`SUPPORTED_SURFACE.adoc`** support tiers: names a subset (GA/Beta/Experimental)
   that predates several of the above.
4. **Design docs / external analyses**: SYSTEM_MAP and ADRs enumerate
   SST/HELIX/NOVA/VIPER (+ gated RAPTOR/SWIFT, ORION) — the external architecture
   analysis reviewed on 2026-07-12 reproduced exactly this partial list, unaware of
   cedar/chrono/sequoia/titan/tst/universal.

*Why it matters (first principles):* the `ComputeScheduler` module doc states "one
engine taxonomy across read and write" as an invariant. When the enum, the module
tree, the support contract, and the docs each tell a different story, every consumer —
routing code, capability matrices, support commitments, agent sessions, external
evaluators — resolves the disagreement by guessing. That is the same drift class as
TD-DOCS-2, instantiated in the engine inventory.

== Deliverable

1. **One canonical engine matrix** (proposed home: `SUPPORTED_SURFACE.adoc`, which the
   status-as-of guard already covers): engine → one-line purpose → support tier
   (GA/Beta/Experimental/Internal-only) → enum variant → module path → feature gate.
   Every engine in `src/storage/engines/` appears exactly once; `sequoia`, `titan`,
   `universal` get an explicit tier (or an explicit retirement note), and ORION is
   listed with its graph-modality home.
2. **Enum doc comments align to the matrix** — each `StorageEngineStrategy` variant's
   comment matches the engine's own module header (the implementation truth), as done
   for `Helix` in this filing's PR.
3. **Design-doc inventories point at the matrix** instead of re-enumerating (SYSTEM_MAP
   engine sections link to it), so the list can no longer fork.
4. **Decide the missing-variant question deliberately**: either `sequoia`/`titan`/
   `universal` earn enum variants (they are routable strategies) or the matrix marks
   them internal/experimental-only (they are implementation substrates, not
   strategies). Record the decision in the matrix, not in tribal knowledge.
