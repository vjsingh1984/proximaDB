== Two capabilities are stranded; the SDP ones are placeholders

CORRECTION (2026-08-18): this TD was filed claiming three of four capabilities already existed in
the Rust SDP pipeline and merely needed pulling down. **That claim was wrong, and reading the code
is what disproved it.** SDP's four stages are named for the capabilities but implement none of
them:

[cols="2,3",options="header"]
|===
| SDP stage | What the code actually does
| 1 — "structure-aware splitting" | `text.split("\n\n")`. Its own comment says a real one "would use a Markdown/HTML parser". No structure is parsed and no heading path is produced.
| 2 — "context-conditioned enrichment" | Prefixes every chunk with the **first chunk's first line**. Contextual retrieval means per-chunk, document-conditioned context; a static document-title prefix is a different and much weaker thing.
| 3 — "semantic boundary refinement" | Writes a metadata flag recording whether the chunk ends in `.!?`. Refines no boundary.
| 4 — "topic-aware deduplication" | Merges neighbours under a hardcoded 100-character threshold. There is no topic signal anywhere in it, and merging small neighbours is not deduplication.
|===

`use_sdp` defaults to `false` and nothing in the tree sets it to `true`, so none of this has ever
run in product. The honest inventory is therefore:

[cols="2,3,2",options="header"]
|===
| Capability | Where it exists | State
| Heading-aware splitting **with hierarchy path** | anvaiops connector-sdk (used by Confluence/SharePoint/Google Drive) | **Genuinely implemented**, in the wrong layer. ProximaDB's `semantic.py` detects headings then **discards them**.
| Abbreviation-aware sentence splitting | Victor `rust/…/chunking.rs`, compiled + shipped as `victor_native` 0.1.0 | **Genuinely implemented, never called** — its only Python front end has zero callers, while five Python regexes do the job worse.
| Context-conditioned enrichment | — | **ABSENT.** SDP stage 2 is a title prefix, not contextual retrieval.
| Topic-aware deduplication | — | **ABSENT.** SDP stage 4 is a 100-char merge with no topic signal.
| Semantic boundary refinement | — | **ABSENT.** SDP stage 3 sets a flag.
|===

Why the correction is worth the words: "stranded" and "absent" imply opposite plans. Stranded means
wire it up; absent means design, build, and evaluate it. Had this TD been executed as filed, the
work would have been to port stubs — inheriting four placeholder implementations under names that
promise real capabilities, which is worse than starting from nothing because the names would have
suppressed the design work. **A named stage is not an implementation**, and this is the second time
in this program that reading the code contradicted a confident claim about it (the first: Rust does
read `size_tokens`/`overlap_pct`, which I had said had zero readers).

Consequence for scope: this is now **two** consolidations (heading paths, the Rust splitter) plus
**three** genuinely new capabilities, not "three of four already built". The sequencing below is
unchanged — it already put the cheap consolidations first — but the effort estimate for items 2, 4
and 5 must be read as new design work, and each needs the eval rubric below before it is written,
not after.

Genuinely new work, and the reason this TD is not pure plumbing:

* **Parent-document / small-to-big retrieval** — index small precise child chunks, return the larger
  parent for generation. The biggest retrieval-quality lever in the list and entirely absent; no
  parent/child linkage exists on `TextChunk`. **ProximaDB is uniquely placed**: the parent edge is an
  ORION graph edge, not a duplicated metadata copy — which is a differentiator no pure vector store can
  offer, and the clearest case in this program for building rather than borrowing.

== Co-design framing

Each item names the cost term it moves, per the mandate — no item lands on "it would be nice":

* **Topic dedup → KEU and KSU directly.** A duplicated chunk is paid for once in embedding and forever in
  storage. This is the only item that *reduces* cost rather than trading it — and, per the correction
  above, it must be **built**, not wired up.
* **Heading paths → recall at constant cost.** Metadata on an existing chunk; no extra vectors, so no KSU
  or KEU delta. Strictly free quality.
* **Context enrichment → KEU up, recall up.** Prefixing lengthens the embedded text, so it must be
  measured, not assumed: gate on recall@k per KEU spent, not on recall alone.
* **Small-to-big → KSU up (two granularities), read cost *down*.** Fewer, more precise probes at query
  time. The trade must be measured on the ADR-091 corpus before it is defaulted on.
* **Rust splitter → compute down, quality up.** Replaces ProximaDB's two Python regexes, one of which is
  the quadratic path (518 KB → 17.5 s). Evaluate behind the TD-CHUNK-2 port, which is exactly the seam
  ADR-091 chose so a native segmenter is a backend swap and not a rewrite.

== What heading paths taught (2026-08-18, item 1 done)

* **Detection was never the gap.** `semantic.py` already found markdown and HTML headings and already
  excluded a `#` inside a fenced code block. What it discarded was the **hierarchy** — it recorded
  "level 2, titled Docker", never "Installation > Docker". Level and title do not identify a section;
  the path does. The census entry "detects headings then discards them" is more precisely "detects
  headings, keeps level and title, discards the ancestor chain".
* **The value is the annotator, not the boundary source** — and this follows from TD-CHUNK-2's
  token-granularity finding. A heading *start* and the preceding paragraph *end* usually fall within
  one token, so a heading source often moves no cut. A source can only describe chunks that happen to
  END on one of its proposals, and most chunks end mid-section because the budget ran out. Labelling
  by **lookup** (`annotate_heading_paths`) works for every chunk under every strategy, including
  `fixed_size`, which knows nothing of structure.
* **The extraction was the point.** The correct detection was private inside `SemanticStrategy` —
  exactly how this census's five forks happened. It moved to `structure.py` and is now shared rather
  than copied, asserted by a test so a private copy cannot drift back.
* **Wiring is part of the item, not a follow-up.** This census's central finding was capabilities
  built and never called; landing an annotator no ingest path invokes would have reproduced the
  finding rather than fixed it. It is called from `TextDocumentProcessor`, the SDK's only production
  text-ingest path (and the one anvaiops delegates to), gated on the previously-DEAD
  `preserve_structure` flag rather than a third structure-ish setting.
* Content before the first heading is deliberately left **unlabelled** rather than given an invented
  "Introduction", which would put a title in the index that the document never contained.

== Sequencing

Cheapest-and-free first, so value lands before the expensive measurement work:

. **Heading paths** — constant cost, immediate filtered-retrieval win, and half-built already in
  `semantic.py`'s detection.
. **Topic dedup** — the only cost *reduction*; gate on a recall ratchet so dedup can never silently drop
  a distinct chunk.
. **Rust splitter behind the port** — evaluate against the Python sentence source on the shared corpus.
. **Context enrichment** — requires the KEU-per-recall measurement to justify.
. **Small-to-big on ORION edges** — the largest piece of new design; sequence last so it lands on a port
  and an invariant suite that are already proven.

== The eval harness exists (2026-08-18) — items 2/4/5 are now unblocked

Built on `feat/chunk-boundary-port` as `conformance/evals.py`, because this TD says the absent
capabilities need their rubric *before* they are written. Eight cases, each a real question expressed
as the literal span that answers it, scored on **output** (containment, density) and **trajectory**
(structural integrity, attributability), gated on recorded floors in the same CI job as the invariant
ratchet.

**The design decision worth carrying forward: this is deliberately NOT an eval of the embedding
model.** Scoring recall@k would move the gate whenever the model or the index changed, so a red gate
could never be attributed to chunking — and a gate that cannot attribute its own failure gets muted.
Every metric is model-independent and measures only what the chunker decides. Retrieval-level
recall@k belongs in the ANN harnesses, where the model *is* the thing under test; this measures the
layer underneath, which those harnesses assume and never check.

Two results worth acting on:

* **SEMANTIC scores best on every axis** (containment 1.00, density 0.462, structure 1.00,
  attributability 0.62) — the strategy production was repointed *away from* in #1670 for losing up to
  100% of a document. Its correctness defects are fixed; its boundary quality is the highest of the
  seven. This is precisely the measurement `TextDocumentProcessor._get_chunker` asks for in its own
  comment. **Filed as evidence, not acted on** — eight synthetic cases is not enough to flip a
  production default, and the comment already asks for that to be a separate, measured decision.
* Scoring must happen at a **tight budget**. At the default 512 every corpus answer fits and every
  chunker scores 1.00 containment; a saturated metric measures nothing. A guard test now fails if the
  rubric ever flattens again.

== Evals, not just tests

Boundary quality is a ranked surface, so per the evals mandate it needs a rubric rather than an
assertion. Gate on **output** (does retrieval return the span that answers the question) and
**trajectory** (was the boundary source appropriate to the document's shape), measured as recall@k
against the f32 baseline on the ADR-091 corpus, threshold-gated in CI, with suites versioned in the PR
that changes behaviour. Every item above ships default-OFF until its eval clears.
