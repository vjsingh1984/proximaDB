== Context (the gap Phase 1b left)

Phase 1b routed the graph **gRPC + Flight node/edge ops** through `for_tenant`, composing the
structural scope `{tenant}/{graph_id}` once at the boundary. But graph **collection creation** was
NOT scoped, and the two are coupled by a hard gate:

* `get_or_create_graph_engine(graph_id)` (`service_engine_factory.rs:35`) is *not* purely lazy — on
  an engine-cache miss it **verifies the collection exists in `collection_service`** and errors
  `Graph collection '{}' does not exist` otherwise.
* Graph collections are created bare (`create_graph_collection(graph_id, …)`) via the v1 REST
  handler, pgwire `CREATE`, `database.rs`, embedded, and internal paths — **none tenant-scoped**.
  There is no `POST /api/v2/graphs` create endpoint; the v2 gRPC surface defers creation to REST.

Consequence: once node/edge ops scope to `{tenant}/{graph_id}` but creation stays bare, every
scoped create→use fails the existence gate. Two symptoms:

* **Default-tenant regression (fixed surgically here):** `resolved_tenant_id` returns the canonical
  `"default"` (never empty), so absent an explicit tenant the ops scoped to `default/{graph_id}`
  while creation stayed bare — breaking the previously-working single-tenant flow (the
  `service_with_graph` gRPC handler tests: `node_crud_roundtrip`, `edge_query_traverse_shortest_path`,
  `td124_batch_analytics_constraint_stream`). Mitigated by making `scoped_graph_id` return the BARE
  id for the DEFAULT tenant (creation is bare, so reads must be bare too) — see the comment in
  `scoped_graph_id`.
* **Named-tenant isolation is not yet functional:** a real tenant creating a graph via REST/pgwire
  (bare `graph_id`) and then node-op'ing via gRPC (`{tenant}/graph_id`) hits "collection does not
  exist". Phase 1b's `{tenant}/…` scoping is therefore **foundational plumbing** (clean network
  names + one composition point + fold removal), NOT end-to-end isolation. The isolation tests pass
  only because they provision the backing collection under the scoped key explicitly. NOTE: this is
  **not a regression** — before Phase 1b the `{tenant}::{graph_id}` fold had the identical create→use
  break for named tenants (creation never folded either); Phase 1b changed the separator, not the
  functional state.

== Landed (core fix — lazy auto-provision)

Named-tenant graph create→use is now **functional end-to-end** via lazy provisioning, chosen over
threading scoped creation through every request-scoped create path (which would need `TenantContext`
added to legacy REST v1, pgwire-create scoping, a facade create forwarder, and `{tenant}/` strip
logic across many response sites):

* `GraphCollectionService::ensure_or_create_graph(graph_id)` (`src/services/graph_collection.rs`) —
  race-safe get-or-create; on a miss it registers the collection with defaults (ORION engine,
  service default storage root) under the passed key.
* `get_or_create_graph_engine` (`src/graph/service_engine_factory.rs`) now calls it instead of
  `ensure_graph_exists`. So a tenant-scoped first write (`for_tenant` composes `{tenant}/{graph_id}`)
  auto-registers its collection under the scoped key — no out-of-band bare create needed. The
  default tenant stays bare, so its explicitly-created collections are found on the first branch and
  never double-provisioned.
* Test: `named_tenant_graph_auto_provisions_on_first_write_and_isolates` (v2 graph_service) — a named
  tenant writes+reads under a clean logical id with NO explicit create; a second tenant on the same
  id is isolated (its own empty scoped graph). Ratchet +0; server binary + clippy clean.

== Remaining follow-ons (open)

* **Custom create metadata for named tenants.** Auto-provision uses DEFAULT engine/schema. A
  named tenant that wants a custom schema/engine still needs a tenant-aware create path (scope
  pgwire `create_graph_collection` + add `TenantContext` to a REST create, or add a v2 graph-create
  RPC that routes through `for_tenant().create_graph_collection`).
* **Default-tenant uniformity.** The default tenant stays bare (its create paths are bare). Once
  those creates scope, flip `scoped_graph_id` to also scope the default (`default/{graph_id}`).
* **REST v1 list scoping.** REST v1 `list_graph_collections` is unscoped and would surface named
  tenants' scoped keys (`{tenant}/{graph_id}`) to a default-tenant/legacy caller — scope + strip
  when REST v1 gains tenant-awareness.

== Original proposal (superseded by the auto-provision fix above)

== Proposed resolution (make it functional)

. **Scope graph collection creation in lockstep** — every create path that feeds a tenant-scoped
  read composes `{tenant}/{graph_id}` (via `scoped_graph_id` / a `for_tenant().create_graph_collection`
  forwarder that rewrites `req.graph_id`): the v1 REST create, pgwire `CREATE`, any `POST /api/v2/graphs`,
  and internal creators that are request-scoped. Internal/embedded/observability creators with no
  request tenant keep bare keys (they are single-tenant control-plane graphs).
. **Then flip the default tenant to also scope** (`default/{graph_id}`) for uniformity with the other
  modalities, once its creation path scopes too — removing the bare-default special case in
  `scoped_graph_id`.
. **Consider making the create gate auto-provision** for scoped keys (a scoped first-write lazily
  registers the collection) as an alternative to threading creation through every surface — evaluate
  against the metadata the gate needs (`engine_type`, `storage_root_url`).
. Gate with an end-to-end test: create a graph via the (scoped) REST/pgwire path under tenant A,
  node-op + traverse via gRPC under tenant A succeed; the same logical id under tenant B is isolated;
  a bare create→use under the default tenant still works.

== Constraints

* Keep net `proximadb_v1` references non-increasing (TD-123 ratchet, baseline 2917).
* Any change to the on-disk graph key shape must be mixed-read-safe (no flag-day).
* This is shared collection-lifecycle work with [[TD-DOC-TENANT-1]] / [[TD-ENTITY-TENANT-1]] — a
  single "scope collection creation across modalities" effort likely subsumes all three.
