= TD-CACHE-2: `CacheTier::evict_priority()` is unwired — actual eviction is arbitrary (invariants cache) and kind-blind (survivor cache)

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Proposed.** Found 2026-07-24 while auditing the ADR-065 tiering design against the code: the per-tier admission/eviction policy the enum documents is not enforced anywhere.
| Priority | **P2** (P1 once TD-CACHE-1 warming lands — warming's value depends on priority-aware retention).
| Component | `src/storage/engines/sst/segment_format.rs` (`CacheTier::evict_priority`, `SegmentInvariantsCache::put` eviction loop), `crates/foundation/proximadb-cache` (`TenantCache`, `CacheKind`).
| Evidence | `grep -rn "evict_priority"` → **zero callers** outside the definition. `SegmentInvariantsCache::put` evicts `map.keys().next()` — HashMap iteration order, i.e. an arbitrary victim: a hot segment's Region A (~24 MB, re-read every query — the tier the enum pins at priority 3) can be evicted while a cold segment's entry survives. `TenantCache` uses `CacheKind` for stats separation only; eviction is byte-budget/moka policy, kind-blind.
|===

== The finding

The ADR-065 cache-co-design intent — RaBitQ Region A + control prefix hardest
to evict (a hit saves the full-region GET), then meta, then OID ranges, then
SQ8 survivor ranges (cheapest to refetch) — is encoded in
`CacheTier::evict_priority()` and its doc comment ("One enum drives BOTH the
per-tier GET trace AND the cache's per-tier admission/eviction policy"). Only
the first half is true: the trace uses the enum; no eviction path consults it.

What protection exists today is **structural only**: Region A lives in
`SegmentInvariantsCache` with its own byte budget, so survivor/OID churn in
the separate `TenantCache` cannot displace it. Within each cache, policy is
absent (arbitrary victim) or generic (moka default).

== Direction

S1 — **Invariants cache: priority-then-recency victim selection.** Replace the
`keys().next()` loop with: evict lowest `evict_priority` first, ties by
least-recent touch (a per-entry `last_hit: AtomicU64` tick is enough; no full
LRU list needed at this entry count). This is the same small rework moment as
the TD-SEARCH-2 S2 lock fix (shard or `RwLock` the map) — do both in one pass
over the structure.

S2 — **Survivor cache: kind-weighted budgets.** Give `TenantCache` optional
per-`CacheKind` budget fractions (e.g. QuantizedCodes ≥ 70% of pool) so OID
churn cannot flush SQ8 survivor ranges; full priority eviction inside moka is
not required — budget partitioning approximates it cheaply.

S3 — **Warming interaction (TD-CACHE-1)**: prefill (its S1/S2) must insert
with correct tiers so a budget-exceeding warm-up sheds the *right* entries
(survivor ranges before Region A), not arbitrary ones.

== Design note (2026-07-24): single pool vs per-region structures

Resolved three-axis split (from the "one DashMap or one-per-region?" question):

* **Budget = ONE shared byte pool** with per-class floor/ceiling fractions —
  never per-region static budgets (they need estimation and go stale as the
  workload phase shifts between ingest-heavy and read-heavy). Floors give the
  isolation separate pools would; elasticity removes the sizing guess.
* **Physical structures = two, by CONTENTION DOMAIN** (invariants + survivor),
  not five by region. When the TD-SEARCH-2 S2 lock rework shards the
  invariants map (DashMap-style), strict global victim selection conflicts
  with sharding — use **sampled eviction** (pick ~8 random entries across
  shards, evict worst by `(evict_priority, last_hit)`, Redis-style): near-exact
  policy, no global lock.
* **Entry granularity = split invariants keys by byte class** —
  `(segment, RegionA)` / `(segment, Control)` / `(segment, Meta)` instead of
  one bundled entry. Today evicting a segment's entry discards its ~100 KB
  always-useful control prefix along with the ~24 MB region; per-class keys
  make control/meta effectively evict-never (tiny) and Region A the single
  elastic class the pool manages. This delivers per-region policy without
  per-region structures.

S1 (exact global min under the existing mutex) is the correct stepping stone:
policy semantics land now; sampling + sharding + key-split ride the S2
structure rework.

== Verification
- Unit: over-budget `put` sequence mixing tiers → Region A/control entries
  survive, survivor/probe entries evicted first, ties by recency.
- The TD-SEARCH-2 S2 concurrency sweep re-run shows no hit-rate regression
  (policy change must not cost the 100%-hit hot path anything).
