== The finding

One policy — "how big is a server-side chunk" — is declared in **three** independent places. None of
them is connected to any other, and two of them disagree about what the words mean.

[cols="1,2,2",options="header"]
|===
| Where | Declares | State
| Wire | `proto/proximadb/v1/collection_types.proto:134-139` — `ChunkConfig { size_tokens, overlap_pct, strategy }`, reachable as `EmbeddingPolicy.chunk` | **No Rust code references the generated type.** Accepted on the wire, converted by nothing.
| Rust | `crates/modalities/proximadb-embedding/src/config.rs:430` — an independent, identically-named mirror struct; `Serialize`/`Deserialize`, embedded as `EmbeddingConfig.chunk`, re-exported from `lib.rs:57` | **Config-reachable and publicly exported**, so an operator can set it. Its only consumer (`chunker.rs`) has **zero callers** anywhere in the tree.
| SDK | `chunking_strategies` — `chunk_size`/`chunk_overlap` in the configured measure's units, now also `SizingPolicy(window=…, overlap=Fraction(…))` | Live, tested, and the only one that actually chunks anything.
|===

== Why this is more than duplication

**A settable field that does nothing is worse than an absent one.** `ChunkConfig` is serde-derived and
publicly exported, and `size_tokens`/`overlap_pct` are on the wire. A tenant can set `size_tokens: 512`
on a collection and observe no error and no effect. Absent surfaces get feature requests; inert ones get
bug reports and lost trust.

**The names do not mean what they say**, in the one implementation that exists
(`proximadb-embedding/src/chunker.rs`, verified 2026-08-18):

* `fixed_window` and `sliding_window` never touch the tokenizer. They compute
  `char_window = size_tokens * 4` (`chunker.rs:43,64`) and window over `chars`. So **`size_tokens` counts characters**, at a
  hardcoded 4× ratio, for two of the four strategies.
* The comment says "Approximate by character window first; refine with token count for boundaries."
  **There is no refinement** — no second pass exists.
* `overlap_pct` is therefore a fraction of a *character* window, not of a token budget.
* `size_tokens` means tokens only in `paragraph()`, the single site that calls
  `tokenizer.count_tokens` (`chunker.rs:101`).
* `ChunkStrategy::Heading` silently falls back to `paragraph` (`chunker.rs:35`), so a persisted
  `Heading` policy is a promise the code does not keep — the same defect ADR-091 D6 records for the
  catalog.

The 4× ratio is also the specific approximation ADR-091 exists to remove: characters under-count tokens
by roughly 4× on CJK, so a "256-token" window built as 1024 characters can carry ~1024 tokens and
overflow a 512-token model. The provider then truncates silently — recall loss with no signal — or
rejects the call.

== Why it was left out of the ADR-091 measure PR

That PR added `SizingPolicy(window=Absolute(512), overlap=Fraction(0.10))` to the SDK. The obvious
convenience would have been to make `Fraction` mean whatever `overlap_pct` already means, so the two
"match". That would have hardcoded an approximation nobody chose, in a new API, permanently.

Instead `Fraction` names its referent (`Of.WINDOW` — a fraction of the resolved window in the resolved
measure), and `Of` is an enum precisely so an explicit `CHAR_WINDOW_APPROX` member can be added **if**
this TD decides the wire semantics must be reproduced bit-for-bit. Matching by accident is the failure
mode; matching by decision is fine.

== Progress 2026-08-19 — option (2)'s prerequisite, done

The recommendation below was "retire, then wire when server-side chunking is actually built". The
Rust half of that is done: `chunker.rs` and the mirror struct are deleted. Nothing referenced
`Chunker`, and every construction site for `ChunkConfig` in the tree was a test — so removing it
destroys no behaviour, only a false implementation. `cargo check -p proximadb-embedding
--all-targets` is clean.

**The wire fields are deliberately still there.** No Rust references the generated type, so they are
inert either way, but removing a proto field requires regenerating every SDK in the same PR under
the spec-driven-SDK mandate. That is a coordinated change with its own drift gates and its own blast
radius, not a rider on a Rust deletion. It is the remaining work in this TD.

Net effect today: three spellings become two, and the surviving pair no longer disagree about
semantics — because the one that read `size_tokens` as `size_tokens * 4` characters is gone. The
inert-wire-field problem is unchanged and still the reason this TD is open.

== The decision to make

Pick one, deliberately:

. **Retire the wire fields and the Rust mirror.** Nothing consumes either. Server-side chunking is not a
  shipped capability, so removing an inert surface costs nothing today and prevents a compatibility
  obligation from accruing. Pre-GA this is a clean break (see the ENV_GATE_REGISTRY precedent for
  pre-GA renames); post-GA it is not available.
. **Wire them to the SDK's semantics** — `size_tokens` really counts tokens, `overlap_pct` is a fraction
  of the resolved window. Requires the Rust chunker to gain a real token measure, and makes the two
  implementations agree by construction rather than by comment.
. **Keep the approximation and document it** — rename to `size_chars_approx`/`overlap_char_pct` so the
  names stop lying, and add `Of.CHAR_WINDOW_APPROX` to the SDK for exact reproduction.

**Recommendation: (1), then (2) when server-side chunking is actually built.** The capability does not
exist; carrying a wire contract for it, in three spellings, is pure liability. (3) is the worst of both
— it preserves a hardcoded 4× ratio as a permanent contract.

== Acceptance

Whichever option is chosen, the TD closes only when **one** of these holds, asserted by a test:

* the wire fields and the Rust mirror are gone, and the proto change is recorded as a pre-GA break; or
* a document chunked through the wire policy and the same document chunked through the SDK at the
  equivalent policy produce the **same chunk boundaries**, on the ADR-091 conformance corpus.

A comment claiming the two agree is not acceptance — the existing "refine with token count" comment is
exactly the artifact this TD was written to distrust.

== Co-design note

Chunk count is the billable quantity (KEU once at embedding, KSU for the life of the collection), so a
policy that is silently ignored is not a cosmetic bug: it means the operator's cost lever is
disconnected from the cost. That is the argument for settling it before the capability ships, not after
it has tenants.

== Wire half executed 2026-08-19 — and it uncovered a broken build

`ChunkConfig`, `ChunkStrategy` and `EmbeddingConfig.chunk` are removed from
`proto/proximadb/v1/collection_types.proto`. **Field 2 is reserved by number and by name**, which is
the whole point of choosing removal over renaming: if server-side chunking ever ships it gets a new
field whose semantics are *decided*, and cannot silently inherit a meaning where `size_tokens`
counted characters at a hardcoded 4x ratio. Python stubs regenerated in the same change per the
spec-driven-SDK mandate; no other SDK had the type generated.

Regenerating also surfaced **pre-existing stub drift**: the checked-in `collection_types_pb2.py` was
missing `index_policy`, `pax_vector_quant`, the `IndexPolicy` message and the typed-id fields on
`StorageAssignment`. Proto changes had landed without the Python stubs being regenerated, and nothing
caught it — the `grpc_drift_baseline` gate compares *services and rpcs*, so a message-only change is
invisible to it. Worth its own follow-up; recorded here rather than fixed silently.

**The Rust deletion had broken the server binary.** `apps/proximadb-server/src/main.rs` still
constructed `proximadb_embedding::config::ChunkConfig::default()` on the startup path — not
feature-gated — after the struct was deleted, so `cargo check -p proximadb-server` failed while
`cargo check -p proximadb-embedding --all-targets` (what the earlier note recorded as clean) passed.
Exactly the gap the "verify the server binary builds, not just `--lib`" mandate names, and a reminder
that a per-crate check is not a build.

**Acceptance is met by the first of the two clauses**: the wire fields and the Rust mirror are gone,
and the proto change is recorded as a pre-GA break with the field reserved forever. The second clause
(boundary equivalence between a wire policy and the SDK) becomes the acceptance test for option (2),
if and when server-side chunking is built.
