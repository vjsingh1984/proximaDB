== Symptom

`storage::document::service::tests::test_canonical_document_wal_recovery_replays_into_record_store`
(and its `..._replays_deletes_...` sibling) intermittently fail under
`cargo test --lib`:

----
assertion `left == right` failed
  left: 0
 right: 1
src/storage/document/service.rs (recovered_records.len())
----

The failure is *not* deterministic:

* Passes in isolation (`cargo test --lib <test_name>`).
* Passes when the whole `storage::document::service::tests` module runs.
* Passes in clean full `cargo test --lib` runs (observed 8336 passed / 0 failed).
* Failed only during a full run executed under heavy concurrent build/test I/O.

== What it is NOT

It is *not* the global WAL manifest singleton, despite first appearances. The
document WAL recovery path does not touch `manifest::get_service()` at all:

* `DocumentService::recover_from_wal` reads via `UnifiedWALReader::read_all`,
  which reads `wal_{:08}.log` segment files directly from the service's own
  `wal_path` (a unique `tempfile::tempdir()` per test).
* `insert_document` / `flush_wal` write through a per-instance
  `UnifiedWALWriter` (also no manifest).
* `CedarEngine.collections` is a per-instance `DashMap` (fresh in `new()`), so
  the two tests do not share record state.

Therefore a `manifest::reset()` in the test would be a no-op dressed up as a fix.
Also ruled out: working-directory churn (the `set_current_dir` tests are confined
to `filesystem/local.rs`, `LocalConfig::default` has `root_dir: None`, and the
test uses absolute `file://` URLs); and any process-global filesystem cache
(none exists).

== Likely root cause

A write-then-read *visibility* gap in the WAL flush path under I/O load.
`UnifiedWALWriter::flush_current_segment` does `fs.write(url, full_data, None)`
followed by `fs.sync_file(url)`; a freshly constructed `UnifiedWALReader`
(separate `FilesystemFactory`) then opens and reads the same file. Under heavy
concurrent I/O this read occasionally observes an empty/partial segment, which
recovery silently tolerates (`read_segment` logs and continues on a deserialize
or truncation error), yielding zero recovered records.

This is a (rare) durability/visibility question in foreign WAL code that was in
active flux from the ADR-024 schema merge at the time of writing, so it was not
patched speculatively.

== Hardening attempts that did NOT work

* `drop(first)` before booting the `restarted` service (to model a true restart
  and release the first writer's file handles): made things *worse* — both
  recovery tests failed when run together, recovering the wrong document
  content. Reverted.
* Retry-on-`scan_records`: useless — recovery reads the WAL once at boot, so
  re-scanning the in-memory store cannot change the result.

== Workaround (recommended)

Run this suite via the repository's documented unit-test runner,
`cargo nxlib` / nextest, which gives each test its own process. The recovery
tests (and other process-singleton-sensitive WAL tests) are green there, in
isolation, and in clean `cargo test --lib` runs.

== Suggested fix (for the WAL owner)

Audit `UnifiedWALWriter::flush_current_segment` for read-after-write durability:
ensure `sync_file` actually fsyncs and that a subsequent independent reader is
guaranteed to observe the flushed bytes. Consider having `read_segment` surface
(rather than silently swallow) truncation/deserialize errors during recovery so
a partial read fails loudly instead of recovering zero records.
