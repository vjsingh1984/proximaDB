== Diagram Architecture Philosophy

=== Design Principles
* **Modular by Capability**: Each diagram focuses on one capability or module
* **Hierarchical Abstraction**: High-level overviews → detailed implementations  
* **Content Alignment**: Diagrams match their documentation section purpose
* **Cognitive Load Management**: No monolithic diagrams, clear focus areas

=== Abstraction Levels
[cols="1,2,2", options="header"]
|===
| Level | Purpose | Audience

| **Overview** 
| System-wide understanding, module relationships
| Business stakeholders, new developers

| **Module**
| Capability-focused, module boundaries
| Developers working on specific modules

| **Implementation**  
| Detailed workflows, class relationships
| Developers implementing features
|===

== Maintenance Guidelines

=== Adding New Diagrams
1. **Identify abstraction level**: Overview, Module, or Implementation
2. **Choose appropriate diagram type**: Use case, class, sequence, activity, or state
3. **Follow naming convention**: `[type]-[module/capability]-[purpose].mmd`
4. **Create focused content**: One capability or workflow per diagram
5. **Update appropriate documentation section**: Align with content purpose

=== Updating Existing Diagrams  
1. **Maintain focus**: Keep diagrams capability-focused
2. **Preserve abstraction level**: Don't add implementation details to overview diagrams
3. **Update documentation references**: Ensure links remain valid
4. **Test content alignment**: Verify diagram matches section purpose

=== Best Practices
* **Modular Design**: Each diagram addresses one specific need
* **Hierarchical Clarity**: Clear distinction between overview and detail
* **Content Alignment**: Diagram complexity matches documentation section
* **Cognitive Load**: Prefer multiple focused diagrams over one complex diagram
