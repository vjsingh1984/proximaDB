== Overview

This document provides comprehensive documentation for the ProximaDB gRPC API, including all messages, fields, enums, and their usage patterns. The API follows a proto-first architecture for optimal performance and type safety.

=== Key Design Principles

* **Proto-First Architecture**: Zero double serialization, VectorRecord flows natively as proto types
* **Performance Optimized**: Efficient enums instead of strings for common attributes
* **One-to-Many Relationships**: Model specifications stored once per collection, referenced by vectors
* **Type Safety**: Strong typing through protobuf for compile-time validation
* **Scalability**: Designed for millions of vectors with minimal overhead

== Service Definition

=== ProximaDB Service

The main gRPC service interface for all ProximaDB operations.

[source,protobuf]
----
service ProximaDB {
  rpc CollectionOperation(CollectionRequest) returns (CollectionResponse);
  rpc VectorBatch(VectorBatchRequest) returns (VectorOperationResponse);
  rpc VectorSearch(VectorSearchRequest) returns (VectorOperationResponse);
  rpc VectorGet(VectorGetRequest) returns (VectorOperationResponse);
  rpc Health(HealthRequest) returns (HealthResponse);
  rpc GetMetrics(MetricsRequest) returns (MetricsResponse);
}
----

==== RPC Methods

===== CollectionOperation
* **Purpose**: Unified endpoint for all collection management operations
* **Input**: `CollectionRequest` - Contains operation type and collection configuration
* **Output**: `CollectionResponse` - Operation result with collection metadata
* **Use Cases**: Create, update, delete, list collections; manage schemas and indexes

===== VectorBatch
* **Purpose**: Optimized batch operations for vectors (insert/upsert/delete)
* **Input**: `VectorBatchRequest` - Batch of vector operations
* **Output**: `VectorOperationResponse` - Batch operation results
* **Performance**: Designed for high-throughput bulk operations

===== VectorSearch
* **Purpose**: Vector similarity search with advanced filtering
* **Input**: `VectorSearchRequest` - Search parameters and query vector
* **Output**: `VectorOperationResponse` - Search results with optional source content
* **Features**: Progressive search, metadata filtering, source content retrieval

===== VectorGet
* **Purpose**: Retrieve specific vectors by ID
* **Input**: `VectorGetRequest` - Vector IDs and retrieval options
* **Output**: `VectorOperationResponse` - Retrieved vectors with metadata
* **Use Cases**: Point lookups, batch ID retrieval, metadata inspection

===== Health
* **Purpose**: Service health monitoring
* **Input**: `HealthRequest` - Health check parameters
* **Output**: `HealthResponse` - Service status and diagnostics

===== GetMetrics
* **Purpose**: Performance and usage metrics
* **Input**: `MetricsRequest` - Metrics query parameters
* **Output**: `MetricsResponse` - System metrics and statistics

enum DistanceMetric {
  DISTANCE_METRIC_UNSPECIFIED = 0;
  COSINE = 1;                    // Cosine similarity (most common)
  EUCLIDEAN = 2;                 // L2 distance
  DOT_PRODUCT = 3;               // Inner product
  HAMMING = 4;                   // Hamming distance (binary vectors)

  JACCARD = 6;                   // Jaccard similarity (sets)
  CUSTOM = 7;                    // Custom distance function
  CHEBYSHEV = 8;                 // L∞ distance (maximum norm)
  CANBERRA = 9;                  // Canberra distance
  MINKOWSKI = 10;                // Minkowski distance (generalized)
  ANGULAR = 11;                  // Angular distance
  BRAY_CURTIS = 12;              // Bray-Curtis distance
  HELLINGER = 13;                // Hellinger distance

----

**Usage Patterns**:
* **COSINE**: Default for text embeddings, normalized vectors
* **EUCLIDEAN**: Raw vectors, image features, continuous data
* **DOT_PRODUCT**: When vectors are already normalized
* **HAMMING**: Binary embeddings, hash codes
* **CUSTOM**: Domain-specific distance functions

=== Embedding Model Management

==== EmbeddingModelRegistry
Collection-level registry storing embedding model specifications once for efficient reuse.

[source,protobuf]
----
message EmbeddingModelRegistry {
  map<string, EmbeddingModelSpec> models = 1;  // model_id -> full specification
}
----

**Fields**:
* **models**: Map of model IDs to their complete specifications
  - **Key**: Unique model identifier (e.g., "openai-ada-002", "sentence-transformers-mini")
  - **Value**: Complete model specification with dimensions and characteristics
  - **Performance**: O(1) lookup by model ID from vectors

**Usage Pattern**:
1. Define models once in collection configuration
2. Vectors reference models by lightweight string ID
3. 90%+ storage reduction compared to per-vector model storage

=== Vector Records

==== VectorRecord
Core data structure for vector storage with optimized serialization.

[source,protobuf]
----
message VectorRecord {
  string id = 1;                             // MANDATORY: Unique identifier
  repeated float vector = 2;                 // REQUIRED for inserts
  repeated MetadataItem metadata = 3;        // Key-value metadata
  uint32 timestamp = 4;                      // Creation timestamp (seconds since epoch)
  optional uint32 updated_at = 5;            // Update timestamp (if different)
  optional uint32 expires_at = 6;            // TTL support (seconds since epoch)
  optional uint32 version = 7;               // Optimistic concurrency control
  
  // Storage-optimized fields
  optional bytes quantized_vector = 8;       // Pre-quantized vector data
  
  // Source content storage
  optional SourceContent source = 10;        // Original content that generated vector
}
----

**Field Details**:

===== id (field 1)
* **Type**: `string` (mandatory)
* **Purpose**: Unique vector identifier for correlation and retrieval
* **Requirements**: Must be unique within collection
* **Best Practices**: Use UUID v4, content hash, or domain-specific ID
* **Performance**: Indexed for O(log n) retrieval

===== vector (field 2)
* **Type**: `repeated float` (required for inserts)
* **Purpose**: Vector embedding data
* **Constraints**: Dimension must match collection configuration
* **Format**: IEEE 754 single-precision floating point
* **Optimization**: May be omitted in search results if not requested

===== metadata (field 3)
* **Type**: `repeated MetadataItem`
* **Purpose**: Key-value metadata for filtering and annotation
* **Structure**: Type-safe values (string, number, boolean)
* **Indexing**: Filterable columns can be indexed for fast queries
* **Performance**: Efficient protobuf encoding vs JSON parsing

===== timestamp (field 4)
* **Type**: `uint32` (required)
* **Purpose**: Record creation time
* **Format**: Seconds since Unix epoch (2038-safe for 64-bit systems)
* **Usage**: Sorting, analytics, retention policies
* **Compactness**: 4 bytes vs 8-byte int64

===== updated_at (field 5)
* **Type**: `optional uint32`
* **Purpose**: Last modification time
* **Optimization**: Only set if different from timestamp (saves space)
* **Use Cases**: Change tracking, invalidation, conflict resolution

===== expires_at (field 6)
* **Type**: `optional uint32`
* **Purpose**: Time-to-live (TTL) support
* **Format**: Seconds since Unix epoch
* **Behavior**: Records automatically removed after expiration
* **Use Cases**: Temporary data, cache invalidation, GDPR compliance

===== version (field 7)
* **Type**: `optional uint32`
* **Purpose**: Optimistic concurrency control
* **Pattern**: Increment on each update
* **Conflict Resolution**: Update fails if version doesn't match
* **Use Cases**: Concurrent updates, data consistency

===== quantized_vector (field 8)
* **Type**: `optional bytes`
* **Purpose**: Pre-computed quantized vector data
* **Performance**: Avoids re-quantization during search
* **Storage**: Typically 1/4 to 1/8 the size of full precision
* **Progressive Search**: Used for fast initial filtering

===== source (field 10)
* **Type**: `optional SourceContent`
* **Purpose**: Original content that generated the vector
* **Use Cases**: RAG applications, content retrieval, audit trails
* **Storage**: Supports inline, block, file, and external storage tiers

== Migration and Compatibility

=== Upgrading from String-Based Storage

1. **Model Registry Migration**:
   - Create `EmbeddingModelRegistry` in collection config
   - Map existing model strings to enum values
   - Update vectors to reference model IDs

2. **Enum Migration**:
   - Convert string fields to enum equivalents
   - Use `CUSTOM_*` enum values for unmapped strings
   - Preserve custom string values in dedicated fields

3. **Backward Compatibility**:
   - Proto optional fields ensure old messages remain valid
   - Gradual migration with dual field support
   - Default enum values handle missing fields

=== Best Practices

1. **Model Management**:
   - Define models in collection registry before inserting vectors
   - Use consistent model IDs across collections
   - Version model specifications for tracking changes

2. **Enum Usage**:
   - Prefer enum values over custom strings when possible
   - Use descriptive custom values for unmapped cases
   - Plan enum extensions for future requirements

3. **Source Content**:
   - Enable tiering for automatic storage optimization
   - Use appropriate compression for content types
   - Consider external storage for large multimedia files

4. **Performance Optimization**:
   - Enable progressive search for large collections
   - Use metadata filters to reduce search scope
   - Configure appropriate index types for query patterns

== Error Handling

=== Common Error Patterns

1. **Dimension Mismatch**:
   - Vector dimension doesn't match collection configuration
   - Model registry dimension conflicts with collection

2. **Missing Model References**:
   - Vector references model ID not in registry
   - Model registry not configured for collection

3. **Invalid Enum Values**:
   - Unknown enum values in requests
   - Custom enum values without corresponding custom fields

4. **Storage Tier Violations**:
   - Content size exceeds tier thresholds
   - External storage configuration missing

=== Error Response Format

All error responses include:
- **success**: `false`
- **message**: Human-readable error description
- **error_code**: Machine-readable error identifier
- **details**: Additional context for debugging
