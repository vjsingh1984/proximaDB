=== Storage-Aware Search Engine

ProximaDB implements a storage-aware polymorphic search system that automatically optimizes search operations based on the collection's storage engine type. This provides significant performance improvements through storage-specific optimizations.

==== Architecture Overview

The storage-aware search system routes search requests to optimized search engines:

- **VIPER Search Engine**: Optimized for Parquet columnar storage
- **SST Search Engine**: Optimized for log-structured storage

Each engine leverages storage-format-specific optimizations for maximum performance.

==== VIPER Search Optimizations

**For collections using VIPER storage engine:**

[source,rust]
----
// VIPER search provides:
// - Static column projection (50-80% I/O reduction)
// - Predicate pushdown to Parquet column filters
// - ML-driven cluster selection (70-90% search space reduction)
// - Pre-computed quantization (zero runtime overhead)
// - Hardware acceleration (SIMD, NEON, CUDA, ROCm, MPS)
// - Two-stage search with quantized filtering

// Expected performance: Optimized search with 100% accuracy
let request = SearchVectorsRequest {
    collection_id: viper_collection_id,
    query_vector: query_embedding,
    k: 10,
    search_hints: Some(SearchHints {
        predicate_pushdown: true,       // Enable Parquet filtering
        quantization_level: PQ4,        // 4x speed, ~90% accuracy
        clustering_hints: Some(ClusteringHints {
            enable_ml_clustering: true,
            max_clusters_to_search: 5,
            cluster_confidence_threshold: 0.8,
        }),
    }),
};
----

**Unified Quantization Levels (Phase 4):**
- `None`: Full FP32 precision (100% accuracy, baseline speed)
- `Uniform(bits)`: Custom bit precision 1-32 (2-32x compression)
- `ProductQuantization`: 
  - `PQ8`: 8-bit codes (4x compression, 95% accuracy)
  - `PQ4`: 4-bit codes (8x compression, 90% accuracy)
- `Scalar`: INT8/INT16 with scale/offset (4x speed, 98% accuracy)
- `Binary`: 1-bit quantization (32x compression, 85% accuracy)
- `Custom`: Flexible bit-level with optional codebooks

**Two-Stage Search Strategy:**
[source,rust]
----
// Stage 1: Fast candidate selection with quantized vectors
// Stage 2: Accurate refinement with FP32 vectors
let request = SearchVectorsRequest {
    collection_id: collection_id,
    query_vector: query_embedding,
    k: 10,
    search_hints: Some(SearchHints {
        use_two_stage_search: true,
        candidate_multiplier: 3.0,  // Select 3x candidates in Stage 1
        quantization_level: UnifiedQuantizationLevel::pq8(16),
    }),
};
----

==== SST Search Optimizations

**For collections using SST storage engine:**

[source,rust]
----
// SST search provides:
// - Tiered search strategy (MemTable → Level 0 → Higher Levels)
// - Bloom filter optimization (90-95% false positive reduction)
// - Level-aware search prioritization
// - Tombstone handling for correct deletion semantics

// Expected performance: 2-3x faster than generic search
let request = SearchVectorsRequest {
    collection_id: sst_collection_id,
    query_vector: query_embedding,
    k: 10,
    search_hints: Some(SearchHints {
        use_bloom_filters: true,        // Skip irrelevant SSTables
        max_levels_to_search: 5,        // Search up to 5 SST levels
        search_strategy: "tiered_memtable_first",
    }),
};
----

**SST Search Strategy:**
1. **MemTable Search**: Search active memtable (most recent data)
2. **Level 0 Search**: Search recent flush files
3. **Higher Level Search**: Search older, compacted data
4. **Result Merging**: Handle duplicates and tombstones

==== Basic Usage

[source,python]
----
import asyncio
from proximadb import ProximaDBClient, CollectionConfig, DistanceMetric

async def main():
    # Create client (auto-detects best protocol)
    client = ProximaDBClient("localhost:5678")
    
    # Create collection for BERT embeddings
    collection_config = CollectionConfig(
        name="bert_embeddings",
        dimension=768,
        distance_metric=DistanceMetric.COSINE,
        description="BERT base model embeddings"
    )
    
    collection_id = await client.create_collection(collection_config)
    print(f"Created collection: {collection_id}")
    
    # Insert vectors with metadata
    vectors = [
        {
            "vector_id": "doc_1",
            "vector": bert_embedding_1,  # 768-dimensional list
            "metadata": {"category": "news", "topic": "technology"}
        },
        {
            "vector_id": "doc_2", 
            "vector": bert_embedding_2,
            "metadata": {"category": "research", "topic": "ai"}
        }
    ]
    
    await client.batch_insert(collection_id, vectors)
    
    # Perform similarity search
    results = await client.search_vectors(
        collection_id=collection_id,
        query_vector=query_embedding,
        k=5,
        metadata_filter={"category": "research"},
        return_metadata=True
    )
    
    for result in results:
        print(f"ID: {result.vector_id}, Score: {result.similarity_score:.4f}")
        print(f"Metadata: {result.metadata}")

# Run the async function
asyncio.run(main())
----

|**COSINE** |Text embeddings |Angle-based, magnitude-independent (0=identical)
|**EUCLIDEAN** |Spatial data |L2 norm, straight-line distance
|**DOT_PRODUCT** |Recommendation |Inner product (higher=more similar)
|**MANHATTAN** |Grid-based |L1 norm, sum of absolute differences
|**HAMMING** |Binary data |Bit-level differences
|**JACCARD** |Set similarity |Intersection over union
|**CHEBYSHEV** |Max difference |L∞ norm, maximum absolute difference
|**CANBERRA** |Sparse data |Weighted Manhattan, sensitive to small changes
|**MINKOWSKI** |Generalized |Lp norm with configurable p (default=3)
|**ANGULAR** |Directional |Arc-cosine based angular distance
|**BRAY_CURTIS** |Ecological |Compositional data dissimilarity
|**HELLINGER** |Distributions |Statistical distance for probabilities
|===

All metrics support hardware acceleration (AVX-512, NEON) and GPU offloading.

==== BERT Integration Example

[source,python]
----
from transformers import AutoTokenizer, AutoModel
import torch
import numpy as np

class BERTEmbeddingGenerator:
    def __init__(self, model_name="bert-base-uncased"):
        self.tokenizer = AutoTokenizer.from_pretrained(model_name)
        self.model = AutoModel.from_pretrained(model_name)
        self.model.eval()
    
    def generate_embedding(self, text: str) -> list[float]:
        # Tokenize and encode
        inputs = self.tokenizer(text, return_tensors="pt", 
                              truncation=True, max_length=512)
        
        # Generate embeddings
        with torch.no_grad():
            outputs = self.model(**inputs)
            # Use [CLS] token embedding
            embedding = outputs.last_hidden_state[:, 0, :].squeeze()
            
        return embedding.numpy().tolist()

# Usage with ProximaDB
bert = BERTEmbeddingGenerator()

texts = [
    "The quick brown fox jumps over the lazy dog",
    "Machine learning is revolutionizing artificial intelligence",
    "ProximaDB provides fast vector similarity search"
]

# Create collection for BERT embeddings
collection_id = await client.create_collection(CollectionConfig(
    name="bert_documents",
    dimension=768,
    distance_metric=DistanceMetric.COSINE
))

# Insert BERT embeddings
for i, text in enumerate(texts):
    embedding = bert.generate_embedding(text)
    await client.insert_vector(
        collection_id=collection_id,
        vector_id=f"doc_{i}",
        vector=embedding,
        metadata={"text": text, "length": len(text)}
    )

# Search with BERT query
query_text = "fast vector search database"
query_embedding = bert.generate_embedding(query_text)

results = await client.search_vectors(
    collection_id=collection_id,
    query_vector=query_embedding,
    k=3,
    return_metadata=True
)

for result in results:
    print(f"Score: {result.similarity_score:.4f}")
    print(f"Text: {result.metadata['text']}")

=== SQL Query Engine Usage

ProximaDB includes a powerful SQL query engine that supports vector similarity search alongside traditional SQL operations. The SQL engine is currently implemented in the core but will be exposed through REST and gRPC APIs in the next release.

==== SQL Engine Architecture

[source,text]
----
SQL Query → Parser → Query Planner → Execution Engine → Results
             ↓           ↓               ↓
         ParsedQuery  ExecutionPlan  DirectVectorService
----

==== Supported SQL Features

===== VECTOR_SIMILARITY Function
The `VECTOR_SIMILARITY` function is the core of ProximaDB's SQL support:

[source,sql]
----
VECTOR_SIMILARITY(vector_column, query_vector, distance_metric)
----

**Parameters:**
- `vector_column`: The vector field to search (usually 'vector')
- `query_vector`: Array of floats in format `[0.1, 0.2, ...]` (note: square brackets, not ARRAY)
- `distance_metric`: One of 'cosine', 'euclidean', 'dot_product', 'manhattan', 'hamming', 'jaccard'

===== Currently Supported SQL Features

**Actually Working:**
- Basic `SELECT` with field selection
- `WHERE` clause with simple equality (`=`)
- `IN` operator for simple value lists
- `metadata->>'field'` for JSON field extraction
- `ORDER BY VECTOR_SIMILARITY()`
- `LIMIT` and `OFFSET`

**Metadata Access:**
- `metadata->>'field'` - Extract JSON field as text (only operator currently working)

===== Current Limitations

**Planned but Not Yet Implemented:**
- `AND`, `OR`, `NOT` operators (returns "Complex conditions not supported yet")
- Comparison operators other than `=` (no `!=`, `<`, `>`, `<=`, `>=`)
- `LIKE` operator (returns "Operator Like not supported")
- `IS NULL`, `IS NOT NULL`
- Parentheses for grouping conditions
- `metadata->'field'` (without double arrow)

**Not Supported:**
- `CAST` operations
- `BETWEEN` operator
- Subqueries or CTEs
- `UNION`, `INTERSECT`, `EXCEPT`
- Multiple `VECTOR_SIMILARITY` calls in one query
- `JOIN` operations
- Window functions
- Aggregations (`COUNT`, `AVG`, etc.)

**Performance Tips:**
- Apply metadata filters before vector search for better performance
- Use indexed fields in `filterable_metadata_fields` for faster queries
- Query plan caching provides 2-8x speedup for repeated query structures
- Batch size affects insert performance dramatically (up to 30x difference)

==== Handling Rate Limits in Python SDK

[source,python]
----
from proximadb import connect_rest
from proximadb.exceptions import ProximaDBError
import time

client = connect_rest("http://localhost:5678")

def with_retry(func, max_retries=3):
    """Decorator to handle rate limiting with exponential backoff"""
    def wrapper(*args, **kwargs):
        for attempt in range(max_retries):
            try:
                return func(*args, **kwargs)
            except ProximaDBError as e:
                if "QUOTA_EXCEEDED" in str(e) or "429" in str(e):
                    if attempt < max_retries - 1:
                        wait_time = 2 ** attempt  # Exponential backoff
                        print(f"Rate limited, waiting {wait_time}s...")
                        time.sleep(wait_time)
                        continue
                raise
        return None
    return wrapper

# Usage example
@with_retry
def insert_batch(collection_id, vectors):
    return client.insert_vectors(collection_id, vectors)

def bulk_import(collection_id, all_vectors, chunk_size=500):
    """Import vectors with rate limit awareness"""
    total = len(all_vectors)
    imported = 0
    
    for i in range(0, total, chunk_size):

                print("Rate limit hit, waiting 60s...")
                time.sleep(60)
                # Retry the chunk
                client.insert_vectors(collection_id, chunk)

===== High-Frequency Search
[source,python]

# Implement client-side rate limiting
from threading import Semaphore
import asyncio

class RateLimitedClient:
    def __init__(self, client, max_qps=100):
        self.client = client
        self.semaphore = Semaphore(max_qps)
        self.reset_task = None
        
    async def search(self, collection_id, vector, **kwargs):
        """Rate-limited search"""
        if not self.semaphore.acquire(blocking=False):
            # Wait for next window
            await asyncio.sleep(0.1)
            return await self.search(collection_id, vector, **kwargs)
            
        try:
            return await self.client.search(collection_id, vector, **kwargs)
        finally:
            # Release after 1 second
            asyncio.create_task(self._release_after(1.0))
            
    async def _release_after(self, delay):
        await asyncio.sleep(delay)
        self.semaphore.release()

=== Best Practices

1. **Choose the Right Storage Engine:**
   - VIPER: Best for analytical queries, aggregations, columnar access
   - SST: Best for high write throughput, point lookups, row-based access

2. **Protocol Selection:**
   - REST: Easy to use, good for prototyping, JSON-based
   - gRPC: Higher performance, binary protocol, better for production

3. **Concurrency Configuration:**
   - Use lock-free for high-concurrency workloads (>10 concurrent clients)
   - Traditional locking sufficient for low-concurrency scenarios

4. **Batch Operations:**
   - Always batch inserts when possible (100-1000 vectors per batch)
   - Use connection pooling for concurrent operations

5. **SQL Optimization:**
   - Use appropriate indexes (bloom filters for SST)
   - Leverage metadata filtering to reduce search space
   - Consider query complexity when choosing storage engine

6. **Rate Limit Management:**
   - Implement exponential backoff for retries
   - Use client-side rate limiting for predictable load
   - Monitor rate limit headers in responses
   - Consider upgrading limits for production workloads

== WriteBuffer Cloud Integration

=== Overview

ProximaDB's WriteBuffer (Write-Ahead Log) system features comprehensive cloud integration through the enhanced `WalBatchStrategy` interface, enabling seamless operations across multiple cloud storage providers with URL-based routing and atomic operations.

=== Enhanced Multi-Cloud URL Routing

**Supported URL Formats:**

- `file://` - Local filesystem operations with absolute path validation
- `s3://` - Amazon S3 object storage with bucket validation  
- `gcs://` - Google Cloud Storage with bucket validation
- `adls://` - Azure Data Lake Storage with account/container validation
- `abfs://` - Azure Blob File System with container@account format validation
- `hdfs://` - Hadoop Distributed File System with namenode validation

**URL Validation Examples:**
[source,rust]
----
// Valid URLs
file:///tmp/test.txt                    // Local filesystem
s3://bucket-name/path/to/file           // Amazon S3
gcs://bucket-name/path/to/object        // Google Cloud Storage
adls://account/container/path/to/file   // Azure Data Lake Storage
abfs://container@account/path/to/file   // Azure Blob FileSystem
hdfs://namenode:9000/path/to/file       // Hadoop HDFS

// Invalid URLs (missing required components)
file://relative/path                    // Must be absolute
s3:///missing-bucket/file.bin           // Bucket required
abfs://invalid-format/file.bin          // @ format required
----

=== Enhanced WalBatchStrategy Interface

**Core Cloud Methods:**
[source,rust]

=== Cloud Backup Configuration

**TOML Configuration Example:**
[source,toml]
----
[storage.write_buffer_config.performance.cloud_backup]
enabled = true
backup_url = "s3://my-bucket/proximadb-write-buffer/"
strategy = "OnFlush"
verify_integrity = true

[storage.write_buffer_config.performance.cloud_backup.frequency]
operations_threshold = 1000
time_threshold_secs = 300
size_threshold_bytes = 104857600  # 100MB

[storage.write_buffer_config.performance.cloud_backup.cleanup_policy]
retention_days = 7
max_backups = 100
cleanup_frequency_hours = 24

[storage.write_buffer_config.performance.cloud_backup.retry_config]
max_retries = 3
initial_delay_ms = 100
max_delay_ms = 5000
backoff_multiplier = 2.0
----

**Backup Strategies:**

- **`RealTime`** - Immediate cloud backup on every write operation
- **`Periodic`** - Scheduled batch backup at fixed intervals
- **`OnFlush`** - Backup triggered during flush operations (recommended)
- **`OnDemand`** - Manual backup control via API

=== Usage Examples

**Basic Cloud Backup:**
[source,rust]
----
// Configure cloud backup
let mut config = WalConfig::default();
config.performance.cloud_backup = Some(CloudBackupConfig {
    enabled: true,
    backup_url: "s3://my-bucket/write-buffer/".to_string(),
    strategy: CloudBackupStrategy::OnFlush,
    ..Default::default()
});

// Insert vectors with automatic cloud backup
let sequences = strategy.insert_vectors_with_cloud_backup(
    collection_id,
    vectors,
    Some("s3://my-bucket/write-buffer/"),
).await?;
----

**Manual Migration:**
[source,rust]
----
// Migrate specific batch to cloud
let cloud_url = strategy.migrate_batch_to_cloud(
    &collection_id,
    &batch,
    "/local/path/write_buffer_batch.bin",
    "gcs://my-bucket/write-buffer/",
).await?;

println!("Migrated batch to: {}", cloud_url);
----

**Cloud Health Check:**

// Verify cloud accessibility
let is_healthy = strategy.check_cloud_health(

=== Performance Considerations

**Optimized for Large-Scale Operations:**

- **Batch Serialization**: Uses `bincode` for optimal Rust performance
- **Atomic Operations**: Prevents partial writes during failures
- **Concurrent Operations**: Multiple cloud writes can execute in parallel
- **Verification**: Optional read-back verification for mission-critical data

**Network Optimization:**

- **Compression**: Automatic compression for network transfers
- **Connection Pooling**: Reuses connections across operations
- **Retry Logic**: Exponential backoff for transient failures
- **Parallel Uploads**: Multiple batches can upload simultaneously

=== Security Best Practices

**Authentication:**
- Use IAM roles and managed identities when possible
- Rotate credentials regularly
- Implement least-privilege access policies
- Enable audit logging for all cloud operations

**Data Protection:**
- Enable encryption at rest in cloud storage
- Use TLS for all network communications
- Implement client-side encryption for sensitive data
- Regular security audits and penetration testing

**Access Control:**
- Implement collection-level access controls
- Use signed URLs for time-limited access
- Enable versioning for audit trails
- Regular access reviews and cleanup
