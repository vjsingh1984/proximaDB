=== Core Design Principles

**Proto-Native Operations**:: Protocol Buffers used throughout the system for consistency
**Reduced Serialization**:: Direct proto serialization reduces overhead
**Handler Consolidation**:: Unified business logic reduces code duplication
**Storage Engine Selection**:: Choose appropriate engine based on workload

=== Key Architectural Innovations

image::two-stage-search.png[Two-Stage Search Process, width=800, align=center]

_Diagram source: link:diagrams/two-stage-search.mmd[View Mermaid source]_

==== 1. DirectVectorService Architecture
- **Reduced latency** by eliminating unnecessary abstraction layers
- **Direct memtable access** for write operations
- **Coordinated search** across WAL and storage layers
- **Efficient result delivery** for search operations

==== 2. Unified Memtable Architecture

- **Multiple backend options**: BTree, SkipList, HashMap, DashMap
- **Specialized behaviors** for different storage engines
- **Trait-based design** for code reuse
- **Configurable backend** selection

==== 3. Intelligent Storage Optimization
- **CompactionCoordinator** for automatic background compaction after flushes
- **Workload-aware serialization** with Proto/Bincode/Avro format selection
- **StreamingSearchService** for lock-free non-blocking search
- **Unified batch strategies** eliminating 90% duplicate code

== System Architecture

=== Handler Consolidation Layer

image::proximadb-architecture-overview.png[ProximaDB Architecture Overview, width=800, align=center]

_Diagram source: link:diagrams/proximadb-architecture-overview.mmd[View Mermaid source]_

**UnifiedHandlers Design**::
- **Consolidated business logic** reducing code duplication
- **Protocol adapters** for REST (JSON ↔ Proto) and gRPC (direct proto)
- **Single implementation** for all operations
- **Efficient serialization** throughout the pipeline

**Transport Independence**::
- REST API (port 5678): JSON interface with automatic proto conversion
- gRPC API (port 5679): Native protobuf with 64MB message support
- **Protocol-agnostic** business logic in UnifiedHandlers
- **Automatic failover** and health check integration

=== Storage-Aware Engine Layer

image::multi_disk_architecture.png[Multi-Disk Storage Architecture, width=800, align=center]

_Diagram source: link:diagrams/multi_disk_architecture.mmd[View Mermaid source]_

**Dual Storage Strategy**::
- **VIPER Engine**: Parquet columnar storage with ML clustering
- **LSM Engine**: Row-based SSTable with bloom filter optimization
- **Automatic engine selection** based on collection configuration
- **Storage-aware polymorphic search** with 6.10x performance improvement

**Proto-First WAL System**::
- **ProtoWalBatchStrategy**: Native proto serialization (default)
- **One API call = One batch** design for optimal throughput
- **Legacy compatibility** via AvroWalBatchStrategy and BincodeWalBatchStrategy
- **Automatic format detection** with graceful migration support

=== Unified Quantization System

image::unified_quantization_system.png[Unified Quantization System, width=800, align=center]

_Diagram source: link:diagrams/unified_quantization_system.mmd[View Mermaid source]_

**Quantization Engine Features**::
- **Hardware acceleration**: SIMD, AVX, NEON, CUDA, ROCm support
- **Multiple quantization levels**: FP32, PQ8, PQ4, Binary, INT8
- **Dynamic quantization selection** based on query characteristics and hardware
- **Codebook training** with K-means clustering for optimal compression

**Two-Stage Search Optimization**::
- **Stage 1**: Binary quantization for ultra-fast candidate selection
- **Stage 2**: FP32 refinement for accuracy guarantee
- **Configurable candidate multiplier** (default: 3x for optimal speed/accuracy)
- **Maintains 100% recall** while achieving 3-6x speedup

=== Unified Bloom Filter Architecture

image::bloom-filter-architecture.png[Unified Bloom Filter Architecture, width=800, align=center]

_Diagram source: link:diagrams/bloom-filter-architecture.mmd[View Mermaid source]_

**Polymorphic Design Benefits**::
- **Single configuration type**: One `BloomFilterConfig` used everywhere
- **Strategy pattern**: Different implementations for different use cases
- **Zero duplication**: Eliminated all duplicate bloom filter implementations
- **Type safety**: Compile-time guarantees through trait-based design

**Strategy Implementations**::
- **ByteAligned**: Optimized for SSTable disk persistence
- **BitPacked**: Memory-efficient for in-memory structures  
- **Simple**: Fast operations for small datasets
- **Composite**: Metadata-aware filtering for complex queries
- **NoOp**: Edge case handling for disabled/empty filters

**Integration Points**::
- **LSM Engine**: ByteAligned filters in SSTables for key lookups
- **VIPER Engine**: Composite filters for metadata queries
- **Memtable**: BitPacked filters for memory efficiency
- **Factory Pattern**: Unified creation and serialization

NOTE: See link:architecture/bloom-filter-unified-design.adoc[Bloom Filter Architecture Guide] for detailed design documentation and link:architecture/bloom-filter-quick-reference.adoc[Quick Reference] for usage patterns.

=== Storage-Aware Search Infrastructure

image::storage-aware-search.png[Storage-Aware Search Infrastructure, width=800, align=center]

_Diagram source: link:diagrams/storage-aware-search.mmd[View Mermaid source]_

**Storage-Aware Search Coordination**::
- **Layer 1**: Unflushed WAL search with latest data
- **Layer 2**: Flushed storage engine search (VIPER or LSM)
- **Layer 3**: Compacted storage with historical data
- **Multi-tier deduplication**: MVCC version ordering with sequence numbers

**Engine-Specific Optimizations**::
- **VIPER**: Parquet predicate pushdown, ML clustering, column projection
- **LSM**: Bloom filter optimization, memtable priority, level-aware search
- **Automatic selection**: Based on data location and query patterns
- **6.10x performance improvement** with 100% accuracy maintained

=== Multi-Tier Storage Strategy

**Hot Tier (NVMe)**::
- WAL files for immediate write acknowledgment
- Active LSM memtables and recent SSTable files
- Sub-100ms access latency for real-time operations

**Warm Tier (SSD)**::
- VIPER Parquet files with ML clustering
- Frequently accessed vector collections
- Active search indexes and bloom filters

**Cold Tier (HDD)**::
- Compacted historical data and archived vectors
- Long-term storage with compression
- Automated lifecycle management
