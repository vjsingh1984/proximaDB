== Recent Feature Enhancements (2025-08-01)

=== Index-Based Filtering Framework

ProximaDB implements a sophisticated **index-based filtering framework** that separates filter evaluation from data reading, enabling optimal engine-specific optimizations.

==== Core Design Principles

1. **Index-First Approach**: Filter evaluation returns qualifying ROW INDICES, not data
2. **Engine-Specific Optimization**: Each engine uses indices optimally for its storage model
3. **Early Termination**: Empty indices = skip entire blocks/row groups
4. **Parallel Column Processing**: AND/OR operations can run on multiple threads

==== Engine Strategies

[source,rust]
----
// SST Strategy: Read entire blocks, filter using indices
let all_data = read_entire_block().await;
let results = filter_by_indices(&all_data, &indices);

// VIPER Strategy: Use indices to selectively read parquet rows/columns  
let results = read_rows_by_indices(&indices).await;
----

==== Performance Benefits

- **VIPER**: 60-90% I/O reduction via predicate pushdown
- **SST**: 30% processing savings via index-based filtering  
- **Parallel**: 2-4x faster complex filter evaluation
- **Set Ops**: Union/intersection on indices (microseconds vs milliseconds)

**Implementation Files**:
- `/src/core/search/index_based_filter.rs` - Core framework
- `/src/storage/engines/sst/index_based_reader.rs` - SST implementation
- `/src/storage/engines/viper/index_based_reader.rs` - VIPER implementation

=== MVCC Implementation

ProximaDB includes a complete Multi-Version Concurrency Control (MVCC) system across all storage engines:

==== Core MVCC Rules

1. **Version Continuity**: Versions must be sequential (1,2,3...) without gaps
2. **Gap Handling**: Stop processing at first version gap
3. **Duplicate Resolution**: For same ID and version, keep record with earliest timestamp
4. **Tombstone Handling**: Records marked as deleted are removed during compaction
5. **Append-Only Support**: Vectors without IDs bypass all version checks

==== Implementation Highlights

- **Intelligent Compaction**: Metadata-based file size estimation without loading full datasets
- **Version Continuity Validation**: Across VIPER and SST engines
- **Search Result Deduplication**: Consistent MVCC rules applied
- **Comprehensive Testing**: 21 MVCC-specific tests ensure correctness

=== Advanced Metadata Filtering

==== SST Engine: Three-Stage Filtering Pipeline

1. **Bloom Filter Pre-filtering** - Skip entire files (99% accuracy)
2. **Index Entry Block Filtering** - Use min/max statistics to skip data blocks  
3. **Fast In-Memory Row Filtering** - Vectorized metadata filtering on `SstRecord`

==== VIPER Engine: Predicate Pushdown Strategy

1. **Extract filter columns** - Identify required metadata columns
2. **Load metadata columns only** - Skip vector column (largest data)
3. **Column-level parallel evaluation** - Each thread processes one column
4. **Return qualifying indices** - Enable selective vector reads (60-90% I/O savings)

== Initialization and Startup Architecture

=== Clean Initialization Order (Fixed 2025-07-31)

ProximaDB implements a clean initialization sequence that eliminates circular dependencies:

[mermaid]
....
sequenceDiagram
    participant Main as ProximaDB::new
    participant SS as SharedServices
    participant CS as CollectionService
    participant SE as StorageEngine
    participant MS as MultiServer
    
    Main->>SS: 1. Create SharedServices first
    SS->>CS: Create CollectionService
    SS-->>Main: Return (SharedServices, CollectionService)
    
    Main->>SE: 2. Create StorageEngine
    Main->>SE: Inject CollectionService from SharedServices
    
    Main->>SE: 3. Start StorageEngine
    SE->>SE: Recover collections from metadata
    
    Main->>SS: 4. Recover vectors from write buffer
    SS->>SE: Get recovered collections
    SS->>SS: Load vectors into memtable
    
    Main->>MS: 5. Create MultiServer with SharedServices
    Main->>MS: 6. Start servers (HTTP:5678, gRPC:5679)
....

==== Key Improvements

1. **SharedServices Created First**: Owns all business logic and services
2. **No Circular Dependencies**: SharedServices doesn't depend on StorageEngine
3. **Clean Dependency Injection**: CollectionService passed from SharedServices to StorageEngine
4. **Proper Recovery Order**: Collections → Assignments → Vectors

== Recovery Architecture

=== 3-Phase Recovery System

ProximaDB implements a robust 3-phase recovery process that ensures fast startup and data consistency:

[mermaid]
....
graph TD
    A[Server Startup] --> B[Phase 1: Metadata Recovery]
    B --> C[Load Collection Metadata]
    C --> D[Initialize Storage Assignments] 
    D --> E[Phase 2: Assignment Recovery]
    E --> F[Discover Collections from Storage]
    F --> G[Restore Assignment Mappings]
    G --> H[Phase 3: Write Buffer Recovery]
    H --> I[Scan Write Buffer Files]
    I --> J[Replay Unflushed Operations]
    J --> K[Server Ready]
    
    style A fill:#e1f5fe
    style K fill:#e8f5e8
    style B fill:#fff3e0
    style E fill:#fff3e0
    style H fill:#fff3e0
....

==== Phase 1: Metadata Recovery (11.8ms avg)

**Objective**: Restore collection configurations and engine assignments

**Performance**: 11.8ms for 1 collection, linear scaling up to ~50ms for 50 collections

==== Phase 2: Assignment Recovery (Concurrent)

**Objective**: Discover collections from filesystem and restore assignment mappings

**Key Features**:
* Parallel discovery across 3 component types (WriteBuffer, Storage, Index)
* Hash-based assignment consistency ensures same collection always maps to same location
* Graceful handling of missing or orphaned data

==== Phase 3: Write Buffer Recovery (Direct-to-Storage)

**Objective**: Replay unflushed operations directly to storage engines

**Design Principles**:
* **Direct-to-Storage**: Bypasses memtable to avoid memory pressure during recovery
* **Parallel Processing**: Collections recovered concurrently using CPU-based worker pools
* **Automatic Cleanup**: Successfully recovered WriteBuffer files are removed
* **Progress Tracking**: Real-time metrics on recovery progress
