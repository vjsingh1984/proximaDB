= ProximaDB Architecture
:toc: left
:toclevels: 2
:imagesdir: diagrams/images

**High-performance vector database with proto-first design and dual storage engines.**

== Overview

image::business-system-overview.svg[ProximaDB Overview, align=center]

ProximaDB uses a streamlined architecture optimized for vector operations:

* **DirectVectorService**: Eliminates abstraction layers for 40-60% latency reduction
* **Proto-First Design**: Native protobuf serialization throughout
* **Dual Storage Engines**: SST (write-optimized) + VIPER (analytics-optimized)
* **Hardware Acceleration**: Automatic SIMD/GPU optimization

== Core Components

=== DirectVectorService

The heart of ProximaDB - handles all vector operations with minimal overhead:

[source,rust]
----
DirectVectorService
├── Direct memtable access (writes)
├── Coordinated search (WriteBuffer + Storage)
├── Atomic operations via UnifiedAtomicCoordinator
└── Result streaming for large queries
----

=== Storage Engines

==== SST Engine (Row-Based)
* Optimized for write-heavy workloads
* Fast point lookups and updates
* Efficient compaction with bloom filters
* MVCC support for consistency

==== VIPER Engine (Columnar)
* Optimized for analytics and complex queries
* Efficient compression with Parquet format
* Predicate pushdown for filtered searches
* 60-90% I/O reduction on metadata queries

=== AXIS Indexing System

Adaptive index selection based on data characteristics:

* **HNSW**: For high-recall requirements
* **IVF**: For large-scale datasets
* **LSH**: For approximate matching
* **Annoy**: For memory-constrained environments

== Key Design Patterns

=== Proto-First Architecture

[source]
----
REST Request → JSON → Proto → DirectVectorService → Proto → Storage
gRPC Request → Proto → DirectVectorService → Proto → Storage
----

Benefits:
* Zero double serialization
* Consistent data model
* Efficient network transport
* Language-agnostic API

=== Unified Interfaces

All components use trait-based design for flexibility:

* `UnifiedMemtable`: Multiple backend implementations
* `UnifiedSearchEngine`: Consistent search across engines  
* `UnifiedAtomicCoordinator`: ACID operations
* `BloomFilterStrategy`: Pluggable filter implementations

=== Memory Optimization

Advanced memory management for efficiency:

* **Vector Memory Pool**: 30-50% allocation reduction
* **RAII Pooled Vectors**: Automatic lifecycle management
* **Zero-Copy Operations**: Using bytemuck for serialization
* **Adaptive Compression**: ZSTD with smart thresholds

== Data Flow

=== Write Path

[source]
----
Client Request
    ↓
DirectVectorService
    ↓
UnifiedMemtable (in-memory)
    ↓
WriteBuffer (persistent)
    ↓
Storage Engine (SST/VIPER)
----

=== Search Path

[source]
----
Search Request
    ↓
DirectVectorService
    ↓
Parallel Search:
├── WriteBuffer (recent data)
├── Memtable (active data)
└── Storage Engine (historical)
    ↓
Result Merging & Deduplication
    ↓
Client Response
----

== Performance Characteristics

=== Latency Profile
* **Insert**: <1ms (memtable), <5ms (durable)
* **Search**: <2ms (P50), <10ms (P99)
* **Update**: <2ms (in-place optimization)

=== Throughput
* **Writes**: 49K vectors/sec (gRPC batch)
* **Reads**: 48 QPS concurrent search
* **Mixed**: 80/20 read/write optimal

=== Resource Usage
* **Memory**: 100MB base + data
* **CPU**: Scales with cores (SIMD)
* **Storage**: 30-50% compression ratio

== Security & Reliability

=== Data Protection
* ACID transactions with MVCC
* Atomic operations for consistency
* Write-ahead logging for durability
* Point-in-time recovery support

=== Operational Features
* Health checks and readiness probes
* Prometheus metrics integration
* Structured JSON logging
* Hot configuration reload
