ProximaDB's architecture delivers 6.10x performance improvement through three core innovations: unified storage, intelligent search, and multi-cloud abstraction.

== Core Architecture Principles

image::proximadb-component.png[ProximaDB Component Architecture,width=100%]

=== Design Philosophy

**Cloud-Native First**:: URL-based storage abstraction enables seamless multi-cloud deployment
**Performance-Driven**:: Every component optimized for sub-millisecond latency
**Production-Ready**:: Built for reliability with comprehensive monitoring and observability

=== Key Innovations

image::unified_memtable_architecture.png[Unified Memtable Architecture,width=100%]

**Unified Memtable Architecture**:: 
- Single interface with pluggable backends (SkipList, BTree, HashMap, DashMap)
- Behavior wrappers eliminate 40% code duplication
- Automatic selection based on workload patterns

**Storage-Aware Polymorphic Search**::
- Automatic engine selection based on data location
- Three-tier search: WAL → VIPER → LSM
- 6.10x performance improvement with 100% accuracy

**Dual Storage Strategy**::
- VIPER: Vector-optimized Parquet with ML clustering
- LSM: Row-based SSTable with bloom filters
- Both engines support granular ID-based retrieval

== System Components

=== API Layer

**Multi-Protocol Support**::
- REST API (port 5678): HTTP/JSON for web integration
- gRPC API (port 5679): Binary protocol for high performance
- Identical feature parity across both protocols

**Protocol Detection**::
- Content-type based routing with zero overhead
- Automatic client protocol selection
- Transparent failover between protocols

=== Storage Layer

image::proximadb-class-storage.png[Storage Architecture,width=100%]

**Write-Ahead Log (WAL)**::
- Pluggable serialization strategies (Avro, Bincode)
- Atomic operations with MVCC support
- Configurable flush policies (size, time, count)

**VIPER Engine**::
- Parquet-based columnar storage
- ML-driven clustering for >1M vectors
- Predicate pushdown for filtered queries

**LSM Engine**::
- Row-based SSTable storage
- Bloom filters for efficient lookups
- Automatic compaction with garbage collection

=== Quantization System (Phase 4)

image::unified_quantization_system.png[Unified Quantization Architecture,width=100%]

**Unified Quantization Engine**::
- Support for 1-32 bit quantization levels
- Product Quantization (PQ4, PQ8) with configurable subvectors
- Scalar quantization (INT8, INT16) with learned scale/offset
- Binary quantization for maximum compression
- Hardware acceleration (SIMD, NEON, CUDA, ROCm, MPS)

**Two-Stage Search Strategy**::
- Stage 1: Fast candidate selection using quantized vectors
- Stage 2: Accurate refinement with FP32 vectors
- Configurable candidate multiplier (default: 3x)
- Maintains 100% recall with 3-6x speedup

**Static Column Projection**::
- Query-aware column selection reduces I/O by 50-80%
- Automatic quantization format detection
- Optimized Parquet file reading
- Intelligent caching of frequently accessed columns

=== Indexing System

image::tenant-routing-architecture.png[ML Clustering Architecture,width=100%]

**AXIS Framework**::
- Adaptive index selection based on data characteristics
- HNSW integration for approximate nearest neighbor search
- Configurable update modes (sync, async, hybrid)

**Search Optimization**::
- Parallel cluster search with nearby cluster inclusion
- Multi-tier result deduplication
- Intelligent query planning

== Data Flow

image::proximadb-data-flow.png[Data Flow Architecture,width=100%]

=== Write Path

[source,text]
----
Client → API Layer → Collection Service → WAL → Storage Engine
                                      ↓
                                   Indexing
----

**Write Process**:
1. Client sends vector via REST/gRPC
2. API layer validates and routes request
3. Collection service manages metadata
4. WAL ensures durability before acknowledgment
5. Background processes handle flush and indexing

=== Read Path

[source,text]
----
Client → API Layer → Search Service → Storage-Aware Router
                                            ↓
                                    WAL + VIPER + LSM
                                            ↓
                                    Result Aggregation
----

**Search Process**:
1. Client sends query vector
2. Search service determines optimal strategy
3. Storage-aware router queries appropriate engines
4. Results aggregated and deduplicated
5. Top-k results returned to client

== Deployment Architecture

=== Single-Node Deployment

**Optimal For**:
- Development and testing
- Small to medium workloads (<10M vectors)
- Simplified operations

**Configuration**:
- All components co-located
- Local storage with optional cloud backup
- Vertical scaling through resource allocation

=== Multi-Cloud Deployment

**URL-Based Storage**:
[source,toml]
----
[storage]
wal_urls = [
    "file:///local/fast/storage",
    "s3://backup-bucket/wal",
    "adls://account.dfs.core.windows.net/container"
]
----

**Benefits**:
- Zero-downtime cloud migration
- Automatic failover between providers
- Cost optimization through storage tiering
