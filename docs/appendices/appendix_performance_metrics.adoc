== SQL Query Caching

ProximaDB implements a sophisticated lock-free SQL query cache to improve performance for repeated queries.

=== Cache Architecture

- **Implementation**: Lock-free concurrent LRU cache using DashMap
- **Thread Safety**: Zero contention for read operations
- **Cache Key Components**:
  * Normalized SQL query (whitespace removed, lowercase)
  * Collection ID for targeted invalidation
  * Parameter hash for parameterized queries

=== Cache Configuration

```toml
[sql.cache]
enabled = true                    # Enable/disable SQL caching
max_entries = 1000               # Maximum cached queries
ttl_seconds = 300                # Cache TTL (5 minutes)
max_result_size_bytes = 1048576  # Max 1MB per result
```

== Optimization Guidelines

=== Protocol Selection

**Use gRPC when**:
- Maximum throughput is required
- Bulk operations are common
- Low latency is critical
- Binary data efficiency matters

**Use REST when**:
- SQL queries are needed
- Browser/JavaScript clients
- Simple HTTP tooling required
- Debugging/monitoring ease

=== Hardware Acceleration

**SIMD Optimization**:
- AVX-512: Up to 16x speedup for distance calculations
- AVX2: 8x speedup (fallback for older CPUs)
- SSE4.1: 4x speedup (minimum requirement)

**GPU Acceleration**:
- CUDA: NVIDIA GPUs for batch operations
- ROCm: AMD GPU support
- Metal: Apple Silicon optimization
- Automatic CPU fallback for unsupported hardware

== Workload-Specific Tuning

=== Write-Heavy Workloads

1. Use SST storage engine
2. Increase write buffer to 256MB
3. Reduce compaction frequency (600s interval)
4. Enable batch commits
5. Use gRPC protocol for bulk inserts

=== Read-Heavy Workloads

1. Use VIPER storage engine
2. Increase cache size to 1024MB
3. Enable bloom filters
4. Optimize with HNSW indexes
5. Enable SQL query caching

=== Mixed Workloads

1. Use dual-engine setup
2. Route collections by access pattern
3. Balance memory between engines
4. Monitor metrics for optimization
5. Use adaptive indexing (AXIS)

== Performance Best Practices

=== Batch Operations

**Insert Performance**:
```python
# Optimal: Single batch insert
client.insert_vectors(collection, vectors, ids, metadata)  # 17,666 vec/s

# Suboptimal: Individual inserts
for i in range(1000):
    client.insert_vector(...)  # ~500 vec/s
```

**Batch Size Recommendations**:
- Small vectors (128d): 1,000-5,000 per batch
- Medium vectors (384d): 500-1,000 per batch
- Large vectors (1536d): 100-500 per batch

=== Query Optimization

**Metadata Filtering**:
- Use VIPER engine for complex filters
- Enable predicate pushdown (60-90% I/O reduction)
- Index frequently filtered fields

**Top-K Optimization**:
```python
# Efficient: Small K with metadata filter
results = client.search(collection, vector, top_k=10, 
                       metadata_filter={"category": "electronics"})

# Less efficient: Large K without filter
results = client.search(collection, vector, top_k=1000)
```

=== SQL Best Practices

**Query Normalization**:
```sql
-- These queries will share the same cache entry:
SELECT * FROM products WHERE price > 100
SELECT   *   FROM   products   WHERE   price   >   100
```

**Parameterized Queries**:
```python
# Use parameters for variable values
sql = "SELECT * FROM products WHERE price > $1"
params = [100]
# Different parameter values = different cache entries
```

**Cache-Friendly Patterns**:
```sql
-- Good: Specific, repeated queries
SELECT id, name FROM products 
WHERE category = 'electronics' 
ORDER BY VECTOR_SIMILARITY(vector, $1, 'cosine')
LIMIT 10

-- Avoid: Dynamic or unique queries
SELECT * FROM products 
WHERE description LIKE '%random_search_term%'
```

=== Configuration

==== Server Configuration
REST server automatically enables all compression algorithms with priority order:

1. Deflate (fastest, low CPU)
2. Gzip (good balance)
3. Zstandard (better ratio)
4. Brotli (best compression)

==== Python SDK Configuration
[source,python]
----
from proximadb import ProximaDBClient, ClientConfig, CompressionConfig

config = ClientConfig(
    url="http://localhost:5678",
    compression=CompressionConfig(
        enabled=True,
        algorithm="gzip",      # deflate, gzip, zstd, br
        threshold_bytes=1024,  # Only compress if larger
        level=6               # 1-9 compression level
    )
)
client = ProximaDBClient(config=config)
----

=== Best Practices

1. **Algorithm Selection**:
   - Use deflate for lowest latency
   - Use gzip for best compatibility
   - Use zstd/brotli for maximum compression

2. **Threshold Configuration**:
   - Set threshold to 1KB to avoid compressing small requests
   - Increase threshold for latency-sensitive operations

3. **Client-Server Negotiation**:
   - Clients send Accept-Encoding header
   - Server selects best common algorithm
   - Automatic fallback to uncompressed if needed
