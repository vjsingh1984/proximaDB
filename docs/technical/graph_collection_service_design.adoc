= Graph Collection Service Design
:toc:
:toclevels: 3

== Overview

Following the vector services pattern, we need to split the current `GraphService` into two distinct services:

* **GraphCollectionService** - Manages graph metadata and configurations
* **GraphOperationsService** - Handles graph CRUD operations within collections

== Current Issues

The current `GraphService` violates the separation of concerns by handling both:

* Collection-level operations (graph creation, metadata management, engine selection)
* Data-level operations (node/edge CRUD, traversals, queries)

This is inconsistent with the vector services architecture and creates maintainability issues.

== GraphCollectionService

=== Responsibilities

==== Graph Lifecycle Management
* Create/delete graph collections
* Update graph metadata and configuration
* List and search available graphs
* Graph statistics and health monitoring

==== Metadata Management
* Graph schema definitions (node labels, edge types)
* Property type validation and constraints
* Index configurations and optimization hints
* Access control and permissions

==== Storage Configuration
* Engine selection (ORION, PULSAR, QUASAR)
* Storage location and partitioning strategies
* Compression and serialization settings
* Backup and replication policies

==== Schema Management
* Node label schemas and validation rules
* Edge type schemas and cardinality constraints
* Property type definitions and default values
* Schema evolution and migration support

=== Graph Metadata Structure

[source,protobuf]
----
message GraphCollection {
  string graph_id = 1;                    // Unique identifier
  string name = 2;                        // Human-readable name
  string description = 3;                 // Documentation
  GraphSchema schema = 4;                 // Schema definitions
  StorageConfig storage_config = 5;       // Storage settings
  EngineConfig engine_config = 6;         // Engine selection/config
  AccessControl access_control = 7;       // Permissions
  GraphStats stats = 8;                   // Statistics
  int64 created_at = 9;                   // Creation timestamp
  int64 updated_at = 10;                  // Last modification
}

message GraphSchema {
  repeated NodeLabelSchema node_labels = 1;    // Allowed node types
  repeated EdgeTypeSchema edge_types = 2;      // Allowed edge types
  map<string, PropertySchema> properties = 3; // Property definitions
  repeated UniqueConstraint unique_constraints = 4; // Uniqueness rules
}

message NodeLabelSchema {
  string label = 1;                           // Label name (e.g., "Person")
  repeated string required_properties = 2;   // Must-have properties
  repeated string optional_properties = 3;   // Optional properties
  bool allow_additional_properties = 4;      // Schema flexibility
}

message EdgeTypeSchema {
  string edge_type = 1;                      // Type name (e.g., "KNOWS")
  repeated string source_labels = 2;         // Valid source node labels
  repeated string target_labels = 3;         // Valid target node labels
  repeated string required_properties = 4;   // Must-have properties
  repeated string optional_properties = 5;   // Optional properties
  bool allow_additional_properties = 6;      // Schema flexibility
  Cardinality cardinality = 7;              // Relationship constraints
}

message PropertySchema {
  string name = 1;                           // Property name
  PropertyType type = 2;                     // Data type
  bool required = 3;                         // Required flag
  PropertyValue default_value = 4;           // Default value
  repeated PropertyConstraint constraints = 5; // Validation rules
}

enum PropertyType {
  STRING = 0;
  INTEGER = 1;
  FLOAT = 2;
  BOOLEAN = 3;
  DATETIME = 4;
  JSON = 5;
  ARRAY = 6;
}

enum Cardinality {
  ONE_TO_ONE = 0;
  ONE_TO_MANY = 1;
  MANY_TO_ONE = 2;
  MANY_TO_MANY = 3;
}

== GraphOperationsService

=== Responsibilities

==== Node Operations
* Create, read, update, delete nodes
* Batch node operations
* Node property management
* Node label management

==== Edge Operations
* Create, read, update, delete edges
* Batch edge operations
* Edge property management
* Edge weight management

==== Native Graph Query Operations
* Simple node/edge lookups by ID
* Property-based filtering
* Label-based queries
* Neighborhood queries (get neighbors, incoming/outgoing edges)
* Graph traversals (BFS, DFS, shortest path)
* Pattern matching queries

==== Transaction Management
* ACID transaction support
* Batch operation coordination
* Rollback and recovery
* Conflict resolution

== SQLService (Unified Query Layer)

=== Responsibilities

The SQLService handles ALL SQL-based queries across different data types:

==== Vector Queries
* `SELECT * FROM vectors WHERE similar(embedding, [0.1, 0.2], 10)`
* `SELECT * FROM vectors WHERE metadata.category = 'product'`
* Vector similarity search with SQL syntax

==== Graph Queries
* `SELECT * FROM nodes WHERE label = 'Person' AND properties.age > 25`
* `SELECT * FROM edges WHERE edge_type = 'KNOWS'`
* Standard SQL queries over graph data

==== Hybrid Queries
* `SELECT v.*, n.* FROM vectors v JOIN graph.nodes n ON v.id = n.vector_id`
* Combined vector similarity and graph traversal
* Multi-modal search operations

==== SKS (Semantic Knowledge Store) Queries
* `SELECT * FROM FOLLOW('person_123', 3)` - Graph traversal function
* `SELECT * FROM SIMILAR(vector, 10) JOIN FOLLOW(node_id, 2)` - Hybrid function
* `SELECT * FROM ASSEMBLE(concepts)` - Knowledge assembly function

== Migration Plan

=== Phase 1: Create GraphCollectionService
1. Extract collection management from current GraphService
2. Implement GraphCollection metadata structure
3. Add basic CRUD operations for graph collections
4. Update API handlers to use new service

=== Phase 2: Refactor GraphOperationsService
1. Rename current GraphService to GraphOperationsService
2. Remove collection management responsibilities
3. Add graph_id parameter to all operations
4. Implement transaction support

=== Phase 3: Add Schema Management
1. Implement GraphSchema definitions
2. Add schema validation to operations
3. Create schema migration system
4. Add constraint enforcement

=== Phase 4: Performance Optimization
1. Add caching and indexing optimizations
2. Implement batch operation optimization
3. Add monitoring and metrics
4. Optimize engine selection logic
