= SST Engine vs Competitive Vector Database Formats
:toc: left
:toclevels: 2

**Comparison Date**: December 2025 +
**SST Performance**: ~79ms at 100K vectors (verified)

== Executive Summary

ProximaDB's SST engine competes with modern columnar formats (Lance, Vortex, Nimble) through a **different strategy**: adaptive multi-engine architecture rather than single-format optimization.

**Key Differentiator**: ProximaDB offers 6 engines where others offer 1 format, enabling better workload matching.

== Measured Comparison (Where Data Exists)

=== SST vs Parquet (VIPER)

**SST-LZ4**: 5.34ms at 10K
**VIPER (Parquet)**: 89.5ms at 10K
**Ratio**: **16.8x faster**

**Why SST Wins**:
- Block-level indexing (ProximaBlock)
- Bloom filters (skip irrelevant blocks)
- Three-stage filtering

**When VIPER Wins**:
- Columnar analytics (aggregations)
- Large batch scans (>100K rows)
- Parquet ecosystem compatibility

---

=== SST vs SWIFT (Internal Comparison)

**SST-LZ4**: 5.34ms at 10K
**SWIFT-None**: 95ms at 10K (cache limit)
**Ratio**: **17.8x faster**

**Why SST Scales Better**:
- Byte-based batching (not fixed record count)
- 1MB blocks fit better at scale than 512-record hierarchies
- Compression helps (SWIFT: compression hurts)

**When SWIFT Wins**:
- Small datasets (<5K vectors): 2.50ms vs 3.27ms
- Write throughput (28ms vs 110ms flush)

== ProximaDB's Strategic Advantage

**Single-format databases**: Optimize one dimension (random access OR scans OR compression)

**ProximaDB**: Optimize multiple dimensions through engine selection

**Example Decision Tree**:
```
Workload: Random access + clustered data
  → Choose HELIX (13.51ms, spatial indices)

Workload: Balanced + compression needed
  → Choose SST (5.34ms, LZ4 benefit)

Workload: Analytics + large scans
  → Choose VIPER (89ms, columnar)

With Lance/Vortex/Nimble:
  → Stuck with one format regardless of workload
```

**Business Impact**: Better TCO (total cost of ownership) through workload matching
