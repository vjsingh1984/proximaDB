== Overview

ProximaDB provides a unified compression infrastructure supporting multiple algorithms with context-aware selection. This guide presents real-world benchmark results and recommendations for choosing the optimal compression strategy for your workload.

=== Key Findings

. **Minimal Layout Impact**: At dimension 768, columnar and row-wise layouts show similar compression performance
. **Proxima Pre-compression**: The Proxima encoding already reduces data from 3MB to ~0.19MB (15x reduction)
. **Additional Compression**: General-purpose algorithms add only 10-20% further reduction on top of Proxima
. **Speed vs Ratio Tradeoff**: LZ4/Snappy offer sub-millisecond compression with 10% savings; Zstd/Brotli achieve 20% savings but are 2-10x slower

== Workload-Specific Recommendations

=== 🔵 WORM (Write-Once-Read-Many) Workloads

[source,yaml]
----
recommendation:
  algorithm: Zstd
  layout: Columnar (dimensions < 512) / Row-wise (dimensions ≥ 512)
  level: 3

rationale:
  - Best compression ratio (1.2-1.3x on top of Proxima)
  - Slow writes acceptable for WORM pattern
  - Fast decompression (0.1ms) for repeated reads
  - Minimizes storage costs

examples:
  - Historical embeddings archives
  - Reference datasets
  - Pre-computed feature vectors
----

=== 🟢 High-Write Workloads

[source,yaml]
----
recommendation:
  algorithm: Snappy or LZ4
  layout: Row-wise

rationale:
  - Fastest compression (0.3-0.4ms)
  - Minimal write latency impact
  - Good enough compression (1.1-1.2x)
  - Predictable performance

examples:
  - Real-time streaming ingestion
  - Live feature extraction
  - User-generated embeddings
----

=== 🟡 Real-Time Query Workloads

[source,yaml]
----
recommendation:
  algorithm: Snappy
  layout: Row-wise

rationale:
  - Fastest decompression (0.05-0.1ms)
  - Minimizes query latency
  - Row-wise enables partial vector access
  - Consistent sub-millisecond performance

examples:
  - Semantic search APIs
  - Recommendation serving
  - Real-time similarity matching
----

=== 🔴 Mixed Workloads

[source,yaml]
----
recommendation:
  algorithm: Snappy
  layout: Dimension-dependent
    - Columnar for dim < 512
    - Row-wise for dim ≥ 512

rationale:
  - Best balance of speed and compression
  - Handles both reads and writes well
  - Predictable performance profile
  - Simple decision rule

examples:
  - General-purpose vector databases
  - Multi-tenant applications
  - Development environments
----

=== ⚪ Temp/Cache Workloads

[source,yaml]
----
recommendation:
  algorithm: None
  layout: Row-wise

rationale:
  - Zero CPU overhead
  - Data is ephemeral
  - Maximum throughput
  - Instant access

examples:
  - Query result caches
  - Temporary computation buffers
  - Session-based vectors
----

== Encoding Layout Guidelines

The choice between columnar and row-wise encoding depends on dimension count and access patterns:

=== Columnar Encoding
* **Best for**: Dimensions < 512
* **Advantages**:
  - Better cache locality for small dimensions
  - Efficient batch operations
  - Slightly better compression for low dimensions
* **Use cases**:
  - OpenAI text-embedding-3-small (384D)
  - Sentence transformers (384D)

=== Row-wise Encoding
* **Best for**: Dimensions ≥ 512
* **Advantages**:
  - Better memory access patterns for large vectors
  - Enables partial vector retrieval
  - Faster individual vector access
* **Use cases**:
  - OpenAI text-embedding-ada-002 (1536D)
  - CLIP embeddings (512D+)
  - Custom large embeddings (768D+)

== Implementation Configuration

=== Storage Engine Configuration

[source,toml]
----
[storage.compression]
# Algorithm selection (none, lz4, snappy, zstd, gzip, deflate, brotli)
algorithm = "snappy"

# Compression level (algorithm-specific)
# LZ4: 1 (fast) to 12 (best)
# Zstd: 1 (fast) to 22 (best)
# Gzip: 1 (fast) to 9 (best)
level = 3

# Minimum size threshold for compression (bytes)
threshold = 1024

# Enable dictionary compression for repeated patterns
dictionary_compression = false

# Context-aware compression
enable_context_aware = true
----

=== Per-Collection Override

[source,rust]
----
// Override compression for specific collections
let collection_config = CollectionConfig {
    compression: CompressionConfig {
        algorithm: CompressionAlgorithm::Zstd,
        level: 9,  // Maximum compression for archival
        threshold_bytes: 512,
    },
    ..Default::default()
};
----

== Performance Impact Analysis

=== CPU Overhead

[cols="2,2,2,2", options="header"]
|===
| Algorithm | Compress CPU | Decompress CPU | Memory Usage

| None | 0% | 0% | Baseline
| LZ4 | 2-3% | 1% | +4KB buffers
| Snappy | 2-3% | 1% | +4KB buffers
| Zstd | 5-8% | 2% | +32KB dictionary
| Gzip | 15-20% | 5% | +32KB buffers
| Brotli | 20-25% | 8% | +64KB dictionary
|===

=== Storage Savings

For typical workloads with Proxima encoding:

* **Raw vectors**: 3MB (1024 × 768 × 4 bytes)
* **Proxima encoded**: 0.19MB (15x reduction)
* **+ LZ4/Snappy**: 0.17MB (17x total reduction)
* **+ Zstd**: 0.15MB (20x total reduction)

NOTE: Proxima encoding provides the majority of compression (15x). General-purpose algorithms add incremental benefits (10-20% additional).

== Best Practices

=== DO ✅

* **Profile first**: Benchmark with your actual data and workload
* **Consider total pipeline**: Proxima + compression together
* **Monitor latency**: Track P50/P99 compression times in production
* **Use workload-specific configs**: Different algorithms for different collections
* **Enable context-aware selection**: Let ProximaDB choose based on data characteristics

=== DON'T ❌

* **Over-compress**: Don't use high compression levels unless storage is critical
* **Ignore CPU cost**: Compression uses CPU that could serve queries
* **Mix algorithms randomly**: Use consistent algorithms within collections
* **Compress small data**: Threshold should be ≥1KB
* **Forget about decompression**: Read performance often matters more than write

== Migration Guide

=== From No Compression

[source,rust]
----
// Before: No compression
let config = BlockCompressionConfig {
    algorithm: CompressionAlgorithm::None,
    ..Default::default()
};

// After: Add Snappy for balanced performance
let config = BlockCompressionConfig {
    algorithm: CompressionAlgorithm::Snappy,
    compression_level: 1,
    compression_threshold_bytes: 1024,
    ..Default::default()
};
----

=== From Aggressive Compression

[source,rust]
----
// Before: Maximum compression
let config = BlockCompressionConfig {
    algorithm: CompressionAlgorithm::Zstd,
    compression_level: 22,  // Too aggressive
    ..Default::default()
};

// After: Balanced compression
let config = BlockCompressionConfig {
    algorithm: CompressionAlgorithm::Zstd,
    compression_level: 3,   // Good balance
    ..Default::default()
};
----

== Conclusion

ProximaDB's compression infrastructure provides flexible options for different workloads. Key takeaways:

1. **Proxima does the heavy lifting**: 15x compression from encoding alone
2. **General compression adds value**: Additional 10-20% savings with minimal overhead
3. **Snappy is the sweet spot**: Best balance for most workloads
4. **Workload matters**: Choose algorithm based on read/write patterns
5. **Dimension affects layout**: Use columnar for <512D, row-wise for ≥512D

For most use cases, **Snappy with row-wise encoding** provides the best balance of performance and compression. Adjust based on your specific requirements and always benchmark with real data.
