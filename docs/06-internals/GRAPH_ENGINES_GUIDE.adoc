== Introduction

ORION is the only graph runtime in ProximaDB. It maintains high-performance
topology projections over canonical graph records. It does not own durable graph
truth; durable authority remains in xCatalog, canonical records, WAL/log/manifest
state, policy/RLS, version/time, and provenance.

== Runtime Boundary

[source,text]
----
Graph APIs / traversal / graph RAG
        |
      ORION
        |
CSR/adjacency projections + graph planning hints
        |
Relational distributed planning and execution
        |
xCatalog + canonical WAL + policy + storage routing
----

ORION owns graph-specific traversal and projection behavior. It does not own:

* shard placement,
* distributed query coordination,
* fanout/fanin execution,
* rebalancing,
* cold-tier authority,
* storage repair source,
* isolation or policy boundaries.

Those responsibilities belong to the relational/storage substrate.

== ORION

=== Overview

ORION uses Compressed Sparse Row (CSR) and adjacency projections for fast graph
traversal. These projections are rebuildable from canonical records.

=== Performance Characteristics

* 1M+ edges/second traversal target
* <1us node lookup target
* <100 bytes/node memory overhead target
* projection WAL/snapshot support as a compatibility recovery buffer

=== Configuration

ORION is the default runtime. No graph-engine feature flag is required.

[source,rust]
----
let engine = OrionGraphEngine::new();

let engine = OrionGraphEngine::with_persistence_for_graph(
    "my_graph".to_string(),
    "file:///tmp/proximadb".to_string(),
    true,
).await?;
----

== Distributed Graph Scale

Scale-out graph behavior is implemented through the relational distributed
planner/coordinator and cataloged partitioning metadata. ORION supplies graph
planning hints such as node/edge locality, traversal depth, frontier shape, and
edge-type selectivity. The relational substrate decides route, placement,
fanout/fanin, freshness, policy boundary, and isolation.

Former PULSAR-specific ideas are now tracked as relational distributed
requirements, not as graph engine code.

== Projection Tiering

Hot/cold behavior is implemented as catalog/storage projection policy. ORION may
consume access heat and projection freshness hints, but cold placement is a
storage/catalog decision over canonical records.

Former QUASAR-specific ideas are now tracked as xCatalog/storage projection
requirements, not as graph engine code.

== Retired Engine Names

`PULSAR` and `QUASAR` are retired graph engine names. The code no longer exposes
separate modules, feature flags, REST routes, or engine factories for them.
Requests that specify these names are rejected with a compatibility error that
directs users to ORION.

== Operational Guidance

* Use ORION for all graph workloads.
* Use relational distributed configuration for scale-out behavior.
* Use xCatalog/storage policy for projection retention and tiering.
* Do not document, demo, or release-note PULSAR or QUASAR as product engines.
