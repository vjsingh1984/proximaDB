= Multi-Model Execution Architecture
:toc: left
:toclevels: 3

== Overview

ProximaDB is a multi-model database where each data model has its own purpose-built execution path from API to storage. The models do NOT share a single storage engine trait or result type.

== New Storage Traits

=== DocumentStorageEngine (CEDAR)

[source,rust]
----
#[async_trait]
pub trait DocumentStorageEngine: Send + Sync {
    // Identity
    fn engine_name(&self) -> &'static str;

    // Document CRUD
    async fn insert_document(&self, collection: &str, doc: DocumentRecord) -> Result<DocumentRecord>;
    async fn get_document(&self, collection: &str, id: &str) -> Result<Option<DocumentRecord>>;
    async fn update_document(&self, collection: &str, id: &str, updates: Vec<DocumentUpdate>) -> Result<DocumentRecord>;
    async fn delete_document(&self, collection: &str, id: &str) -> Result<bool>;

    // Query
    async fn query_documents(&self, collection: &str, params: DocumentQueryParams) -> Result<DocumentQueryResult>;
    async fn scan_documents(&self, collection: &str, limit: Option<usize>) -> Result<Vec<DocumentRecord>>;

    // Aggregation
    async fn aggregate(&self, collection: &str, pipeline: Vec<AggregationStage>) -> Result<Vec<serde_json::Value>>;

    // Index management
    async fn create_index(&self, collection: &str, field: &str, index_type: IndexType) -> Result<()>;

    // Persistence
    async fn flush(&self, collection: &str) -> Result<FlushResult>;
    async fn compact(&self, collection: &str) -> Result<CompactionResult>;
}
----

=== ObservabilityStorageEngine (CHRONO)

[source,rust]
----
#[async_trait]
pub trait ObservabilityStorageEngine: Send + Sync {
    // Identity
    fn engine_name(&self) -> &'static str;

    // Metric operations
    async fn ingest_metrics(&self, namespace: &str, samples: Vec<MetricSample>) -> Result<u64>;
    async fn query_metrics(&self, namespace: &str, name: &str, labels: &[(String, String)],
                           start_ns: i64, end_ns: i64) -> Result<Vec<MetricSample>>;
    async fn aggregate_metrics(&self, namespace: &str, params: MetricAggParams) -> Result<MetricAggResult>;

    // Log operations
    async fn ingest_logs(&self, namespace: &str, entries: Vec<LogEntry>) -> Result<u64>;
    async fn query_logs(&self, namespace: &str, start_ns: i64, end_ns: i64,
                        severity: Option<Severity>, text_filter: Option<&str>) -> Result<Vec<LogEntry>>;

    // Trace operations
    async fn ingest_spans(&self, namespace: &str, spans: Vec<TraceData>) -> Result<u64>;
    async fn query_traces(&self, namespace: &str, trace_id: Option<&str>,
                          service: Option<&str>, start_ns: i64, end_ns: i64) -> Result<Vec<TraceData>>;

    // Persistence
    async fn flush(&self, namespace: &str) -> Result<FlushResult>;
    async fn compact(&self, namespace: &str) -> Result<CompactionResult>;

    // Metrics about the engine itself
    async fn series_count(&self) -> u64;
    async fn collect_engine_metrics(&self) -> Result<HashMap<String, serde_json::Value>>;
}
----

== SQL Lowering Per Data Model

The UQL lowerer produces model-specific operators, not storage-engine-specific operators:

[source,text]
----
SQL: SELECT * FROM doc_users WHERE $.age > 25 LIMIT 10

Lowering:
  1. Detect store type: "doc_" prefix → Document
  2. Parse: collection="users", filter=$.age>25, limit=10
  3. Produce: DocumentQueryPlan { collection, filter, limit }
  4. Execute: DocumentService.query_documents(params)
  5. Return: Vec<DocumentRecord>
  6. Format: PG rows (id, document, version)

SQL: SELECT * FROM graph_social WHERE label = 'Person'

Lowering:
  1. Detect store type: "graph_" prefix → Graph
  2. Parse: graph="social", label_filter="Person"
  3. Produce: GraphQueryPlan { graph, node_filter }
  4. Execute: GraphService.query_nodes(filter)
  5. Return: Vec<Node>
  6. Format: PG rows (id, labels, properties)

SQL: SELECT AVG(value) FROM log_metrics WHERE name = 'cpu' AND timestamp > X

Lowering:
  1. Detect store type: "log_" prefix → Observability
  2. Parse: namespace="metrics", metric="cpu", time_range, aggregation=AVG
  3. Produce: MetricQueryPlan { namespace, name, time_range, agg }
  4. Execute: ObservabilityService.aggregate_metrics(params)
  5. Return: MetricAggResult
  6. Format: PG rows (name, avg_value, timestamp)
----

== Impact on CEDAR and CHRONO Engines

CEDAR and CHRONO should implement their model-specific traits, NOT `UnifiedStorageEngine`:

- `CedarEngine` implements `DocumentStorageEngine`
- `ChronoEngine` implements `ObservabilityStorageEngine`
- Both are wired into their respective service layers (`DocumentService`, `ObservabilityService`)
- The `UnifiedStorageEngine` trait remains vector-only

The existing `UnifiedStorageEngine` stub on these engines serves only for factory registration
and can delegate to the model-specific trait methods internally.
