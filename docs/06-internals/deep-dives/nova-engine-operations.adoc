== Overview

The NOVA (Progressive Columnar) storage engine has been refactored into a modular operations-based architecture, separating core engine logic from specific operation types. This new design improves maintainability, testability, and enables independent optimization of different operation categories.

== Module Structure

=== Operations Module (`operations/mod.rs`)

The central operations coordinator that provides a unified interface to all NOVA operations.

**Location**: `src/storage/engines/impls/nova/operations/mod.rs`

**Exports**:
- `NovaFlushOperations`: Flush operation coordination
- `NovaCompactionOperations`: Compaction and merging logic
- `NovaSearchOperations`: Progressive search implementation

=== Flush Operations (`operations/flush.rs`)

Handles data persistence from memory to columnar storage with hierarchical statistics.

**Key Features**:
- **Hierarchical Statistics**: Multi-level data organization with SuperBlocks
- **Batch Optimization**: Intelligent batching for optimal I/O patterns
- **Compression Integration**: Automatic compression algorithm selection
- **Progressive Writing**: Incremental writes with consistency guarantees

== Integration with Core Engine

=== Engine Coordination

The core NOVA engine coordinates operations through a unified interface:

[source,rust]
----
impl NovaEngine {
    pub fn flush_operations(&self) -> &NovaFlushOperations {
        &self.flush_ops
    }

    pub fn compaction_operations(&self) -> &NovaCompactionOperations {
        &self.compaction_ops
    }

    pub fn search_operations(&self) -> &NovaSearchOperations {
        &self.search_ops
    }

    // Unified operation coordination
    pub async fn execute_operation(
        &self,
        operation: NovaOperation,
    ) -> Result<OperationResult> {
        match operation {
            NovaOperation::Flush(params) => {
                self.flush_operations()
                    .flush_with_hierarchical_stats(params.vectors, &params.collection_id, &params.base_path)
                    .await
                    .map(OperationResult::Flush)
            }
            NovaOperation::Compact(params) => {
                self.compaction_operations()
                    .compact_with_zone_maps(params.input_files, &params.target_file, &params.zone_map_config)
                    .await
                    .map(OperationResult::Compaction)
            }
            NovaOperation::Search(params) => {
                self.search_operations()
                    .progressive_search(&params.query, params.refinement_stages)
                    .await
                    .map(OperationResult::Search)
            }
        }
    }
}
----

=== Performance Tuning

==== Flush Operations Tuning

1. **SuperBlock Size**: Larger sizes reduce metadata overhead but increase memory usage
2. **Row Group Size**: Balance between I/O efficiency and memory consumption
3. **Compression**: Choose algorithm based on data characteristics and CPU availability

==== Compaction Operations Tuning

1. **Zone Map Granularity**: Finer granularity improves pruning but increases overhead
2. **Merge Threshold**: Higher thresholds reduce compaction frequency but may increase query latency
3. **Cost-Based Optimization**: Enable for complex workloads with diverse query patterns

==== Search Operations Tuning

1. **Progressive Stages**: More stages provide better accuracy but higher latency
2. **Accuracy Target**: Balance between result quality and search speed
3. **Streaming Threshold**: Adjust based on available memory and result set sizes

== Migration and Compatibility

=== Migration from Monolithic Design

1. **Backward Compatibility**: All existing NOVA engine APIs remain functional
2. **Gradual Migration**: Operations can be migrated incrementally
3. **Configuration Migration**: Existing configurations are automatically converted

=== API Compatibility

The refactored NOVA engine maintains full API compatibility:

[source,rust]
----
// Original API still works
impl UnifiedStorageEngine for NovaEngine {
    async fn do_flush(&self, params: &FlushParameters) -> Result<FlushResult> {
        // Delegates to NovaFlushOperations
        self.flush_operations()
            .flush_with_hierarchical_stats(params.vectors.clone(), &params.collection_id, &params.base_path)
            .await
    }

    async fn search_vectors_unified(&self, ctx: &StorageQueryContext) -> Result<Vec<OptimizedSearchRecord>> {
        // Delegates to NovaSearchOperations
        self.search_operations()
            .progressive_search(&ctx.query, ctx.refinement_stages)
            .await
    }
}

== Best Practices

=== Operations Design

1. **Single Responsibility**: Each operation module handles one specific type of operation
2. **Composability**: Operations can be combined to create complex workflows
3. **Error Handling**: Comprehensive error handling with detailed error context
4. **Resource Management**: Careful resource cleanup and memory management

=== Performance Optimization

1. **Async Operations**: All operations are fully asynchronous
2. **Batching**: Operations support batching for improved throughput
3. **Caching**: Intelligent caching of metadata and intermediate results
4. **Monitoring**: Comprehensive metrics for performance analysis

=== Maintainability

1. **Clear Interfaces**: Well-defined interfaces between operations
2. **Documentation**: Comprehensive documentation for all operations
3. **Testing**: Unit and integration tests for all operations
4. **Versioning**: Careful versioning to maintain backward compatibility

== Conclusion

The NOVA engine operations refactoring represents a significant architectural improvement, providing:

- **Better Maintainability**: Clear separation of concerns and modular design
- **Enhanced Performance**: Specialized optimizations for each operation type
- **Improved Testability**: Independent testing of each operation module
- **Greater Flexibility**: Easy addition of new operations and optimization strategies

This modular architecture positions the NOVA engine for continued evolution and optimization while maintaining the progressive columnar storage capabilities that make it ideal for mixed workloads and complex analytical queries.
