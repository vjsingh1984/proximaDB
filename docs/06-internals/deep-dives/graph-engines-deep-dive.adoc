**Why ProximaDB has three graph engines and how each solves different scaling challenges**

== Design Philosophy

=== The Problem: Graph Scaling is Hard

Graph workloads have fundamentally different scaling challenges than vector workloads:

* **Traversal locality**: Neighbors of neighbors are often accessed together
* **Power-law distribution**: Some nodes have millions of edges, most have few
* **Unpredictable access**: Random walks, shortest paths, graph algorithms
* **Memory pressure**: Large graphs don't fit in RAM

ProximaDB provides three engines for three scaling dimensions:

[cols="2,2,3", options="header"]
|===
| Engine | Scaling Dimension | Use Case

| **ORION** | Latency (in-memory) | Real-time traversal, sub-millisecond queries
| **PULSAR** | Capacity (distributed) | Billion+ node graphs across shards
| **QUASAR** | Cost (tiered) | Large sparse graphs with hot/cold separation
|===

== ORION: In-Memory CSR Engine

=== Why CSR Format?

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
graph TB
    subgraph ADJLIST["Adjacency List"]
        AL1["Node 0 → [1, 2, 3]"]
        AL2["Node 1 → [2]"]
        AL3["Node 2 → []"]
        note1["Random memory access<br/>Cache unfriendly"]
    end

    subgraph CSR["Compressed Sparse Row"]
        CSR1["Offsets: [0, 3, 4, 4]"]
        CSR2["Targets: [1, 2, 3, 2]"]
        note2["Sequential memory access<br/>Cache friendly"]
    end

    style ADJLIST fill:#ffe6e6,stroke:#e06666
    style CSR fill:#e6ffe6,stroke:#93c47d
----

**CSR advantage**: Getting neighbors of node `i` is:

1. Look up `offsets[i]` and `offsets[i+1]`
2. Read `targets[offsets[i]..offsets[i+1]]`
3. **Sequential memory access** → CPU cache friendly

=== CSR Structure

[source,text]
----
Example Graph:
  Node 0 → Node 1, Node 2
  Node 1 → Node 2

CSR Encoding:
  offsets = [0, 2, 3, 3]
            │  │  │  │
            │  │  │  └─ End marker
            │  │  └─ Node 2 starts at index 3 (0 edges)
            │  └─ Node 1 starts at index 2 (1 edge)
            └─ Node 0 starts at index 0 (2 edges)

  targets = [1, 2, 2]
            │  │  │
            │  │  └─ Node 1's edge
            └──┴─ Node 0's edges

Neighbor lookup for Node 0:
  start = offsets[0] = 0
  end = offsets[1] = 2
  neighbors = targets[0..2] = [1, 2]

Cost: O(1) index lookups + O(degree) memory reads
----

**Rayon threshold**: Only parallelize when frontier > 1000 nodes (thread overhead vs parallelism benefit).

=== When to Choose ORION

[cols="1,4", options="header"]
|===
| Choose ORION When | Rationale

| **Sub-millisecond queries needed**
| In-memory CSR provides O(1) neighbor lookup

| **Graph fits in memory**
| Typical: <100 bytes/node overhead

| **Real-time traversals**
| Social networks, knowledge graphs, recommendations

| **Concurrent read/write**
| DashMap provides lock-free concurrent access
|===

== PULSAR: Distributed Sharding Engine

=== Why Consistent Hashing?

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
graph TB
    subgraph NAIVE["Naive Sharding (Hash Mod N)"]
        N1["Add shard → rehash ALL data"]
        N2["Remove shard → rehash ALL data"]
        N3["Expensive rebalancing"]
    end

    subgraph CONSISTENT["Consistent Hash Ring"]
        C1["Add shard → move ~1/N data"]
        C2["Remove shard → move ~1/N data"]
        C3["Minimal rebalancing"]
    end

    style NAIVE fill:#ffe6e6,stroke:#e06666
    style CONSISTENT fill:#e6ffe6,stroke:#93c47d
----

**Virtual nodes**: Each shard gets 150 virtual positions on the ring → even distribution despite varying node counts.

=== Cross-Shard Traversal

[source,text]
----
Cross-Shard BFS Challenge:

Query: Find path from Node A (Shard 0) to Node D (Shard 2)

Shard 0          Shard 1          Shard 2
┌─────┐          ┌─────┐          ┌─────┐
│  A  │ ───────→ │  B  │ ───────→ │  D  │
└─────┘          └─────┘          └─────┘

Steps:
1. BFS on Shard 0: A → neighbors include B@Shard1
2. Cross-shard to Shard 1: B → neighbors include D@Shard2
3. Cross-shard to Shard 2: Found D!

Result: A → B → D (3 network hops)

Optimization: Pre-fetch likely next shards based on locality hints
----

=== When to Choose PULSAR

[cols="1,4", options="header"]
|===
| Choose PULSAR When | Rationale

| **Billion+ nodes**
| Horizontal scaling across shards

| **High availability needed**
| Replication factor 2-3 for fault tolerance

| **Multi-tenant isolation**
| Assign different tenants to different shards

| **Geo-distributed deployment**
| Shards can be placed in different regions
|===

== QUASAR: Hot/Cold Tiering Engine

=== Why Tiering?

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
graph TB
    subgraph PROBLEM["The Problem"]
        PR1["1B nodes × 100 bytes = 100GB"]
        PR2["Only 1% accessed frequently"]
        PR3["99GB wasted RAM"]
    end

    subgraph SOLUTION["QUASAR Solution"]
        S1["Hot tier: 1% in ORION (1GB RAM)"]
        S2["Cold tier: 99% on disk (SST/Parquet)"]
        S3["Auto-promote on access"]
    end

    style PROBLEM fill:#ffe6e6,stroke:#e06666
    style SOLUTION fill:#e6ffe6,stroke:#93c47d
----

=== Tiering State Machine

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
stateDiagram-v2
    [*] --> Hot: Create Node

    Hot --> Cooling: No access (1 hour)
    Cooling --> Hot: Access
    Cooling --> Cold: Migration worker

    Cold --> Warming: Access request
    Warming --> Hot: Load complete

    Hot --> [*]: Delete
    Cold --> [*]: Delete
----

**Thresholds**:

* `cold_migration_threshold`: 1 hour of no access → demote
* `hot_promotion_threshold`: 5 minutes of frequent access → promote
* `migration_interval`: Background worker runs every 60 seconds

=== When to Choose QUASAR

[cols="1,4", options="header"]
|===
| Choose QUASAR When | Rationale

| **Sparse access patterns**
| Most nodes rarely accessed; hot tier stays small

| **Cost-sensitive deployment**
| 80-90% storage cost reduction vs all-memory

| **Historical data**
| Archive old relationships; promote when queried

| **Large but cold graphs**
| Reference data accessed occasionally
|===

=== Performance Comparison

|===
| Operation | ORION | PULSAR | QUASAR

| Node lookup | 0.1µs | 10µs (network) | 0.1µs (hot) / 1ms (cold)
| Edge traversal | 1µs/edge | 10µs/edge | 1µs (hot) / 5ms (cold)
| BFS (depth 3) | 10µs | 100µs (cross-shard) | Variable
| Create node | 2µs | 50µs (replicated) | 2µs
| Memory/node | 100 bytes | 100 bytes × replicas | ~10 bytes (cold)
|===

== Common Architecture

=== Arc-Based Memory Pool

[source,text]
----
All engines share Arc-based memory for zero-copy node sharing:

GraphMemoryPool
├── nodes: DashMap<NodeId, Arc<Node>>
├── total_allocated: AtomicUsize
└── peak_allocated: AtomicUsize

Why Arc?
- Multiple traversals can reference same node
- No copying during BFS frontier expansion
- Thread-safe reference counting
- Automatic cleanup when all references drop
----

=== WAL Persistence

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
sequenceDiagram
    participant C as Client
    participant E as Engine
    participant W as WAL
    participant M as Memory

    C->>E: create_node(node)
    E->>W: log(CreateNode, node)
    W->>W: fsync()
    W-->>E: ack
    E->>M: insert(node)
    E-->>C: Ok(node_id)

    Note over W: Durability before<br/>memory update
----

**Recovery**: On startup, replay WAL entries to reconstruct in-memory state.

== Configuration Guide

=== ORION Configuration

[source,toml]
----
[graph.orion]
enable_persistence = true
enable_wal = true
snapshot_interval_seconds = 3600
max_memory_mb = 4096
parallel_bfs_threshold = 1000  # Parallelize when frontier > 1000
----

[source,toml]
----
[graph.pulsar]
shard_count = 16
replication_factor = 2
consistency_level = "quorum"  # "any", "quorum", "all"
virtual_nodes_per_shard = 150
----

hot_promotion_threshold_seconds = 300
cold_storage_backend = "sst"  # or "parquet"
----

== Summary: Graph Engine Design Principles

1. **ORION: Latency-optimized** - CSR format + DashMap for sub-millisecond traversals
2. **PULSAR: Capacity-optimized** - Consistent hashing + replication for billion+ nodes
3. **QUASAR: Cost-optimized** - Hot/cold tiering for sparse access patterns
4. **Shared architecture** - Arc-based memory pool + WAL persistence across all engines
5. **Parallel BFS** - Rayon-powered parallelism when frontier exceeds threshold
