**Why HELIX exists and how spatial locality transforms vector search**

== Design Philosophy

=== The Problem HELIX Solves

Vector similarity search has a fundamental inefficiency: **semantically similar vectors are scattered randomly across storage**. When searching for "similar images of cats", the database must scan vectors that represent cars, buildings, and text documents before finding relevant cat images.

**The insight**: High-dimensional vectors often live on low-dimensional manifolds. Images of cats cluster in embedding space. If we could store nearby vectors together on disk, we could skip entire regions during search.

**The challenge**: How do you preserve N-dimensional neighborhoods when writing to 1-dimensional disk?

=== The Hilbert Curve Solution

**Why Hilbert curves?**

|===
| Property | Hilbert Curve | Alternative: Z-Order (Morton)

| **Locality Quality** | 0.95 (excellent) | 0.82 (good)
| **Worst-case jumps** | Bounded to neighbors | Can jump diagonally
| **Range queries** | Connected regions | May have gaps
| **Computation** | 2x slower | Fast bit interleaving
|===

HELIX chooses Hilbert over Z-order because **locality quality is paramount** - the 2x computation cost is negligible compared to I/O savings from better pruning.

=== Core Design Decisions

[cols="2,3,3", options="header"]
|===
| Decision | Rationale | Trade-off

| **PCA before Hilbert**
| Hilbert curves are O(2^d) in dimensionality; PCA reduces 768D to 16D tractably
| Model training overhead; potential information loss (mitigated by capturing 80%+ variance)

| **Per-collection PCA model**
| Different collections have different data distributions; shared model would be suboptimal
| Storage overhead (~1MB per collection); model drift over time

| **Disk-only LSM (no memtable)**
| Uses global WAL; avoids duplicate write buffering
| Slightly higher flush latency (acceptable for read-optimized workload)

| **5-stage progressive search**
| Each stage is cheaper than the next; eliminate candidates early
| Complexity; tuning difficulty
|===

=== The PCA → Hilbert → Storage Pipeline

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
stateDiagram-v2
    [*] --> RawVector: 768-dim input

    state "PCA Projection" as PCA {
        RawVector --> LoadModel: Get collection PCA
        LoadModel --> Project: Model exists
        LoadModel --> Train: First flush (>1000 vectors)
        Train --> Project: Model trained
        Project --> PCACoords: 16-dim output
    }

    state "Hilbert Encoding" as HILBERT {
        PCACoords --> Quantize: Normalize to [0, 2^bits)
        Quantize --> Encode: Hilbert curve mapping
        Encode --> HilbertKey: 64-bit spatial key
    }

    state "Block Assignment" as BLOCK {
        HilbertKey --> SortByKey: Order vectors
        SortByKey --> GroupIntoBlocks: 128-256 vectors each
        GroupIntoBlocks --> ComputeCentroids: Per-block centroid
        ComputeCentroids --> Flush: Write Hilbert-sorted SSTable
    }

    Flush --> [*]

    note right of Train
        Train on first 1000+ vectors
        Capture 80%+ variance
        Save to __model/pca_model.bin
    end note

    note right of Encode
        LUT-accelerated for 2D
        Generic n-dim for higher
    end note
----

=== When to Choose HELIX

[cols="1,4", options="header"]
|===
| Choose HELIX When | Rationale

| **Data has natural clusters**
| Image embeddings, document topics, user preferences cluster in semantic space

| **Similarity search dominates**
| Hilbert pruning eliminates 90%+ blocks for spatial queries

| **Large datasets (100K+ vectors)**
| Pruning benefit scales with data size; overhead amortized

| **Read-heavy workload**
| Optimized for query, accepts slower writes
|===

=== When NOT to Choose HELIX

[cols="1,2,2", options="header"]
|===
| Scenario | Better Choice | Why

| Random/uniform data distribution
| **SST**
| No clusters to exploit; Hilbert adds overhead without benefit

| Write-heavy workload
| **SST**
| PCA + Hilbert computation on every write

| Metadata filtering primary
| **SST**
| Three-stage filtering more effective than spatial pruning

| Small datasets (<10K)
| **SWIFT**
| Hilbert overhead not justified for few blocks

| Frequently changing data patterns
| **RAPTOR**
| PCA model drift makes HELIX suboptimal
|===

== Progressive Search: The 5-Stage Pipeline

=== Why Five Stages?

Each stage is exponentially cheaper than the next. Early elimination saves expensive computation.

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
flowchart TB
    subgraph S1["Stage 1: Hilbert Range (SSTable level)"]
        A[1000 SSTables] -->|Hilbert distance| B[100 SSTables]
    end

    subgraph S2["Stage 2: Binary Quantization (1-bit)"]
        B -->|Hamming distance| C[10K candidates]
    end

    subgraph S3["Stage 3: INT8 Quantization (8-bit)"]
        C -->|SIMD L2| D[1K candidates]
    end

    subgraph S4["Stage 4: PQ8 Product Quantization"]
        D -->|Lookup tables| E[100 candidates]
    end

    subgraph S5["Stage 5: FP32 Reranking"]
        E -->|Full precision L2| F[Top-K Results]
    end

    style S1 fill:#e6f3ff,stroke:#4a90e2
    style S2 fill:#fff3e6,stroke:#f4a261
    style S3 fill:#e6ffe6,stroke:#93c47d
    style S4 fill:#ffe6f3,stroke:#e066a0
    style S5 fill:#f3e6ff,stroke:#9066e0
----

|===
| Stage | Compression | Distance | Cost per Vector | Purpose

| Hilbert Range | N/A | Key subtraction | ~10ns | Skip entire files
| Binary | 768→96 bits | Hamming | ~5ns | Ultra-fast coarse filter
| INT8 | 768→768 bytes | SIMD L2 | ~50ns | Balance speed/accuracy
| PQ8 | 768→32 bytes | LUT lookup | ~100ns | High compression filter
| FP32 | 768×4 bytes | Full L2 | ~500ns | Final precise ranking
|===

=== Block-Level Centroid Selection

Within each SSTable, HELIX selects `max(3, sqrt(n))` blocks closest to query:

[source,text]
----
Query vector → PCA project → Hilbert encode → Query key

For each SSTable in Hilbert range:
    1. Load block centroids from index
    2. Compute distance: query_centroid → each block_centroid
    3. Select sqrt(num_blocks) closest blocks
    4. Scan only selected blocks for candidates

Example: 400 blocks → scan 20 blocks → 95% pruning
----

**Why sqrt(n)?**

- Too few blocks → miss relevant vectors → poor recall
- Too many blocks → scan everything → no benefit
- sqrt(n) balances recall and efficiency empirically

    end note

== File Format Design

=== Why Hilbert Range in Header?

[source,text]
----
┌──────────────────────────────────────────────────────┐
│ HELIX SSTable Header                                  │
├──────────────────────────────────────────────────────┤
│ Magic: "HLIX"                                        │
│ Version: 2                                           │
│ ★ Hilbert Range: [min_key, max_key] ★               │
│ Vector Count, Block Count, Dimensions                │
└──────────────────────────────────────────────────────┘

★ Why store Hilbert range in header?

During search:
1. Read only header (128 bytes)
2. If query_key outside [min_key, max_key]: SKIP ENTIRE FILE
3. No need to read index or data blocks

For 1000 files, skip 90% without reading data → massive I/O savings
----

=== Block Structure: Centroid + Hilbert Range

[source,text]
----
┌─────────────────────────────────────────────────────────┐
│ HELIX Block                                              │
├─────────────────────────────────────────────────────────┤
│ Block Centroid: avg(all vectors in block)               │
│   → Used for distance-based block selection             │
│                                                         │
│ Hilbert Range: [min_key, max_key] for vectors in block │
│   → Used for range-based pruning                        │
│                                                         │
│ ProximaDataBlock: actual vectors (Hilbert-sorted)       │
│   → Vectors ordered by Hilbert key within block         │
│   → Enables sequential I/O during scan                  │
└─────────────────────────────────────────────────────────┘

Two pruning mechanisms:
1. Centroid distance: "Is this block's center close to query?"
2. Hilbert range: "Does query key fall in block's Hilbert range?"

Use both for maximum pruning effectiveness.
----

== Compaction: Maintaining Hilbert Order

=== Why Hilbert-Aware Compaction?

Standard LSM compaction merges by key (ID). HELIX merges by **Hilbert key** to maintain spatial locality.

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
graph TB
    subgraph L0["Level 0: Unsorted Flushes"]
        F1["File 1<br/>Hilbert: [5,15]"]
        F2["File 2<br/>Hilbert: [2,8]"]
        F3["File 3<br/>Hilbert: [12,25]"]
        F4["File 4<br/>Hilbert: [1,6]"]
    end

    subgraph MERGE["Hilbert-Ordered Merge"]
        M["K-way merge<br/>sorted by Hilbert key"]
    end

    subgraph L1["Level 1: Hilbert-Sorted"]
        O1["File A<br/>Hilbert: [1,10]"]
        O2["File B<br/>Hilbert: [11,25]"]
    end

    F1 --> M
    F2 --> M
    F3 --> M
    F4 --> M
    M --> O1
    M --> O2

    style L0 fill:#ffd966,stroke:#cc9900
    style L1 fill:#93c47d,stroke:#5a8047
----

**Post-compaction**: Level 1 files have non-overlapping Hilbert ranges. Point queries touch exactly one file.

== Configuration Guide

=== Tuning for Better Locality

[source,toml]
----
[storage.helix]
# More PCA dimensions = better locality, but slower encoding
pca_dimensions = 32  # 16-64 typical

# Higher bits = finer Hilbert resolution
hilbert_bits_per_dimension = 16  # 8-21 range

# Smaller blocks = better pruning granularity
proxima_block_size = 128  # 128-256 typical

# Retrain PCA when data distribution changes
pca_drift_threshold = 0.1  # 10% eigenvalue shift triggers retrain
----

=== Tuning for Query Performance

[source,toml]
----
[storage.helix]
# Parallel search across files
parallel_search_enabled = true
parallel_search_threshold = 3  # Parallelize if >3 files

# Block cache for hot data
block_cache_size_mb = 1024

# Enable liquid clustering for adaptive layout
enable_liquid_clustering = true  # Learn from query patterns
----

== Summary: HELIX Design Principles

1. **Spatial locality through Hilbert curves** - Adjacent vectors in N-dim stay adjacent in 1D storage
2. **PCA dimensionality reduction** - Make Hilbert tractable for high-dimensional vectors
3. **Per-collection PCA models** - Optimal projection for each data distribution
4. **5-stage progressive search** - Eliminate candidates with increasingly expensive operations
5. **Hilbert-aware compaction** - Maintain spatial locality as data grows
