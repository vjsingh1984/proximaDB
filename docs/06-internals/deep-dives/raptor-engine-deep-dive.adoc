**Why RAPTOR exists and how the Matrix Trinity enables adaptive learning**

== Design Philosophy

=== The Problem RAPTOR Solves

Most storage engines use fixed strategies that work well for one workload but poorly for others. RAPTOR addresses:

* **Unknown query patterns**: New applications don't know their access patterns upfront
* **Evolving workloads**: User behavior changes over time
* **Variable k values**: Some queries need top-10, others need top-1000
* **Multi-tenant diversity**: Different tenants have different patterns

=== The Matrix Trinity Innovation

**Key insight**: Pre-compute all three distance relationships, then adaptively select which to use based on query patterns.

=== Core Design Decisions

[cols="2,3,3", options="header"]
|===
| Decision | Rationale | Trade-off

| **Pre-computed P² matrix**
| O(1) neighbor lookup within row groups; GPU-acceleratable
| O(n²) storage per row group; recompute on updates

| **Sparse K² matrix**
| Skip distant centroids (3× avg distance); reduce memory 50-70%
| May miss edge cases; requires threshold tuning

| **Adaptive P×K matrix**
| Learn which vectors need centroid distances based on query patterns
| Training period needed; storage overhead for boundary vectors

| **Adaptive row group sizing**
| 500-5000 vectors based on expected k value
| Prediction may be wrong for new workloads
|===

== Architecture Overview

=== Why Matrix Trinity?

[source,text]
----
The Navigation Problem:

Given: 1M vectors in 1000 row groups
Query: Find top-10 similar to query vector

Traditional approach (SST/HELIX):
  1. Scan all row groups → compute distances → sort
  2. Cost: O(1M) distance computations

Matrix Trinity approach:
  1. K² Matrix: Query centroid → find 10 closest clusters
  2. P×K Matrix: Identify boundary vectors that might be closer
  3. P² Matrix: Within selected clusters, O(1) neighbor lookup
  4. Cost: O(10 × 1000) + O(boundary) + O(1) = O(10K)

Speedup: 100x for typical queries
----

**Why 16-bit quantization?**

* Full precision: N × N × 4 bytes = 4MB for 1000 vectors
* Quantized: N × N × 2 bytes = 2MB for 1000 vectors
* Error: <0.1% for typical embedding distances
* **50% storage reduction with negligible quality loss**

=== K² Matrix: Inter-Centroid Navigation

[source,text]
----
K² Matrix Sparsification:

Dense storage (naive):
  K × K distances = 1M entries for 1000 clusters

Sparse storage (RAPTOR):
  Only store distances < 3× average
  Result: ~30% non-zero entries
  Savings: 70% memory reduction

Example:
  avg_distance = 0.5
  threshold = 1.5
  Clusters > 1.5 apart: not stored (unlikely to be relevant)
----

=== P×K Matrix: Adaptive Coverage

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
flowchart TB
    subgraph DETECTION["Boundary Detection"]
        B1["For each vector:"]
        B2["Distance to primary cluster"]
        B3["Distance to secondary cluster"]
        B4["Ratio = secondary / primary"]
        B5{Ratio < 1.2?}
        B5 -->|Yes| B6["Boundary vector"]
        B5 -->|No| B7["Interior vector"]
    end

    subgraph STORAGE["Adaptive Storage"]
        S1["Boundary vectors: store all K distances"]
        S2["Interior vectors: store only primary"]
        S3["Result: 10-50% coverage"]
    end

    DETECTION --> STORAGE

    style DETECTION fill:#e6f3ff,stroke:#4a90e2
    style STORAGE fill:#e6ffe6,stroke:#93c47d
----

**Why boundary vectors matter?**

* Interior vectors: Clearly belong to one cluster; centroid distance sufficient
* Boundary vectors: Near cluster edges; might be closer to query in adjacent cluster
* Storing all distances for boundaries ensures no false negatives

=== When to Choose RAPTOR

[cols="1,4", options="header"]
|===
| Choose RAPTOR When | Rationale

| **Unknown query patterns**
| Matrix Trinity adapts to discovered patterns

| **Variable k values**
| Adaptive row group sizing (500-5000) matches k

| **GPU available (Apple Silicon)**
| Metal MPS accelerates P² matrix building

| **Multi-tenant diversity**
| Different tenants get different learned optimizations
|===

=== When NOT to Choose RAPTOR

[cols="1,2,2", options="header"]
|===
| Scenario | Better Choice | Why

| Predictable workload
| **SST** or **HELIX**
| Pre-computation overhead not justified

| Memory-constrained
| **VIPER** or **SST**
| Matrix storage requires ~2-3GB for 10M vectors

| Simple point queries
| **SST**
| Bloom filters faster than matrix navigation

| Static data (no updates)
| **HELIX**
| Hilbert curves don't need recomputation
|===

=== Why Adaptive Sizing?

[source,mermaid]

        F3["k=1000: too many row groups"]
    end

    style FIXED fill:#ffe6e6,stroke:#e06666
----

=== Sizing Algorithm

[source,text]
----
Adaptive Row Group Sizing:

Input: Expected k value, dimension, cloud profile

if k < 10:
    base_size = 500      # Minimize read waste
elif k < 100:
    base_size = 1000     # Balanced
else:
    base_size = 5000     # Maximize throughput

# Adjust for cloud storage latency
if cloud_profile == S3:
    size = max(base_size, 1000)  # Larger for network amortization
elif cloud_profile == HighLatency:
    size = base_size * 2
else:
    size = base_size

# P² matrix memory: N × N × 2 bytes
# 500 → 500KB, 1000 → 2MB, 5000 → 50MB
----

== GPU Acceleration

=== Metal MPS for P² Matrix

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
sequenceDiagram
    participant CPU as CPU
    participant GPU as Metal MPS
    participant MEM as Memory

    CPU->>MEM: Vectors (row group)
    CPU->>GPU: Copy vectors to GPU memory
    GPU->>GPU: Parallel distance computation
    Note over GPU: N×N distances in parallel
    GPU->>MEM: 16-bit quantized P² matrix
    CPU->>CPU: Continue with K² navigation
----

**Performance**:

* CPU (SIMD): 1000×1000 distances = 50ms
* GPU (Metal): 1000×1000 distances = 8ms
* **6x speedup for P² matrix building**

=== GPU Threshold

[source,text]
----
GPU Threshold Decision:

GPU overhead: ~2ms for memory copy + kernel launch

Breakeven analysis:
  N < 100: CPU faster (overhead dominates)
  N >= 100: GPU faster (parallelism wins)

Default: gpu_min_batch_size = 100
----

== File Format Design

=== Why Store Matrices in File?

[source,text]
----
RAPTOR File Structure:

┌──────────────────────────────────────────┐
│ Header (512 bytes)                        │
│   Magic: "RPTR"                          │
│   Centroid count, Row group count        │
├──────────────────────────────────────────┤
│ Global HNSW Graph (~100MB for 10M vecs)  │
│   Entry points for navigation            │
├──────────────────────────────────────────┤
│ K² Matrix (sparse)                        │
│   Centroid-to-centroid distances         │
├──────────────────────────────────────────┤
│ Row Group 0                               │
│   P² Matrix (N × N × 2 bytes)            │
│   P×K Matrix (adaptive coverage)          │
│   Local HNSW graph                        │
│   Vector data (Proxima compressed)        │
├──────────────────────────────────────────┤
│ Row Group 1, 2, ... N                     │
└──────────────────────────────────────────┘

Why store matrices?
- Avoid recomputation on read
- Matrices are O(n²), expensive to rebuild
- Trade storage for query latency
----

== Configuration Guide

=== Tuning for Unknown Workloads

[source,toml]
----
[raptor]
# Adaptive sizing
base_rowgroup_size = 1000
min_rowgroup_size = 500
max_rowgroup_size = 5000

# All three matrices for full adaptivity
enable_p2_matrix = true
enable_k2_matrix = true
enable_pxk_matrix = true
pxk_strategy = "adaptive"  # Learn from queries

# GPU if available
enable_gpu = true
gpu_min_batch_size = 100
----

=== Tuning for High-k Queries

[source,toml]
----
[raptor]
# Larger row groups for high k
base_rowgroup_size = 3000
max_rowgroup_size = 5000

# More HNSW connections
hnsw_m = 32              # More connections
hnsw_ef_search = 100     # Higher search quality
----

== Summary: RAPTOR Design Principles

1. **Matrix Trinity architecture** - P² (intra-cluster), K² (inter-cluster), P×K (adaptive) provide complete distance coverage
2. **Adaptive row group sizing** - 500-5000 vectors based on expected k value
3. **GPU acceleration** - Metal MPS for P² matrix building (6x speedup)
4. **Learned optimization** - P×K matrix adapts to query patterns over time
5. **Sparse K² storage** - 70% memory reduction by skipping distant centroids
