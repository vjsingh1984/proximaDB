== Design Philosophy

=== The Problem NOVA Solves

Most vector databases optimize for either:

* **OLTP (SST)**: Fast writes, simple queries, real-time updates
* **OLAP (VIPER)**: Batch analytics, high compression, columnar scans

But many workloads are **mixed**: real-time updates with analytical queries. NOVA bridges this gap with hierarchical zone maps that enable both fast writes AND intelligent pruning.

**Key insight**: Each level (SuperBlock → RowGroup → Page) stores min/max bounds. Queries prune based on whether their threshold overlaps the bounds.

=== Core Design Decisions

[cols="2,3,3", options="header"]
|===
| Decision | Rationale | Trade-off

| **Three-level zone maps**
| SuperBlock (1GB) → RowGroup (100MB) → Page (1MB) provides hierarchical pruning
| Zone map storage overhead (~1-2% of data)

| **Progressive search (5 stages)**
| Zone Map → Binary → INT8 → PQ8 → FP32 eliminates candidates at each level
| More complexity; tuning required

| **Apache Parquet backend**
| Mature ecosystem; columnar compression; row group statistics
| Parquet overhead for small files

| **Cost-based optimizer**
| Chooses optimal search path based on selectivity estimates
| Requires accurate statistics
|===

    SB1 --> RG1

    RG1 --> P2

----

**Pruning cascade**:

1. **SuperBlock level**: Skip 50% of SuperBlocks (coarse bounds)
2. **RowGroup level**: Skip 80% of remaining RowGroups (medium bounds)
3. **Page level**: Skip 50% of remaining pages (fine bounds)
4. **Total**: 90%+ data never read

=== Five-Stage Progressive Search

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
flowchart TB
    subgraph S1["Stage 1: Zone Map Pruning"]
        A[1M vectors] -->|Bounds check| B[100K vectors]
        note1["Skip entire regions<br/>Cost: O(1) per region"]
    end

    subgraph S2["Stage 2: Binary Filter"]
        B -->|Hamming distance| C[5K candidates]
        note2["1 bit/dim<br/>Cost: 5ns/vector"]
    end

    subgraph S3["Stage 3: INT8 Ranking"]
        C -->|SIMD L2| D[500 candidates]
        note3["8 bits/dim<br/>Cost: 50ns/vector"]
    end

    subgraph S4["Stage 4: PQ8 Scoring"]
        D -->|Lookup tables| E[50 candidates]
        note4["32 subquantizers<br/>Cost: 100ns/vector"]
    end

    subgraph S5["Stage 5: FP32 Rerank"]
        E -->|Full precision| F[Top-K Results]
        note5["32 bits/dim<br/>Cost: 500ns/vector"]
    end

    style S1 fill:#e6f3ff,stroke:#4a90e2
    style S2 fill:#fff3e6,stroke:#f4a261
    style S3 fill:#e6ffe6,stroke:#93c47d
    style S4 fill:#ffe6f3,stroke:#e066a0
    style S5 fill:#f3e6ff,stroke:#9066e0
----

|===
| Stage | Input | Output | Time | Data Read

| Zone Map | 1,000,000 | 100,000 | 10ms | Metadata only
| Binary | 100,000 | 5,000 | 50ms | 96 bytes/vec
| INT8 | 5,000 | 500 | 30ms | 768 bytes/vec
| PQ8 | 500 | 50 | 20ms | 32 bytes/vec
| FP32 | 50 | 10 | 10ms | 3KB/vec
|===

**Total**: 120ms for 1M vectors → **208x speedup** vs full scan

=== When to Choose NOVA

[cols="1,4", options="header"]
|===
| Choose NOVA When | Rationale

| **Mixed workloads**
| Balanced write throughput (75K/s) with intelligent read pruning

| **Queries benefit from spatial bounds**
| Zone maps provide 90%+ pruning for selective queries

| **Moderate update frequency**
| Handles updates better than pure columnar (VIPER)

| **Analytics + real-time queries**
| Five-stage progressive search balances recall and latency
|===

=== When NOT to Choose NOVA

[cols="1,2,2", options="header"]
|===
| Scenario | Better Choice | Why

| Pure batch analytics
| **VIPER**
| VIPER's pure columnar achieves better compression

| Real-time point queries
| **SST**
| SST's bloom filters are faster for point lookups

| Multi-tenant hierarchy
| **SWIFT**
| SWIFT's SuperBlocks provide tenant isolation

| Maximum write throughput
| **SST**
| SST's LSM-tree has lower write latency
|===

== Zone Map Design

=== Zone Map Structure

[source,text]
----
Zone Map at Each Level:

┌────────────────────────────────────────────────────┐
│ ZoneMap                                             │
├────────────────────────────────────────────────────┤
│ min_values: [f32; dimension]  // Per-dim minimum   │
│ max_values: [f32; dimension]  // Per-dim maximum   │
│ centroid: Option<[f32; dimension]>  // For cosine  │
│ radius: Option<f32>           // Bounding sphere   │
│ vector_count: u64             // For statistics    │
└────────────────────────────────────────────────────┘

Pruning Decision:

For Euclidean distance:
  Compute minimum possible distance to zone bounds
  If min_distance > query_threshold: PRUNE

For Cosine similarity:
  Compute max possible similarity using centroid + radius
  If max_similarity < query_threshold: PRUNE
----

=== Why Centroid + Radius for Cosine?

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
graph TB
    subgraph EUCLIDEAN["Euclidean: Bounding Box"]
        E1["min/max bounds define box"]
        E2["Query point → min distance to box"]
        E3["If min_dist > threshold: prune"]
    end

    subgraph COSINE["Cosine: Bounding Sphere"]
        C1["centroid + radius define sphere"]
        C2["Query point → similarity to centroid"]
        C3["If similarity - radius < threshold: prune"]
    end

    style EUCLIDEAN fill:#e6f3ff,stroke:#4a90e2
    style COSINE fill:#e6ffe6,stroke:#93c47d
----

**Min/max bounds are tight for Euclidean** (rectangles), but **loose for Cosine** (angle-based). Centroids with radius provide tighter bounds for Cosine similarity.

== Compaction Strategy

=== Zone Map-Aware Compaction

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%

    subgraph INPUTS["Input Files"]
        I1["File A: zone_map A"]

    end

    subgraph OUTPUT["Output File"]
        O1["Merged file"]
        O2["Combined zone_map"]
    end

    I1 --> M1
    I2 --> M1
    M1 --> M2
    M2 --> M3
    M3 --> O1
    M3 --> O2

    style INPUTS fill:#ffe6e6,stroke:#e06666
    style MERGE fill:#fff3e6,stroke:#f4a261
    style OUTPUT fill:#e6ffe6,stroke:#93c47d
----

**Why recalculate?**

* Merged data may have different bounds than either input
* Zone maps must accurately reflect actual data for correct pruning
* Stale bounds → incorrect pruning → missed results

== Configuration Guide

=== Tuning for Mixed Workloads

[source,toml]
----
[nova]
# Hierarchical organization
superblock_size_mb = 1024    # 1GB SuperBlocks
row_group_size_mb = 100      # 100MB RowGroups

# Zone map settings
enable_zone_maps = true
zone_map_granularity = "row_group"  # or "page" for finer

# Progressive search
progressive_search.stages = 5
progressive_search.adaptive = true  # Cost-based optimization

# Caching for zone maps
cache.superblock_cache_mb = 100
cache.zone_map_cache_mb = 50
----

=== Tuning for Analytics-Heavy

[source,toml]
----
[nova]
# Larger units for better compression
superblock_size_mb = 2048
row_group_size_mb = 200

# More aggressive quantization
quantization.enable_pq8 = true
quantization.pq_segments = 64  # More segments = better quality
----

== Monitoring & Debugging

=== Key Health Indicators

[cols="2,3,2", options="header"]
|===
| Metric | Healthy Range | Action if Unhealthy

| `zone_map_pruning_ratio` | >80% | Check zone map accuracy; verify data is clustered
| `superblock_cache_hit_rate` | >95% | Increase superblock_cache_mb
| `progressive_stages_avg` | 4-5 | If always 5, zone maps may not be effective
| `quantization_recall` | >96% | Increase PQ segments; check training samples
|===

== Summary: NOVA Design Principles

1. **Hierarchical zone maps** - SuperBlock → RowGroup → Page bounds enable cascading pruning
2. **Five-stage progressive search** - Zone Map → Binary → INT8 → PQ8 → FP32 eliminates candidates early
3. **Mixed workload optimization** - Balances write throughput with intelligent read pruning
4. **Cost-based optimization** - Chooses optimal search path based on selectivity
5. **Zone map-aware compaction** - Maintains accurate bounds during merges
