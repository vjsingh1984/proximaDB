**Why VIPER exists and how pure columnar storage transforms analytics**

== Design Philosophy

=== The Problem VIPER Solves

Vector databases typically optimize for real-time queries, sacrificing storage efficiency. But many workloads are **analytics-first**:

* Batch processing of ML pipeline outputs
* Data warehouse integration with columnar tools (Spark, Presto, DuckDB)
* Cloud storage where egress costs dominate
* Archival storage where compression matters more than latency

These workloads need a fundamentally different storage model.

=== The Columnar Insight

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
graph TB
    subgraph ROW["Row-Based Storage (SST)"]
        R1["vec1: [0.12, -0.34, 0.87, ...]"]
        R2["vec2: [0.15, -0.31, 0.85, ...]"]
        R3["vec3: [0.13, -0.33, 0.86, ...]"]
        note1["Mixed values → poor compression"]
    end

    subgraph COL["Columnar Storage (VIPER)"]
        C1["dim_0: [0.12, 0.15, 0.13, ...]"]
        C2["dim_1: [-0.34, -0.31, -0.33, ...]"]
        C3["dim_2: [0.87, 0.85, 0.86, ...]"]
        note2["Similar values → 69% compression"]
    end

    style ROW fill:#ffe6e6,stroke:#e06666
    style COL fill:#e6ffe6,stroke:#93c47d
----

**Key insight**: Embedding vectors have strong correlations **within dimensions** but weak correlations **across dimensions**.

* Dimension 0 across all vectors: `[0.12, 0.15, 0.13, 0.14]` → Similar values, compress well
* Row across all dimensions: `[0.12, -0.34, 0.87, ...]` → Mixed values, compress poorly

**Result**: VIPER achieves **69.5% compression** vs ~16% for hybrid columnar engines.

=== Core Design Decisions

[cols="2,3,3", options="header"]
|===
| Decision | Rationale | Trade-off

| **Pure Parquet format**
| Industry-standard columnar format; integrates with Spark/Presto/DuckDB; mature compression
| No custom optimization; Parquet overhead for small files

| **50K vectors per row group**
| Large groups enable better compression modeling; amortize Parquet overhead
| Higher memory during writes; coarser pruning granularity

| **Pre-computed quantization columns**
| Store Binary/INT8/PQ alongside FP32; avoid re-quantization at query time
| 4x storage overhead for quantized columns; stale if distribution changes

| **No memtable (disk-only)**
| Uses global WAL; batch-oriented writes fit analytics workload
| Higher write latency than SST; not suitable for real-time inserts
|===

**Parquet advantages for vectors**:

1. **Columnar layout**: Each dimension compressed independently
2. **Row group statistics**: Min/max per column enables pruning
3. **Ecosystem integration**: Read with Spark, Presto, DuckDB
4. **Cloud-native**: Optimized for S3/GCS/Azure Blob

=== Storage Schema

[source,text]
----
VIPER Parquet Schema:

├── Core Columns (always present)
│   ├── id: String                    // Vector ID
│   ├── vector_fp32: FixedSizeList    // Original 768-dim float32
│   ├── timestamp: i64                // Insertion time
│   └── metadata: Map<String, String> // User metadata

├── Quantization Columns (pre-computed)
│   ├── q_binary: Binary              // 1 bit/dim → 96 bytes for 768D
│   ├── q_int8: FixedSizeList         // 8 bits/dim → 768 bytes
│   └── q_pq8: Binary                 // Product quantization codes

├── Quantization Parameters (per row group)
│   ├── qp_binary_threshold: f32      // Binarization threshold
│   ├── qp_int8_min/max/scale: f32    // INT8 normalization
│   └── qp_pq_centroids: Binary       // PQ codebook

Why pre-compute quantization?
- Analytics queries often scan millions of vectors
- Re-quantizing at query time = O(n × d) overhead
- Pre-computed = instant access to compressed representation
----

=== When to Choose VIPER

[cols="1,4", options="header"]
|===
| Choose VIPER When | Rationale

| **Storage cost is critical**
| 69.5% compression reduces cloud storage costs 4x vs hybrid formats

| **Batch analytics workload**
| Columnar format optimized for scanning, filtering, aggregating

| **Cloud storage backend**
| Parquet's row group structure enables selective reads → lower egress

| **Ecosystem integration**
| Read VIPER files directly with Spark, Presto, DuckDB, pandas

| **Archival/cold storage**
| Maximum compression for infrequently accessed data
|===

=== When NOT to Choose VIPER

[cols="1,2,2", options="header"]
|===
| Scenario | Better Choice | Why

| Real-time writes
| **SST**
| VIPER's large row groups (50K) have higher write latency

| Point queries (by ID)
| **SST** or **SWIFT**
| Row-based formats have O(1) ID lookup; VIPER requires row group scan

| Spatial locality queries
| **HELIX**
| VIPER doesn't preserve vector proximity in storage layout

| Frequently updated data
| **SST**
| VIPER's immutable row groups require rewriting for updates

| Sub-millisecond latency
| **SWIFT**
| Parquet parsing overhead > SWIFT's in-memory hierarchy
|===

== Progressive Search: The Quantization Cascade

=== Why Pre-Compute Multiple Quantization Levels?

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
flowchart TB
    subgraph QUERY["Query: top-10 from 1M vectors"]
        Q[Query Vector]
    end

    subgraph S1["Stage 1: Binary Filter"]
        A[1M vectors] -->|Hamming distance| B[100K candidates]
        note1["96 bytes × 1M = 96MB scanned<br/>90% eliminated"]
    end

    subgraph S2["Stage 2: INT8 Ranking"]
        B -->|SIMD L2 distance| C[10K candidates]
        note2["768 bytes × 100K = 73MB scanned<br/>90% eliminated"]
    end

    subgraph S3["Stage 3: PQ8 Scoring"]
        C -->|Lookup table distance| D[1K candidates]
        note3["32 bytes × 10K = 320KB scanned<br/>90% eliminated"]
    end

    subgraph S4["Stage 4: FP32 Rerank"]
        D -->|Full precision L2| E[Top-10 Results]
        note4["3KB × 1K = 3MB scanned<br/>Final ranking"]
    end

    Q --> S1
    S1 --> S2
    S2 --> S3
    S3 --> S4

    style S1 fill:#ffe6e6,stroke:#e06666
    style S2 fill:#fff3e6,stroke:#f4a261
    style S3 fill:#e6f3ff,stroke:#4a90e2
    style S4 fill:#e6ffe6,stroke:#93c47d
----

|===
| Stage | Column Read | Bytes/Vector | Total I/O (1M) | Elimination

| Binary | `q_binary` | 96 | 96MB | 90%
| INT8 | `q_int8` | 768 | 73MB (100K) | 90%
| PQ8 | `q_pq8` | 32 | 320KB (10K) | 90%
| FP32 | `vector_fp32` | 3072 | 3MB (1K) | Final
|===

**Key insight**: Pre-computing quantization means each stage reads only its column. No re-quantization = pure I/O bound.

**Total**: 169MB scanned vs 3GB for full FP32 scan → **17x I/O reduction**

=== Row Group Pruning

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
sequenceDiagram
    participant Q as Query
    participant F as Footer
    participant RG as Row Groups
    participant R as Results

    Q->>F: Read Parquet footer (4KB)
    F->>F: Parse row group statistics

    loop Each Row Group
        F->>F: Check min/max vs filter
        alt Statistics match
            F->>RG: Add to scan list
        else Statistics don't match
            F->>F: Skip row group (PRUNED)
        end
    end

    Note over F,RG: 80%+ row groups pruned<br/>for selective filters

    RG->>R: Read only selected columns<br/>from selected row groups
----

**Example**: Filter `timestamp > 2024-01-01`

* 20 row groups total
* Footer statistics show 16 row groups have `max(timestamp) < 2024-01-01`
* Only 4 row groups actually read → **80% I/O reduction**

== Compression Deep Dive

=== Why 69.5% vs 16%?

[source,text]
----
Compression Analysis (768-dim OpenAI embeddings):

Row-Based (SST):
  Vector: [0.12, -0.34, 0.87, 0.45, -0.23, ...]
  Next vector: [0.15, -0.31, 0.85, 0.42, -0.21, ...]

  Compressor sees: [0.12, -0.34, 0.87, 0.45, -0.23, 0.15, -0.31, ...]
                   └─────────────── No pattern ───────────────────┘

  Result: ~16% compression (random-looking data)

Columnar (VIPER):
  Dimension 0: [0.12, 0.15, 0.13, 0.14, 0.11, ...]
  Dimension 1: [-0.34, -0.31, -0.33, -0.32, -0.35, ...]

  Compressor sees: [0.12, 0.15, 0.13, 0.14, ...]
                   └── Clear pattern: values near 0.13 ──┘

  Result: 69.5% compression (exploits dimension correlation)

Why the difference?
1. Same-dimension values cluster in narrow range
2. Delta encoding captures small differences efficiently
3. ZSTD's context modeling works better on similar values
----

== Cloud Storage Optimization

=== S3/GCS/Azure Design

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
stateDiagram-v2
    [*] --> QueryReceived

    state "Footer Cache Check" as CACHE {
        QueryReceived --> CacheHit: Footer in memory
        QueryReceived --> CacheMiss: Footer not cached
        CacheMiss --> FetchFooter: Download 4KB footer
        FetchFooter --> ParseFooter: Parse row group metadata
        ParseFooter --> CacheFooter: Store in memory
    }

    state "Selective Download" as DOWNLOAD {
        CacheHit --> PruneRowGroups: Use statistics
        CacheFooter --> PruneRowGroups
        PruneRowGroups --> SelectColumns: Project needed columns
        SelectColumns --> StreamRowGroups: Download only selected
    }

    StreamRowGroups --> ProcessResults
    ProcessResults --> [*]

    note right of CACHE
        Footer caching: 4KB × files
        Typical: 10-100KB memory
        Saves 500ms+ per query
    end note

    note right of DOWNLOAD
        Column projection: Read only q_binary
        for first pass (96 bytes/vec)
        vs full vector (3KB/vec)
    end note
----

**Cloud cost optimization**:

1. **Footer caching**: Parse once, reuse forever (files are immutable)
2. **Row group pruning**: Download only matching groups
3. **Column projection**: Read only needed columns (Binary < INT8 < PQ < FP32)

**Example**: Search 1M vectors on S3

* Without VIPER: Download 3GB (full vectors)
* With VIPER: Download 96MB (Binary column only) + 3MB (final FP32 for top-1K)
* **Egress reduction: 30x**

== Compaction Strategy

=== Why Quantization-Aware Compaction?

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
graph TB
    subgraph NAIVE["Naive Compaction (WRONG)"]
        N1[File A: vectors 1-1000<br/>Binary threshold: 0.12]
        N2[File B: vectors 1001-2000<br/>Binary threshold: 0.15]
        N3["Merge row groups<br/>Keep old thresholds"]
        N4["PROBLEM: Thresholds<br/>don't match merged data"]

        N1 --> N3
        N2 --> N3
        N3 --> N4
    end

    subgraph SMART["VIPER Compaction (CORRECT)"]
        S1[File A: vectors 1-1000]
        S2[File B: vectors 1001-2000]
        S3["1. Merge FP32 vectors<br/>2. Retrain quantization<br/>3. Write new columns"]
        S4["Result: Consistent<br/>quantization across file"]

        S1 --> S3
        S2 --> S3
        S3 --> S4
    end

    style NAIVE fill:#ffe6e6,stroke:#e06666
    style SMART fill:#e6ffe6,stroke:#93c47d
----

**The problem**: Each file has its own quantization parameters trained on its vectors. Merging files without retraining creates inconsistent quantization → search quality degrades.

**VIPER solution**: Compaction always retrains quantization on merged data. This is expensive but ensures consistent quality.

== Summary: VIPER Design Principles

1. **Pure columnar for maximum compression** - Same-dimension values compress 4x better than row-based
2. **Pre-computed quantization columns** - Store Binary/INT8/PQ alongside FP32 for instant access
3. **Large row groups (50K)** - Better compression modeling, amortize Parquet overhead
4. **Cloud-native with footer caching** - Minimize egress through selective row group/column reads
5. **Quantization-aware compaction** - Always retrain on merged data for consistent quality
