= ProximaDB Documentation Structure
:toc:
:toclevels: 3

== Overview

ProximaDB uses a **two-tier documentation system** to eliminate duplication and improve maintainability:

1. **Top-Level Docs** (`docs/`): User-facing guides, overviews, and cross-cutting concerns
2. **Module-Level Docs** (`src/*/README.adoc`): Implementation details within code modules

== Guiding Principles

[quote]
____
*"Details live in module docs. Top-level docs reference them."*
____

[NOTE]
====
Keep top-level docs aligned with current system status:
- WAL recovery has a known pool metadata propagation bug; wherever recovery is described, reference `URGENT_FIX_INSTRUCTIONS.md` / `FINAL_FIX_NEEDED.md` and the validation script `RECOVERY_TEST_FRESH.sh`.
- Cloud and GPU features are feature-gated/experimental; highlight this in any docs that mention them.
- For commands/standards, defer to `AGENTS.md` to avoid drift.
====

=== Benefits

* **No Duplication**: Implementation details exist in one place (module docs)
* **Better Maintenance**: Code changes update nearby module docs automatically
* **Clear Navigation**: Users start with `docs/`, developers go to `src/*/README.adoc`
* **Version Control**: Module docs stay in sync with code (same PR)

== Documentation Locations

=== When to Use Top-Level Docs (`docs/`)

Use for **external-facing** content:

* ✅ **Getting Started Guides**: Quick start, tutorials, first steps
* ✅ **Architecture Overviews**: High-level system design (diagrams, concepts)
* ✅ **User Guides**: How to use features (not how they're implemented)
* ✅ **Operations**: Deployment, monitoring, troubleshooting
* ✅ **API Reference**: REST/gRPC endpoint documentation
* ✅ **Performance Benchmarks**: Results, comparisons, tuning guides
* ✅ **Business Case**: Competitive advantages, use cases

**Example**: `docs/06-internals/storage/engine_selection.adoc`

* Compares SST vs VIPER vs NOVA for different workloads
* References `src/storage/engines/impls/sst/README.adoc` for implementation

=== When to Use Module-Level Docs (`src/*/README.adoc`)

Use for **implementation details**:

* ✅ **Module Purpose**: What this code does and why it exists
* ✅ **Architecture**: Internal structure, key components, data flow
* ✅ **Implementation**: Algorithms, data structures, performance characteristics
* ✅ **Integration Points**: How other modules use this one
* ✅ **Testing**: Test strategy, running tests, test locations
* ✅ **Configuration**: Module-specific config options
* ✅ **Future Work**: TODOs, planned enhancements specific to this module

**Example**: `src/storage/engines/impls/sst/README.adoc`

* Explains SST internals: flush strategy, block structure, filtering
* Referenced by `docs/06-internals/storage/engine_selection.adoc`

== Example: Event Modules Documentation

=== Problem Statement

User asked: *"Why do we have two similar modules? Are they doing the same thing?"*

Modules in question:
* `src/index/axis/eventlog/` - AXIS indexing coordination
* `src/services/events/` - Service wrapper for EventLog

=== Solution: Module-Level READMEs

Created comprehensive module docs that explain:

1. **`src/index/axis/eventlog/README.adoc`**:
   - Purpose: Core AXIS indexing coordination
   - Components: EventLog queue, persistence, recovery
   - Integration: How storage engines emit events

2. **`src/services/events/README.adoc`**:
   - Purpose: Service-level wrapper for dependency injection
   - Lifecycle: Initialized at server startup
   - Relationship: References AXIS EventLog README for core logic

3. **Cross-References**:
   - Both READMEs link to each other
   - Top-level `docs/architecture/` references both for context

=== Result

* **Clear Separation**: Core logic vs service wrapper
* **No Duplication**: Details only in module READMEs
* **Easy Navigation**: Top-level docs point to modules
* **Semantic Names**: Clarified in module docs (no code rename needed)

== Documentation Standards

=== Format Requirements

* **File Format**: All docs must be `.adoc` (AsciiDoc), not Markdown
* **Diagrams**: Use Mermaid syntax in `[source,mermaid]` blocks
* **Visual Style**: Follow ProximaDB color scheme (see `docs/README.adoc`)
* **Cross-References**: Use AsciiDoc `link:` syntax

=== Module README Template

[source,asciidoc]
----
= Module Name
:toc:
:toclevels: 2

== Overview

Brief 1-2 sentence description.

== Purpose

*Primary Goal*: What problem does this module solve?

=== Problem Solved

Detailed explanation of the problem and why this solution exists.

src/module/

== Creating New Documentation

=== For New Features

1. **Create module README** (`src/feature/README.adoc`):
   - Implementation details, architecture, testing

2. **Update top-level guide** (e.g., `docs/guides/feature_guide.adoc`):
   - User-facing how-to
   - Reference module README for details

3. **Update main docs index** (`docs/README.adoc`):
   - Add link to new guide

=== For Refactoring

1. **Update module README** to reflect new structure
2. **No need to update top-level docs** if external behavior unchanged
3. **Update if API changes** affect user-facing guides

== Migration from Old Structure

=== Consolidation Steps

1. **Identify Duplicates**: Find content in both `docs/` and code comments
2. **Move to Module READMEs**: Implementation details go to `src/*/README.adoc`
3. **Simplify Top-Level**: Keep only user-facing content in `docs/`
4. **Add Cross-References**: Link top-level docs to module docs
5. **Remove Redundancy**: Delete duplicate content

=== Completed Migrations
