= Hybrid Fusion Strategies
:toc: auto
:toclevels: 2

ProximaDB's hybrid search combines BM25 full-text scores with vector
similarity scores via a configurable fusion strategy. This guide describes
which strategy to choose and why.

== Default: Reciprocal Rank Fusion (RRF)

RRF is the **default** and the recommended starting point for production
workloads.

* Robust to differences in score scale between BM25 and vector search.
* Best on relevance metrics (nDCG@10, MRR) on the TREC-COVID benchmark
  (paper-reported nDCG@10 = 0.828, +6.1% over dense-only, +14.9% over
  sparse-only — best of 6 configurations evaluated; arXiv:2604.13728).
* Single tunable parameter `k` (default 60) — rarely needs adjustment.

If you have no preference, use RRF.

== Alternative: Projection Fusion (B5)

Projection Fusion projects normalized BM25 + vector scores onto a unit
vector parameterized by `theta = alpha * pi/2`:

[source]
----
score = bm25_norm * cos(theta) + vector_norm * sin(theta)
----

When to choose Projection over RRF:

* You need **lower fusion latency** at the per-query critical path.
* You want **higher result diversity** (lower intra-list redundancy).

When NOT to choose it:

* You're optimizing for peak relevance — the same paper that introduced B5
  reports RRF as the relevance winner on TREC-COVID. Projection is a
  speed/diversity tradeoff, not a quality upgrade.

Tunable parameters:

|===
| Parameter | Default | Effect

| `alpha`
| `0.5`
| `0.0` = pure BM25, `1.0` = pure vector. `0.5` blends evenly.
|===

== Other Strategies

[cols="2,1,4", options="header"]
|===
| Strategy | Default? | When to use

| `weighted_linear`
| No
| You have empirical weights from offline tuning (`alpha` parameter).

| `rank_biased_precision`
| No
| Top-of-list relevance matters disproportionately.

| `borda_count`, `comb_sum`, `comb_min`, `comb_max`
| No
| Classical ensemble baselines for comparison.

| `condorcet`
| No
| Small result sets only; O(n²) pairwise.

| `dempster_shafer`
| No
| Evidence-theoretic combination with belief masses.

| `adaptive`
| No
| Selects between RRF and weighted-linear based on observed result overlap.
|===

== Selecting via REST (canonical fusion surfaces)

All cross-modal ranking in ProximaDB routes through one shared `FusionService`.
The vector `/search` surface, the dense+BM25 hybrid, and the tri-modal
`fusion-search` route are all instances of the same calibrated, `oid`-keyed
fusion engine -- per-surface fusion is intentionally avoided (see
link:../12-design/SEARCH_SURFACE_CONTRACT_2026_06_24.adoc[Search Surface Contract]).

The canonical place to exercise the strategies above end-to-end is the v2 graph
fusion-search route, which seeds from a vector ANN, expands over the graph, and
-- when `text_query` is supplied -- merges a BM25 document leg by shared `oid`:

[source,bash]
----
# Tri-modal fusion (vector + graph + BM25), RRF fallback
curl -X POST http://localhost:5678/api/v2/graphs/topology/fusion-search \
  -H "Content-Type: application/json" \
  -d '{
    "vector_collection": "products",
    "query_vector": [0.1, 0.2, 0.3],
    "text_query": "laptop",
    "limit": 10,
    "max_depth": 1,
    "rrf": true
  }'

# Omit text_query for vector+graph-only fusion; tune vector_weight / graph_weight
# / document_weight to bias a modality, or set rrf:false for PIT-calibrated linear.
----

NOTE: The older `POST /api/v1/hybrid/search` route (dense+BM25 with an explicit
`fusion_strategy` selector) is retained as a *deprecated compatibility alias*
only -- new clients should target the v2 fusion surfaces above. The removed
`/api/v1/experimental/hybrid/search` mock route (deleted 2026-05-26) is gone, and
its `/strategies` listing was never re-mounted. The supported strategy names are
the `FusionStrategy` enum at `src/core/search/hybrid/strategies.rs`, reproduced
below in "Selecting via Python SDK". See
link:../SUPPORTED_SURFACE.adoc[SUPPORTED_SURFACE] for the current gRPC parity
status of hybrid retrieval.

== Selecting via Python SDK

[source,python]
----
from proximadb_sdk.hybrid import FusionStrategy

# Default: relevance-optimal
strategy = FusionStrategy.RRF

# Tradeoff: faster + more diverse
strategy = FusionStrategy.PROJECTION
----

== Benchmarking

The repository ships a Criterion harness comparing fusion strategies on
synthetic data:

[source,bash]
----
cargo bench --bench bench_21_hybrid_search_fusion
----

The `fusion_rrf_vs_projection` group reports head-to-head latency for input
sizes 50/100/500/1000. Quality benchmarks against labeled IR datasets
(MS MARCO, BEIR scifact) are tracked under
`docs/10-quality/TECHNICAL_DEBT.adoc` TD-044 and not yet in tree.
