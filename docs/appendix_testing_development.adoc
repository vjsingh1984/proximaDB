== Testing Strategy

**Test Coverage**: Core services 550+ tests (98%), storage engines 450+ tests (95%), API handlers 280+ tests (92%), Python SDK 180+ tests (72%). **Total**: 1,460+ tests with 100% pass rate (0 failures).

**Unit Tests**: `cargo test --lib` for all, `cargo test storage::engines::sst` for specific modules, `cargo test -- --nocapture` for output.

**Integration Tests**: `cargo test --test '*'` for all, `cargo test --test vector_operations` for specific tests, `cargo test --release` for faster execution.

**Python SDK Tests**: `pytest tests/ -v` for testing, `pytest tests/ --cov=proximadb --cov-report=html` for coverage.

== Development Workflow

**Setup**: Clone repository, install Rust stable, cargo-watch, cargo-tarpaulin. Setup Python with `pip install -e ".[dev]"`.

**Development Server**: Use `cargo watch -x 'run --bin proximadb-server'` for auto-restart, `RUST_LOG=debug` for debug logging, `--config dev.toml` for custom config.

**Code Quality**: `cargo fmt` for formatting, `cargo clippy -- -D warnings` for linting, `cargo audit` for dependency checks.

== Debugging Guide

**Debug Logging**: Set `log_level = "debug"` in config.toml or use `RUST_LOG=proximadb=debug,tower_http=debug`.

**Memory Issues**: Use `valgrind --leak-check=full` for memory leak detection.

**Performance Issues**: Use `perf record/report` for CPU profiling, `cargo flamegraph` for flame graphs.

== Recent Development Achievements (August 2025)

=== Hardware Capabilities Centralization

**Implementation**: Complete centralization of hardware detection into `src/core/hardware_capabilities.rs` with global `OnceLock` access pattern.

[source,rust]
----
// Before: Duplicated detection in multiple modules
let cpu_features = detect_cpu_features(); // Repeated overhead

// After: Centralized once at startup
initialize_hardware_capabilities_default()?;
let caps = get_hardware_capabilities(); // Zero overhead access
----

**Benefits**:
- **Performance**: Single detection (10-50ms) vs repeated calls
- **Consistency**: All modules use same hardware profile
- **Thread Safety**: Lock-free concurrent access after initialization
- **Testing**: Deterministic hardware setup for tests

**Test Infrastructure**: Added `setup_hardware_capabilities()` pattern to all test modules, ensuring consistent hardware state across 1,460+ tests with 100% pass rate.

=== Advanced SQL Processing Acceleration

**GPU-Accelerated SQL Parser** (`src/query/sql_engine/gpu_parser.rs`):
- **Multi-GPU Support**: CUDA, ROCm, MPS (Apple), OpenCL backends
- **Intelligent Fallback**: GPU tokenization + CPU grammar parsing
- **Performance Tracking**: Statistics for GPU vs CPU parsing ratios
- **Complex Query Support**: Handles `VECTOR_SIMILARITY` with array literals

[source,rust]
----
// GPU-accelerated parsing with fallback
let query = parse_sql_gpu("SELECT * FROM collection 
    ORDER BY VECTOR_SIMILARITY(vector, [0.1, 0.2], 'cosine')")?;

=== Development Best Practices Established

**Hardware Integration Pattern**:
1. **Startup Initialization**: Call `initialize_hardware_capabilities_default()`
2. **Global Access**: Use `get_hardware_capabilities()` throughout application
3. **Capability Checks**: Use `caps.has_*()` methods for feature detection
4. **Graceful Degradation**: Always provide CPU fallbacks

**Testing Pattern**:
[source,rust]
----
static INIT: Once = Once::new();

fn setup_hardware_capabilities() {
    INIT.call_once(|| {
        let _ = initialize_hardware_capabilities_default();
    });
}

#[test]
fn test_hardware_feature() {
    setup_hardware_capabilities();
    // Test implementation
}
----
