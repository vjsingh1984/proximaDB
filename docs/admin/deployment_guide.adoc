= Multi-Disk Configuration Guide
:toc: left
:toclevels: 2
:imagesdir: ../diagrams/images

**Leverage multiple disks for improved performance, scalability, and fault tolerance.**

image::multi-disk-deployment-detail-modular.svg[Multi-Disk Architecture, width=800]

== Key Benefits

* *Parallel I/O*: Distribute I/O operations across multiple disks to improve throughput.
* *Load Distribution*: Assign collections to different storage locations based on weight or other strategies.
* *Fault Tolerance*: Isolate disk failures to a subset of collections.
* *Multi-Cloud*: Use a combination of local and cloud storage for a hybrid deployment.

== Storage Assignment

=== Collection-Level Assignment
Each collection is assigned to a single storage location at creation time. This can be done automatically by the system or specified by the user.

* *Automatic*: The system selects a storage location based on the configured assignment strategy.
* *User-Specified*: The user can specify a `storage_location` when creating a collection.
* *Unified*: The Write-Ahead Log (WAL), data, and indexes for a collection are all stored together in the same location.

== Configuration

=== Basic Multi-Disk Setup
To configure multiple storage locations, add a `[[storage.storage_locations]]` table for each location in your `config.toml` file.

[source,toml]
----
[storage]
metadata_url = "file:///data/disk1/metadata"

[[storage.storage_locations]]
url = "file:///data/disk1/proximadb"  # NVMe
weight = 3  # Higher weight means more likely to be selected
tags = ["fast", "nvme"]

[[storage.storage_locations]]
url = "file:///data/disk2/proximadb"  # SSD
weight = 2
tags = ["ssd"]

[[storage.storage_locations]]
url = "file:///data/disk3/proximadb"  # HDD
weight = 1
tags = ["capacity"]

[storage.assignment_config]
strategy = "weighted"  # Options: "random", "weighted", "hash", "roundrobin"
affinity = true       # Keep all data for a collection in the same location
----

=== Cloud Storage
ProximaDB supports AWS S3, Azure Blob Storage, and Google Cloud Storage.

==== AWS S3
[source,toml]
----
[[storage.storage_locations]]
url = "s3://my-bucket/proximadb"
weight = 1
aws_use_iam_role = true
----

==== Azure Blob Storage
[source,toml]
----
[[storage.storage_locations]]
url = "adls://myaccount.dfs.core.windows.net/proximadb"
use_managed_identity = true
----

==== Google Cloud Storage
[source,toml]
----
[[storage.storage_locations]]
url = "gcs://my-bucket/proximadb"
use_workload_identity = true
----

== Deployment Scenarios

=== Development
For development, you can use a single local directory.

[source,toml]
----
[[storage.storage_locations]]
url = "file:///tmp/proximadb/storage"
weight = 1
----

=== Production On-Premises
For production on-premises deployments, you can use a combination of fast and slow disks.

[source,toml]
----
[[storage.storage_locations]]
url = "file:///mnt/nvme1/proximadb"
weight = 3
tags = ["nvme", "primary"]

[[storage.storage_locations]]
url = "file:///mnt/sata1/proximadb"
weight = 1
tags = ["capacity", "archive"]
----

=== Hybrid Cloud
For hybrid cloud deployments, you can use a combination of local and cloud storage.

[source,toml]
----
[[storage.storage_locations]]
url = "file:///mnt/nvme1/proximadb"
weight = 5  # Prefer local storage
tags = ["local", "hot"]

[[storage.storage_locations]]
url = "s3://proximadb-storage/collections"
weight = 1  # Use cloud storage for cold data
tags = ["cloud", "cold"]
----

== Performance Tuning

=== Disk Types
ProximaDB can take advantage of different disk types to optimize performance.

* *NvmeSsd*: Up to 100,000 IOPS.
* *SataSsd*: Up to 50,000 IOPS.
* *Hdd*: Up to 1,000 IOPS.
* *NetworkStorage*: ~5ms latency.

=== Optimization Tips
* For NVMe SSDs, you can increase the `max_iops` setting in the storage location configuration.
* For network storage, use a conservative capacity estimate.
* Set the `storage_full_threshold` to 95% for NVMe SSDs and 80% for network storage.

== Monitoring

You can monitor the health and usage of your storage locations using the following methods:

* *Health Check*: `curl http://localhost:5678/health`
* *Storage Usage*: `curl http://localhost:5678/admin/storage/usage`
* *Disk Usage*: `df -h /path/to/disk`
* *I/O Statistics*: `iostat -x 1`

== Troubleshooting

=== Common Issues
* *Permissions*: Check the file permissions of the storage directories using `ls -la`.
* *URL Format*: Make sure you are using the correct URL format (`file:///` for local files).
* *Disk Failure*: If a disk fails, you can replace it at the same mount point.
* *Performance*: Use `iostat` and `iotop` to identify I/O bottlenecks.

== Best Practices

* Use consistent path conventions for your storage locations.
* Use separate configuration files for each environment (development, staging, production).
* Regularly check the health of your disks using SMART tools.
* Plan for capacity and do not let your disks get more than 80% full.
* Enable encryption at rest for sensitive data.
* Test your backup and recovery procedures regularly.

== URL Schemes

* *Local*: `file:///path/to/directory`
* *AWS S3*: `s3://bucket/prefix`
* *Azure Blob Storage*: `adls://account.dfs.core.windows.net/container`
* *Google Cloud Storage*: `gcs://bucket/prefix`
