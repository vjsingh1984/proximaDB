==== Performance Inversion Analysis

**1536D Deep Clone Breakdown:**

1. **Memory copy:** 1536 × 4 bytes = 6144 bytes
2. **M4 Pro bandwidth:** ~300 GB/s theoretical
3. **Expected copy time:** 6144 / 300×10^9 = 20.5ns
4. **Actual time:** 4.10µs
5. **Overhead:** 4.10µs - 20.5ns = 4.08µs (protocol buffer serialization)

**1536D Arc Clone Breakdown:**

1. **Arc allocation:** ~500ns (estimated)
2. **Reference count increment:** ~50ns × 1536 elements = 76.8µs
3. **Actual time:** 51.92µs
4. **Analysis:** Per-element reference counting overhead dominates

**Root Cause Hypothesis:**

```rust
// VectorRecord: Single memcpy
memcpy(dest, src, 1536 * 4);  // 6144 bytes → 4.10µs

// OptimizedRecord: Per-field Arc increment
for field in 0..1536 {
    Arc::clone(&self.vector[field]);  // 50ns × 1536 = 76.8µs
}
```

Arc overhead exceeds memcpy cost when:
```
n × arc_increment_cost > memcpy_size / bandwidth
n × 50ns > (n × 4 bytes) / 300×10^9
n > (4 / 300×10^9) / 50×10^-9
n > 26.67 elements  ← Very low threshold!
```

**Actual crossover at 1536 suggests:**
- Protobuf serialization overhead (4µs) masks true memcpy cost
- Arc implementation may have per-vector overhead, not per-element
- Need profiling to determine exact bottleneck

==== Strategy Selection Algorithm

**Empirical Decision Tree:**

[source,rust]

pub fn select_aggregation_strategy(n: usize, k: usize) -> AggregationStrategy {
    let ratio = k as f64 / n as f64;

    match (n, k, ratio) {
        // Small sets: sort is fastest due to low overhead
        (_, _, _) if n < 500 => AggregationStrategy::Sort,

        // Large sets with small k: heap dominates
        (_, _, r) if n >= 1000 && r < 0.1 => AggregationStrategy::Heap,

        // Medium ratio: partial sort optimal
        (_, _, r) if r >= 0.1 && r < 0.3 => AggregationStrategy::PartialSort,

        // High ratio: full sort unavoidable
        _ => AggregationStrategy::Sort,
    }
}

==== Performance Anomaly: Heap at n=1000, k=100

**Observation:**
```
Partial Sort: 36.59µs
Heap Select:  136.05µs  ← 3.7x SLOWER
Expected:     Heap should be faster
```

**Analysis:**

BinaryHeap overhead breakdown:
```rust
// Heap operations per element
for each of 1000 elements {
    if heap.len() < k {
        heap.push(element);        // O(log k) = log(100) ≈ 6.6 ops
    } else if element > heap.peek() {
        heap.pop();                // O(log k) = 6.6 ops
        heap.push(element);        // O(log k) = 6.6 ops
        // Total: 13.2 ops per comparison
    }
}

Total ops: 1000 × 13.2 = 13,200 operations
Time per op: 136.05µs / 13,200 = 10.3ns
```

vs. Partial Sort:
```rust
// Quicksort partition to k=100
// Expected: O(n + k log k) = 1000 + 100×6.6 = 1,660 ops
Time per op: 36.59µs / 1,660 = 22ns
```

**Root Cause:** BinaryHeap per-element overhead (10.3ns) includes:
- Heap structure maintenance
- Comparison function calls
- Branch mispredictions
- Memory allocations for heap growth

**Recommendation:** Use partial_sort when k/n > 0.05 and n < 5000.

==== Sparsity Optimization Analysis

**Why L2 Benefits Most:**

[source,rust]
----
// Dense L2 (1024 ops)
for i in 0..1024 {
    let diff = v1[i] - v2[i];
    sum += diff * diff;
}

// Sparse L2 with 90% zeros (103 ops)
for i in non_zero_indices {  // Only ~103 indices
    let diff = v1[i] - v2[i];
    sum += diff * diff;
}
// Speedup: 1024/103 = 9.94x theoretical
// Actual: 2.68x (branch overhead, index lookup)
----

**Why Cosine Fails:**

[source,rust]
----
// Sparse Cosine Similarity
let dot = sparse_dot_product(v1, v2);    // Fast with sparse
let norm1 = sparse_l2_norm(v1);          // SLOW: Must check all dims
let norm2 = sparse_l2_norm(v2);          // SLOW: Must check all dims
let similarity = dot / (norm1 * norm2);

// Problem: Norm requires checking all 1024 dimensions
// even though only ~103 are non-zero
----

**Branch Prediction Impact at 99% Sparsity:**

```
Probability of non-zero: 1%
Branch misprediction cost: ~20 cycles
Mispredictions per 1024 elements: ~512 (50%)
Total cost: 512 × 20 = 10,240 cycles
At 3.75 GHz: 10,240 / 3.75×10^9 = 2.73µs overhead

Observed overhead: 1.479ms - 41.92µs = 1.437ms
Analysis: Severe cache misses + branch penalties
```

==== Recommendations

**Sparsity-Aware Distance Selection:**

[source,rust]
----
pub fn select_distance_kernel(
    v1_sparsity: f32,
    v2_sparsity: f32,
    metric: DistanceMetric,
) -> DistanceKernel {
    let avg_sparsity = (v1_sparsity + v2_sparsity) / 2.0;

    match (metric, avg_sparsity) {
        // Cosine similarity: avoid for sparse vectors
        (DistanceMetric::Cosine, s) if s > 0.5 => {
            warn!("Cosine similarity {:.0}% slower for {}% sparse vectors",
                  (s * 100.0), (s * 100.0));
            DistanceKernel::DenseNormalized
        },

        // L2 distance: use sparse kernel for 50-90% sparsity
        (DistanceMetric::L2, s) if s >= 0.5 && s <= 0.9 => {
            DistanceKernel::SparseL2  // 2-3x faster
        },

        // Extreme sparsity (>90%): use dense kernel to avoid branches
        (_, s) if s > 0.9 => {
            DistanceKernel::DenseSIMD  // Better branch prediction
        },

        // Dense or mildly sparse: standard kernel
        _ => DistanceKernel::DenseSIMD,
    }
}
----

**Expected Impact:**
- L2 distance: 2-3x faster for 50-90% sparse vectors
- Cosine: Avoid 35x degradation for sparse data
- Recommendation: Use L2 or dot product for sparse embeddings

Break-even when: parallel_overhead = sequential_time - parallel_time

Let w = work per item (µs)
Let n = number of items

Sequential: n × w
Parallel: (n × w / num_threads) + o

Break-even: n × w = (n × w / 8) + 1060
           n × w × (7/8) = 1060

For w = 1µs: n = 1211 items
For w = 5µs: n = 242 items

Observed: n ≈ 5000 (parallel converges)

==== Recommendations

**Intelligent Batch Processing:**

[source,rust]
----
pub struct BatchConfig {
    pub parallel_threshold: usize,     // 5000
    pub prealloc_threshold: usize,     // 100
    pub rayon_chunk_size: usize,       // 1000
}

impl BatchConfig {
    pub fn process<T, F>(&self, items: &[T], process_fn: F) -> Vec<Result<T>>
    where
        F: Fn(&T) -> Result<T> + Sync,
    {
        let n = items.len();

        // Preallocate buffer for known size
        let mut results = Vec::with_capacity(n);

        if n >= self.parallel_threshold {
            // Large batch: Use Rayon with optimal chunk size
            results = items
                .par_chunks(self.rayon_chunk_size)
                .flat_map(|chunk| chunk.iter().map(&process_fn))
                .collect();
        } else {
            // Small/medium batch: Sequential processing
            for item in items {

[source,rust]

// Adjust for clock speed and IPC
fn normalize_single_thread(
    m4_time: f64,
    target_clock: f64,
    target_ipc: f64,
) -> f64 {
    let m4_clock = 3.75;  // GHz
    let m4_ipc = 1.0;     // Relative

    let clock_factor = m4_clock / target_clock;
    let ipc_factor = m4_ipc / target_ipc;

    m4_time * clock_factor * ipc_factor
}

// Example: Intel Xeon @ 2.5 GHz, IPC=1.15
// Arc clone 97.29ns on M4 Pro

// = 97.29 × (3.75/2.5) × (1.0/1.15)
// = 97.29 × 1.5 × 0.87
// = 126.9ns

==== Parallel Processing

[source,rust]
----
// Adjust for core count and memory bandwidth
fn normalize_parallel(
    m4_time: f64,
    target_cores: usize,
    target_bandwidth_gbps: f64,
) -> f64 {
    let m4_cores = 10;  // Performance cores
    let m4_bandwidth = 300.0;

    // Amdahl's law with 95% parallelizable portion
    let parallel_fraction = 0.95;
    let serial_time = m4_time * (1.0 - parallel_fraction);
    let parallel_time = m4_time * parallel_fraction;

    let core_speedup = (target_cores as f64 / m4_cores as f64).min(
        target_bandwidth_gbps / m4_bandwidth
    );

    serial_time + (parallel_time / core_speedup)
}

// Example: AMD EPYC 64 cores @ 200 GB/s
// Parallel batch 1.635ms on M4 Pro
let epyc_time = normalize_parallel(1635.0, 64, 200.0);
// core_speedup = min(64/10, 200/300) = min(6.4, 0.67) = 0.67 (BW limited)
// serial = 1635 × 0.05 = 81.75µs
// parallel = 1635 × 0.95 / 0.67 = 2317.5µs
// total = 2399.25µs (slower due to BW bottleneck)
----

=== Issue #2: Heap Select Anomaly at k/n=0.1

**Status:** 🟡 MEDIUM - Requires investigation

**Impact:** 3.7x slower than partial sort for k=100, n=1000

2. Comparison function overhead

**Proposed Solutions:**

**Option A: Custom Fixed-Capacity Heap**

[source,rust]
----
pub struct FixedHeap<T> {
    data: Vec<T>,
    capacity: usize,
    comparator: fn(&T, &T) -> Ordering,
}

impl<T> FixedHeap<T> {
    pub fn new(capacity: usize, comparator: fn(&T, &T) -> Ordering) -> Self {
        Self {
            data: Vec::with_capacity(capacity),
            capacity,
            comparator,
        }
    }

    pub fn push(&mut self, item: T) {
        if self.data.len() < self.capacity {
            self.data.push(item);
            self.bubble_up(self.data.len() - 1);
        } else if (self.comparator)(&item, &self.data[0]) == Ordering::Greater {
            self.data[0] = item;
            self.bubble_down(0);
        }
    }
}
----
