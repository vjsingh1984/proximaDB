= Memory Pool Quick Reference
:doctype: article
:icons: font

[abstract]
--
Quick reference for ProximaDB memory pool configuration and tuning on Apple M4 Pro (ARM64).
Based on comprehensive benchmarks showing **97-98% cache hit rates** with optimized settings.
For detailed analysis, see link:MEMORY_POOL_ANALYSIS.adoc[Memory Pool Benchmark Analysis].
--

== TL;DR (Apple M4 Pro)

[cols="2,3"]
|===
|**Recommended Default** |`pool_size=64`, `growth_factor=2.0`, `enable_stats=true`
|**Cache Hit Rate** |**97-98%** (pool_size=64: 98.6%)
|**Memory Usage** |~4MB per pool type, ~16MB total
|**Stats Overhead** |~4% (+2µs) - acceptable for production monitoring
|**Concurrency** |⚠️  **CONTENTION DETECTED** - Slower with more threads
|**Thread Recommendation** |**Single-threaded** or investigate lock contention
|===

== Configuration Presets

=== Optimal (Recommended for M4 Pro) ⭐

[source,toml]
----
[memory.pool]
vector_buffer_pool_size = 64        # ~4MB - 98.6% hit rate
serialization_buffer_pool_size = 64 # 4MB
compression_buffer_pool_size = 64   # 2MB
metadata_buffer_pool_size = 64      # ~256KB
growth_factor = 2.0                 # Best balance: 4 grows to steady state
max_pool_size = 1024                # ~64MB cap per pool type
enable_stats = true                 # Only 4% overhead
----

**Use when**: Apple M4 Pro systems, most production workloads
**Performance**: 97-98% hit rate, 2.45 Melem/s throughput
**Memory**: ~16MB total footprint

=== Memory-Constrained

[source,toml]

**Use when**: Limited memory environments, embedded systems

=== High-Throughput

[source,toml]
----
[memory.pool]
vector_buffer_pool_size = 256       # 1MB
serialization_buffer_pool_size = 256 # 16MB
compression_buffer_pool_size = 256  # 8MB
metadata_buffer_pool_size = 256     # 1MB
growth_factor = 2.0
max_pool_size = 1024

----

**Use when**: High concurrency (16+ threads), burst workloads

== Monitoring Checklist (M4 Pro)

✅ **Enable stats** in production (`enable_stats = true`) - only 4% overhead

✅ **Track hit rate** - Alert if <95% (target: 97-98%)

✅ **Monitor pool growth** - Alert if >15 events in steady state

✅ **Watch peak outstanding** - Alert if >500 (memory pressure)

✅ **Track acquisition latency** - Alert if >1ms (contention detected)

⚠️  **Avoid concurrent access** - Benchmarks show 14-550% slowdown with multiple threads (lock contention)

== Troubleshooting

[cols="2,3,2"]
|===
|Symptom |Cause |Solution

|Low hit rate (<95%)
|Pool too small or improper sizing
|Increase `initial_size` to 64+ (M4 Pro optimal)

|Frequent growth events
|Pool exhausted
|Increase `initial_size` or `growth_factor`

|High memory usage
|Pool too large
|Decrease `initial_size`

|Poor concurrent scaling
|Lock contention (confirmed in benchmarks)
|⚠️  Use single-threaded access or investigate pool implementation
|===

----

rate(proximadb_pool_acquisitions_total[5m])

rate(proximadb_pool_grows_total[1h])

# Peak size vs initial
proximadb_pool_peak_size - on(buffer_type) proximadb_pool_initial_size

== When to Adjust Pool Size

[cols="3,2"]
|===
|Scenario |Action

|Hit rate <80%
|Increase by 2x

|Pool grows >10/hour
|Increase by 1.5x

|Memory pressure
|Decrease by 0.5x

|Concurrency >8 threads
|Use pool_size=256

|Burst workloads
|Increase `max_pool_size`
|===
