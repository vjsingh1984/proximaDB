=== IndexConfig Flow Implementation

The sequence diagram shows how IndexConfig flows through the system:

[source,mermaid]
----
sequenceDiagram
    participant Client
    participant REST
    participant CS as CollectionService
    participant AM as AxisManager
    participant HNSW as HNSW Index
    participant IVF as IVF Index
    
    Note over Client,IVF: Collection Creation with IndexConfig
    Client->>REST: POST /collections (with IndexConfig)
    REST->>CS: create_collection(config)
    CS->>CS: apply_smart_defaults(IndexConfig)
    CS->>CS: store_collection_metadata(with IndexConfig)
    CS->>AM: set_collection_service(self)
    REST-->>Client: Collection created
    
    Note over Client,IVF: Index Build Operation
    Client->>REST: POST /vectors (insert vectors)
    REST->>VectorService: insert_vectors()
    VectorService->>StorageEngine: flush()
    StorageEngine->>AM: notify_new_vectors(collection_id, vectors)
    AM->>CS: get_collection_index_config(collection_id)
    CS-->>AM: IndexConfig
    
    alt IndexConfig.update_mode == Synchronous
        AM->>HNSW: build_index_sync(vectors, hnsw_config)
        HNSW-->>AM: Index built
        AM-->>VectorService: Index build complete
    else IndexConfig.update_mode == Asynchronous
        AM->>AM: spawn_async_task()
        AM-->>VectorService: Index build scheduled
        AM->>IVF: build_index_async(vectors, ivf_config)
        IVF-->>AM: Index built
    else IndexConfig.update_mode == Hybrid
        AM->>AM: evaluate_batch_size()
        alt Small batch
            AM->>HNSW: build_index_sync(vectors, hnsw_config)
        else Large batch
            AM->>IVF: build_index_async(vectors, ivf_config)
        end
    end
    
    Note over Client,IVF: Index Config Update
    Client->>REST: PUT /collections/{id}/index_config
    REST->>CS: update_collection_index_config(id, new_config)
    CS->>CS: validate_and_store(new_config)
    CS->>CS: invalidate_cache(collection_id)
    CS-->>REST: Config updated
    REST-->>Client: Success
----

== Architecture Summary

The ProximaDB architecture demonstrates several key innovations:

=== Key Architectural Principles

. **Separation of Concerns**: IndexConfig handling moved from storage engines to AXIS where it belongs
. **Unified Interfaces**: Consistent APIs across different storage and index engines
. **Pluggable Components**: Modular design allowing different backends and algorithms
. **Smart Defaults**: Automatic configuration based on collection characteristics
. **Flexible Configuration**: Per-collection settings with algorithm-specific parameters

=== IndexConfig Integration Benefits

. **Proper Architecture**: Storage engines focus on storage, AXIS handles indexing
. **Consistent Configuration**: Single source of truth for index settings
. **Dynamic Adaptation**: Index builds can be synchronous, asynchronous, or hybrid
. **Performance Optimization**: Smart defaults based on collection size and vector dimension
. **Maintainable Code**: Clear separation of responsibilities

This architecture provides a solid foundation for the next phases of ProximaDB development while maintaining clean separation of concerns and extensibility.
