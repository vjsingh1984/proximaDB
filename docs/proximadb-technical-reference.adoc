== Introduction

ProximaDB is a high-performance vector database built with Rust, featuring:

* **Optimized write throughput** with batched operations
* **Low-latency** search capabilities
* **Unified architectures** reducing code duplication
* **Dual storage engines** for different workload types

image::proximadb-unified-architecture.svg[ProximaDB Architecture Overview, width=100%]

=== Key Features

* **Proto-First Design**: Zero serialization overhead
* **Dual Storage Engines**: SST (row-based) and VIPER (columnar)
* **Direct Vector Service**: 40-60% latency reduction
* **Unified Architectures**: Consistent APIs across all components
* **Enterprise Ready**: Multi-cloud support, monitoring, security

=== Design Principles

1. **Single Responsibility**: Each component does one thing well
2. **Direct Access**: No unnecessary indirection or registries
3. **Atomic Operations**: All writes use UnifiedAtomicCoordinator
4. **Clean Separation**: Clear boundaries between components
5. **Performance First**: Optimized for real-world workloads

* Single business logic implementation

== Core Components

=== DirectVectorService

The DirectVectorService provides direct memtable access, eliminating unnecessary abstraction layers:

[source,rust]
----
pub struct DirectVectorService {
    storage_engines: HashMap<String, Arc<dyn StorageEngine>>,
    wal_manager: Arc<WalManager>,
    collection_service: Arc<CollectionService>,
}
----

Features:
* **Direct memtable access**: Reduces overhead by eliminating abstraction layers
* **Engine-specific routing**: Routes operations to appropriate storage engine
* **Collection-aware**: Operations consider collection configuration
* **Explicit configuration**: No hidden defaults

image::direct-vector-service.svg[Direct Vector Service Architecture, width=80%]

=== Storage Engines

==== SST Engine

The Log-Structured Merge (SST) engine provides:

* **Atomic compaction**: ACID guarantees via staging
* **Metadata filtering**: Block-level statistics
* **Manifest tracking**: Centralized SSTable registry
* **Unified bloom filters**: Polymorphic design

[source,rust]
----
pub struct LsmEngine {
    memtable: Arc<dyn UnifiedMemtable>,
    manifest: Arc<LsmManifest>,
    atomic_coordinator: Arc<UnifiedAtomicCoordinator>,
    bloom_filter: Arc<dyn BloomFilterStrategy>,
}
----

==== VIPER Engine

The Vectorized Parquet Engine provides:

* **Columnar storage**: Optimized for analytics
* **Predicate pushdown**: Filter at storage level
* **ML clustering**: Locality-preserving organization
* **Quantization support**: Reduced memory footprint

=== WriteBuffer Architecture

The Write-Ahead Log system features clean separation of concerns:

image::write-buffer-strategy-pattern.svg[WriteBuffer Strategy Pattern, width=100%]

Components:
* **WalManager**: Orchestration only
* **SerializationStrategies**: Format conversion
* **MemtableManager**: Memory operations
* **DiskManager**: I/O operations
* **RecoveryManager**: Recovery logic

Features:
* Batched write operations for improved throughput
* Optimized serialization reducing latency
* Parallel recovery for faster startup

== Unified Architectures

=== Bloom Filter Design

ProximaDB uses a unified polymorphic bloom filter design:

image::bloom-filter-architecture.svg[Bloom Filter Architecture, width=80%]

[source,rust]
----
pub trait BloomFilterStrategy: Send + Sync {
    fn insert(&mut self, key: &[u8]);
    fn might_contain(&self, key: &[u8]) -> bool;
    fn serialize(&self) -> Result<Vec<u8>>;
    fn false_positive_rate(&self) -> f64;
}
----

Strategies:
* **ByteAligned**: SSTable optimized
* **BitPacked**: Memory efficient
* **Simple**: Fast for small datasets
* **Composite**: Metadata filtering
* **NoOp**: Disabled

=== Unified Storage Engine

All storage engines implement a common interface:

[source,rust]
----
pub trait UnifiedStorageEngine: Send + Sync {
    fn engine_name(&self) -> &str;
    fn flush(&self, params: FlushParameters) -> Result<FlushResult>;
    fn compact(&self, params: CompactionParameters) -> Result<()>;
    fn search(&self, query: SearchQuery) -> Result<Vec<SearchResult>>;
}
----

Benefits:
* Consistent API across engines
* Easy to add new engines
* Shared infrastructure
* Simplified testing
