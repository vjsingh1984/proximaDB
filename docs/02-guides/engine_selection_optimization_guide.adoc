==== NOVA vs VIPER: Columnar Architecture Differences

Both NOVA and VIPER are columnar engines using Parquet format, but with critical architectural differences:

.Parquet Row Group Architecture
[cols="3,4,4", options="header"]
|===
| Feature | VIPER (Standard Parquet) | NOVA (Parquet + Sidecar)

| **Row Group Size**
| 50,000 vectors (configurable)
100,000 for compacted files
| 50,000 vectors per row group
10-20 row groups per SuperBlock

| **Metadata Structure**
| Standard Parquet footer only:
- Row group offsets
- Column min/max statistics
- Optional bloom filters
| Standard Parquet PLUS .nova_meta sidecar:
- SuperBlock aggregations
- Enhanced zone maps
- Hierarchical statistics

| **Pruning Strategy**
| Single-level row group pruning
Linear scan of row group metadata
| Two-level hierarchical pruning:
1. SuperBlock level (70% elimination)
2. Row group level (90% elimination)

| **File Access Pattern**
| Direct row group access via offsets
Cached footer metadata (~8KB)
| Same Parquet access PLUS:
- Sidecar metadata preload
- SuperBlock-guided navigation

| **Statistics Collected**
| Per row group:
- Min/max per column
- Null counts
- Distinct counts
| Per row group AND SuperBlock:
- Vector centroids
- Variance per dimension
- L2 norm bounds
- Quantization selectivity

| **Query Optimization**
| Row group elimination based on predicates
Column projection
| Progressive search with early termination
Multi-dimensional zone map pruning
Cost-based SuperBlock selection

| **Implementation Status**
| ✅ Full StreamingParquetWriter
✅ Bloom filters on filterable columns
✅ Direct row group reads
| ✅ NovaMetadataCollector trait
✅ Sidecar .nova_meta generation
⚠️ TODO: Integration with flush/compact
|===

.How Row Groups Enable Efficient Access
****
**Standard Parquet (Both Engines):**

1. **Footer Metadata** (last ~8KB of file):
   - Contains all row group metadata
   - Byte offsets for direct seeking
   - Cached by ProximaDB for repeated access

2. **Direct Row Group Access**:
   ```
   File Layout:
   [Row Group 0: 100MB] [Row Group 1: 100MB] ... [Footer: 8KB]

   To read Row Group 1:
   - Read cached footer (or last 8KB if not cached)
   - Extract byte offset for Row Group 1
   - Seek directly to offset, read 100MB
   - No need to read Row Group 0
   ```

3. **Parallel Reading**:
   - Multiple row groups can be read concurrently
   - Each row group is independently decodable
   - Better I/O utilization for cloud storage

**NOVA's Additional Hierarchical Layer (Selective Queries Only):**

```
SuperBlock 0 (Row Groups 0-9):     ← 70% queries eliminated here
  ├── Aggregated zone map
  ├── Centroid and variance
  └── If matches, check individual row groups:
      ├── Row Group 0: Check statistics  ← 90% of remaining eliminated
      ├── Row Group 3: Check statistics
      └── Row Group 7: Check statistics

Result: Read only 3 of 100 row groups (97% I/O reduction)
```

.When NOVA Sidecar Metadata Is Used
[WARNING]
====
**Sidecar metadata is ONLY used for selective queries:**

* ✅ **Similarity search** (top-k queries): 70-97% pruning benefit
* ✅ **Filtered queries**: Metadata predicates eliminate row groups
* ✅ **Range queries**: Dimensional bounds enable pruning
* ❌ **Compaction**: Full scan reads all data, sidecar adds overhead
* ❌ **Full exports**: No pruning benefit when reading everything
* ❌ **Batch updates**: Sequential access faster without metadata

The sidecar `.nova_meta` files are automatically skipped during compaction and full scans to avoid unnecessary overhead.

==== Implementation Architecture

.NOVA Sidecar Metadata Integration
****
**File Structure on Disk:**
```
/data/collections/my_collection/nova/
├── data_001.parquet          # Standard Parquet file (VIPER-compatible)
├── data_001.nova_meta         # NOVA sidecar with SuperBlocks
├── data_002.parquet
├── data_002.nova_meta
└── ...
```

**MetadataCollector Integration (Implemented):**
```rust
use std::sync::Arc;
use proximadb::storage::engines::core::formats::columnar::{
    ParquetWriterConfig,
    parquet_write_engine::streaming_writer::StreamingWriterBuilder,
};
use proximadb::storage::persistence::filesystem::FilesystemFactory;

// During flush operation (src/storage/engines/impls/nova/engine.rs)
let config = ParquetWriterConfig::default();
let file_path = "/data/collections/my_collection/nova/data_001.parquet";

// Optionally, create a filesystem factory (local/cloud)
let filesystem_factory = Arc::new(FilesystemFactory::create_default().await?);

// Build an async streaming writer and attach the NOVA collector
let mut writer = StreamingWriterBuilder::new()
    .with_path(file_path)
    .with_dimension(768)
    .with_config(config)
    .with_filesystem_factory(filesystem_factory)
    .build()
    .await?;

writer = writer.with_metadata_collector(Box::new(
    NovaMetadataCollector::new(NovaCollectorConfig {
        row_groups_per_superblock: 10,
        compute_vector_stats: true,
        sample_rate: 0.1,
    })
));

// Collector gathers statistics during write
// No re-reading required - statistics collected inline
let (stats, collector) = writer.finalize().await?;

// Write sidecar file with collected metadata
if let Some(collector) = collector {
    let metadata_path = format!("{}.{}", file_path, collector.sidecar_extension());
    fs.write(&metadata_path, &collector.serialize_metadata()?).await?;
}
```

**Query Optimization Flow:**
```rust
// 1. Load sidecar metadata (cached after first read)
let nova_meta = NovaMetadata::load(&format!("{}.nova_meta", parquet_file))?;

// 2. SuperBlock-level pruning (coarse-grained)
let relevant_superblocks = nova_meta.superblocks
    .filter(|sb| sb.zone_map.overlaps_with_query(query_vector));

// 3. Row group-level pruning (fine-grained)
let row_groups_to_read = relevant_superblocks
    .flat_map(|sb| sb.row_groups)
    .filter(|rg| nova_meta.row_group_stats[rg].matches_predicate());

// 4. Direct Parquet row group access (with unified caching filesystem)
use proximadb::storage::persistence::filesystem::FilesystemFactory;
use proximadb::storage::persistence::filesystem::unified::UnifiedCachingFilesystem;
use proximadb::storage::engines::core::formats::columnar::columnar_query_engine::unified_reader::UnifiedParquetReader;
use std::sync::Arc;

let filesystem_factory = Arc::new(FilesystemFactory::create_default().await?);
let base_fs = filesystem_factory.get_filesystem("file://")?;
let cached_filesystem = Arc::new(UnifiedCachingFilesystem::new(
    base_fs,
    collection_id.clone(),
    "columnar".to_string(),
));

let reader = UnifiedParquetReader::new(
    vec![parquet_file.to_string()],
    /* dimension: */ 768,
    filesystem_factory.clone(),
    cached_filesystem,
    collection_id.clone(),
    "columnar".to_string(),
)?;

let results = reader
    .read_row_groups_projected(
        &collection_id,
        &row_groups_to_read.collect::<Vec<_>>(),
        Some(&projection_columns),
    )
    .await?;
```

=== HELIX Engine (Spatial Locality Optimization)

**Optimal Use Cases:**
- Geographic information systems
- Computer vision and image processing
- Multi-dimensional spatial data
- Scientific simulations with spatial patterns

**Technical Deep Dive:**
HELIX is a highly specialized engine optimized for spatial locality and multi-dimensional data patterns. It achieves this through a sophisticated multi-stage process:

1.  **Dimensionality Reduction with PCA**: High-dimensional vectors are first projected into a lower-dimensional space using Principal Component Analysis (PCA). This captures the most significant variance in the data, making the subsequent locality-preserving steps more effective.

2.  **Locality-Preserving with Hilbert Curve**: The lower-dimensional vectors are then mapped onto a 1D Hilbert curve. This ensures that vectors that are close in the multi-dimensional space are also close on the 1D curve, providing excellent spatial locality.

3.  **Spatial Optimization with Liquid Clustering**: This is the core of HELIX's spatial optimization. The engine monitors access patterns and spatial relationships to identify data with strong locality patterns. The liquid clustering mechanism then adaptively reorganizes the data, grouping spatially related vectors together. This ensures that spatially relevant data is physically co-located, leading to significant performance improvements for spatial queries.

```python
import time
from concurrent.futures import ThreadPoolExecutor

def benchmark_engine(engine_name, vector_count=10000):
    """Benchmark specific engine performance"""
    base_url = "http://localhost:5678"

    # Create collection with specific engine
    collection_data = {
        "name": f"benchmark_{engine_name.lower()}",
        "dimension": 768,
        "engine": engine_name
    }

    response = requests.post(f"{base_url}/v1/collections", json=collection_data)
    print(f"Created collection for {engine_name}: {response.status_code}")

    # Measure insert performance
    start_time = time.time()
    for i in range(vector_count):
        vector_data = {
            "vectors": [{
                "id": f"vec_{i}",
                "values": [0.1] * 768,  # Simple test vector
                "metadata": {"engine": engine_name, "batch": i // 1000}
            }]
        }
        requests.post(f"{base_url}/v1/collections/benchmark_{engine_name.lower()}/vectors",
                     json=vector_data)

    insert_time = time.time() - start_time
    insert_throughput = vector_count / insert_time

    print(f"{engine_name} Insert Performance:")
    print(f"  Throughput: {insert_throughput:.2f} vectors/sec")
    print(f"  Total time: {insert_time:.2f} seconds")

    # Measure query performance
    query_data = {
        "query_vector": [0.1] * 768,
        "top_k": 10
    }

    query_times = []
    for _ in range(100):  # 100 queries for average
        start_time = time.time()
        response = requests.post(f"{base_url}/v1/collections/benchmark_{engine_name.lower()}/search",
                               json=query_data)
        query_time = time.time() - start_time
        query_times.append(query_time * 1000)  # Convert to ms

    avg_query_time = sum(query_times) / len(query_times)
    p95_query_time = sorted(query_times)[int(len(query_times) * 0.95)]

    print(f"{engine_name} Query Performance:")
    print(f"  Average latency: {avg_query_time:.2f} ms")
    print(f"  P95 latency: {p95_query_time:.2f} ms")
    print()

if __name__ == "__main__":
    engines = ["SST", "SWIFT", "VIPER", "NOVA", "RAPTOR", "HELIX"]

    for engine in engines:
        print(f"Benchmarking {engine} Engine...")
        benchmark_engine(engine, vector_count=1000)  # Smaller dataset for testing
```

== **Best Practices Summary**

=== Engine Selection Checklist

**For Real-time Applications:**
- Use **SST** for high-throughput OLTP (200K+ vec/sec)
- Use **SWIFT** for ultra-low latency (<1ms)
- Configure adequate memory buffers
- Enable write-ahead logging for ACID compliance

**For Analytics Workloads:**
- Use **VIPER** for standard analytics (5K vec/sec)
- Use **NOVA** for advanced research (4K vec/sec, 90% compression)
- Optimize row group sizes for query patterns
- Enable column-level compression

**For Resource-Constrained Environments:**
- Use **VIPER** for efficient columnar compression
- Configure aggressive quantization
- Optimize row group sizes for memory efficiency
- Monitor memory usage and compression ratios

**For Variable/Unknown Workloads:**
- Use **RAPTOR** for adaptive optimization
- Enable P×K optimization and workload learning
- Configure reasonable adaptation intervals
- Monitor adaptation metrics

**For Spatial Data:**
- Use **HELIX** for spatial locality optimization
- Configure appropriate spatial grouping thresholds
- Enable liquid clustering for spatial patterns
- Optimize Hilbert curve order for data dimensionality

=== Performance Optimization Principles

1. **Match Engine to Workload**: Choose engine based on primary use case
2. **Monitor Key Metrics**: Track engine-specific performance indicators
