== Executive Summary

This guide provides step-by-step instructions for migrating from the legacy SKS (Semantic Knowledge Store) split storage architecture to the new graph-first architecture powered by Orion graph engine.

**Migration Benefits:**

* **Performance**: 3-6x faster entity operations (105K+ entities/sec)
* **Memory**: 21% reduction in memory footprint
* **Simplicity**: Unified storage eliminates data fragmentation
* **Reliability**: Automated validation and rollback capabilities

toc::[]

== Architecture Overview

=== Legacy Architecture (v0.1.x)

[source]
----
┌─────────────────────────────────────┐
│     ProximaEntityStore (Legacy)      │
├──────────────┬──────────────────────┤
│ Vector Engine│ InMemoryRelationsStore│
│  (SST/VIPER) │     (HashMap CSR)     │
├──────────────┼──────────────────────┤
│  File KV     │ ProvenanceRegistry    │
│  (Metadata)  │    (In-Memory)        │
└─────────────────────────────────────┘

Problems:
- Data scattered across 4 separate systems
- Poor cache locality
- Multiple lookups for hybrid queries
- No unified indexing
----

=== Graph-First Architecture (v0.2.0)

[source]
----
┌──────────────────────────────────────┐
│  OrionBackedEntityStore (Graph-First)│
├──────────────────────────────────────┤
│        Orion Graph Engine             │
│  ┌────────────┬──────────────────┐   │
│  │   Nodes    │      Edges       │   │
│  │ (Entities  │   (Relations)    │   │
│  │ +Embeddings│   (CSR Format)   │   │
│  │ +Metadata) │                  │   │
│  └────────────┴──────────────────┘   │
└──────────────────────────────────────┘

Benefits:
- Unified storage (single system)
- Excellent cache locality
- O(1) graph traversal
- Native hybrid queries
----

== Migration Methods

=== Method 1: Automated Migration (Recommended)

Use the built-in migration utilities for seamless transition.

==== Step 1: Enable Graph-First Feature

The `graph-first-sks` feature is **enabled by default** in v0.2.0.

To verify:

[source,toml]
----
# Cargo.toml
[features]
default = ["sql_frontend", "graph-first-sks"]
----

To disable (not recommended):

[source,bash]
----
cargo build --no-default-features --features sql_frontend
----

==== Step 2: Run Migration Script

[source,rust]
----
use proximadb::storage::entity_store::{
    ProximaEntityStore, OrionBackedEntityStore,
    migration::{migrate_to_graph_first, MigrationConfig}
};
use proximadb::graph::GraphOperationsService;
use std::sync::Arc;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    // Initialize legacy store
    let legacy_store = ProximaEntityStore::new(
        vector_engine,
        relations_store,
        provenance_registry
    );

    // Initialize graph service
    let graph_service = Arc::new(GraphOperationsService::new());

    // Configure migration
    let config = MigrationConfig {
        collection_id: "my-collection".to_string(),
        batch_size: 1000,          // Adjust based on available RAM
        validate: true,             // Recommended
        cleanup_legacy: false,      // Set to true after validation
    };

    // Run migration
    let stats = migrate_to_graph_first(
        &legacy_store,
        "my-collection",
        graph_service,
        &config
    ).await?;

    println!("Migration complete!");
    println!("  Entities migrated: {}", stats.entities_migrated);
    println!("  Relations migrated: {}", stats.relations_migrated);
    println!("  Errors: {}", stats.errors);
    println!("  Duration: {}ms", stats.duration_ms);

    Ok(())
}
----

==== Step 3: Validation

The migration automatically validates if `validate: true` is set.

**Manual Validation:**

[source,rust]
----
// Verify entity count matches
let legacy_count = legacy_store.list_entities("my-collection", 0, usize::MAX)
    .await?
    .len();

let graph_count = graph_store.list_entities("my-collection", 0, usize::MAX)
    .await?
    .len();

assert_eq!(legacy_count, graph_count, "Entity count mismatch!");
println!("✓ Validation successful: {} entities", graph_count);
----

# Run performance comparison

=== Method 2: Manual Migration

For fine-grained control over the migration process.

==== Step 1: Create New Graph Collection

[source,rust]
----
use proximadb::proto::proximadb_v1::CreateGraphRequest;

let create_request = CreateGraphRequest {
    graph_id: "my-collection".to_string(),
    name: Some("My Collection (Graph-First)".to_string()),
    description: Some("Migrated from legacy storage".to_string()),
    schema: None,
    storage_config: None,
    engine_config: None,
    access_control: None,
};

graph_service.create_graph_collection(create_request).await?;
----

==== Step 2: Migrate Entities in Batches

[source,rust]
----
let batch_size = 1000;
let entities = legacy_store.list_entities("my-collection", 0, usize::MAX).await?;

for chunk in entities.chunks(batch_size) {
    let mut batch = Vec::new();
    for entity in chunk {
        let mut entity_copy = entity.clone();
        entity_copy.collection_id = "my-collection".to_string();
        batch.push(entity_copy);
    }

    let count = graph_store.batch_upsert_entities("my-collection", batch).await?;
    println!("Migrated {} entities", count);
}
----

==== Step 3: Migrate Relations

[source,rust]
----
// Get all relations from legacy store
let relations = legacy_store.get_all_relations("my-collection").await?;

for relation in relations {
    graph_store.add_relation(relation).await?;
}

println!("Migrated {} relations", relations.len());
----

== Rollback Procedure

If you need to roll back to legacy storage:

=== Option 1: Restore from Backup

[source,bash]
----
# Stop the server
pkill proximadb-server

# Restore backup
rm -rf data/
cp -r data_backup_YYYYMMDD/ data/

# Rebuild with legacy features
cargo build --no-default-features --features sql_frontend

# Restart server
cargo run --bin proximadb-server
----

=== Option 2: Use Rollback Utility

[source,rust]
----
use proximadb::storage::entity_store::migration::rollback_migration;

rollback_migration(graph_service, "my-collection").await?;

// Note: Manual cleanup may be required
// Delete the graph collection manually if needed
----

== Post-Migration

=== 1. Update Application Code

No code changes required! The `EntityStore` trait interface remains the same.

**Before (Legacy):**
[source,rust]
----
let store = ProximaEntityStore::new(...);
let entity = store.get_entity("coll", "id", true, false).await?;
----

**After (Graph-First):**
[source,rust]
----
let store = OrionBackedEntityStore::new(graph_service, "coll".to_string());
let entity = store.get_entity("coll", "id", true, false).await?;
----

=== 2. Monitor Performance

Track key metrics:

[source,rust]
----
// Entity lookup latency
let start = std::time::Instant::now();
let entity = store.get_entity("coll", "id", true, false).await?;
let latency = start.elapsed();
println!("Lookup latency: {:?}", latency);  // Expected: <50µs

// Batch insert throughput
let start = std::time::Instant::now();
let count = store.batch_upsert_entities("coll", entities).await?;
let duration = start.elapsed();
let throughput = count as f64 / duration.as_secs_f64();
println!("Throughput: {:.2} entities/sec", throughput);  // Expected: 75K+
----

=== 3. Cleanup Legacy Data

**After** confirming the migration is successful:

[source,bash]
----
# Remove legacy storage files
rm -rf data/legacy_entity_store/
rm -rf data/legacy_relations/

# Optional: Re-run migration with cleanup enabled
let config = MigrationConfig {
    cleanup_legacy: true,  // NEW: Clean up after migration
    ..Default::default()
};
----

## Troubleshooting

=== Migration Fails with "Collection ID Mismatch"

**Error:**
[source]
----
Error: Collection ID mismatch: expected 'my-collection', got 'old-collection'
----

**Solution:**
Ensure all entities have the correct `collection_id` before migration:

[source,rust]
----
for entity in &mut entities {
    entity.collection_id = "my-collection".to_string();
}
----

=== Out of Memory During Migration

**Error:**
[source]
----
Error: Failed to allocate memory for batch
----

**Solution:**
Reduce batch size:

[source,rust]
----
let config = MigrationConfig {
    batch_size: 500,  // Reduced from 1000
    ..Default::default()
};
----

=== Validation Fails

**Error:**
[source]
----
Error: Validation failed with 5 errors
----

**Solution:**
1. Check migration logs for specific errors
2. Verify entity IDs are consistent
3. Re-run migration with `validate: false` temporarily
4. Manually inspect failed entities

=== Performance Not as Expected

**Issue:** Throughput < 30K entities/sec

**Checklist:**
1. ✅ Verify `graph-first-sks` feature is enabled
2. ✅ Check system resources (RAM, CPU)
3. ✅ Run in release mode: `cargo build --release`
4. ✅ Verify batch size is appropriate (1000-5000)

== Best Practices

=== 1. Migration Timing

* **Do:** Migrate during maintenance windows
* **Do:** Test on staging environment first
* **Don't:** Migrate during peak traffic

=== 2. Batch Size Tuning

[source,rust]
----
// Small datasets (<10K entities)
batch_size: 500

// Medium datasets (10K-100K entities)
batch_size: 1000

// Large datasets (>100K entities)
batch_size: 5000
----

=== 3. Validation Strategy

* **Always** enable validation for production migrations
* **Consider** sampling validation for very large datasets (>1M entities)
* **Keep** backups until validation passes

=== 4. Gradual Rollout

For production systems:

1. Migrate 10% of collections
2. Monitor for 24 hours
3. Migrate 50% of collections
4. Monitor for 1 week
5. Migrate remaining collections
