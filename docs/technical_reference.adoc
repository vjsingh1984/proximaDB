=== Storage-Aware Polymorphic Search

**Engine Selection Logic**:
[source,rust]
----
async fn select_search_engine(&self, query: &SearchQuery) -> Vec<Box<dyn SearchEngine>> {
    let mut engines = Vec::new();
    
    // WAL search for unflushed data
    if self.wal_has_unflushed_data(query.collection_id) {
        engines.push(Box::new(WalSearchEngine::new(self.wal.clone())));
    }
    
    // VIPER search with two-stage strategy for quantized data
    if self.has_quantized_data(query.collection_id) {
        engines.push(Box::new(TwoStageSearchEngine::new(
            self.distance_compute.clone(),
            self.quantization_engine.clone(),
        )));
    }
    
    // VIPER search for clustered data
    if self.viper_has_data(query.collection_id) {
        engines.push(Box::new(ViperSearchEngine::new(self.viper.clone())));
    }
    
    // LSM search for compacted data
    if self.lsm_has_data(query.collection_id) {
        engines.push(Box::new(LsmSearchEngine::new(self.lsm.clone())));
    }
    
    engines
}
----

**Result Aggregation**:
- **Deduplication**: ID-based merging with timestamp precedence
- **Ranking**: Unified distance scoring across all engines
- **Limit**: Top-k selection with exact tie-breaking

== Metadata Backend Architecture

=== Overview

ProximaDB supports multiple metadata backend implementations to meet different performance, scalability, and deployment requirements.

=== Available Backends

**Filestore Backend (Default)**::
- Proto-based serialization with schema evolution
- Atomic writes with staging and rename operations
- Support for local filesystem and cloud storage (S3, GCS, Azure)
- Single unified index for consistent lookups

**Cached Filestore Backend**::
- Two-level cache architecture (L1 hot cache, L2 warm cache)
- LRU eviction policy with configurable TTL
- Write-through and write-back caching modes
- Automatic cache promotion based on access patterns

**RocksDB Backend**::
- LSM tree architecture for write optimization
- Column families for organized data storage
- Built-in compression and bloom filters
- ACID transactions with optimistic concurrency

**Memory Backend**::
- In-memory storage for testing and development
- Ultra-fast operations with no disk I/O
- No persistence (data lost on restart)

=== Backend Selection Guide

[cols="2,3,3,2"]
|===
| Backend | Best For | Pros | Cons

| **Filestore**
| General use, cloud deployments
| Simple, reliable, cloud-compatible
| Slower for large datasets

| **Cached Filestore**
| Read-heavy workloads
| Fast reads, configurable caching
| Higher memory usage

| **RocksDB**
| Write-heavy, large scale
| High performance, ACID transactions
| Requires local disk, complex tuning

| **Memory**
| Testing only
| Fastest possible
| No persistence
|===
