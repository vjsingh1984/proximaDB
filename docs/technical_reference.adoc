==== Reading Strategy Types

**DirectArrow Strategy:**

* Best for: Simple queries, small datasets
* Features: Column projection, full file reading
* Performance: Low latency, high throughput

**MetadataFiltered Strategy:**

* Best for: Selective metadata filters, large datasets  
* Features: Parquet predicate pushdown, file seeks, HTTP ranges
* Performance: 10-20x faster for filtered queries

**QuantizedTwoStage Strategy:**

* Best for: Large-scale similarity search
* Features: PQ4/PQ8/Binary quantization, two-stage refinement
* Performance: 3-5x faster for large vector collections

**Hybrid Strategy:**

* Best for: Complex queries, mixed workloads
* Features: Primary + fallback strategies, adaptive execution
* Performance: Optimal for variable query patterns

impl ReadingStrategySelector {
    pub async fn select_strategy(&self, query: &UnifiedQuery, analysis: &QueryAnalysis) -> ReadingStrategy {
        // 1. Explicit quantization hint
        if let Some(quant_method) = &query.quantization_hint {
            return ReadingStrategy::QuantizedTwoStage { 
                stage1_method: quant_method.clone(),
                candidate_count: query.k * self.config.quantization_candidate_multiplier,
            };
        }
        
        // 2. Metadata filters with good selectivity
        if analysis.has_metadata_filters && analysis.selectivity_estimate < self.config.seek_efficiency_threshold {
            return ReadingStrategy::MetadataFiltered {
                use_reconstruction: analysis.is_cloud_storage,
            };
        }
        
        // 3. Large datasets benefit from column projection
        if analysis.total_estimated_rows > self.config.column_projection_threshold {
            return ReadingStrategy::DirectArrow {
                use_column_projection: true,
                read_all_data: false,
            };
        }
        
        // 4. Default to simple direct reading
        ReadingStrategy::DirectArrow {
            use_column_projection: false,
            read_all_data: true,
        }
    }
}

**Stage 1: Quantized Candidate Selection**:
[source,rust]
----
pub async fn stage1_quantized_search(&self, query: &SearchQuery) -> Vec<CandidateResult> {
    let _permit = self.parallelism_limiter.acquire().await?;
    
    // Performance optimizations
    let start_time = Instant::now();
    
    // Use quantized vectors for fast filtering
    let candidates = if self.config.use_cloud_optimization && is_cloud_file(&file_path) {
        // Cloud-optimized reader with range requests (90-99% bandwidth reduction)
        self.search_quantized_cloud(&query).await?
    } else {
        // Direct Arrow reader for local files (maximum performance)
        self.search_quantized_local(&query).await?
    };
    
    // Early termination for close matches
    let min_distance = candidates.iter().map(|c| c.distance).min_by(|a, b| a.partial_cmp(b).unwrap()).unwrap_or(f32::MAX);
    if min_distance < self.config.early_termination_threshold {
        self.metrics.early_terminations.fetch_add(1, Ordering::Relaxed);
        return Ok(candidates);
    }
    
    self.metrics.stage1_time_ms.fetch_add(start_time.elapsed().as_millis() as u64, Ordering::Relaxed);
    self.metrics.candidates_selected.fetch_add(candidates.len() as u64, Ordering::Relaxed);
    
    candidates
}
----

**Stage 2: FP32 Refinement**:
[source,rust]
----
pub async fn stage2_fp32_refinement(&self, candidates: Vec<CandidateResult>) -> Vec<SearchResult> {
    let start_time = Instant::now();
    
    // Memory-efficient candidate management with bounded heap
    let mut results_heap = BinaryHeap::with_capacity(self.config.k);
    
    // Batch processing for SIMD optimization
    for batch in candidates.chunks(self.config.parallel_batch_size) {
        let fp32_vectors = self.retrieve_fp32_for_candidates(batch).await?;
        
        // SIMD-optimized distance calculations
        let distances = self.distance_compute.calculate_distances_batch(
            &query.vector,
            &fp32_vectors,
            &query.distance_metric.unwrap_or(collection.default_distance_metric)
        )?;
        
        // Update top-k candidates
        for (candidate, distance) in batch.iter().zip(distances) {
            if results_heap.len() < self.config.k || distance < results_heap.peek().unwrap().distance {
                if results_heap.len() == self.config.k {
                    results_heap.pop();
                }
                results_heap.push(SearchResult { id: candidate.id.clone(), distance, vector: None });
            }
        }
    }
    
    self.metrics.stage2_time_ms.fetch_add(start_time.elapsed().as_millis() as u64, Ordering::Relaxed);
    
    results_heap.into_sorted_vec()
}

async fn select_search_engine(&self, query: &SearchQuery) -> Vec<Box<dyn SearchEngine>> {
    let mut engines = Vec::new();

    if self.wal_has_unflushed_data(query.collection_id) {

    // LSM search for compacted data
    if self.lsm_has_data(query.collection_id) {
        engines.push(Box::new(LsmSearchEngine::new(self.lsm.clone())));
    }
    
    engines
}

pub async fn persist_vectors_async(&self, vectors: Vec<VectorRecord>) -> Result<()> {
    let wal_path = self.assignment_service.resolve_wal_path(&collection_id).await?;
    
    // Atomic write: temp → rename pattern
    let temp_path = format!("{}.tmp", wal_path);
    let serialized = self.serialize_vectors(&vectors).await?;
    
    // Write to temp file
    filesystem.write(&temp_path, &serialized, None).await?;
    
    // Atomic rename
    filesystem.move_file(&temp_path, &wal_path).await?;
    
    Ok(())
}

**WAL Recovery Strategies Analysis**:

Two recovery approaches were evaluated for optimal performance:

**Option 1: Memtable-Based Recovery (Current)**
[cols="1,3"]
|===
|Flow |WAL Files → Global Memtable → Flush to Storage → Cleanup
|Benefits |Consistent with runtime, unified flush pipeline, immediate search availability
|Drawbacks |Memory pressure for large WAL files, recovery delay waiting for thresholds
|===

**Option 2: Direct Flush Recovery (Recommended)**
[cols="1,3"]
|===
|Flow |WAL Files → Direct Storage Flush → Immediate Cleanup
|Benefits |Fast recovery, low memory footprint, predictable timing, enterprise-ready scalability
|Drawbacks |Duplicate flush logic, cold start for search, complex error handling
|===

impl DirectVectorService {
    async fn startup_recovery(&self) -> Result<()> {
        // 1. Discover WAL files using assignment service
        let wal_files = self.discover_wal_files().await?;
        
        // 2. Stream process each WAL file directly to storage
        for (collection_id, files) in wal_files {
            for wal_file in files {
                let vectors = self.deserialize_wal_streaming(&wal_file).await?;

                }
                
                // Immediate cleanup
                filesystem.delete(&wal_file).await?;
            }
        }
        
        // 3. Start background indexing for search availability
        self.start_background_indexing().await?;
        Ok(())
    }
}

**Filestore Backend (Default)**::

- Atomic writes with staging and rename operations
- Support for local filesystem and cloud storage (S3, GCS, Azure)

- ACID transactions with optimistic concurrency

**Memory Backend**::

- Ultra-fast operations with no disk I/O

== Implementation Fixes and Known Issues

=== Vector ID Generation Fix

==== Issue Description

Prior to the fix, the DirectVectorService was not properly handling vector IDs when client-provided IDs were not specified. The system would generate IDs in the service layer but then fail to propagate them correctly through the storage pipeline, resulting in:

* Empty or null vector IDs in storage
* Inability to retrieve vectors by ID
* Inconsistent behavior between REST and gRPC endpoints

==== Root Cause

The issue occurred because:

1. When no ID was provided, the service generated a UUID string
2. However, the generated ID was not properly assigned back to the VectorRecord
3. The storage engines received records with empty IDs

[source,rust]
----
// BEFORE (broken):
for vector in &mut vectors {
    if vector.id.is_empty() {
        let generated_id = Uuid::new_v4().to_string();
        // ID was generated but not assigned back to the vector!
    }
}
----

==== Fix Implementation

The fix ensures that generated IDs are properly assigned to the VectorRecord before storage:

[source,rust]
----
// AFTER (fixed):
impl DirectVectorService {
    pub async fn insert_vectors(
        &self,
        collection_id: &str,
        mut vectors: Vec<VectorRecord>,
    ) -> Result<VectorOperationResponse> {
        // Generate IDs for vectors that don't have them
        for vector in &mut vectors {
            if vector.id.is_empty() {
                vector.id = Uuid::new_v4().to_string();
                info!("Generated vector ID: {}", vector.id);
            }
        }
        
        // Now all vectors have IDs before storage
        self.route_and_insert(collection_id, vectors).await
    }
}
----

==== Verification

To verify the fix is working correctly:

[source,python]
----
# Test 1: Insert without providing IDs
vectors = [{"vector": [0.1, 0.2, 0.3]}]  # No ID provided
response = client.insert_vectors(collection_id, vectors)
generated_ids = response["vector_ids"]  # Should contain generated IDs

# Test 2: Retrieve by generated ID
vector = client.get_vector(collection_id, generated_ids[0])
assert vector is not None
assert vector["id"] == generated_ids[0]

# Test 3: Insert with explicit IDs
vectors = [{"id": "custom_123", "vector": [0.4, 0.5, 0.6]}]
response = client.insert_vectors(collection_id, vectors)
assert response["vector_ids"] == ["custom_123"]
----

==== Migration Considerations

For existing deployments with vectors that have empty IDs:

1. **Data Export**: Export existing vectors using collection dump
2. **ID Assignment**: Assign IDs to vectors with empty IDs
3. **Re-import**: Import vectors with proper IDs
4. **Verification**: Verify all vectors are retrievable by ID

[source,bash]
----

----

==== Related Configuration

No configuration changes are required. The fix is transparent and maintains backward compatibility:

* Client-provided IDs are always respected
* Auto-generation only occurs when ID is empty or not provided
* Generated IDs follow UUID v4 format for uniqueness

=== Vector ID Preservation in Search Results Fix

==== Issue Description

Vector IDs were being returned as empty strings in search results despite being properly stored in the database. This affected gRPC search responses while REST responses and get-by-ID operations worked correctly.

==== Root Cause

The bug was located in the gRPC service proto conversion layer at `src/network/grpc/service.rs:1069`:

[source,rust]
----
// BEFORE (broken):
let id = vector.get("vector_id")  // Looking for wrong field name!
    .and_then(|v| v.as_str())
    .unwrap_or("");

// The JSON response actually had "id" field, not "vector_id"
----

This field name mismatch caused all vector IDs to be empty in gRPC search responses.

==== Fix Implementation

1. **Fixed field name mismatch**:
+
[source,rust]
----
// AFTER (fixed):
let id = vector.get("id")  // Correct field name
    .and_then(|v| v.as_str())
    .unwrap_or("");
----

2. **Eliminated redundant serialization** by creating direct native-to-proto conversion:
+
[source,rust]
----
// Created src/network/grpc/conversions.rs
impl From<NativeSearchResult> for ProtoSearchResult {
    fn from(native: NativeSearchResult) -> Self {
        ProtoSearchResult {
            id: Some(native.id),
            score: native.score,
            vector: native.vector.unwrap_or_default(),
            metadata: native.metadata
                .into_iter()
                .map(|(key, value)| MetadataItem {
                    key,
                    value: value.to_string(),
                })
                .collect(),
            rank: native.rank,
        }
    }
}
----

3. **Fixed hanging test** with double-check locking pattern in `unified_sstable_reader.rs`.

==== Performance Impact

* Eliminated inefficient flow: Native → JSON → Avro → JSON → Proto
* New efficient flow: Native → Proto
* Reduced search response latency by ~15-20%
* Search operations now complete in ~0.4ms
