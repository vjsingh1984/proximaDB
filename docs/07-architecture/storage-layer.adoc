== Storage Engines

=== SST: Hybrid Columnar Storage

**Architecture**: ProximaBlocks format - hybrid columnar with metadata columns and configurable vector encoding

**Key Features**:
- Write-optimized with efficient updates
- Three-stage filtering (Bloom, zone maps, exact)
- Real-time query support
- Configurable vector compression

**Performance**:
- Writes: 10,000-15,000 ops/sec
- Point queries: <5ms p99
- Bulk inserts: 50,000-100,000 records/sec

**Implementation Details**: link:../../src/storage/engines/impls/sst/README.adoc[SST Implementation Guide]

**Configuration**:
[source,toml]
----
[storage.sst]
write_buffer_size = 8388608
bloom_filter_enabled = true
zone_maps_enabled = true
compression = "lz4"
----

=== VIPER: Columnar Parquet Storage

**Architecture**: Pure columnar format using Apache Parquet with ProximaCodec

**Key Features**:
- Optimized for analytical queries
- Efficient column pruning
- High compression ratios
- Batch operation support

**Performance**:
- Analytical scans: 100K-500K vectors/sec
- Compression: 10:1 - 30:1 ratio
- Column pruning: 70-90% speedup

**Implementation Details**: link:../../src/storage/engines/impls/viper/README.adoc[VIPER Implementation Guide]

**Configuration**:
[source,toml]
----
[storage.viper]
row_group_size = 1048576
compression = "snappy"
page_size = 8192
enable_dictionary = true
----

=== NOVA: Progressive Columnar Storage

**Architecture**: Progressive columnar with adaptive reorganization

**Key Features**:
- Balances read and write performance
- Automatic reorganization
- Flexible for mixed workloads
- Gradual optimization

**Performance**:
- Mixed workloads: balanced performance
- Adaptive to access patterns
- Moderate overhead for reorganization

**Implementation Details**: link:../../src/storage/engines/impls/nova/README.adoc[NOVA Implementation Guide]

**Configuration**:
[source,toml]
----
[storage.nova]
reorganization_threshold = 10000
optimization_window = 3600
----

=== SWIFT: Hierarchical Storage

**Architecture**: Three-tier hierarchical (SuperBlock → DataBlock → Record)

**Key Features**:
- Multi-tenant isolation
- Hierarchical organization
- Version control support
- Efficient nested queries

**Performance**:
- Multi-tenant: Excellent isolation
- Hierarchical queries: <10ms
- Version traversal: O(log n)

**Implementation Details**: link:../../src/storage/engines/impls/swift/README.adoc[SWIFT Implementation Guide]

**Configuration**:
[source,toml]
----
[storage.swift]
superblock_size = 1048576
datablock_size = 65536
max_hierarchy_depth = 5
----

=== HELIX: Locality-Optimized Storage

**Architecture**: Hilbert curve spatial locality with PCA dimensionality reduction

**Key Features**:
- Spatial locality preservation
- Excellent for range queries
- PCA-based clustering
- LSM-tree organization

**Performance**:
- Range queries: 90-95% pruning
- Clustering: 768D/1536D → 16-64D
- Query latency: 2-5ms

**Implementation Details**: link:../../src/storage/engines/impls/helix/README.adoc[HELIX Implementation Guide]

**Configuration**:
[source,toml]
----
[storage.helix]
pca_dimensions = 32
hilbert_order = 10
liquid_clustering_threshold = 10000
----

=== RAPTOR: Adaptive Row-Group Storage

**Architecture**: Adaptive row-group with dynamic reorganization

**Key Features**:
- Adapts to workload changes
- Dynamic row-group sizing
- Automatic optimization
- Workload-aware reorganization

**Performance**:
- Adaptive performance
- Low reorganization overhead
- Workload learning

**Implementation Details**: link:../../src/storage/engines/impls/raptor/README.adoc[RAPTOR Implementation Guide]

**Configuration**:
[source,toml]
----
[storage.raptor]
min_row_group_size = 1000
max_row_group_size = 100000
adaptation_window = 1000
----

== Unified Storage Interface

All engines implement the `UnifiedStorageEngine` trait:

[source,rust]
----
pub trait UnifiedStorageEngine: Send + Sync {
    async fn insert(&self, record: VectorRecord) -> Result<()>;
    async fn batch_insert(&self, records: Vec<VectorRecord>) -> Result<()>;
    async fn get(&self, id: &str) -> Result<Option<VectorRecord>>;
    async fn search(&self, params: SearchParams) -> Result<Vec<SearchResult>>;
    async fn delete(&self, id: &str) -> Result<()>;
    async fn flush(&self) -> Result<()>;
}
----

**Benefits**:
- Transparent engine switching
- Consistent API across engines
- Easy migration between engines
- Unified testing

== Common Storage Components

=== UnifiedCachingFilesystem

All engines use the unified caching filesystem:

- **Metadata caching**: Collection configs, indexes
- **Disk caching**: Recently accessed blocks
- **Prefetching**: Predictive loading
- **Zero-copy I/O**: Direct memory mapping

**Documentation**: `src/storage/persistence/filesystem/unified.rs`

=== Write-Ahead Log (WAL)

Global WAL manifest coordinates recovery:

- **Cloud-optimized**: S3, Azure Blob, GCS
- **LSN tracking**: Global log sequence numbers
- **Parallel recovery**: Multi-threaded startup
- **Direct-to-storage**: Bypass memtable on recovery

**Documentation**: `src/storage/persistence/write_ahead_log/`

=== Cache Orchestrator

Centralized cache coordination:

- **VectorCache**: Specialized for vector operations
- **Eviction policies**: LRU, LFU, Adaptive
- **Multi-tier**: Memory + disk tiers
- **Cache-aware scheduling**: Optimize hit rates

**Documentation**: `src/storage/cache/`

== Storage Configuration

=== Global Storage Config

[source,toml]
----
[storage]
data_dir = "/var/lib/proximadb/data"
metadata_dir = "/var/lib/proximadb/metadata"
default_engine = "auto"  # or specific engine name

[storage.wal_config]
global_manifest_url = "file:///var/lib/proximadb/manifest"
enable_wal = true
write_buffer_size_mb = 8192
memory_flush_size_bytes = 16777216
----

=== Engine Auto-Selection

ProximaDB can automatically select the optimal engine:

[source,toml]
----
[storage]
default_engine = "auto"

[storage.auto_selection]
enabled = true
workload_analysis_window = 3600  # seconds
min_samples = 1000
----

**Auto-selection factors**:
- Write/read ratio
- Update frequency
- Query patterns
- Data size
- Multi-tenancy requirements

== Migration Between Engines

ProximaDB supports zero-downtime migration:

[source,bash]
----
# Start migration
curl -X POST http://localhost:5678/api/v1/collections/my_collection/migrate \
  -H "Content-Type: application/json" \
  -d '{
    "target_engine": "VIPER",
    "strategy": "background",
    "parallel_readers": 4
  }'

# Monitor progress
curl http://localhost:5678/api/v1/collections/my_collection/migration/status
----

**Migration strategies**:
- **Background**: Gradual migration with no downtime
- **Snapshot**: Fast migration with brief read-only period
- **Parallel**: Multi-threaded for fastest migration

== Best Practices

=== Engine Selection

1. **Start with SST** for general-purpose workloads
2. **Use VIPER** when analytics dominates (>80% reads)
3. **Choose SWIFT** for multi-tenant SaaS applications
4. **Pick HELIX** for geospatial or clustering workloads
5. **Try NOVA** for unpredictable mixed workloads
6. **Use RAPTOR** when workload changes over time

=== Configuration Tuning

1. **Write buffer size**: Increase for write-heavy workloads
2. **Compression**: Trade CPU for storage (snappy vs zstd)
3. **Cache size**: Allocate based on working set size
4. **WAL settings**: Balance durability vs performance

=== Capacity Planning

1. **Estimate data size**: `vectors × dimension × 4 bytes × compression_ratio^-1`
2. **Add overhead**: 10-25% depending on engine
3. **Plan for growth**: 3-6 month runway
4. **Monitor metrics**: Set alerts at 70% capacity

== Troubleshooting

=== Slow Writes

**Symptoms**: High write latency, backpressure

**Solutions**:
1. Increase write buffer size
2. Enable batching in client
3. Check WAL disk performance
4. Consider engine switch (→ SST or SWIFT)

=== Slow Reads

**Symptoms**: High query latency, cache misses

**Solutions**:
1. Increase cache size
2. Add indexes (AXIS)
3. Enable query optimization
4. Consider engine switch (→ VIPER or HELIX for analytics)

=== High Storage Usage

**Symptoms**: Disk usage growing faster than expected

**Solutions**:
1. Enable compression
2. Adjust compression algorithm (lz4 → zstd)
3. Run manual compaction
4. Check for duplicate data
