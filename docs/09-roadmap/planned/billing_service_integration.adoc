[[introduction]]
== 1. Introduction

=== 1.1 Purpose
This document outlines the requirements, design, and detailed integration plan for incorporating an external billing service API and multi-cloud marketplace integrations (AWS, GCP, Azure, Oracle, Rackspace) into the `proximaDB` platform. The goal is to enable robust customer management, subscription handling, payment processing, usage-based billing, and seamless onboarding for customers acquiring `proximaDB` SaaS through various cloud marketplaces.

=== 1.2 Scope
This specification covers the integration of `proximaDB`'s backend services with a third-party billing provider's API *and* the specific APIs and mechanisms of AWS Marketplace, Google Cloud Marketplace, Azure Marketplace, Oracle Cloud Marketplace, and Rackspace Marketplace. It includes functional and non-functional requirements, architectural design, data model considerations, API interaction patterns, and a detailed integration roadmap. It focuses on metering, entitlement, and billing reconciliation across these platforms. It does not cover specific UI/UX design for billing portals, though integration points are considered.

=== 1.3 Goals
*   Automate customer and subscription lifecycle management, both direct and via marketplaces.
*   Securely process payments and handle billing events, leveraging marketplace billing for marketplace customers.
*   Provide accurate and timely billing information to users, reflecting their purchase channel.
*   Support various pricing models (e.g., fixed subscriptions, usage-based) across all channels.
*   Ensure high availability, security, and scalability of billing operations.
*   Enable `proximaDB` to be listed and sold as a SaaS offering on AWS, GCP, Azure, Oracle, and Rackspace Marketplaces.

== 2. Requirements

=== 2.1 Functional Requirements

==== FR-BILL-001: Customer Management
*   The system SHALL be able to create and update customer records in the primary billing service upon direct user registration/profile updates in `proximaDB`.
*   The system SHALL be able to provision `proximaDB` accounts for customers purchasing via AWS, GCP, Azure, Oracle, and Rackspace Marketplaces.
*   The system SHALL be able to retrieve customer billing information (e.g., payment methods, subscription status) from the relevant billing source (primary billing service or marketplace).

==== FR-BILL-002: Subscription Management
*   The system SHALL allow users to subscribe to different `proximaDB` plans (products) via direct purchase or through cloud marketplaces.
*   The system SHALL support subscription activation, cancellation, upgrades, and downgrades, initiated either directly or via marketplace entitlement changes.
*   The system SHALL track the current status and details of each user's subscription, including its origin (direct or specific marketplace).
*   The system SHALL handle subscription renewals automatically, respecting marketplace billing cycles for marketplace customers.

==== FR-BILL-003: Payment Processing
*   For direct customers, the system SHALL securely collect and store payment method details via the primary billing service's secure mechanisms.
*   For marketplace customers, the system SHALL rely on the respective cloud provider for payment processing.
*   The system SHALL initiate charges for direct subscriptions and usage via the primary billing service.
*   The system SHALL handle payment failures, retries, and notifications for direct customers.

==== FR-BILL-004: Invoice Management
*   The system SHALL retrieve and display past and upcoming invoices to users, distinguishing between direct and marketplace invoices.
*   The system SHALL handle invoice generation and delivery (managed by the primary billing service for direct, and by the marketplace for marketplace customers).

==== FR-BILL-005: Usage Tracking and Metering
*   The system SHALL track usage metrics for all `proximaDB` instances and services.
*   For direct customers, the system SHALL report usage metrics to the primary billing service for aggregation and billing.
*   For marketplace customers, the system SHALL report usage metrics to the respective cloud provider's metering service (AWS Marketplace Metering Service, GCP Cloud Billing API, Azure Marketplace Metering API, Oracle Cloud Marketplace Metering API, Rackspace Marketplace Metering API) for aggregation and billing.
*   The system SHALL be able to query current usage for a given customer/subscription.

==== FR-BILL-006: Webhook/Notification Processing
*   The system SHALL receive and process webhooks from the primary billing service for critical events (e.g., `invoice.paid`, `subscription.updated`).
*   The system SHALL receive and process notifications/webhooks from AWS Marketplace (e.g., SNS notifications for entitlement changes).
*   The system SHALL receive and process notifications/webhooks from GCP Marketplace (e.g., Pub/Sub messages for entitlement changes).
*   The system SHALL receive and process notifications/webhooks from Azure Marketplace (e.g., Webhooks for subscription changes).
*   The system SHALL receive and process notifications/webhooks from Oracle Cloud Marketplace (e.g., specific API calls or webhooks for entitlement changes).
*   The system SHALL receive and process notifications/webhooks from Rackspace Marketplace (e.g., specific API calls or webhooks for entitlement changes).
*   Webhook/notification processing SHALL be idempotent and secure (e.g., signature verification, message validation).

==== FR-BILL-007: Entitlement Management
*   The system SHALL validate marketplace entitlements upon customer provisioning and ongoing usage.
*   The system SHALL activate/deactivate `proximaDB` services based on marketplace subscription status (e.g., `subscribed`, `suspended`, `cancelled`).

=== 2.2 Non-Functional Requirements

==== NFR-BILL-001: Security
*   All communication with billing services and marketplace APIs SHALL use HTTPS/TLS.
*   Sensitive payment information SHALL NOT be stored directly in `proximaDB`'s database; it SHALL be handled by the primary billing service or the respective cloud provider.
*   Webhook/notification endpoints SHALL be secured and verify the authenticity of incoming requests.
*   API keys and secrets for all billing and marketplace integrations SHALL be stored securely.

==== NFR-BILL-002: Reliability & Availability
*   The integration SHALL be resilient to temporary outages or latency from any billing service or marketplace API (e.g., with retries, circuit breakers).
*   Critical billing and entitlement operations SHALL be eventually consistent across `proximaDB` and all integrated platforms.

==== NFR-BILL-003: Performance
*   API calls to billing and marketplace services SHALL not introduce significant latency to user-facing operations.
*   Webhook/notification processing SHALL be efficient to avoid timeouts and backlog.
*   Metering data submission SHALL be performed efficiently and asynchronously.

==== NFR-BILL-004: Scalability
*   The integration SHALL scale to handle a growing number of customers, subscriptions, and usage events across all integrated platforms.

==== NFR-BILL-005: Observability
*   All interactions with billing and marketplace APIs (requests, responses, errors) SHALL be logged appropriately.
*   Metrics related to billing operations (e.g., API call success rates, webhook processing times, metering submission rates) SHALL be collected for each platform.
*   Alerts SHALL be configured for critical billing failures (e.g., failed payments, entitlement errors, metering submission failures).

==== NFR-BILL-006: Error Handling
*   The system SHALL gracefully handle errors returned by all integrated APIs, providing meaningful feedback to users and administrators.
*   Appropriate retry mechanisms with exponential backoff SHALL be implemented for transient errors.

=== 3.2 Integration Points

The primary integration points will be:

*   **User Registration/Login:** Create/retrieve customer records in the primary billing service or identify marketplace customers.
*   **Marketplace Subscription Activation:** Process initial marketplace purchase events to provision `proximaDB` accounts.
*   **Plan Selection/Subscription:** Initiate subscription creation or modification (direct or via marketplace).
*   **Payment Method Management:** Securely update payment details (direct customers only).
*   **Usage Reporting:** Send usage data to the primary billing service or respective cloud provider metering APIs.
*   **Webhook/Notification Endpoints:** Receive asynchronous notifications from the primary billing service and all cloud marketplaces.
*   **Entitlement Checks:** Periodically verify marketplace entitlements.

=== 3.3 Data Model

`proximaDB` will maintain billing-related data, including marketplace-specific identifiers, with the external billing service or marketplace being the source of truth for detailed financial information.

*   **`User` Table (existing):**
    *   `billing_customer_id`: String (External ID from Primary Billing Service)
    *   `marketplace_customer_id`: String (ID from the specific marketplace, e.g., AWS Customer ID, GCP Account ID, Azure Subscription ID, Oracle Subscription ID, Rackspace Customer ID)
    *   `marketplace_type`: Enum (e.g., `NONE`, `AWS`, `GCP`, `AZURE`, `ORACLE`, `RACKSPACE`)
    *   `current_subscription_id`: String (External ID from Primary Billing Service or Marketplace Subscription ID)
    *   `subscription_status`: Enum (e.g., `active`, `trialing`, `past_due`, `canceled`)

*   **`Subscription` Table (new/extended):**
    *   `id`: UUID (Internal `proximaDB` ID)
    *   `user_id`: UUID (Foreign key to `User`)
    *   `billing_subscription_id`: String (External ID from Primary Billing Service or Marketplace Subscription ID)
    *   `marketplace_type`: Enum (e.g., `NONE`, `AWS`, `GCP`, `AZURE`, `ORACLE`, `RACKSPACE`)
    *   `plan_id`: String (External ID for the subscribed plan/product)
    *   `status`: Enum (e.g., `active`, `trialing`, `past_due`, `canceled`)
    *   `start_date`: Timestamp (When subscription started)
    *   `end_date`: Timestamp (When subscription ends, if applicable)
    *   `current_period_end`: Timestamp (End of current billing period)
    *   `cancel_at_period_end`: Boolean (True if subscription will cancel at period end)
    *   `marketplace_entitlement_id`: String (Specific ID for marketplace entitlement, if applicable)

*   **`PaymentMethod` (optional, for display - primarily for direct customers):**
    *   `id`: UUID
    *   `user_id`: UUID
    *   `billing_payment_method_id`: String (External ID)
    *   `card_brand`: String (e.g., "Visa")
    *   `last4`: String (Last 4 digits of card)
    *   `exp_month`: Integer
    *   `exp_year`: Integer
    *   `is_default`: Boolean

=== 3.4 API Endpoints (Examples)

The `Billing Service Module` and `Marketplace Integration Layer` will expose internal APIs for `proximaDB`'s backend and UI to interact with billing functionalities.

*   `POST /api/billing/customer`: Create or update customer (for direct billing).
*   `POST /api/billing/subscribe`: Create a new subscription (for direct billing).
*   `POST /api/billing/subscription/{id}/cancel`: Cancel a subscription (direct or marketplace).
*   `POST /api/billing/subscription/{id}/update_plan`: Change subscription plan (direct or marketplace).
*   `GET /api/billing/customer/{id}/subscriptions`: Get all subscriptions for a customer.
*   `GET /api/billing/customer/{id}/invoices`: Get invoices for a customer.
*   `POST /api/billing/webhook`: Endpoint for receiving webhooks from the primary billing service.
*   `POST /api/marketplace/aws/notification`: Endpoint for AWS SNS/SQS notifications.
*   `POST /api/marketplace/gcp/notification`: Endpoint for GCP Pub/Sub notifications.
*   `POST /api/marketplace/azure/webhook`: Endpoint for Azure Marketplace webhooks.
*   `POST /api/marketplace/oracle/notification`: Endpoint for Oracle Cloud Marketplace notifications.
*   `POST /api/marketplace/rackspace/notification`: Endpoint for Rackspace Marketplace notifications.

=== 3.5 Internal Service Design

==== Billing Service Module
Encapsulates all logic related to the primary external billing provider (e.g., Stripe, Chargebee).

*   **`BillingClient`:** A client library for interacting with the primary billing service's REST API.
*   **`BillingService`:** Core business logic for direct customer billing, handling data mapping, retries, and database updates.

==== Marketplace Integration Layer
This layer will contain specific adapters for each cloud marketplace, abstracting their unique APIs and notification mechanisms.

*   **`AwsMarketplaceAdapter`:**
    *   Interacts with AWS Marketplace Metering Service for usage reporting.
    *   Interacts with AWS Marketplace Entitlement Service for subscription status.
    *   Handles SNS/SQS notifications for entitlement changes.
*   **`GcpMarketplaceAdapter`:**
    *   Interacts with GCP Cloud Billing API for usage reporting.
    *   Interacts with GCP Partner Procurement API for entitlement management.
    *   Handles Pub/Sub messages for entitlement changes.
*   **`AzureMarketplaceAdapter`:**
    *   Interacts with Azure Marketplace Metering API for usage reporting.
    *   Interacts with Azure Marketplace Fulfillment API for subscription management.
    *   Handles Azure Marketplace webhooks for subscription changes.
*   **`OracleMarketplaceAdapter`:**
    *   Interacts with Oracle Cloud Marketplace Metering API for usage reporting.
    *   Interacts with Oracle Cloud Marketplace Entitlement/Subscription APIs for status.
    *   Handles Oracle Cloud Marketplace notifications (e.g., API polling or webhooks) for entitlement changes.
*   **`RackspaceMarketplaceAdapter`:**
    *   Interacts with Rackspace Marketplace Metering API for usage reporting.
    *   Interacts with Rackspace Marketplace Entitlement/Subscription APIs for status.
    *   Handles Rackspace Marketplace notifications (e.g., API polling or webhooks) for entitlement changes.

==== Webhook Handler Module
Dedicated component to receive, validate, and process incoming webhooks/notifications from all sources.

*   **`WebhookDispatcher`:** Routes incoming webhooks/notifications to the correct handler based on source (primary billing service, AWS, GCP, Azure, Oracle, Rackspace).
*   **`MarketplaceNotificationHandler`:** Specific handlers for each marketplace's notification format, verifying authenticity and dispatching to internal event processors.

== 4. Detailed Integration Plan

=== 4.1 Authentication & Authorization

*   **Primary Billing Service:** API keys (secret and publishable) stored securely.
*   **AWS Marketplace:** IAM roles/users with appropriate permissions for Metering and Entitlement services. SNS/SQS topic policies for notifications.
*   **GCP Marketplace:** Service accounts with necessary roles for Cloud Billing API and Pub/Sub. Pub/Sub topic permissions for notifications.
*   **Azure Marketplace:** Azure AD application registration with permissions for Metering and Fulfillment APIs. Webhook secrets for notification validation.
*   **Oracle Cloud Marketplace:** API keys, OAuth tokens, or other credentials as required by Oracle's APIs for metering and entitlement. Notification configuration.
*   **Rackspace Marketplace:** API keys, OAuth tokens, or other credentials as required by Rackspace's APIs for metering and entitlement. Notification configuration.

=== 4.2 Error Handling & Retries

*   **Unified Strategy:** Implement exponential backoff with jitter for retrying API calls to all billing and marketplace services.
*   **Idempotency:** Utilize idempotency keys where available (primary billing service) or implement custom idempotency for marketplace API calls (e.g., by tracking request IDs).
*   **Marketplace-Specific Errors:** Map marketplace-specific error codes to a common internal error model for consistent handling.
*   **Circuit Breaker:** Implement circuit breaker patterns for each `BillingClient` and `MarketplaceAdapter` to isolate failures.

=== 4.3 Webhook/Notification Processing

*   **Dedicated Endpoints:** Separate, publicly accessible HTTPS endpoints for the primary billing service and each cloud marketplace's notification mechanism.
    *   `/api/billing/webhook` (Primary Billing Service)
    *   `/api/marketplace/aws/notification` (AWS SNS/SQS via HTTP endpoint or direct SQS consumption)
    *   `/api/marketplace/gcp/notification` (GCP Pub/Sub via push subscription to HTTP endpoint)
    *   `/api/marketplace/azure/webhook` (Azure Marketplace webhooks)
    *   `/api/marketplace/oracle/notification` (Oracle Cloud Marketplace notifications)
    *   `/api/marketplace/rackspace/notification` (Rackspace Marketplace notifications)
*   **Signature/Message Verification:** Implement specific verification logic for each platform:
    *   Primary Billing Service: Signature header verification.
    *   AWS: SNS message signature verification.
    *   GCP: Pub/Sub message validation (e.g., JWT if applicable).
    *   Azure: Webhook signature/shared secret verification.
    *   Oracle: Specific API/webhook signature or token validation.
    *   Rackspace: Specific API/webhook signature or token validation.
*   **Asynchronous Processing:** All incoming notifications SHALL be immediately acknowledged and then processed asynchronously via a message queue.
*   **Idempotency:** All webhook/notification handlers SHALL be idempotent.
*   **Event Handling:** Specific handlers for each platform's events:
    *   **AWS:** `aws-marketplace-entitlement-notification` (for subscription changes), `aws-marketplace-metering-notification` (if applicable).
    *   **GCP:** `partner-procurement-subscription-change` (for entitlement changes).
    *   **Azure:** `SubscriptionStatusChanged`, `UsagePlanChanged` (for subscription lifecycle).
    *   **Oracle:** Specific entitlement/subscription change events.
    *   **Rackspace:** Specific entitlement/subscription change events.

=== 4.4 Data Synchronization and Reconciliation

*   **Source of Truth:** The respective marketplace (AWS, GCP, Azure, Oracle, Rackspace) SHALL be the source of truth for marketplace-purchased subscriptions and entitlements. The primary billing service remains the source of truth for direct subscriptions.
*   **Initial Sync:** Implement processes to import existing marketplace subscriptions and entitlements upon initial integration.
*   **Ongoing Sync:** Webhooks/notifications are the primary mechanism. Additionally, periodic reconciliation jobs will query marketplace APIs to ensure `proximaDB`'s state is consistent with the marketplaces.
*   **Customer Linking:** Establish a robust mechanism to link a `proximaDB` user account to their corresponding marketplace customer/subscription ID.

=== 4.5 UI Integration Considerations

*   **Marketplace-Specific Onboarding:** Guide users purchasing through marketplaces through a specific onboarding flow that links their marketplace subscription to their `proximaDB` account.
*   **Billing Portal:** For direct customers, link to the primary billing service's portal. For marketplace customers, inform them that billing is handled by their cloud provider.
*   **Display Data:** Clearly indicate the source of a subscription (direct, AWS, GCP, Azure, Oracle, Rackspace) and display relevant status and usage data by querying the appropriate internal APIs.

=== 4.6 Testing Strategy

*   **Unit Tests:** Test `BillingClient` and all `MarketplaceAdapter` components in isolation, mocking external API calls.
*   **Integration Tests:** Test full flows against *mocked* or *sandbox* environments for the primary billing service and each cloud marketplace.
*   **Webhook/Notification Tests:** Use testing tools provided by each platform (e.g., AWS SNS simulator, GCP Pub/Sub emulator, Azure webhook testing tools, Oracle/Rackspace equivalents) to test end-to-end processing.
*   **End-to-End Tests:** Simulate user actions (e.g., marketplace purchase, subscription changes) and verify that the billing service and `proximaDB`'s internal state are correctly updated.
*   **Error Scenario Tests:** Test various error conditions, including marketplace API failures, entitlement revocations, and metering submission errors.

=== 4.7 Deployment Considerations

*   **Environment Variables/Secrets:** Securely manage API keys, client IDs, secrets, and other credentials for all integrated platforms.
*   **Webhook/Notification Endpoints:** Ensure all endpoints are publicly accessible, secured, and configured correctly in each respective platform.
*   **Monitoring & Alerting:** Set up comprehensive monitoring for API calls, notification processing, and data synchronization across all billing and marketplace integrations. Configure alerts for critical failures.
*   **Cloud-Specific Resources:** Deploy necessary cloud resources (e.g., AWS SNS topics, GCP Pub/Sub topics, Azure Event Grid, Oracle/Rackspace equivalents) for receiving notifications.
