= Semantic Knowledge Store (SKS) Enhancement Specification
:toc: left
:toclevels: 3
:icons: font
:source-highlighter: rouge

== Executive Summary

This document specifies the requirements, design, and implementation plan for evolving ProximaDB from a high-performance vector database into a comprehensive Semantic Knowledge Store (SKS). The SKS represents a new category of data system that unifies embeddings, metadata, relationships, provenance, and temporal reasoning into a single coherent platform.

=== Non-Goals (Initial Phases)

- Full-fledged property graph query language (e.g., full Cypher/Gremlin parity)
- End-to-end ETL pipelines and document extraction frameworks
- LLM generation/inference services; SKS focuses on storage and retrieval
- Ontology editor UI; start with file-based versioned ontologies
- Cross-collection transactional joins; keep operations within a collection
- Global ACID across collections/tenants; use best-effort multi-store consistency

== Current State Analysis

=== ProximaDB Existing Capabilities

ProximaDB currently provides:

* **Vector Storage & Search**: High-performance vector similarity search with multiple distance metrics
* **Storage Engines**: Four storage engines (VIPER, SST, DSST, DVIPER) optimized for different workloads
* **Metadata Support**: Basic metadata filtering with typed fields (MetadataItem proto structure)
* **SQL Interface**: SQL-like query language for vector search with metadata filters
* **Indexing**: Six indexing algorithms (HNSW, IVF, PQ, FLAT, ANNOY, LSH)
* **Quantization**: Advanced quantization for storage and memory optimization
* **MVCC**: Multi-version concurrency control with versioning support
* **Cloud Storage**: S3/GCS/Azure blob storage support
* **Compression**: 14 compression algorithms with context-aware selection

== Feature Requirements

=== Tier 1: MVP Features (v0.1)

==== 1.1 Entity Data Model

*Requirement*: Transform from vector-centric to entity-centric storage model.

*Design*:
[source,protobuf]
----
message Entity {
  string id = 1;
  repeated EmbeddingVersion embeddings = 2;
  TypedMetadata typed_metadata = 3;
  google.protobuf.Struct flexible_metadata = 4;
  Provenance provenance = 5;
  repeated Relation relations = 6;
  TemporalInfo temporal = 7;
}

message EmbeddingVersion {
  string model_id = 1;
  string model_version = 2;
  repeated float vector = 3;
  uint32 dimension = 4;
  uint32 created_at = 5;
  map<string, string> model_params = 6;
}

message Provenance {
  string source_id = 1;          // Original document/source
  string chunk_id = 2;           // Specific chunk within source
  uint32 chunk_position = 3;     // Position in source
  string extraction_method = 4;   // How it was extracted
  uint32 extracted_at = 5;       // When extracted
  map<string, string> metadata = 6; // Additional provenance data
}
----

*Use Cases*:
- Track multiple embedding versions as models evolve
- Maintain full audit trail of data lineage
- Enable filtering by source or extraction method

*Integration Notes*:
- Protos: add `proximadb.v1.entity` in `proto/proximadb/v1/entity.proto` and import from existing `collection.proto` and `search.proto`.
- Storage: persist `Entity` as the logical record; store vectors in existing engines keyed by `(collection_id, entity_id, model_id, modality)`; keep a thin row-store for the `Entity` header (typed/flexible metadata, temporal, provenance) in SST.
- Indexing: extend `IndexConfig` to allow `name` and `selector` (e.g., `model_id`, `modality`) to map embeddings to indices; maintain one primary index per modality with optional auxiliaries.
- Keys: canonical primary key `entity_id` (string), with partitioning by `source_id` and/or time where configured.
- MVCC: reuse existing MVCC; add `tombstone` at `EmbeddingVersion` granularity for soft-deletes and re-embeds.

==== 1.2 Enhanced Metadata System

*Requirement*: Support both typed (optimized) and flexible (ad-hoc) metadata.

*Design*:
[source,protobuf]
----
message TypedMetadata {
  // Declared at collection creation for optimization
  map<string, TypedField> fields = 1;
}

message TypedField {
  oneof value {
    string string_value = 1;
    int64 int_value = 2;
    double double_value = 3;
    bool bool_value = 4;
    repeated string string_array = 5;
    Timestamp timestamp_value = 6;
  }
  bool indexed = 7;  // Whether to create index
  bool filterable = 8;  // Whether to allow filtering
}
----

*Implementation*:
- Typed fields use columnar storage (Parquet) for performance
- Flexible fields stored as JSON with automatic indexing for frequently queried paths
- Hybrid query optimizer chooses between index scan and full scan

*DDL and Config*:
- Collection creation: extend `CollectionConfig` with `typed_metadata_schema` describing field names, types, and `indexed/filterable` flags; example:
[source,yaml]
----
typed_metadata_schema:
  fields:
    author: { type: string, indexed: true, filterable: true }
    year:   { type: int64, indexed: true, filterable: true }
    tags:   { type: string_array, indexed: true }
----
- Auto-indexing for flexible fields: track query frequency per JSONPath; promote to secondary index when threshold crossed (e.g., 100+ queries/day, 95% cache miss).
- Enforcement: typed schema is optional; if present, validate on write and coerce types when safe.

==== 1.3 Declarative Query Language Extensions

*Requirement*: SQL-like interface with semantic operations.

*New Operators*:
[source,sql]
----
-- Similarity search with metadata filters
FIND entities
WHERE SIMILAR(embedding, "quantum computing", model="openai/ada-002", top_k=10)
  AND metadata.year > 2020
  AND metadata.domain = 'physics';

-- Multi-model similarity
FIND entities  
WHERE SIMILAR_ANY(embeddings, "quantum", top_k=5)
ORDER BY similarity DESC;

-- Provenance-aware search
FIND entities
WHERE SIMILAR(embedding, "climate change")
  AND provenance.source_id IN (SELECT id FROM sources WHERE trusted = true);
----

==== 1.4 Versioning Support

*Requirement*: Multiple embeddings per entity with model tracking.

*Implementation*:
- Store embeddings as array with model metadata
- Query interface allows specifying model/version
- Automatic fallback to latest if not specified
- Migration utilities for re-embedding with new models

*Indexing Strategy*:
- Maintain per-(model_id, modality) posting lists to avoid fan-out scans.
- Default search resolves to `latest(model_id)` per modality unless caller pins a version.
- Background compactor prunes superseded embeddings when policy configured (retain N versions or by TTL).

=== Tier 2: Differentiating Features (v0.2)

==== 2.1 Graph Relationships

*Requirement*: Native entity-to-entity relationships.

*Design*:
[source,protobuf]
----
message Relation {
  string source_entity_id = 1;
  string target_entity_id = 2;
  string relation_type = 3;  // "cites", "part_of", "contradicts"
  float weight = 4;          // Strength of relationship
  uint32 created_at = 5;
  map<string, string> properties = 6;
}
----

*Query Extensions*:
[source,sql]
----
-- Graph traversal
FIND entities
WHERE SIMILAR(embedding, "machine learning")
FOLLOW relations.cites TO depth=2
RETURN path;

-- Relationship filtering
FIND entities e1, e2
WHERE RELATION(e1, e2, type="contradicts")
  AND e1.metadata.author != e2.metadata.author;
----

*APIs and Storage*:
- Protos: `Relation` lives in `entity.proto`; add gRPC `RelationsService` with `CreateRelation`, `DeleteRelation`, `ListRelations`, `Traverse`.
- Storage: adjacency list per `entity_id` persisted in SST keyed by `(collection_id, entity_id, relation_type)`; maintain reverse edges for fast inbound traversal.
- Consistency: relation writes can be co-authored with entity upserts (same WAL entry) or independent with cross-reference validation.

==== 2.2 Context Assembly

*Requirement*: Reconstruct full documents from chunks.

*Design*:
[source,rust]
----
pub struct ContextAssembler {
    pub fn assemble_document(&self, source_id: &str) -> Document {
        // 1. Find all chunks from source
        // 2. Order by chunk_position
        // 3. Reconstruct with overlap handling
        // 4. Return unified document
    }
    
    pub fn assemble_context(&self, entity_ids: Vec<String>, radius: usize) -> Context {
        // 1. Get surrounding chunks for each entity
        // 2. Merge overlapping contexts
        // 3. Return coherent narrative
    }
}
----

*Design Details*:
- Source linkage: reuse structures from `docs/09-roadmap/planned/source_content_storage_design.adoc`; reference chunks via `(source_id, chunk_id, position)`.
- Overlap handling: prefer longest non-overlapping spans; merge when `gap <= overlap_threshold` (configurable, default 20 tokens).
- Deduplication: compute MinHash signatures for contiguous paragraphs to avoid repeated context in assemblies.
- Output: return `Context` with ordered `segments` carrying `text`, `provenance`, and `score` fields.

*Query Support*:
[source,sql]
----
-- Reconstruct document
ASSEMBLE document
FROM chunks
WHERE source_id = 'doc_123'
ORDER BY chunk_position;

-- Get context around search results
FIND entities
WHERE SIMILAR(embedding, "climate policy")
ASSEMBLE CONTEXT radius=2;
----

==== 2.3 Multimodal Support

*Requirement*: Store and query across modalities.

*Design*:
[source,protobuf]
----
message MultimodalEntity {
  string id = 1;
  repeated ModalEmbedding embeddings = 2;
}

message ModalEmbedding {
  enum Modality {
    TEXT = 0;
    IMAGE = 1;
    AUDIO = 2;
    VIDEO = 3;
  }
  Modality modality = 1;
  EmbeddingVersion embedding = 2;
  bytes raw_data = 3;  // Optional original data
}
----

*Operational Notes*:
- Indexing: maintain separate indices per modality; name convention `${modality}-${model_id}`; cross-modal queries dispatch to an alignment model or mapping function configured per collection.
- Raw data: store large `raw_data` in external object storage (S3/GCS/Azure); persist only content-addressable URI and hash in the `MultimodalEntity`.
- Scoring: for fusion, compute `score = Σ w_i * normalize(sim_i)` with `w_i` from `FUSE` clause; normalization defaults to z-score per index.

*Execution Model*:
- Store ontologies as versioned documents in a dedicated `ontology` namespace; compile to lookup tries and relation expansion rules at load.
- Query planner uses ontology to expand concepts (e.g., `disease` → subconcepts) with controllable expansion depth and weights.

*Cross-Modal Queries*:

----

*Signals and Actions*:
- Signals: track per-query template latency, selectivity, cache hit/miss, result churn; bucket templates by normalized AST.
- Actions: propose creation of secondary indices (typed fields bloom/bitmap), HNSW ef tuning, IVF centroids adjustments, or HOT partitions.
- Safety: changes land behind feature flags; measure before/after with automatic rollback on regression.

==== 2.4 Temporal Awareness

*Requirement*: Time-aware storage and queries.

*Design*:
[source,protobuf]
----
message TemporalInfo {
  uint32 created_at = 1;
  uint32 valid_from = 2;
  uint32 valid_to = 3;
  bool is_current = 4;
  repeated TemporalVersion versions = 5;
}

message TemporalVersion {
  uint32 timestamp = 1;
  string version_id = 2;
  map<string, string> changes = 3;
}
----

*Temporal Queries*:
[source,sql]
----
-- Point-in-time query
FIND entities
WHERE SIMILAR(embedding, "AI regulation")
AT TIME '2023-01-01';

-- Temporal range query
FIND entities
WHERE metadata.topic = 'climate'
VALID BETWEEN '2020-01-01' AND '2023-12-31';

-- Evolution tracking
TRACK EVOLUTION OF concept
WHERE name = 'machine learning'
FROM '2015-01-01' TO NOW;
----

*Indexing and Semantics*:
- Clock source: use server-side monotonic clock for `created_at` and rely on client-provided validity windows; reject inverted ranges.
- Index: maintain time-ordered segment tree or per-day partitions; planner prunes partitions prior to vector search.
- Compaction: when `valid_to` is set, mark non-current; background tasks merge historical snapshots according to retention policy.

==== 3.3 Streaming Ingestion

*Requirement*: Real-time data ingestion with incremental indexing.

*Design*:
- Event-driven ingestion pipeline
- Incremental index updates without full rebuild
- Backpressure handling for rate limiting
- Exactly-once semantics with checkpointing

*Connectors and Semantics*:
- Sources: Kafka, Kinesis, Pub/Sub, NATS (pluggable); each source defines an `idempotency_key` per record.
- Checkpoints: maintain per-partition offsets in a durable state store; commit after WAL append and index acknowledgment.
- Retries: exponential backoff with DLQ routing for permanent failures; provide `replay` admin API by time or offset.

=== REST Endpoints

- `POST /api/v1/entities/{collection_id}`: upsert entity (idempotent via `entity_id`).
- `GET /api/v1/entities/{collection_id}/{entity_id}`: fetch entity with embeddings metadata.
- `DELETE /api/v1/entities/{collection_id}/{entity_id}`: soft-delete or hard-delete with `?hard=true`.
- `POST /api/v1/search/{collection_id}`: semantic search with SIMILAR and filters; `?progressive=true` enables staged results.
- `POST /api/v1/relations/{collection_id}`: create relation; `DELETE`/`GET` similarly.
- `POST /api/v1/context/{collection_id}/assemble`: assemble context/document.

== Validation and Limits

- Max entity size: 1 MB for header (typed+flexible metadata, provenance); embeddings unbounded but recommend <8 models x 4096 dims.
- Max relations per entity: default 10k; hard cap 1M with paging and degree limiting in traversals.
- Max modalities: 4 (TEXT, IMAGE, AUDIO, VIDEO); extensible via enum but indices required per modality.
- Query limits: `top_k` default 10, max 1000; traversal depth default 2, max 5.
- Write batch: up to 10k entities per request; WAL entry size capped at 16 MB.

== Error Model

- Error envelope contains `code`, `message`, `details`, and `retryable` boolean.
- Common codes: `INVALID_ARGUMENT`, `FAILED_PRECONDITION` (schema/ACL), `NOT_FOUND`, `ALREADY_EXISTS`, `RESOURCE_EXHAUSTED`, `UNAVAILABLE` (retryable), `INTERNAL`.
- Partial success semantics for batch upserts with per-item status; include `failed_indices` for index-level failures.

== Default Configuration

- Progressive search stages: `[candidate_k=200, rerank_k=50]` then `[candidate_k=1000, rerank_k=100]`.
- Typed metadata: no fields by default; recommended to declare high-selectivity fields (author, year).
- Retention: keep last 2 embedding versions per (model, modality); relations TTL none (infinite) unless configured.
- Quantization: enabled by default for embeddings dimension > 2048 with PQ m=64.

- Support PII tagging in metadata; row-level filters can enforce redaction at query time.

- DoS: degree and depth limits for traversal, per-tenant QPS and memory quotas.
- Leakage: ACL-enforced predicate filters; hash entity ids in traces and logs.

== Compatibility Matrix (Initial)

- Engines: VIPER, SST supported for embeddings; DSST/DVIPER evaluated post-MVP.
- Indexing: HNSW, IVF, PQ supported; ANNOY/LSH later.
- SDKs: Python gRPC first; REST parity in next minor.

== Technical Architecture

=== Storage Layer Changes

[source,mermaid]
----
graph TD
    A[Entity Store] --> B[Vector Storage]
    A --> C[Metadata Store]
    A --> D[Graph Store]
    A --> E[Provenance Store]
    
    B --> F[VIPER Engine]
    B --> G[SST Engine]
    
    C --> H[Typed Fields<br/>Parquet]
    C --> I[Flexible Fields<br/>JSON]
    
    D --> J[Adjacency Index]
    D --> K[Property Graph]
    
    E --> L[Source Registry]
    E --> M[Lineage Graph]
----

*Data Layout*:
- Entity header table (SST): key `(collection_id, entity_id)` → value `{typed_metadata, flexible_metadata, temporal, provenance_summary}`.
- Embeddings table (vector engines): key `(collection_id, entity_id, model_id, modality, version)` → vector payload + small header.
- Relations table (SST): key `(collection_id, entity_id, relation_type, target_id)` → `{weight, created_at, properties}` and reverse index.
- Provenance registry (SST): `source_id` → source attributes; chunk index keyed by `(source_id, chunk_id)`.

=== Query Processing Pipeline

[source,mermaid]
----
sequenceDiagram
    participant Client
    participant Parser
    participant Planner
    participant Executor
    participant Storage
    
    Client->>Parser: SQL Query
    Parser->>Parser: Parse SIMILAR, FOLLOW, ASSEMBLE
    Parser->>Planner: AST
    Planner->>Planner: Optimize query plan
    Planner->>Executor: Execution plan
    Executor->>Storage: Vector search
    Executor->>Storage: Graph traversal
    Executor->>Storage: Context assembly
    Storage-->>Executor: Results
    Executor-->>Client: Assembled response
----

*Planner Steps*:
- Parse SQL-like query → AST; normalize to a canonical template for caching.
- Apply temporal pruning and metadata predicate pushdown using typed/flexible indexes.
- Choose index set by modality/model; if progressive, define stages with `candidate_k` and `rerank_k` per stage.
- Execute vector search → candidate set; expand via `FOLLOW` when present with bounded depth; deduplicate by `entity_id`.
- Assemble context when requested; compute final scores and envelope response.

== Consistency and Transactions

- Write path: append to WAL with a composite record `{entity, embeddings[], relations[]}`; perform storage updates; mark commit when all sub-stores ack or schedule repair.
- Idempotency: deduplicate by `(collection_id, entity_id, client_op_id)` when provided.
- Repairer: background task reconciles mismatches across stores using WAL.

== Security and Access Control

- Multi-tenant isolation via `tenant_id` carried in collection and all keys.
- ACLs: collection-level roles (admin, writer, reader) and optional row-level filters expressed as metadata predicates.
- Audit: provenance changes and relation mutations are audited with actor and timestamp.

== Observability

- Metrics: `sks_search_latency_ms`, `sks_traversal_nodes_visited`, `sks_context_segments`, `sks_index_hit_ratio`, `sks_compactions_total`.
- Tracing: spans for `parse`, `plan`, `vector_search`, `graph_traverse`, `assemble`, `commit` with entity_id tags (hashed).
- Logs: structured JSON with op ids; sampling for high-volume search paths.

== Data Lifecycle

- Retention: per-collection policies for embeddings history, relations TTL, provenance retention.
- Compaction windows: daily for metadata/relations, weekly for embeddings if cold.
- Export: snapshot APIs to materialize entities and relations for offline analysis.

== Performance Considerations

=== Storage Overhead

* **Entity Model**: ~15% overhead for provenance and relations
* **Multi-Embeddings**: Linear with number of models (mitigated by compression)
* **Graph Index**: O(E) space for E edges (use sparse representation)

=== Query Performance

* **SIMILAR**: Maintain existing sub-millisecond latency
* **FOLLOW**: Graph traversal in O(k*d) for depth d, degree k
* **ASSEMBLE**: Document reconstruction in O(n log n) for n chunks
* **Temporal**: Time-range index for O(log t) lookup

=== Optimization Strategies

1. **Hierarchical Caching**: Entity → Embedding → Index
2. **Lazy Loading**: Load relations/provenance on demand
3. **Partition Pruning**: Time-based and source-based partitions
4. **Adaptive Compression**: Compress cold embeddings more aggressively

== Conclusion

The evolution from ProximaDB to a Semantic Knowledge Store represents a significant opportunity to define a new category of data system. By carefully implementing the features in three tiers, we can deliver immediate value while building toward a comprehensive knowledge management platform.

The key differentiators will be:

1. **Unified Model**: Entities with vectors, metadata, relations, and provenance
2. **Declarative Queries**: SQL-like language with semantic operations
3. **Knowledge Assembly**: Reconstruct context and narratives
4. **Temporal Awareness**: Track knowledge evolution over time
5. **Multimodal First**: Native support for all content types

With this roadmap, ProximaDB can transcend the limitations of current vector databases and become the foundation for next-generation AI applications that require rich semantic understanding and knowledge management.
