== Executive Summary

This document specifies the requirements, design, and implementation plan for evolving ProximaDB from a high-performance vector database into a comprehensive Semantic Knowledge Store (SKS). The SKS represents a new category of data system that unifies embeddings, metadata, relationships, provenance, and temporal reasoning into a single coherent platform.

== Current State Analysis

=== ProximaDB Existing Capabilities

ProximaDB currently provides:

* **Vector Storage & Search**: High-performance vector similarity search with multiple distance metrics
* **Storage Engines**: Four storage engines (VIPER, SST, DSST, DVIPER) optimized for different workloads
* **Metadata Support**: Basic metadata filtering with typed fields (MetadataItem proto structure)
* **SQL Interface**: SQL-like query language for vector search with metadata filters
* **Indexing**: Six indexing algorithms (HNSW, IVF, PQ, FLAT, ANNOY, LSH)
* **Quantization**: Advanced quantization for storage and memory optimization
* **MVCC**: Multi-version concurrency control with versioning support
* **Cloud Storage**: S3/GCS/Azure blob storage support
* **Compression**: 14 compression algorithms with context-aware selection

== Feature Requirements

=== Tier 1: MVP Features (v0.1)

==== 1.1 Entity Data Model

*Requirement*: Transform from vector-centric to entity-centric storage model.

*Design*:
[source,protobuf]
----
message Entity {
  string id = 1;
  repeated EmbeddingVersion embeddings = 2;
  TypedMetadata typed_metadata = 3;
  google.protobuf.Struct flexible_metadata = 4;
  Provenance provenance = 5;
  repeated Relation relations = 6;
  TemporalInfo temporal = 7;
}

message EmbeddingVersion {
  string model_id = 1;
  string model_version = 2;
  repeated float vector = 3;
  uint32 dimension = 4;
  uint32 created_at = 5;
  map<string, string> model_params = 6;
}

message Provenance {
  string source_id = 1;          // Original document/source
  string chunk_id = 2;           // Specific chunk within source
  uint32 chunk_position = 3;     // Position in source
  string extraction_method = 4;   // How it was extracted
  uint32 extracted_at = 5;       // When extracted
  map<string, string> metadata = 6; // Additional provenance data
}
----

*Use Cases*:
- Track multiple embedding versions as models evolve
- Maintain full audit trail of data lineage
- Enable filtering by source or extraction method

==== 1.2 Enhanced Metadata System

*Requirement*: Support both typed (optimized) and flexible (ad-hoc) metadata.

*Design*:
[source,protobuf]
----
message TypedMetadata {
  // Declared at collection creation for optimization
  map<string, TypedField> fields = 1;
}

message TypedField {
  oneof value {
    string string_value = 1;
    int64 int_value = 2;
    double double_value = 3;
    bool bool_value = 4;
    repeated string string_array = 5;
    Timestamp timestamp_value = 6;
  }
  bool indexed = 7;  // Whether to create index
  bool filterable = 8;  // Whether to allow filtering
}
----

*Implementation*:
- Typed fields use columnar storage (Parquet) for performance
- Flexible fields stored as JSON with automatic indexing for frequently queried paths
- Hybrid query optimizer chooses between index scan and full scan

==== 1.3 Declarative Query Language Extensions

*Requirement*: SQL-like interface with semantic operations.

*New Operators*:
[source,sql]
----
-- Similarity search with metadata filters
FIND entities
WHERE SIMILAR(embedding, "quantum computing", model="openai/ada-002", top_k=10)
  AND metadata.year > 2020
  AND metadata.domain = 'physics';

-- Multi-model similarity
FIND entities  
WHERE SIMILAR_ANY(embeddings, "quantum", top_k=5)
ORDER BY similarity DESC;

-- Provenance-aware search
FIND entities
WHERE SIMILAR(embedding, "climate change")
  AND provenance.source_id IN (SELECT id FROM sources WHERE trusted = true);
----

==== 1.4 Versioning Support

*Requirement*: Multiple embeddings per entity with model tracking.

*Implementation*:
- Store embeddings as array with model metadata
- Query interface allows specifying model/version
- Automatic fallback to latest if not specified
- Migration utilities for re-embedding with new models

=== Tier 2: Differentiating Features (v0.2)

==== 2.1 Graph Relationships

*Requirement*: Native entity-to-entity relationships.

*Design*:
[source,protobuf]
----
message Relation {
  string source_entity_id = 1;
  string target_entity_id = 2;
  string relation_type = 3;  // "cites", "part_of", "contradicts"
  float weight = 4;          // Strength of relationship
  uint32 created_at = 5;
  map<string, string> properties = 6;
}
----

*Query Extensions*:
[source,sql]
----
-- Graph traversal
FIND entities
WHERE SIMILAR(embedding, "machine learning")
FOLLOW relations.cites TO depth=2
RETURN path;

-- Relationship filtering
FIND entities e1, e2
WHERE RELATION(e1, e2, type="contradicts")
  AND e1.metadata.author != e2.metadata.author;
----

==== 2.3 Multimodal Support

*Requirement*: Store and query across modalities.

*Design*:
[source,protobuf]
----
message MultimodalEntity {
  string id = 1;
  repeated ModalEmbedding embeddings = 2;
}

message ModalEmbedding {
  enum Modality {
    TEXT = 0;
    IMAGE = 1;
    AUDIO = 2;
    VIDEO = 3;
  }
  Modality modality = 1;
  EmbeddingVersion embedding = 2;
  bytes raw_data = 3;  // Optional original data
}
----

*Cross-Modal Queries*:
[source,sql]
----
-- Text to image search
FIND images
WHERE SIMILAR_CROSS(text_embedding, "sunset over mountains", target_modality=IMAGE);

-- Multimodal fusion
FIND entities
WHERE SIMILAR(text_embedding, "product description")
  AND SIMILAR(image_embedding, @product_image)
FUSE weights=[0.7, 0.3];
----

==== 2.4 Temporal Awareness

*Requirement*: Time-aware storage and queries.

*Design*:
[source,protobuf]
----
message TemporalInfo {
  uint32 created_at = 1;
  uint32 valid_from = 2;
  uint32 valid_to = 3;
  bool is_current = 4;
  repeated TemporalVersion versions = 5;
}

message TemporalVersion {
  uint32 timestamp = 1;
  string version_id = 2;
  map<string, string> changes = 3;
}
----

*Temporal Queries*:
[source,sql]
----
-- Point-in-time query
FIND entities
WHERE SIMILAR(embedding, "AI regulation")
AT TIME '2023-01-01';

-- Temporal range query
FIND entities
WHERE metadata.topic = 'climate'
VALID BETWEEN '2020-01-01' AND '2023-12-31';

-- Evolution tracking
TRACK EVOLUTION OF concept
WHERE name = 'machine learning'
FROM '2015-01-01' TO NOW;
----

== Migration Strategy

=== Backward Compatibility

1. **Dual API Support**: Maintain existing vector DB APIs while adding SKS features
2. **Progressive Enhancement**: Existing collections work without modification
3. **Opt-in Features**: New features enabled per collection via configuration

=== Migration Path

[source,yaml]
----
migration:
  phase1:
    - Add entity wrapper around existing vectors
    - Auto-generate provenance from existing metadata
    - Enable typed metadata for new collections
  
  phase2:
    - Batch convert existing collections to entity model
    - Build relationship graph from metadata hints
    - Enable temporal tracking going forward
  
  phase3:
    - Full SKS features for new data
    - Background migration of historical data
    - Deprecate legacy APIs
----

== Performance Considerations

=== Storage Overhead

* **Entity Model**: ~15% overhead for provenance and relations
* **Multi-Embeddings**: Linear with number of models (mitigated by compression)
* **Graph Index**: O(E) space for E edges (use sparse representation)

=== Query Performance

* **SIMILAR**: Maintain existing sub-millisecond latency
* **FOLLOW**: Graph traversal in O(k*d) for depth d, degree k
* **ASSEMBLE**: Document reconstruction in O(n log n) for n chunks
* **Temporal**: Time-range index for O(log t) lookup

=== Optimization Strategies

1. **Hierarchical Caching**: Entity → Embedding → Index
2. **Lazy Loading**: Load relations/provenance on demand
3. **Partition Pruning**: Time-based and source-based partitions
4. **Adaptive Compression**: Compress cold embeddings more aggressively

== Conclusion

The evolution from ProximaDB to a Semantic Knowledge Store represents a significant opportunity to define a new category of data system. By carefully implementing the features in three tiers, we can deliver immediate value while building toward a comprehensive knowledge management platform.

The key differentiators will be:

1. **Unified Model**: Entities with vectors, metadata, relations, and provenance
2. **Declarative Queries**: SQL-like language with semantic operations
3. **Knowledge Assembly**: Reconstruct context and narratives
4. **Temporal Awareness**: Track knowledge evolution over time
5. **Multimodal First**: Native support for all content types

With this roadmap, ProximaDB can transcend the limitations of current vector databases and become the foundation for next-generation AI applications that require rich semantic understanding and knowledge management.
