== Technical Architecture

=== Overall Implementation Strategy

* **Modular Architecture:** Three independent engines that can operate standalone or unified
* **Proto-First Design:** Zero-copy protobuf serialization throughout
* **Arc-Based Memory:** Shared memory pool with Arc<T> for zero-copy between engines
* **Intra-Process Performance:** All engines in single process, no network overhead
* **Asynchronous & Concurrent:** Tokio-based async runtime with work-stealing

== Phase 1: Core Graph Data Model & Storage Integration

*   **Goal:** Establish the fundamental data structures for nodes, edges, and properties, and integrate their persistence with ProximaDB's `StorageEngine`.

*   **Tasks:**

    1.  **Define Core Protobuf Schemas:**
        *   Create `proto/graph.proto` (or similar) to define `Node`, `Edge`, and `Property` messages.
        *   `Node`: `id` (UUID/ULID), `labels` (list of strings), `properties` (map<string, Value>).
        *   `Edge`: `id` (UUID/ULID), `from_node_id`, `to_node_id`, `type` (string), `properties` (map<string, Value>).
        *   `Value`: A Protobuf `oneof` to support various property types (string, int64, float64, bool, bytes, etc.).
        *   **Design Tradeoff:** Using a generic `map<string, Value>` for properties offers flexibility but might incur serialization/deserialization overhead compared to strongly typed schemas for known properties. This is a good starting point for schema-less properties.

    2.  **Implement Rust Data Structures:**
        *   Generate Rust structs from the Protobuf definitions using `prost` or similar.
        *   Implement `From` and `Into` traits for conversion between Protobuf and internal Rust representations.

    3.  **Storage Engine Integration (Key-Value Mapping):**
        *   Determine how nodes and edges will be mapped to key-value pairs in the `StorageEngine`.
        *   **Recommendation:**
            *   Nodes: `nodes:<node_id>` -> `Node` protobuf bytes.
            *   Edges: `edges:<edge_id>` -> `Edge` protobuf bytes.
            *   Adjacency: `node_out_edges:<node_id>:<edge_type>:<edge_id>` -> empty/metadata.
            *   Adjacency: `node_in_edges:<node_id>:<edge_type>:<edge_id>` -> empty/metadata.
        *   **Design Tradeoff:** Storing adjacency lists separately allows for efficient traversal from a node. This is generally preferred over adjacency matrices for sparse graphs common in real-world scenarios.

    4.  **Basic CRUD Operations (Storage Layer):**
        *   In `src/storage/engine.rs` (or a new `src/storage/graph_store.rs`), implement:
            *   `put_node(node: Node) -> Result<()>`
            *   `get_node(node_id: Uuid) -> Result<Option<Node>>`
            *   `delete_node(node_id: Uuid) -> Result<()>`
            *   `put_edge(edge: Edge) -> Result<()>`
            *   `get_edge(edge_id: Uuid) -> Result<Option<Edge>>`
            *   `delete_edge(edge_id: Uuid) -> Result<()>`
            *   `get_out_edges(node_id: Uuid, edge_type: Option<String>) -> Result<Vec<Edge>>`
            *   `get_in_edges(node_id: Uuid, edge_type: Option<String>) -> Result<Vec<Edge>>`
        *   Ensure these operations are atomic and leverage the existing WAL and memtable for durability and performance.

*   **Verification:**
    *   Write unit tests for all new data structures and storage layer CRUD operations.
    *   Ensure data can be written, read, and deleted correctly.

=== High-Performance Traversal Algorithms

[source,rust]
----
// Optimized BFS with early termination and filtering
pub async fn parallel_bfs(
    &self,
    start: NodeId,
    max_depth: u32,
    filter: Option<Box<dyn Fn(&Node) -> bool>>,
    early_stop: Option<Box<dyn Fn(&[Node]) -> bool>>,
) -> Result<Vec<Node>> {
    // Use bit vector for visited tracking (cache-friendly)
    let visited = Arc::new(BitVec::with_capacity(self.node_count()));
    
    // Parallel frontier processing with work-stealing
    let (tx, rx) = mpsc::channel(1000);
    
    // Process levels in parallel
    for depth in 0..max_depth {
        let frontier = self.process_frontier_parallel(
            frontier,
            &visited,
            filter.as_ref(),
        ).await?;
        
        if let Some(ref stop) = early_stop {
            if stop(&frontier) {
                break;
            }
        }
    }
}
----

        *   **Recommendation:** Use a separate key-value store for indexes: `index:<property_key>:<property_value>:<entity_id>` -> empty.

=== Critical Implementation Notes

**1. Always Use Arc for Shared Data:**
[source,rust]
----
// ✅ CORRECT: Use Arc for zero-copy sharing
pub struct Node {
    pub id: NodeId,
    pub labels: Arc<Vec<String>>,      // Shared across engines
    pub properties: Arc<PropertyMap>,   // No cloning needed
    pub embedding: Option<Arc<Vec<f32>>>, // Shared with vector engine
}

// ❌ WRONG: Don't clone data
pub struct Node {
    pub properties: PropertyMap,  // Will be cloned everywhere
}
----

**2. Maintain Mode Separation:**
[source,rust]
----
pub enum OperationMode {
    VectorOnly,   // Graph operations return errors
    GraphOnly,    // Vector operations return errors  
    Unified,      // Both operations available
}

impl GraphService {
    pub fn new(mode: OperationMode) -> Self {
        match mode {
            OperationMode::GraphOnly | OperationMode::Unified => {
                // Initialize graph engine
            }
            OperationMode::VectorOnly => {
                // Graph operations will fail gracefully
            }
        }
    }
}
----
