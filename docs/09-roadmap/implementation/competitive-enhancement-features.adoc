==== Replication Sink Integration (C6)

The replication sink handles data replication to shard replicas:

[source,rust]

// Create replication sink
let sink = GrpcReplicationSink::new(connection_manager.clone());

// Use in replication module
async fn replicate_to_followers(
    sink: &impl ReplicationSink,
    replicas: &[NodeEndpoint],
    entry: ReplicateRequest,
    consistency: ConsistencyLevel,
) -> Result<(), ReplicationError> {
    let responses = futures::future::join_all(
        replicas.iter().map(|replica| sink.replicate(replica, entry.clone()))
    ).await;

    // Check consistency requirements
    let acked = responses.iter().filter(|r| r.is_ok()).count();
    match consistency {
        ConsistencyLevel::One => if acked >= 1 { Ok(()) } else { Err(...) },
        ConsistencyLevel::Quorum => if acked >= replicas.len() / 2 + 1 { Ok(()) } else { Err(...) },
        ConsistencyLevel::All => if acked == replicas.len() { Ok(()) } else { Err(...) },
    }
}

[source,rust]

// Create search fanout
let fanout = GrpcSearchFanout::new(connection_manager.clone());

// Use in distributed query execution
async fn distributed_search(
    fanout: &impl SearchFanout,
    shards: &[(NodeEndpoint, ShardId)],
    query: Vec<f32>,
    top_k: usize,
) -> Result<Vec<SearchResult>, SearchError> {
    // Fan-out to all shards
    let futures: Vec<_> = shards.iter().map(|(endpoint, shard_id)| {
        let req = ShardSearchRequest {
            shard_id: shard_id.clone(),
            vector: query.clone(),
            top_k,
            ..Default::default()
        };
        fanout.shard_search(endpoint, req)
    }).collect();

    let responses = futures::future::join_all(futures).await;

    // Merge results
    let mut all_results: Vec<SearchResult> = responses
        .into_iter()
        .filter_map(|r| r.ok())
        .flat_map(|r| r.results)
        .collect();

    // Sort by score and take top_k
    all_results.sort_by(|a, b| b.score.partial_cmp(&a.score).unwrap());
    all_results.truncate(top_k);

    Ok(all_results)
}

    /// This node is a follower
    Follower,
    /// Status is unknown (election in progress)

}

/// Leader election manager

**Usage Example**:

[source,rust]
----
use proximadb::embedded::coordination::LeaderElection;

// Try to become leader
let election = LeaderElection::new("/path/to/data", "node1")?;

if election.is_leader() {
    // This process is the leader, can write
    println!("I am the leader!");
    db.insert(...).await?;
} else {
    // This process is a follower, read-only
    println!("Following leader: {:?}", election.leader_id());
    let results = db.search(...).await?;
}

// Step down from leadership
election.step_down()?;

// Try to become leader again
if election.try_become_leader("/path/to/data")? {
    println!("Became leader!");
}

**Key Observations**:

* Sub-microsecond cache hits enable query result caching without measurable overhead
* Lock-free DashMap implementation provides linear scaling with concurrent readers
* Partial invalidation (single collection) achieves similar performance to full invalidation due to efficient dependency tracking
* Mixed read/write workloads maintain high throughput with minimal contention

=== Streaming Search Performance

The `EmbeddedSearchIterator` (F3) provides measurable improvements over non-streaming search, particularly for large result sets:

[cols="2,2", options="header"]
|===
| Scenario | Performance Improvement

| 1,536 dimensions
| 5.0% faster than non-streaming

| 3,072 dimensions
| 3.9% faster than non-streaming

| 32.4% faster than non-streaming

| ~1.3ns
|===

**Key Observations**:

* Streaming provides consistent improvements across all tested vector dimensions
* Performance gains increase significantly with larger result sets due to reduced memory allocation pressure
* Per-result memory overhead is negligible (~1.3 nanoseconds), making streaming suitable for all use cases
* Backpressure control through bounded channels prevents memory exhaustion with large result sets
