= Distributed Architecture – Implementation Plan Prompt
:toc: left
:toclevels: 2

Purpose
- Provide a complete, actionable prompt any coding assistant can follow to implement ProximaDB’s initial distributed architecture (sharding + replication) while honoring the collection→engine binding and existing server APIs.

Scope (Phase 1)
- Collection‑level sharding with consistent hashing and routing.
- Optional vector‑aware sharding strategy for improved locality.
- Per‑shard replication with configurable consistency (ONE, QUORUM, ALL).
- Node membership, health, and shard registry (in‑memory + persisted metadata).
- RPC for remote shard search/write; merge results server‑side.
- Admin APIs + config plumbing; Python SDK routing updates.

Non‑Goals (Phase 1)
- Cross‑region replication, multi‑tenant network isolation, or dynamic rebalancing that moves data live (basic manual rebalance hooks only).
- Distributed transactions across collections; graph analytics distribution (later phases).

Reference Materials
- Q3 2025 plan: docs/09-roadmap/implementation/active/Q3_2025_IMPLEMENTATION.adoc (CollectionShardManager, EngineReplication scaffolding)
- Future notes: docs/09-roadmap/future/ROADMAP_2025.adoc, PRIORITY_ACTION_PLAN.adoc
- Server endpoints and router: src/network/rest/v1/handlers.rs, src/network/multi_server.rs

High‑Level Architecture
- Cluster Coordinator: maintains shard registry, node membership, and placement decisions.
- Shard Manager (per node): executes local operations for assigned shards and proxies remote.
- Replication Engine: WAL‑first write + async replica fanout; promotion on failure.
- RPC Layer: internal node‑to‑node gRPC for shard operations.
- SDK Router: resolves collection → shard(s) and sends requests to the correct node.

Optional Enhancements (Phase 1 candidates)
- Query Planner: predict relevant shards; adaptive fanout to reduce unnecessary queries.
- Compaction Coordinator: serialize shard compactions to prevent resource contention.
- Enhanced metrics: shard hotness, fanout count, merge time, replication lag.

Data Models
- ShardInfo { shard_id, collection, engine_type, node_id, key_range(start_hash,end_hash), replicas[] }
- ReplicaInfo { node_id, address, role: Primary|Follower, lag_ms }
- DistributedConfig { sharding_enabled, shard_count, replication_factor, consistency_level }
- HealthStatus { node_id, role, shards_local, shards_replica, last_heartbeat_ms }

Work Items (ordered)
1) Core crates and modules
- Add `src/distributed/mod.rs`
- Sharding: `src/distributed/sharding/collection_sharding.rs`
- Replication: `src/distributed/replication/engine_replication.rs`
- Membership: `src/distributed/membership/mod.rs`
- RPC: `src/distributed/rpc/mod.rs` (gRPC service definitions shared with server)

2) Sharding implementation
- Hashing: consistent hash on a routing_key or id → shard_id.
- Registry: RwLock<HashMap<Collection, Vec<ShardInfo>>>; persist to metadata backend.
- Placement: simple round‑robin across live nodes with replication_factor.
- Routing: route_request(collection, SearchRequest) → shards; distributed_search merges by score.

2A) Vector‑aware sharding (optional, Phase 1)
- Add strategy enum (ConsistentHash | VectorClustering | TimeRange | Hybrid).
- Implement VectorClustering: precompute K centroids; map centroid→shard; periodic rebalance.
- Use for collections with ann_approx=true for better locality.

3) Replication implementation
- WAL‑first append; compute required ACKs from ConsistencyLevel.
- Fanout to replicas (write WAL marker + operation payload via RPC or filesystem abstraction).
- Promotion: detect primary failure, select best replica (lowest lag) and update registry.

3A) Consistency enhancements (Phase 2)
- Read repair: background repair on reads with probability.
- Hinted handoff: buffer writes when replica down and replay later.

4) Membership and health
- Heartbeats: /health JSON already exists; add internal node health gRPC.
- Node registry: in‑memory set + persisted record with last_seen_ms.
- Simple leader (local node) for phase 1; place scaffolding for Raft later.

5) Internal RPC APIs (gRPC)
- service ShardService
  - rpc SearchShard(ShardSearchRequest) returns (ShardSearchResponse)
  - rpc InsertShard(ShardInsertRequest) returns (ShardInsertResponse)
  - rpc ApplyWAL(ShardWalEntry) returns (Ack)
  - rpc GetShardHealth(ShardId) returns (ShardHealth)

5A) Query planner & adaptive fanout (optional, Phase 1)
- Predict relevant shards using vector stats; probe a subset then expand.
- Support streaming partial results and speculative execution for tail latency.

6) Admin REST APIs
- POST /api/v1/cluster/nodes/register {node_id,address}
- GET  /api/v1/cluster/nodes
- POST /api/v1/collections/:id/shard/plan {shard_count,replication_factor}
- POST /api/v1/collections/:id/shard/rebalance
- GET  /api/v1/collections/:id/shard/registry

7) SDK (Python) updates
- Add router: resolve collection → shard(s) using registry (fetched from server).
- Support routing_key in search/insert builders.
- Failover: on node error, retry on replica (respect consistency level). 

8) Feature flags and rollout
- Gate by `[distributed].enabled` and collection flag `distributed=true`.
- Dark‑launch: registry writable but single node execution until enabled.

8A) Dev mode
- `[distributed.dev_mode] enabled=true` to emulate multi‑node in single process.
- Options: single_node_emulation, fake_network_latency_ms.

9) Observability
- Metrics: distributed.search.latency, replication.lag_ms, acks.count, shard.count.
- Logs: shard placement, failover events, promotion decisions.
- Tracing: span per shard RPC and merge stage.

9A) Enhanced metrics
- Shard metrics: shard.size_bytes, shard.query_rate, shard.hot_key_ratio.
- Replication: replication.lag_seconds, catchup_rate_mb_per_sec, promotion_count.
- Search: search.fanout_count, search.merge_time_ms, cross_shard_ratio.

10) Tests (incremental)
- Unit: hashing → shard mapping; merge ordering; ack calculation.
- Integration: 2–3 local nodes via multi‑process or loopback ports.
- Failure: kill one node process mid‑write; verify promotion + recovery.
- Consistency: ONE/QUORUM/ALL behaviors on insert + read‑after‑write.

11) Docs and Examples
- docs/04-operations: distributed deployment guide; systemd/docker compose with 3 nodes.
- Update demo: add `demo/distributed/` with mini‑cluster bootstrap + routed search.

Acceptance Criteria
- Can create sharded+replicated collection via admin API.
- Inserts with QUORUM succeed when one replica is down.
- Search runs across shards and returns correct top_k ordering.
- Node failure triggers replica promotion and registry update.
- Metrics emitted for shard/search and replication paths.

Out‑of‑Scope Callouts

- Online shard split/merge: manual rebalance hook only.
- Cross‑collection transactions: deferred.

Milestones
- M1: Shard registry + distributed search (read‑only)
- M2: Replicated writes with QUORUM + promotion on failure
- M3: Admin APIs + SDK routing + demo
- M4: Hardening, metrics, and docs

Priority Upgrades (from improvements doc)
- Include in Phase 1 if time allows: vector‑aware sharding, query planner, compaction coordinator.
- Phase 2: read repair, shard affinity groups, enhanced failure detection (phi accrual), automated rebalance.

Consensus & Metadata Robustness (Pre-Raft)
- Implement lease-based leader election using metadata store:
  - Acquire a time-limited lease key `/cluster/lease` with term/epoch and owner; renew periodically.
  - Fencing: operations must include current term; nodes reject stale-term operations.
  - Lease expiry triggers re-election.

Secure Internal RPC (mTLS)
- Enable mTLS for ShardService; nodes present certs signed by internal CA.
- Configuration:
```toml
[distributed.rpc.tls]
enabled = true
ca_cert = "/etc/proximadb/ca.pem"
cert_file = "/etc/proximadb/node.crt"
key_file = "/etc/proximadb/node.key"
```

Read Consistency Strategies
- `read_consistency`: PRIMARY | REPLICA_STALE | REPLICA_FRESH(threshold_ms)
- SDK router selects replica based on replication lag metrics for REPLICA_FRESH.

Risks and Mitigations
- Split‑brain registry: single‑leader assumption in Phase 1; edge detection via startup locks.
- Hot shards: manual rebalance hook and metrics to detect imbalance.
- Backpressure: cap concurrent shard RPCs per request; timeouts + circuit breakers.
- Compaction contention: serialize compaction per node via coordinator and distributed locks.

Phase-wise Execution Plan (per working session)

Session 1 (Foundation)
- Registry: Persist shard registry at `<metadata_url>/cluster_registry.json` and load on startup.
- Admin: nodes/register, collections/:id/shard/plan, shard/registry.
- Affinity: add CollectionSticky and SegmentSticky APIs and manager support.
- Read-only search: route detection + local fanout/merge (no RPC), gated by `[distributed].enabled`.
- Deliverables: green build, ops guide updated, example curl scripts.

Session 2 (Secure RPC + Planner)
- ShardService (tonic) with SearchShard; enable mTLS via `[distributed.rpc.tls]`.
- Query planner (basic): probe subset of shards then expand; configurable thresholds.
- Placement: least-primaries heuristic across nodes for new shard plans.
- Deliverables: RPC integration tests, plan toggles in config, improved logs/metrics.

Session 3 (Writes + Consistency)
- Replication: WAL-first ApplyWAL RPC, required_acks for ONE/QUORUM/ALL.
- Promotion stub: select best replica and update registry (with fencing token from lease term).
- Read strategies: PRIMARY | REPLICA_STALE | REPLICA_FRESH(threshold_ms); expose replica lag metrics.
- Deliverables: consistency tests, SDK read_consistency plumbed, enhanced metrics.

Session 4 (Coordination + Compaction)
- Lease-based leader election in metadata `/cluster/lease` with term/epoch and TTL.
- Compaction coordinator: serialize compactions per collection/segment; distributed locks.
- Admin: targeted rebalance actions (evacuate_node, promote_replica);
- Deliverables: robustness tests for failover, compaction under load, and admin rebalance.

Session 5 (Anti-Entropy + Polishing)
- Anti-entropy: Merkle tree or range checksums; targeted resync.
- Dev mode: single process, fake latency; demo shootout for cloud/NAS/local disk modes.
- Docs: performance tuning, placement policy guide, read strategy trade-offs.

Acceptance per Session
- S1: Registry bootstraps + affinity routes log; local fanout OK.
- S2: mTLS RPC passes; planner reduces fanout on approximate queries.
- S3: QUORUM writes succeed under single-replica failure; REPLICA_FRESH adheres to lag thresholds.
- S4: Leader changes do not corrupt registry; compactions serialized; targeted rebalance works.
- S5: Anti-entropy detects and repairs drift; dev mode reproducible.
