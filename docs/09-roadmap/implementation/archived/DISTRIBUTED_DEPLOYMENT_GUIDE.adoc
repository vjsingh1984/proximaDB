= Distributed Deployment (Phase 1)
:toc: left

Overview
- This guide describes how to run a small ProximaDB cluster (3 nodes) with collection‑level sharding and per‑shard replication (Phase 1).

Prerequisites
- Build server on each node; configure unique `distributed.node_id` and advertise address.
- Shared configuration file with `[distributed]` enabled.

Configuration (config/config.toml)
```toml
[distributed]
enabled = true
node_id = "${NODE_ID}"
cluster_name = "proximadb"

[distributed.replication]
default_factor = 3
default_consistency = "quorum"

[distributed.sharding]
default_shard_count = 8
strategy = "ConsistentHash"   # ConsistentHash | VectorClustering | TimeRange | Hybrid

[distributed.rpc.tls]
enabled = true
ca_cert = "/etc/proximadb/ca.pem"
cert_file = "/etc/proximadb/node.crt"
key_file = "/etc/proximadb/node.key"

[distributed.read]
default_consistency = "PRIMARY"   # PRIMARY | REPLICA_STALE | REPLICA_FRESH
freshness_threshold_ms = 250
```

Bootstrap
1. Start node A/B/C with unique `NODE_ID` and addresses.
2. Register nodes via admin API (to be added): `POST /api/v1/cluster/nodes/register`.
3. Create sharded collection: `POST /api/v1/collections/:id/shard/plan` with `shard_count` and `replication_factor`.

Operations
- Inspect registry: `GET /api/v1/collections/:id/shard/registry`.
- Rebalance: `POST /api/v1/collections/:id/shard/rebalance`.
- Set collection affinity (cloud object store mode):
  - `POST /admin/distributed/collections/:id/affinity {"mode":"CollectionSticky","sticky_node_id":"node-1"}`
  - `GET  /admin/distributed/collections/:id/affinity`

Affinity Modes
- None: default behavior (no stickiness)
- CollectionSticky: route all collection requests to a sticky node (better cache locality)
- SegmentSticky: own individual files/segments by node (fine-grained cache ownership)

Failure
- Node health monitored via heartbeat; on failure, replica promotion occurs and registry is updated.

Notes
- Phase 1 uses a single metadata leader (no consensus) and best‑effort rebalancing hooks.
- Use QUORUM consistency for production trials.

Deployment Modes

Cloud Object Storage (S3/GS/ADLS)
- Nodes are stateless; enable CollectionSticky affinity for best cache locality.
- For very large collections, use SegmentSticky to spread cache pressure.

NAS (NFS/SMB)
- CollectionSticky typically improves OS page cache and readahead effectiveness.
- SegmentSticky useful if NAS or host cache pressure is high.

Local Disk (Direct-Attached)
- If collection files are on a single node, use CollectionSticky for true locality.
- For sharded local files across nodes, SegmentSticky aligns reads with owners.

Affinity Configuration
- Set CollectionSticky:
  - `POST /admin/distributed/collections/foo/affinity {"mode":"CollectionSticky","sticky_node_id":"node-1"}`
- Set SegmentSticky:
  - `POST /admin/distributed/collections/foo/affinity {"mode":"SegmentSticky"}`
- Inspect:
  - `GET  /admin/distributed/collections/foo/affinity`

Read Consistency Strategies
- PRIMARY: route reads to primary shard only.
- REPLICA_STALE: route to any replica (best performance/availability; may be stale).
- REPLICA_FRESH: route to a replica only if lag <= freshness_threshold_ms, else fallback.

Security
- Enable mTLS for internal RPC via `[distributed.rpc.tls]`.
- Distribute cluster CA and node certs securely; restrict admin endpoints to admin role.

Leader Election (Pre-Raft)
- Use lease-based leader election persisted in metadata (`/cluster/lease`).
- Only the leader performs placement/rebalance updates; operations carry a fencing term.

Phase-wise Runbook (Sessions)
- Session 1: Registry & affinity, local fanout; verify logs & results, curl admin endpoints.
- Session 2: Enable RPC mTLS, test shard fanout via gRPC, verify query planner reduces fanout.
- Session 3: Test QUORUM writes; simulate replica failure; validate read strategies in SDK.
- Session 4: Induce leader change; test compaction coordination and targeted rebalance.
- Session 5: Validate anti-entropy, run dev mode end-to-end in CI.
