== Technical Architecture

=== Overall Implementation Strategy

* **Modular Architecture:** Three independent engines that can operate standalone or unified
* **Proto-First Design:** Zero-copy protobuf serialization throughout
* **Arc-Based Memory:** Shared memory pool with Arc<T> for zero-copy between engines
* **Intra-Process Performance:** All engines in single process, no network overhead
* **Asynchronous & Concurrent:** Tokio-based async runtime with work-stealing

== Phase 1: Core Graph Data Model & Storage Integration

*   **Goal:** Establish the fundamental data structures for nodes, edges, and properties, and integrate their persistence with ProximaDB's `StorageEngine`.

*   **Tasks:**

    1.  **Define Core Protobuf Schemas:**
        *   Create `proto/graph.proto` (or similar) to define `Node`, `Edge`, and `Property` messages.
        *   `Node`: `id` (UUID/ULID), `labels` (list of strings), `properties` (map<string, Value>).
        *   `Edge`: `id` (UUID/ULID), `from_node_id`, `to_node_id`, `type` (string), `properties` (map<string, Value>).
        *   `Value`: A Protobuf `oneof` to support various property types (string, int64, float64, bool, bytes, etc.).
        *   **Design Tradeoff:** Using a generic `map<string, Value>` for properties offers flexibility but might incur serialization/deserialization overhead compared to strongly typed schemas for known properties. This is a good starting point for schema-less properties.

    2.  **Implement Rust Data Structures:**
        *   Generate Rust structs from the Protobuf definitions using `prost` or similar.
        *   Implement `From` and `Into` traits for conversion between Protobuf and internal Rust representations.

    3.  **Storage Engine Integration (Key-Value Mapping):**
        *   Determine how nodes and edges will be mapped to key-value pairs in the `StorageEngine`.
        *   **Recommendation:**
            *   Nodes: `nodes:<node_id>` -> `Node` protobuf bytes.
            *   Edges: `edges:<edge_id>` -> `Edge` protobuf bytes.
            *   Adjacency: `node_out_edges:<node_id>:<edge_type>:<edge_id>` -> empty/metadata.
            *   Adjacency: `node_in_edges:<node_id>:<edge_type>:<edge_id>` -> empty/metadata.
        *   **Design Tradeoff:** Storing adjacency lists separately allows for efficient traversal from a node. This is generally preferred over adjacency matrices for sparse graphs common in real-world scenarios.

    4.  **Basic CRUD Operations (Storage Layer):**
        *   In `src/storage/engine.rs` (or a new `src/storage/graph_store.rs`), implement:
            *   `put_node(node: Node) -> Result<()>`
            *   `get_node(node_id: Uuid) -> Result<Option<Node>>`
            *   `delete_node(node_id: Uuid) -> Result<()>`
            *   `put_edge(edge: Edge) -> Result<()>`
            *   `get_edge(edge_id: Uuid) -> Result<Option<Edge>>`
            *   `delete_edge(edge_id: Uuid) -> Result<()>`
            *   `get_out_edges(node_id: Uuid, edge_type: Option<String>) -> Result<Vec<Edge>>`
            *   `get_in_edges(node_id: Uuid, edge_type: Option<String>) -> Result<Vec<Edge>>`
        *   Ensure these operations are atomic and leverage the existing WAL and memtable for durability and performance.

*   **Verification:**
    *   Write unit tests for all new data structures and storage layer CRUD operations.
    *   Ensure data can be written, read, and deleted correctly.

=== Addendum: Data Model, IDs, and Constraints (Leveraging Core Infrastructure)

*   **Goal**: Nail down write-safety and schema choices while maximizing infrastructure reuse for performance and reliability.

*   **Infrastructure Integration Strategy**:
    *   **ULID Generation**: Leverage existing core utils ULID infrastructure
    *   **Compression**: Use unified compression module (10x storage reduction)
    *   **FastLane Encoding**: Delta encoding for node IDs, dictionary for properties  
    *   **Write-Ahead Log**: Existing WAL for ACID transactions and crash recovery
    *   **Event Log**: Track graph mutations for replication and audit trails

*   **Design Decisions with Infrastructure Alignment**:
    *   **IDs**: Use existing ULID generator for `NodeId`/`EdgeId` with FastLane delta encoding
    *   **Storage Architecture**: 
        - **Node Properties**: VIPER engine (columnar, 4x Brotli compression)
        - **Edge Storage**: SST engine (transactional, ZSTD compression)
        - **Adjacency Lists**: FastLane RunLength encoding for dense regions
    *   **Directionality**: Directed edges with `bidirectional` flag; leverage edge weight quantization
    *   **Temporal Support**: `valid_from`/`valid_to` with FastLane BitPacked timestamp encoding
    *   **Referential Integrity**: WAL-backed atomic constraint checking with cascade/restrict modes

*   **Performance Optimizations via Reuse**:
    ```rust
    // Node storage with unified compression
    let node_storage = ViperEngine::new(CompressionContext::Column)?;
    node_storage.set_compression("brotli")?; // 4x reduction for properties
    
    // Edge storage with FastLane encoding  
    let edge_storage = SstEngine::new(CompressionContext::Block)?;
    edge_storage.enable_fastlane(FastLaneScheme::Delta)?; // Sequential edge IDs
    
    // Transaction safety via existing WAL
    let tx = GraphTransaction::begin_with_wal()?;
    tx.insert_node_with_integrity_check(node)?; // <1ms ACID guarantees
    ```

*   **Modular Implementation Tasks**:
    1.  **ULID Integration**: Use `proximadb_core::utils::ulid` with existing patterns
    2.  **Proto Extension**: Add temporal/bidirectional fields with encoding optimization hints
    3.  **WAL Integration**: Leverage existing transaction coordinator for graph operations  
    4.  **Compression Setup**: Configure context-aware compression for graph data types
    5.  **Event Log Setup**: Use existing mutation tracking for graph change streams

*   **Expected Performance Gains**:
    *   **10x Storage Reduction**: Context-aware compression (Brotli text, ZSTD adjacency, LZ4 hot)
    *   **4-16x Encoding Speed**: SIMD-optimized FastLane encoding for IDs/weights/timestamps
    *   **<1ms Transaction Latency**: Production-tested WAL with optimized graph operation patterns
    *   **Hardware Acceleration**: Existing SIMD/GPU infrastructure for constraint validation

*   **Verification**: Unit tests for RI violations, multi-edge handling, temporal fields, plus integration tests with WAL/compression/encoding systems.

=== High-Performance Traversal Algorithms

[source,rust]
----
// Optimized BFS with early termination and filtering
pub async fn parallel_bfs(
    &self,
    start: NodeId,
    max_depth: u32,
    filter: Option<Box<dyn Fn(&Node) -> bool>>,
    early_stop: Option<Box<dyn Fn(&[Node]) -> bool>>,
) -> Result<Vec<Node>> {
    // Use bit vector for visited tracking (cache-friendly)
    let visited = Arc::new(BitVec::with_capacity(self.node_count()));
    
    // Parallel frontier processing with work-stealing
    let (tx, rx) = mpsc::channel(1000);
    
    // Process levels in parallel
    for depth in 0..max_depth {
        let frontier = self.process_frontier_parallel(
            frontier,
            &visited,
            filter.as_ref(),
        ).await?;
        
        if let Some(ref stop) = early_stop {
            if stop(&frontier) {
                break;
            }
        }
    }
}
----

== Phase 5: Transactions & Concurrency Control

*   Goal: Provide atomic multi-operation writes and safe concurrent access.
*   Design:
    *   Atomic Batches: Group node/edge mutations into a single WAL transaction.
    *   OCC: Versioned entities with compare-and-swap; retry on conflict.
    *   Isolation: Serializable-by-default for single-partition ops; document eventual semantics for cross-partition (future PULSAR).
*   Tasks: Transaction API (`begin/commit/rollback` or implicit batch), OCC checks in `put_*`, and WAL grouping.
*   Verification: Crash-recovery tests, conflict simulations, and atomicity assertions.

== Phase 6: Dynamic CSR, Deltas, and Compaction

*   Goal: Make CSR efficient under frequent updates.
*   Design: CSR + Write-Optimized Deltas
    *   Append-only adjacency delta logs per node (insert/delete markers) with in-memory caches.
    *   Periodic compaction merges deltas into base CSR; background, rate-limited.
    *   Tombstones and Fragmentation Metrics: track per-node delta size; trigger compaction thresholds.
*   Tasks: Implement delta layer, merge iterator for traversals, and compaction scheduler.
*   Verification: Update-heavy benchmarks; correctness under interleaved reads/writes.

== Phase 7: Distribution (PULSAR)

*   Goal: Scale to billions of nodes/edges across shards.
*   Design:
    *   Partitioning: Vertex-cut (by node hash/range) with ghost vertices; configurable replication factor.
    *   Routing: Directory service maps `NodeId` → shard; client/server-side routing.
    *   Cross-Shard Traversal: Iterative deepening with batched RPC; minimize fan-out; optional Bloom filters per shard.
    *   Rebalancing: Background migration with dual-write and cutover; hot-spot detection.
    *   Consistency: Per-shard strong writes, async replication; tunable read consistency.
*   Tasks: Shard metadata, RPC protocols, cross-shard cursor, and rebalancer.
*   Verification: Multi-node integration tests, fault-injection (partition/latency) and consistency checks.

== Phase 8: Security & Multi‑Tenancy

*   Goal: Enterprise-grade isolation and control.
*   Design:
    *   AuthN/Z: Pluggable auth (OIDC/API keys); role-based ACLs on collections and graph labels.
    *   Namespaces: Tenant-scoped key prefixes and memory pools; resource quotas per tenant.
    *   Encryption: At-rest via storage engine; in-transit TLS; optional per-tenant keys.
    *   Auditing: Structured audit logs for access and mutations.
*   Tasks: Policy engine integration, request context propagation, per-tenant metrics/limits.
*   Verification: Permission matrix tests, quota enforcement, and audit coverage checks.

== Phase 9: Ingest, Export, Backup & Restore

*   Goal: Operational data mobility and safety.

    *   Export: GraphML/CSV/JSONL with pagination and streaming.
    *   Snapshots: Coordinated storage checkpoints + graph manifest; fast restart path to rebuild CSR.
*   Tasks: Import CLI, export endpoints, snapshot/restore procedures and docs.
*   Verification: Large ingest tests, restore drills, checksum validation.
