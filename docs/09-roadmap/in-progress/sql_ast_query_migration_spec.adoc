= SQL-AST Query Migration Design – ProximaDB
:toc:
:icons: font
:source-highlighter: rouge
:status: in-progress

== Executive Summary

 ProximaDB’s REST query API currently accepts custom JSON payloads for vector search and bespoke parsing in parts of the stack. Meanwhile, `src/query/sql_engine/` provides a solid base for SQL parsing/planning/execution and `sks_extensions.rs` sketches SKS operators. This document proposes consolidating on a SQL-first interface with a standard SQL AST, integrating SKS extensions, and exposing SQL over REST/gRPC. The goals are: fewer DSLs, better ergonomics, safer parameterization, and tighter integration with the unified optimizer.

== Current State (Code Review)

 - Query engine entry: `src/query/mod.rs` exposes `SqlEngine`, `QueryOptimizer`, and vector search helpers; `execute_sql` is wired when `SqlEngine` present.
 - SQL engine: `src/query/sql_engine/{parser,planner,executor}.rs` implements a custom SQL-like parser, logical planning, and execution with vector-aware ORDER BY and WHERE conversion to `FilterExpression`.
 - SKS extensions: `src/query/sks_extensions.rs` defines SIMILAR, FOLLOW, ASSEMBLE, TEMPORAL operators with placeholder parsers.
 - Optimizer: `src/query/unified_query_optimizer.rs` provides cost modeling, filter/search planning, and combined steps.
 - REST: `src/network/rest/v1/handlers.rs` exposes JSON vector search endpoints; a prior `handlers.rs.backup2` shows an `/api/v1/sql/execute` endpoint pattern.

Limitations:
 - Multiple syntaxes (JSON + bespoke SQL) increase client and server complexity.
 - Missing standard SQL grammar coverage; no formal parameter binding; ad hoc SKS parsing.
 - REST endpoints not aligned to SQL-first flow; gRPC lacks an ExecuteSql RPC.

== Implementation Status (Reviewed: 2025-09-09)

- SQL Frontend: Present under `src/query/sql_frontend/` (parser complete; lowering WIP).
- REST: `/api/v1/sql/execute` implemented; `/api/v1/sql/explain` now calls `QueryEngine::explain_sql()` and surfaces VOS plan hints; no gRPC `ExecuteSql` yet.
- Vector orchestration: Delegation to VOS is functional; hybrid orchestration path exists but not wired to public APIs.
- Next steps: Choose single SQL path (frontend vs engine), wire EXPLAIN to real plan/hints, add gRPC ExecuteSql, and integrate hybrid execution end-to-end.

== Proposal Overview

- Adopt a SQL-first API: accept SQL text + bound parameters; parse into a canonical AST; plan and execute.
- Use `sqlparser-rs` for baseline grammar and map to an internal AST, then extend for vectors/SKS (or continue with existing parser if coverage is sufficient; recommendation is sqlparser-rs for robustness).
- Expose SQL over both REST and gRPC; deprecate JSON query bodies over time.
- Harden with parameterized queries, timeouts, and work budgets.

=== Delegation Principle (Vector Operations)

- The VectorOperationsService (VOS) already implements caching, pruning, and detailed search planning; we will delegate vector planning/execution to VOS.
- The Query module remains responsible for: parsing SQL → AST, validating and lowering to VOS search API requests, orchestrating multi-stage queries (e.g., hybrid graph+vector), and shaping results.
- Benefit: single source of truth for vector planning shared by REST/gRPC/SDKs; avoids duplicate caches/logic in the query layer.

=== VOS Integration Contract

Request mapping (AST → VOS):
- Collection: derive from `FROM <collection>` or function argument for table functions (e.g., SIMILAR).
- Query vector: from `SIMILAR(embedding, $qvec, ...)` or `ORDER BY COSINE_DISTANCE(embedding, $vec)`; support `$param` binding and `VECTOR([...])` literals.
- Top-k/offset: `LIMIT k [OFFSET o]` maps to `(k+o)`; Query layer trims the first `o` results.
- Filter: SQL `WHERE` → `FilterExpression` (existing conversion in `sql_engine/planner.rs`); pass to VOS when coupled with vector.
- Config (UnifiedSearchConfig):
  - `optimization_goal`: map from session/default or SQL hint (e.g., `/*+ goal=accuracy */`).
  - `progressive_search`: enable by default; allow SQL hint override.
  - `progressive_recalls`: optional; from hints or session.
  - `include_vectors`/`include_metadata`: from SELECT list or explicit flags.
  - `scenario`: optional string for tuned presets (e.g., `high_speed`, `high_recall`).
- Limits/budgets: propagate `timeout_ms`, `work_budget` via request context (outside config) to enforce deadlines.

Response mapping:
- Primary: `Vec<SearchResult>` (proto) as returned by VOS. Query layer shapes rows per SELECT projection.
- Optional hints (proposed): `plan_hints` including `pruned_files`, `ef_search`, `nprobe`, `candidates`, `cache_hit`, `progressive_stages`, `recall_estimates` to surface in `EXPLAIN` (read-only; no duplication of planning).

Streaming execution:
- For large results, use VOS streaming (`services/search/streaming.rs`) with `StreamingSearchConfig`; map SQL `FETCH FIRST n ROWS WITH TIES` (if supported) to streaming fetch.

Error handling:
- VOS errors propagate through Query with sanitized messages; SQL parser/semantic errors remain in Query.

EXPLAIN integration:
- `EXPLAIN`/`EXPLAIN ANALYZE` surfaces orchestration steps plus VOS hints (if available) without re-deriving vector plans.
- Implementation note: VOS provides `unified_search_with_hints(...) -> (Vec<SearchResult>, SearchPlanHints)`; Query exposes `ExplainPlan` with `vector_hints` populated when requested.
 - Hint-only: VOS also exposes `plan_hints_only(config) -> SearchPlanHints` for EXPLAIN without executing search; QueryEngine::explain_sql uses this until the SQL frontend is wired.

== Feature Completeness Goals

- Target SQL-92 core compatibility in Phase 1–3; reach 85–90% of common analytical surface by Phase 4.
- Adopt an AST-first design so all supported constructs are represented (no ad‑hoc parsing paths).
- Cost-based planning for scan, filter, projection, (hash) join order, aggregation, sort, limit, and vector/SKS functions.

== Architecture Changes

1) Parser/AST
- Introduce `src/query/ast/` with stable AST types (SELECT, WHERE, ORDER BY, LIMIT, functions, SKS ops).
- Add `src/query/sql_frontend/`:
  - `parser.rs`: parse via `sqlparser-rs` → front-end AST.
  - `lowering.rs`: lower front-end AST → internal AST (including vector and SKS nodes).
- Migrate/merge `sql_engine/parser.rs` logic into the new frontend or keep it as an internal fallback where sqlparser gaps exist.

AST nodes (indicative):
- Query: `Select { projection, from, joins, where, group_by, having, order_by, limit_offset }`
- From: `TableRef { name | subquery, alias }`
- Joins: `Join { kind, left, right, on: Expr }`
- Expr: `BinaryOp, UnaryOp, Literal, Identifier, Param, FuncCall, Aggregate, Subquery`
- TableFunction: `SimilarFn, FollowFn, AssembleFn` with named args

 2) SKS Extensions in SQL
 - Represent SIMILAR/FOLLOW/ASSEMBLE as SQL functions or table functions:
   - `SIMILAR(embedding, $vec, metric => 'cosine', top_k => 10)`
   - `FOLLOW(entity_id => $id, rel => 'cites', depth => 2, direction => 'out')`
   - `ASSEMBLE(entity_ids => ARRAY[$ids], radius => 3)`
 - Provide alternatives as clauses for readability if desired, but parse to the same AST nodes.

 3) Planning & Optimization
 - For vector paths: Lower AST vector constructs to VOS Search API (e.g., VectorSearchRequest) and delegate planning/execution to VOS.
 - For graph/SKS paths: build high-level orchestration plans (e.g., hybrid sequence GRAPH↔VECTOR) and simple heuristics; leave inner vector plan to VOS.
 - Metadata filters: convert WHERE to FilterExpression (as today) and pass to VOS when coupled with vector, or to graph service for traversal filters.
 - Reuse unified optimizer for non-vector orchestration where useful; augment with VOS-provided hints (cost/selectivity) instead of duplicating index selection.

Cost-based planning extensions (non-duplicative):
- Cardinality estimation: histograms/NDV for SQL predicates used for join/aggregation; sampling fallback.
- Join order: left-deep DP enumeration for small N; rule-based fallback.
- Cost terms: IO/CPU/memory/selectivity/sort; vector-specific costs come from VOS via hints (ef_search, nprobe, candidates) rather than recomputation.
- Statistics maintenance hooks and EXPLAIN cost reporting that incorporate VOS hints where available.

 4) Execution
 - Reuse existing `sql_engine/executor.rs` for result shaping; route vector parts to `VectorOperationsService`, SKS traversal to Graph service, merge per `UnifiedExecutionPlan`.

 5) APIs
 - REST: add `POST /api/v1/sql/execute` accepting `{ sql: string, params?: object, timeout_ms?: u32 }`; respond with a typed result envelope and optional streaming mode for large results.
 - gRPC: add `ExecuteSql(SqlQueryRequest) returns (SqlQueryResponse)`; support server streaming for large result sets.
 - Keep current JSON endpoints for one release with deprecation headers; document migration.

== SQL and Extensions (Grammar Surface)

- Baseline: SELECT-FROM-WHERE-ORDER-LIMIT; comparison ops; IN/BETWEEN/LIKE; functions; simple JOIN (optional phase 2).
- Vector: `COSINE_DISTANCE(a, b)`, `EUCLIDEAN_DISTANCE(a, b)`, `DOT_PRODUCT(a, b)`; `VECTOR([...])` literal; ORDER BY distance; K via `LIMIT`.
- SKS:
  - SIMILAR: function form with named args; parameters allowed.
  - FOLLOW: table function returning rows (entities or paths) with args (rel, depth, direction).
  - ASSEMBLE: table function emitting context rows (chunk_id, source_id, pos, text).

 Example:
 ----
 SELECT id, score
 FROM SIMILAR(embedding, $qvec, metric => 'cosine', top_k => $k)
 WHERE metadata.category = 'electronics'
 ORDER BY score DESC
 LIMIT 10;
 ----

== Security & Resource Controls

 - Parameter binding for values (`$1`, `$name`) to prevent injection; expand in prepared execution context.
 - Server-side limits: max `LIMIT`, max work budget, timeout propagation to services.
 - Statement whitelisting over REST (SELECT only); gRPC may support EXPLAIN.
 - Safe error reporting (no internal stack traces or plans in errors by default).

== Backwards Compatibility & Migration

 - Release N: Add SQL endpoints (REST/gRPC); keep JSON endpoints; add deprecation warnings + docs.
 - Release N+1: Default clients migrate to SQL; JSON marked deprecated.
 - Release N+2: Remove JSON query endpoints (or hide behind feature flag).
 - Provide a compatibility shim to convert common JSON requests to SQL for a period.

== Testing & Validation

- Parser conformance tests with golden SQL → AST snapshots (cover vector/SKS).
- Planner tests: SQL → logical plan → `UnifiedExecutionPlan` assertions.

. Phase 1: Frontend & AST
  - Add `query/ast/*` and `query/sql_frontend/*`; integrate `sqlparser-rs`.
  - Map vector functions and basic WHERE/ORDER/LIMIT; feature-gate SKS.
. Phase 2: SKS Operators
  - Implement SIMILAR/FOLLOW/ASSEMBLE as functions/table functions; lower to internal AST.
. Phase 3: Planner Integration
  - AST → logical plan → `UnifiedExecutionPlan`; extend optimizer for SKS costs.
. Phase 4: Aggregation & Joins
  - Implement GROUP BY/HAVING, INNER/LEFT joins with cost-based join order for 2–3 tables.
  - Add cardinality estimation (histograms) and rule-based fallback.

  - REST `/api/v1/sql/execute`; gRPC `ExecuteSql`; request/response schema; streaming.
. Phase 6: Subqueries & CTEs
  - IN/EXISTS scalar and non-correlated subqueries; simple `WITH` CTE.
. Phase 7: Migration & Deprecation
  - Compatibility shim; docs; client SDK updates; telemetry for adoption.

== Shared Query Utilities for Graph + Vector

Goal: extract common query mechanics used by `src/graph/query` and `src/query` into reusable utilities to reduce duplication and ensure consistent behavior.

Shared modules (added under `src/query/utils/`):
- `params.rs`: Parameter binding (`Params`) for SQL and programmatic calls.
- `limits.rs`: Request budgets/timeouts/frontier caps shared by graph traversals and vector search.
- `metrics.rs`: Hooks to the unified metrics framework for start/end/latency; wire into `proximadb_metrics` where available.
- `normalize.rs`: Field normalization and filter pushdown helpers (align dotted paths, label/property naming).

Planned integrations:
- Vector path: SQL WHERE → `FilterExpression` already exists; reuse `normalize_field` and `RequestLimits` in planner/executor.
- Graph path: traversal endpoints accept budget/frontier/timeout; unify to `RequestLimits` and instrument with `metrics` helpers; normalize property keys before index lookup.
- Cost model: use common stats providers and cost terms (IO/CPU/memory/selectivity), reuse distance/quantization modules for vector ops, and share histogram/statistics hooks for both planners.
- Compression/encoding: continue using existing compression, distance, and quantization modules end-to-end; no ad‑hoc copies.

Verification:
- Unit tests for `utils/*` and cross-stack usage in both graph and vector query tests.
- Metrics presence and limits enforcement checks in e2e tests.

== Unified Caching & Infrastructure

Goal: reduce latency and cloud API costs by leveraging VOS’s unified caches for vector work, and sharing only orchestration-level caches in the query layer.

Unified caches (no duplication of vector caches):
- VOS Caches (authoritative): file/segment metadata, bloom filters, vector stats, distance/quantization artifacts; accessed via VOS APIs and hints.
- Query-layer caches: PlanCache (SQL → orchestration plan), PreparedStmtCache, small ResultCache; optional ColumnStatsCache for SQL join/agg estimates (not duplicating VOS internals).

Pruning strategy (delegated):
- For vector segments, rely on VOS to prune using its file metadata and bloom filters; Query passes normalized predicates and receives pruned candidates/hints.
- Maintain a collection manifest in storage (owned by VOS); Query does not perform separate remote HEAD/GET for vector paths.
- For graph-only paths, use graph planner’s own caches and stats (as specified in the graph spec addendum).

Infra details:
- Thread-safe DashMap + parking_lot RwLocks; size-bounded with LRU/LFU and TTL; metrics for hit/miss/evictions.
- Share caches across REST/gRPC workers and both query stacks (graph/vector).

Tasks:
- Add Plan/Prepared/Result caches in query layer; invalidate on schema changes.
- Define VOS hint surface (cost/selectivity/pruned files) and consume in orchestration.
- Instrument miss penalties and cloud calls avoided (via VOS metrics); surface in SQL EXPLAIN.

Verification:
- Unit tests for pruning correctness; integration tests verifying reduced I/O.
- Metrics dashboards: cache hit rate > 80% on steady workloads; reduced remote calls.
