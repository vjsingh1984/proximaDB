= Query Layer + SQL Migration — Consolidated Plan (ProximaDB)
:toc:
:status: in-progress

== Executive Summary

Consolidates the SQL-AST migration and Unified Query Layer alignment into one plan. We standardize on `sql_frontend` (sqlparser-rs) as the single SQL parser and canonical AST source, expose SQL over REST/gRPC with typed rows/params, and route execution to vector (VOS) and graph stacks via a unified planner/orchestrator. We deprecate the custom parser under `sql_engine`; planning/execution code is retained and refactored to consume the frontend AST.

== Key Decisions (Final)

- Single parser + AST: Keep `src/query/sql_frontend/*` as the only SQL entry; use `src/query/ast/*` as the canonical internal AST.
- Deprecate custom parser: Remove `src/query/sql_engine/parser.rs` after transition; no dual parsers.
- Planner/Executor refactor: Reuse useful pieces from `sql_engine/{planner,executor}.rs` by moving them under `src/query/execution/` to consume the frontend AST and call VOS/graph services.
- SQL-first API: Accept SQL text + typed params (`proximadb.v1.SqlValue`) over REST and gRPC; return typed rows (`SqlRow/SqlValue`).
- Delegation: Orchestrate in QueryEngine; delegate vector work to VOS and graph work to graph planner; add hybrid orchestration as a first-class path.

== Current State (Verified 2025-09-10)

- REST SQL endpoints: `/api/v1/sql/{execute,explain}` present in `src/network/rest/v1/handlers.rs`; EXPLAIN calls `QueryEngine::explain_sql()`.
- gRPC: `SqlService/ExecuteSql` implemented in `src/network/grpc/sql_service.rs` with `ExecuteSqlRequest/Response` (typed rows via `SqlRow/SqlValue`).
- Frontend: `src/query/sql_frontend/{parser.rs}` uses sqlparser-rs to produce a rich AST; `lowering.rs` is a stub.
- Execution: `src/query/sql_engine/{parser,planner,executor}.rs` is currently wired in handlers; custom parser overlaps with frontend capability.
- VOS: `VectorOperationsService` integrated; progressive search supported. SKS operators exist with placeholder parsing in `sks_extensions.rs`.
- Hybrid: `src/graph/hybrid/mod.rs` implemented but not wired into SQL or REST.

== Refactoring Details by Module

=== Frontend & AST (Authoritative)
- Parser: `src/query/sql_frontend/parser.rs` (sqlparser-rs) → produces `src/query/ast/*` (internal AST).
- Lowering: `src/query/sql_frontend/lowering.rs` → converts frontend AST to logical plan inputs. Handles params (`$1`, `:name`) as typed `SqlValue`.
- Extensions: Add function mappings for `SIMILAR`, `FOLLOW`, `ASSEMBLE`, `TEMPORAL` into AST as table/functions for uniform planning.

=== Execution Planner (New, reusing engine logic)
- Create `src/query/execution/planner.rs` by extracting reusable parts of `sql_engine/planner.rs` to work on internal AST (Scan, Filter, VectorSearch, Join, Project, Sort, Limit nodes).
- Vector path: plan `VectorSearch` nodes by delegating to VOS (build `SearchParams`, distance metric, progressive flags) and pushing down filters.
- Graph path: plan `GraphTraversal` nodes by delegating to graph planner (maintain algorithm, limits, attribute filters).
- Hybrid path: compose subplans, then a `Fusion` node (rank/merge) with weights and cutoffs.

=== Executor/Orchestrator (New)
- Create `src/query/execution/executor.rs` by extracting from `sql_engine/executor.rs` with adapters for:
  - Vector execution: call `services/operations/vectors.rs::VectorOperationsService` (native path) per plan.
  - Graph execution: call graph planner/executor with traversal specs.
  - Hybrid: add orchestrator that runs components (parallel where safe), then fuses results; supports server-side paging/streaming.
- Shared utilities: reuse `src/query/utils/{params,limits,metrics,normalize}.rs` across paths.

== Reuse of Existing Code
- Move/Adapt: `sql_engine/{planner,executor}.rs` → `query/execution/{planner,executor}.rs` with inputs from internal AST.
- Keep: `VectorOperationsService` (authoritative vector layer), `unified_query_optimizer.rs` for cost/hints, and graph planner modules.
- Unify: Typed row shaping remains `SqlRow/SqlValue` end-to-end (REST/gRPC).

== SKS & Hybrid Queries (Design)

=== SQL Surface (Table/Scalar Functions)
- SIMILAR(embedding_field, $vec [, top_k=>K, metric=>"cosine", model=>"id"]) → yields rows with id, score, optional metadata.
- FOLLOW(graph, edge_type [, depth=>N, direction=>"both"]) → yields node/edge paths.
- ASSEMBLE(context [, radius=>R, max_size=>M]) → yields ordered chunks with provenance.
- TEMPORAL(at=>ts | between=>[t1,t2] | since=>t)

=== Lowering Targets
- SIMILAR → VectorSearch node(s) with model/dimension validation, filters, and top-k.
- FOLLOW → GraphTraversal node with algorithm/limits; accepts graph namespace.
- ASSEMBLE → ContextRetrieval node over storage/indices.
- Hybrid (SIMILAR + FOLLOW/ASSEMBLE) → compose and add Fusion node (Additive/Multiplicative/Harmonic/Weighted).

=== Multi-Collection & Multi-Graph Support
- Collections: SIMILAR accepts list/pattern; planner resolves to target collections and runs per-collection searches with correct index/dimension, then merges/limits globally.
- Graphs: FOLLOW accepts graph namespace(s); orchestrator routes per-graph traversal and merges results.
- Tenancy/Namespaces: preserve collection/graph IDs in row metadata; fusion can weigh by source if needed.

=== Multi‑Modal & Model Registry
- Model registry: map `model_id` → {dimension, metric, normalization, encoder hints}. Validate query vector length against target collection/model.
- Per-column vectors: allow multiple embedding fields with different dimensions; SIMILAR disambiguates by field or model.
- Cross‑modal fusion: planner/executor allow combining signals from different dimensions by score normalization; no implicit re-embedding.

=== Orchestration & Scalability
- Parallelism: fan-out across collections/graphs with bounded concurrency; early termination when global top-k stabilized.
- Budgets: enforce `RequestLimits` (time, scanned rows, segments, frontier) across subplans.
- Caching: leverage VOS caches for vector work; maintain plan/prepared/result caches in query layer; expose cache hints in EXPLAIN.
- Streaming: support server streaming in gRPC and chunked REST for large result sets.

==== Advanced Fusion and Ranking
To achieve state-of-the-art hybrid query results, we will move beyond simple additive/multiplicative fusion.

- **Reciprocal Rank Fusion (RRF):** Implement RRF as a primary fusion strategy for combining ranked lists from vector and graph components. RRF is robust to score distributions and effective for combining heterogeneous results.
- **Learning-to-Rank (LTR) Models:** Explore integrating LTR models (e.g., LambdaMART, RankNet) to learn optimal fusion weights and ranking functions based on training data. This allows for highly accurate and adaptable fusion.
- **Dynamic Weighting:** Implement mechanisms for dynamically adjusting fusion weights based on query characteristics (e.g., presence of specific keywords, query intent), user preferences, or real-time performance metrics of underlying components.

==== Query Understanding and Rewriting
Enhance the query processing pipeline with intelligent pre-processing.

- **Intent Recognition and Entity Extraction:** Utilize NLP techniques to understand query intent (e.g., "find similar documents," "explore connections") and extract key entities (e.g., specific vector IDs, graph node names, temporal ranges). This can guide plan selection and parameterization.
- **Automatic Filter Inference:** Based on query context or schema analysis, automatically infer and apply additional filters to narrow down search spaces for both vector and graph components, improving precision and performance.
- **Predicate Pushdown and Join Reordering:** Optimize logical plans by pushing down filters closer to data sources and reordering join operations to minimize intermediate result sizes.
- **Knowledge Graph-Enhanced Query Rewriting (KGEQR):** Leverage an internal or external knowledge graph to enrich and rewrite incoming SQL queries. KGEQR can:
    - **Expand Query Terms:** Automatically add synonyms, related concepts, or hierarchical relationships from the knowledge graph to vector search terms or graph traversal starting points, improving recall.
    - **Infer Implicit Relationships:** Identify implicit relationships between entities in the query that are not explicitly stated but exist in the knowledge graph, translating them into additional graph traversal or join conditions.
    - **Disambiguate Entities:** Use the knowledge graph to resolve ambiguous terms in the query, ensuring the correct entities are targeted in both vector and graph searches.
    This process aims to transform a user's initial query into a more comprehensive and precise hybrid query, leading to higher accuracy and more relevant results.

==== Adaptive Query Execution
Introduce dynamic elements into query execution for improved efficiency and resilience.

- **Early Exit and Pruning:** Implement mechanisms to terminate sub-queries early if sufficient results have been found or if a component is unlikely to contribute to the final top-k results based on intermediate scores.
- **Broadening/Narrowing Search:** Dynamically adjust search parameters (e.g., `top_k`, graph traversal depth) for sub-components based on the quality and quantity of intermediate results. For example, if a vector search yields very few high-quality results, the graph traversal might be broadened.

==== Enhanced Caching Strategies
Beyond basic caching, implement a multi-layered, intelligent caching system.

- **Multi-Level Caching:**
    - **Plan Cache:** Cache optimized logical and physical query plans to avoid re-planning frequently executed queries.
    - **Intermediate Result Cache:** Cache results of expensive sub-queries (e.g., a specific vector search or graph traversal) that can be reused across multiple hybrid queries or within the same complex query.
    - **Data Cache:** Leverage existing VOS data caches (e.g., for embeddings, segment data) and introduce similar mechanisms for graph data.
- **Intelligent Cache Invalidation:** Implement sophisticated cache invalidation policies (e.g., LRU, LFU, time-based expiry, event-driven invalidation upon data modification) to ensure cache freshness.

==== Hardware Acceleration and Optimizations
Leverage underlying hardware capabilities for maximum performance.

- **SIMD for Vector Operations:** Fully exploit SIMD (Single Instruction, Multiple Data) instructions for distance calculations, vector aggregations, and other numerical operations within the VOS layer.
- **GPU Acceleration (Exploration):** Investigate the feasibility of offloading computationally intensive tasks to GPUs, particularly for large-scale vector similarity search (e.g., using libraries like FAISS) or complex graph algorithms (e.g., for massive graph traversals or community detection).

==== Advanced Data Structures and Algorithms
Propose specific, cutting-edge data structures and algorithms for each modality and their combination.

- **Vector Search (VOS Layer):**
    - **HNSW Optimizations:** Implement advanced HNSW (Hierarchical Navigable Small World) graph construction and search optimizations, including:
        - **Graph Pruning:** Techniques to reduce graph size while maintaining search quality (e.g., using degree limits, or removing redundant edges).
        - **Quantization:** Integrate Product Quantization (PQ) or Scalar Quantization (SQ) for memory-efficient storage of high-dimensional vectors, enabling larger indices in memory.
    - **IVF (Inverted File) Enhancements:** For very large datasets, optimize IVF structures with techniques like IVF-PQ or IVF-ADC (Asymmetric Distance Computation) for faster approximate nearest neighbor search.
- **Graph Algorithms (Graph Layer):}
    - **Efficient Traversal Algorithms:** For `FOLLOW`, implement highly optimized k-hop reachability, bi-directional BFS/DFS, and pathfinding algorithms (e.g., Dijkstra, A* with heuristics).
    - **Community Detection:** Integrate algorithms like Louvain or Leiden for identifying clusters within the graph, useful for grouping related entities.
    - **Centrality Measures:** Support calculation of PageRank, Betweenness Centrality, and Closeness Centrality for identifying influential nodes.
- **Hybrid Data Structures:**
    - **Integrated Embeddings:** Store vector embeddings directly as attributes of graph nodes or edges, allowing for co-located storage and faster access during graph traversals that require vector information.
    - **Graph-Aware Vector Indices:** Explore building specialized vector indices that are aware of the graph topology (e.g., indexing vectors of nodes that are within a certain graph distance, or creating "neighborhood embeddings" that capture local graph structure).

==== Conceptual Algorithms for Hybrid Optimization
To push the boundaries of hybrid query performance and accuracy, we propose the exploration of the following conceptual algorithms, drawing from cutting-edge research:

- **Adaptive Semantic Fusion (ASF):**
  This algorithm extends Learning-to-Rank (LTR) models by incorporating a continuous feedback loop from user interactions and query result analysis. ASF dynamically adjusts the fusion weights and ranking functions not just based on pre-trained models, but also on real-time relevance signals. It aims to learn optimal fusion strategies that prioritize semantic coherence across modalities, ensuring that the combined results are not just numerically high-scoring but also contextually meaningful. This involves:
    - **Cross-Modal Relevance Feedback:** Analyzing user clicks, dwell time, or explicit feedback on hybrid query results to infer the true relevance of combined vector and graph signals.
    - **Semantic Alignment Metrics:** Developing metrics to quantify the semantic alignment between vector search results and graph traversal paths, allowing the fusion model to favor results where both modalities strongly agree on the underlying meaning.
    - **Reinforcement Learning for Fusion:** Employing reinforcement learning techniques where the fusion orchestrator learns to optimize a reward function based on the quality of hybrid query results, adapting its strategy over time.

- **Hierarchical Graph-Aware Vector Indexing (HGAVI):**
  Building upon Graph-Aware Vector Indices, HGAVI introduces a multi-level indexing strategy that leverages the hierarchical nature of many real-world graphs (e.g., communities, clusters). Instead of a flat graph-aware index, HGAVI constructs:
    - **Coarse-Grained Vector Indices:** At higher levels of the graph hierarchy (e.g., for graph communities or super-nodes), a representative vector embedding is computed (e.g., mean, centroid, or a learned embedding of the community). A vector index is built on these coarse-grained embeddings.
    - **Fine-Grained Vector Indices:** Within each community or cluster, a more detailed vector index is maintained for individual nodes.
  During query execution, a hybrid query first performs a vector search on the coarse-grained index to identify relevant communities. Then, it refines the search within the identified communities using the fine-grained indices and graph traversals. This approach significantly reduces the search space for vector components, leading to faster query execution, especially for queries with strong graph locality.

== Intra‑Process Orchestration (Hybrid USP)

Why server‑side hybrid (vs client orchestration)
- Eliminates network/OS stack round‑trips across multiple layers for sequential queries.
- Shares caches (segments, stats, embeddings) and memory pools; enables zero‑copy result shaping where possible.
- Allows coordinated budgets, early cut‑off, and fused ranking that a client cannot do efficiently.

How it routes (no RPC boundaries)
- The `QueryEngine` holds in‑process handles: `Arc<VectorOperationsService>` and graph planner/executor; calls are direct method invocations, not gRPC/HTTP.
- Execution spawns Tokio tasks with a bounded semaphore; results merged via in‑memory channels; cancellation propagated on timeouts/budget exceed.
- Data stays in native structs (`VectorRecord`, graph node/edge types) until final shaping into `SqlRow/SqlValue`.

Concurrency & backpressure
- Per‑collection and per‑graph shards execute in parallel with bounded concurrency; early top‑k stabilization halts lagging tasks.
- Backpressure via MPSC channel sizes; planner feeds batches; executor applies cooperative yields to avoid reactor starvation.

Resilience & fallbacks
- Partial failures degrade gracefully: if a graph namespace is unavailable, return vector‑only results with a warning (and vice‑versa) when policy allows.
- Retries on transient storage/index errors use jittered backoff; idempotent search tasks only.

Client flexibility
- Clients may still orchestrate vector/graph APIs separately, but the recommended, low‑latency path is single hybrid SQL routed in‑process.

- **Time-Series Integration:** Allow seamless querying of time-series data alongside vector and graph data. This includes time-based filtering, aggregation, and joins.
- **Continuous Queries:** Support continuous queries where results are updated in real-time as new data arrives, particularly relevant for dynamic graph structures or streaming vector data.

==== User-Defined Functions (UDFs)
Empower users with custom logic for advanced use cases.

- **Custom Aggregations:** Enable user-defined aggregation functions for summarizing results from hybrid queries.

==== Tiered Storage Awareness
Optimize data access and cost by integrating with tiered storage.

- **Hot/Cold Data Management:** The query orchestrator should be aware of data placement across different storage tiers (e.g., in-memory, SSD, HDD, object storage). Queries should prioritize accessing "hot" data from faster tiers.
- **Intelligent Data Movement:** Implement policies for automatically moving data between tiers based on access patterns and query requirements, ensuring optimal performance for frequently accessed data while minimizing storage costs for less active data.

=== Lowering Rules (sqlparser‑rs → internal AST)
- SELECT list: identifiers → `Expr::Identifier`; `*` → handled in planner (expand to id, similarity, metadata when applicable)
- FROM: single table name → `TableRef { name: Some(..) }`; subqueries later
- WHERE: map comparisons to `Binary{..}` with `BinaryOp::{Eq,Ne,Lt,Le,Gt,Ge,Like}`; AND/OR/NOT → `Binary/Unary`; IN/BETWEEN become sugar expanded to Binary combinations
- ORDER BY: field → `OrderByExpr { expr, asc }`; vector functions (`COSINE_DISTANCE`, `VECTOR_SIMILARITY`) lower to `Expr::FuncCall`
- LIMIT/OFFSET: propagate as `Select.limit/offset`
- Params: `$n` or `:name` → `Expr::Param` replaced by typed literals using `SqlValue`

=== Logical Plan Nodes (internal)
- Scan(collection)
- Filter(expr)
- VectorSearch { field, query_vec, top_k, metric, progressive, model_id }
- GraphTraversal { graph_ns, edge_types, max_depth, direction, filters }
- Project(fields)
- Sort { keys, dir }
- Limit { k, offset }
- Fusion { strategy, weights } (for hybrid)

=== Executor Calls (no RPC)
- Vector: use `VectorOperationsService::unified_search_native(collection, vec, top_k, filter, config)` and convert to rows lazily
- Graph: call graph planner/executor with traversal spec; convert to rows with optional path
- Hybrid: run subplans concurrently; merge by ranking; apply global LIMIT/OFFSET

=== Parameter Binding Algorithm
1) Build param map from `SqlValue` slice (positional or named)
2) Replace `Expr::Param` with `Expr::Literal` using type mapping:
   - String → `'...'`; Number → f64; Bool → true/false; Int64 → number; Null → NULL
   - Array/Object/Bytes → JSON string or typed support where applicable
3) No string replacement of the SQL text; operate on AST only

=== Error Handling & Validation
- Validate collection existence via CollectionService when available; return a clear error if not found
- Validate vector dimension against model/collection; surface a user‑friendly message
- Timeouts/budgets: enforce via `RequestLimits`; return partial results if policy allows
