== Hardware Capabilities Implementation

=== Centralized Detection Architecture

**Design Pattern**: Global singleton with one-time initialization using `std::sync::OnceLock` for thread-safe access across all modules.

[source,rust]
----
static HARDWARE_CAPABILITIES: OnceLock<Arc<HardwareCapabilities>> = OnceLock::new();

pub fn initialize_hardware_capabilities(config: HardwareConfig) -> Result<()> {
    let caps = HardwareCapabilities::detect_with_config(config)?;
    HARDWARE_CAPABILITIES.get_or_init(|| Arc::new(caps));
    Ok(())
}
----

**Performance Benefits**:
- **Startup Cost**: Single detection (10-50ms) vs repeated calls
- **Memory Efficiency**: Shared reference counting with `Arc`
- **Thread Safety**: Lock-free access after initialization
- **Configuration Respect**: Hardware detection respects TOML flags

=== Hardware Detection Implementation

**CPU Detection**:
- Uses `raw_cpuid` crate for x86_64 architecture detection
- Falls back to `num_cpus` for core counting on all architectures
- Vendor and model string extraction from CPUID instructions
- SIMD capability detection through feature flags

**GPU Detection**:
- Feature-gated compilation (`#[cfg(feature = "gpu")]`)
- Fallback structs for non-GPU builds
- Multi-backend support with runtime detection
- Memory and compute capability enumeration

**Memory Detection**:
- Uses `sysinfo` crate for cross-platform memory information
- Recommends cache sizes as 10% of available memory (capped at 8GB)
- Total/available memory tracking for optimization decisions

== MVCC Resolution Implementation

=== Centralized Version Control Architecture

**Design Pattern**: Centralized `MvccResolver` with sophisticated lifecycle management and expiry handling for consistent data versioning across all storage engines.

[source,rust]
----
pub struct MvccResolver {
    current_timestamp: u32,
}

impl MvccResolver {
    pub fn resolve_batch(&self, records: Vec<VectorRecord>) -> Vec<VectorRecord> {
        // 1. Separate by ID presence (empty ID = append-only)
        // 2. Group by ID for version resolution
        // 3. Apply expiry rules (expires_at < current_time)
        // 4. Select highest version without gaps
        // 5. Handle timestamp precedence for same version
    }
}
----

**Resolution Logic**:
1. **Expiry Check**: Records with `expires_at < current_time` are excluded
2. **ID Grouping**: Records grouped by ID for version comparison
3. **Version Selection**: Highest version without gaps wins (starts from 1)
4. **Timestamp Precedence**: Earliest timestamp for identical versions
5. **Append-Only Mode**: Empty/null IDs bypass versioning for throughput
6. **Global Deletion**: Non-empty ID expiry affects all versions

**Performance Characteristics**:
- **Memory Efficient**: HashMap grouping with streaming processing
- **Thread Safe**: Immutable resolver with timestamp injection
- **Test Coverage**: Comprehensive edge case validation
- **Configurable**: Timestamp injection for deterministic testing

impl SimdVectorParser {
    fn parse_with_simd(&mut self, input: &str) -> Result<Vec<f32>> {
        if self.simd_caps.has_avx2 {
            self.parse_avx2(input)
        } else if self.simd_caps.has_sse41 {
            self.parse_sse41(input)
        } else {
            self.parse_scalar(input)
        }
    }
}

**Dynamic Backend Selection**:
[source,rust]
----
pub fn preferred_backend(&self) -> HardwareBackend {
    if self.has_gpu() {
        match self.gpu.backend {
            GpuBackend::CUDA => HardwareBackend::CUDA,
            GpuBackend::ROCm => HardwareBackend::ROCm,
            _ => self.cpu_backend(),
        }
    } else {
        self.cpu_backend()  // AVX512 > AVX2 > SSE > Scalar
    }
}
----

== Search Optimization Analysis

=== Current Architecture Overview

ProximaDB implements a sophisticated three-tier search architecture with parallel processing:

```
Query → DirectVectorService → Parallel Search:
    ├─ Memtable Search (Unflushed WAL)
    ├─ VIPER Engine Search (Parquet files)
    └─ SST Engine Search (SSTable files)
         ↓
    Multi-Tier Deduplication
         ↓
    Final Results
```

=== Key Component Optimizations

**DirectVectorService** (`src/services/direct_vector_service.rs`):
- Zero WAL Manager Registry overhead with direct memtable access
- Parallel search across storage engines
- Unified distance computation with 40-60% latency reduction

**GlobalPartitionedMemtable**:
- Per-collection partitioning for efficient operations
- Native WAL batch storage (no deserialization overhead)
- MVCC support with logical delete via expiry timestamps
- Fast vector ID index for O(1) lookups

**VIPER Engine Adaptive Reading**:
- DirectArrow, MetadataFiltered, QuantizedTwoStage strategies
- Column projection for I/O reduction (60-90% reduction)
- Predicate pushdown to Parquet row groups
- Cloud storage optimization with range requests

**SST Engine Three-Stage Filtering**:
- Bloom → Index Block → Row filtering pipeline
- Block-level caching with LRU eviction
- MVCC-aware result merging
- Bytemuck serialization for 5-10x speedup

=== Implemented Optimizations (2025-08)

**Bloom Filters for Memtable** ✅:
- CompositeBloomFilter integrated into WriteBufferVectorBatch
