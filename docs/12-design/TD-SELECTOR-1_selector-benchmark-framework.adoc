= TD-SELECTOR-1: Calibrated Open-Weight Selector Benchmark

Status:: Implemented — gates 2/4/5 (synthetic) + gate 3 (real dev data; held-out sealed)
Date:: 2026-08-23 (gates 2/4, #1730); 2026-08-25..26 (gate 5, #1736/#1741); 2026-08-27 (gate 3)
Worktree:: `feat/selector-benchmark` (#1730); `feat/selector-onnx-parity` (gate 5 + follow-ups)

== Context

PR #1726 (merged as `574e66021`) established that *candidate generation* is no longer
the binding constraint: Recall@100 reached a 0.3734 pool ceiling, but the *selector*
delivered only 0.3136. The next gains live in selection, and selecting requires
comparing selectors fairly — which requires a harness whose comparisons mean
something.

== Problem Statement

Ad-hoc selector evaluation conflates three things that must be separated:

1. **Generation vs selection.** If each candidate strategy retrieves its own pool,
   a measured difference could be the retriever, the selector, or an interaction.
2. **Point estimates vs evidence.** "0.35 vs 0.34 recall" without an interval or a
   paired test is noise-shaping, especially at n = 50 queries.
3. **Recall vs downstream answer quality.** A selector that loses Recall@100 may
   lose the *specific documents that carry answers*, which is what users feel.

== Solution

A harness in `benches/` plus an integration-test suite, both consuming **synthetic,
seeded beds**:

|`answer_quality_report`)

=== Protocol invariants (each enforced by a test)

1. **Pool preservation** — `noop` measures identically whether run alone or beside
   four rival selectors; no selector can exceed the pool's coverage ceiling.
2. **Recall is recall** — divided by |relevant|, not by k (the first revision
   divided by k and was reporting precision@k).
3. **Truncation is measurable** — a reranker with a 50-deep window scores exactly
   the upstream's Recall@50; widening the window recovers recall monotonically.
4. **Real statistics** — percentile bootstrap CIs; paired sign-flip p-values with a
   `+1` correction so p is never exactly 0; a selector against itself is never
   significant.
5. **Promotion gate** — a point-estimate leader that is not significantly better
   than every rival yields no promotable recommendation.

== Verified results (synthetic bed)

All numbers below are from seeded synthetic beds (40 queries, 2 000 docs,
200 relevant/query, pool 300, seed `0x0DEF_ACED_0000_0001`) and are reproducible
via `cargo nextest run --no-capture selector_sweep_report answer_quality_report`.
They validate the *mechanism*, not production quality.

|cascade_bm25_first |0.3405 |[0.3305, 0.3502] |0.16
|xenc_w50_q90 |0.2577 |[0.2474, 0.2684] |0.65
|===

Findings:

* **RRF leads on the point estimate but was NOT promoted** — the difference vs
  `noop_raw_union` did not reach significance, and the gate correctly withheld the
  recommendation ("Not promotable on this evidence — collect more queries or
  accept the incumbent"). This is gate 3 working as designed.
* **The narrow rerank window is catastrophic** — w50 scores 0.2577 vs the 0.4286 of
  the 50/50 fusion (p = 0.0010). Window size dominates model quality in this
  regime, exactly the PR #1726 shape (0.3734 pool → 0.3136 delivered).
* **Cascades pay structurally** — gating on one retriever's top-100 forfeits the
  union's coverage advantage; `cascade_bm25_first` is worst of the non-truncating
  selectors.
* Latency in this harness is in-process sort/scan time and is not comparable to
  production latency; it is retained only to flag asymptotics (e.g. w400 rerank).

=== Gate 4 — answer quality on the selectors' real rankings

The QA bed pins each question's gold document at a controlled rank (top-10
reachable for 10.0%, top-25 for 18.3%, top-100 for 66.7% of questions). The
selectors from gate 2 produce the rankings; the extractors read them. No
re-simulation.

[cols="3,2,2,2,2"]
|===
|Selector / extractor |EM |F1 |Span IoU |Gold-doc retrieved

|rrf_k60 / best_sentence |1.0000 |1.0000 |1.0000 |1.0000
|weighted_60_40 / best_sentence |1.0000 |1.0000 |1.0000 |1.0000
|keeps_everything / best_sentence |0.9167 |0.9342 |0.9167 |1.0000
|xenc_w100 / best_sentence |0/F1 0.9079 |0.9079 |0.8833 |0.8833
|xenc_w25 / best_sentence |0.4667 |0.5509 |0.4667 |0.4667
|xenc_w10 / best_sentence |0.1833 |0.2868 |0.1833 |0.1833
|whole_top_document (any selector) |0.0000 |≈0.035 |≈0.003 |varies
|===

Findings:

* **EM ≤ gold-doc retrieval always holds**, and is enforced as a test: an extractor
  cannot produce the gold answer from a ranking that does not contain the gold
  document. This bound is what makes the gate interpretable.
* **The cost of truncation reaches the answer.** w10 → 0.1833 EM vs 1.0 for the
  fusions (p = 0.0050). Recall@k loss and answer loss are the same loss, seen from
  different ends.
* **NoOp is NOT optimal on answer quality** — it retrieves every gold document but
  scores 0.9167 EM vs 1.0000 for the fusions, because ordering matters downstream:
  the extractor reads depth first. A selector can be recall-perfect and still cost
  answer quality by putting distractors on top. (Not significant at n=60;
  reported, not promoted.)
* The `whole_top_document` extractor floor (~0.035 F1) quantifies what "return the
  whole chunk" costs vs sentence-level extraction on this bed.

== Scope and honesty boundary

* Synthetic beds, modelled reranker (finite window + quality parameter), lexical
  extractors. **None of these numbers are admissible in `BENCHMARK_EVIDENCE.toml`**
  or as claims about production retrieval. The harness is the deliverable; the
  numbers prove the harness discriminates.
* `recall_utils.rs` computes recall for ANN ground truth typed by distance
  (`GroundTruthResult`); this harness scores IR relevance *sets*. The two do not
  share a ground-truth type, so reuse would be a redefinition, not a deduplication.
  Reuse of `stats` (bootstrap / sign-flip) is direct, within this harness.

== Gate 5 — serving ONNX parity, latency, model catalog (2026-08-25)

=== Parity: the serving path reproduces the evidence path

`crates/modalities/proximadb-rank-onnx/tests/onnx_parity.rs` (features
`real-onnx,bert-tokenizer`, env-gated on the registered
`PROXIMADB_TEST_BERT_ONNX_PATH`) runs the **full production stack** —
`BertPairTokenizingDocFeatureExtractor` → `TokenizedBatch` →
`OrtTokenizedScorerSession` — over 64 deterministic pairs (fixture checked in at
`tests/fixtures/onnx_parity_fixture.json`, reference scores generated on the exact
#1726 path: pinned revision `4bebbd56`, MPS fp32) against an ONNX export of that
same revision (sha256 `891b594d2e81…`, artifact at
`/Users/vijaysingh/proximadb-bench-data/retrieval-quality-onnx-parity-v1/`).

**Measured: max |Δ| = 6.8e-06, Spearman = 1.000000.** Assertion tolerances are
1e-4 absolute / Spearman ≥ 0.999 — ~15× the observed margin, loose enough for
cross-platform ort variance, tight enough that a binding/dtype/segment bug (which
moves logits by whole units) cannot pass. Parity is proven for within-budget pairs
including 359-token long docs.

=== Two contract discoveries (the point of a parity test)

1. **Truncation contract diverges between the paths.** The serving extractor
   *rejects* pairs exceeding `max_seq_len` ("split the document before reranking"
   — the zero-truncation contract), while the #1726 Python gate path asked the
   tokenizer to truncate. Serving is stricter, which is the safe direction:
   window-splitting of oversized documents is a caller responsibility. Parity is
   asserted within-budget; the fixture's max pair is 359 of 512 tokens.
2. **Fixed-length padding cost ~11× compute — FIXED.** The conversion layer
   padded every pair to `max_seq_len`; the fixture's median pair is 37 tokens
   (p90 39, long tail 359), so waste was 512·n/Σlen ≈ **11.0×**. Rows now keep
   their true length and the conversion pads to the longest row in the batch
   (still rectangular, which is all the session contract requires). The pad id
   is resolved from the tokenizer (XLM-R pads with 1; the old hardcoded 0 was
   wrong for non-BERT families). Gate: the parity fixture re-run — max |Δ| =
   6.795e-06, Spearman = 1.000000, *identical to before the change*. Window-25
   latency: 1243 ms → 68.8 ms (~18×). Remaining cost structure: one long
   document sets its whole window's width (window 50 with the 359-token doc
   stays ~1.5 s) — heterogeneous windows want length bucketing or the same
   query-aware window-splitting #1726 used for correctness, now for cost too.

=== Harness integration

`tests/retrieval_quality_gates.rs` grows a `#[cfg(feature = "onnx")]` module that
runs the REAL production scorer as one more selector under the gate-4 protocol:
same preserved pools, same `AnswerQualityEvaluator`, same paired statistics as
the modelled strategies — the comparison isolates real-vs-modelled *scoring*,
not window policy. Long docs are sentence-window split with max-over-window (the
#1726 protocol) rather than rejected. Default CI compiles nothing from the module
(root `onnx` feature off); it runs manually with the registered env gates.

== Gate 3 — selector protocol on real development data (2026-08-27)

Ran the selector protocol on the REAL #1726 campaign data (NFCorpus dev, 324
queries, 57 306 query-source pairs, pinned MiniLM `4bebbd56` cached scores — zero
new inference). Preserved pool: the bm25+bge RRF union (128–200 candidates/query).
Every selector consumes that pool; depths were materialized with the existing
`rerank_source_candidates.py materialize` (the `--rerank-all` reproduction is
byte-identical to the shipped #1726 run, sha `30325bd876661f74` — pipeline
integrity confirmed).

=== Findings

1. **The #1726 selector regression is a depth-policy artifact, not model quality
   — and it is structural.** The shipped run reordered EVERY candidate
   (`rerank_count: "all"`). Any bounded depth D ≤ 100 keeps positions D+1..100 in
   union order, so top-100 membership equals the union's *by construction*: Recall@100
   = 0.3208 for D ∈ {10, 20, 100}, deterministically, while the unbounded reorder
   uniquely loses it (0.3136, −0.0072) by pushing mid-tail relevant documents past
   rank 100. The synthetic gate-2 theorem ("a W-deep reranker's Recall@k IS its
   upstream's Recall@min(W,k)") holds verbatim on production data.
2. **Dev-selected candidate: rerank@20** — best on all four metrics — but the
   paired comparisons vs the incumbent do NOT clear significance at n = 324:
   NDCG@10 Δ +0.006503 CI [−0.001850, +0.014628]; Recall@100 Δ +0.007238 CI
   [−0.002569, +0.017110]. Both intervals include zero.
3. **Verdict: NOT promotable on quality grounds; held-out stays sealed.** The
   decisive claim (recall preservation under bounded depth) is deterministic, so a
   held-out run would confirm nothing; spending the seal on a non-significant
   quality delta is precisely what the promotion rule forbids.

better than the incumbent on NDCG@10 with Recall@100 structurally preserved).

the pre-registered pair (incumbent MiniLM + BGE@20) on the fused test pool, no
selection freedom.

=== Production-shape mapping

`CrossModalReranker` (`crates/query/proximadb-query/src/reranking.rs:536`) does
`records.into_iter().take(rerank_top_k)` — a BOUNDED reorder (default
`rerank_top_k` = 100), so serving does not have the rerank-all pathology for
top-100 consumers. Two caveats recorded for follow-up:

* the tail past `rerank_top_k` is **dropped, not preserved**: a consumer asking
  for top-K > `rerank_top_k` silently loses records. The bench pipeline's
  `materialize_run` keeps the tail (`merged.extend(candidates[D..])`) — the
  recall-preserving shape. Aligning the Rust seam to preserve-and-append is a
  behavior change (result cardinality) that deserves its own eval, not a rider.
* the evidence pipeline's scorer supports both policies (`--rerank-count D` vs
  `--rerank-all`); **`--rerank-all` should not be used for delivered top-100
  selection** — that is the one policy measured to lose recall.

== Remaining gates

* **Gate 3 (held-out confirmation)**: dev-side complete (above); the held-out
  split remains sealed until a dev candidate clears significance. A larger dev
  bed or a stronger reranker (BGE, catalog-pinned) are the two levers that could
  produce one.
* **Length bucketing for heterogeneous windows**: one long document sets the whole
  window's batch width (see the latency table). Bucketing or window-splitting
  recovers it; the parity fixtures re-run as the gate.
* **A third model** (e.g. an int8-quantized MiniLM): export → parity fixture →
  catalog row — the harness is mechanical to extend now.
