== Context

A recurring design challenge: ProximaDB's **dual-path** architecture serves
relational/warehouse workloads with **DataFusion over standard Parquet**
(Iceberg-managed) and vector/ANN workloads with native engines over the custom
**PAX** block format. This raised a sharp co-design question: *why use Parquet at
all — shouldn't a co-designed database own a single primary format optimized for
the object-storage cost model, and relegate Parquet to a secondary export/interop
role?*

The TPC-H pgwire conformance suite is **22/22 green** over the Parquet/DataFusion
arm, so relational lowering is correct and the warehouse arm works. That makes the
*format* question — not the lowering question — the open frontier.

This ADR records the decision after a deep, adversarially-verified survey of how
the leading systems design their **primary** storage format (PostgreSQL, MySQL/
InnoDB, Oracle/Exadata, Amazon Aurora, Neon) and the columnar/lakehouse and
vector-DB landscape (ClickHouse, Snowflake, BigQuery, DuckDB, Delta/Iceberg,
Lance, Turbopuffer). 22 sources, 106 claims extracted, 25 adversarially verified
(24 confirmed, 1 refuted).

== Evidence (verified)

=== Nobody uses Parquet as a primary format

Every surveyed engine owns a primary format co-designed for its access pattern;
open columnar formats appear only at the interop edge:

* **PostgreSQL** — heap, 8KB pages, inline MVCC + TOAST (heap bloat / VACUUM is the cost).
* **MySQL/InnoDB** — clustered (index-organized) B+tree; latest version inline, old versions in undo.
* **Oracle/Exadata** — data blocks + **Hybrid Columnar Compression**, itself a **PAX-style** hybrid (columns grouped within a self-contained Compression Unit); **Smart Scan** offloads *projection + predicate filtering + decompression* to the storage cells (a storage⇄compute co-design; a 1 TB scan returning 2 MB ships only 2 MB to the DB tier).
* **Amazon Aurora** — *"the log is the database"*: only redo log records cross the network; pages are materialized in the storage tier on demand (35× more txns than mirrored MySQL at 7.7× fewer I/Os).
* **Neon** — log-structured **image+delta layer files** keyed by (key-range, LSN) over S3; pages reconstructed from WAL via `get_page_at_lsn`; copy-on-write branching falls out of the immutable layer model.
* **Snowflake** — proprietary **micro-partitions** are primary; Iceberg/Parquet is the *interop* option, with clustering/governance layered on top.
* **ClickHouse** (MergeTree + sparse primary index + min-max/set/Bloom skip indexes), **BigQuery** (Capacitor), **Lance**, **Turbopuffer** — all custom-primary.

=== Parquet's specific failures on object storage

* **Round-trip amplification** — one query can issue **dozens-to-hundreds of sequential dependent S3 GETs** (footer → row-group metadata → page index → data pages). At ~250 ms p90 per <1 MB GET, *round-trip count*, not bytes, dominates.
* **Coarse pruning** — a single per-row-group footer stats layer (ORC has 3; MergeTree adds a sparse primary index Parquet's footer can't replicate).
* **Poor random access** — point lookup is O(n) for variable-width data; reading one row touches a full ~1 MB page; metadata bloats to tens of MB; the page-offset index costs **~20 GiB/billion rows** (Lance caps an equivalent search cache at ~1.28 GiB).
* **No native secondary/vector indexes; weak update/delete** (immutable files defer mutation to a table-format layer).

=== Where the "replace Parquet" case is *overstated* (the refutations matter)

The adversarial pass killed or qualified several common arguments — recorded here
to keep the decision honest:

* ✗ *"Parquet must re-read the footer every query"* — **false**; solvable with metadata caching, not a format limit.
* ⚠️ For pure **sequential OLAP scans**, the custom-vs-Parquet gap is **< 2×**. The 100×-2000× Lance figures are for **random access / point lookup / vector search**, *not* scans.
* ⚠️ **Disaggregation (log-is-the-database) is not free**: workload-dependent (~2.5× write gain only under heavy load; *none* under light load), and read-after-write pays log-replay overhead (20-66% lag).
* ⚠️ **Parquet-as-primary IS right for lakehouse/Iceberg interop** — engine-agnostic cross-engine sharing over one physical copy (Snowflake productizes exactly this).
* The PAX paper itself (Ailamaki et al., VLDB'01) is a **cache/CPU** optimization (≥75% fewer L2 misses, 11-48% on TPC-H), *orthogonal* to I/O — PAX-on-object-storage value comes from the *layout discipline*, not the original cache result.

**Net:** the custom-format payoff is **concentrated in random-access / vector /
selective / round-trip-bound workloads (100×+), and is small (< 2×) for
sequential OLAP scans.**

== Decision

. **The dual-path is vindicated, with a sharper rationale.** Keep **Parquet as the
  primary for the relational-OLAP-scan arm** — it is within ~2× of a custom format
  on scans *and* it is the Iceberg interop seam. This is the correct call there, not
  a compromise. Parquet is **not** demoted to "export only"; it is the legitimate
  primary for relational scan + cross-engine interop + reading externally-produced data.

. **Spend the custom-format (PAX) budget exactly where the data shows 100×:** the
  **vector/ANN + point-lookup + selective** path — which is already PAX (ADR-026).
  The co-design levers the survey most strongly supports are **round-trip
  minimization** and **format⇄index co-design**, not raw scan throughput.

. **Adopt an explicit object-storage round-trip budget on the PAX/vector path**
  (cf. Turbopuffer's ≤3 round-trips per search; ~444 ms cold → ~10 ms warm). The
  `io_trace` `range_gets` term + the route cost model already *measure* this — make
  it a first-class design constraint, and treat Parquet's footer round-trip
  amplification as the measured anti-pattern.

. **Co-optimize the PAX format WITH its indexes** (clustered layout, zone maps,
  secondary + vector indexes over the same dataset — the Lance pattern), rather
  than treating storage and indexing as separate layers.

== Consequences — recast TD-162a-2

TD-162a-2 (the typed `user_columns` PAX stripe + per-column zone maps that unblocks
the native OLAP scan over PAX) is **re-justified**: its value is **not** "beat
Parquet on OLAP scans" (that buys < 2×). Its real worth is:

* **(a) One co-designed store** for relational + vector — no dual materialization, and the round-trip budget applies uniformly.
* **(b) Enables the Native cost-router arm** — gives the routing cost loop a real second arm over PAX, closing the counterfactual-trace gap (the calibrated-surface caveat in the offline routing proof).
* **(c) Zone-map / projection pruning + round-trip control** on the **selective** queries where the custom format wins big — *not* the full-scan aggregates where Parquet already suffices.

Concretely: prioritize the typed stripe + per-column zone maps (pruning, round-trip
control) and the format⇄index co-design over chasing scan-throughput parity with
DataFusion/Parquet (already near-parity). Keep the Parquet/DataFusion warehouse arm
as-is; it is correct and ratcheted (TPC-H 22/22).

== Verification

* The thesis "no serious DB uses Parquet as primary" is confirmed across 5 incumbents + 4 columnar/vector systems.
* The "own a custom format" win is **quantified and bounded**: 100×+ on random access / vector; < 2× on sequential scans — so the investment is targeted, not wholesale.
* Out of scope (not decided here): the specific PAX stripe encoding (TD-162a-2 LLD), and whether the relational Native arm should ever supersede DataFusion for scans (it should not, on this evidence).
