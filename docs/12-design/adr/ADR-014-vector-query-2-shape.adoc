= ADR-014: Vector Query Two-Shape Boundary
:toc: left
:toclevels: 3
:icons: font
:source-highlighter: rouge
:last-updated: 2026-05-25

== Status

Accepted

== Context

`VectorOperationsService` (in `src/services/operations/vectors/legacy.rs`,
~5 000 lines) currently implements two distinct trait contracts whose
`search`-shaped methods do nearly the same work but with different request
shapes:

1. **`proximadb_runtime::VectorOpsPort::search`**
   (`crates/platform/proximadb-runtime/src/service_ports.rs`)
* Takes the proto wire type
   `proximadb_proto::v1::VectorSearchRequest`
* Carries `queries: Vec<SearchQuery>` and a `HashMap<String, _>`-style
   metadata filter built from the gRPC/REST wire schema
* Has three implementors: production `VectorOperationsService`,
   `MockVectorOpsPort` (runtime crate tests), `NoopVectorOpsPort`
   (proximadb-api startup defaults)
* Used widely as `Arc<dyn VectorOpsPort>` from `UnifiedHandlers`, the REST
   v1 handlers, and the multi-server composition root.
2. **`proximadb_vector_query::VectorQueryService::vector_search`**
   (`crates/query/proximadb-vector-query/src/lib.rs`)
* Takes `VectorQueryRequest`, an in-process Rust contract with a single
   `query_vector: Vec<f32>`, typed `DistanceMetric`, and a string filter
   expression
* Has two implementors: `VectorOperationsService` (root crate) and
   `VectorServiceImpl` (`crates/modalities/proximadb-vector`, the Phase 3
   modality-extracted runtime)
* Used by `UnifiedQueryApiState.vector_query_service` and
   `MultiProtocolHandler.vector_query_service` as the trait object that
   cross-modal query orchestration depends on.

Both impls ultimately delegate to the same
`VectorOperationsService::search_v1(VectorSearchRequest)` proto-typed
entry point (`legacy.rs:811`), so for the production service the search
algebra is single-rooted. The duplication is purely at the contract
surface.

CLAUDE.md asserts a "Use proto types directly (zero-copy principle).
Proto types have Serde compatibility for JSON/REST." This points toward
collapsing both shapes onto the proto type. `VectorQueryRequest` was
introduced because the proto type is ergonomically painful for
in-process Rust callers: every cross-modal call site would otherwise
have to construct a one-element `Vec<SearchQuery>`, materialize a
HashMap-based metadata filter, and untyped-stringly map distance
metrics. Worse, requiring the modality crate (`proximadb-vector`) to
depend on the wire proto would couple a clean Phase 3 modality
extraction back to the protocol layer it is meant to be independent of.

The proliferation audit
(`memory/project_proliferation_audit_2026_05_25.md`) surfaced this as a
P5 ("proto-vs-Rust shape mismatch") item, and the question is whether
the second shape is a regression we should remove or a deliberate
boundary we should document.

== Decision

**Keep both shapes. Treat the two-shape situation as a deliberate
control-plane vs. orchestration-plane boundary and prohibit further
convergence attempts that would collapse them.**

The two traits answer different questions for different layers:

[cols="1,2,2"]
|===
| Trait | Question it answers | Owner

| `VectorOpsPort`
| "How does the platform runtime layer call into the concrete vector
service across the crate boundary, using only types the runtime already
needs (proto + std)?"
| `crates/platform/proximadb-runtime`

| `VectorQueryService`
| "What is the minimum, modality-neutral Rust surface a cross-modal
query orchestrator needs to plan and execute one vector probe inside a
larger plan?"
| `crates/query/proximadb-vector-query`
|===

`VectorOpsPort` is a *handler / runtime port*. It is wide (search,
batch, get, flush, metrics), tenant-scoped, and uses proto because the
runtime layer already speaks proto and `UnifiedHandlers` is the
composition root for REST/gRPC handlers. Three implementors exist and
all of them legitimately need the full CRUD surface plus the proto
shape.

`VectorQueryService` is a *cross-modal orchestration contract*. It is
narrow (one async method, read-only), modality-clean, and uses
`ProximaRecord` for results. Two implementors exist and the second one
(`VectorServiceImpl` in `proximadb-vector`) is the entire point: the
Phase 3 modality runtime must be implementable without pulling in the
root crate's proto types.

== Consequences

* The pre-condition for collapsing onto `VectorOpsPort` (option A) is
that the `proximadb-vector` modality crate would have to depend on
`proximadb-proto` and lower its `VectorServiceImpl` through the wire
shape. That regresses the Phase 3 / multi-modal overhaul boundary
(`roadmap/MULTIMODAL_OVERHAUL_SPEC_2026_05_08.adoc`) and is rejected.
* The pre-condition for collapsing onto `VectorQueryService` (option B)
is that `VectorOpsPort::search` would take a Rust-typed request, which
means `UnifiedHandlers` and every REST/gRPC handler does a wire→Rust
conversion before the port call. The port's *purpose* is to be the
proto-facing handler/runtime port. Pushing the conversion to the proto
edge inverts the port's design and is rejected.
* `VectorOperationsService::search_v1` remains the single
implementation root. Both trait impls in
`src/services/operations/vectors/legacy.rs` (`VectorQueryService` at
~4 911 and `VectorOpsPort` at ~4 980) must continue to delegate to
`search_v1` rather than duplicate search logic.
* New entry points (e.g., Arrow Flight, future MPP fragments) must
declare which contract they consume and route through one of the two
existing impls. They must not introduce a third request shape with the
same semantics.
* Conversion direction is fixed:
** Proto → Rust contract lives at the *call site* in the orchestration
plane (e.g., `multi_protocol_handler.rs:1185-1202` constructs
`VectorQueryRequest` from `VectorSearchQuery`). It does *not* live in
`proximadb-vector-query` (the contract crate stays modality-clean) and
it does *not* live in `proximadb-runtime` (the runtime stays
proto-clean).
** Rust contract → proto is *not* a supported direction. If a
`VectorOpsPort` consumer ever needs to call through a
`VectorQueryService`, the answer is "wire a separate
`VectorQueryService` trait object into the consumer" rather than
synthesize a proto request from a Rust one.
* The two-shape boundary must be documented in
`src/services/operations/vectors/legacy.rs` and in the
`proximadb-vector-query` crate docs. Both already carry the rationale
inline; this ADR is the canonical reference both should cite.

== Rejected Alternatives

=== Option A: Proto-first, delete `VectorQueryService`

Make all in-process callers use
`proximadb_proto::v1::VectorSearchRequest`. Delete
`crates/query/proximadb-vector-query` (or shrink it to the trait-free
`VectorSearchExpr` already in that crate). Make
`proximadb-vector::VectorServiceImpl` either depend on
`proximadb-proto` or be deleted.

Rejected because:

* Forces the modality crate to depend on the wire proto, regressing
the Phase 3 modality extraction.
* Forces every cross-modal orchestrator site to construct
`Vec<SearchQuery>` + HashMap filter + untyped metric for what is
semantically a one-vector probe.
* Removes the Rust-typed `DistanceMetric` boundary, which is one of the
deliberate fixes from the `proximadb-distance-types` foundation crate
(see `proximadb-vector-query::lib.rs` re-export comment).

=== Option B: Rust-contract first, push proto conversion to the wire edge

Make `VectorOperationsService::search_v1` take `VectorQueryRequest`.
Move the proto→contract conversion into the REST and gRPC handlers.
`VectorOpsPort::search` would then accept the Rust-typed request.

Rejected because:

* `VectorOpsPort` is *by design* the proto-facing port between
`proximadb-runtime`'s `UnifiedHandlers` and the concrete service.
Stripping the proto type from the port turns it into a second copy of
`VectorQueryService` with extra mutation methods, which is the
proliferation we are trying to avoid.
* `MockVectorOpsPort` and `NoopVectorOpsPort` exist precisely to let
the runtime crate test/boot against the proto contract without
pulling in the Rust contract crate. Inverting the shape breaks that.
* The conversion cost we save in `legacy.rs` is paid back in every
REST and gRPC handler — and they call this path far more often than
the cross-modal orchestrator does.

== Governs

* `src/services/operations/vectors/legacy.rs` — two-shape implementor
* `crates/query/proximadb-vector-query/src/lib.rs` — Rust contract crate
* `crates/modalities/proximadb-vector/src/service.rs` — second
`VectorQueryService` implementor
* `crates/platform/proximadb-runtime/src/service_ports.rs` —
`VectorOpsPort` definition
* `src/network/multi_protocol_handler.rs` — proto→Rust conversion site
(orchestration plane)
* `src/network/rest/v1/multimodal_query.rs` — `vector_query_service`
trait-object wiring
