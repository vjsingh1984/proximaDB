== Context

ProximaDB has Iceberg/Delta/Unity catalog *client* implementations (connecting to external systems) but no way for external compute engines (Spark, Trino, DuckDB, Flink, PyIceberg, Polaris) to treat ProximaDB as a catalog authority without writing a custom connector.

The Apache Iceberg REST Catalog specification v1 is a lightweight HTTP contract that every major compute engine supports out of the box.  Implementing the server side inside xCatalog removes the integration barrier entirely.

Relevant research:

* XTable in Action (2401.09621): format-agnostic catalog metadata translation; confirms Iceberg REST is the convergence point for open-format federation.
* Hadoop InputFormat mental model: `getSplits()` (coordinator, metadata-only) → `createRecordReader()` (worker, data I/O).  Iceberg REST + Arrow Flight maps to this exactly.

== Decision

Mount a full Iceberg REST Catalog v1 server at `/iceberg/v1` (port 5678).  It is always on — no feature gate.  External engines configure:

----
catalog URI: http://host:5678/iceberg/v1
----

This ADR is constrained by ADR-009. Iceberg REST is a schema-on-read catalog and split-planning
surface over xCatalog and `ProximaRecord` views. It must not make Iceberg metadata, Parquet files,
Arrow Flight tickets, or legacy vector-shaped DTOs the semantic record authority.

=== Endpoint Surface

=== ProximaRecord → Iceberg Canonical Schema (ADR-ICE-001)

Every ProximaDB collection exposed as an Iceberg table uses this fixed column prefix.
Cross-engine consistency depends on it — do not deviate.

[cols="3,3,2,3"]
|===
| ProximaRecord field | Iceberg column | Iceberg type | Notes

| `id` / `oid` | `id` | `string` required | partition candidate
| `tenant_id` | `tenant_id` | `string` required | default partition column
| `created_at_ns` | `created_at` | `timestamptz` | nanoseconds ÷ 1000
| `updated_at_ns` | `updated_at` | `timestamptz` |
| `valid_from_ns` | `valid_from` | `timestamptz` optional | bi-temporal lower bound
| `valid_to_ns` | `valid_to` | `timestamptz` optional | bi-temporal upper bound

| `origin` | `origin` | `string` optional | provenance

=== Synthetic Iceberg Snapshot

For existing ProximaDB collections, `load table` returns a synthetic snapshot:

* One current snapshot with a manifest-list URL (`/iceberg/v1/{ns}/{t}/manifests/current`)
* One manifest entry per VIPER/NOVA/HELIX storage shard: row count, size bytes, column stats
* Arrow Flight ticket embedded in `write-credentials` → workers exchange at port 5680

=== Hadoop Split Mapping

[source]
----
Coordinator: getSplits() / planInputPartitions()
  → GET /iceberg/v1/.../tables/{t}        (metadata-only, cheap)
  → parse partition spec + manifest entries
  → one split per ProximaDB storage shard

Worker: createRecordReader() / scan
  → exchange Arrow Flight ticket at port 5680
  → read Arrow IPC batches of ProximaRecord rows
----

This is Trino `ConnectorSplitSource` + `ConnectorPageSource` and Spark `DataSource V2` exactly.

For external Hadoop-style key/value or semi-structured files, xCatalog registration supplies the
`ProximaType` mapping: keys map to identity/partition/index columns and values map to `Map`, `Json`,
`Struct`, `Binary`, or declared typed columns. Readers project data into `ProximaRecord` before
query planning.

=== Key Source Files

* `src/catalog/iceberg_rest_service.rs` — service layer; `CatalogTableSchema ↔ IcebergTableMetadata` translation; synthetic snapshot generation
* `src/network/rest/v1/iceberg_rest_catalog.rs` — Axum route handlers; `IcebergRestState`; `create_iceberg_rest_router()`

== Consequences

=== Positive

* Spark, Trino, DuckDB, Flink, and PyIceberg connect to ProximaDB without any custom connector code.
* ProximaDB becomes a catalog authority; external engines can plan splits against ProximaDB shards.
* HNSW index metadata in table properties lets engines discover embedding dimensions and index types.
* Arrow Flight (port 5680) is the natural data-plane complement; Iceberg REST handles catalog only.

=== Negative / Risks

* Arrow Flight server is currently a stub (501).  Full external data access requires completing the Flight implementation (Phase D/E).
* Synthetic Iceberg manifests must be kept consistent with storage engine shard topology on compaction.
* OAuth2/token auth is currently a 501 stub — production deployments behind a proxy need this wired.

=== Neutral

* Iceberg REST endpoints are added unconditionally (no feature flag).  This is intentional — the catalog is always accessible, keeping external engine configuration simple.
* The `/iceberg/v1` prefix avoids conflict with `/api/v1/*` internal routes.
