= ADR-015: Port Impl Location — Bare Concrete Service vs gRPC Wrapper
:toc: left
:toclevels: 3
:icons: font
:last-updated: 2026-05-25

== Status

Accepted

== Context

`proximadb_runtime` defines a family of port traits
(`CollectionPort`, `VectorOpsPort`, `DocumentPort`, `GraphPort`,
`ObservabilityPort`, `SecurityPort`, etc.) that are the stable contracts
for the platform runtime to call into root-crate concrete services
without importing root-crate types. The Phase 9 "platform extraction"
work depends on these ports being implementable by both
production services and test fixtures so that `SharedServices`,
`MultiServer`, and `proximadb-api` can hold `Arc<dyn XxxPort>` trait
objects rather than concrete root-crate types.

Audit at `docs/_internal/status/PHASE9_REMAINING_2026_05_25.adoc` (Task
#76 section, "design finding: port impl location") shows the 5 services
that already have a port-trait counterpart split into two classes by
where the `impl XxxPort` lives:

* **Bare concrete service** (Collection, Vector): the impl is directly
on `CollectionService` / `VectorOperationsService` — the same type
SharedServices holds.
* **gRPC wrapper** (Document, Observability, Graph): the impl is on
`DocumentServiceImpl` / `ObservabilityServiceImpl` /
`GraphServiceImpl` — gRPC tonic adapters constructed at gRPC-server
startup, each wrapping `Arc<UnderlyingService>` and adding proto
conversion.

The wrapper-located impls came first historically because the gRPC
service was the first non-root caller and the wrapper was already
sitting in front of the underlying service. The bare-located impls
came later when Collection/Vector were promoted to the Phase 9 port
boundary directly.

== Decision

**Port impls belong on the bare concrete service, not on the gRPC
wrapper.** The gRPC wrapper is a thin proto-conversion shim and should
delegate to the port impl, not own it.

For the 3 currently-misplaced impls (`DocumentPort`,
`ObservabilityPort`, `GraphPort`), the migration is:

. Move `impl XxxPort for XxxServiceImpl` body → `impl XxxPort for
UnderlyingService` (the bare type SharedServices holds).
. Update each method body to use `&self` instead of `&self.inner_service` —
the body is mostly proto-conversion + delegation to bare-service methods,
which is exactly what stays on the bare service now.
. Leave the gRPC `XxxServiceImpl` in place; rewrite its trait method
bodies to delegate to `<UnderlyingService as XxxPort>::method(&self,
…)` instead of duplicating the logic.
. Add the parallel port-typed field on `SharedServices` via Arc::clone
+ trait-object coercion, same as `collection_port` + `vector_ops_port`
landed in commit `89bbe7ec3`.

Each service migration is one commit; the three are independent.

== Consequences

* `SharedServices` becomes the canonical holder of port trait objects
for non-gRPC consumers (REST handlers, embedded API, query
orchestrators). The current pattern of "construct a fresh
`XxxServiceImpl` at use-site" disappears outside the gRPC startup
path.
* The gRPC wrapper's trait-method bodies shrink to one-liners
(`self.inner.method(req).await`) once they delegate to the bare-service
port impl. Net code reduction per service: ~80-150 lines (each
method-body's proto-conversion + delegation now lives once on the
bare service).
* `DocumentServiceImpl` / `ObservabilityServiceImpl` /
`GraphServiceImpl` keep their `into_server()` constructors and tonic
trait impls — they remain the gRPC-tonic surface. They just stop
being where the *business* lives.
* Future ports for the remaining ~8 SharedServices fields without
ports (`CatalogManager`, `SegmentRegistry`, `MetricsCollector`,
`UnifiedQueryFacade`, etc.) must follow the same rule: define the
port in `proximadb_runtime`, impl on the bare concrete service, not
on any adapter layer that sits above it.

== Rejected alternatives

=== Option A: Status quo — leave impls on gRPC wrappers

Rejected because:

* `SharedServices` cannot hold `Arc<dyn DocumentPort>` cheaply — it would
have to construct a `DocumentServiceImpl` wrapping the underlying
service, which adds an indirection that has no value outside gRPC.
* Non-gRPC consumers (REST, embedded, query orchestrators) gain nothing
from the port abstraction unless they construct gRPC wrappers
themselves, which is structurally wrong.
* The "wrapper-as-port-impl" pattern doesn't compose for cases where the
port should be implemented by something that has no gRPC analog (e.g.,
an in-process mock that implements `DocumentPort` to satisfy
SharedServices but never speaks gRPC).

=== Option B: Move the impls onto a second new wrapper type

Define a `DocumentPortAdapter` (etc.) that wraps `Arc<DocStorageService>`
and impls `DocumentPort` separately from `DocumentServiceImpl`.

Rejected because:

* Adds proliferation — two wrappers over the same service for two
different traits.
* Misses the architectural truth: the port is the contract, the
service is the implementation; there is no reason for them to be
held apart by a wrapper.

== Governs

* `src/network/grpc/document_service.rs` — `impl DocumentPort` to move
* `src/network/grpc/observability_service.rs` — `impl ObservabilityPort`
  to move
* `src/network/grpc/graph_service.rs` — `impl GraphPort` to move
* `src/storage/document/mod.rs` (or wherever `DocStorageService` is
  defined) — new home for the DocumentPort impl
* `src/observability/service.rs` — new home for ObservabilityPort impl
* `src/graph/service.rs` — new home for GraphPort impl
* `src/network/shared_services.rs` — adds three more parallel port
  fields (`document_port`, `observability_port`, `graph_port`)

== File plan

[cols="1,3,3"]
|===
| Action | Path | Note

| MOVE
| `impl DocumentPort for DocumentServiceImpl` →
`impl DocumentPort for DocStorageService`
| ~150 lines of method bodies. Each method goes from
"convert proto, call self.document_service.method(...)" to
"convert proto, call self.method(...)".

| MOVE
| `impl ObservabilityPort for ObservabilityServiceImpl` →
`impl ObservabilityPort for ObservabilityService`
| Same pattern.

| MOVE
| `impl GraphPort for GraphServiceImpl` →
`impl GraphPort for GraphService`
| Same pattern.

| REWRITE (shrink)
| `impl DocumentService for DocumentServiceImpl` (the gRPC tonic trait)
| Each method becomes `<DocStorageService as DocumentPort>::method(
&self.inner, request.into_inner()).await.map(...)` — one-liner per
method.

| ADD
| `pub document_port: Arc<dyn DocumentPort>` (etc.) on `SharedServices`
| Same parallel-field pattern as `89bbe7ec3`.
|===
