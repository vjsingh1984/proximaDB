= ADR-019: Relational Query Architecture — Algebra, Executor, Transaction, Storage
:toc: left
:toclevels: 3
:icons: font
:last-updated: 2026-05-26

== Status

Accepted

== Context

ADR-018 captures the multi-phase pgwire/SQL parity roadmap. Phase 1
(MVP unblock) shipped: silent transactions, panic guards, ORDER BY,
information_schema standard shape, INSERT-without-cols. Phase 2 is the
substantive engineering — extended query protocol, JOIN execution,
aggregates + GROUP BY, real transactions, type system, functions.

Phase 2 has been blocked by a coherent architecture question: **how
does a SQL SELECT actually execute against ProximaDB's storage
engines?** A breadth survey (2026-05-26) found that:

* **AST parsing is complete** — sqlparser-rs is wired and produces a
  full algebra (JOIN / GROUP BY / aggregates / subqueries / CTEs).
* **PAX storage is rich** — block + stripe + column-meta carry
  min/max, null counts, bloom filter offsets, and MVCC bounds.
* **DML validation is solid** — `CatalogRow::validate` enforces
  schema, primary key, type checks. Mutation kinds
  (Insert/Upsert/Update/Delete) are typed.
* **Storage engines are production-ready** — SST (write-optimized),
  VIPER (columnar), NOVA (zone maps + pushdown), HELIX (PCA).
* **What's missing is the execution path that ties these together:**
  no algebra-node executor, no transaction write buffer, no
  predicate pushdown integration, no cost-based plan selection.
* **A backing-collection shim** masks the gap today — every
  `CREATE TABLE` auto-creates a dimension=1 vector collection, and
  relational data threads through the vector pipeline. This is a
  design smell and a correctness/performance dead-end.

This ADR refines the architecture so Phase 2 can be implemented as a
coherent layer instead of a patchwork of point fixes.

== Decision

Adopt a **five-layer relational query architecture** that cleanly
separates parsing from logical algebra from physical execution from
storage from durability. Each layer has one job; cross-layer leakage
is the bug class we are trying to eliminate.

[source]
----
+--------------------------------------------------+
| L1. SQL Frontend            (sqlparser-rs)       |
|       ↓ AST                                      |
| L2. Logical Algebra         (Scan / Filter /     |
|       ↓ logical plan          Project / Join /   |
|                                Aggregate / Sort/ |
|                                Limit / Distinct/ |
|                                Union / CTE /     |
|                                Subquery)         |
| L3. Physical Planner       (rule + cost rules,   |
|       ↓ physical plan        backend selection,  |
|                              join strategy,      |
|                              pushdown rewrites)  |
| L4. Executor                (volcano iterator    |
|       ↓ tuple stream         per physical node)  |
| L5. Storage Adapter         (engine-agnostic     |
|       ↕ row + column         iterator over PAX,  |
|                              with predicate +    |
|                              projection pushdown)|
|                                                  |
| TX. Transaction Layer       (per-session write   |
|     orthogonal cross-cut      buffer, snapshot,  |
|     consulted by L4 + L5      commit/rollback)   |
+--------------------------------------------------+
----

The transaction layer is orthogonal — every read at L4/L5 consults
it for the session's snapshot; every write goes through it for
buffering.

Drop the "relational backing collection shim". Relational tables
become a first-class engine path with no vector-side detour.

== L1. SQL Frontend (no change)

`src/query/sql_frontend/parser.rs` already wraps sqlparser-rs and
produces a complete AST. Phase 2 keeps this layer unchanged; future
DDL/DML additions go in here.

Open work (additive, not architectural):

* Wire INSERT/UPDATE/DELETE through the new planner instead of the
  current "error-routed to REST/gRPC API".
* Add `WITH` (CTE) lowering — already parsed, not yet flowing.

== L2. Logical Algebra

Introduce explicit logical-algebra node types in a new crate
`crates/query/proximadb-relational-algebra`. The crate ships:

[source,rust]
----
pub enum LogicalNode {
    /// Read all rows of a table; the optimizer may attach
    /// projection/predicate/index hints below.
    Scan {
        table: TableIdentifier,
        // Optional access-path hint set by the planner.
        access: ScanAccess,
    },
    /// Apply a row predicate. Multiple Filters MAY be fused by
    /// the optimizer; semantic equivalence preserved.
    Filter {
        input: Box<LogicalNode>,
        predicate: Expr,
    },
    /// Restrict columns. Pure rewrite — the optimizer pushes
    /// Project through Filter/Join when safe.
    Project {
        input: Box<LogicalNode>,
        outputs: Vec<NamedExpr>,
    },
    /// Inner / Left / Right / Full / Cross.
    Join {
        left: Box<LogicalNode>,
        right: Box<LogicalNode>,
        kind: JoinKind,
        on: Option<Expr>,
        // Set by the planner; not part of the logical contract.
        strategy: JoinStrategy,
    },
    Aggregate {
        input: Box<LogicalNode>,
        group_by: Vec<NamedExpr>,
        aggregates: Vec<AggregateExpr>,
        having: Option<Expr>,
    },
    Sort {
        input: Box<LogicalNode>,
        keys: Vec<SortKey>,
    },
    Limit {
        input: Box<LogicalNode>,
        limit: Option<u64>,
        offset: u64,
    },
    Distinct {
        input: Box<LogicalNode>,
    },
    Union {
        inputs: Vec<LogicalNode>,
        all: bool, // UNION ALL vs UNION
    },
    /// Materialized CTE binding. Optimizer may inline single-use
    /// CTEs or materialize otherwise.
    CteBind {
        name: String,
        body: Box<LogicalNode>,
        usages: Box<LogicalNode>,
    },
    /// Subquery as a relation (used in FROM/IN/EXISTS rewrites).
    SubqueryScalar(Box<LogicalNode>),
}

pub enum Expr {
    Column(ColumnRef),
    Literal(ScalarValue),
    BinOp { op: BinOp, left: Box<Expr>, right: Box<Expr> },
    UnaryOp { op: UnaryOp, expr: Box<Expr> },
    Call { name: String, args: Vec<Expr> },
    Case { conds: Vec<(Expr, Expr)>, otherwise: Option<Box<Expr>> },
    In { expr: Box<Expr>, list: Vec<Expr>, not: bool },
    Like { expr: Box<Expr>, pattern: Box<Expr>, not: bool, case_insensitive: bool },
    IsNull { expr: Box<Expr>, not: bool },
    Exists { sub: Box<LogicalNode>, not: bool },
    Between { expr: Box<Expr>, low: Box<Expr>, high: Box<Expr>, not: bool },
}
----

Lowering rules from sqlparser-rs `Statement::Query`:

* `SELECT cols FROM t WHERE p GROUP BY g HAVING h ORDER BY o LIMIT n` →
  `Limit(Sort(Project(Aggregate(Filter(Scan(t), p), g, h), cols), o), n)`
* `SELECT … FROM t1 JOIN t2 ON c` →
  `Join(Scan(t1), Scan(t2), Inner, Some(c), Auto)`
* Subqueries in WHERE → `Filter` with `Exists`/`In` expression
  carrying the inner `LogicalNode`.
* CTEs → `CteBind` (optimizer decides materialize vs inline).

Validation invariants encoded as constructors that take typed
inputs (`Box<LogicalNode>`, typed `Expr`). Schema resolution
(name → ColumnRef with type) happens during lowering.

== L3. Physical Planner

Two-pass planner:

**Pass A — Rule-based rewrites (cheap, always run):**

* Predicate pushdown: `Filter(Scan(t), p)` → `Scan(t, push_filter=p)`.
* Projection pushdown: `Project(Scan(t), cols)` → `Scan(t, project=cols)`.
* Filter merge: adjacent `Filter` nodes combine.
* Constant folding: `Literal+Literal` evaluated eagerly.
* Decorrelate scalar subqueries: `Scalar(subq)` → join when possible.
* CTE inline: single-use CTEs become inline; multi-use materialize.
* Pushdown through Project: filters reordered above projection when
  predicate columns survive.

**Pass B — Cost-aware choices (rule-only for MVP; CBO in Phase 3):**

* Join strategy selection:
  - `INNER JOIN ON a.x = b.x` with small `b` → HashJoin (b builds).
  - One side reaches statistics-bounded threshold → NestedLoopJoin.
  - Both sides large + on equality → SortMergeJoin.
* Aggregate strategy:
  - All-rows aggregate (no GROUP BY) → StreamingAggregate.
  - Small group cardinality → HashAggregate.
  - Pre-sorted input → SortedAggregate.
* Sort strategy:
  - In-memory if estimated bytes fit threshold; external otherwise.
* Backend selection (per `Scan`):
  - Catalog's `CatalogTableSchema::storage_layouts[0].authority` decides:
    - `InternalCanonical` / `ProximaAuthoritative` → ProximaDB engine
      (SST for primary-key access, VIPER/NOVA for analytic scan).
    - `ExternalAuthoritative` → external table reader.
    - `ProjectionPublication` / `RebuildableProjection` → projection
      reader.
  - `CatalogWorkloadProfile` (OLTP / OLAP / HTAP) influences engine
    pick.

Output: `PhysicalPlan` enum mirroring `LogicalNode` but with
strategy variants resolved and pushdown applied to leaf `Scan` nodes.

== L4. Executor

Volcano-style pull iterators. Each physical node implements:

[source,rust]
----
pub trait PhysicalNode: Send {
    /// Open the node's resources. Idempotent.
    fn open(&mut self, ctx: &ExecContext) -> Result<()>;
    /// Pull the next row, or None if exhausted.
    fn next(&mut self, ctx: &ExecContext) -> Result<Option<Row>>;
    /// Release resources. Called even on early break / error.
    fn close(&mut self, ctx: &ExecContext) -> Result<()>;
    /// Output schema (column names + types).
    fn schema(&self) -> &OutputSchema;
}
----

`ExecContext` carries the per-session transaction handle, the
catalog read-snapshot pinned at session BEGIN, and statement
timeout.

Node implementations (MVP set, Phase 2):

* `ScanNode` — wraps a storage adapter iterator. Pushed-down filter
  and projection are evaluated by the adapter, not in the executor.
* `FilterNode` — evaluates a remaining `Expr` per row.
* `ProjectNode` — re-emits a `Row` with the requested columns.
* `NestedLoopJoinNode` — naive but correct; works for all join kinds.
* `HashJoinNode` — builds hash table on the small side, probes from
  the large side. Inner + Left only at MVP.
* `HashAggregateNode` — accumulator per group key; emits at EOF.
* `StreamingAggregateNode` — when no GROUP BY (single accumulator).
* `SortNode` — k-way external sort with spilling above
  configurable memory threshold.
* `LimitNode` — pure decorator over input.
* `DistinctNode` — hash-based for MVP; sort-based optimization later.
* `UnionAllNode` — concatenates input streams.

Row representation: `Vec<ScalarValue>` for MVP. Column-batch
representation (`RecordBatch`-style) is a Phase 3 optimization;
the executor trait stays the same so it's a drop-in upgrade.

Memory budgeting: each operator declares a "memory hint" at plan
time (`SortNode` largest), and the executor's memory tracker can
ask any operator to spill. For MVP, spill = "fail with helpful
message"; real spill is Phase 3.

== L5. Storage Adapter

A new trait abstracts the engine-specific reader so the executor
doesn't know about SST vs VIPER vs NOVA:

[source,rust]
----
pub trait RelationalReader: Send {
    /// Pushed-down per-block filtering. The adapter SHOULD skip
    /// blocks whose ColumnMeta proves no row can match; if it
    /// can't, it returns all blocks.
    fn open(
        &mut self,
        projection: &[ColumnRef],
        predicate: Option<&Expr>,
        snapshot: ReadSnapshot,
    ) -> Result<()>;

    /// Pull the next row. None means EOF.
    fn next_row(&mut self) -> Result<Option<Row>>;

    /// Optional fast-path for point lookups via primary key.
    fn lookup_pk(&self, key: &[ScalarValue]) -> Result<Option<Row>>;

    /// What this reader can pushdown. Helps the planner choose.
    fn capabilities(&self) -> ReaderCapabilities;
}
----

`ReaderCapabilities` declares whether the reader supports:

* Column projection (PAX-backed engines: yes; row-only: no).
* Predicate pushdown (NOVA: yes; SST: partial; VIPER: partial).
* Bloom filter probes (PAX with bloom-loaded columns: yes).
* Zone-map skipping (PAX with min/max meta: yes).

The planner uses these capabilities to decide what stays in the
executor vs what pushes down.

**Critical refactor: drop the relational-backing-collection shim.**
Today every `CREATE TABLE` creates a dimension=1 vector collection.
This is replaced by a first-class **relational engine path** that
writes rows through:

1. WAL append (same WAL as today; the manifest tracks relational
   segments separately from vector segments).
2. PAX block buffer (in memory until flush threshold).
3. PAX block write to disk with proper `ColumnRole` (Identity for
   primary key, Props for non-vector columns, no Vector stripes).
4. Manifest update.

The PAX block format ALREADY supports this — `ColumnRole::Identity`
/ `Props` / `UserDefined` cover relational columns. The work is
wiring the engine-side write path, not changing the format.

== TX. Transaction Layer

Per-session transaction state machine + write buffer:

[source,rust]
----
pub enum SessionTxState {
    /// Autocommit — every statement is its own transaction.
    Idle,
    /// BEGIN observed. Reads see a snapshot pinned at BEGIN time;
    /// writes go to the per-session WriteBuffer.
    InTransaction(TransactionContext),
    /// A statement inside InTransaction errored. Subsequent
    /// statements (until ROLLBACK) get "current transaction is
    /// aborted, commands ignored until end of transaction block".
    Failed(TransactionContext),
}

pub struct TransactionContext {
    /// The snapshot reads see. Pinned at BEGIN.
    pub snapshot: ReadSnapshot,
    /// Per-table delta buffer. Writes accumulate here until COMMIT.
    pub writes: HashMap<TableIdentifier, WriteBuffer>,
    /// Tables touched (for conflict detection at COMMIT).
    pub touched: HashSet<TableIdentifier>,
    /// Started-at timestamp for statement_timeout enforcement.
    pub started_at_ns: i64,
}

pub struct WriteBuffer {
    /// New rows to be inserted. PK-indexed for read-after-write
    /// visibility within the transaction.
    pub inserts: BTreeMap<RowKey, Row>,
    /// Updates indexed by PK; the read path overlays the update
    /// on the snapshot row.
    pub updates: BTreeMap<RowKey, Row>,
    /// Deleted PKs. The read path filters these out of the snapshot.
    pub deletes: BTreeSet<RowKey>,
}
----

**Read path inside a transaction:**

For each `Scan`, the executor:
1. Starts the storage iterator using `ReadSnapshot` pinned at BEGIN.
2. For each row yielded, checks `writes.deletes` — skip if matched.
3. For each row, checks `writes.updates` — replace if matched.
4. After the scan, emits any rows from `writes.inserts` that match
   the predicate (these aren't in the snapshot).

This gives **read-after-write within the transaction** without
requiring storage-level MVCC.

**Write path inside a transaction:**

`INSERT/UPDATE/DELETE` go to `writes`, not directly to storage.
Subsequent reads in the same transaction see the buffered writes
(per the algorithm above).

**COMMIT:**

1. Acquire row locks on touched PKs.
2. Verify no concurrent writer changed them since the snapshot
   (optimistic concurrency control).
3. If verified, flush `writes` to storage via the normal write
   path (WAL → PAX).
4. Release locks.
5. Transition session to `Idle`.

If verification fails, return a serialization error and stay in
`Failed` — client must ROLLBACK.

**ROLLBACK:**

Discard `writes`, transition to `Idle`. No storage I/O.

**Isolation level:**

MVP ships `READ COMMITTED` semantics — snapshot pinned at BEGIN;
optimistic conflict check at COMMIT; statements within the same
transaction see the buffered writes. `REPEATABLE READ` and
`SERIALIZABLE` are Phase 3 (need real MVCC at the storage layer).

**Savepoints:**

Deferred to Phase 3. MVP returns `0A000`.

== Index Layer

MVP indexes for relational tables:

* **Primary-key index**: B-tree backed by the PAX `ColumnRole::Identity`
  columns. Lookups O(log n); the engine already builds this for every
  table.
* **Hash index** (optional, per column): for equality probes on
  high-cardinality non-PK columns. Stored as a sidecar to the PAX
  block group.

Phase 3 adds:

* B-tree on non-PK columns (for range queries).
* Bitmap index (for low-cardinality columns).
* Functional index (`CREATE INDEX … ON … (lower(col))`).

The existing ANN indices (HNSW, IVF, PQ) are untouched — they live in
the vector engine path and don't interact with the relational
algebra except through dedicated `<->`-operator scan modes.

== Refined Storage Format Notes

PAX is the right format. The survey confirmed: block header + row
directory + column stripes + column meta is exactly what columnar
relational analytics needs. The refinements are:

1. **Relational-specific `ColumnRole` recommendations:**
   - Primary-key column(s) → `Identity` (already supported).
   - Non-PK indexed columns → `Identity` with a sidecar B-tree.
   - All other relational columns → `Props` or `UserDefined`.
   - No `Vector` stripes for relational tables.

2. **Required column-meta fields for relational pushdown:**
   - `min_val` / `max_val` — already in `ColumnMeta`. Used for
     range-predicate skipping.
   - `null_count` — for `IS NULL` / `IS NOT NULL` predicate fast-
     paths.
   - `distinct_hint` — for join cardinality estimation.
   - `bloom_offset` — for equality predicate probes.

   All four exist today; the work is hooking them into the
   `RelationalReader::open` pushdown evaluation.

3. **MVCC row directory:**
   - `RowDirectory` carries 32B/row of MVCC metadata. For relational
     tables without real MVCC at MVP, this is mostly unused. The
     transaction layer's write buffer compensates by serving
     read-after-write at the executor level.
   - When Phase 3 lands real MVCC, the row directory's temporal
     bounds become live (visible-from-ts, deleted-at-ts).

4. **No format change required for Phase 2.** The PAX format is
   already designed for relational + columnar + zone-mapped
   analytics. The work is consuming what's there.

**Cumulative Phase 2 effort: ~85–115 engineer-days (~4–6 weeks
calendar with 2 engineers parallelizing).**

Sequencing rules:

* S1 + S2 must ship before S3 (executor needs the algebra + plan).
* S4 can be partial — start with SST adapter; VIPER / NOVA in
  parallel with later slices.
* S5 (drop the shim) is independent and high-leverage; can start
  as soon as S4-SST is in place.
* S6 (transactions) needs S3 + S5 (executor + storage path) before
  COMMIT can flush.
* S7 (extended protocol) is independent — can run in parallel.
* S8 is mostly schema-translation; independent.

== Why this shape

* **Five layers, one job each.** Each layer is independently
  testable. AST changes don't ripple to the executor; storage
  refactors don't ripple to the planner.
* **Volcano executor** is simple, well-understood, fits 80% of
  SQL workloads. Vectorized batch execution (Phase 3) is a
  drop-in optimization that keeps the same `PhysicalNode` shape.
* **Predicate + projection pushdown via the adapter capabilities
  trait** lets each engine declare what it can do, and the
  planner chooses. No per-engine special-casing in the executor.
* **Transaction layer as a per-session write buffer + snapshot**
  gives real BEGIN/COMMIT/ROLLBACK semantics WITHOUT needing
  storage-level MVCC at MVP. Storage MVCC is Phase 3; the
  executor signature doesn't change.
* **PAX as-is** is the right relational columnar format —
  zone-map metadata + bloom filters + column roles are exactly
  what relational pushdown needs. No format change.
* **Dropping the dim=1 vector shim** removes the worst design
  smell: relational data threading through the vector pipeline.
  Relational tables get a clean engine path.

== Consequences

* **Phase 2 implementation has a clear architecture to plug into.**
  Each slice (S1–S12) has well-defined inputs and outputs.
* **Operator metadata-in-OLTP story is unblocked** at the end of
  S5 (drop the shim) + S6 (real transactions). Until then,
  metadata writes go through Phase 1's autocommit pgwire — safe
  but unsuitable for multi-statement workflows.
* **PAX format gets fully exercised**, justifying the existing
  design (zone maps, bloom filters, column roles). Engine team
  is vindicated; storage team gains no new work.
* **ORM compatibility** arrives at the end of S7 + S8 (extended
  protocol + catalog introspection expansion). SQLx/Diesel can
  connect, run migrations, do basic CRUD.
* **Full Postgres-parity (ADR-018 Phase 3)** then needs MVCC, full
  pg_catalog, savepoints, advanced SQL (CTEs / window / FK
  referential actions / UUID / arrays / triggers / COPY FROM
  STDIN), and SCRAM auth. The architecture in this ADR
  accommodates all of those as natural extensions.

== Decision Index — Key choices and why

[cols="1,3,3"]
|===
| ID | Decision | Why

| D1
| Volcano iterator over batch-vectorized for MVP.
| Simplicity + correctness first; batch is a drop-in upgrade.

| D2
| Per-session write buffer for transactions instead of storage
MVCC.
| MVCC is a storage-layer refactor (months). Write buffer gives
correct ACI in `READ COMMITTED` today.

| D3
| Drop the relational-backing-collection (dim=1 vector) shim.
| Threading relational rows through the vector pipeline is a
performance dead-end and a correctness footgun. PAX already
supports relational-only stripes.

| D4
| Five layers (Frontend / Algebra / Planner / Executor / Storage)
plus orthogonal Transaction.
| Each layer testable in isolation. AST changes don't ripple to
execution; engine refactors don't ripple to planning.

| D5
| `RelationalReader::capabilities` declares pushdown support per
engine.
| Planner picks the right engine without hardcoding. New engines
plug in by implementing the trait + declaring capabilities.

| D6
| Rule-based planner for MVP; CBO in Phase 3.
| 80% of workloads benefit from pushdown + projection without a
cost model. CBO needs statistics infra that's a multi-week build.

| D7
| Hash join + nested-loop join only at MVP; sort-merge in Phase 3.
| Covers `INNER JOIN ON pk = fk` (the 90% case) and `CROSS JOIN`
trivially. Sort-merge is the optimization for "both sides large".

| D8
| `READ COMMITTED` isolation only at MVP.
| Matches PostgreSQL's default. `REPEATABLE READ` /
`SERIALIZABLE` need storage MVCC.
|===

== Test gates

Each slice ships with:

* Unit tests for algebra types, planner rules, individual
  executor nodes.
* Integration tests in `tests/pgwire_phase2_*.rs` running real
  pgwire SQL against the live server.
* A live psql probe script (`scripts/pgwire_phase2_probe.sh`)
  for post-deploy validation.

S12 ships the ORM compatibility gate: Diesel + SQLx integration
tests pass against a live ProximaDB server. That is the Phase 2
exit gate.
