== Context

ProximaDB's vector storage assumes a single physical paradigm — LSM-structured, clustered PAX
segments reorganised at compaction — and applies it to every collection. A measured design review
(2026-07-14: a SIFT1M centroid-prune nprobe sweep at N=100000, plus a source review of the
PAX/SST, Vector Object Economy directory, and ORION graph paths) showed this fits one shape and
mis-fits another:

* **Append-heavy / bulk** (support case notes, bulk vector load): append-mostly, WORM-ish,
  moderate churn. LSM is the right tool; the lever that matters is read-side prune quality, which
  is a function of **clustering geometry**.
* **Agent-driven, update-heavy, graph-coupled code-RAG** (symbols whose embeddings are constantly
  re-embedded as an agent refactors; retrieval is match-then-graph-traverse): update-heavy point
  mutation on a **bounded, hot, freshness-critical** working set. LSM here pays tombstone / write /
  space amplification concentrated on exactly the hot keys, and its data-≫-RAM tiering is machinery
  without a purpose.

Two grounded findings frame the decision:

1. **The prune weakness is clustering geometry, and clustering runs at compaction — which is
   currently dark.** The sweep measured pruned recall@10 falling 0.9891 → 0.8087 as blocks are
   pruned; finer granularity (N=20000 vs N=100000) barely moved it, so the cause is *weak clusters*
   (sort-by-sign-bit MVP), not nprobe granularity. Clustering is (re)applied at compaction — the
   compactor already re-runs `write_pax_segment_full` (`src/storage/engines/sst/compaction.rs`) —
   but compaction is **global and default-OFF** (`PROXIMADB_L0_COMPACTION_ENABLED`,
   `src/storage/engines/sst/flush/mod.rs`). So the append path needs compaction armed per-collection
   and its clustering upgraded (fp32-PCA / IVF, not sign bits).

2. **ORION is a Beta in-memory CSR *projection*, not an authority.** Canonical `ProximaRecord` +
   WAL is the durable authority for graph and vector data; ORION's adjacency and the vector indexes
   are rebuildable, mutable, epoch-fresh projections over it. So the code-RAG answer is **not** "make
   ORION the graph-primary authority" nor "add a new engine" — it is to keep records as authority and
   change only the *read-acceleration projection*.

The durable-authority contract is already correct for both shapes and must not change. What is
missing is a way for a collection to declare *which projection strategy* serves it.

== Decision

Introduce **`StorageProfile`** as a first-class per-collection attribute selecting the
read-acceleration projection strategy. It is deliberately **distinct** from the existing
`CatalogWorkloadProfile` (Oltp/Olap/Vector/Graph…, which routes *query shape → engine* in
`ComputeScheduler`): `StorageProfile` selects a *storage projection*, not a query route.

[cols="1,2,1,2", options="header"]
|===
| Profile | Read-acceleration projection | Freshness | Clustering
| `AppendBulk` (`append` / `bulk`) | Durable coalesced PAX Regions A/B + self-describing footer (ADR-062/065) | flush + delta-merge | SQ8-Morton bootstrap at coalesced flush; fp32-PCA IVF/Hilbert **at compaction**
| `Churn` (code-RAG) | Bounded (~2 MB) memtable delta + Strong brute-force merge (TD-WLP-5) footnote:[Amended 2026-07-15 — see D4. The original "in-memory mutable ANN index + `oid` fusion" mechanism is retired as unnecessary: the unflushed delta is already backpressure-bounded to ~2 MB, so a Strong brute-force merge is sub-ms and already correct. ORION `oid` match-then-traverse fusion is already shipped (TD-045 `/rag`; graph node id == `oid`, no index needed — TD-ORION-1).] | immediate (pre-flush, Strong-merged) | none — small memory-resident delta; no compaction-cluster staleness
|===

=== D1 — `StorageProfile` is a per-collection attribute via the existing tag cascade

A `workload_profile:append|bulk|churn` tag on `CollectionConfig.tags`, resolved by a new
`resolve_storage_profile()` that mirrors `resolve_pax_vector_quant`
(`src/storage/engines/sst/flush/mod.rs`): **tag > env `PROXIMADB_STORAGE_PROFILE` > default
`append`**. No proto/DDL surface change and no new create-time storage engine. `append` and `bulk`
resolve to the same `AppendBulk` durable strategy (they differ only in flush-sizing defaults);
`churn` selects the Strong-merge-over-bounded-delta read strategy (D4, amended).

=== D2 — Authority is invariant across profiles (the load-bearing safety decision)

Canonical `ProximaRecord` + WAL remain the **sole durable authority** for both profiles. The vector
index and ORION CSR are rebuildable projections, never authority. Node vectors stay separate
`ProximaRecord` embedding cells (not graph-node properties); there is no default atomic
node+vector+edge transaction — `CrossModelTransactionCoordinator` (TD-133) stays opt-in. **Profiles
differ only in the read-acceleration projection; never in the durability or recovery contract.**
This is what keeps the change safe: a profile can never lose data, only change how reads are served.

=== D3 — SUPERSEDED serving mechanism; current `AppendBulk` contract is ADR-062/065

The 2026-07-14 decision proposed a Hilbert-on-raw L0 bootstrap and VOE directory/radius-prune
payoff. That serving mechanism is **retired; do not implement it from this ADR**. The measured VOE
route was GET-capped near `0.87` recall, and the sidecar is not the canonical metadata authority.

Current behavior separates lifetime and precision deliberately:

* coalesced L0 flush uses cheap deterministic `cluster_order_sq8_morton`, aligned with Region B and
  requiring no trained model;
* compaction uses canonical-f32 PCA+IVF/Hilbert because its learned cell plan is amortized, improves
  locality, and can become TD-RDSTRAT-8's query-visible Region A0; and
* quantized Regions A/B remain rebuildable search projections, never canonical reconstruction data.

ADR-062/065 own the physical read contract. TD-RDSTRAT-8 owns persisted compaction-model fields;
reviving VOE `pca_model_ref` is not an alternative implementation of that work.

=== D4 — `Churn`: bounded-memtable delta + Strong brute-force merge (no dedicated mutable ANN index)

`Churn` collections serve freshness-critical reads by **Strong-merging the unflushed WAL/memtable
delta** on every read (`forces_strong_reads()`, TD-WLP-5): a re-embedded symbol is immediately
visible **pre-flush**. Durability is WAL (D2); the memtable is a rebuildable projection. Compaction-
clustering is pinned OFF for `Churn` (churn invalidates a model faster than it pays off).

[NOTE]
.Amended 2026-07-15 — the original "dedicated in-memory mutable ANN index + `oid` fusion + memory
guard" mechanism is *retired* (superseded before implementation).
====
The original D4 called for a purpose-built mutable ANN index over unflushed inserts. Reading the
code showed that infrastructure is **unnecessary for the stated premise**: the write path already
**hard-bounds each collection's unflushed delta** to `MemtableConfig::flush_threshold_bytes`
(default **~2 MB**, `src/storage/memtable/core/mod.rs`) via per-collection backpressure
(`wal_behavior.rs`, `current_usage >= threshold`). A Strong brute-force merge over a ≤2 MB delta is
sub-millisecond (≈ a few thousand vectors) and is already **correct** (TD-WLP-5, shipped). A
dedicated mutable index would optimize a *large* unflushed set — a condition the "bounded hot
working set" premise says does not exist — while adding incremental-insert / eviction-on-flush /
double-serving coherence cost. **Measure-don't-assert:** we do not build it speculatively. The
Churn read design is therefore: **WAL authority (D2) + ~2 MB backpressure-bounded memtable delta +
Strong brute-force merge (TD-WLP-5) + observability (`proximadb_churn_collection_working_set_bytes`
gauge + `PROXIMADB_CHURN_WORKING_SET_MB` soft-ceiling warn, TD-WLP-8a, shipped)**.

Two pieces of the original D4 are **deferred, not adopted**:

* **A `Churn`-specific *tighter* flush threshold** (flush sooner than the shared ~2 MB bound so the
  delta is even smaller) is **evidence-gated**: the live flush trigger is spread across three
  write-path serialization strategies and is not profile-parameterized, so a per-`Churn` override is
  real hot-path plumbing for a sub-2 MB gain. Revisit only if a measured `Churn` trace shows the
  bounded delta hurts read latency/freshness. Tracked in link:../../10-quality/td/TD-WLP-10-churn-evidence-gated-flush-threshold.adoc[TD-WLP-10].
* **ORION `oid` match-then-traverse fusion is already shipped** (correction 2026-07-15): the SDK uses
  ONE id — `record_symbol_id()` (ADR-044) — for both the vector record id and the graph node id
  (`code_knowledge.py:527`/`:561`), so the graph `NodeId` *is* the `oid` and ORION's `node_to_index`
  already resolves it — **no `oid`→node index was needed**. The fusion itself is TD-045 "Modular Graph
  RAG" (`src/graph/rag/`: `VectorNodeRetriever` → `KHopSubgraphBuilder` → `RagPipeline`), exposed at
  `POST /graphs/{id}/rag` (`network/rest/canonical/graph.rs:852`). The only residual is a relevance
  **eval** (mandate #13) — tracked in
  link:../../10-quality/td/TD-ORION-1-oid-node-index-and-vector-graph-fusion.adoc[TD-ORION-1].

A dedicated mutable ANN index remains a *future evidence-gated option* (revisit if update-heavy
`Churn` LSM tombstone/version churn — GC'd by compaction, D5 — is measured to be a real cost), not a
planned slice.
====

=== D5 — Implemented actuation seam; fixed threshold superseded as final policy

The shipped cascade is current mechanism: explicitly falsy global env is the hard kill-switch;
`compaction:on|off` is the per-collection override; otherwise `AppendBulk` (including untagged) is
armed and `Churn` is off. `l0_threshold:N` supplies the fixed segment-count trigger, and #1012
wires it to synchronous compaction execution.

What is superseded is treating that constant as the durable query-cost policy. It cannot know
whether a rewrite repays GET/byte savings, whether Region-A entries fit cache admission, or whether
write churn invalidates the work. TD-RDSTRAT-9 layers an observe-first collection read-cost envelope
over this existing gate and preserves its hard-disable, opt-out, and atomic publication seam.

=== D6 — Profile selects a read-path projection, not a query route

`StorageProfile` influences which projection the storage read path consults; it does **not** add a
`ComputeScheduler` engine branch (routing stays on `engages_relational` / `parquet_backed`). Keeping
the two orthogonal — and the names distinct — prevents accidental changes to OLAP/OLTP routing.

=== D7 — SUPERSEDED: radius lower-bound prune is not the canonical accelerator

The implementation remains available as a default-neutral historical mechanism, but its promotion
decision is closed: the SIFT evaluation found block-centroid pruning structurally GET-capped near
`0.87` recall and `radius_k` moved recall by at most ~0.02. ADR-062's Region-A rank → adaptive-M →
Region-B rerank path supersedes it for the object-store read spine.

This tombstone is metric-significant. The old PCA/radius lower bound was L2-specific and must not
be generalized into a cosine/dot correctness gate. TD-RDSTRAT-8 uses metric/dimension/distribution
recall profiles until a score-space-consistent bound is separately proven.

=== D8 — Default-off optimization ratchets gate activation, not unrelated releases

A recall ratchet that deliberately forces an experimental, default-off read optimization ON is
the activation gate for that optimization. It does not by itself prove a regression in the shipped
default path. A release may waive such a ratchet for one named promotion only when all of the
following are recorded and true:

* the optimization and every prerequisite that changes read selection remain default-OFF;
* the same-run unoptimized/default baseline clears its recall floor;
* the failed optimized result, risk, mitigation, owner, and review date are recorded in the
  governing TD;
* every other required promotion check is green; and
* the merge explicitly identifies the single waived check. No blanket red-check bypass is allowed.

A failure in a shipped default path is not eligible for this exception. The exception does not
authorize enabling the optimization: its default may flip only after the original recall ratchet
passes without a waiver.

== First principles / rationale

* **Co-design against the trace, not the component.** For a serverless-on-object-store DB the
  dominant cost is I/O round-trips + transferred bytes, not a codec or distance kernel in
  isolation. AppendBulk uses coalesced regions, cache, selective probing, and collection file
  geometry; Churn optimizes freshness on a bounded delta. TD-RDSTRAT-9 charges compaction CPU and
  write amplification against observed read savings.
* **Vertical inside, standard outside.** WORM immutability is forced by object storage; we are at
  liberty to re-cluster/re-tier *inside* the segment at compaction. That licence is exactly what D3
  spends. But leveled-LSM compaction is workload-specific machinery, not universal — D4 declines it
  where the working set fits memory and mutation dominates.
* **Spend precision where its lifetime repays it.** SQ8-Morton is a model-free L0 locality
  bootstrap. Compaction uses canonical-f32 PCA/IVF because learned cells live longer, tighten
  Region-B runs, and can become TD-RDSTRAT-8's probe directory. Neither projection becomes durable
  value authority.

== Consequences

*Positive.*

* Each workload shape gets the right projection without forking the durability contract or the
  create-time engine.
* The former dark compaction path now has a tested per-collection arm and hard kill-switch; the
  future cost controller reuses it rather than adding another scheduler.
* Untagged collections resolve to `AppendBulk`, cluster at write, and compact at the fixed threshold
  today. TD-RDSTRAT-9 adaptive actuation remains independently default-OFF until evidenced.

*Negative / cost.*

* Two read-path projection strategies to maintain; the bounded Churn delta still needs observable
  backpressure and Strong-merge latency, but no dedicated mutable-index OOM surface was added.
* `AppendBulk` model staleness between compactions (mitigated: SQ8-Morton keeps L0 usable without a
  trained model).
* A latent footgun: conflating `StorageProfile` with `CatalogWorkloadProfile` (mitigated by D6 +
  distinct naming).

== Alternatives considered

* **A1 — a new storage engine per profile at create-time.** Rejected: heavyweight, breaks the
  migration surface, duplicates the LSM, and couples the decision to create-time when the projection
  is a read-path concern.
* **A2 — make ORION the graph-primary authority for `Churn`.** Rejected: violates D2; ORION is Beta
  and explicitly a rebuildable projection with no default atomic node+vector+edge transaction.
* **A3 — use quantized-code order as learned compaction geometry.** Rejected: sign-bit ordering did
  not produce the required locality/recall tradeoff. Narrow shipped exception: SQ8-Morton is the
  cheap L0 bootstrap; it does not replace fp32/PCA compaction or become canonical authority.
* **A4 — auto-infer the profile from the query/write mix in v1.** Deferred, not built:
  `infer_workload_profile` (`ddl/mod.rs`) can layer on later. v1 uses an explicit, predictable tag,
  matching the existing cascade convention.

== Verification / ratchets

Each TD-WLP slice ships its TDD gate:

* Profile resolution — unit test of the tag>env>default cascade (TD-WLP-1).
* Compaction arming — integration test that an `AppendBulk` collection arms compaction while the
  global gate is OFF (TD-WLP-2).
* Radius prune — retained as historical negative evidence; ADR-062's recall/GET/byte ratchets own
  the canonical path (TD-RDSTRAT-6/7).
* Compaction clustering — integration tests prove PCA+IVF locality and `Churn` exclusion; Region-A0
  persistence/read compatibility belongs to TD-RDSTRAT-8, not VOE `pca_model_ref`.
* Churn freshness — integration test: a re-embedded symbol is immediately visible pre-flush, and WAL
  replay reconstructs identical state; an `AppendBulk` collection in the same process is unaffected
  (TD-WLP-5).

The global recall ratchet (`tests/sift_pax_recall_ratchet_test.rs`) must not regress on the default
(untagged) path at any slice.
