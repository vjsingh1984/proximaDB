== Context

ProximaDB's branchable state feature (inspired by Neon copy-on-write branching, see
`DATA_AI_PLATFORM_ARCHITECTURE_ANCHOR_2026_05_12.adoc`) allows creating data branches for
development environments, agent state isolation, and agentic workflow replay. Relational rows
and document records have straightforward merge semantics via MVCC: last-writer-wins on
primary key, or explicit conflict resolution.

Graph topology presents a harder problem. When two branches independently mutate graph
structure — adding edges, removing nodes, changing edge weights — merging them requires
semantic decisions that cannot be resolved by timestamp ordering alone:

* Branch A deletes edge (u, v, "follows"). Branch B adds edge (u, v, "follows") with a new
  weight. Merge: which interpretation wins?
* Branch A adds node X with embedding E1. Branch B adds node X with embedding E2. Merge:
  which embedding is canonical?
* Both branches add edges (A, B, "related") and (B, A, "related") independently. Merge:
  keep both, keep one, keep neither?

Without a defined merge policy, graph branches cannot be merged deterministically.

Literature basis:

* Version Control System for Data with MatrixOne (arXiv:2604.03927). Demonstrates
  practical data version control at DB level including snapshot branches for tables.
  Does not address graph merge semantics directly; treats tables as independent objects.
* Multi-modal Verification of Replicated Data Types (arXiv:2603.27202). Formalizes
  verification of CRDTs across modalities.
* A framework to reason about consistency and atomicity guarantees in a distributed system
  (arXiv:2603.03899). Establishes the CRDT contract for convergent merge.
* SQL/PGQ data model (cited in RELATIONAL_DOCUMENT_GRAPH_CONVERGENCE): property graphs
  have tabular representation; graph operations can be modeled as relational operations.
* Higher-Order Graph Databases (arXiv:2506.19661). Formalizes graph mutation semantics
  including edge and node identity across versions.

== Decision

Graph branch merge semantics are defined per mutation type using a CRDT-inspired model.
The `__proxima_branch_id` field (ADR-009) plus the canonical WAL (Layer 0) provide the
causal ordering needed for deterministic merge.

=== Merge Conflict Classes

[cols="1,2,3,2"]
|===
| Mutation type | Conflict condition | Default resolution | Override via

| Node upsert
| Same node OID mutated in both branches
| Last-writer-wins on `updated_at_ns`
| `branch_merge_node_policy` catalog property

| Node deletion
| Node deleted in branch A; mutated in branch B
| Delete wins (2P-Set semantics)
| `branch_merge_delete_wins: false` to prefer mutation-wins

| Edge add
| Same (src, label, dst) edge added in both branches with different weights
| Last-writer-wins on `updated_at_ns`
| `branch_merge_edge_policy`

| Edge deletion
| Edge deleted in A; weight-updated in B
| Delete wins
| `branch_merge_delete_wins: false`

| Embedding update
| Same node embedding updated in both branches
| Last-writer-wins on `updated_at_ns`
| Explicit conflict resolver function

| Label set mutation
| Labels added/removed in both branches for same node/edge
| Union of surviving labels (Add-Wins Set for additions; 2P-Set for removals)
| `branch_merge_label_policy: "intersect"` for intersection

| Graph topology rebuild
| Both branches trigger a CSR/HNSW projection rebuild
| Merge canonical records first; rebuild projections from merged L1 state
| N/A — projection rebuild is always post-merge
|===

=== Node and Edge Identity

A graph node is canonically identified by its `ProximaRecord.oid`. An edge is canonically
identified by `(edge_source_id, edge_type, edge_target_id)` triple, NOT by a surrogate key.
This is the standard property-graph identity model per SQL/PGQ (ISO 39075).

When an edge OID is reused across branches with different source/target/type, it is treated
as two independent edge mutations and both are preserved in the merged graph (duplicate edge
OIDs produce a conflict error at commit time and must be resolved by the branch author).

=== Branch Merge Protocol

[source,text]
----
1. Identify the merge base: the WAL position / snapshot at which the two branches diverged.

2. For each ProximaRecord mutated after the merge base in either branch:
   a. Classify as: node, edge, label mutation, embedding update, or deletion.
   b. Look up the merge base version of the same OID.
   c. Apply the per-class resolution rule from the table above.
   d. Emit a merged ProximaRecord version with:
      - origin = "branch_merge:<branch_a_id>:<branch_b_id>"
      - actor = the principal triggering the merge
      - valid_from_ns = merge commit timestamp
      - branch_id = target branch / HEAD

3. Write merged records through the canonical WAL path (CanonicalOperation::RecordUpsert).
   Merge is not a separate operation type.

4. After L1 merge is committed, trigger L2 projection rebuild for:
   - CSR/COO graph topology projections (mark RebuildRequired, use RTO from CatalogProjection)
   - HNSW vector projections for any merged embedding updates (incremental update path)

5. Return a MergeResult with:
   - records_merged: u64
   - conflicts_auto_resolved: u64
   - conflicts_requiring_user_action: Vec<MergeConflict>
   - estimated_projection_rebuild_seconds: f64  (from RebuildRtoSpec)
----

=== Merge Conflict Struct

[source,rust]
----
pub struct MergeConflict {
    /// OID of the conflicting ProximaRecord.
    pub record_oid: String,
    /// Mutation class that produced the conflict.
    pub conflict_class: GraphMergeConflictClass,
    /// The version from branch A.
    pub branch_a_version: Option<ProximaRecord>,
    /// The version from branch B.
    pub branch_b_version: Option<ProximaRecord>,
    /// Suggested resolution if auto-resolution was blocked by policy.
    pub suggested_resolution: GraphMergeResolution,
}

pub enum GraphMergeConflictClass {
    NodeDeleteVsMutate,
    EdgeDeleteVsMutate,
    EmbeddingConflict,
    DuplicateEdgeOid,
    PolicyViolation,
}

pub enum GraphMergeResolution {
    KeepBranchA,
    KeepBranchB,
    KeepBoth,
    Delete,
    RequiresUserAction,
}
----

=== HNSW Branch Behavior

When a branch is created for a collection with a `VectorAnn` projection:

* The HNSW index is NOT copied. The branch shares the base snapshot's HNSW index.
* New vector writes in the branch are tracked in the branch WAL only.
* Vector searches on the branch must union: base HNSW results + branch-WAL records
  (freshness cost is acceptable for development/agentic branches).
* On merge, new embeddings from the branch are fed into the HNSW incremental update path
  (using the in-place HNSW update algorithm, arXiv:2502.13826).

This avoids copying gigabytes of HNSW data per branch while maintaining correctness.

=== Schema-Only and Masked Branches

Schema-only branches contain no record data. Graph merge for schema-only branches is
equivalent to schema evolution (ADR-009 `FLEXIBLE_SCHEMA_ON_WRITE` rules apply).

Masked branches use anonymized/synthetic embeddings and property values. Merging a masked
branch into a production branch is explicitly blocked by the catalog policy boundary
(`policy_boundary: "masked-data-boundary"`) and requires explicit operator approval.

== Consequences

=== Positive

* Graph branch merge is deterministic: given the same inputs and policies, merge always
  produces the same output.
* CRDT-inspired conflict classes are proven convergent for the mutation types covered.
* Agentic workflows (create branch → agent mutates graph state → merge to HEAD) are
  first-class supported without separate conflict-resolution code per agent.
* HNSW sharing avoids storage amplification from branch creation.

=== Constraints / Risks

* "Delete wins" default means resurrecting a deleted node requires an explicit re-add after
  merge, not a branch rollback. This matches 2P-Set semantics and prevents zombie nodes.
* Embedding conflicts (two embeddings for the same node from different models or different
  runs) are resolved by LWW, which may not be semantically correct if embeddings carry
  different information. Future work: multi-embedding node record supporting both versions.
* CSR projection rebuild is required after any merge that adds or removes edges. See
  `RebuildRtoSpec::csr_estimated()` for expected rebuild times. Applications should not
  expect immediate CSR freshness after a large graph merge.
