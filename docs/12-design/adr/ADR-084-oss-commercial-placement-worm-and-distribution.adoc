= ADR-084: OSS↔commercial placement — WORM/compliance (TD-GST-2) and multi-node distribution

:status: Proposed
:date: 2026-07-30
:deciders: owner + architecture
:relates-to: OSS_ENTERPRISE_BOUNDARY_2026_06_17.adoc, ADR-060 (commercial Rust crate seam), OPEN_CORE.md, TD-GST-2, ADR-017 (DR engine surface), ADR-063/ADR-069 (single-node durability)

== Status

**Proposed** (2026-07-30). Records the placement decisions for the two upcoming
capabilities that sit closest to the OSS↔commercial seam — **before** either has
code on `develop`, while the choice is still free. Once a capability ships in an
Apache-2.0 release its openness is irrevocable; placement must therefore be
decided at spec time, not implementation time.

== Context

A full boundary review (2026-07-30, both repos at `develop` HEAD) confirmed the
governing model holds: the OSS engine ships **capability + mechanism** (engines,
formats, quantization, routing, tenant isolation, neutral meters), the commercial
layer holds **policy, operations, and go-to-market** (pricing/tier values,
provisioning, console, connectors), consuming the engine as a digest-pinned image
overlay with **no fork and no engine IP** on the commercial side. The
`check_oss_boundary.py` CI guard enforces the seam durably.

Two capabilities are approaching that seam and are classic *paid* gates elsewhere
in the database market:

1. **WORM / retention-lock / tamper-evident hash-chain** — specified in TD-GST-2,
   not yet implemented. Compliance retention is an enterprise-priced feature at
   most vendors.
2. **Multi-node distribution** — the `cluster` feature flag (Raft consensus,
   default-OFF) exists as a framework; operational hardening has not been done.
   HA/replication is the single most common commercial line in the DB market.

Three constraints govern the choice:

* **The open-core covenant** (`OPEN_CORE.md`): the **full single-node engine** is
  free forever, with no enterprise-only flags — "we gate operations, never
  features"; a change that makes an engine capability conditional on a commercial
  entitlement is *on the wrong side of the seam*. Note the covenant's scope is
  deliberate: it promises the **single-node** engine.
* **TD-GST-2's own rationale**: app-layer immutability is defeatable; the
  integrity root must live **in the system of record** (the engine), and AnvaiOps
  should retire its hand-rolled content-hash convention in favor of an engine
  guarantee.
* **ADR-060 (commercial Rust crate seam, Option A)**: commercial Rust crates
  depend on OSS crates from a separate workspace and are **never linked into the
  OSS engine at runtime** — so any enforcement that must run on the engine's
  write path *cannot* be commercial-only code.

*License posture (context, not a decision here):* the engine remains Apache-2.0 +
trademark policy. This accepts managed-service free-riding as a deliberate
pre-traction trade (adoption is the scarce resource); revisiting the license for
*new* code is a separate decision with a traction trigger, filed if and when that
trigger nears.

== Decision 1 — WORM/retention/hash-chain: **the engine proves; the commercial layer attests**

The TD-GST-2 *mechanism* lands in the OSS engine; the compliance *product* around
it is commercial.

[cols="1,3",options="header"]
|===
| Layer | Contents
| **OSS engine (mechanism)**
| Everything in TD-GST-2's acceptance: WORM collection mode selected at
create-time, per-record retention-lock enforced on the record write path (typed
policy error on pre-expiry overwrite/delete), optional hash-chain in LSN order,
chain metadata on reads, and the **chain-verify** operation. Ships default-OFF
per the storage-format mandate (mixed-read-safe, opt-in until baked) — a
**maturity** gate, never a license gate; it goes GA free.
| **Port (values via config/claims)**
| Retention *authority* — which tenant/collection gets which `retention_years`
/ legal-hold state — flows through the existing operator-config + request-claim
seams (same shape as `TierPolicy`/`LimitsResolver`). OSS standalone honors
whatever the collection creator specifies; the control plane supplies
fleet-level policy.
| **Commercial (attestation + operations)**
| Scheduled chain verification and evidence retention; auditor-facing
attestation reports; **external anchoring** of chain heads (publishing to an
outside root so tampering with the whole store is detectable); legal-hold
workflow and console; compliance packaging (GST-ASP filing vertical, SOC2/HIPAA
narratives); entitlement of the *managed* compliance capability in the SaaS
tiers.
|===

**Rejected:**

* *Fully-commercial WORM* — violates the covenant (an engine capability gated on
  payment) and is technically unworkable: ADR-060 commercial crates are not
  linked into the engine, and retention enforcement must run on the write path.
* *App-layer chain in AnvaiOps* — the defeatable status quo TD-GST-2 exists to
  kill; puts the integrity root outside the system of record.

== Decision 2 — multi-node distribution: **single-node OSS excellence; distribution is a commercial/ops capability**

The covenant's "full **single-node** engine" scoping is hereby recorded as
**intentional**, not accidental. Concretely:

* **Single-node includes all durability.** WAL, object-store restartability
  (ADR-063), tiered flush (ADR-069), DR/CRR *mechanism*, and object-store
  scale-out of data remain fully OSS. The line is **coordination across nodes**
  — consensus, membership, replication, failover orchestration — not durability
  or capacity.
* **The OSS `cluster` feature (Raft) is frozen at Experimental.** It keeps
  compiling (no user breakage, flag stays default-OFF), but receives **no
  further OSS hardening or promotion investment**; it is not on the path to GA
  in this repository.
* **Multi-node HA/DR is sold as operations.** Today that is the AnvaiOps managed
  topology (multi-AZ profiles, DR runbooks, spot-reap drills). If and when
  engine-side distribution code is needed (replica placement, log shipping,
  coordinated failover), it lands in the **commercial Rust workspace per
  ADR-060 Option A** — depending on OSS crates from outside, never in the OSS
  tree.

**Why:** distribution is where operational value (and the market's willingness
to pay) concentrates, it is the hardest subsystem to harden, and open-sourcing a
hardened cluster would hand the top managed-service differentiator to any
re-hoster while consuming the most engineering. Single-node excellence is the
adoption funnel; the covenant already draws this line — this ADR commits to it.

**Rejected:**

* *Harden Raft clustering in OSS* — burns the most engineering to give away the
  strongest commercial differentiator; against the covenant's deliberate scope.
* *Delete the `cluster` flag now* — needless churn for existing experimenters;
  freezing is sufficient. Revisit removal at GA if it is still inert.

== Consequences

* TD-GST-2 proceeds **engine-side** as specified, carrying the Decision-1 split;
  its `Relates to` row now references this ADR (same PR).
* `docs/SUPPORTED_SURFACE.adoc` should note `cluster` as *Experimental — frozen;
  multi-node distribution is a commercial/operations capability* the next time
  that file is touched (status-as-of guard applies).
* `check_oss_boundary.py` needs no change — neither decision introduces
  commercial terms, entitlements, or dependency edges into OSS code.
* `OPEN_CORE.md` needs no change — both decisions are consistent with it by
  construction; Decision 2 makes its single-node scoping explicit.
* Everything already shipped under Apache-2.0 stays open (irrevocable); this ADR
  governs **future** placement only.
