= ADR-008: OLTP Catalog Backends in xCatalog
:status: Accepted
:date: 2026-05-17
:deciders: ProximaDB Architecture
:supersedes: none

== Status

Accepted

== Context

ProximaDB's existing xCatalog implementations (Iceberg client, Delta, Unity, Polaris) target large-scale
lakehouse metadata.  For small datasets (< 1 GB) or workloads that need strict ACID point lookups on
catalog metadata, a relational OLTP backend offers lower latency and simpler operational model than
maintaining a full lakehouse transaction log.

== Decision

Add OLTP catalog backends — PostgreSQL, MariaDB/MySQL, SQLite — as first-class xCatalog options, selected
automatically by collection size or explicitly by operator configuration.

=== Scope: Metadata-Only

OLTP stores ONLY catalog metadata:

* Namespace definitions and properties
* Table/collection schema (column list, types, partition spec)
* Snapshots and schema history
* Statistics (row count, size bytes, column stats)

Record data ALWAYS stays in ProximaDB's storage engines (VIPER/NOVA/HELIX).
The OLTP DB is NOT a durable record store.  This aligns with the stacked durability mandate.

This ADR is governed by ADR-009 for schema modes and API surfaces. OLTP catalog backends define
schema-on-write metadata and constraints for `ProximaRecord`/`ProximaValue` loads; they do not
authorize REST, gRPC, Arrow, SQL, SDK, or embedded paths to use legacy vector-shaped records as their
target contract.

=== Write Path (OLTP route)

----
REST/gRPC/Arrow/SQL/embedded insert
  → xCatalog schema validation/coercion             ← schema-on-write authority
  → CanonicalOperation::RecordUpsert (WAL)           ← Layer 0: durable journal
  → ProximaRecord in VIPER/NOVA/HELIX                ← Layer 1: canonical record store
  → OltpCatalog.update_statistics() async            ← xCatalog metadata update
  → ProjectionDirective::IcebergManifest (opt)       ← Layer 2: rebuildable projection
----

=== Supported Backends

[cols="2,2,2"]
|===
| Backend | Connection string prefix | Feature flag

| PostgreSQL / Neon / Supabase / CockroachDB | `postgres://` | `oltp-catalog-postgres`
| MariaDB / MySQL / TiDB / PlanetScale | `mysql://` | `oltp-catalog-mysql`
| SQLite (dev / embedded) | `sqlite:///` | `oltp-catalog-sqlite`
| All three | — | `oltp-catalog-full`
|===

SQL driver: `sqlx 0.7` with `runtime-tokio-native-tls`, `json`, `chrono`, `uuid` base features.

=== DDL Schema (auto-migrated on startup, prefix `xcatalog_`)

[source,sql]
----
CREATE TABLE IF NOT EXISTS {prefix}namespaces (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    namespace_path TEXT[] NOT NULL,    -- JSON array on MySQL/SQLite
    properties JSONB,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE(namespace_path)
);

CREATE TABLE IF NOT EXISTS {prefix}tables (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    namespace_path TEXT[] NOT NULL,
    table_name TEXT NOT NULL,
    schema_json JSONB NOT NULL,
    properties JSONB,
    format TEXT DEFAULT 'INTERNAL',
    location TEXT,
    size_bytes BIGINT DEFAULT 0,
    row_count BIGINT DEFAULT 0,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE(namespace_path, table_name)
);

CREATE TABLE IF NOT EXISTS {prefix}snapshots (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    table_id BIGINT REFERENCES {prefix}tables(id) ON DELETE CASCADE,
    snapshot_id BIGINT NOT NULL UNIQUE,
    parent_snapshot_id BIGINT,
    timestamp_ms BIGINT NOT NULL,
    manifest_list TEXT,
    summary JSONB,
    schema_id INT
);

CREATE TABLE IF NOT EXISTS {prefix}schema_history (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    table_id BIGINT REFERENCES {prefix}tables(id) ON DELETE CASCADE,
    schema_version INT NOT NULL,
    schema_json JSONB NOT NULL,
    applied_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE IF NOT EXISTS {prefix}statistics (
    table_id BIGINT REFERENCES {prefix}tables(id) ON DELETE CASCADE PRIMARY KEY,
    row_count BIGINT,
    size_bytes BIGINT,
    column_stats JSONB,
    updated_at TIMESTAMPTZ DEFAULT NOW()
);
----

Backend dialect notes:

* MySQL/MariaDB: `JSON` not `JSONB`; `BIGINT AUTO_INCREMENT`; arrays as JSON-encoded `TEXT`.
* SQLite: `INTEGER PRIMARY KEY AUTOINCREMENT`; all JSON/array columns as `TEXT`.

=== Size-Based Routing Policy

[source,rust]
----
// CatalogManager::catalog_for_size(size_bytes, threshold_bytes)
// Default threshold: 1_073_741_824 (1 GB)
//   size < threshold  →  look for a catalog named "oltp-*"
//   size >= threshold →  use default (lakehouse) catalog
----

Operators register an OLTP catalog named `oltp-postgres` (or `oltp-mysql`, `oltp-sqlite`).
`catalog_for_size()` finds it by prefix match.

=== Proto Extension

[source,protobuf]
----
// proto/proximadb/v1/catalog.proto
enum CatalogType {
  CATALOG_TYPE_OLTP_POSTGRES = 10;
  CATALOG_TYPE_OLTP_MYSQL    = 11;
  CATALOG_TYPE_OLTP_SQLITE   = 12;
}

message OltpCatalogConfig {
  string connection_string    = 1;
  uint32 pool_max_connections = 2;   // default 10
  string table_prefix         = 3;   // default "xcatalog_"
  bool   auto_migrate         = 4;   // run CREATE TABLE IF NOT EXISTS on startup
  uint64 size_threshold_bytes = 5;   // default 1 GB
}
----

=== Key Source Files

* `src/catalog/oltp.rs` — `OltpCatalog` struct; `Catalog` trait impl; DDL generation; in-memory HashMap fallback when no feature flag active
* `src/catalog/mod.rs` — `CatalogManager::create_oltp_catalog()` factory; `catalog_for_size()` routing helper
* `proto/proximadb/v1/catalog.proto` — OLTP catalog type enum + `OltpCatalogConfig` message

=== Build Commands

[source,bash]
----
cargo build --features oltp-catalog-postgres   # PostgreSQL, Neon, Supabase, CockroachDB
cargo build --features oltp-catalog-mysql      # MariaDB, MySQL, TiDB, PlanetScale
cargo build --features oltp-catalog-sqlite     # SQLite (dev/embedded)

----

== Consequences

=== Positive

* Small collections (< 1 GB) get fast ACID point-lookup metadata without lakehouse overhead.
* Neon/Supabase support lets operators use managed serverless Postgres with zero ops burden.
* SQLite allows fully embedded deployments with no external DB dependency.
* Catalog routing is transparent to query and insert paths — same `Catalog` trait throughout.

=== Negative / Risks

* `sqlx::AnyPool` requires runtime backend detection from connection string; type information is lost at compile time in the fallback path.
* MySQL/SQLite dialect differences in DDL (no native array type, no `JSONB`) require per-backend DDL generation — `generate_ddl()` in `OltpCatalog` handles this but must be kept in sync.
* Without `oltp-catalog-*` feature flags, `OltpCatalog` falls back to an in-memory HashMap — correct but not durable across restarts.

=== Neutral

* OLTP catalog is metadata-only by design.  This is not a compromise — it is the correct separation: ProximaDB engines own record durability; xCatalog owns schema and statistics.
* The 1 GB default threshold is configurable per `OltpCatalogConfig.size_threshold_bytes`.
