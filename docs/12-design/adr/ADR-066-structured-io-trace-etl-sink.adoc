== 1. Context — first principles

A query trace is, from first principles, **the per-query bill of materials for the five co-design
dimensions** (ADR-052): the object-storage I/O, the network egress, the local-disk/cache hits, the
per-modality compute, and the governance context (tenant, route) that one query consumed. ProximaDB
already *captures* this in-process — `IoTraceSnapshot`
(`crates/modalities/proximadb-observability-engine/src/io_trace.rs`) is stamped at every I/O boundary
and read at `instrument()` exit by three observers: the cost model (route), the cache stats, and the
always-on **billing** observer (ADR-027). ADR-064 Decision 3 / TD-TRACE-1 added the *structured*
content (routing reasons, lowering declines, and — Slice 2 — the per-operator `exec[]` vector).

But the trace is **ephemeral and shapeless**:

[listing]
----
  per-query:  I/O boundaries ──stamp──▶ IoTraceSnapshot ──instrument() exit──▶ observers ──▶ {cost model, cache, BILLING}
                                              │                                                         │
                                              └── optional tracing::info!(target=io_trace) ─────────────┴─▶ ./log/proximadb.log  (MIXED w/ app log,
                                                     (io-trace feature, default OFF; formatted text)                              text, io-trace-gated)
       ▲                                                                                                    ▲
       │ no DURABLE, QUERYABLE history                                                                       │ not ETL-native: parse log lines back out
----

Two structural problems, from first principles:

1. **No durable, queryable history.** The snapshot dies with the request. The only external landing is
   a *formatted `tracing::info!` line* mixed into `proximadb.log`, gated OFF by default, that must be
   *re-parsed* to recover structure — fragile, lossy, and useless for fleet-wide analytics (which
   routes regress, which tenants pay the most GET round-trips, where the cost model mis-attributes).
   The billing observer ships *aggregates* per tenant, not the *per-query evidence* behind them.

2. **The snapshot is one wide, sparse, ever-widening struct.** `IoTraceSnapshot` is a flat superset:
   object-store counters, footer hits, `compute_ms`, wall spans, egress, route, the plan-geometry
   vector, and now `exec_ops`. Every modality that wants to be observable (vector prune ratios, graph
   frontier, embedding KEU) adds *more flat fields that are null for every other modality*. This is a
   sparse-superset anti-pattern: it widens forever, and it columnar-compresses badly (a `trace_exec`
   column is null for every vector query, and vice-versa).

The decision below separates the three concerns a durable trace conflates — the **data model** (what a
trace *is*), the **transport** (how it *durably lands*), and the **consumption** (billing vs cost-model
vs analytics) — and co-designs each against its dominant cost term.

== 2. Decision

=== D1 — Data model: an **envelope**, not one wide struct

A trace record is a homogeneous **header** + a modality-discriminated **payload** (a tagged union), not
a flat superset.

[listing]
----
  TraceRecord = Header  ⊕  Payload
  ─────────────────────────────────────────────────────────────────────────────
  Header   (EVERY modality emits it — the homogeneous co-design cost spine):
    query_id, tenant, ts, route(shape_class,backend),
    get_ops/put_ops/list_ops, bytes_read, range_gets, footer_hits/misses,
    compute_ms{engine→ms}, setup_ms/open_ms/emit_ms, egress_bytes(KOU), storage_profile
  Payload  (tagged by modality — internally HOMOGENEOUS):
    Relational { plan geometry (depth/nodes/fanout/blocking), exec:[{op,rows_in,rows_out,ms_self,bytes,spill}] }
    VectorAnn  { prune ratios, candidates, stripe gets, quant tier }
    Graph      { hops, frontier sizes }
    Document   { shred stats }        Embedding { KEU input/output tokens }
----

**First principle:** a trace has a *homogeneous cost spine* every query pays (I/O round-trips, compute,
egress — the co-design dimensions) and a *modality-specific tail*. Forcing the tail into the spine
makes the record a sparse superset. The envelope keeps the spine stable (billing reads *only* the
header — a stable seam) and makes each payload internally homogeneous, which is exactly what columnar
storage rewards (D3). The current flat `IoTraceSnapshot` is the **migration source**, not the target;
the header↔payload split lands at a stable seam so **billing is never broken** (it already reads only
header-class fields — `compute_ms`, `egress_bytes`).

=== D2 — Two buses: cost/I-O trace (this one) vs quality/eval, never merged

The cost/I-O trace is **per-query, billing-grade, emitted for every query**. Quality/eval signals —
recall@k, hybrid/RRF ranking, semantic relevance — are **sampled, eval-grade**, and already ride the
`predicate_diagnostics` bus; TD-TRACE-1 named recall an explicit non-goal. Merging them would
(a) tax the hot path with sampling/scoring logic it must not carry, and (b) mix billing-grade evidence
with sampled quality data in one schema. **They stay two buses.** This ADR governs only the cost/I-O
trace.

=== D3 — Format: two formats, two tiers, config-selected

[listing]
----
  HOT write path  ──▶  SPOOL  = JSONL + zstd            ──async compaction──▶  WAREHOUSE = star-schema Parquet
                       (append-native, one record/line)                        trace_header  +  satellites:
                       schema-evolution-free (serde #[default])                 trace_exec / trace_vector / trace_graph …
                       modality heterogeneity for free                          joined on query_id
                       debuggable (zcat | jq)                                   each satellite internally HOMOGENEOUS
----

* **Spool = JSONL + zstd** on the hot write path. Append-only (one record per line), so no rewrite;
  **schema-evolution-free** because the snapshot already round-trips under `#[serde(default)]`
  back-compat; it carries modality heterogeneity *for free* (each line is whatever payload the query
  produced); and it is directly debuggable (`zcat | jq`). It is the *lowest-ceremony durable format* —
  the right choice where the constraint is a cheap, robust append.
* **Warehouse = star-schema Parquet**, produced by the async seal/compaction step:
  a `trace_header` fact table + **one satellite per modality** (`trace_exec`, `trace_vector`,
  `trace_graph`, …), joined on `query_id`. Each satellite is internally homogeneous → columnar
  compression and projection/predicate pushdown *win* (the exact benefit the flat sparse struct
  forfeits). Flattening the relational `exec[]` LIST into one `trace_exec` **row per operator**
  sidesteps the nested-LIST concern and makes "which operator is slowest across the fleet" a trivial
  DataFusion scan.
* **Reject Avro.** Avro is row-oriented with no predicate/projection pushdown; it earns its keep only
  as a Kafka/schema-registry wire format, which is out of scope (D2 non-goal). In a warehouse read
  through DataFusion it would be transcoded to Parquet anyway — so we produce Parquet directly.

=== D4 — Transport: object-store dispatch, co-designed against the dominant cost term

The dominant cost term for a cloud trace stream is **object-store request count + GB-month at rest**,
*not* CPU. The transport is co-designed to that:

* **Background async only.** The observer at `instrument()` exit *only enqueues* the record to a bounded
  local spool. A background task **seals a segment on size OR interval (whichever first)**, compresses
  zstd, and PUTs. The query path **never** compresses or PUTs — zero hot-path I/O, zero added latency
  (co-design: don't pay CPU/round-trips on the hot path).
* **Batch to the efficient PUT size.** Target **4MB objects by default (1MB option)** — a natural
  multipart part-size, good PUT throughput, and a sensible ranged-read granularity for the downstream
  DataFusion warehouse read. One 4MB PUT beats thousands of tiny ones (requests are the metered unit).
* **Keys via `DrPathBuilder`**, e.g. `data/_system/observability/io_trace/dt=YYYY-MM-DD/{host}-{seq}.jsonl.zst`
  (a system stream), or partitioned by `tenant_id` when traces are billing-grade evidence that needs
  per-tenant isolation (D6-governance).
* **Access tier is the at-rest lever (ADR-036).** PUT these objects **Cool/Cold** via the canonical,
  cloud-neutral `ObjectAccessTier` / `FileOptions.storage_class` (never per-cloud strings) — GB-month is
  the cost term, moved by the tier, not the scheme.
* **Spool overflow → drop-oldest.** The spool is bounded (`spool_max_bytes`); on overflow it drops the
  oldest segment. Observability is **best-effort** and must *never* block or OOM the database.

=== D5 — Consumption: a separate, gated observer; billing untouched

A new `set_trace_observer` seam, **distinct from the billing observer**. Billing stays always-on and
**never gated** (ADR-027, enforced by `scripts/check_billing_never_gated.py`) — the trace sink is
default-**OFF**, env/TOML-gated, and reads the same snapshot without touching the billing input set
(`compute_ms`/`egress_bytes`), so it is provably **zero-double-count** and cannot regress a meter.

=== D6 — Configuration: TOML-first, env-override (12-factor)

[source,toml]
----
[observability.io_trace_sink]
enabled          = false          # default OFF; env: PROXIMADB_IO_TRACE_SINK=1
local_dir        = "./log/io_trace"
segment_bytes    = 4194304        # seal+compress+PUT at 4 MiB (1 MiB option)
flush_interval_s = 60             # ...or this, whichever first (bounds latency-to-warehouse)
compression      = "zstd"
format           = "jsonl"        # jsonl | parquet (parquet = DataFusion-native ETL)
object_store_uri = "az://…/io_trace"   # or reuse the data object-store
access_tier      = "cool"         # Cool/Cold — GB-month lever (ADR-036)
partition_by     = "date"         # date | tenant | host
retention_days   = 30
spool_max_bytes  = 268435456      # bounded spool; drop-oldest on overflow
----

Every field takes an env override (12-factor). Config default-OFF ⇒ zero behavior change until an
operator opts in.

== 3. Co-design dimensional analysis (ADR-052 spine)

Each of the five physical dimensions, and the dominant cost term this ADR moves on it:

[cols="1,3",options="header"]
|===
| Dimension | Decision & dominant cost term
| **Object storage** | *Requests + GB-month.* Batch to 4MB PUTs (D4), zstd (3–5× on repetitive JSON), Cool/Cold access tier (D4/ADR-036), flat immutable keys via `DrPathBuilder`, lifecycle/retention GC. The record count → object count → PUT count is the knob.
| **Network** | *Egress round-trips.* Traces flow app→warehouse in-region, batched — few large requests, not per-query chatter. No cross-region egress on the hot path.
| **Local disk / cache** | *Backpressure buffer.* The bounded local spool IS the write buffer and the backpressure absorber; drop-oldest bounds it. The seal size (4MB) sets the disk↔object-store handoff granularity.
| **Compute-per-modality** | *Near-zero on the hot path.* The observer only enqueues; compress/transcode run on the background task. The **envelope+typed-payload** model (D1/D3) keeps downstream columnar compute cheap (homogeneous satellites → pushdown), the reason the flat sparse struct is rejected.
| **Governance / security** | *Isolation + retention + no row leakage.* The trace carries `tenant_id` + counters + route, **never row data / vector values / raw query text** (join key is an opaque `query_id`). Per-tenant key partitioning is available when traces are billing-grade evidence; retention via lifecycle policy.
|===

== 4. Alternatives considered — and rejected

* **A1 — Keep one wide `IoTraceSnapshot` forever.** Rejected: the sparse-superset widens with every
  modality and columnar-compresses badly (D1). Envelope+typed-payload is the target end-state.
* **A2 — Log-routing only (a `tracing` Layer to a dedicated file).** A `fmt::Layer::json()` filtered to
  `target=proximadb::io_trace` would separate the stream cheaply, but it rides the `io-trace` feature
  gate, re-serializes from a formatted event, and still needs log-line parsing for ETL. Useful as a
  *stopgap*, not the architecture. The observer→structured-sink (D5) is the durable path.
* **A3 — Avro / Kafka streaming bus.** Rejected: row-oriented, no pushdown, and it earns its keep only
  with a schema registry + streaming consumer (out of scope, D2). It would transcode to Parquet in the
  warehouse anyway (D3).
* **A4 — Fold the trace sink into the billing observer.** Rejected: entangles observability with
  billing, violating ADR-027 (billing never gated); a separate observer keeps billing provably
  unaffected (D5).
* **A5 — Synchronous upload at query time.** Rejected: puts compress + PUT round-trips on the hot path
  (D4). Enqueue-only + background seal is the co-design-correct split.
* **A6 — Parquet on the hot write path.** Rejected: Parquet's schema rigidity fights modality
  heterogeneity and forces buffering/rewrite (write amplification) vs a JSONL append. Parquet is the
  *warehouse* format, produced by async compaction (D3).

== 5. Consequences & migration

* **Incremental, safe rollout.** The sink first serializes the **existing flat snapshot** as JSONL
  (S1–S2 in TD-TRACE-2), so no data-model refactor blocks the durable stream. The **envelope refactor**
  (D1) lands later at a stable seam (billing reads header-class fields throughout) as a separate slice.
* **`query_id`.** A stable per-query id is needed to join header↔satellites; mint it at
  `instrument()` entry if one does not already exist in the trace scope.
* **Parquet producer.** Land JSONL on the write path; **async-compact JSONL→star-schema Parquet**
  (keeps the write path trivial). Compaction is an optional later slice.
* **Retention.** Prefer an object-store **lifecycle policy** for `retention_days` GC (no app cron);
  fall back to an app GC only where lifecycle rules are unavailable.
* **Gate.** Observe-only, **no served-result change**; gated by a JSONL/Parquet **round-trip test** and
  the standing `check_billing_never_gated` guard; the spool is bounded (no OOM); default-OFF.
