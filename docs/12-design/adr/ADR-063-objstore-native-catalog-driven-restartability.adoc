= ADR-063: Object-store-native catalog & catalog-driven restartability (serverless posture)
:status: Proposed (2026-07-15; r2 amended same day per adversarial review — D4 rewritten with pre-PUT fenced ordering + crash-idempotent materialization, D6 inventory corrected boot-constructor-derived, D3/D7/D8 scoped)
:date: 2026-07-15
:deciders: architecture
:relates-to: ADR-020 (WAL authority), ADR-028 (anvaiops object-store deployment), ADR-031 (catalog object identity), ADR-036 (flat keys / access tier), ADR-045 (durable core vs rebuildable metadata), ADR-048 (SystemCatalog authority), TD-OBJSTORE-1..5, TD-CAT-4/5, CATALOG_OBJECT_STORE_DESIGN_REVIEW_2026_07_14
:supersedes: none

== Context

ProximaDB targets a **fully serverless posture on object storage**: a node is a cache; the
object store is the database. Catalogs in this class of system (Unity Catalog, Polaris,
Gravitino) typically lean on a side RDBMS (MySQL/Postgres) for metadata authority — which
reintroduces a stateful, always-on, separately-HA'd dependency and defeats the serverless
economics. The 2026-07-14 catalog design review already verified our alternative is sound:
`SystemCatalog` publishes generation-fenced, put-if-absent versioned snapshots to
`_operator/catalog/_manifests/` (Nessie/Delta-kernel-grade commit protocol, no RDBMS).

What the review did **not** cover is the data plane's restart contract. A measured
process-boundary reproduction (2026-07-15, Azurite emulator; test
`zero_vector_kv_record_survives_restart` in
`apps/proximadb-server/tests/object_store_restart_recovery.rs`) proved TD-OBJSTORE-1
batch 3 and localized it precisely — and it is **not** a zero-vector bug:

* Seed two dim-1 records (`[0.5]` control + `[0.0]` KV) → both acked and readable.
  SIGKILL. Restart on a fresh local disk. **Both** records 404.
* The WAL data object **is durable** (`{root}/collections/1/wal/8dWbZDDUPo.bcwal`
  present in the store) — the sync `PerBatch` data write worked.
* Its **pointer is not**: `disk_manager.rs:273` registers the batch in the global WAL
  manifest via `append_async` — a channel drained by a background worker batching at
  100 ms (`manifest/service.rs:44`). SIGKILL after ack, before the batcher flushed →
  durable data, lost pointer, no error logged anywhere.
* The safety net is also broken: catalog-driven per-collection recovery DID run
  ("Found 1 collections in catalog" → engine registered), but the best-effort LIST
  fallback (`disk_manager.rs:362 list_collection_files`) gates on
  `filesystem.exists(dir_url)` for a **directory prefix** — on a flat-key object store
  `exists()` is a HEAD on the literal key (`azure_blob.rs:277`), which is false for
  prefixes → early-return **0 files** while the `.bcwal` sits right there.
* Result: "Recovered 0 vectors from 0 files". The anvaiops KV collections (API keys,
  tenant registry) are small and never flush, so they live-or-die on exactly this path.

A parallel recovery-surface inventory found the same *class* of gap elsewhere: the legacy
document WAL, observability WAL, external-collections registry, and primary-pod registry
persist to **local disk only**; the AXIS event log is in-memory. Each silently violates
the serverless contract on a fresh-disk restart.

First principles for object storage:

* **LIST is the ground truth.** S3/Azure/GCS LIST has been strongly consistent since
  2020-21. An object that exists IS discoverable; no secondary pointer is needed for
  correctness. Pointers buy ordering and latency, not truth.
* **Ack is a durability promise.** Anything acked to a client must survive
  SIGKILL + disk loss using object-store state alone.
* **Round-trips are the dominant cost term** (co-design mandate): the design must not
  buy durability by doubling PUTs per write when a boot-time LIST per collection
  (bounded, parallel, once) achieves the same guarantee.

== Decision

**D1 — The catalog is object-store-native. No side RDBMS, ever.** `SystemCatalog`'s
generation-fenced put-if-absent snapshot chain under `_operator/catalog/_manifests/`
(ADR-048; verified state-of-the-art in the 2026-07-14 review) is the sole metadata
authority. Any future catalog feature (multi-writer DDL, followers, account catalogs)
must extend this protocol, not introduce a database dependency. This is the load-bearing
serverless decision.

**D2 — The catalog is the recovery root.** Restart = open catalog (snapshot + WAL tail)
→ enumerate namespaces/collections **across all modalities** (vector, graph, document,
timeseries, relational) → for each collection, derive its physical roots from
`storage_assignment.base_location` / `DrPathBuilder` → recover state found **under those
prefixes**. The catalog row is the dependency-order authority: no orphan scanning of the
whole bucket, no recovery of collections the catalog does not know. (TD-OBJSTORE-2
already established snapshot-before-DDL-ack; this ADR extends the same discipline to the
data plane.) _Scope note (r2): this describes the **target** architecture. Today only
vector WAL recovery is catalog-enumerated; graph, document, and observability recovery
run through separate boot paths (see D6 inventory). Convergence is incremental — the
binding rule now is that **new** engines/surfaces must enumerate from the catalog, and
each existing separate path converges via its D6 migration TD._

**D3 — Ack-durability invariant (write ordering).** When a write is acked, its data
AND its discoverability are durable on the object store. Discoverability means: the data
object itself is LISTable under the catalog-derived prefix. Because LIST is strongly
consistent, the synchronous data PUT alone satisfies the invariant — **no second
synchronous pointer PUT is required**, and none may be relied upon. _Scope (r2): the
strong-LIST premise is certified only for the **primary endpoints** of AWS S3, Azure
Blob, and GCS (each documents strongly consistent listing). S3-compatible third-party
implementations, secondary/replication endpoints, and proxies are NOT certified by
carrying an `s3://` URL — deployments on such stores must declare it, and recovery
treats any LIST error (authorization, network, throttle) as **fail-closed** (retry then
loud per-collection recovery failure), never as an empty prefix._

**D4 — LIST is the discovery authority; correctness travels IN the WAL object
(self-describing, pre-PUT-ordered); manifests are caches.** _(Revised after review:
the r1 claim that replay was already idempotent via mandate 16 was wrong — the dead-record
predicate and tombstone suppression are read-merge semantics, not `do_flush` invariants,
and `do_flush` mints a fresh L0 segment per call. Ordering by object timestamp / legacy
batch-id was also unsafe: wall-clock + process-local counters can resurrect old state
when an old same-key orphan replays after a newer manifested batch.)_

Per-collection WAL replay enumerates batches by **LIST under `{collection}/wal/`**; the
global WAL manifest remains a pure cache (skip-list, flushed-status) and is never the
gate. To make that sound, every WAL object must be **self-describing and totally
ordered before it is written**:

* *Pre-PUT ordering token.* Before the data PUT, the writer allocates
  `{recovery_epoch, per-collection monotonic sequence}` — the epoch from the
  collection's generation-fenced lease (D7), the sequence durable-monotonic within the
  epoch. The token is encoded in the **object key** (lexicographically sortable) and in
  the serialized **batch header**, together with checksum, format/version, and
  encryption metadata. The WAL object is created with **conditional create
  (put-if-absent)** so key collisions are impossible. LIST alone then yields a totally
  ordered, integrity-checkable, decryptable replay set — zero extra write-path
  round-trips, no second correctness object. (The current manifest LSN cannot serve:
  it is allocated *after* the data PUT.)
* *Crash-idempotent materialization.* Recovery resolves all recovered same-key
  mutations in token order **in memory**, then materializes through **deterministic
  segment naming derived from the replayed token range + conditional create** — so a
  crash after a successful flush but before WAL deletion/status persistence makes the
  re-run a no-op instead of a duplicate L0 segment.
* *Fail-closed on ambiguity and error.* Legacy orphan batches without tokens replay
  automatically only when unambiguous (at most one legacy orphan for the collection);
  otherwise recovery halts loudly for operator decision (pre-GA acceptable — the token
  naming ships with this ADR, bounding the legacy window). A LIST failure
  (authorization, network) is **never** interpreted as an empty prefix: retry, then
  fail recovery for that collection loudly.
* *Manifest-state fix folded in:* manifest load must dedup equal-LSN entries
  status-aware (`Flushed` supersedes `Active` at the same LSN), closing the stale-Active
  reload defect.

**D5 — `exists()`-before-LIST on a prefix is a forbidden pattern.** On flat keyspaces,
prefix existence is answered by LIST (empty result = absent), never by HEAD. The
`list_collection_files` gate is a defect; a source-guard test (pattern:
`objstore_url_construction_test.rs`) backstops the class.

**D6 — Every durable surface roots under the catalog-derived object-store prefix, or
declares itself rebuildable.** _(Revised r2: the r1 classification was partly stale;
this inventory is now **boot-constructor-derived** — from `src/database.rs` +
`SharedServices` construction — and must be re-derived, not copied, whenever this ADR is
amended.)_

[cols="2,2,3", options="header"]
|===
| Surface | Current state | Disposition
| External-collections registry | local `data_dir` JSON | (a) migrate — TD to file
| Collection-pinning registry | local `data_dir/pinning/registry.json` | (a) migrate — TD to file
| Primary-pod registry | catalog hydration/migration EXISTS; local fallback remains | (a) finish migration, then remove the local fallback
| Legacy document service WAL | still constructed at boot; canonical record store (ADR-055) has not replaced it | (a) supersede via canonical record store; audit its buffering/ack durability on scheme-qualified URLs
| Observability WAL | accepts scheme-qualified storage URLs on some paths; ack/buffer durability unaudited | (a) audit, then certify or migrate
| AXIS event log | **filesystem-backed** (not in-memory as r1 claimed); rebuildable projection | (b) document the rebuild + compaction consequences of loss
| Graph (ORION) checkpoints | object-store durable, but recovered via a separate boot path | converge to D2 enumeration (migration TD)
| VOE directory / caches / query plans | rebuilt from segments | (b) rebuildable, ephemeral OK
|===

Class (a) items each get a TD; class (b) items must document their rebuild path.
Nothing may sit in class "durable on local disk only".

**D7 — Tenancy scopes recovery; recovery is single-writer per collection.** The
two-tier Operator/Account catalog (Phase 5) and
`_operator/leases/{tenant}/{collection}` generation fences are also the recovery
boundaries: a pod recovers exactly the collections its catalog role can name, under
account-scoped prefixes (structural isolation, never a filter predicate). Recovery
inherits `TenantContext` plumbing at every I/O boundary (billing + isolation).
_Amendment (r2): before replaying a collection, the recoverer must **acquire that
collection's generation-fenced lease** (the existing partition-lease primitive). This
makes concurrent recoverer pods safe, and the acquired lease epoch IS the
`recovery_epoch` in D4's ordering token — one fencing mechanism covers stale writers
and concurrent recoverers._

**D8 — Restartability is CI-gated on real object-store APIs, in cost-credible tiers.**
_(Revised r2: the r1 "full matrix everywhere" framing was not credible on 16 GB hosted
runners — a cloud-emulator QA run already takes ~52 min before adding a server build,
and the root-crate compile is pinned to `jobs=1` for OOM safety.)_ Tiering
(TD-OBJSTORE-5):

* *PR tier (path-gated):* Azurite-only strict restart repro (`--features azure` only —
  one cloud backend compiled) + cheap **backend contract tests** in the small
  object-store crate (PUT → prefix-LIST sees it; prefix-HEAD-negative) against all
  three emulators — no main-crate compile.
* *QA tier:* one `cloud-full` server build; Azure and S3 emulators run **sequentially**
  (stop one before starting the next — memory headroom); restart proof per store;
  recall ratchet on **one** strict backend (recall is a ranged-read/footer test, not
  the restart correctness gate).
* *Nightly / large-runner tier:* GCS compatibility (restart + recall) and cross-backend
  recall. GCS is explicitly **not called a gate** while its failures are best-effort
  warnings.

The process-boundary restart test (`object_store_restart_recovery.rs`, now accepting
`gs://` too) is the restartability ratchet: seed → SIGKILL → fresh-disk boot → verify
by id. It caught batch 3; it stays red until D3-D5 land, and the CI wiring must be
**red-first** on develop to prove the gate bites.

== Alternatives rejected

* **A1 — Side RDBMS catalog (Unity/Polaris/Gravitino shape).** Reintroduces a stateful
  service with its own HA/backup/patching; breaks scale-to-zero; adds a second
  consistency domain to reconcile with the store. Our put-if-absent + generation-fence
  protocol already provides single-writer DDL commit semantics at object-store cost.
* **A2 — Synchronous manifest pointer PUT per WAL batch.** Fixes the observed loss but
  doubles the write-path round-trips (the dominant cost term) and still leaves a
  window unless made atomic with the data PUT — and no object-store primitive
  (conditional PUT, append blob, GCS generation match, multipart completion) can
  atomically commit **two independent objects**; a conditional pointer only prevents
  pointer lost-updates while keeping the cross-object failure window. The
  zero-extra-round-trip resolution is D4's **self-describing WAL object**: the ordering
  token, checksum, format/version, encryption metadata, and fencing identity travel in
  the object's key/header, so LIST discovers everything recovery needs from ONE object.
  The pointer stays async as a cache.
* **A3 — Mutable "latest" tip pointer for recovery.** Already rejected in the
  2026-07-14 review (lost-update hazard); LIST-for-latest stays the documented choice.
* **A4 — Bucket-wide orphan scan at boot.** Violates D2 (catalog is the root) and costs
  unbounded LIST on shared buckets; per-collection prefixes keep boot I/O proportional
  to catalog size.

== Consequences

* *(+)* Acked writes survive SIGKILL + disk loss with **no added write-path round-trips**;
  the manifest keeps its latency benefits without carrying correctness weight.
* *(+)* One recovery model for every modality: catalog → prefix → LIST → replay/reopen.
  New engines inherit restartability by construction instead of custom recovery code.
* *(+)* Full serverless posture: any pod can die at any moment; a replacement boots from
  the store alone. No RDBMS to operate, back up, or pay for at idle.
* *(−)* Boot does one LIST per collection WAL prefix (parallelizable; bounded by catalog
  size). Mitigation: manifest-as-cache short-circuits ordering work when present.
* *(−)* Class-(a) local-disk surfaces need migration TDs (tracked under D6); until they
  land, their loss windows must stay documented in TD-OBJSTORE-1's "not-VM-loss-durable"
  list with loud runtime warnings.

== Failure modes covered (r2)

Each must have an explicit mechanism in TD-OBJSTORE-4 before this ADR flips Accepted:

[cols="3,3", options="header"]
|===
| Failure mode | Mechanism
| Crash after SST flush, before WAL deletion/status persistence | deterministic recovery-segment naming + conditional create (re-run = no-op)
| Equal-LSN `Active`/`Flushed` manifest entries survive reload | status-aware dedup on manifest load (`Flushed` wins)
| Encrypted WAL recovery loses key metadata | encryption metadata in the self-describing batch header
| LIST-discovered orphan lacks integrity metadata | checksum + format/version in key/header
| Same-key update/delete/tombstone split across manifested + orphan batches | total order by pre-PUT token; in-memory resolution before one flush
| Clock rollback / batch-id collision / process restart / concurrent writers | fenced `{epoch, sequence}` token + conditional create; epoch from the lease
| Concurrent recovery pods | D7 lease acquisition before replay
| LIST permission/transient failure read as "empty collection" | fail-closed policy (retry → loud per-collection failure)
| Legacy unordered orphans with ambiguous same-key order | fail-closed: auto-replay only when ≤1 legacy orphan; else operator override
| GCS restart coverage missing from the test | `gs://` accepted by the restart test; exercised in the nightly tier
|===
