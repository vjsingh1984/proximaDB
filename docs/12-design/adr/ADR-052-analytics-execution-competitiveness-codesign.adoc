== Context

A first-principles + competitor review (2026-07-03) of ProximaDB's analytics/OLAP path
against Apache Gluten, Apache Comet, Velox, DataFusion, Databricks Photon, Snowflake, AWS
EMR, and Onehouse Quanton surfaced three findings:

. **The seams are excellent; the native OLAP *execution* is embryonic.** ADR-039 freezes an
engine-neutral `LogicalNode → ExecutionPipelineResult` seam with DataFusion as one swappable
backend; ADR-050 makes routing cost-based; ADR-033 ratifies Parquet+Iceberg for OLAP and PAX
for vectors; the Iceberg REST catalog is live (ADR-007). But the native relational executor
itself is a *row-wise Volcano iterator*: `crates/query/proximadb-relational-executor/src/lib.rs:1`
("Volcano-style executor… Pure pull model"), evaluating expressions row-at-a-time over
`ProximaValue` (`.eval(&row, …)`, `row.push(…)`). That is the model the entire field
abandoned — Kersten et al. (PVLDB 2018) show Volcano is 1–2 orders of magnitude slower than
vectorized or code-generated execution. The function registry ships ~8 scalars and one
aggregate demonstrator (`crates/foundation/proximadb-functions/src/lib.rs`); window functions
are absent.

. **TPC-DS/TPC-H are CONFORMANCE ratchets, not PERFORMANCE evidence.**
`tests/{tpcds,tpch}_pgwire_e2e.rs` assert query counts (TPC-H 22, TPC-DS 16) over a tiny
deterministic dataset, gated in `.github/workflows/qa-gate.yml`. No scale factor, no
latency/throughput, no baseline vs DuckDB/DataFusion/ClickHouse. Per the co-design mandate
(#11: reject component microbenchmarks masquerading as end-to-end claims; #2: capture the
trace first), "competitive with Photon/Snowflake" is today an *unmeasured* assertion.

. **The statistics substrate is DESIGNED, not WIRED.** ADR-037/038 specify a mergeable
statistics envelope (min/max, NDV/HLL, TDigest, null-count, freshness watermark) and
`src/core/statistics/{summary,sketches}` implement the sketches, but `schema_inference`
still returns `ColumnStatistics::new_unknown()` and the planner is statistics-blind (ADR-050
D2 is the close, in flight). No runtime filters (Dynamic Partition Pruning, bloom
semi-joins), no Adaptive Query Execution.

== First principles (why this shape)

* **Attack the DOMINANT cost term — and in cloud OLAP that is bytes scanned, not CPU.**
  Snowflake's entire thesis (SIGMOD 2016 §3.3.3) and the Iceberg manifest architecture are
  scan-avoidance systems; Quanton's wedge is work proportional to the data *differential*
  since the last run. Photon/Velox/Comet win ~2–3× on CPU (vectorization) but pruning +
  runtime filters win 10–100× on I/O. Therefore ProximaDB's competitive order of work is:
  scan-avoidance first (zone maps, bloom, runtime filters, deletion vectors, late
  materialization, materialized aggregates), vectorized execution second. This inverts the
  naive "build a faster engine" instinct and is the co-design spine applied to analytics.

* **Vectorized-first; do NOT reimplement operators.** The 2020–2026 consensus (Photon,
  SIGMOD 2022 Best Industry Paper; DuckDB; ClickHouse; Velox; DataFusion) is
  vectorized-interpreted execution over columnar Arrow batches, chosen for development
  velocity, observability, and runtime adaptivity — not peak microbenchmark throughput.
  Photon explicitly *"chose to build the engine using the vectorized-interpreted model in
  lieu of code generation."* Only HyPer/Umbra/CedarDB remain codegen-flagships, and even
  they hybridize (Data Blocks; Incremental Fusion, ICDE 2024). ProximaDB already has
  DataFusion behind a frozen seam (ADR-039) and cost-based routing toward it (ADR-050).
  Reusing DataFusion's vectorized scan/filter/agg/join/sort kernels — instead of growing a
  parallel native operator engine — collapses years of work into integration and keeps one
  function definition (ADR-039 invariant 4).

* **The native work that is WORTH doing is the SCAN, co-designed with ANN.** ProximaDB's
  unique asset is a PAX substrate already co-designed for vectors (RaBitQ/SQ8 tiers, zone
  maps, bloom, `RecordReader`). No incumbent co-designs ANN + OLAP scan on one format:
  Lance concedes OLAP; Snowflake's `VECTOR` is a 4096-dim, no-quantization bolt-on with no
  Iceberg-table support and ANN = a separate Cortex Search object; ClickHouse ANN
  pre-filtering falls back to brute-force scan; pgvector is single-node. A PAX-native scan
  operator that emits Arrow `RecordBatch`es to DataFusion is *both* the performance lever
  (one reader, one prune stack, one I/O-trace path — ADR-027) *and* the structural
  differentiator (ANN index and OLAP scan over the same geometry), eliminating the
  CDC/replica/cache Frankenstein stack that causes vector+SQL to "silently discard over 30%
  of correct results" on JOINs (arXiv 2506.23071).

* **The boundary is the contract; keep it standard outside.** Iceberg+Parquet is the
  interop seam (the format war is decided: AWS S3 Tables chose Iceberg Dec 2024; Databricks
  acquired Tabular Jun 2024; Apache Polaris graduated TLP Feb 2026 and now owns the catalog
  fight). ProximaDB keeps internal verticality (PAX scan + ANN co-design) and external
  standardness (Iceberg REST, Substrait-ready `LogicalNode`). ADR-033/039 unchanged.

== Decision (invariants)

. **OLAP execution = vectorized-over-Arrow via DataFusion; the native Volcano is OLTP-only.**
  Bulk scan/filter/project/aggregate/join/sort over analytical tables executes in DataFusion's
  vectorized kernel set. The row-wise `proximadb-relational-executor` Volcano is the floor for
  OLTP / point-lookup / low-cardinality shapes (where row-wise is fine) and the
  no-DataFusion build floor (ADR-039 / TD-181) — *not* the OLAP execution engine. Conformance
  is identical either way (TPC-H/TPC-DS bind to the `LogicalNode` seam, not the engine).

. **The "NativeOlap route" (blueprint P2) is a PAX-native SCAN operator, not a parallel
  operator engine.** It lowers `LogicalNode::Scan` (with pushed predicate + projection) to a
  `RecordReader`-backed scan that applies hierarchical pruning (zone maps TD-154, bloom,
  range coalescing TD-151) and emits Arrow `RecordBatch` consumed by ordinary DataFusion
  operators. Do NOT reimplement HashAgg/HashJoin/Sort natively. This refines blueprint §3/§4
  and is tracked under TD-OLAP-1.

. **Scan-avoidance is the primary competitive work order.** Before any execution-kernel
  optimization, the work that moves the cloud-dominant cost term (bytes scanned) is: wire real
  statistics into the planner (ADR-050 D2 / ADR-037/038 → TD-OLAP-2); add runtime filters —
  Dynamic Partition Pruning + bloom semi-join (TD-OLAP-3, the Photon signature lever);
  deletion vectors (ADR-025) and relational late-materialization (TD-OLAP-5). Each is
  flag-gated, default-off, and promoted only after the per-query I/O trace (TD-158) shows it
  moves the dominant cost term — observe→ingest→act (co-design method §3).

. **Competitiveness is measured, not asserted.** TPC-DS/TPC-H gain a *performance* tier
  (SF1, then SF10) with an evidence ledger: latency + bytes-scanned vs DuckDB, plain
  DataFusion-on-Parquet, and ClickHouse, on the same object store, in CI. The conformance
  ratchets (counts only go up) remain. No "beats Photon/Snowflake" claim enters a doc without
  a ledger entry (mandate #11). TD-OLAP-4.

. **Non-goals (explicit, to protect focus).**
  * No LLVM/Cranelift query codegen now — vectorized-first; codegen layered later *only* on
    measured hot expressions (Velox/ClickHouse do this experimentally; Photon explicitly
    declined for velocity/observability/adaptivity).
  * No distributed MPP/Ballista now — win single-node / pseudo-distributed / embedded first
    (the DuckDB / InfluxDB-IOx / GreptimeDB path); distribution via the pluggable
    `ExecutionEngine` trait later.
  * Do not overclaim five-mode parity — the defensible competitive niche is **vector + OLAP +
    lakehouse (3-mode) co-design**; graph/document are stretch modes.

== Consequences

* **Positive.** Reusing DataFusion execution avoids reimplementing a vectorized operator
  library, a function library of 100+, codegen, spill, and morsel scheduling — the multi-year
  tail that makes "build a competitive OLAP engine" intractable for a small team. The
  PAX-native scan is the one place ProximaDB adds *unique* value (ANN+OLAP co-design) and is
  additive behind the frozen seam. Scan-avoidance attacks the term that actually dominates
  cloud cost.
* **Costs / watch-items.**
  - The PAX-scan→Arrow bridge must be zero-copy and preserve prune-stack semantics across the
    DataFusion `TableProvider`/`ExecutionPlan` boundary (same shape as
    `src/datafusion/proxima_scan_exec.rs` today).
  - DataFusion's hash-join does not yet spill (Comet 0.15 caveat) — large joins need
    sort-merge until upstream lands; the ledger must flag this.
  - Vectorized-first accepts DataFusion's per-op microbenchmark ceiling vs Velox (EDBT 2026,
    Zhao & Fang, SFU: DataFusion 1.45× vs Velox 1.98× over Spark on TPC-DS top-20) in
    exchange for the Rust/Arrow ecosystem, the seam, and development velocity — the ledger
    makes the trade explicit rather than hidden.
* **Relationship to ADR-050.** ADR-050 activates cost-based routing to DataFusion for
  Parquet-backed tables and feeds real stats. ADR-052 extends that posture to the PAX-backed
  native path (the scan operator) and fixes the execution-model + dominant-cost-term +
  measurement framing that ADR-050 does not cover. The two compose; they do not conflict.

== Verification

* **Uniqueness guard:** `python3 scripts/check_td_adr_unique.py` (this ADR + TD-OLAP-1..5).
* **Seam invariant unchanged:** the ADR-039 leakage ratchet stays green; no new `datafusion::`
  import outside the adapter allow-list.
* **Conformance unchanged:** TPC-H (22) / TPC-DS (16) pgwire ratchets pass with OLAP routed
  either way.
* **Performance ledger (new, TD-OLAP-4):** SF1 TPC-DS latency + bytes-scanned vs
  DuckDB / DataFusion-on-Parquet / ClickHouse, in CI, before any "competitive" claim is cited.
