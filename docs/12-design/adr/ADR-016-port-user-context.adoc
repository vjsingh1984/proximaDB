= ADR-016: PortUserContext — Boundary Type for SecurityPort Authentication
:toc: left
:toclevels: 3
:icons: font
:last-updated: 2026-05-25

== Status

Accepted

== Context

`proximadb_runtime::SecurityPort` is the platform runtime's port for
RBAC, role, audit, and policy operations. It is the contract
`proximadb-api`'s gRPC `SecurityServiceImpl` uses to call into the
root-crate security subsystem without importing root-crate types.

`SecurityPort` deliberately does NOT expose authentication
(`authenticate_request` etc.). The Phase 9 audit at
`docs/_internal/status/PHASE9_REMAINING_2026_05_25.adoc` (Task #69)
identified the blocker:

`SecurityCoordinator::authenticate_request`
(`src/security/security_coordinator.rs:329-348`) returns
`UnifiedUserContext`, a root-crate concrete type used in 20+ files
across 117 references:

* `src/security/auth_service.rs`, `rbac_service.rs`, `rls/service.rs`,
`auth/{mod,ldap,oidc}.rs`
* `src/network/auth/middleware.rs`,
`src/network/middleware/tenant.rs`,
`src/network/grpc/{auth,security_service}.rs`
* `src/services/collection/security.rs`,
`src/services/operations/secure_operations.rs`
* `src/query/unified/executor.rs`, `src/storage/traits/query.rs`,
`src/graph/service.rs`

`UnifiedUserContext` carries a fanout of related root-crate concrete
types (`UnifiedPermission`, `UnifiedAuthMethod`, effective-permissions
cache, session id, capability scopes), and the REST middleware path
(`auth_middleware_unified`) still takes `Arc<SecurityCoordinator>`
directly via `from_fn_with_state`.

`SecurityPort::authenticate(...)` cannot be added today because its
return type cannot move to the runtime crate without one of:

* (a) duplicating `UnifiedUserContext` as a port-level type and wrapping
it on both ends, or
* (b) extracting the entire `UnifiedUserContext` graph
(`UnifiedPermission`, `UnifiedAuthMethod`, effective-permissions
cache, session id, capability scopes) into a shared contracts crate.

This ADR picks option (a) and defines the port-level type's shape.

== Decision

Define `proximadb_runtime::PortUserContext` as a **minimal, lossy
projection** of `UnifiedUserContext`. Production callers that need the
full context continue to use `UnifiedUserContext`; cross-crate boundary
callers (the runtime port, gRPC handlers in `proximadb-api`) use
`PortUserContext`.

=== `PortUserContext` shape

[source,rust]
----
#[derive(Debug, Clone)]
pub struct PortUserContext {
    /// Opaque user identifier (string for forward-compat across auth providers).
    pub user_id: String,
    /// Tenant the request is being authenticated under.
    pub tenant_id: String,
    /// Roles assigned to the user — strings, not the typed
    /// root-crate `UnifiedRole` enum.
    pub roles: Vec<String>,
    /// Scopes / capabilities granted to the request — strings.
    pub scopes: Vec<String>,
    /// JSON-serialized effective-permissions snapshot.  Opaque to the
    /// runtime layer; consumers either pass through or deserialize via
    /// the root-crate `UnifiedPermission` schema.
    pub effective_permissions_json: String,
    /// Authentication method label (e.g. "oidc", "ldap", "apikey").
    /// String for forward-compat.
    pub auth_method: String,
    /// Optional session id (None for stateless auth).
    pub session_id: Option<String>,
}
----

All fields are owned strings or owned Vec<String>; no lifetime
parameters, no root-crate types, no proto types. Serde-derived if a
gRPC wire is needed in the future.

=== `SecurityPort` extension

Add ONE method:

[source,rust]
----
#[async_trait]
pub trait SecurityPort: Send + Sync {
    // ... existing methods unchanged ...

    /// Authenticate an incoming request and return a port-level user
    /// context.  Implementations on the root crate side construct this
    /// by lossy projection of `UnifiedUserContext`; full context stays
    /// accessible via `SecurityCoordinator` directly for callers that
    /// need typed permission objects.
    async fn authenticate(
        &self,
        request: AuthenticationData,
    ) -> Result<PortUserContext>;
}
----

`AuthenticationData` is the existing input shape used by
`SecurityCoordinator::authenticate_request` (string token, header map,
or similar — depends on current implementation).

=== Migration plan (multi-session)

. **Land** `PortUserContext` + `SecurityPort::authenticate` in
`proximadb_runtime`. Add the trait method with a default
`unimplemented!()` body so existing impls compile unchanged.
. **Implement** `authenticate` on `SecurityCoordinator` by lossy
projection: pull each field from `UnifiedUserContext` after the
existing `authenticate_request` succeeds.
. **Cut a parallel** `auth_middleware_unified_port` that uses the port
and stores `PortUserContext` in `request.extensions`. Existing
`auth_middleware_unified` continues to work; consumers can opt in
to the port version when their code path is ready.
. **Migrate consumers** off `UnifiedUserContext` one site at a time.
Each migration either:
.. accepts `PortUserContext` and uses string-typed `roles` / `scopes`
fields directly, or
.. when typed permission checks are needed, re-deserializes
`effective_permissions_json` via the existing root-crate
`UnifiedPermission` schema.
. **Remove** `auth_middleware_unified` and the root-crate
`UnifiedUserContext` references from any code that has migrated to
the port path. The fully-typed `UnifiedUserContext` stays in the
root crate for paths that legitimately need it (e.g.,
`rbac_service`-internal permission evaluation).

Estimated effort: 3-4 commits for steps 1-3 (land the type + auth +
parallel middleware), then 1 commit per consumer site migrated in step
4 (~10-15 small commits depending on how aggressively typed-permission
sites are converted vs left on the typed path).

== Consequences

* The runtime crate gains exactly one new type (`PortUserContext`) and
one new trait method. No new wide surface.
* `UnifiedUserContext` is NOT deleted. It stays as the root-crate
"rich" context for permission evaluation, RLS predicate construction,
and audit logging. The boundary type is the port projection, not a
replacement.
* `effective_permissions_json` is opaque to the runtime — this is the
lossy bit. Callers that need typed permission objects continue to
use the root-crate path via `SecurityCoordinator` directly.
* gRPC `SecurityServiceImpl` in `proximadb-api` can finally call
`SecurityPort::authenticate` end-to-end without touching root-crate
types, completing Phase 9.11 for the gRPC side. The REST side
(currently `auth_middleware_unified` taking `Arc<SecurityCoordinator>`)
becomes a separate migration tracked in step 3.
* Task #69 in `docs/_internal/status/PHASE9_REMAINING_2026_05_25.adoc`
moves from "blocked" to "design done, implementation in flight" once
step 1 of the migration plan above lands.

== Rejected alternatives

=== Option (b): extract the full UnifiedUserContext graph into a shared crate

Pull `UnifiedUserContext`, `UnifiedPermission`, `UnifiedAuthMethod`,
the effective-permissions cache, session model, and capability scopes
all into a new `proximadb-security-context` foundation crate. Make
both the root crate's `SecurityCoordinator` and the runtime's
`SecurityPort` depend on it.

Rejected because:

* The dependency graph for the typed permission objects pulls in
RLS predicate types, audit-log schema, and capability-checking
machinery that legitimately belong with the security subsystem in
the root crate. Extracting them creates a crate that's effectively
"the security subsystem with no impl" — same proliferation problem
ADR-014 rejects for vector queries.
* The string + opaque-JSON projection (option a) gives the runtime
layer everything it actually needs (who, what tenant, what
roles/scopes) without the typed graph's complexity. Typed access
remains available via the root-crate `SecurityCoordinator` for the
paths that need it.

=== Option (c): make SecurityPort generic over the user-context type

`pub trait SecurityPort<U: UserContext>: Send + Sync { … }`. Each
deployment picks a `U` (root-crate `UnifiedUserContext`, mock context,
etc.).

Rejected because:

* `Arc<dyn SecurityPort>` becomes `Arc<dyn SecurityPort<U>>` and the
runtime crate cannot pick `U` for downstream consumers. Composition
falls apart.
* Generics over trait objects are awkward in the port-trait-object
composition pattern the rest of the runtime uses
(`Arc<dyn CollectionPort>`, `Arc<dyn DocumentPort>`, etc.).

== Governs

* `crates/platform/proximadb-runtime/src/security_port.rs` — new
`PortUserContext` type + new `authenticate` method on `SecurityPort`
* `src/security/security_coordinator.rs` — adds the lossy-projection
`impl SecurityPort::authenticate` body
* `src/network/auth/middleware.rs` — parallel `auth_middleware_unified_port`
* All ~20 `UnifiedUserContext` consumer sites — multi-session migration
following the recipe in step 4
