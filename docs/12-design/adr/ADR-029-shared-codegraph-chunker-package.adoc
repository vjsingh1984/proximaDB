== Context

=== The problem: the same code→symbol chunker exists (at least) twice, and a document chunker three times

A first-principles audit across the four repositories the author owns found the *code-aware chunker* — a tree-sitter parser that turns source files into code **symbols** (function/class/method/struct…) plus **relations** (CALLS/INHERITS/IMPLEMENTS/IMPORTS…) — independently implemented twice, and the *document chunker* three times:

[cols="2,3,2,3", options="header"]
|===
| Capability | ProximaDB | Victor | anvaiops
| **Code→symbol+relation chunker** (tree-sitter) | `clients/python/src/proximadb_sdk/chunking_strategies/code.py` (4,353 LoC; 23 langs registered; 18 symbol + 18 relation types; **no size-capping**; JS/TS parser is a **stub** returning empty symbols) | `victor-coding/victor_coding/codebase/{chunker.py,tree_sitter_extractor.py,tree_sitter_analysis.py,embeddings/chunker.py}` (Python-`ast` + tree-sitter; **size-aware**, body-aware sub-chunking; hierarchical IDs; Rust-accelerated sliding-window fallback; feeds a real CPG) | _none_ (planned: `ADR-0017` Phase F3 "code-graph-sync worker")
| **Document chunker** (fixed/sliding/semantic/heading) | `chunking_strategies/{fixed_size,sliding_window,sentence,paragraph,semantic,semantic_embedding,recursive}.py` | `victor-rag/victor_rag/chunker.py` (`DocumentChunker`: text/markdown/code/html/json) | `packages/connector-sdk/.../chunking.py` (`FIXED_WINDOW`/`SLIDING_WINDOW`/`PARAGRAPH`/`SEMANTIC`/`HEADING`/`JSON_PATH`/`XML_XPATH`/`ENTITY`)
|===

The two code chunkers are near-duplicate tree-sitter symbol+relation extractors. Per the CLAUDE.md
*Agentic Engineering* mandate, this is precisely the "silent duplication of an existing primitive"
failure mode — two diverging copies of one capability, each with a different bug surface (ProximaDB:
no size cap + JS/TS stub; Victor: the richer pipeline but coupled to the `victor-coding` vertical).

=== The roles are already fixed by existing design docs

* **ProximaDB** = the *generic* correlated store (relational+graph+vector over one `ProximaRecord`).
  `OSS_ENTERPRISE_BOUNDARY_2026_06_17.adoc`: OSS ships **capability + mechanism**, never commercial
  policy; the CI guard `scripts/check_oss_boundary.py` hard-blocks `anvai*` and commercial concepts in
  non-doc code. A code-domain AST parser is an *application* concern, not a generic-DB concern — it does
  not belong in the DB SDK long-term.
* **Victor** = the OSS terminal coding agent. Its durable memory is a Code Property Graph
  (`CODE_GRAPH_CORRELATED_SUBSTRATE_2026_06_22.adoc`): symbols as nodes+vectors, relations as edges.
  The chunker is squarely Victor's *domain* — and Victor already owns the most complete implementation.
* **anvaiops** = the SaaS/control-plane (its core product today is enterprise *ops-memory*; code-graph
  is a **planned vertical** on the same rails, `ADR-0017`, Phase F, gated by the "Code-Graph Dogfood"
  milestone). It owns tenancy, the KSU/KRU/KIU/KEU/KOU meter spine, RBAC, multi-repo orchestration —
  *policy*, not the parser.

=== Reference posture: what LlamaIndex `CodeSplitter` does and does not do

LlamaIndex `CodeSplitter` is a *size-bounded, AST-boundary-aligned text splitter* (`max_chars`,
`chunk_lines`, `chunk_lines_overlap`): it keeps chunks under a budget while respecting syntax, but
extracts **no** symbols, signatures, relations, or graph. It is the discipline ProximaDB's `code.py`
*lacks* (size-capping) and that Victor *has* (body-aware splitting). It is **not** a substitute for the
symbol/relation extraction both our chunkers do — it is the lower bound. The shared package must do
strictly more (symbols + relations + CPG projection) while adopting `CodeSplitter`'s size discipline.

== Decision

=== D1 — Extract one standalone, commercially-neutral PyPI package: `victor-codegraph`

Create a new package in the Victor family (the same `vjsingh1984/*` PyPI release topology as
`victor-contracts` / `victor-coding`), depending on **only** `victor-contracts` (zero-runtime-dep
protocol layer) + `tree-sitter` + the grammar packs. It is Apache-2.0, carries **no** SaaS/commercial
concept (so it never trips ProximaDB's OSS boundary guard), and exposes:

. **`parse(content, language, path) -> ParsedCode`** — the union of the best of both existing parsers:
  Victor's fallback chain (`python-ast → tree-sitter → config-aware → sliding-window`) and size
  discipline (body-aware sub-chunking above a token budget, à la LlamaIndex `max_chars`), plus
  ProximaDB's richer taxonomy (18 `SymbolType`, 18 `RelationType`, complexity metrics, docstrings,
  signatures, scope chains).
. **A neutral data model** — `CodeSymbol` / `CodeRelation` / `SourceLocation` (the intersection of the
  two existing dataclasses), carrying *deterministic* symbol IDs so incremental re-index is an
  idempotent upsert.
. **A projection adapter** — `to_proxima_records(parsed) -> list[...]` mapping each symbol to **one**
  `ProximaRecord` shape per the substrate keystone (`oid = graph/{repo}/node/{symbol_oid}`,
  `labels=["graph_node","code_symbol"]`, props = relational columns, `embeddings:[EmbeddingCell]`,
  edges as separate records). The adapter emits the *shape*; it does not embed or call the DB.

The package owns the chunker; embedding and storage stay with the consumer.

=== D2 — Each repo consumes the package; none re-implements

[cols="1,4", options="header"]
|===
| Repo | Change
| **Victor** | Promote `victor-coding`'s chunker + `TreeSitterExtractor` into `victor-codegraph` (it is the donor of record). `victor-coding` re-exports for back-compat, then depends on the package. Victor's embedded CPG (`proximadb_provider.py` swap seam) consumes `to_proxima_records()`.
| **ProximaDB SDK** | *Retire* `chunking_strategies/code.py` symbol-extractor. Add an **optional extra** `proximadb-sdk[codegraph]` that depends on `victor-codegraph`; the SDK keeps its generic *document* chunkers (those are legitimately generic) but stops shipping a code-domain AST parser. The generic DB SDK gets smaller and stays neutral. (TD-CG2)
| **anvaiops** | Phase F3 "code-graph-sync worker" (`ADR-0017`) sources `victor-codegraph` instead of writing a third parser; anvaiops adds **only** the SaaS layer (git-webhook ingest on the connector pattern, `{tenant}_{repo}_codegraph` routing, `EmbeddingMode::Cold` SQ8, KEU-code meter, per-repo RBAC). (TD-CG3)
|===

=== D3 — Dependency direction respects the boundary

The arrow points *into* the generic layers, never out of them:

----
  victor-codegraph  (Apache-2.0, neutral: tree-sitter + victor-contracts only)
        ▲                    ▲                         ▲
        │ import             │ optional extra          │ import (server-side)
   Victor (OSS agent)   ProximaDB SDK[codegraph]   anvaiops (SaaS, adds policy)
----

ProximaDB never depends on Victor or anvaiops. anvaiops depends on ProximaDB's SDK (already true) and
on `victor-codegraph` (new) — both neutral. No commercial concept crosses into OSS; the
`check_oss_boundary.py` guard stays green because the package is policy-free.

== Design principles — the "best posture" for agentic-AI-coding chunking (synthesized)

Distilled from Victor's measured CPG trace, ProximaDB's substrate spec, and LlamaIndex `CodeSplitter`:

. **Chunk at *symbol* granularity, not statement and not fixed-size.** Measured: a real repo is 1.26M
  nodes but only **79,744 symbol nodes** carry the traversable graph; embeddings live at symbol
  granularity (77,902 vectors). Embed functions/classes/methods, not statements.
. **Align to AST boundaries *and* cap size.** Never split mid-statement (both our parsers do this); but
  also bound chunk size and body-split oversized symbols (Victor + LlamaIndex do this; ProximaDB's
  `code.py` does **not** — the headline gap to fix in the merge).
. **Extract relations, project to a CPG.** A chunk is not just text — emit CALLS/IMPORTS/INHERITS so the
  agent answers "who calls X / blast radius" from a graph instead of re-reading files.
. **Deterministic IDs + content hash → idempotent incremental re-index.** A file change is a single
  upsert keyed by deterministic symbol id; the watch-daemon/webhook re-runs one file. Hierarchical IDs
  (`module:Class.method:body:idx`) disambiguate body sub-chunks (Victor's pattern).
. **Co-store snippet + embedding on the symbol record** so a code edit rewrites text *and* re-embeds in
  one atomic `record_version` bump (substrate keystone — retires the `embedding_ref` drift).
. **Graceful fallback chain**, never hard-fail: `ast → tree-sitter → config-aware → sliding-window`.
. **Token budget matched to the embedding model** (BGE-small 384-d → ~512-token chunks), not an
  arbitrary char count.

== Alternatives considered

* **A2 — Keep the chunker in the ProximaDB SDK; Victor + anvaiops depend on the DB SDK.** Rejected:
  inverts the boundary (pushes code-domain logic into the generic DB), and makes the OSS coding agent
  depend on the database SDK to chunk its own code. Contradicts "ProximaDB stays generic."
* **A3 — Promote in-place inside `victor-coding`; others depend on the whole vertical.** Rejected:
  drags `victor-coding`'s heavier surface (and its `victor-sdk`/runtime deps) into ProximaDB and
  anvaiops just to get a parser. The standalone package keeps the dependency hair-thin.
* **A4 — Do nothing (let three copies drift).** Rejected: the duplication is already causing divergent
  bugs (ProximaDB JS/TS stub vs Victor's working multi-lang) and three maintenance surfaces.

== Consequences

* **Positive:** one chunker, three consumers; ProximaDB SDK shrinks and stays neutral; Victor keeps
  ownership of its domain; anvaiops Phase F3 is sourcing not building; the OSS/SaaS boundary holds; the
  JS/TS stub and the missing size-cap are fixed *once*.
* **Negative / cost:** a new repo + release pipeline (`victor-codegraph-v*`); a migration window where
  `code.py` is deprecated-but-present; a contract to keep `to_proxima_records()` in lockstep with the
  `ProximaRecord` shape (mitigated: the substrate keystone already pins that shape).
* **Neutral:** the *document* chunker triplication (ProximaDB ⊕ victor-rag ⊕ anvaiops connector-sdk) is
  **out of scope here** but noted as a follow-up — a second shared package (`victor-docchunk`) or
  consolidation is a separate ADR.

== Migration (phased, mixed-read-safe)

. **TD-CG1** — Stand up `victor-codegraph` by promoting `victor-coding`'s chunker; port ProximaDB's
  richer taxonomy + the `to_proxima_records()` adapter; add size-capping; fix the JS/TS parser. Ship
  with round-trip + recall-parity tests (per CLAUDE.md storage-migration mandate, even though this is a
  library) and an **eval suite** for the ranked/extracted surface (CLAUDE.md mandate 13).
. **TD-CG2** — ProximaDB SDK: add `[codegraph]` extra → `victor-codegraph`; deprecate `code.py` with a
  shim that re-exports + warns; delete after one minor release.
. **TD-CG3** — anvaiops F3 worker imports the package; adds SaaS layer only. Gated behind ADR-0017
  Gate #1.

== Verification

* Parity test: the merged parser reproduces both donors' outputs on a fixed corpus (Python/Rust/Go/Java
  deep; JS/TS now non-empty).
* Boundary: `scripts/check_oss_boundary.py` stays green (package is policy-free; ProximaDB gains no
  `anvai*`/commercial reference).
* Substrate: `to_proxima_records()` output round-trips through `EmbeddedProximaDB` and reproduces the
  `tests/embedded_code_graph_parity_e2e.rs` impact_analysis/fusion_search results.
