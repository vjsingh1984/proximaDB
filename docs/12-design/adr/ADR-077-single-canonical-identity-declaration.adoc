= ADR-077: One canonical identity declaration per table
:status: Accepted (2026-07-28) — M1 implemented
:date: 2026-07-28
:authors: foundation session 2026-07-28
:amends: ADR-072 D1 (catalog as the governance seam)
:tracked-by: TD-CAT-6

== Context

ADR-072 **D1** ratified that *"constraint/index enforcement is written **once against
the metamodel**"*, and made that the justification for `ConditionalKeyStore` being
modality-agnostic: *"uniqueness on the entity's identity key" is a metamodel concept.*

The implementation does not match. `CatalogTableSchema` lets one fact — *what identity
does this table declare?* — be written to **six** places:

[cols="3,2,2"]
|===
| Location | Written by | Read by

| `schema.primary_key` | most creation paths, evolution | record_store, fc_metamodel, pgwire, introspection
| `relational_capabilities.primary_key` | **one** site (CREATE TABLE) | `relational::effective_primary_key`, table_write_plan
| `relational_capabilities.unique_indexes` | **one** site (inline `UNIQUE(...)`) | the enforcement path
| `relational_capabilities.constraints[Unique]` | CREATE TABLE + ALTER | the enforcement path
| `schema.indexes[].is_unique` | CREATE INDEX, ALTER ADD CONSTRAINT | fc_metamodel, introspection
| `properties["constraint:unique:…"]` | ALTER ADD CONSTRAINT | nothing
|===

Nothing validated agreement between them, and no consumer read all of them. The
consequences were not hypothetical:

* **`ALTER TABLE … ADD CONSTRAINT … UNIQUE` was cataloged and never enforced** — the
  write and the read touched disjoint fields. Fixed in the S0 commit of TD-CAT-6.
* **Renaming a PK column left a stale primary key** in the capabilities copy, which
  `effective_primary_key` *prefers* — so row validation resolved a column that no longer
  existed. Fixed likewise.
* **`DROP CONSTRAINT` leaked its property row**, because the key is derived from columns
  and the filter matched on the constraint *name*.
* **Five different answers to "what is the primary key"**, with different precedence and
  fallbacks, across `record_store`, `relational`, `table_write_plan`,
  `relational_pipeline`, and introspection.
* **`relational_capabilities.secondary_indexes` has zero non-test writers** — the
  TD-127 secondary-index path is dead in production because `CREATE INDEX` writes
  `schema.indexes` instead.

TD-CAT-6 established *why* this is structural rather than careless: the canonical answer
lived in the root crate, `control → root` is forbidden by the layering guard, so every
lower layer was **forced** to re-derive. Its slice 1 put discovery in the catalog crate
(`schema::table_identity`), which stops the readers diverging.

**That fixes the readers. It does not fix the writers.** Six writable locations with no
invariant is a generator of the defects above: each new writer picks a field, each new
reader picks a subset, and nothing makes disagreement impossible.

== Decision

**One canonical location per identity fact. Every other location becomes derived or is
removed, so an inconsistent schema becomes unrepresentable.**

. **Primary key** — `schema.primary_key` is canonical.
  `relational_capabilities.primary_key` is removed from the write surface and, while it
  must still deserialize, is never read for a decision.
. **Uniqueness** — `relational_capabilities.constraints` (the `ColumnConstraint::Unique`
  form) is canonical, because it is the only representation that survives without a
  constraint name and is already what the enforcement path reads.
  `relational_capabilities.unique_indexes` and `schema.indexes[].is_unique` become
  *projections* maintained for introspection (pg/JDBC surfaces genuinely want an index
  view), never sources of truth. The `properties["constraint:unique:…"]` blob is retired.
. **Writes go through one constructor**, not by assigning fields. Identity declarations
  are set via a method on the schema that maintains every projection together, so a
  partial update is not expressible.
. **`validate_schema` enforces the invariant** — already tightened in TD-CAT-6 S0 to
  reject a disagreeing primary key; extended here to reject any projection that disagrees
  with its canonical source.

`schema::table_identity` (TD-CAT-6 S1) is the **migration shim**, not the destination.
It exists to read the pre-migration shapes; once the collapse lands, it reads one field
and its four-route fallback logic is deletable.

== Migration (amended 2026-07-28 — the original five phases were mis-specified)

[IMPORTANT]
====
**The first draft of this section applied the wrong pattern.** It treated the collapse as
a *storage-format* change and prescribed CLAUDE.md §8's five-phase dance. That pattern
exists for changes where old and new bytes are **mutually unreadable** — a block format, a
codec, a magic byte. This is not one of those, and the phasing bought nothing.
====

=== Why there is no byte-level incompatibility

`CatalogTableSchema` is JSON (`serde_json`), derives plain `Deserialize` with **no
`deny_unknown_fields`**, and carries `#[serde(default)]` on `relational_capabilities`
(`lib.rs:662`). Therefore, as long as the legacy fields remain declared on the struct:

* **old bytes → new code**: the legacy fields still exist, so they deserialize;
* **new bytes → old code**: `#[serde(default)]` fills whatever is absent.

The repo already relies on exactly this and pins it: `lib.rs:4262` deserializes a minimal
legacy schema and asserts *"legacy schema must deserialize"*. Mixed-read-safety for this
type is **already structural** — serde provides it, at no cost, permanently.

A flag day is therefore not reachable. Phasing to avoid one is ceremony.

=== The real risk is semantic, and phasing does not address it

The genuine hazard is **silent semantic loss**, not a parse failure: a schema whose UNIQUE
lives only in `relational_capabilities.unique_indexes`, read by code that consults only
`relational_capabilities.constraints`, loses the constraint — quietly, exactly as
`ALTER … ADD CONSTRAINT … UNIQUE` did before TD-CAT-6 S0.

Deploy phasing does nothing about that: every phase still has *some* reader consulting a
subset of locations. The correct mitigation is **normalize on load** — fold every legacy
location into the canonical one at the deserialization boundary, which is
`schema::table_identity` applied once where schemas enter memory (`native.rs:708/723`,
`oltp.rs:369`). After that point no reader can see a pre-canonical shape, so no reader can
miss a declaration.

=== The one thing pre-release genuinely changes

Not read-compat — **rollback**. Once normalized schemas are written, an *older* binary
reading them would find the legacy fields empty and the canonical field unrecognized, and
would lose the declaration. That is the only scenario the five phases actually protected,
and it is a rollback scenario, not an upgrade one.

Pre-release (v0.2, no supported downgrade path) makes that acceptable. But it need not be
relied on, because the mitigation is nearly free:

**Keep writing the projections.** Decision 3 already routes all identity writes through
one constructor that maintains every projection together. Having it keep populating
`unique_indexes` / `indexes[].is_unique` costs one function body and is wanted anyway —
the pg/JDBC introspection surfaces legitimately need an *index* view of a UNIQUE
(`catalog-introspection/src/lib.rs:538/807/1100`). Write-both is not a migration phase
here; it is the steady state.

=== Amended plan

[cols="1,3"]
|===
| Step | Content

| **M1** (one PR) ✅ **implemented**
| `schema::normalize_identity` folds every discovered UNIQUE into the canonical field — additively, so the index names and types the projections carry survive — and runs inside `apply_evolution`, so the backfill happens *on touch* rather than in an offline pass. `CatalogTableSchema::with_unique` is the single write constructor, maintaining canonical + projection together. `validate_schema` rejects a projection holding a UNIQUE the canonical field lacks (the "cataloged but never enforced" shape), while allowing canonical *without* a projection — an unnamed UNIQUE has no index form to project into.

**Correction found while implementing:** this section first said normalize *on load*. That was wrong. `validate_schema` is called on **write** paths only — the seven `create_table` sites plus `apply_evolution` — and **never on load**, so a legacy schema is never rejected merely for being read. Normalizing on load would have addressed a problem that does not exist while missing the one that does; the hook belongs in `apply_evolution`, before validation.

| **M2** (optional, GA or never)
| Remove the legacy fields from the struct. Only worth doing if the projections stop being useful to introspection — which today they are not, so **the honest expectation is that M2 never happens**.
|===

Net: **one PR, not five**, with *better* safety than the original plan — normalize-on-load
closes the semantic-loss hole that phasing left open, and write-both removes the rollback
exposure that phasing was actually there to manage.

=== What this means for CLAUDE.md §8

§8's mixed-read-safe mandate is not waived; it is **satisfied by construction** here
(serde defaults + retained fields + normalize-on-load) rather than by a version/magic-byte
handshake. The lesson worth carrying: §8's phased pattern is the right tool for *encoding*
changes; for a change that only redistributes *which field holds a fact*, the right tools
are normalize-on-load and a single write constructor. Reaching for the heavier pattern by
reflex cost this ADR a 5× overestimate of the work.

== Consequences

**Positive.** The class of defect above stops being expressible rather than being fixed
case by case. ADR-072 D1's "written once against the metamodel" becomes true of the
implementation. The identity slot's role model (`UniquenessPrimary` vs
`UniquenessSecondary`) can then feed the CKS directly, which is what lets the write path
distinguish *0 extra durable writes* (PK — the `oid` **is** the key, D3) from *1 write +
coordination* (secondary UNIQUE) — a distinction a flat column-name list cannot carry, and
which the current code encodes in control flow that admits it only handles single-column
PKs.

**Negative.** "One location" means one **source of truth**, not literally one field:
introspection surfaces legitimately want an *index* view of a UNIQUE, so the projections
stay and must be kept in sync by the write constructor. That is a standing obligation, not
a one-off migration — a future writer that sets a field directly rather than through the
constructor can still desynchronize them, which is why `validate_schema` must reject a
disagreeing projection rather than trusting discipline.

**Risk if deferred.** Every new consumer must rediscover six locations; the census already
found five disagreeing PK rules and one dead code path. The cost compounds with each
modality that stacks on the catalog — which is precisely the surface D1 exists to protect.

== Alternatives considered

* **Keep `table_identity` as the permanent answer.** Cheapest, and it fixes the readers —
  but writers can still produce inconsistent schemas, so the accessor is papering over a
  representable-invalid state. It is the right shim, not the right end state.
* **Validation only** (reject disagreement, keep all six fields). Turns silent corruption
  into loud failure, which is better, but pushes the burden onto every writer forever and
  makes legitimate partial writes (most creation paths leave `relational_capabilities`
  empty) hard to distinguish from bugs.
* **Collapse in one commit.** Originally rejected on the grounds that "the type is
  persisted, so a flag day would make schemas written by the previous version unreadable."
  **That reasoning was wrong** — serde defaults plus retained fields mean old schemas stay
  readable regardless (see the amended Migration section). With normalize-on-load and
  write-both, a single-PR collapse is both feasible and safer than the phased plan. This
  is now the chosen approach (M1).
