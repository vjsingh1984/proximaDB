| link:ADR-032-durable-tenant-prefixed-object-store-catalog.adoc[ADR-032]

| Proposed

| link:ADR-033-primary-storage-format-strategy.adoc[ADR-033]
| Primary Storage Format Strategy — own the vertical (PAX) where it pays, keep Parquet at the interop seam
| Proposed
| An adversarially-verified survey (22 sources; Postgres/InnoDB/Oracle-HCC/Aurora/Neon + ClickHouse/Snowflake/BigQuery/Delta/Iceberg/Lance/Turbopuffer) settles the "why Parquet, not our own format" question: **no serious engine uses Parquet as primary** — all own a co-designed format and expose open formats only at the interop edge. But the win is **workload-specific**: custom formats beat Parquet **100×+ on random-access / vector / selective** queries and **< 2× on sequential OLAP scans**, and Parquet-as-primary is genuinely right for lakehouse/Iceberg interop. Decision: the **dual-path is vindicated** — keep Parquet as the relational-scan + interop primary (not demoted to export), and spend the PAX budget on the vector/random-access path via **object-storage round-trip minimization** (Turbopuffer's ≤3-round-trip budget; Parquet's footer amplification is the measured anti-pattern) and **format⇄index co-design** (the Lance pattern). Recasts **TD-162a-2**: its worth is unifying relational+vector storage, enabling the Native cost-router arm, and zone-map/projection pruning on selective queries — *not* chasing scan-throughput parity (already < 2×). Adds a **first-principles cost spine** (latency = dependency-DEPTH × RTT; **depth ≫ width ≫ bytes ≫ CPU**) and an **egress correction** (egress = the customer result only; object-store reads are internal; quantization is a residency/round-trip lever, not egress). Tracked: TD-162a-2

| link:ADR-034-objectstore-access-path-codesign.adoc[ADR-034]
| Object-Store Access-Path Co-Design — minimize dependency depth
| Proposed
| Applies ADR-033's cost spine to the *access path*. A map of the real PAX format found the layout sound but the read path reproduces Parquet's failure internally: a pruned ranged read is **`1+3K` serial dependent GETs** (segment-index → per-block footer → per-block col-meta → per-block body), and graph traversal pointer-chases cold object storage (no RAM topology). Records 8 derived principles (depth-first; predictive/cached metadata; large-outside/fine-inside; codes-only residency; **graph = the adversarial workload → topology in RAM + batched frontier**; criticality tiering; round-trip budget as a planner constraint; LSM with free delta detection) and six ROI-ordered gap-closure decisions: **TD-167** read-path depth collapse (zone-map summary in `SegmentIndex` + `read_ranges` body-batching → depth ~1-2), **TD-168** graph topology RAM index, **TD-169** segment code region, **TD-170** round-trip budget, **TD-171** criticality tiering, and TD-162a-2 (typed stripes, last — < 2× scan). All additive, mixed-read-safe, GET-count-harness + recall-ratchet gated. Tracked: TD-167..171, TD-162a-2

| link:ADR-035-per-tenant-system-catalog-cache.adoc[ADR-035]
| Per-Tenant System Catalog — two-group object layout + 3-tier read cache + provisioning lifecycle
| Proposed
| Resolving a collection's metadata costs **1+N+M object-store GETs** on a cold cache (`list_namespaces` + per-ns `list_tables` + per-table `get_table`), re-paid after every pod restart — the wrong bill on the hot path. Decision: (D1) split the per-tenant system catalog into two object-store groups — **METADATA** (read-heavy registry, keyed by global `u64` object_id since names collide across tenants: `_syscat/objects/{oid}.json` + a `name→oid` index) and **OPERATIONAL** (write-heavy append: `_metering`/`_trace`/`_billing`, TD-161). (D2) a **3-tier read path** — hot in-memory `TenantCache` (≤1 MB/tenant, 5-min TTL, corpus-version-stamped) → warm local disk (OS page cache) → canonical object store. (D3) a **provisioning lifecycle** — signup pre-creates a bare-minimum skeleton, user DDL appends system-managed rows. (D4) hydration triggers — pgwire session-ready warm + lazy warm-on-first-miss for the stateless edges. Composes existing `TenantCache`/`CorpusVersionRegistry`/`CacheInvalidationCoordinator`/`IdAllocator`. Full read/write/provision/pod-start/invalidation branch table. Mixed-read-safe; default-on read accelerator first. Tracked: TD-SC-1..5; depends on ADR-032/TD-CAT-2.

| link:ADR-036-azure-objectstore-orientation.adoc[ADR-036]
| Azure / Object-Store Orientation — one account, Blob endpoint, flat keys, HNS-off, access-tier as the cost lever
| Proposed
| Re-orients the code to Azure ground truth after the MVP work found we registered four schemes (`adls`/`abfs`/`az`/`azure`) as if distinct, titled the backend "ADLS Gen2", and **silently dropped** the per-object access tier (every cloud `write` ignored `FileOptions`). Truth: one Storage account, **Blob endpoint** (flat keys) + an optional DFS endpoint *only* under Hierarchical Namespace; **ADLS Gen2 = Blob + HNS**; our four schemes all resolve to the *same* flat Blob backend, so `adls`/`abfs` were misleading (never engaged ABFS/DFS/HNS). The **cost lever is the access tier** (Hot/Cool/Cold/Archive), a property of the PUT available on a **flat (HNS-off)** account — HNS is a cost add, not a benefit, for our flat-key/immutable/ranged-read workload. Decisions: run flat Blob HNS-off (default cold = Cool/Cold tier); plumb a **canonical cloud-neutral `ObjectAccessTier`** (`hot`/`cool`/`cold`/`archive`) through `FileOptions.storage_class` → `object_store` `Attribute::StorageClass` (Azure `x-ms-access-tier` + S3 `x-amz-storage-class`), default-safe on unset/typo; scheme honesty (`az`/`azure` canonical, `adls`/`abfs` documented Blob aliases + one-time INFO log). GCS + `ProximaObjectStore` tier deferred (need backend-aware mapping; not the MVP path). Additive, no flag-day, moves the **at-rest GB-month** cost term (not the round-trip count). Tracked: TD-173

| link:ADR-039-olap-engine-boundary-swappable-physical-backend.adoc[ADR-039]
| OLAP Engine Boundary — DataFusion is a swappable physical backend behind the shared `LogicalNode` seam
| Accepted
| Ratifies + freezes the (audited 2026-06-27) design that makes DataFusion swappable as a *backend*, not a rewrite: the SQL frontend emits ProximaDB's own engine-neutral `LogicalNode` IR (relational crates carry **zero** DataFusion deps); DataFusion lowers `LogicalNode → datafusion::LogicalPlan` inside `src/datafusion/**` only; results come back as Arrow → `RelationalRow`/`ProximaValue` (pgwire never sees a DataFusion type); scalar functions are defined **once** in `proximadb-functions` and merely *bound* per engine; DataFusion is an optional cargo feature with the native Volcano path as the floor. Dispatch is `dyn`/enum at the **per-query** seam — coarse, so the runtime bears no per-row cost (no engine generics threaded through the pipeline). Tracked: TD-181

| link:ADR-040-conformance-accuracy-ratchet.adoc[ADR-040]
| Conformance ratchets are ACCURACY ratchets — differential cross-engine + anchored answers, not "executes cleanly"
| The pgwire conformance ratchets (TPC-H 22, TPC-DS 16, graph 10, doc 11, ts 10) count queries that **execute without error**, not queries that return **correct answers** — only ~1 query per suite has its result asserted (TPC-H verifies Q1; the other 21 are execution-only). So the ratchet measures the *demo*, not the *eval* (against mandates #10/#13). The dual-engine cost-trace harness (PR #455), running each query on native AND DataFusion, proved this lets wrong results pass: `document` `d04/d08/d10` return **0 rows** (JSON-path SELECT projection silently empty) while `count(*)` shows the table non-empty; `g04` returns 16 rows native vs 32 DataFusion; `d06` 0 vs 1. *Decision:* a query counts only when verified correct by (1) **differential cross-engine equivalence** (native ≡ DataFusion after canonicalization — disagreement fails CI; near-free, no hand-grading) and/or (2) **anchored expected answers** (required for one-engine-only queries; catches "both wrong the same way"). Ratchet counts *accurate* queries, not merely executed. External Postgres/DuckDB oracle deferred. Phased rollout, one suite per PR (document first — pins the known JSON bug), each filing the bugs it uncovers. Tracked: TD-182

| link:ADR-042-canonical-segment-statistics-contract.adoc[ADR-042]

| Proposed

| link:ADR-043-unified-relational-expression-evaluation.adoc[ADR-043]
| Unified relational expression evaluation — one cast lowering, one function definition per binding, fail-loud predicate contract
| Accepted
| TD-183 (document JSON-path) had to be "fixed" in four code paths because predicate/scalar evaluation is fragmented: **4 disagreeing cast mechanisms** (translator string-strip with a hard-coded suffix list that forgot `::int` and over-strips `::boolean`; a frontend `lower_expr` with **no `Cast` arm**; a partial native `cast_value`; a fuller-but-unreachable DataFusion matrix), **3 function "registries"** (canonical `builtins()`, an empty `NoFunctions` at the pushdown boundary, and JSON funcs defined **only** as DataFusion UDFs so native lacks them), and **2 error contracts** (operators propagate via `?`, but the storage-pushdown predicate is a `Fn(&[ProximaValue]) -> bool` closure that coerces eval errors to `false` → **silently drops rows** = a wrong answer that looks like success). *Decision:* three normative invariants — (1) **never silently drop on eval error** (type the pushdown closure `-> Result<bool, ExprError>`, propagate like `FilterExec`); (2) **one cast lowering owned by the typed frontend** (add the `Cast` arm, delete the translator strip list, fill `cast_value` gaps); (3) **one function definition per binding** (move JSON kernels into `proximadb-functions`; F2 auto-binds DataFusion; native gets them free; engine-only scalars prohibited except listed Arrow specials). SOLID for an OLTP+OLAP hybrid: fail-loud + single-definition let an engine that can't serve a query escalate (ADR-039) instead of returning a plausible wrong answer. Surfaced by the ADR-040 accuracy harness. Tracked: TD-186

| link:ADR-051-strong-freshness-default-cheap-under-concurrency.adoc[ADR-051]

| Proposed
| Answers "should typed `/search` stop defaulting to Strong?" — **no.** D1: Strong stays the default (a deliberate, test-asserted read-after-write contract, `default()==Strong`, added because an INSERT→SEARCH visibility gap was a prod bug; matches turbopuffer); weakening globally is rejected — per-collection opt-out is TD-074. | Proposed
| Diagnosis (grounded in a 3-agent code investigation + 4-agent adversarial review, 2026-07-10): the router conflates **eligibility** (a soundness question — *can* engine E serve query Q over storage S?) with **selection** (a cost question — among eligible engines, which is cheapest?).
