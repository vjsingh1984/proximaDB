= Catalog-on-object-store design review — ProximaDB vs Polaris / Horizon / open catalogs (2026-07-14)
:toc: macro

Reviewed against: Apache Polaris (incubating), Snowflake Horizon, the Iceberg
REST commit protocol, HadoopCatalog, Project Nessie, Delta Lake's `_delta_log`,
Unity Catalog OSS, Apache Gravitino, and the post-2024 conditional-PUT
object-store-native catalogs (Boring Catalog, SlateDB, AWS S3 Tables).
Companion change: the TD-OBJSTORE-1 catalog batch (scheme-generic wiring +
`adls://`/`gcs://` alias normalization + DeltaCatalog object-store persistence).

toc::[]

== How the field stores catalog metadata

[cols="2,3,3", options="header"]
|===
| System | Backing store | Commit/concurrency algorithm

| Apache Polaris
| Transactional RDBMS (JDBC/PostgreSQL; EclipseLink deprecated; design
  descends from Snowflake's FoundationDB assumptions)
| Versioned *entities*; every update is an entity-version compare-and-swap.
  The Iceberg table pointer is just a CAS'd entity attribute.

| Snowflake Horizon
| FoundationDB (ordered KV + object-mapping layer), triple-replicated
| Serializable ACID transactions in FDB; governance/policy layers above.

| Iceberg REST protocol
| server-defined (any)
| *Change-based* commits: client sends `requirements` + `updates`; the server
  CASes the metadata pointer and can auto-rebase disjoint updates. ETag/
  `If-None-Match` freshness on reads (304 ⇒ no payload).

| HadoopCatalog (anti-pattern)
| object store directly (`metadata/v{N}.metadata.json` + `version-hint.text`)
| Atomic RENAME — which S3 lacks; concurrent writers can clobber. Deprecated.

| Project Nessie
| pluggable KV/RDBMS (RocksDB, DynamoDB, Cassandra, JDBC…)
| Git-like commit graph: immutable hash-keyed commit objects written
  optimistically, then ONE CAS of a global branch-heads pointer ⇒
  multi-table atomic transactions by construction.

| Delta Lake
| the log IS the catalog: `_delta_log/{N:020}.json`
| put-if-absent on the next numbered slot = the whole protocol; Parquet
  checkpoints + fixed-key `_last_checkpoint` bound cold-load LIST/replay.
  (Pre-conditional-PUT S3 needed a DynamoDB mutex; native ETag CAS since
  late 2024.)

| Unity OSS / Gravitino
| RDBMS (PostgreSQL/MySQL; H2 dev)
| DB transactions; no object-store-native mode.

| Boring Catalog / SlateDB / S3 Tables
| object store ONLY
| single small pointer object committed with `If-Match` ETag CAS
  (`object_store::PutMode`); conflict ⇒ refresh + retry.
|===

== Where ProximaDB stands (verdicts)

**The production authority already matches the state of the art.** The
`SystemCatalog` (ADR-048) serves reads from RAM, persists each DDL as one
fsync'd local WAL append, and publishes its snapshot through
`ObjectStoreSnapshotStore` → `ManifestCommitter`: immutable, monotonically
versioned manifest objects claimed by **create-only put (put-if-absent CAS)**
with an 8-byte **generation fence** (the Neon `index_part.json` model).
That is exactly the Nessie/Delta commit kernel — immutable content + one CAS'd
advance — and *stronger* than Polaris' RDBMS entity-CAS for our deployment
shape, because it needs no database sidecar. Multi-pod coherence is the
Phase 6b follower poll over `latest_version` (a version check, no payload
fetch — equivalent in spirit to Iceberg REST's ETag/304 flow).

**What was actually broken was wiring, not architecture** (fixed in this PR):

1. `shared_services` gated the durable path on a scheme allowlist missing
   `adls://`/`abfs://`/`azure://`/`gcs://` — Azure deployments silently fell
   back to `NativeCatalog`'s temp-cache staging.
2. `store_for_url` forwarded ProximaDB's documented `adls://`/`gcs://` aliases
   to the upstream parser, which does not know them (it knows
   `az|adl|azure|abfs|abfss` and `gs`) — so even the fenced snapshot store
   could not open on those spellings.
3. `CatalogManager::create_native_catalog` had the same allowlist; now both
   native and delta creation share one scheme-generic
   `resolve_object_store_fs`.
4. `DeltaCatalog` staged ALL cloud metadata in `$TMPDIR` — now persists
   through the injected `FileSystem` (TD-CAT-4; CAS follow-up listed there).

== Algorithms & data structures assessment

[cols="3,2,3", options="header"]
|===
| Ours | Verdict | Notes vs field

| `ManifestCommitter` versioned put-if-absent + generation fence
| ✅ Right primitive
| Identical class to Delta slot-claim + Nessie pointer-CAS; fencing is ahead
  of most open catalogs (resurrected-writer safety).

| `latest_version` via LIST (no tip pointer)
| ✅ Acceptable, *by decision*
| "Never LIST for latest" (Delta `_last_checkpoint`, Nessie global pointer)
  was weighed in-repo and rejected: a mutable tip pointer reintroduces the
  lost-update/ABA hazard the create-only protocol avoids, and TD-MANIFEST-1
  retention pruning bounds the LIST to ≈`keep_k` objects — one paginated
  round trip. Matches Delta's checkpoint-bounded tail in cost shape. Revisit
  only if follower-poll LIST spend shows up in the KRU/KOU trace.

| Iceberg REST *change-based* commit (`requirements`+`updates`)
| ◻ Not adopted (deliberate)
| Our snapshot payload is opaque bytes; conflicts surface to the single
  writer, which re-snapshots from RAM. Auto-rebase adds value only with
  many concurrent DDL writers — not our deployment model (generation fence
  enforces single-writer). Note for a future multi-writer control plane.

| `CatalogCache` 4× `RwLock<HashMap>` + TTL, LRU by full scan at capacity
| ⚠ Fix filed
| O(n) victim scan on insert-at-capacity under the write lock → TD-CAT-5
  (O(1) LRU / sampled eviction / sharding — measure first).

| `NativeCatalog` full-file JSON rewrite per DDL, dual-write (name + oid),
  last-writer-wins, no CAS
| ⚠ Superseded-by-design
| The ADR-048 cutover (SystemCatalog authority) is the strategic fix; do not
  retrofit CAS into NativeCatalog. It remains the `file://` default and the
  `PROXIMADB_DISABLE_SYSTEM_CATALOG` kill-switch target.

| `DeltaCatalog` single-JSON pointer, last-writer-wins
| ⚠ Follow-up filed
| Same shape as Boring Catalog *minus* the ETag CAS — safe single-writer;
  TD-CAT-4 lists the CAS/checkpoint follow-ups.

| Per-tenant sharding of commit logs (`DrPathBuilder` prefixes)
| ✅ Ahead of field
| Pointer-per-tenant/collection means writers never serialize on one global
  key — the scaling weakness of single-pointer catalogs; aligns with the
  co-design tenant-isolation mandate structurally.
|===

== Non-goals / rejected

* **RDBMS/FoundationDB sidecar (Polaris/Horizon model)** — wrong dominant cost
  term for a single-VM/object-store deployment: adds an always-on service and
  a second durability domain to operate; our fenced manifest log gets the same
  CAS semantics from the store itself.
* **Mutable tip pointer for `latest_version`** — see table (decided in
  `manifest.rs` prune docs).
* **HadoopCatalog-style rename commits** — never; rename is not atomic on any
  of our target stores.
