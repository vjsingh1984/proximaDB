[.lead]
This is the **single pane of glass** for ProximaDB. It exists to answer one question fast — "where does
a thing live, and what does it converge on?" Current manifest reality: 66 workspace members, 61 crates
under `crates/`, and 46 real top-level `src/` module directories. It is navigation-first: it does not
duplicate the per-module detail in the feeder docs, it indexes and ties them together so they stop
diverging.

[IMPORTANT]
====
**Why this doc exists.** The codebase grew three partially-overlapping whole-system maps
(`ARCHITECTURE_ATLAS_2026_05_22`, `MODULE_COMPONENT_LLD_2026_05_22`, `docs/05-concepts/architecture.adoc`).
Each is correct but none is canonical, so they drift. This doc is declared the apex; the three become
subordinate feeders. New whole-system diagrams belong here or in a feeder linked from here — **not in a
fourth competing map**. That rule is itself a convergence gate (see
link:CONVERGENCE_AUDIT_2026_05_30.adoc[CONVERGENCE_AUDIT_2026_05_30]).
====

== How to use this map

* Need the *system shape and ownership boundaries*? Start at <<workspace>> then <<feeders>>.
* Need *where a `src/` module lives and what it does*? <<srcmap>>.
* Need *how a write or read flows end to end*? <<writepath>> / <<readpath>>.
* Need *why four protocols don't mean four truths*? <<convergence>>.
* Need *where the known divergent seams are*? <<seams>>.

`Foundation -> Contracts -> Control -> Horizontal -> Modality -> Storage -> Query/Cross-Model -> Platform -> Apps/Bindings`.
Crates are added only for real dependency or ownership payoff.

[#convergence]
== Layer 4 — Protocol-facade → canonical-authority convergence

Four wire protocols are *facades*, not authorities. They lower into the same canonical record + WAL +
catalog chain. This is the load-bearing invariant the whole architecture rests on: proliferation is
allowed at the edge, never in the durable core.

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
flowchart TB
  classDef edge fill:#cfe2f7,stroke:#2e5c8a,color:#000;
  classDef core fill:#4a90e2,stroke:#2e5c8a,color:#000;

  R1[REST v1]:::edge --> SVC
  R2[REST v2]:::edge --> SVC
  GR[gRPC]:::edge --> SVC
  AF[Arrow Flight]:::edge --> SVC
  PG["pgwire 5433<br/>(pgvector compat)"]:::edge --> SVC

  SVC["services/ (shared)"]:::core --> REC["ProximaRecord<br/>ProximaType / ProximaValue"]:::core
  REC --> WAL["canonical WAL"]:::core
  WAL --> XC["xCatalog (durable authority)"]:::core
----

== Where the seams are

This map is the apex; it points at the live divergent seams rather than hiding them. The authoritative
catalog with reconcile directions and queued TD items is
link:CONVERGENCE_AUDIT_2026_05_30.adoc[CONVERGENCE_AUDIT_2026_05_30]. Summary:

[cols="2,3", options="header"]
|===
| Seam | One-line status

| Phase 9 handler/service extraction
| Real impl in `src/api_handlers/request_handlers.rs`; `proximadb-runtime/src/handlers.rs` is a stub. Migration in progress.

| Deprecated gRPC shims
| `src/network/grpc/*_service.rs` deprecation shims; real impls migrated. Removal targeted for v0.2 (pulls forward from the code's `0.3.0` markers).

| Proto-v1 internal mirrors
| `VectorRecord`/`SqlValue`/`SqlObject` still used internally; canonical is `ProximaRecord`/`ProximaValue`.

| Scattered configs
| RESOLVED 2026-06-05 at the app-config seam; connector/runtime-local specialization remains local.

| PlanCache B/C/D
| Four impls; A consolidated, B/C/D intentionally separate (documented as by-design).

| Read-side distributed execution
| `ComputeScheduler` and `RoutedReadPlan` exist; DataFusionLocal is the first OLAP route, while
Ballista-backed `DataFusionDistributed` remains a planned/experimental adapter behind the same route
contract.
|===

[#state]
== Current state and MVP readiness

This section intentionally separates *code presence* from *product maturity*. The support contract is
link:../SUPPORTED_SURFACE.adoc[docs/SUPPORTED_SURFACE.adoc]; this map summarizes it in system terms.

[cols="2,2,3", options="header"]
|===
| Area | Current system state | MVP readiness

| Durable authority
| xCatalog + canonical WAL/log/manifest + `ProximaRecord`/`ProximaType`/`ProximaValue` are the
target spine. Proto v1 DTOs and legacy `VectorRecord`/`SqlValue`/`SqlObject` remain edge adapters or
internal migration debt.
| Ready for narrow v0.2 only when flows stay on the canonical record path. Full internal migration is
still TD-106/ADR-024 work.

| Vector path
| REST/gRPC v2 record CRUD and vector search are the supported product path. Multiple vector storage
engines and AXIS index families exist; v1 vector APIs are compatibility facades.
| MVP-ready for single-node vector CRUD/search. Hybrid, filtered ANN policy, recall-gate enforcement,
and object-economy claims stay Beta/Experimental unless explicitly scoped.

| Document / graph / observability
| Document, ORION graph, and observability runtimes exist and are useful. ORION is the only graph
runtime; former PULSAR/QUASAR names are retired. These modalities should be treated as projections or
facades over canonical authority, not separate durable truths.
| Beta. Good for controlled workflows, not yet the same maturity as the supported vector surface.

| SQL / pgwire / relational
| pgwire, relational frontend/algebra/executor, DML routing, `ComputeScheduler`, DataFusionLocal
route decisions, and read-side `RoutedReadPlan` now exist. Full PostgreSQL parity, complete
constraints, MVCC/index state, HTAP delta union, and distributed consistency gates remain in TD-110.
| Not MVP as a PostgreSQL replacement. Useful Beta/Experimental surface for scoped relational and
EXPLAIN work.

| DataFusion / distributed execution
| DataFusion integration and route vocabulary exist. `DataFusionDistributed` is now represented in
the typed read route contract, but Ballista execution, split-aware readers, scheduler/executor
deployment, and no-overlap tests are not complete.
| Post-MVP / Experimental. Do not claim distributed execution support in v0.2.

| Open formats and object economy
| Object-store and Iceberg engine crates are in the workspace; Parquet/Arrow bridge work is the
analytics/open-format trajectory. Open formats are publications/imports/federated assets unless
explicitly external-authoritative in xCatalog.
| Beta/Experimental depending on path. Safe claim is interoperability direction, not default durable
authority.

| Security / ops / deployment
| Security runtime, mTLS/JWT/API key hooks, observability, backup/restore, and deployment assets
exist. Some admin/status APIs and production runbooks still need hardening.
| Sufficient for developer/private deployments; enterprise production positioning should remain
scoped.
|===

MVP posture: ProximaDB is ready to position as a **single-node context database foundation** with a
supported canonical vector record path and Beta multimodal surfaces. It is not yet ready to position
as a mature distributed database, full PostgreSQL-compatible OLTP/HTAP system, or warehouse-scale
MPP engine. The architecture is aligned for that aspiration through xCatalog, route-once planning,
DataFusion/Ballista contracts, and canonical record convergence, but the implementation is still
slice-based and must keep support claims narrow.

== Agent-memory note

ProximaDB's positioning as a memory substrate for AI agents and its mapping to the mem0 / agentmemory
orchestration libraries are specified in
link:adr/ADR-022-agent-memory-layer.adoc[ADR-022] +
link:AGENT_MEMORY_LAYER_HLD_2026_05_30.adoc[AGENT_MEMORY_LAYER_HLD_2026_05_30]. The short version: the
agent-memory layer is a *consumer* of the surfaces mapped above (AQL, Graph RAG, RERANK, hybrid fusion,
`ProximaRecord.memory_type`, pgvector wire), not a new storage stack.
