This atlas is the top-down map for ProximaDB as an OSS core database and as the data plane behind
a hosted SaaS product. It is intentionally navigation-first: it shows ownership boundaries,
authority boundaries, and where lower-level module maps live.

== Non-Negotiable Architecture Invariants

* Durable authority is `xCatalog + WAL/log/manifest + ProximaRecord + policy/RLS + version/time`.
* Protocols are adapters: REST, gRPC, pgwire, Arrow Flight, SDKs, and embedded bindings lower into
  canonical records, catalog metadata, and shared query/write contracts.
* Open formats are interoperability contracts. Iceberg, Delta, Hudi, Parquet, and object stores are
  publications, imports, federated reads, or explicit external-authoritative assets.
* Storage engines and modality-specific indexes are layouts, projections, and access methods. They
  do not own independent durable truth unless xCatalog declares that authority mode explicitly.
* The router is a control-plane planner boundary: route once per plan/fragment/split, emit typed
  route/explain metadata, and dispatch to leaf executors/readers.

  -> service layer executes against canonical record/storage contracts

== Victor Graph Findings

Victor's Rust CCG construction previously resolved CALLS edges per-file only — `name_to_ids` was
built from a single file's nodes during `_build_calls_edges`, so any callee defined in another
file resolved to the empty set and no edge was emitted. With cross-file CALLS empty,
`ModuleAnalyzer._load_module_graph` (which only loads cross-file `graph_edge` rows) returned an
empty module set and `graph_module_metric` stayed at zero rows.

Resolution now proceeds in three coordinated layers:

1. *Project-wide leaf-name index* in `_resolve_cross_file_calls` runs after all nodes are
   persisted and emits CALLS edges via UPSERT. A fanout cap
   (`cross_file_call_max_fanout`, default 25) keeps common names (`new`, `default`, `from`) from
   inflating the graph.
2. *Impl-type index* keyed by `(impl_type, method_name)`, populated from the existing
   ``parent_id`` linkage (methods inside ``impl T`` carry ``parent_id`` pointing at the impl
   node, whose name is ``T``). When a call record carries ``receiver_type``, the typed pass
   binds against this index and bypasses the fanout cap — typed dispatch is unambiguous.
3. *Receiver-type inference in the Rust plugin* covers four expression shapes:
+
[loweralpha]
.. ``self`` against the enclosing ``impl T`` (including ``Self::method()`` path calls).
.. ``identifier`` against the current function's scope (parameter annotations and
   ``let x: T = ...`` / ``let x = T::new()`` bindings).
.. ``field_expression`` chains like ``self.a.b.method()`` walk through a per-file
   ``struct_item`` field map.
.. ``call_expression`` chains like ``a.foo().bar()`` walk through a per-file impl-method
   return-type map.
+
Cross-file struct fields and return types are out of scope for this round; method chains and
field receivers that cross file boundaries fall back to name-only.

The 2.7x jump in CALLS between the basic and full receiver-typed snapshots is recovered
edges, not new noise. Calls like ``self.field.method()``, ``a.foo().bar()``, and
``Self::method()`` that previously had ``receiver_type=None`` would fall back to name-only
resolution — and the leaf names involved (``iter``, ``format``, ``handle``, ``process``,
``run``, ``execute``) routinely exceed the fanout cap of 25 candidates and got *skipped*
entirely. With the new inferences, each of those calls now binds to a specific
``impl <type>::<method>`` and is included again, this time precisely. Cross-file ratio
climbs to 95% because typed dispatch overwhelmingly resolves to methods in other files
(impl blocks are rarely co-located with every caller).

== Victor Reproducibility Queries

Use read-only SQLite queries against `.victor/project.db` after each expansion/consolidation cycle.
The schema columns used here are `graph_node.file`, `graph_node.type`, and `graph_edge.type`.

[source,sql]
----
select count(*) from graph_module_metric;
select count(*) from graph_node;
select count(*) from graph_edge;

select type, count(*)
from graph_edge
group by type
order by count(*) desc;

select type, count(*)
from graph_node
group by type
order by count(*) desc
limit 20;

select substr(file, 1, instr(file || '/', '/') - 1) as prefix, count(*)
from graph_node
group by prefix
order by count(*) desc
limit 20;

select file, count(*) as nodes
from graph_node
group by file
order by nodes desc
limit 20;

select
  sum(case when src_node.file = dst_node.file then 1 else 0 end) as same_file_calls,
  sum(case when src_node.file <> dst_node.file then 1 else 0 end) as cross_file_calls
from graph_edge edge
join graph_node src_node on edge.src = src_node.node_id
join graph_node dst_node on edge.dst = dst_node.node_id
where edge.type = 'CALLS';
----

Current interpretation:

* `graph_module_metric` contains 1,706 rows. Module-level PageRank, instability, cohesion,
  hotspot, and TDD priority metrics are first-class signals; use them as gates alongside Cargo
  dependency centrality. Current top hotspots: `src/network/rest/v1/handlers.rs` (Ce=550,
  2,238 symbols), `src/network/multi_server.rs`, `src/network/arrow_ipc/service.rs`,
  `src/services/operations/vectors/legacy.rs`, `src/services/dml/mod.rs`. Note that Ce
  values have roughly tripled vs. the basic-receiver-typed snapshot — that's a true
  reflection of the cross-module call graph, previously hidden behind name-only fanout
  skips.
* `CALLS` resolves cross-file at 95% (1.2M of 1.26M total). The resolver applies receiver-typed
  dispatch whenever the Rust plugin can infer the receiver from any of: ``self`` inside
  ``impl T``, ``Self::method()`` path calls, scope identifiers (parameter type, ``let`` binding),
  ``struct_item`` field chains (``self.field.method()`` and longer paths), and impl-method
  return-type chains (``a.foo().bar()``).
* Falls back to name-only resolution (with fanout cap 25) when the receiver-type chain hits
  something unsupported: a method call on a stdlib type (``Vec``, ``HashMap``) whose impl lives
  outside the codebase, a generic parameter with no concrete bound resolved at parse time, a
  trait object (``Box<dyn Trait>``), or a cross-file struct field whose type is declared in
  another module. None of these are wrong — they're just imprecise; the fanout cap keeps the
  noise bounded.
* Treat call-edge counts as a tight upper bound: typed dispatch is exact; the name-only tail
  is fanout-bounded; the recovered edges in the third snapshot are real calls that the
  earlier resolvers were dropping silently.
* Statement-level nodes still dominate the graph. Use file/module aggregation first, then
  inspect human-authored hotspot files manually.

== Consolidation / Expansion Zigzag

Use this cycle for feature growth:

1. Expand behind existing contracts, feature flags, and xCatalog-declared authority.
2. Refresh Victor and Cargo coupling metrics.
3. Identify hotspots, duplicated authority, and root-crate fanout.
4. Consolidate one boundary at a time into the existing crate/module owner.
5. Add or update the module LLD section before enabling by default.
6. Run focused tests plus workspace layering validation.
7. Repeat.

This keeps the system from drifting into parallel protocol, storage, or modality paths while still
allowing rapid feature expansion.
