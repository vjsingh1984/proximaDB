== 2. HLD — the seam and the strategy

=== 2.1 The reframing (critical)
* There is **no `StorageRow`** type (earlier scoping was wrong). The document row is
  `DocumentRecord` (`src/storage/document/mod.rs:110`) with `document: SqlObject` (proto v1,
  `{ fields: HashMap<String, SqlValue> }`).
* Canonical types **and adapters already exist**:
** `ProximaValue` (28 variants) — `crates/foundation/proximadb-data-model/src/lib.rs:305`
** `ProximaTree = HashMap<String, ProximaTreeNode>`, `ProximaTreeNode = Value(ProximaValue) | Object(ProximaTree)` — `crates/foundation/proximadb-records/src/lib.rs:66`
** `ProximaRecord.props: ProximaTree` — `…/proximadb-records/src/lib.rs:760`
** Adapters: `canonical_adapter.rs::{sql_object_to_proxima_tree, proxima_tree_to_sql_object}`;
   `proximadb-records/src/conversions.rs::{sql_value_to_proxima, proxima_to_sql_value, json_to_proxima}`;
   `core/search/sql_value_filter.rs::{proxima_value_to_json, proxima_tree_to_json_map}`.
* **Durable authority is already `ProximaRecord`** (service.rs writes/reads it). So `SqlObject`
  is purely an *in-memory compute* representation in the document engine — **WAL/serde is a
  non-issue** for the internal slices. The work removes `SqlObject` from the *compute* path.

=== 2.2 Strategy (unchanged)
. **Convert-at-boundary** for compute kernels — each function converts to canonical at its
  own edge via the existing adapters; signatures stay stable; revertible per slice. (Done: Group A.)
. **Working-set flip** (Group B) — push the boundary outward: the internal working set becomes
  `Vec<ProximaTree>`, converting only at the two outermost edges. Kills per-stage/per-edge conversion.
. **Terminal dual-carry** (Group C) — add `props: ProximaTree` to `DocumentRecord`, migrate
  readers, delete `document: SqlObject`.
. **Reject big-bang** field-flip of `DocumentRecord` in one commit (454 sites).

== 3. Group B — Slice 5: working-set type flip (HLD + LLD + spec)

=== 3.1 Goal
Flip the aggregation internal working set `Vec<SqlObject>` -> `Vec<ProximaTree>` so no
per-stage `SqlObject<->ProximaTree` conversion happens; convert only at the outermost edges.

=== 3.2 Blast radius (confirmed)
* **`src/storage/document/aggregation.rs`** (~20 functions) — whole-file data-type change. This
  is **atomic** (the working set is shared across every `process_*`/helper; cannot be sub-sliced).
* **`src/storage/document/service.rs`** — the aggregate methods that consume the executor:
** `executor.execute(documents, filter, &pipeline)` at ~1738, ~1815 (returns `Vec<SqlObject>`).
** the hand-rolled stage loop at ~1876–1902 with `working_set: Vec<SqlObject>` interleaving
   `process_lookup`/`process_stage` — must carry `Vec<ProximaTree>` to kill per-stage conversion there too.
* **~8 inline tests** in aggregation.rs build `SqlObject` inputs / assert `SqlObject` outputs.

=== 3.3 Edge boundaries (where conversion stays)
* **Input edge** — `execute()`: `documents.into_iter().map(|d| d.document)` becomes
  `.map(|d| sql_object_to_proxima_tree(&d.document))`. (Group C removes this when DocumentRecord carries props.)
* **Output edge** — `execute()` keeps its public `Result<Vec<SqlObject>>` by converting the final
  `Vec<ProximaTree>` via `proxima_tree_to_sql_object` (until callers are migrated). OR change the
  return to `Vec<ProximaTree>` and convert in service.rs — pick one; keeping `Vec<SqlObject>` return
  is lower-churn for service.rs.
* **Filter edge** — `process_match` builds a temp `DocumentRecord` to call
  `FilterEvaluator::evaluate(&DocumentFilter, &DocumentRecord)`. Since filter still takes
  `DocumentRecord{document: SqlObject}`, convert the working `ProximaTree` -> `SqlObject`
  (`proxima_tree_to_sql_object`) to build that temp record. (Group C / a later filter-input slice removes this.)

=== 3.4 LLD — mechanical substitution table (aggregation.rs)

[cols="2,3",options="header"]
|===
| Pattern (current) | Replace with
| `Vec<SqlObject>` / `&[SqlObject]` / `&[&SqlObject]` / `&SqlObject` / `&mut SqlObject` | `…ProximaTree…` (same shapes)
| `SqlObject { fields: HashMap::new() }` | `ProximaTree::new()` (it *is* a `HashMap`)
| `doc.fields.get(k)` | `doc.get(k)` -> `Option<&ProximaTreeNode>` (match `Value(pv)` / `Object(sub)`)
| `doc.fields.insert(k, sqlvalue)` | `doc.insert(k, ProximaTreeNode::Value(proximavalue))`
| `result.fields = doc.fields.clone()` | `result = doc.clone()`
| `sql_object_to_json(&SqlObject)` | build `JsonValue::Object` from `proxima_tree_to_json_map(&ProximaTree)`; **delete** the local `sql_object_to_json`/`sql_value_to_json`
| `extract_value`/`extract_group_key` (jsonpath input) | render the tree via `proxima_tree_to_json_map`, run jsonpath, lift with `json_to_proxima` (already used)
| `set_path_value(&mut SqlObject, path, SqlValue)` | `set_path_value(&mut ProximaTree, path, ProximaValue)` -> insert `ProximaTreeNode::Value`
| `compare_by_path` + `compare_sql_values(&SqlValue,…)` | compare on `ProximaValue` (add `compare_proxima_values`); **drop** the temporary `proxima_to_sql_value` convert-back added in Slice 4
| `process_group`: `proxima_to_sql_value(&agg_value)` at insert | insert `ProximaTreeNode::Value(agg_value)` directly; `_id` -> `ProximaTreeNode::Value(ProximaValue::String(key))`
| `project_document` -> `SqlObject` | -> `ProximaTree`; computed field inserts `ProximaTreeNode::Value(val)` (drop the Slice-4 `proxima_to_sql_value`)
| `process_unwind`: `…map(proxima_to_sql_value)` + match `SqlValue::ArrayValue` | match `ProximaValue::Array`; `set_path_value` with `ProximaValue`; **drop** the convert-back
|===

NOTE: the accumulators (`agg_*`, `compute_aggregation`) already return `ProximaValue` (Slice 3) and
read via `extract_value` which already returns `ProximaValue` (Slice 4) — they only need their `docs:
&[&SqlObject]` params retyped to `&[&ProximaTree]`.

=== 3.5 LLD — service.rs
. `execute(documents, …)` already takes `Vec<DocumentRecord>`; only its internals/return change
  (output edge). Callers at 1738/1815 unchanged if `execute` keeps `Vec<SqlObject>` return.
. The stage loop (~1876–1902): change `working_set` to `Vec<ProximaTree>`; convert `documents`
  (`DocumentRecord.document`) -> `ProximaTree` once before the loop; convert the final
  `working_set` -> `Vec<SqlObject>` once after. `process_stage`/`process_lookup` signatures become
  `&[ProximaTree] -> Vec<ProximaTree>`.
. `process_lookup` -> `execute_lookup` (aggregation_extensions.rs) currently `&[SqlObject]`; either
  retype it to `ProximaTree` (it's a join/array-shaping fn — moderate) or wrap-convert at this one
  call. Recommend retype for consistency (it's the one wired extensions export).

=== 3.7 Tests
Rewrite the ~8 inline tests: build `ProximaTree` inputs (helper `create_test_doc` ->
`ProximaTree`; `int_value`/`string_value` -> `ProximaValue` + `ProximaTreeNode::Value`); assert on
`ProximaTree`/`ProximaValue`. Tests that go through `execute()` (output edge = `SqlObject`) can keep

=== 3.8 Verification
`cargo check --lib` (file compiles) then `cargo test --lib storage::document` (25 agg + 8 filter

=== 3.9 Risks
* **Atomicity** — the whole file changes at once; budget 2–3 build cycles (~28 min each).
* **`ProximaTreeNode` nesting** — `doc.get(k)` returns `Value(pv)` *or* `Object(sub-tree)`;
  handle both where the old code assumed a flat `SqlValue` (esp. nested-path/jsonpath cases).
* **Filter edge** — `process_match` convert-back must be exact (`proxima_tree_to_sql_object`).
* **Hot branch** — `git commit -o <files>` only; a red `cargo test --lib` may be *foreign* WIP
  (check error file paths before assuming it's yours — happened in Slice 4 with dml/record_store).
