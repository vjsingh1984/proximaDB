== 2. HLD — the seam and the strategy

=== 2.1 The reframing (critical)
* There is **no `StorageRow`** type (earlier scoping was wrong). The document row is
  `DocumentRecord` (`src/storage/document/mod.rs:110`) with `document: SqlObject` (proto v1,
  `{ fields: HashMap<String, SqlValue> }`).
* Canonical types **and adapters already exist**:
** `ProximaValue` (28 variants) — `crates/foundation/proximadb-data-model/src/lib.rs:305`
** `ProximaTree = HashMap<String, ProximaTreeNode>`, `ProximaTreeNode = Value(ProximaValue) | Object(ProximaTree)` — `crates/foundation/proximadb-records/src/lib.rs:66`
** `ProximaRecord.props: ProximaTree` — `…/proximadb-records/src/lib.rs:760`
** Adapters: `canonical_adapter.rs::{sql_object_to_proxima_tree, proxima_tree_to_sql_object}`;
   `proximadb-records/src/conversions.rs::{sql_value_to_proxima, proxima_to_sql_value, json_to_proxima}`;
   `core/search/sql_value_filter.rs::{proxima_value_to_json, proxima_tree_to_json_map}`.
* **Durable authority is already `ProximaRecord`** (service.rs writes/reads it). So `SqlObject`
  is purely an *in-memory compute* representation in the document engine — **WAL/serde is a
  non-issue** for the internal slices. The work removes `SqlObject` from the *compute* path.

== 3. Group B — Slice 5: working-set type flip (HLD + LLD + spec)

=== 3.1 Goal
Flip the aggregation internal working set `Vec<SqlObject>` -> `Vec<ProximaTree>` so no
per-stage `SqlObject<->ProximaTree` conversion happens; convert only at the outermost edges.

=== 3.2 Blast radius (confirmed)
* **`src/storage/document/aggregation.rs`** (~20 functions) — whole-file data-type change. This
  is **atomic** (the working set is shared across every `process_*`/helper; cannot be sub-sliced).
* **`src/storage/document/service.rs`** — the aggregate methods that consume the executor:
** `executor.execute(documents, filter, &pipeline)` at ~1738, ~1815 (returns `Vec<SqlObject>`).
** the hand-rolled stage loop at ~1876–1902 with `working_set: Vec<SqlObject>` interleaving
   `process_lookup`/`process_stage` — must carry `Vec<ProximaTree>` to kill per-stage conversion there too.
* **~8 inline tests** in aggregation.rs build `SqlObject` inputs / assert `SqlObject` outputs.

=== 3.3 Edge boundaries (where conversion stays)
* **Input edge** — `execute()`: `documents.into_iter().map(|d| d.document)` becomes
  `.map(|d| sql_object_to_proxima_tree(&d.document))`. (Group C removes this when DocumentRecord carries props.)
* **Output edge** — `execute()` keeps its public `Result<Vec<SqlObject>>` by converting the final
  `Vec<ProximaTree>` via `proxima_tree_to_sql_object` (until callers are migrated). OR change the
  return to `Vec<ProximaTree>` and convert in service.rs — pick one; keeping `Vec<SqlObject>` return
  is lower-churn for service.rs.
* **Filter edge** — `process_match` builds a temp `DocumentRecord` to call
  `FilterEvaluator::evaluate(&DocumentFilter, &DocumentRecord)`. Since filter still takes
  `DocumentRecord{document: SqlObject}`, convert the working `ProximaTree` -> `SqlObject`
  (`proxima_tree_to_sql_object`) to build that temp record. (Group C / a later filter-input slice removes this.)

=== S7 is NOT just field deletion — it must migrate three SqlObject-native compute engines
Deleting `document: SqlObject` forces every reader onto `props`. The blocker is that
the document compute layer is built on **proto `SqlObject`/`SqlValue`**, not just the record field:

. **`query::path_parser::JsonPath`** (`src/storage/document/query/path_parser.rs`) — `parse()` + `evaluate(&SqlObject) -> Vec<SqlValue>`. Used by `indexes::extract_path_value`/`extract_array_values` **and** `service::apply_projection`.
. **`indexes::fulltext::FullTextIndex`** — `index_document(&SqlObject)` + `extract_text(&SqlObject)`.
. **The update-mutation family** in `service.rs` (`apply_update` + `set_path_value`/`unset_path`/`increment_path`/`push_to_array`/`pull_from_array`/`add_to_set`/`rename_path`, ~330 LOC) — path navigation/mutation over `&mut SqlObject`/`SqlValue`.
. `filter.rs::evaluate_condition`/`extract_path_value` — already half-canonical (comparison kernel is `ProximaValue` since Slice 1/2); cheap to flip to `&ProximaTree` via `proxima_tree_to_json_map`.

Wrapping these engines with per-record `proxima_tree_to_sql_object(&rec.props)` would
delete the field but **re-introduce per-record conversions in the index-build / query-sort
/ filter hot paths** — a perf regression and not real convergence. Therefore S7 must
**migrate the engines to `ProximaTree`/`ProximaValue` natively**, which is a multi-slice
project, not one atomic commit.

== 6. New tech debt surfaced — TD-109 (proposed): consolidate json<->proxima converters
Found **3+ scattered private copies** of `json -> ProximaValue` and a separate `proxima -> json`:

* `src/network/arrow_ipc/codec.rs:640` `json_to_proxima_value`
* `src/network/rest/websocket.rs:105` `json_value_to_proxima_value`
* `src/network/rest/v2/query.rs:58` `json_to_proxima_value`
* `src/core/search/sql_value_filter.rs:236` `proxima_value_to_json` + `:304` `proxima_tree_to_json_map`

Canonical home now exists: `proximadb_records::conversions::json_to_proxima` (added in Slice 2).
**TD-109**: converge the 3 json->proxima copies onto it, and move `proxima_value_to_json` /
`proxima_tree_to_json_map` into `conversions.rs` (or a shared `proximadb-records` json module) so both
directions live in one place.

[IMPORTANT]
====
**The 3 copies are NOT identical (verified 2026-06-03) — it is not a safe drop-in.**
The canonical `json_to_proxima` maps numbers as `as_i64 -> Int64` else `as_f64 -> Float64`
(no `UInt64`; mirrors the `SqlValue` path, which has no u64).

* `network/rest/v2/query.rs:58` and `network/arrow_ipc/codec.rs:640` — add a **`UInt64`** branch
  (`as_i64 -> Int64`, `as_u64 -> UInt64`, `as_f64 -> Float64`). Converging onto canonical drops
  `UInt64 -> Float64` for json numbers in `(i64::MAX, u64::MAX]` (param-bind / arrow-ingest edge).
* `network/rest/websocket.rs:105` — **lossy / divergent**: only handles String/Number/Bool;
  Null and **Array/Object are stringified** (`v.to_string()`), not mapped to `Null`/`Array`/`Map`.
  Converging is a behavior change at the WS protocol boundary (more correct, but must verify consumers).

**Recommended TD-109 path:** add a `UInt64` branch to canonical `json_to_proxima` (makes it a true
superset of query/codec), AND add `UInt64` arms to the document filter kernel
(`filter.rs::proxima_values_equal`/`proxima_value_to_f64`) + `aggregation.rs::extract_numeric_value`
— otherwise a document field holding a json number `> i64::MAX` becomes `UInt64` and silently stops
matching (the filter kernel currently only has Int64/Float64 arms). Then replace query/codec copies
(`&value` vs owned — adjust call sites) and decide websocket separately. NOT the trivial drop-in the
ticket assumed; needs the UInt64 semantics decision + a small test.
