= Stacked Durability and Modality Convergence Mandate
:toc:
:toclevels: 3
:sectnums:

Status: Accepted architectural mandate +
Date: 2026-05-14 +
Scope: vector, document, graph, relational, observability, SKS/entity, event log, multi-model query lowering, indexing, durability, and agent guidance

== Decision

ProximaDB's durable source of truth for vectors, documents, graph nodes, graph edges, relational rows, observability records, SKS entities, relationships, and event streams MUST converge on the unified record/relational storage model defined by `roadmap/MULTIMODAL_OVERHAUL_SPEC_2026_05_08.adoc`.

Modality services and APIs remain valid user-facing and planner-facing facades. This includes `VectorOperationsService`, `DocumentService`, graph services, observability services, SKS/entity APIs, event-log APIs, Cypher/PGQ surfaces, SQL extensions, and SDK helpers. They MUST NOT evolve into independent durable systems with separate transaction semantics, separate record envelopes, or separate persistence rules.

The target shape is:

[source,text]
----
API/query facades
  REST/gRPC vector/document/graph/observability/entity/event APIs,
  Cypher/PGQ, SQL extensions, SDK helpers

Logical services
  VectorOperationsService, DocumentService, GraphOperationsService,
  ObservabilityService, Entity/SKS services, EventLog APIs,
  query strategies, planners

Unified logical algebra
  Filter, Project, Sort, Limit, Aggregate, Join, HybridTraverse,
  PatternMatch, CrossModelJoin, VectorTopK, SemanticJoin

Canonical durable store
  ProximaRecord / ProximaType / ProximaValue
  relational table projections for all modality records
  engine-level tenant/RLS fields

Adaptive physical projections
  JSON path indexes, inverted/full-text indexes, columnar projections,
  edge tables sorted by (src, label, dst), CSR/COO topology caches,
  vector HNSW/IVF/PQ indexes, time partitions, metric rollups,
  trace indexes, event indexes, SKS entity/relationship views
----

== Stacked Durability Model

The architectural rule is not "everything is stored in one physical file format." The rule is that every modality has a clear stack, and only the canonical layers are allowed to be authoritative.

[source,text]
----
Layer 4: Facades and Protocols
  REST, gRPC, Arrow Flight, PostgreSQL wire, SDKs, Cypher/PGQ, PromQL, AQL/UQL

Layer 3: Query and Logical Services
  vector search, document query, graph traversal, observability query,
  SKS/entity retrieval, event replay

Layer 2: Rebuildable Projections and Access Methods
  AXIS HNSW/IVF/PQ, JSON path indexes, Tantivy/full-text,
  adjacency tables, CSR/COO, time partitions, rollups, trace indexes,
  event indexes, caches, materialized SKS views

Layer 1: Canonical Durable Records
  ProximaRecord/ProximaType/ProximaValue with identity, profile,
  variation, tenancy, time, provenance, props, refs, edge,
  embeddings, sequence, labels, and extensions

Layer 0: Canonical Commit/Journal Stream
  WAL, manifest, append-only event records, CDC, replay metadata
----

Rules:

* Layer 1 is the normal source of truth for current state.
* Layer 0 is the source of truth for replay, event-sourced domains, CDC, and regulatory history.
* Layer 2 is rebuildable unless explicitly promoted to retained canonical aggregate records by a retention policy.
* Layers 3 and 4 never own durable semantics.
* Internal foundation, modality, storage, query, and catalog contracts MUST prefer
  `ProximaRecord` plus `ProximaType`/`ProximaValue` for richer datatype support.
  v2 protobuf records are the protocol/wire alignment for this canonical model,
  not a separate internal durable model. Legacy v1 `SqlValue`/`SqlObject` shapes
  are compatibility adapter types only and must not be used as new internal
  modality contracts.

This allows specialized engines to exist, but only with a clear role:

* as a canonical record layout/access method;
* as an append-only canonical journal;
* as a rebuildable projection/index/cache;
* as a compatibility adapter with a retirement plan.

== Why This Is The Mandate

=== Repository evidence

The current code already points in this direction, but it has not fully converged.

* `DocumentService` is the operational API facade for documents. It contains collection metadata, JSON path indexing, query execution, WAL replay, in-memory hot storage, and a legacy vector-storage flush path.
* `DocumentStorageEngine` and `CedarEngine` exist as document-native abstractions, but CEDAR is still phase-1/in-memory and the current `DocumentService` CRUD path continues to use its own maps and index manager.
* `SequoiaEngine` models typed relational rows with schema, filters, projection, ordering, DDL, and row CRUD.
* ORION graph storage uses in-memory CSR for fast traversal. CSR is an adjacency-list projection encoded into contiguous arrays, not an adjacency matrix and not the durable record model.
* Vector storage already has a `VectorRecord` to `ProximaRecord` migration surface and multiple physical engines. Those engines should be storage layouts/access methods for vector-bearing records, not independent vector-only semantics.
* Observability already separates `ObservabilityService`, `ObservabilityStorageEngine`, partitioned storage, query engines, and rollups. Logs, metric samples, and trace spans should map to canonical observability records; partitions, rollups, and indexes are projections.
* SKS/entity storage currently has legacy split storage and ORION-backed graph storage. Entity state, relationships, embeddings, and provenance should converge to canonical entity/edge/vector/event records.
* EventLog is append-only and sequence-based. That is a valid canonical journal shape, but indexes, snapshots, and current-state reconstruction are projections over the append-only event records.
* `roadmap/MULTIMODAL_OVERHAUL_SPEC_2026_05_08.adoc` already states that Layer 1 is unified record storage, Layer 2 is topology storage, and edge records live in Layer 1 while topology storage builds CSR offsets and hash maps for traversal.

=== Product and engineering rationale

Separate durable semantics for document and graph create avoidable duplication:

* duplicate record envelopes and type systems;
* duplicate WAL/recovery semantics;
* duplicate RLS/tenant enforcement;
* duplicate indexing and compaction decisions;
* inconsistent REST/gRPC/Arrow Flight/PostgreSQL wire behavior;
* harder distributed ownership, CDC, replication, snapshots, and branch/restore.

The preferred architecture is PostgreSQL-style extensibility: one canonical durable store and transaction model, with specialized access methods, indexes, operators, and physical projections where they pay for themselves.

=== External precedent

This decision is consistent with the database literature and SQL standard direction:

* SQL:2023 added SQL/PGQ for property graph queries over relational data.
* The Vertexica work from Jindal, Madden, Deshpande, and Stonebraker showed a vertex-centric graph API translated onto Vertica could outperform Giraph and Neo4j for evaluated graph analytics workloads.
* SQLgraph showed property graph storage and querying can be effective on relational foundations with adjacency tables and JSON properties.
* Stonebraker's broader "one size fits all" argument supports specialized physical designs for workloads, not independent semantics for every API surface.

The conclusion for ProximaDB: use specialized graph/document physical structures as projections and indexes, not as separate systems of record.

=== Refined architectural trajectory

The evidence does not support a choice between "one generic row store" and "many isolated durable
engines." The best path is a stacked system:

1. Durable authority is unified: `ProximaRecord`, `ProximaType`, xCatalog, WAL/log/manifest,
   tenant/RLS, version/time/provenance.
2. Physical specialization is aggressive: LSM, PAX, columnar, adjacency tables, CSR/COO,
   GraphAr-style lake projections, HNSW/IVF/PQ/DiskANN-style ANN fragments, Gorilla-style
   time-series blocks, trace indexes, and event streams.
3. Semantics are added once: SQL, SQL/PGQ, Cypher/GQL, document filters, vector search,
   observability query, and agent/SKS APIs lower into shared algebra and policy-aware scans.
4. Performance decisions are empirical: every projection family has workload thresholds,
   freshness semantics, rebuild rules, and benchmarks before it becomes default behavior.

The resulting target is "stacked durability with adaptive projections":

[source,text]
----
Canonical authority:
  xCatalog + ProximaRecord/ProximaType + WAL/log/manifest + engine-level RLS

Physical layout families:
  row/record segments, LSM levels, PAX, columnar/Parquet/Arrow, event streams

Adaptive projections:
  JSON path and full-text indexes
  edge tables, CSR/COO, graph property pages, graph lake files
  HNSW/IVF/PQ/DiskANN/LSM-vector fragments
  time-series compression blocks, rollups, trace/service indexes

Logical surfaces:
  SQL/pgwire, SQL/PGQ, Cypher/GQL, document API, vector API,
  observability API, SKS/entity API, event API, REST/gRPC/Arrow Flight/SDKs
----

This keeps ProximaDB competitive with specialized databases without inheriting their worst
maintenance property: separate durable semantics for every modality.

=== Format Fungibility Rule

Stacked durability is not a mandate to force all data into one physical layout. It is a mandate to
keep authority, policy, type semantics, and recovery coherent while allowing the physical shape to
vary by workload.

Accepted physical families include:

* LSM or row/record segments for write-heavy OLTP, vector metadata, events, and hot agent state;
* B-tree/range/hash-style secondary indexes where relational constraints or point lookups need
  them;
* PAX and columnar segments for mixed OLTP/OLAP workloads;
* Arrow batches for in-memory exchange and Arrow Flight transport;
* Parquet/ORC-style files for analytical/cold projections;
* Iceberg/Delta/Hudi tables as external snapshot/table formats when registered in xCatalog;
* HNSW/IVF/PQ/DiskANN/LSM-vector fragments for vector search;
* adjacency tables, CSR/COO, and graph lake files for graph access;
* time-series compression blocks, trace indexes, rollups, and event streams for observability.

These layouts may be plugins or access methods. They MUST NOT define their own durable record
envelope, scalar type system, RLS rules, branch semantics, WAL/recovery model, or hidden catalog.

External formats may be authoritative only when xCatalog explicitly records ownership mode,
snapshot/isolation semantics, `ProximaType` mapping and lossy conversions, policy enforcement
boundary, write/refresh mode, and rebuild or repair source.

== Current-State Interpretation

=== Document

`DocumentService` should be understood as a logical/API service. It owns:

* document collection lifecycle;
* document API compatibility;
* JSON path parsing and filter translation;
* Mongo-like update semantics;
* aggregation pipeline translation;
* full-text and inverted-index coordination;
* document-specific metrics.

It should not own long-term independent persistence. CEDAR should either become:

* a document access method over `ProximaRecord`/relational storage; or
* a short-lived compatibility adapter that is retired after convergence.

Do not build a second durable document engine unless an accepted ADR proves that it cannot be represented as:

* a `ProximaRecord` profile/variation;
* a relational row with JSON/Map/Struct values;
* a document index/projection over the canonical record store.

=== Graph

Graph nodes and edges are canonical records/tables:

[source,sql]
----
nodes(
  graph_id,
  node_id,
  labels,
  props,
  tenant_id,
  permitted_principals,
  valid_from,
  valid_to,
  version,
  provenance
)

edges(
  graph_id,
  edge_id,
  src_node_id,
  dst_node_id,
  edge_label,
  props,
  tenant_id,
  permitted_principals,
  valid_from,
  valid_to,
  version,
  provenance
)
----

The primary relational adjacency projections are:

[source,sql]
----
edges_by_src(graph_id, src_node_id, edge_label, dst_node_id, edge_id)
edges_by_dst(graph_id, dst_node_id, edge_label, src_node_id, edge_id)
----

CSR/COO is a physical topology projection:

* `offsets`: row pointer per dense source-node id;
* `targets`: dense destination-node ids;
* `edge_ids`: edge metadata lookup keys;
* optional incoming CSR mirrors `edges_by_dst`;
* optional delta/epoch overlays absorb writes before rebuild.

CSR MUST NOT be the only durable representation of graph topology. It is a cache/index/projection used by `HybridTraverse`, `PatternMatch`, path finding, centrality, and hot traversal workloads.

=== Relational

Relational storage is the canonical durable substrate for:

* closed-shape relational tables;
* open-shape document profiles with JSON/Map/Struct payloads and variation metadata;
* node/edge tables and adjacency projections;
* queryable indexes and constraints;
* RLS pushdown and protocol alignment.

`SequoiaEngine` and the broader `ProximaRecord` storage work should absorb the durable responsibilities currently duplicated in document and graph paths.

Relational rigor is a set of cataloged table capabilities, not a global cost imposed on every
collection. A table/profile may opt into:

* primary key enforcement;
* unique indexes;
* non-unique secondary indexes;
* foreign key/reference constraints;
* check constraints;
* materialized views;
* transaction/isolation profiles;
* stricter schema evolution rules.

When enabled, these capabilities are durable semantics and must be enforced below all protocol
surfaces. Their physical implementation may use B-tree/range/hash indexes, LSM-friendly uniqueness
checks, deferred validation, or materialized reference indexes, but the semantics are declared in
xCatalog and recovered through WAL/log/manifest.

=== Vector

Vector data is already the historical core of ProximaDB, but it still needs the same layered discipline as newer modalities.

Canonical vector truth is the vector-bearing `ProximaRecord`:

* record identity and collection;
* one or more embedding cells with modality tag and dimension;
* sparse/binary/dense vector type;
* metadata as typed props, not opaque side maps for new work;
* tenant/RLS, time, version, and provenance fields;
* optional source text/content references.

Legacy `VectorRecord` remains a compatibility and migration shape only. New durable design should use the `VectorRecord -> ProximaRecord` migration services as the transition path, not extend `VectorRecord` as the long-term envelope.

Physical vector engines are access methods/layouts:

* SST/SWIFT for write-optimized and low-latency hot paths;
* VIPER/NOVA/RAPTOR/HELIX for columnar, progressive, high-dimensional, or tier-aware layouts;
* AXIS HNSW/IVF/PQ/LSH/Annoy as vector indexes;
* quantized codes as search/storage encodings with explicit quality policy.

HNSW/IVF/PQ indexes MUST be rebuildable from canonical vector records. If lossy quantized data becomes the only retained vector representation, that is no longer just a projection; it must be represented as an explicit canonical retention/compression policy with recall/error metadata.

Filtered vector search is a correctness surface, not just a performance feature. Tenant/RLS,
permitted principals, branch/time, retention, and typed metadata predicates must be available to the
ANN candidate-generation path where the chosen index family can support it. Post-filter and
overfetch strategies are compatibility fallbacks and must be visible in `EXPLAIN` with recall/failure
risk where they can return fewer than the requested matching top-k.

=== Observability

Observability has three logical submodalities: logs, metrics, and traces. They share one rule: raw ingest records are canonical unless retention policy explicitly replaces them with retained aggregate records.

Logs map to canonical records with:

* namespace;
* event timestamp and ingestion timestamp;
* severity;
* service/source/resource;
* message/body;
* attributes/labels;
* trace/span correlation fields when present;
* tenant/RLS fields.

Metrics map to canonical sample records with:

* namespace;
* metric name;
* sample timestamp;
* value and unit;
* labels;
* aggregation temporality/kind when relevant;
* tenant/RLS fields.

Traces map to canonical span records with:

* namespace;
* trace id, span id, parent span id;
* name and service;
* start/end timestamps;
* status;
* attributes/events/links;
* tenant/RLS fields.

Time partitions, label indexes, Tantivy log indexes, PromQL acceleration, trace assembly, and metric rollups are Layer 2 projections. Rollups become canonical only when a retention policy intentionally drops raw samples and preserves aggregate records with explicit window, aggregation, source range, and provenance metadata.

CHRONO/TST-style engines should become observability/time-series access methods over canonical records or retained aggregate records, not independent observability truth.

SIEM and observability competitiveness requires more than storing OTLP-shaped data. The long-term
surface should include:

* log search with full-text/analyzer support and structured predicates;
* metric rollups, downsampling, label indexes, and PromQL-style adapters;
* trace assembly, service maps, critical path lookup, and span/event correlation;
* profiles and high-cardinality event streams;
* alert/anomaly projections with explicit derivation and retention metadata;
* LLM/agent observability records for prompts, tool calls, retrieval evidence, token/cost metrics,
  evaluations, and safety events.

All of those are canonical records plus projections. Alerts, anomalies, and rollups become durable
facts only when written as canonical derived records with provenance.

=== SKS And Entity

Semantic Knowledge Store state spans entity, relationship, vector, document, graph, and event-log concepts. It must not add another durable substrate.

Canonical SKS truth decomposes into:

* entity records for semantic units;
* relationship edge records for entity relations;
* embedding cells for semantic search;
* document/source records for supporting evidence;
* event records for provenance, decisions, and temporal memory;
* typed semantic memory/category fields as record properties.

The legacy split `EntityStore`, `RelationsStore`, `CsrRelationsStore`, and ORION-backed entity storage are transition/projection paths. The long-term SKS service should compose:

* vector indexes for semantic recall;
* graph topology projections for relationship traversal;
* document/text indexes for evidence lookup;
* event-log replay for temporal/provenance history;
* query algebra for hybrid ranking and filtering.

Entity current-state materializations, semantic memory indexes, relationship CSR, and hybrid ranking caches are rebuildable views over canonical records and event history.

=== Event Log

The event log is the one modality where append-only records can be the canonical truth. That does not conflict with this mandate.

An event stream should be represented as canonical immutable records with:

* sequence/offset;
* stream id or entity id;
* event type;
* payload;
* causation/correlation ids;
* event time and append time;
* actor/principal;
* tenant/RLS fields;
* provenance and retention policy.

Event indexes, snapshots, point-in-time state, temporal query caches, and replay cursors are projections. They must be rebuildable from the append-only event records.

If event replay produces current entity/document/graph state, that state is a materialized projection unless it is also written as canonical state records with a clear derivation link to the event sequence.

== Non-Negotiable Architecture Rules

1. One durable record envelope: all documents, nodes, edges, and rows map to `ProximaRecord`.
2. One scalar/composite type system: use `ProximaType`/`ProximaValue`; do not extend legacy `SqlValue` for new semantics.
3. One transaction/RLS boundary: tenant and principal fields are enforced in scan/index iterators, not only in document or graph services.
4. Services are facades: `DocumentService` and graph services expose API semantics and planner semantics, but delegate durable reads/writes to canonical storage.
5. Specialized structures are projections: JSON indexes, full-text indexes, adjacency indexes, CSR/COO, HNSW, and columnar layouts are rebuildable from canonical records.
6. No new durable graph/document engine without ADR: a proposal must prove why relational/record storage plus adaptive projections cannot satisfy correctness and performance.
7. Protocol parity is required: REST, gRPC, Arrow Flight, PostgreSQL wire, and SDK behavior must resolve through the same logical model.
8. Performance claims require benchmarks: keeping ORION/CSR, CEDAR, or any separate projection requires workload-specific evidence.
9. Physical format flexibility is allowed; semantic fragmentation is not. LSM, row, PAX,
   columnar, Arrow, Parquet, Iceberg, Delta, graph, vector, and observability layouts are
   access methods/projections unless xCatalog marks a different authority mode with explicit
   snapshot, type, policy, write, and recovery semantics.
10. Optional relational constraints are real durable semantics when enabled. They must be
    cataloged, recovered, and protocol-consistent rather than implemented as API-layer checks.

== Target Technical Design

=== Canonical record mapping

Documents:

[source,text]
----
collection -> entity type / table
document id -> record identity
document body -> props Json/Map/Struct column
schema_id/document_type -> variation metadata
indexed paths -> generated columns or secondary index descriptors
version/updated_at -> record version/time fields
----

Graph nodes:

[source,text]
----
graph id + node id -> record identity
labels -> label bitmap/string-array projection
properties -> props Json/Map/Struct column
embedding refs -> embedding cells or AXIS index references
----

Graph edges:

[source,text]
----
graph id + edge id -> record identity
src/dst/label -> edge fields plus refs
properties -> props Json/Map/Struct column
adjacency key -> generated physical key (graph_id, src, label, dst, edge_id)
incoming key -> generated physical key (graph_id, dst, label, src, edge_id)
----

=== Query lowering

Document filters:

[source,text]
----
DocumentFilter
  -> JSON path normalized expression
  -> logical Filter/Project/Aggregate
  -> relational/record scan with optional path index
----

Graph pattern queries:

[source,text]
----
Cypher/SQL-PGQ/GraphQuery
  -> PatternMatch / HybridTraverse
  -> adjacency index or CSR topology projection
  -> edge/node record fetch with RLS predicates
----

Relational SQL:

[source,text]
----
SQL
  -> logical algebra
  -> relational rows / ProximaRecord scans
  -> optional document/graph/vector operators
----

=== Adaptive projection strategy

Use a tiered decision for graph topology:

[cols="1,2,2"]
|===
| Workload | Default Physical Path | Rationale

| Write-heavy graph
| relational adjacency tables with `(graph_id, src, label)` and `(graph_id, dst, label)` indexes
| avoids CSR rebuild amplification

| Mixed graph
| adjacency tables plus incremental hot CSR for high-degree or hot partitions
| preserves write throughput while accelerating repeated traversals

| Read-heavy/static graph
| epoch-built CSR/COO projection
| cache-efficient traversal and graph algorithms

| Distributed graph
| partitioned edge tables plus shard-local topology projections
| deterministic ownership and rebuildable projections
|===

Use a parallel decision for documents:

[cols="1,2,2"]
|===
| Workload | Default Physical Path | Rationale

| Point CRUD
| row/record store keyed by collection/id
| transaction/RLS consistency

| JSON path filters
| generated path indexes over canonical records
| no separate document heap needed

| Full-text
| Tantivy/inverted index referencing record ids
| rebuildable from canonical records

| Stable-shape analytics
| variation-aware columnar projection
| avoids scanning large JSON blobs
|===

== Module Ownership Trajectory

Workspace isolation must follow the stacked-durability rule. Modality crates own facade semantics,
operators, and projection/access-method families. They do not own independent durable truth unless an
accepted ADR explicitly creates a new canonical store.

[cols="1,2,2,2"]
|===
| Module / crate area | Owns long term | Must depend on | Must not own

| `proximadb-records` / data model foundation
| `ProximaRecord`, `ProximaType`, `ProximaValue`, record identity/version/time/provenance shapes
| kernel/proto/config contracts
| service behavior, protocol handlers, concrete engines

| `proximadb-storage-common` and future log/manifest contracts
| WAL/log/manifest primitives, segment abstractions, object-store-neutral IO, replay contracts
| data model, config, policy contracts
| document-only or graph-only persistence semantics

| future `proximadb-catalog`
| xCatalog schema, variation, index, layout, statistics, policy, branch, lineage, retention metadata
| data model and policy contracts
| REST/gRPC/pgwire handler logic or concrete projection builders

| `proximadb-document`
| document API semantics, JSON path normalization, update operators, full-text/path projection logic
| record store, catalog, query/filter contracts
| separate document heap, separate WAL, separate RLS boundary

| `proximadb-graph`
| graph API semantics, graph query AST/planner pieces, `PatternMatch`/`HybridTraverse`, topology projection APIs
| record/edge contracts, catalog, query contracts
| separate durable graph envelope, ORION/CSR as sole truth

| `proximadb-vector`
| ANN indexes, quantization, vector scoring, vector freshness/rebuild policy
| vector-bearing records, cataloged index metadata, storage-common
| vector-only metadata truth that diverges from records

| `proximadb-observability`
| log/metric/span/profile logical APIs, compression/rollup/trace projections
| record/event/retention/catalog contracts
| separate observability durable records outside `ProximaRecord`

| `proximadb-query`
| shared algebra, lowering, cost rules, cross-model operators, explain
| modality capability traits, catalog stats, policy context
| protocol-specific response shaping or concrete engine internals

| `proximadb-api` / runtime
| REST/gRPC/Arrow Flight/pgwire adapters, composition, auth/runtime wiring
| query/runtime/service contracts
| catalog, policy, or storage source-of-truth semantics
|===

== Terms

Canonical record::
The authoritative durable `ProximaRecord` representation of a document, node, edge, row, event, vector-bearing object, or other modality entity.

Facade::
An API, service, or planner boundary that provides modality-specific semantics without owning an independent durable system of record.

Projection::
A rebuildable physical structure derived from canonical records, such as JSON path indexes, full-text indexes, adjacency tables, CSR/COO topology, columnar variation tables, or HNSW indexes.

Adjacency table::
A relational edge projection keyed for graph traversal, usually by `(graph_id, src_node_id, edge_label, dst_node_id, edge_id)` and its incoming-edge mirror.

CSR::
Compressed Sparse Row. A compact adjacency-list projection using offset and target arrays. It is excellent for read-heavy traversal and graph algorithms, but it is expensive to mutate directly and should be rebuildable from canonical edge records.
