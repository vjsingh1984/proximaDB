= ENV GATE REGISTRY — the authoritative catalog of `PROXIMADB_*` environment gates
:status: Authoritative (CI-enforced by `scripts/check_env_gates.py`)
:updated: 2026-07-25

== Why this exists

221 unique `PROXIMADB_*` variables exist in the tree. Unregistered
proliferation is a cognitive-load tax and produces near-miss names — the
canonical incident: `PROXIMADB_IVF2` (WRITE: train A0 at compaction) vs
`PROXIMADB_IVF2_PROBE` (READ: use A0 at search), two default-OFF halves of
one feature whose confusion cost a full measurement cycle on 2026-07-25.
This file is the single source of truth: **a `PROXIMADB_*` name that is not
listed here fails CI** (`check_env_gates.py`, wired into
`make work-commit-check`).

== Naming rules (new gates MUST follow; existing names are frozen aliases)

1. `PROXIMADB_<AREA>_<SEMANTIC>` — area = subsystem (PAX, CACHE, SEARCH,
   WAL, QUEUE, TRACE, TEST…). Semantic says what it DOES, not the feature
   codename.
2. **Paired write/read gates carry `WRITE_`/`READ_` (or `EMIT_`/`USE_`)
   explicitly** — never two near-identical names. (Had the rule existed:
   `PROXIMADB_PAX_WRITE_A0_TRAIN` / `PROXIMADB_PAX_READ_COARSE_PROBE`.)
3. Booleans: presence-style gates accept `1|true|on|yes`; kill-switches are
   named for what they DISABLE (`…_DISABLE`) so unset = shipped default.
4. State the compile-time default and the flip-precondition in this table at
   introduction time; `TODO` is only legal for pre-registry legacy rows.
5. Renaming a shipped gate = alias forever (operational API, mixed-safety):
   support both names, document the alias here, never repurpose a name.

== Lifecycle tiers

*eval* (diagnostics/benchmarks; may change anytime) · *opt-in* (default-OFF
feature, flip-precondition documented) · *kill-switch* (default-ON, env is
the emergency off) · *config-mirror* (env overrides a config field) ·
*test-only* (never read in production paths).
