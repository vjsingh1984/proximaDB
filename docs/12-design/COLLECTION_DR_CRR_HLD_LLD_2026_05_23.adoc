== Purpose

This document is the consolidated HLD/LLD tracker for collection-level DR
and cloud object replication. It turns "enable CRR for this collection" into
a cataloged, billable, auditable control-plane workflow instead of a direct
provider-side bucket/container toggle.

The core decision:

* The customer-facing unit is a **collection DR policy** in xCatalog.
* The provider-facing unit is an AWS S3 replication rule or Azure Blob object
  replication rule scoped to a stable collection prefix.
* Provider replication is created only by ProximaDB control-plane automation.
* DR lifecycle is monotonic and retention-aware; customers cannot accidentally
  disable DR and leave us paying untracked destination, version, transaction,
  and egress costs.

mutable storage surface.

== Decision Index

[cols="1,3,4"]
|===
| ID | Question | Decision

| D1
| Is DR configured per collection, namespace, or tenant?
| Customer-facing DR is per collection. Namespace and tenant define the
  authority boundary and physical prefix. Tenant-level defaults may auto-apply
  to new collections, but xCatalog still materializes one policy per collection.

| D2
| Is namespace tied to tenant ID?
| Yes. Physical storage paths include stable `tenant_id`, stable
  `namespace_id`, and stable `collection_id`. Human namespace names are labels
  and must not drive object movement on rename.

| D3
| Can customers turn DR off?
| Not as an immediate toggle. Disable is a retirement workflow:
  `Active -> PendingRetirement -> Retired`, with explicit cost/retention
  acknowledgement and optional ops approval.

| D4
| Which tiers can use DR?
| Launch with Business and Enterprise. Pro may get a paid add-on later.
  FreeTrial and Team are not eligible.

| D5
| Should we use separate data buckets/containers by tier?
| Yes. Use separate provider storage pools: `pooled`, `business`,
  `enterprise`, and `enterprise-dedicated`. Mirror this on Azure with storage
  accounts and containers.

| D6
| Should Enterprise always get dedicated buckets/accounts?
| Default dedicated for large, regulated, custom KMS, custom region-pair, or
  high collection-count tenants. Small Enterprise tenants may start in the
  Enterprise shared pool if the contract allows it.

| D7
| Can S3 prefix replication enforce collection scope?
| Yes. Use replication rules filtered by
  `data/{tenant_id}/{namespace_id}/{collection_id}/`.

| D8
| Can Azure ADLS Gen2 HNS accounts use native object replication?
| Do not assume so. Azure object replication documentation calls out lack of
  support for hierarchical namespace accounts. HNS/ADLS workloads need either a
  non-HNS Blob DR account or a ProximaDB-controlled replication worker.

| D9
| Do deletes replicate?
| Default: conservative. Delete marker replication requires explicit policy
  and retention validation. Collection delete schedules DR retirement; it does
  not immediately erase replicated destination versions.

| D10
| How do we avoid unbilled provider charges?
| Provider replication is provisioned only after billing approval and cost-owner
  persistence. Reconciler marks out-of-band drift and billing mismatch as
  `dr_unhealthy` / `billing_blocked`.
|===

=== Control Plane Responsibilities

The control plane owns:

* tenant and tier entitlement;
* collection DR policy lifecycle;
* provider rule creation and drift reconciliation;
* billing and cost-owner binding;
* namespace/collection delete guards;
* restore/failover readiness metadata;
* audit evidence and support workflows.

The data plane owns:

* writing all collection bytes under the assigned storage prefix;
* emitting WAL/manifest/snapshot checkpoints that can prove restore
  completeness;
* surfacing DR health metadata to query planning and collection introspection;
* rejecting direct writes to DR destination paths.

Provider APIs own:

* physical asynchronous replication when native replication is supported;
* object versioning behavior;
* provider-side replication lag and error state;
* destination object creation.

== HLD: Policy Boundaries

=== Tenant, Namespace, Collection

DR policy is collection-level, but collection identity must be nested under a
tenant-bound namespace:

[source]
----
tenant_id
  namespace_id
    collection_id
      CollectionDrPolicy
----

Rules:

* A namespace belongs to exactly one tenant.
* A collection belongs to exactly one namespace.
* A collection DR policy cannot target a prefix outside that tenant/namespace.
* Namespace renames do not change object prefixes.
* Collection renames do not change object prefixes.
* Namespace delete is rejected while any child collection has active or pending
  DR retirement.

=== Authority Mode

`CollectionDrPolicy` is metadata authority for DR. Provider rules are
rebuildable projections of that policy. If provider state diverges from
xCatalog, xCatalog wins and the reconciler either repairs provider state or
marks the collection unhealthy.

DR replication does not change:

* collection schema authority;
* WAL commit authority;
* RLS/policy authority;
* tenant ownership;
* billing ownership;
* supported-surface maturity.

=== Tier Gate

Launch policy:

[cols="2,2,3"]
|===
| Tier | DR status | Notes

| FreeTrial
| Disabled
| No CRR. Shared pooled object store only.

| Team
| Disabled
| No CRR. Shared pooled object store only.

| Pro
| Deferred add-on
| Possible future paid add-on. Do not launch initially unless pricing and
  support workflows are ready.

| Business
| Enabled by add-on or bundle
| Use Business tier storage pools and explicit billing approval.

| Enterprise
| Enabled
| Prefer dedicated tenant storage accounts/buckets for regulated, large, custom
  KMS, custom region-pair, or high rule-count tenants.
|===

Downgrade rule:

* Business/Enterprise tenants with active DR cannot downgrade into an
  ineligible tier until each DR policy is either retained as a paid add-on or
  scheduled for retirement.

== HLD: Storage Pool Strategy

Use tier-classed provider pools rather than one global bucket/account:

[cols="2,3,4"]
|===
| Pool | Tenants | Purpose

| `pooled`
| FreeTrial, Team, non-DR Pro
| Lowest operational overhead. No per-collection CRR rules.

| `business`
| Business and future DR-enabled Pro
| Shared Business source/destination pools with prefix-scoped collection rules.

| `enterprise`
| Small Enterprise tenants when contract permits shared infra
| Shared Enterprise pool with stricter KMS, monitoring, and rule budgeting.

| `enterprise-dedicated`
| Large/regulated/custom Enterprise tenants
| One provider bucket/storage-account pair per tenant and region pair.
|===

Why this shape:

* avoids bucket/account sprawl for low-cost tenants;
* lets Business DR costs and rule limits be managed separately from pooled
  workloads;
* avoids Enterprise noisy-neighbor and rule-limit issues;
* maps cleanly to custom KMS, private endpoints, residency, and audit evidence;
* keeps Azure parallel to AWS by using account/container pool classes.

== LLD: Physical Path Contract

All DR-eligible collection data uses this root:

[source]
----
data/{tenant_id}/{namespace_id}/{collection_id}/
----

Subprefixes:

[source]
----
data/{tenant_id}/{namespace_id}/{collection_id}/wal/
data/{tenant_id}/{namespace_id}/{collection_id}/manifests/
data/{tenant_id}/{namespace_id}/{collection_id}/snapshots/
data/{tenant_id}/{namespace_id}/{collection_id}/segments/
data/{tenant_id}/{namespace_id}/{collection_id}/indexes/
data/{tenant_id}/{namespace_id}/{collection_id}/restore-checkpoints/
----

Rules:

* Temporary compaction files use `_tmp/` under the same collection root only if
  they are safe to replicate. Otherwise they must live outside the DR prefix.
* Provider lifecycle rules must not delete source bytes before manifest and WAL
  retention prove that restore RPO is still satisfied.
* Destination lifecycle rules are owned by DR policy, not by generic cold-tier
  lifecycle automation.
* A collection cannot be moved to a new physical prefix without a cataloged
  relocation workflow.

== LLD: AWS S3 Automation

Preconditions:

* source and destination buckets exist;
* source and destination bucket versioning is enabled;
* KMS key policy allows S3 replication role use when SSE-KMS is enabled;
* source bucket has replication IAM role;
* destination bucket policy accepts replication writes from the role;
* billing approval has been recorded;
* source prefix exists or is reserved.

Replication rule shape:

[source,json]
----
{
  "Role": "arn:aws:iam::<account-id>:role/proximadb-dr-replication",
  "Rules": [
    {
      "ID": "dr-<tenant_id>-<namespace_id>-<collection_id>-v<policy_version>",
      "Status": "Enabled",
      "Priority": 100,
      "Filter": {
        "Prefix": "data/<tenant_id>/<namespace_id>/<collection_id>/"
      },
      "DeleteMarkerReplication": {
        "Status": "Disabled"
      },
      "Destination": {
        "Bucket": "arn:aws:s3:::proximadb-prod-<region>-<pool>-dr",
        "StorageClass": "STANDARD"
      }
    }
  ]
}
----

Provider notes:

* Prefix filters are the default S3 mechanism for collection-scoped rules.
* Delete marker replication is disabled by default. Enable only for policies
  where destination version retention and restore semantics have been tested.
* S3 replication rule limits require bucket sharding or dedicated buckets for
  high collection counts.
* Existing object replication is a separate operation from live replication.
  `replicate_existing_objects` must be explicit and billable.

== LLD: Azure Blob / ADLS Automation

Preconditions for native Azure Blob object replication:

* source and destination storage accounts exist;
* source and destination containers exist;
* blob versioning is enabled on source and destination accounts;
* change feed is enabled on the source account;
* destination account/container is not used for application writes;
* storage-account capabilities support object replication.

Rule shape:

[source,json]
----
{
  "sourceAccount": "<source-storage-account>",
  "destinationAccount": "<destination-storage-account>",
  "rules": [
    {
      "ruleId": "dr-<tenant_id>-<namespace_id>-<collection_id>-v<policy_version>",
      "sourceContainer": "<source-container>",
      "destinationContainer": "<destination-container>",
      "filters": {
        "prefixMatch": [
          "data/<tenant_id>/<namespace_id>/<collection_id>/"
        ]
      }
    }
  ]
}
----

ADLS/HNS rule:

* If the source storage account has hierarchical namespace enabled, do not use
  native object replication as the assumed path.
* Preferred path for HNS workloads:
  . write canonical DR objects into a non-HNS Blob account/container that
    supports object replication; or
  . run a ProximaDB-controlled replication worker that tails WAL/manifest
    checkpoints and copies committed objects.
* The control plane records `provider = AzureAdlsHns` and
  `provider_binding = replication_worker` so the path is explicit and
  explainable.

== LLD: State Machine

[source,mermaid]
----
stateDiagram-v2
  [*] --> Disabled
  Disabled --> PendingBillingApproval: request_enable
  PendingBillingApproval --> PendingProviderProvisioning: approve_billing
  PendingBillingApproval --> Disabled: cancel_before_provider
  PendingProviderProvisioning --> Active: provider_rule_created
  PendingProviderProvisioning --> Disabled: provisioning_failed_no_rule
  Active --> SuspendedByOps: ops_suspend
  SuspendedByOps --> Active: ops_resume
  Active --> PendingRetirement: request_retire
  PendingRetirement --> Retired: provider_rule_disabled_and_retention_recorded
  Retired --> [*]
----

Invalid transitions:

* `Active -> Disabled`
* `PendingProviderProvisioning -> Disabled` after a provider rule exists without
  an explicit cleanup event;
* `Retired -> Active` with the same provider rule ID;
* tenant downgrade while any policy is `Active`, `SuspendedByOps`, or
  `PendingRetirement` unless billing remains active.

== LLD: Reconciler

The reconciler is idempotent and runs from xCatalog policy state.

Loop:

. Load all policies in `PendingProviderProvisioning`, `Active`,
  `SuspendedByOps`, and `PendingRetirement`.
. For each policy, fetch provider replication state.
. Validate provider state:
  * rule exists;
  * prefix matches exactly;
  * destination bucket/container matches;
  * versioning/change feed prerequisites remain enabled;
  * IAM/KMS binding is intact;
  * provider rule status matches desired xCatalog state.
. Repair safe drift automatically.
. Mark unsafe drift as `DrHealthState::Drifted` or `ProviderBlocked`.
. Emit `collection_dr_events`.
. Update cost metering with destination bytes, versions, requests, and lag.

Unsafe drift examples:

* prefix changed;
* rule removed manually;
* destination changed;
* versioning disabled/suspended;
* KMS key policy revoked;
* Azure policy re-created with a new policy ID;
* destination accepts application writes.

== LLD: Billing And Cost Controls

Billable units:

* replicated destination bytes;
* retained non-current versions;
* provider replication PUT/COPY/write transactions;
* provider read/change-feed processing;
* cross-region data transfer;
* restore validation reads;
* dedicated bucket/account/KMS/private endpoint cost where applicable.

Controls:

* No provider rule is created without `billing_approval_id`.
* `cost_owner_tenant_id` is mandatory.
* DR metering has a hard invariant: if provider rule exists and no active
  billing binding exists, mark `BillingBlocked` and page ops.
* Cost estimates are shown before enablement and updated after first full day of
  metering.
* Per-tenant invoices include DR policy ID, collection ID, source region,
  destination region, and usage dimensions.

== LLD: Delete, Retention, And Legal Holds

Collection delete:

. Reject immediate delete when DR policy is active.
. Create a retention-aware delete plan.
. Transition DR policy to `PendingRetirement`.
. Disable provider rule after final checkpoint and retention acknowledgement.
. Keep destination versions until `destination_retention_days` expires or legal
  hold releases.
. Mark collection tombstoned in xCatalog only after the authoritative delete
  commit is durable.

Namespace delete:

* Rejected while any child collection DR policy is not `Retired`.

Tenant delete:

* Requires all namespaces/collections to complete DR retirement.
* Dedicated Enterprise buckets/accounts can be scheduled for provider-level
  deletion after retention and legal-hold checks.

Delete replication:

* Default `replicate_deletes = false`.
* If true, S3 delete marker replication or Azure delete behavior must be
  explicitly validated for the collection restore model.

== LLD: Restore, Failover, And Failback

Restore readiness requires:

* latest replicated manifest;
* WAL checkpoint within RPO;
* segment/snapshot objects for the manifest;
* index rebuild metadata or replicated index objects;
* tenant and collection metadata exported to the DR control plane;
* KMS/decryption access in the DR region.

Failover flow:

. Mark source region impaired.
. Freeze writes or route writes to new primary according to contract.
. Select latest complete DR checkpoint.
. Rebuild or attach data plane from destination bucket/container.
. Rehydrate xCatalog metadata from replicated metadata export.
. Run collection consistency checks.
. Promote DR region endpoint.
. Emit failover audit event and billing state transition.

Failback is a separate planned workflow. Do not assume provider replication can
reverse automatically without a new policy and billing approval.

== Security

IAM/RBAC:

* Customers cannot create provider replication rules directly.
* Control-plane service account owns provider rule changes.
* Provider IAM roles are scoped to exact prefixes whenever provider policy
  expressiveness allows it.
* Destination buckets/containers reject application writes.

KMS:

* Source and destination KMS keys must allow provider replication use.
* Enterprise dedicated tenants may bring custom KMS/key vault policies.
* KMS policy drift is a provider-blocking DR health error.

Audit:

* Every policy state transition is audit logged.
* Every provider rule create/update/delete is audit logged.
* Every blocked delete/downgrade due to DR is audit logged.

== Test Plan

Unit tests:

* policy state-machine valid/invalid transitions;
* tier entitlement matrix;
* prefix construction and tenant/namespace/collection escaping;
* provider rule renderers for S3 and Azure;
* billing gate rejects provider provisioning without approval;
* namespace/collection delete guard.

Integration tests:

* enable DR policy and observe provider rule desired state;
* out-of-band provider rule deletion marks `Drifted`;
* downgrade blocked while DR is active;
* collection delete schedules retirement instead of deleting destination bytes;
* Azure HNS account routes to unsupported/worker path;
* S3 rule-count sharding planner chooses dedicated bucket when needed.

Operational tests:

* restore from DR destination within RPO;
* failover drill;
* failback planning drill;
* billing reconciliation against provider usage;
* KMS permission revocation alert;
* destination write rejection.

== Open Questions

. Should Business include DR by default or expose it as an add-on? Default
  recommendation: add-on until usage/cost curves are proven.
. Should Pro receive a DR add-on at launch? Default recommendation: no. Add
  after Business/Enterprise workflows are stable.
. What is the first supported Azure HNS story? Default recommendation:
  non-HNS Blob DR account first; replication worker later.
. Should delete marker replication be enabled for all DR? Default
  recommendation: no. Enable only for contracts that require delete-state
  mirroring and have retention tests.
. Do we replicate indexes or rebuild from segments/WAL? Default recommendation:
  replicate manifests/segments/WAL first; indexes can be replicated for lower
  RTO but must be rebuildable.
