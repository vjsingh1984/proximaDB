= INT-2.5 Bincode Compatibility Memo
:toc:
:toclevels: 2

Status: Design proposal — pending review +
Date: 2026-05-23 +
Decides: how `EmbeddingCell.values` flips from `Vec<f32>` to `EmbeddingValues` without breaking existing v1 bincode WAL files.

[NOTE]
====
**2026-06-05 correction.** The shipped `EmbeddingCell::serialize` drifted from
§Step 2 below: it had been changed to *skip* the trailing `precision_epoch`
field when `None` (emitting 0 bytes). Because bincode is positional, that
desynced the decoder — every `deserialize_batch` of a `None`-epoch record (the
common case) failed with `io error: unexpected end of file`, and `Vec`
boundaries became ambiguous. This broke ~16 WAL serialization/recovery tests.
The fix restores §Step 2's design: on binary (non-human-readable) wires
`precision_epoch` is ALWAYS emitted (`None` = one `0x00` Option-tag byte);
human-readable JSON still omits the key. The `embedding_cell_bincode_fixture_locks_pre_2_5b_layout`
fixture was updated to include the trailing `0x00`.
====

== Problem

PR 1 added the `EmbeddingValues` typed enum but kept `EmbeddingCell.values: Vec<f32>` as the durable storage field for back-compat. To realize the fp16 storage win, INT-2.5b must flip the field type so producers can carry typed values through to the PAX writer (INT-3).

The complication: bincode is positional. The derived `Serialize` impl writes each field's bytes in declaration order with no field tags. If `values: Vec<f32>` becomes `values: EmbeddingValues`, the derived impl emits a 4-byte enum discriminant followed by the variant payload. **Every existing v1 WAL file becomes unreadable.**

This memo picks the bincode strategy before code lands.

== Constraints

. **Zero new field positions in the v1 bincode layout.** Existing v1 WAL files MUST stay readable by post-2.5b binaries.
. **Byte-identical writes for fp32 records on the v1 path.** Operators with the precision-schema-v2 flag OFF (the default) should see no on-disk change.
. **The v2 path (segment header present) can use a different shape.** INT-2b already gates the v2 segment header on the env flag; the bincode payload inside a v2 segment is free to use the natural enum layout.
. **The 145 read sites must migrate cleanly.** The dominant access pattern is `.values.len()` / `.values.iter()` / `.values.as_slice()`. The migration should be greppable + mechanically applicable.

== Options considered

=== Option A: Custom Serialize/Deserialize on EmbeddingCell (CHOSEN)

`EmbeddingCell.values` becomes `EmbeddingValues` in memory. Custom serde impls handle the v1 path:

* **Serialize**: extract the fp32 representation via `EmbeddingValues::to_fp32_owned()` and serialize as `Vec<f32>` at the same field position. Bincode byte layout for the cell is identical to PR 1's. Non-fp32 variants get downconverted to fp32 (lossy) on the v1 path; the PR 3b `validate_records_for_schema_v1` ingest guard already rejects non-fp32 records when the flag is off, so this lossy path is never hit in production.
* **Deserialize**: read `Vec<f32>` at the same field position and wrap in `EmbeddingValues::Fp32(v)`. Existing v1 files load with their fp32 bytes intact and a Fp32 variant tag in memory.

For the v2 path (records inside a PWAL-prefixed segment from INT-2b): introduce a separate `serialize_batch_v2_typed` method on the WAL serializer that uses the natural enum layout. The reader dispatches on the segment header — v1 segments → v1 deserializer (fp32-shaped); v2 segments → v2 deserializer (enum-shaped).

**Pros**:

* Byte-identical for v1 writes today (every record is fp32).
* Existing v1 WAL files read unchanged.
* No `schema_version` bump cluster-wide; rolling deploy works.
* The v2 segment header already exists (INT-2b) — repurpose it as the dispatch lever.

**Cons**:

* Custom serde impls are delicate code. Need round-trip tests against every existing v1 WAL fixture.
* Lossy v1 path for non-fp32 records, but blocked by the existing validator.

=== Option B: schema_version cluster-wide bump

Change the field type, bump `ProximaRecord.schema_version` to 2, require all WAL files to be re-written under the new shape.

**Pros**: simplest code.

**Cons**: forces a one-shot migration. Existing v1 files become unreadable. Breaks rolling deploy completely. Rejected: violates Constraint 1.

=== Option C: parallel field

Keep `values: Vec<f32>` AND add `typed_values: Option<EmbeddingValues>`.

**Pros**: no derived-serde shape change at the existing field.

**Cons**: adds a new field at the end of the struct → bincode-positional violation for old readers reading new bytes (they hit EOF on the new field). Also confusing: two paths in the data model where one should be authoritative. Rejected: violates Constraints 1 and 4 (the new field invites split-brain reads).

== Chosen approach (Option A) — execution plan

=== Step 1: helper to extract fp32 bytes from any variant

Already shipped: `EmbeddingValues::to_fp32_owned()`. Returns a `Vec<f32>` for every variant (promote on read; lossy for non-fp32 → fp32 conversion which is unavoidable).

=== Step 2: custom Serialize on EmbeddingCell

Field order matches PR 1: `model_id, modality, values, dim, precision, precision_epoch`. The `values` field writes as a `Vec<f32>` regardless of variant — exactly the bytes a derived impl would write for `values: Vec<f32>`.

[source,rust]
----
impl Serialize for EmbeddingCell {
    fn serialize<S: Serializer>(&self, serializer: S) -> Result<S::Ok, S::Error> {
        use serde::ser::SerializeStruct;
        let mut state = serializer.serialize_struct("EmbeddingCell", 6)?;
        state.serialize_field("model_id", &self.model_id)?;
        state.serialize_field("modality", &self.modality)?;
        // KEY: write the fp32 view, not the enum.
        state.serialize_field("values", &self.values.to_fp32_owned())?;
        state.serialize_field("dim", &self.dim)?;
        state.serialize_field("precision", &self.precision)?;
        state.serialize_field("precision_epoch", &self.precision_epoch)?;
        state.end()
    }
}
----

=== Step 3: custom Deserialize on EmbeddingCell

Reads the v1 layout (`Vec<f32>` at the `values` position) and wraps in `EmbeddingValues::Fp32`.

=== Step 4: field type flip

`pub values: Vec<f32>` → `pub values: EmbeddingValues`. Mechanical compile-error-driven migration of construction sites (every site that builds `EmbeddingCell { values: vec![...], ... }` becomes `EmbeddingCell { values: EmbeddingValues::Fp32(vec![...]), ... }`).

=== Step 5: 145-site read migration

Pattern-based. Most common patterns and their replacements:

[cols="2,2"]
|===
| Today | After 2.5b

| `&cell.values` | `&*cell.as_fp32_cow()` (zero-copy for fp32)
| `cell.values.len()` | `cell.values.len()` (works, the enum has `.len()`)
| `cell.values.iter()` | `cell.as_fp32_cow().iter()` (one-shot allocate for non-fp32; zero-copy for fp32)
| `cell.values.clone()` | `cell.values.to_fp32_owned()` (always owned)
| `cell.values.as_slice()` | `&*cell.as_fp32_cow()`
| `vec![ ... ] == cell.values` | `vec![ ... ] == *cell.as_fp32_cow()`
|===

Greppable migration via `sed` for the simple cases; remaining sites need eye review (the assertions and the proto bridges).

=== Step 6: v2 segment payload using the natural enum shape

After 2.5b lands, INT-3 can implement `BincodeSerializer::serialize_batch_v2_typed` that emits records using the natural enum layout (no custom serde — `derive(Serialize)` on a wrapper type that has `values: EmbeddingValues`). The v2 WAL writer chooses this when the active config + collection precision indicate fp16+ storage.

== Open questions for review

. **Is "lossy v1 path for non-fp32 records" actually unreachable?** The PR 3b validator runs at ingest. Are there code paths that construct non-fp32 records that bypass ingest (recovery? compaction? cross-region replication)? If yes, the v1 serializer needs an explicit `debug_assert!(matches!(self.values, EmbeddingValues::Fp32(_)))` to catch the bug rather than silently downconvert.
. **Should the custom Deserialize set `precision = Fp32` unconditionally, or honor whatever was on disk?** The on-disk `precision` field is already advisory. Setting `Fp32` matches the actual wrapped variant. Honoring the on-disk value preserves intent for diagnostic purposes. Recommend setting to `Fp32` so the in-memory invariant `cell.precision == cell.values.scalar_type()` holds.
. **Does the 145-site migration land in 2.5b or as a separate 2.5b' commit?** Splitting would mean the field type flip relies on `Deref<Target=Vec<f32>>` or similar trickery temporarily so old read sites compile. Cleaner to land both in one commit — the compiler is the test that the migration is complete.
