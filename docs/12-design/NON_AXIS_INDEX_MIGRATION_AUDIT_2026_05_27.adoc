= Non-AXIS Index Migration Audit
:toc:
:toclevels: 3
:date: 2026-05-27

== Status: ACTIVE TD-064 Related Work

== Purpose

Document indexes that exist outside the AXIS management system for migration planning.
Migrating these indexes to AXIS provides:

* Unified tiering and caching via AxisTieringManager
* Consistent filterable metadata support (TD-064) via the shared
  `FilterableMetadataCache` helper now shipped with AXIS
  (see `src/index/axis/filterable_metadata.rs`)
* Single point of control for index lifecycle
* Reduced code duplication

== Verified State (2026-05-27)

Grep against `crate::index::hnsw`, `crate::index::ivf`, `crate::index::diskann`,
`crate::index::sparse_hnsw` shows **no external production users** outside
their own modules. Mentions in `src/core/search/filter_pushdown_engine.rs`,
`src/bench/ann_benchmarks/adapter.rs`, and docs are *names only* (variants,
strings, comments) — not type imports. These modules are effectively orphan
code paths from the perspective of the live search path, which already routes
through AXIS.

This means the migration is largely a **delete/replace** rather than a
porting exercise: the AXIS-native equivalents are already the production
implementations. Deletion can be done in isolation per module once unit
tests are reviewed for any unique coverage worth preserving.

== AXIS-Native Filterable Metadata Coverage

All four AXIS-native indexes now compose `FilterableMetadataCache` and
implement the TD-064 `AxisVectorIndex` trait methods (`add_with_metadata`,
`search_with_predicate`, `supports_predicate_search`,
`configure_filterable_fields`):

* `AxisHnswIndex` — native skip-through traversal predicate (best support)
* `UnifiedIvfIndex` — oversample 2× then post-filter
* `AxisAnnoyIndex` — oversample 2× then post-filter (Annoy is static)
* `AxisLshIndex` — oversample 2× then post-filter

IVF / Annoy / LSH inline-traversal predicate pushdown is tracked under
TD-064 Phase 3. Today the oversample-and-filter shape is correct and
disclosed via EXPLAIN; only the recall headroom differs.

== Non-AXIS Indexes

=== src/index/hnsw/ (FilteredHNSWIndex)

*Status: Legacy - Duplicate Functionality*

==== Description

Filtered HNSW index with metadata-aware graph traversal.
Exists as a standalone implementation separate from AXIS HNSW.

==== Key Features

* Filtered search with early pruning
* Graph traversal with metadata lookup
* Adaptive ef based on filter selectivity

==== Migration Strategy

*Phase 1* (1-2 days): Compare functionality with `AxisHnswIndex`
*Phase 2* (2-3 days): Port unique features to AXIS HNSW (if any)
*Phase 3* (1 day): Deprecate and remove

==== Migration Blockers

* None - this is pure duplication

=== src/index/ivf/ (FilteredIVFIndex)

*Status: Legacy - Duplicate Functionality*

==== Description

Filtered IVF (Inverted File) index with metadata-aware posting list filtering.
Exists as a standalone implementation separate from AXIS IVF.

==== Key Features

* Filtered posting list search
* Metadata statistics per posting list
* Early pruning of non-matching postings

==== Migration Strategy

*Phase 1* (1-2 days): Compare functionality with `UnifiedIvfIndex`
*Phase 2* (2-3 days): Port unique features to AXIS IVF (if any)
*Phase 3* (1 day): Deprecate and remove

==== Migration Blockers

* None - this is pure duplication

=== src/index/diskann/ (DiskANN Index)

*Status: External Integration Candidate*

==== Description

DiskANN implementation for billion-scale vector search with SSD optimization.
Currently exists as a standalone module without AXIS integration.

==== Key Features

* Vamana graph structure (different from HNSW)
* SSD-optimized layout for sequential reads
* Product quantization for compression
* 1B+ vector capacity target

==== Migration Strategy

*Phase 1* (3-5 days): Design DiskANN as a new `AxisDiskannIndex` type
*Phase 2* (5-7 days): Implement AxisVectorIndex trait for DiskANN
*Phase 3* (2-3 days): Wire into AxisTieringManager for tiered caching
*Phase 4* (1-2 days): Add TD-064 filterable metadata support

==== Migration Blockers

* DiskANN graph structure is fundamentally different from HNSW/IVF
* Requires custom tiering logic for SSD-optimized layout
* May need specialized cache policies

=== src/index/geo/ (Geo-Spatial Index)

*Status: Domain-Specific - Keep Separate*

==== Description

Geospatial index for location-based queries (geohash, R-tree).
This is domain-specific functionality that doesn't fit vector similarity.

==== Migration Strategy

*Keep separate* - this is not a vector similarity index and doesn't belong in AXIS.

=== src/index/edr/ (EDR Index)

*Status: Already Integrated - Migration Complete*

==== Description

Edit Distance Reasoning index for fuzzy text matching.
Already integrated into AxisVectorIndex trait as `EdrIndex` variant.

==== Migration Strategy

*Complete* - No action needed.

== Benefits of Migration

=== Code Consolidation

* Eliminate duplicate HNSW/IVF implementations
* Single source of truth for filterable metadata handling
* Unified testing infrastructure

=== Infrastructure Benefits

* All indexes benefit from AxisTieringManager
* Consistent memory management and eviction policies
* Unified observability and metrics

=== TD-064 Synergy

Migrating non-AXIS indexes enables:

1. Consistent filterable metadata support across all indexes
2. Unified predicate-aware search API
3. Single EXPLAIN disclosure for all index types
