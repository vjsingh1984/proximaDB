== Purpose

This document is the high-level and low-level design for reducing storage footprint and I/O by
combining physical co-location, modality-aware codec selection, and lossless compression. It turns
the codec/PAX/proximablocks review into a tracked implementation plan.

Authoritative context:

* `docs/12-design/RELATIONAL_DOCUMENT_GRAPH_CONVERGENCE_2026_05_14.adoc`
* `docs/12-design/RELATIONAL_STORAGE_FORMAT_AND_INTEROPERABILITY_2026_05_19.adoc`
* `docs/12-design/COMPETITIVE_OLTP_OLAP_MPP_TRAJECTORY_2026_05_20.adoc`
* `docs/12-design/adr/ADR-004-unified-explain-contract.adoc`
* `docs/12-design/adr/ADR-010-pax-block-format.adoc`

Key principle: PAX blocks, vector spatial layouts, graph CSR/COO, JSON path stripes, and ANN
fragments are Layer 2 projections or access methods unless a separate ADR promotes a retained
aggregate to canonical authority. They must be repairable from Layer 0/1 and must not introduce
hidden durable semantics.

== Non-Negotiable Invariants

* `ProximaRecord` plus `ProximaType`/`ProximaValue` remains the semantic record authority.
* PAX compression decisions never change visible values. The default storage path is lossless.
* Dimensionality reduction may choose physical row order or index keys; it must not replace exact
  vector payloads in authoritative storage.
* Lossy quantization, PQ, sketches, and learned projections are allowed only as cataloged
  projections with explicit `loss_policy`, freshness, rebuild source, and EXPLAIN metadata.
* `proximadb-codec` is the canonical codec and codec-selection layer. Compute `proximacodec`
  should provide runtime routing, SIMD/GPU dispatch, and compatibility wrappers only.
* PAX readers must be able to skip blocks/stripes from metadata before decoding payload bytes.
* Every automatic layout or codec decision must be explainable and must record rejected candidate
  reasons when a cheaper or smaller codec is not selected.

== LLD: Canonical Codec Profile

`proximadb-codec` should own the canonical codec-decision API. The compute module may call this
API and then route the selected codec implementation through scalar, SIMD, GPU, or fallback paths.

[source,rust]
----
pub struct CompressionProfile {
    pub authority_mode: AuthorityMode,
    pub loss_policy: LossPolicy,
    pub workload_profile: WorkloadProfile,
    pub storage_specialization: StorageSpecialization,
    pub hotness: AccessTemperature,
    pub random_access_granularity: RandomAccessGranularity,
    pub target_compression_ratio: Option<f32>,
    pub target_decode_ns_per_value: Option<u64>,
    pub max_encode_cpu_ms_per_block: Option<u64>,
    pub block_context: BlockContext,
}

pub struct LayoutHints {
    pub modality: ColumnModality,
    pub physical_ordering: Option<PhysicalOrdering>,
    pub correlation_group: Option<CorrelationGroupId>,
    pub vector_layout: Option<VectorLayoutHint>,
    pub graph_layout: Option<GraphLayoutHint>,
    pub json_layout: Option<JsonLayoutHint>,
    pub dictionary_scope: DictionaryScope,
    pub sortedness: Sortedness,
}

pub struct CodecDecision {
    pub scheme: ProximaScheme,
    pub parameters: CodecParameters,
    pub expected_ratio: f32,
    pub expected_decode_ns_per_value: Option<u64>,
    pub exact_reconstruction: bool,
    pub rejected_candidates: Vec<RejectedCodecCandidate>,
}
----

Selection rules:

* If `loss_policy = ExactOnly`, reject lossy schemes even when they are smaller.
* If `hotness = Hot`, prefer codecs with predictable low decode latency and small random-access
  granularity.
* If `hotness = Cold`, allow larger blocks and heavier entropy coding when profiling shows an I/O
  win.
* If `physical_ordering` declares a correlation order, evaluate delta/FOR/XOR/learned-correlation
  families before generic dictionary or raw fallback.
* If the candidate ratio is worse than a configured threshold, store raw and record the rejected
  reason.

== LLD: PAX Stripe Metadata V2

ADR-010 keeps the fixed PAX block shape. This blueprint extends the logical metadata carried by a
stripe. The physical encoding can remain backward-compatible by using existing offsets for a
parameter blob or by bumping the block format version when fixed headers are exhausted.

[cols="1,3"]
|===
| Field | Purpose

| `encoding_id`
| Stable `ProximaScheme` identifier.

| `codec_params_offset`, `codec_params_len`
| Optional parameter blob for base vectors, dictionaries, bit widths, model coefficients, shape
  dictionaries, or graph degree buckets.

| `layout_id`
| Declares `None`, `SortByPrimaryKey`, `SortByTime`, `VectorSpatial`, `GraphVertexOrder`,
  `JsonShapeOrder`, or future layout families.

| `layout_params_offset`, `layout_params_len`
| Optional row permutation, spatial projection id, vertex remap id, shape dictionary id, or
  rebuild epoch reference.

| `stats_profile_id`
| Catalog reference for profiling results used to select the codec.

| `loss_policy`
| `ExactOnly`, `ProjectionMayBeLossy`, or `ExternalAuthoritative`.

| `pruning_summary`
| Min/max, null count, distinct hint, bloom/frequency sketch, spatial code range, degree bucket,
  or JSON path presence summary.
|===

Reader rules:

* Unknown exact codecs must fail closed with a clear unsupported-codec error.
* Unknown lossy projection codecs must never be used to answer exact reads.
* A reader may skip a stripe from `pruning_summary` before loading codec parameters.
* A reader must emit codec and layout metadata into EXPLAIN when requested.

== LLD: Lossless Vector Co-Location

Goal: improve exact vector storage density and disk locality without changing vector values.

Build path:

1. Sample embeddings from the compaction input.
2. Fit or reuse a cataloged layout projection: PCA, random projection, IVF centroid assignment,
   Hilbert/Morton/Z-order over reduced coordinates, or an existing spatial encoder.
3. Assign each row a physical layout key. The key is used only for sorting and pruning metadata.
4. Sort rows within the PAX compaction unit by `(tenant, partition, vector_layout_key, primary key)`.
5. Choose an exact vector codec per block or cluster:
   * `VectorRawF32` fallback.
   * `VectorBaseXorEntropy`: store an exact f32 base vector, XOR each f32 bit pattern with the
     base, and entropy-code byte planes or positions.
   * `VectorDeltaF32Bytes`: delta byte planes only when exact reconstruction is proven.
6. Store the row permutation and layout metadata needed to map row directory entries to stripe
   positions.

Safety rules:

* The base vector is stored exactly in the block or dictionary scope.
* The payload reconstructs identical IEEE-754 f32 bit patterns.
* ANN quantization and PQ may share layout projections but are separate lossy index projections.
* If compression ratio or decode budget misses the configured threshold, write raw f32 stripes.

Current pilot:

* `proximadb-codec::baseline::functions::vector_base_xor` implements the first exact
  `VectorBaseXorEntropy` candidate for non-null, fixed-dimension f32 vector rows.
* The pilot stores an exact base vector and run-codes zero/literal XOR words. It exposes
  `VectorBaseXorProfile` with raw bytes, encoded bytes, compression ratio, byte/value cost, and
  run counts for fallback decisions.
* `benches/bench_23_codec_vector_base_xor.rs` profiles raw decode, base-XOR encode, and base-XOR
  decode on representative 1024 x 384 vector blocks:
  ** co-located identical rows: 1,572,864 raw bytes to 1,553 encoded bytes, ratio 1012.8, selected;
  ** co-located sparse drift: 1,572,864 raw bytes to 87,485 encoded bytes, ratio 18.0, selected;
  ** normalized random fallback: 1,572,864 raw bytes to 1,573,356 encoded bytes, ratio 1.0, rejected.
  Initial local release-profile timings show raw decode near 286 us/block, selected base-XOR decode
  near 348-370 us/block, and base-XOR encode near 845-926 us/block for these matrices.
* The pilot deliberately has no durable `ProximaScheme` marker yet. PAX f32 vector stripes continue
  to write/read `Raw` until catalog flags, null-row handling, representative benchmarks, decode-cost
  thresholds, and EXPLAIN metadata are wired.

Pruning metadata:

* vector dimension and model id;
* reduced-space bounding box or spatial code min/max;
* cluster/centroid id;
* exact vector byte length and codec ratio;
* row permutation version.

== LLD: Graph Topology Compression

Graph topology remains a rebuildable projection over canonical node and edge records.

Build path:

1. Read canonical edge records for a graph and topology epoch.
2. Choose vertex ordering:
   * natural/catalog id for mutable graphs;
   * source-sorted order for adjacency-table compatibility;
   * community/BFS/degree-aware remap for read-heavy static graphs.
3. Split adjacency by direction and edge label when cardinality makes it worthwhile.
4. Sort neighbor lists and encode:
   * raw `u32/u64` for tiny or hot mutable lists;
   * gap/delta + varint for normal lists;
   * PFor/Simple8b/bitpack for medium dense lists;
   * Elias-Fano or Roaring-style containers for large monotonic lists;
   * optional nearby-list reference compression for static graphs after measurement.
5. Store edge-property payloads as PAX stripes keyed by edge id or adjacency ordinal.

Routing rules:

* Use adjacency-table projection for write-heavy or stale CSR workloads.
* Use compressed CSR/CSC when topology epoch is fresh and queries are read-heavy.
* EXPLAIN must show topology epoch, vertex ordering, compression scheme, freshness, and fallback.

Current pilot:

* `proximadb-graph::topology_codec` provides the first exact sorted-neighbor codec for CSR/CSC
  projections. It selects `GapVarint` for non-decreasing neighbor ids when the measured ratio clears
  the configured threshold, otherwise it stores `RawU64` and records a fallback reason.
* `GraphTopologyProjectionMetadata` records topology epoch, direction, vertex ordering, compression,
  edge-label split, raw/encoded bytes, and fallback reason. The projection descriptor remains
  rebuildable and never write-authoritative.
* `EncodedTopologyProjection` aggregates encoded adjacency lists into a CSR/CSC-style snapshot and
  exposes exact neighbor reads. Focused traversal tests compare raw and compressed snapshots.
* ORION live traversal still reads raw in-memory CSR arrays until the compressed projection is
  cataloged, persisted, and freshness-gated.

== LLD: JSON And Document Structural Stripes

Column ID 8 `props` remains an exact fallback envelope. Document-heavy tables should gain a
structural projection during compaction.

Build path:

1. Profile props for path frequency, type stability, selectivity, null ratio, shape similarity,
   and average encoded byte size.
2. Assign a `shape_id` to common structural variants.
3. Build a path dictionary for frequent paths.
4. Emit typed leaf stripes for promoted paths:
   * numeric/date/time leaf stripes with min/max and delta/FOR codecs;
   * string leaf stripes with dictionary, prefix, or bloom summaries;
   * boolean/enumeration stripes with bitpack/RLE;
   * array/object presence summaries for pruning.
5. Keep the full msgpack/ProximaValue tree for exact roundtrip unless a table explicitly opts into
   normalized-only storage with a separate ADR.

Promotion rules:

* Promotion is a physical optimization and does not change the logical schema unless cataloged as a
  generated or materialized column.
* Promotion candidates must be selected from measured frequency, type stability, selectivity, and
  compression benefit.
* JSON path predicates should use typed leaf stripes when fresh; otherwise they fall back to props
  blob scan.

Current pilot:

* `proximadb-document::structural_projection` profiles canonical `ProximaTree` props batches and
  emits deterministic `shape_id` assignments from sorted structural signatures.
* The projection builder selects frequent, stable non-null scalar paths into row-aligned typed
  stripes and records frequent arrays/objects/maps/structs as presence summaries for pruning.
* Mixed-type paths are rejected by default when type stability is required. Missing values and
  explicit `ProximaValue::Null` remain distinguishable inside typed stripes.
* The projection metadata always records `props` as the exact fallback envelope and keeps
  `exact_fallback_required = true`; live PAX storage still writes column 8 msgpack props until the
  path dictionary, catalog freshness, and read-time fallback rules are wired.

== LLD: Profiling And Cost Model

Add a benchmark and profiling loop before enabling new codecs by default.

Measured dimensions:

* raw bytes, compressed bytes, compression ratio;
* encode CPU ms per block;
* decode ns per value and per row group;
* selective scan latency and bytes read;
* point lookup latency through row directory;
* memory used by codec parameters and dictionaries;
* rebuild cost from Layer 0/1;
* rejected candidate reasons.

Required benchmark matrices:

* vector raw order vs PCA/Z-order/Hilbert/IVF order;
* f32 raw vs base-XOR entropy vs byte-plane delta;
* graph natural vertex order vs remapped order, raw CSR vs gap/PFor/Elias-Fano;
* JSON opaque msgpack vs path dictionary plus typed leaf stripes;
* hot, warm, and cold tiers with different block sizes.

Catalog feedback:

* xCatalog stores a compact `CompressionStatsProfile` per table/projection/layout family.
* The planner reads stats to decide whether a projection is eligible for default use.
* EXPLAIN includes selected scheme, ratio estimate, decode estimate, layout, freshness, and fallback
  reason.

Current pilot:

* `proximadb-codec::profiling` defines serializable `CompressionStatsProfile`,
  `CompressionBenchmarkRecord`, rejected-candidate records, and EXPLAIN-facing compression fields.
  The records preserve `CompressionProfile`, `LayoutHints`, selected scheme, expected/measured
  ratio, exactness, raw/encoded bytes, value count, CPU/decode hints, and rejected alternatives.
* `benches/bench_23_codec_vector_base_xor.rs` now emits one `PCX_PROFILE_JSON` line per benchmark
  dataset so codec benchmark output can be captured by catalog-ingestion or CI tooling without
  scraping Criterion's human-oriented text.
* xCatalog `CatalogTableSchema` now carries `compression_stats_profiles` with compact
  `CatalogCompressionStatsProfile` records for table, layout, or projection feedback. The catalog
  type is storage/runtime agnostic and keeps codec names and rejection reasons as strings so
  experimental schemes can be recorded before they become durable `ProximaScheme` variants.
* Unified plan context now carries resolved compression profiles from xCatalog into
  `ResolvedObjectContext`. `StorageAuthorityExplanation` exposes them under
  `storage_authority.compression_profiles` with selected scheme, layout/projection id, raw and
  encoded bytes, measured ratio, exactness, encode/decode hints, bytes per value, and rejected
  codec candidates.
* These records are evidence only. Runtime codec selection and EXPLAIN routing must still verify
  freshness, loss policy, authority mode, policy boundary, and decode budget before relying on a
  stored profile.

== LLD: Dead Code Retirement

Cleanup must happen after a checkpoint commit and only when the canonical path has tests. Removal
should preserve compatibility modules when external or older internal imports still depend on the
module path.

Current pilot:

* Commit `b8122857f` checkpoints PCX-005 through PCX-009 before deletion-oriented cleanup.
* The duplicate compute baseline codec implementation files under
  `src/compute/proximacodec/baseline/functions/` have been removed. The directory now keeps only a

== Implementation Order

1. Land profile structs and canonical selection API in `proximadb-codec`.
2. Make PAX writer/reader call the canonical selector and preserve backward-compatible raw blocks.
3. Add profiling and EXPLAIN output before enabling adaptive choices by default.
4. Pilot vector co-location and exact base-XOR codec behind a catalog flag.
5. Add graph CSR compression and JSON structural stripes as separate projection families.
6. Remove duplicate/dead code after callers and tests no longer depend on it.

== Acceptance Criteria

* Exact reads from compressed PAX blocks return byte-identical scalar, string, JSON, and f32 vector
  values for every exact codec.
* Lossy projections can never answer exact reads unless the query explicitly accepts projection
  semantics.
* Codec selection is deterministic from profile, stats, and catalog policy.
* Every automatic decision has an EXPLAIN representation and a fallback reason.
* PAX block tests cover old raw blocks and new encoded blocks.
* Benchmarks demonstrate at least one workload where I/O reduction justifies extra CPU and at least
  one workload where raw fallback is correctly selected.

== Open Questions

* Which workloads require insertion-order-preserving physical reads, and should those tables disable
  compaction-time row reordering by policy?
* What default decode budget should hot OLTP, HTAP, cold OLAP, ANN rerank, graph traversal, and JSON
  document scans use?
* Should vector base dictionaries be block-local only at first, or can segment-local dictionaries be
  introduced after recovery and random-access costs are measured?
* What is the smallest PAX format-version change that can carry codec and layout parameter blobs
  without disrupting existing raw readers?
* Which JSON paths should become catalog-visible generated columns versus physical-only projection
  stripes?
