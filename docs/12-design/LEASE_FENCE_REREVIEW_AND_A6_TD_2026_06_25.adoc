== Scenario 1 (vector-record split-brain) — status

* *Routing-layer half: CLOSED by PR #337.* Lease-on-write (`RecordOpsService::ensure_collection_lease` → `PartitionLeaseManager::ensure_owned`) makes the shared primary-pod registry the gates consult durably lease-backed, so a restarted/partitioned pod CAS-discovers the true owner instead of seeing an empty registry → `Allow`. The Arrow `DoExchange` bulk path (previously the one ungated vector-write path) now gates symmetrically with `do_put`.
* *Boundary half: WIRED (default-OFF).* A pod that passes admission, then stalls and loses the lease, can still flush stale data later — only a storage-write fence (A6) catches that. As of this PR the fence is wired at the consolidated flush boundary via `is_fenced_out` (#346), gated `PROXIMADB_WRITE_FENCING=1`; see §"A6 enforcement — LANDED". It is fully exercised end-to-end once the live shutdown path is made tenant-aware + materializing (TD-163).

== Directive-16 + ADR-025 implications (priority elevation)

* *Directive 16 (#312)* mandates correctness be *enforced, not asserted*, via ratchet tests. The unwired A6 fence is exactly an asserted-not-enforced correctness contract; an unfenced stale writer can durably *resurrect a deleted/tombstoned record* on shared storage — a Directive-16(a)/(d) failure on the cold path.
* *ADR-025 N1* (deletion vectors) plans to flush tombstones → per-file DV bits committed via Iceberg snapshot manifests at the flush boundary — the exact seam A6 must fence. A6 enforcement should be a *prerequisite* for ADR-025 N1.

== A6-enforcement TD — scoping (why it is NOT a bounded follow-up)

Three independent investigations established that the storage-flush layer is, by deep
design, *tenant-agnostic and lease-unaware*:

. The record-write path and flush are *decoupled by the WAL* — the synchronous write ends at a WAL append; flush happens later/async.
. `BackgroundFlushContext` carries *no tenant*, and `to_collection_proto()` does not populate `config.tags`/`owner` (where tenant lives), so tenant cannot be recovered downstream.
. *`execute_coordinated_flush` is not on the live write/flush path.* Its only production caller is the graceful-shutdown `flush_all_collections` (passes `None, None`). The real per-collection flush calls `engine.do_flush` *directly* in the serialization strategies (`avro_serialization_strategy.rs:383`, `bincode_serialization_strategy.rs:462`, `proto_serialization_strategy.rs:354`), bypassing the coordinator, with no tenant and no context. The WAL/write-buffer is keyed by `collection_id` only.

=== What a correct A6 fence requires (the actual work)

. *Make the flush path tenant-aware.* Add `tenant_id: Option<String>` to `BackgroundFlushContext` (struct + `from_collection_service` at `background_flush_context.rs:229`, deriving via `CollectionService::collection_tenant_id` — currently private at `manager.rs:254`), OR give the strategy flush sites a `CollectionService` to resolve `(collection_id → tenant)` per flush. The WAL/write-buffer keying by `collection_id` alone is the root obstacle.
. *Give the flushing component a lease handle.* Add `Option<Arc<PartitionLeaseManager>>` + setter to the component that performs the live flush (the serialization strategies and/or the coordinator instance that actually runs it — note the live shutdown coordinator at `engine.rs:241` is a throwaway with neither `collection_service` nor a lease handle). Source: `lease_manager_for_writes` in `shared_services.rs` (clone the `Arc` before it is moved into `record_ops().set_lease_manager`).
. *Add a durable-read accessor* on `PartitionLeaseManager` (e.g. `current_holder(tenant, collection) -> Option<(version, PartitionLease)>` delegating to the private `store.read`), since none is exposed.
. *The check* (default-OFF, `PROXIMADB_WRITE_FENCING=1` + lease handle present), placed at the *strategy `do_flush` sites* (the live write), before the write: `read(tenant, collection)`; if `Some((_, lease))` and `!lease.released` and `!lease.is_expired(now)` and `lease.holder_pod != self_pod_id` ⇒ reject (fenced). Absent/released/expired ⇒ allow (fail-open).
. *Mixed-read-safe + gated* per CLAUDE.md mandate #8: default-OFF until baked; `None`/flag-off ⇒ unfenced ⇒ byte-identical ingest (protects recall@k).
. *Co-design*: emit `io_trace` for the lease read; carry `TenantContext`; reuse `dml_lock_metrics` for fence outcomes; amortize the read (one per flush, not per row).

=== Explicitly rejected shortcuts

* *Fence only at `execute_coordinated_flush`* — correct as written but enforces solely on the shutdown flush-all path and is inert there today (no lease handle, no tenant). Misleading as "the fence."
* *Admission-only fence* (at `RecordOpsService`) — advisory; does not catch stall-after-admission (Kleppmann/CockroachDB: validate at write/commit time, not admission). PR #337's lease-on-write is the routing layer, not the boundary fence.
* *Fence at the iceberg `ManifestCommitter`* — vector engines persist via `SstManifest`, not the fenced committer; no call site.

== A6 enforcement — LANDED (2026-06-25)

The §4 TD predicted the live flush issued `engine.do_flush` *directly from the
serialization strategies*. A **runtime trace of the actual server binary**
(insert→flush→shutdown; see `runtime-evidence/A6_FLUSH_BOUNDARY_RUNTIME_TRACE_2026_06_25.md`)
overturned that and pinned the real boundary:

* *The strategy `do_flush` sites are DEAD.* The WAL manager has no strategy field
  (`_strategy` is dropped at `write_ahead_log/mod.rs:1431`); the avro/bincode/proto
  `flush_collection` sites are never on the live path.
* *Live insert never reaches `do_flush`.* A 500-vector insert persists only to a
  WAL segment (`.bcwal`) + manifest. Zero SST/data files on disk during normal
  operation — server durability is WAL-backed; materialization does not happen on
  the live path.
* *The one live `do_flush` boundary is the SIGINT graceful-shutdown coordinator —
  and it currently FAILS* ("No storage engine specified … no metadata available",
  0 collections flushed): the throwaway coordinator at `engine.rs` has no
  `collection_service` and passes `None, None`. (The server traps SIGINT only, not
  SIGTERM.)

So the fence is wired at the **single consolidated coordinator boundary**
(`execute_coordinated_flush`), checked **before** record extraction / metadata
resolution — exercised regardless of the downstream materialization gap and correctly
positioned for when it is fixed. The §"Explicitly rejected shortcuts" note that
fencing at `execute_coordinated_flush` is "inert / misleading as the fence" is
**superseded by the runtime evidence**: it is the only live boundary, so it is the
correct seam; the residual caveat (dark on shutdown until tenant + `collection_service`
are wired) is tracked as TD-163, not a reason to fence the dead strategy sites.

=== Decisions (D1–D5)

[cols="1,3",options="header"]
|===
| # | Decision
| D1 Canonical path | *One funnel.* The coordinator's storage write now goes through the trait `flush()` funnel (`engine.flush(params)`, was `engine.do_flush(&params)`), the same funnel the embedded path uses. Bytes written are identical (`flush()` delegates to the same `do_flush`).
| D2 Fence mechanism | *Ownership check* (`PartitionLeaseManager::is_fenced_out`, #346) at the boundary — *no* WAL/format change, so no mandate-#8 migration. Coarser than token-carry (a re-acquire after takeover could let earlier-buffered data through) but adequate as the boundary backstop behind lease-on-write (#337) routing. Token-carry (`validate_fencing` + a `FlushParameters` generation) is left to TD-163 if the coarseness ever bites.
| D3 Tenant carriage | *Field on `BackgroundFlushContext`* (`tenant_id`, resolved once via `CollectionService::collection_tenant_id`, now `pub(crate)`), plus a coordinator `resolve_flush_tenant` fallback through `collection_service`. *Not* on `FlushParameters` — that struct is `Serialize` and has ~120 literal constructors without `..Default`; a required field there is a needless wide blast radius. Co-design: one amortized lookup per flush, never per row.
| D4 Coordinator fate | *Converge, do not retire.* It is the only shutdown flush path; retiring it would drop graceful-shutdown materialization entirely. It becomes the single fenced boundary.
| D5 Rollout | *Default-OFF env gate first* (`PROXIMADB_WRITE_FENCING=1`); flag-off ⇒ the fence is never consulted ⇒ byte-identical ingest (recall-safe). Per-collection opt-in is a later step.
|===

=== What landed (this PR)

* `storage::write_fence` — `StorageWriteFence` trait + `write_fencing_enabled()`
  gate + a pure, unit-tested `evaluate_fence` decision (keeps `storage` decoupled
  from `cluster`; `FlushParameters` cannot carry the lease manager as it is
  `Serialize`).
* `network::storage_write_fence::LeaseStorageWriteFence` — adapter over the **same**
  `PartitionLeaseManager` the write-gates use, injected from `shared_services` →
  `StorageEngine::set_storage_write_fence` (post-construction, mirroring
  `set_precision_resolver`) → the shutdown `WALFlushCoordinator`.
* Fence check at the top of `execute_coordinated_flush`; tenant via
  `BackgroundFlushContext.tenant_id` + `resolve_flush_tenant`.
* Tests: cross-pod `is_fenced_out` takeover, the adapter-through-`evaluate_fence`
  integration (reject-when-ON / byte-identical-when-OFF), `evaluate_fence` matrix,
  and the coordinator tenant/fence wiring — all deterministic.

=== Deferred to TD-163 (server vector-flush materialization)

The fence is correctly positioned but **dark on the live shutdown path** until the
coordinator there gets a `collection_service` (for tenant) and engine/metadata
resolution (so the flush actually materializes to SST). That is a correctness-critical,
not-offline-verifiable change (needs real SST round-trip/recall testing) and is its
own TD. When it lands, the A6 fence becomes load-bearing end-to-end with no further
fence changes. ADR-025 N1 (deletion vectors) remains a dependent of A6.
