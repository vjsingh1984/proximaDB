== 1. The seam

Two `UnifiedHandlers` implement `ApiHandlersPort`
(`crates/platform/proximadb-runtime/src/port.rs:26`):

* **ROOT (inherent-logic)** — `src/api_handlers/request_handlers.rs:232`. Holds **12
  concrete services** (`CollectionService`, `VectorOperationsService`, `DocumentService`,
  `ObservabilityService`, `EventLogEngine`, 3× graph services, `MetricsQueryService`,
  `QueryFacadeAdapter`, `DmlService`, `CanonicalPrecisionResolver`). Implements the 7
  `ApiHandlersPort` methods **plus ~30 inherent-only methods** (metrics/admin, record
  APIs, `execute_sql_frontend`, cache/setters).
* **RUNTIME (port-based)** — `crates/platform/proximadb-runtime/src/handlers.rs:129`. Holds
  **3 port trait objects** (`CollectionPort`, `VectorOpsPort`, `QueryAdapterPort`) + cache.
  Implements exactly the 7 `ApiHandlersPort` methods by delegation; **zero inherent logic**.

`ApiHandlersPort` (7 methods): `handle_collection_operation_for_tenant`,
`handle_vector_search_v1{,_for_tenant}`, `handle_vector_batch_v1_for_tenant`,
`handle_vector_v1_for_tenant`, `execute_hybrid_query`, `execute_sql_v1`.

== 2. Current wiring (the good news)

* **REST already prefers RUNTIME.** `src/network/rest/v1/handlers.rs:1337` casts
  `state.api_handlers` (RUNTIME, built in `shared_services.rs:1529`) and only **falls back**
  to `state.request_handlers` (ROOT) when `api_handlers` is `None`. In normal boot both exist
  and REST collection/vector dispatch already goes through RUNTIME.
* **gRPC / Arrow Flight / pgwire are locked to ROOT** — `multi_server.rs` passes
  `services.request_handlers` (ROOT) directly to those servers (many sites ~445–1509).
* **Router-build field extractions are locked to ROOT** — AQL source registration, the
  hybrid backend, bulk-load coordinator, and memory store read concrete fields off ROOT:
  `.vector_operations_service` (rest/v1/handlers.rs:1207/1399/1462/1482/1511/1521/1547),
  `.document_service` (:1492), `.observability_service` (:1498), `.event_log`
  (:1474/1554/1567), `.graph_execution_service` (rest/server.rs:308). These are **build-time
  wiring**, separate from per-request dispatch.

== 3. Blockers to full convergence (missing port surface)

The RUNTIME handler can't yet replace ROOT everywhere because the ports don't cover ROOT's
inherent methods. Ports live in `crates/platform/proximadb-runtime/src/service_ports.rs`.

== 4. Recommended slicing

* **S1 — always wire RUNTIME into REST, then remove the ROOT fallback (CORRECTED — NOT a
  trivial cast-removal).** Verified 2026-06-03: the `unwrap_or_else(ROOT)` fallback at
  `rest/v1/handlers.rs:1337` is **load-bearing for multi-port mode with gRPC disabled**, not
  dead. The handlers.rs `AppState.api_handlers` is `Option` (set only via `with_api_handlers`,
  called only when `ports: Some`). In `multi_server.rs`:
** **Unified-port mode (default)** already builds `RestServerPorts` unconditionally with
   `api_handlers: services.api_handlers.clone()` (multi_server.rs:843–848) → REST **already
   uses RUNTIME** there. This half of the seam is effectively closed in the default config.
** **Multi-port mode** builds `rest_ports_opt` **inside the `if enable_grpc` block**
   (multi_server.rs:302/466) → when gRPC is off, `ports == None`, `api_handlers` stays `None`,
   and REST dispatch falls back to ROOT. Replacing 1337 with `.expect(...)` would **panic** in
   that config.
+
**Corrected S1:** hoist the `api_handlers` wiring (and the `doc_port`/`graph_port`/`obs_port`
that `RestServerPorts` bundles) **out of the gRPC-gated block** so the multi-port REST server
always receives `services.api_handlers` (always built at `shared_services.rs:1733`). Then the
1337 fallback is truly dead and can be removed. **Risk: moderate** — touches server-boot wiring
across unified + multi-port (+ gRPC on/off) modes; must be exercised in each mode (can't be
unit-tested from `cargo test --lib`). Est. ~1d incl. mode verification, not 0.5d.
* **S2 — `MetricsPort` (or extend `VectorOpsPort`) (~2d).** Add `metrics`,
  `collection_metrics`, `query_hints`, `force_flush_collection`, `list_unflushed_vectors`;
  implement on the concrete services; surface on RUNTIME.
* **S3 — `DocumentPort`/`RecordPort` (~3d).** Cover `handle_record_{search,get,scan,
  scan_paginated,delete_batch,batch,insert_batch}_for_tenant`; cut gRPC record paths over.
* **S4 — SQL frontend (~2d).** Fold `execute_sql_frontend` into `QueryAdapterPort` (or
  deprecate the legacy path) so the multiplex/pgwire SQL route leaves ROOT.
* **S5 — build-time field extraction (~3d, the hard part).** Re-wire AQL source
  registration / hybrid backend / bulk-load / memory store / graph AQL source to receive
  injected services (or ports) at boot instead of reaching into ROOT's concrete fields.
  Only after S2–S5 can gRPC/Arrow/pgwire move off ROOT and ROOT be deleted.

Full convergence ≈ 10 engineering days. **S1 is independently shippable now** and removes
the live REST dependence on ROOT without touching the other protocols.

== 5. Convergence Gate notes

* New ports (`MetricsPort`, `DocumentPort`) must declare authority mode / policy boundary in
  their doc headers per the Gate; they are facades over the same concrete services (no new
  durable authority).
* Do **not** expose concrete services as public fields to "fix" S5 — that re-introduces the
  hidden coupling the seam exists to remove. Inject at boot.
* ROOT deletion is the terminal step; keep both handlers until gRPC/Arrow/pgwire + build-time
  wiring are all on ports.
