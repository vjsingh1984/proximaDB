== TL;DR

INT-3 step 1 (commit `7fd2ac623`) shipped the standalone PAX v2 block
encode/decode unit + the `should_use_v2_for_records` dispatch lever.
**INT-3-followup as written in the integration plan ("SST/HELIX/SWIFT
block flush paths choose the writer based on the column types") is not
a one-shot wire-up** — the current SST engine doesn't use a PAX block
format. Per-block dispatch into PAX v2 requires a bridge-layer change,
not just a writer swap.

This memo documents the gap discovered during INT-3-followup scoping
and proposes splitting the followup into landable units.

== What the integration plan assumed

[source,asciidoc]
----
* src/storage/engines/sst/mod.rs (and HELIX/SWIFT equivalents) — the
  SST/HELIX/SWIFT block flush paths choose the writer based on the
  column types in the batch.
----

The plan read as: there's an existing per-block writer with a v1 PAX
layout; flip a `if should_use_v2_for_records → encode_pax_v2_block`
branch at the writer boundary and the engines start writing v2 blocks.

== What the codebase actually has

The SST file format is **Arrow IPC** end-to-end:

* `src/storage/engines/core/formats/arrow_block/writer.rs:120-176` —
  `ArrowBlockWriter::write_block` converts `Vec<ProximaRecord>` to an
  Arrow `RecordBatch` via `DefaultProximaRecordBridge::proxima_records_to_batch`
  and writes via Arrow IPC `StreamWriter::write(&batch)`.
* `src/storage/engines/core/formats/arrow_block/reader.rs:171-213` —
  `ArrowBlockReader::read_block` reads via Arrow IPC `FileReader` and
  bridges back to `ProximaRecord`.
* `src/storage/schema/proxima_record_bridge.rs:188` — the embedding
  column is materialized as a `Float32Builder` (`FixedSizeListArray<Float32>`).
  Every `EmbeddingValues::Fp16` is downconverted to fp32 at the
  bridge before it ever reaches the Arrow writer.
* The `RowBasedHeader` (`PROXSST\0` / `PROXSWF\0` magic) at
  `src/storage/engines/core/formats/proximablocks/header_metadata.rs:486`
  is the SST/SWIFT *file* header, not a per-block header. Inside the
  file each block is an Arrow IPC `RecordBatch`, not a `PXBL`-magic
  block.

Consequence: even if a v1/v2 dispatch is inserted at
`arrow_block::write_block`, fp16 records have already been lossily
narrowed to fp32 by the bridge upstream. The PAX v2 byte-halving
payoff requires fp16 to flow through unconverted.

== Why this isn't a one-PR wire-up

Three independent changes are needed to make fp16 storage real in the
SST engine:

1. **Bridge fp16 path.** `proxima_records_to_batch` and `batch_to_proxima_records`
   need a typed-precision branch: when `EmbeddingValues::Fp16` is
   present, emit `Float16Array` (arrow-rs supports `half::f16`) instead
   of `Float32Array`. Reader: dispatch on Arrow column dtype to
   reconstruct the original `EmbeddingValues` variant.

2. **Engine route.** SST + HELIX + SWIFT need to decide per-collection
   whether to invoke the fp16-aware bridge path (collection has
   `canonical_embedding_precision != Fp32`) or stay on the legacy
   fp32-Arrow path. Same per-collection lookup as
   <<int-2-5c-followup, INT-2.5c-followup>>; defer until both are
   designed together.

3. **Compaction preservation.** `src/storage/engines/sst/compaction.rs`
   block-level compaction calls `writer.write_block(&records)` —
   reading a fp16 block then re-writing must preserve the precision
   through the bridge round-trip. The bridge fix in (1) is necessary
   but not sufficient; compaction needs an explicit assertion that
   the rewritten precision matches the source.

The PR 5 PAX `PXBL` block format is an *alternative* on-disk shape that
could replace the Arrow IPC inner-block format entirely, but doing so
is a much larger rewrite (file layout, index, bloom, statistics, footer
— all are currently Arrow-aware). The unit-level
`encode_pax_v2_block` / `decode_pax_v2_block` helpers stay useful for
that future work, but they're not the right primitive for an
incremental fp16 storage win on the existing SST engine.

== Proposed split

Replace the single "INT-3-followup" task with:

[cols="1,3,2", options="header"]
|===
| ID | Scope | Depends on

| INT-3-followup-a
| Bridge fp16 path: `proxima_records_to_batch` and
  `batch_to_proxima_records` emit/decode `Float16Array` when the
  embedding column is `EmbeddingValues::Fp16`. Bit-exact round-trip
  test through the bridge.
| —

| INT-3-followup-b
| Per-collection canonical-precision lookup at the engine boundary.
  Shared with INT-2.5c-followup; same catalog read.
| INT-3-followup-a

| INT-3-followup-c
| Engine route: SST + HELIX + SWIFT writers consult the canonical
  precision and invoke the fp16-aware bridge path. Test: write a
  fp16 collection, scan with `cargo run --bin ann-benchmarks`,
  verify recall ≥ 0.99 vs fp32 baseline.
| INT-3-followup-b

| INT-3-followup-d
| Compaction preservation: re-write must preserve source precision.
  Add assertion + dedicated compaction test for an fp16 collection.
| INT-3-followup-c
|===

INT-4-full's e2e + byte-halving assertion lands AFTER all four. The
`/metrics/prometheus` byte ratio test is the canary that proves the
chain works.

== What stays useful from INT-3 step 1

* `should_use_v2_for_records` — engine dispatch lever, still the
  right primitive; just plug it into the fp16-aware bridge route
  decision instead of the writer swap.
* `encode_pax_v2_block` / `decode_pax_v2_block` — kept as the
  primitive for any future PAX-native engine (e.g. an explicit
  HTAP/MPP columnar engine). Not on the critical path for the
  Arrow-based engines' fp16 storage win.
* PR 5's `PaxBlockHeaderV2` + `peek_pax_block_version` — same: kept
  as the contract for the future PAX-native path.

== INT-3-followup-d gap discovered during scoping

INT-3-followup-d landed the precision-preservation primitive
(`EmbeddingCell::coerce_to_precision`) + 4 unit tests, but the actual
compaction wire-up is held by a separate gap: **compaction reads
records via the legacy `VectorRecord` intermediate
(`crates/foundation/proximadb-records/src/conversions.rs:181`
`proxima_record_to_vector`), which has `vector: Vec<f32>` and
unconditionally calls `to_fp32_owned()`**. The precision label is
lost at this hop, so even with a fp16 source block and a fp16-typed
bridge, the rewritten block emits Float32Array.

A failing-by-design `#[ignore]`'d test
(`sst::compaction::tests::tests::fp16_records_survive_compaction_round_trip_bit_exact`)
stands as the regression that the next wiring commit must flip from
ignored to passing. The wiring commit needs:

* `CompactionTask.precision_hint: Option<EmbeddingScalarType>` — the
  target precision the writer should reconstitute to, populated by
  the compaction scheduler.
* Compaction manager calls `CanonicalPrecisionResolver::resolve` (#68)
  to populate the hint before enqueueing the task.
* `compaction.rs` writer reconstitution sites
  (`src/storage/engines/sst/compaction.rs:1083-1087, 1190-1194`)
  call `cell.coerce_to_precision(target)` before passing records to
  `ArrowBlockWriter::write_block`.

Scope of the wiring commit: ~3 small edits + flip the ignored test
to passing + add a recall@10 assertion on the rewritten block. Held
out of INT-3-followup-d because it touches CompactionTask
construction sites broadly and benefits from a focused review.

== INT-4-full readiness

After the wiring commit lands, the e2e + byte-halving assertion has
all its prerequisites:

* fp16 ingest path (followup-c) ✓
* fp16 storage on flush (followup-a + -c) ✓
* fp16 preservation through compaction (followup-d primitive ✓ +
  wiring commit pending)
* canonical-bytes per-precision metric (INT-2b — already shipped)

The e2e test writes a fp16 collection, forces a flush + compaction,
scrapes `/metrics/prometheus`, asserts the byte ratio is ~50% of an
fp32 baseline.

== Decision needed

Two paths forward:

. **Bridge-first** (recommended): land INT-3-followup-a (bridge fp16)
  as the next narrow PR. Lowest-risk win — preserves fp16 through the
  existing engine stack without touching file format. Then layer
  followup-b/c/d on top.
. **PAX-native engine**: design + implement a new SST-shaped engine
  whose block format IS `PXBL` (uses `encode_pax_v2_block` directly,
  skips Arrow). Bigger surgery; better long-term story for the
  competitive OLTP/OLAP/HTAP/MPP roadmap; doesn't reuse SST tooling.

The bridge-first path is reversible and gets fp16 storage shipping in
weeks not months. Recommend it for the next iteration.
