== Why this document exists

Phase 2 (PRs 1–12) shipped every contract module needed for fp16 canonical: type system, schema versioning, feature flag, WAL+PAX header parsers, catalog policy, hardware probe, boundary downconverters, BYO precision field, PQ codebook lifecycle, recall harness, end-to-end test scaffold. Most PRs deferred the live-path wiring with explicit follow-up notes so the contracts could ship in isolation.

Three "cheap" follow-ups have landed since: PR 7 boot hw probe wire-up, PR 7b Prometheus registry wire-up, PR 3b ingest-edge validator. These closed the observability + producer-safety story.

What remains for an actual fp16 collection to compress on disk + serve native fp16 inference: three substantial integrations. This document scopes them as a coherent mini-phase so a reviewer sees the full sequence before any single commit lands an irreversible storage format change.

== Goal

A demonstrable fp16 collection: create + insert 10k records + search + verify both `recall@10 ≥ 0.99` (LLD §Q13 cosine gate) AND `proximadb_embedding_precision_canonical_bytes{precision="fp16"}` reports ≈½ the bytes of the fp32 equivalent. This is the LLD §"PR 12 — End-to-end fp16 collection (the payoff)" demo.

== Acceptance gates

All four MUST hold before this mini-phase merges to main:

. **Backward compatibility on disk:** every existing fp32 WAL segment + PAX block created by the v1 path reads unchanged. The PR 2 `peek_segment_version` + PR 5 `peek_pax_block_version` dispatch is the contract enforcing this; reader-only tests against fixture v1 files prove it.
. **Feature flag gates all writes:** `PROXIMADB_EMBED_PRECISION_SCHEMA_V2=false` (the default) keeps the writer on v1 byte-for-byte. The integration tests run both flag positions and diff WAL bytes for the OFF case against a pre-mini-phase fixture.
. **Storage gauge proves the win:** with the flag ON and `canonical_embedding_precision=Fp16` on a fresh collection, `proximadb_embedding_precision_canonical_bytes{precision="fp16"}` is between 45% and 55% of the same workload at fp32 (the LLD §Motivation invariant, with ±5% headroom for metadata).
. **Recall gate held:** the PR 11 recall harness against SIFT-1M and a 10k-row synthetic corpus reports recall@10 within the §Q13 gate (≥ 0.99 cosine/L2, ≥ 0.995 dot).

== PR sequence

Four PRs. Each is independently rollback-able and behind the existing `PROXIMADB_EMBED_PRECISION_SCHEMA_V2` flag. They should land in the order below.

[cols="1,3,1,3"]
|===
| PR | Scope | Risk | Rollback

| INT-1 (BGE boundary)
| Wire `project_to_canonical` into `BgeModel::embed_batch_onnx` response path. When the active route's collection has `canonical_embedding_precision = Fp16`, write `EmbeddingValues::Fp16(...)` into the `EmbeddingCell.values` field; otherwise behave identically. Emits the PR 7b `conversions_total{from,to,site=ingest_boundary}` counter.
| Medium. Touches the embedding hot path.
| `git revert` the single commit; no on-disk state changes (records still flow through the existing WAL writer which currently materializes back to `Vec<f32>`).

| INT-2 (WAL writer v2)
| Extend WAL bincode writer to emit a v2 segment header (PR 4's `V2SegmentHeader::encode`) when the active config has `schema_v2_enabled = true`. Reader uses `peek_segment_version` to dispatch v1 (existing path) vs v2 (parse header → stamp `ProximaRecord.schema_version = V2` on each record). Per-record serialization shape is unchanged in this PR (still fp32-storage bincode); the header tag is what enables PR INT-3 to switch to native fp16 storage.
| Medium. WAL format. Requires the LLD-mandated soak test.
| Existing v1 segments unaffected. New v2 segments can be re-read by binary that reverts INT-2 because the dispatch is magic-based, not version-checked at parse time (peek runs first). Worst-case: leave v2 segments un-replayed by old binaries, replay on fresh binary.

| INT-3 (PAX writer v2)
| Extend PAX block writer to emit `PaxBlockHeaderV2` (PR 5) when the column carries `EmbeddingValues::Fp16`. Reader uses `peek_pax_block_version` for v1/v2 dispatch. Per-column payload writer respects the alignment table. fp32 columns continue to use the v1 layout for back-compat.
| High. Storage format. Touches every PAX block writer + reader.
| v1 blocks read unchanged. v2 blocks are detected by magic; old binaries reject them with the existing "unsupported version" error rather than crash. Roll forward only — once a v2 block is written, the binary that reverts INT-3 will need a one-time rewrite job to convert (or a compaction sweep at next maintenance window).

| INT-4 (e2e + storage gauge)
| Integration test that creates an fp16 collection via REST v3, inserts 10k records, searches, and reads `/metrics/prometheus` to assert the canonical-bytes gauge. Wires the PR 7b `set_canonical_bytes` setter at the WAL writer flush boundary so the gauge is populated by INT-2's writer. Uses the PR 11 recall harness for the recall gate.
| Low (test-only addition + one setter call site).
| Test-only; revert is a single commit.
|===

== Per-PR scope details

=== INT-1: BgeModel boundary downconversion

Files:

* `crates/modalities/proximadb-embedding/src/models/bge.rs` — extract the response Vec<f32> as today, then dispatch through `project_to_canonical(EmbeddingOutput::Fp32(...), canonical)`. The `canonical` parameter comes from the per-request `EmbedRoute` (PR 9's `EmbedRoute::native_precision()` is the lookup) or, when the route doesn't carry it, from the collection's `canonical_embedding_precision` (PR 6b catalog field).
* `crates/modalities/proximadb-embedding/src/scheduler.rs` — plumb the `canonical: EmbeddingScalarType` parameter from the calling collection's catalog row through the scheduler to BgeModel.
* `crates/modalities/proximadb-embedding/src/precision/boundary.rs` — already has `project_to_canonical`; add a `convert_with_metric()` wrapper that increments the PR 7b `conversions_total` counter when the conversion narrows precision.

Test: a unit test in `bge.rs` that asserts the response variant matches the requested canonical (this is the existing `boundary.rs` test pattern in a new file). End-to-end test of "fp32 input via REST, fp16 stored" lands in INT-4.

External HTTP clients (OpenAI / Cohere / Azure / Byo) are explicitly out of scope for INT-1 — they keep returning fp32 today per LLD `native_precision()`, so projecting to fp16 happens later in the pipeline (at WAL write time in INT-2). Adding them here would touch four client crates without changing observable behavior.

=== INT-2: WAL v2 segment header writer

Files:

* `src/storage/persistence/write_ahead_log/serialization/bincode.rs` — when opening a new segment AND `cached_precision_config().schema_v2_enabled`, prepend the PR 4 `V2SegmentHeader` bytes before the first record. The header carries `canonical_default_precision` (read from the collection's catalog row), `precision_epoch` (from the same row), and `policy_id` / `policy_version` (from the collection's precision policy reference, defaulting to `GLOBAL_DEFAULT_POLICY_ID` when None).
* `src/storage/persistence/write_ahead_log/recovery_manager.rs` — on recovery, `peek_segment_version` on each segment. V1 → existing legacy path. V2 → parse header, pass `schema_version: V2` to `deserialize_batch_with_schema_version` (PR 2c).

What this PR does NOT do: per-record fp16 storage. The bincode payload format stays fp32 in INT-2. The segment header is the version tag PR INT-3 keys on to decide whether per-column fp16 storage is allowed. Splitting this way means INT-2 can land + soak without changing per-vector bytes, isolating the segment-header migration risk from the columnar layout risk.

Soak test: spin up a 3-node cluster with mixed flag settings (one OFF, two ON) per LLD §Q18 rolling-deploy. Insert 100k records. Force segment rotation. Verify all three nodes can read both v1 and v2 segments and that the catalog `current_precision_epoch` matches what's in segment headers.

=== INT-3: PAX v2 block writer

Files:

* `src/storage/engines/core/formats/proximablocks/block_structures.rs` (or sibling new file) — extend the PAX writer's per-column laying-out step to call `PaxBlockHeaderV2::plan_layout` when any column carries `EmbeddingValues::Fp16` / `Bf16` / `Int8Scalar`. fp32-only blocks continue to use v1 layout.
* `src/storage/engines/core/formats/proximablocks/block_reader.rs` — `peek_pax_block_version` dispatch at the top of the read path. V1 → existing path. V2 → `PaxBlockHeaderV2::decode`, then per-column reads honor the alignment table for safe `&[u8]` → `&[u16]` casts on memmap.
* `src/storage/engines/sst/mod.rs` (and HELIX/SWIFT equivalents) — the SST/HELIX/SWIFT block flush paths choose the writer based on the column types in the batch.

Caveat: the existing `RowBasedHeader` (magic `PROXSST\0`) is the SST file header, not the per-block header. PR 5's `PaxBlockHeaderV2` (magic `PXBL`) is the per-block header inside an SST file. Both magics coexist — `PROXSST\0` for the outer file, `PXBL` for v2 blocks within. v1 PAX blocks inside an SST file have an implicit 4-byte alignment marker; the reader dispatches on `peek_pax_block_version` of each block.

Risk knob: gate the writer choice on column types FIRST, then on the feature flag. This means a collection with all-fp32 columns NEVER hits the v2 write path even with the flag on, so the format risk is bounded to collections that explicitly opt into a non-fp32 precision.

Soak test: write 10k fp16 records, force compaction, read back via every search engine that uses PAX (SST, HELIX, SWIFT, NOVA). Verify bit-exact round-trip on the fp16 column.

=== INT-4: End-to-end fp16 collection integration test

Files:

* `tests/integration/fp16_collection_e2e.rs` (new) — full pipeline:
.. Set `PROXIMADB_EMBED_PRECISION_SCHEMA_V2=true` in test env.
.. Create a collection via REST v3 with `canonical_embedding_precision = "fp16"`.
.. Insert 10k synthetic records (deterministic xorshift, same generator as PR 12 e2e).
.. Force WAL flush + PAX block compaction.
.. Search 32 queries; verify recall@10 ≥ 0.99 vs an fp32 baseline collection running in the same test process.
.. Scrape `/metrics/prometheus`; assert `proximadb_embedding_precision_canonical_bytes{collection="<name>", precision="fp16"}` is between 45% and 55% of the fp32 baseline's canonical_bytes.

* `src/storage/persistence/write_ahead_log/serialization/bincode.rs` — at the WAL flush boundary (or wherever the writer counts bytes), call `PrecisionMetrics::set_canonical_bytes(collection, precision, bytes)`. Single setter call; the rest of INT-4 is the test.

Skip with `cfg(feature = "integration-fp16")` so it doesn't run on every CI invocation (the 10k-record test is slow). Nightly + on-demand only.

== Dependencies between PRs

[source]
----
INT-1 (BGE boundary) ──┐
                       ├──→ INT-4 (e2e test)
INT-2 (WAL v2 header) ─┤
                       │
INT-3 (PAX v2 writer) ─┘
----

INT-2 and INT-3 can land in either order; both depend on the flag infrastructure already in place. INT-4 depends on all three because the storage-gauge assertion needs INT-2's writer to call `set_canonical_bytes`. INT-1 is independent of INT-2 / INT-3 — without them, the BGE boundary's fp16 output still flows through the v1 WAL writer which materializes it back to fp32 (lossy round-trip, but functionally correct).

Recommended sequencing: INT-1 → INT-2 → INT-3 → INT-4. INT-1 is the smallest and proves the BGE boundary plumbing; INT-2 unlocks the segment-header tag without changing per-record bytes; INT-3 actually flips the storage; INT-4 proves it.

== Rollback story per PR

* **INT-1**: `git revert` the single commit. BgeModel falls back to fp32 output; no on-disk impact.
* **INT-2**: `git revert` works because reader dispatch is magic-based — old binary reads existing v1 segments unchanged, ignores v2 segments (or rejects them with the LLD-locked error). Production rollback: stop the v2 writer first (flip flag OFF + restart), then revert the binary; new segments will be v1, old v2 segments stay readable as long as the v2 reader code is still in tree (i.e. don't revert INT-2 in the same release that flips the flag OFF cluster-wide).
* **INT-3**: Same magic-based dispatch as INT-2. v1 blocks read forever; v2 blocks become un-readable by binaries that revert INT-3. Production rollback playbook: hold off v2 block writes (flag OFF), wait for compaction to rewrite all v2 blocks to v1, THEN revert INT-3.
* **INT-4**: Test-only revert.

== What this mini-phase does NOT do

Out of scope (deferred to a later mini-phase or Phase 3):

. **External API client downconverters.** OpenAI / Cohere / Azure / Byo HTTP clients still return fp32 at the wire. The PR 8 `project_to_canonical` adapter handles the conversion at the WAL boundary in INT-2 (transparent to clients). Native client-side fp16 lands when a provider actually ships a fp16 response format.
. **Native fp16-fp16 distance kernels.** Promote-at-compute (fp16 stored, fp32 multiplied) is the LLD §Q10 default. Native kernels are Phase 6 per LLD §"Open Items Deferred".
. **Adaptive policy auto-flip.** Fixed-mode policies only in this mini-phase. The catalog `PolicyMode::Adaptive` variant stays unused per LLD.
. **bf16 / int8 canonical.** This mini-phase ships fp16 only. int8 is the Phase 3 plan in the LLD; bf16 stays in `EmbeddingScalarType` as a reserved variant.
