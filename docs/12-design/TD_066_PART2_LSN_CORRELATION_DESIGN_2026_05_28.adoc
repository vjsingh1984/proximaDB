== Context

Today's commits closed three of four halves of TD-066:

* **Emission** (`b36a24b17`): `GraphOperationsService::flush_wal` persists
  `CanonicalOperation::Checkpoint(SnapshotManifest)` to the canonical WAL.
* **Production wiring** (`4ece74250`): single shared `FramedTableWalAppender`
  on `SharedServices` so graph emission + pgwire direct writes can't
  collide on `next_sequence`.
* **Recovery read-side** (`18c846ae8`): `OrionPersistence::canonical_checkpoint_lsn`
  scans the canonical WAL and `OrionGraphEngine::recover` logs the
  latest checkpoint LSN for the graph being recovered.

The fourth half (this design's subject) is the **behavior change**:
actually use the canonical checkpoint LSN to scope ORION's recovery so
the canonical WAL becomes the durability authority per ADR-020.

ADR-020 §3: "Recovery must use the canonical WAL as authority; ORION
engine WAL replay becomes a best-effort fast-path validated against
canonical records."

== The actual problem

ORION's `replay_wal` (`src/graph/engines/orion/persistence.rs:797`) reads
the engine-local `UnifiedWALWriter` segment files and replays
`UnifiedWALOperation::GraphOp(graph_op)` entries from the beginning.
Today this works because:

1. `OrionPersistence::checkpoint()` (line 951) truncates the engine WAL
   after writing a snapshot — so replaying from "the beginning" only
   replays post-checkpoint entries.
2. `flush_wal()` (line 783) flushes the engine WAL buffer but does NOT
   truncate; the engine WAL keeps growing across flushes.

The canonical WAL's `SnapshotManifest.sequence_number` is the **engine's
edge-epoch LSN at the time of `flush_wal`** (per
`src/graph/service.rs:944-958`). This LSN is not the engine WAL's frame
sequence — engine WAL frames are timestamp-ordered and carry their own
opaque sequence numbers managed by `UnifiedWALWriter`.

There is no current correlation between:

* the canonical checkpoint LSN (an `edge_epoch` snapshot value), and
* engine WAL frame ordering (UnifiedWALWriter internal sequencing).

So "scope engine WAL replay to entries with sequence > canonical
checkpoint LSN" is not a one-line filter today. The correlation has to
be **established** before it can be used.

== Five options surveyed

=== Option A — Tag engine WAL entries with the canonical emission LSN

Add a new field to the engine WAL frame format:
`canonical_emission_lsn: Option<u64>`. When `flush_wal` emits a canonical
Checkpoint at LSN X, also write a *marker frame* to the engine WAL with
`canonical_emission_lsn = Some(X)`. On recovery:

* Read all engine WAL frames.
* Find the latest marker whose `canonical_emission_lsn <=
  canonical_checkpoint_lsn` (the durably-committed checkpoint).
* Replay only frames AFTER that marker.

==== Scope

* `UnifiedWALWriter` frame schema bump (forward-compat via versioned
  envelope; old frames decode as `canonical_emission_lsn = None`).
* New `flush_wal` step: after canonical emission, write the marker.
* `OrionPersistence::replay_wal` updated to scan for the marker and
  filter.
* ~150 LOC + format-migration test coverage.

==== Tradeoffs

* **Pros**: surgical; engine WAL remains the recovery authority for its
  own data plane; canonical WAL stays a witness; no snapshot cost change.
* **Cons**: introduces a parallel "engine LSN" concept that's hard to
  reason about; on-disk engine WAL format change needs migration plan
  (or feature-gated rollout); the marker can desync from the canonical
  WAL if a crash interleaves the two writes.

=== Option B — Snapshot + truncate on every `flush_wal`

Make `flush_wal` ALSO call `checkpoint()` internally: take a snapshot,
truncate the engine WAL, then emit the canonical Checkpoint. After
`flush_wal`, the engine WAL is empty by invariant. Recovery is then
trivial: load snapshot, replay (likely empty) engine WAL.

==== Scope

* `OrionGraphEngine::flush_wal` now calls `persistence.checkpoint(self)`
  (which takes a snapshot + truncates) before/after the canonical
  emission.
* No format changes.
* ~30 LOC; affects every existing test that calls `flush_wal` because
  durability cost goes up.

==== Tradeoffs

* **Pros**: cleanest invariant — engine WAL is always replayable from
  empty after `flush_wal`; matches ADR-020's "engine WAL is a buffer"
  framing precisely; no LSN correlation needed.
* **Cons**: every `flush_wal` now incurs full-graph snapshot cost.
  Today `flush_wal` is documented as "called during graceful shutdown
  or before critical operations" — fine for shutdown, but `flush_wal`
  is also called from REST endpoints (`POST /graphs/.../flush`) and
  background timers in some configurations. Forcing a snapshot on
  every call breaks the lightweight contract.

=== Option C — Canonical WAL becomes the authoritative write log

Every graph mutation writes a `CanonicalOperation::RecordUpsert`
(node/edge as canonical record) to the shared canonical WAL FIRST, then
mutates engine state. Engine WAL becomes a per-process in-memory journal
that's flushed periodically as a perf optimization. On recovery:

* Read canonical WAL.
* Find latest Checkpoint for this graph.
* Replay `RecordUpsert` entries after the checkpoint LSN through a
  graph-specific `ProjectionRebuilder`.
* Engine WAL is discarded as stale cache.

==== Scope

* Every graph mutation path (`create_node`, `update_node`, `delete_node`,
  edge variants, batch variants) now emits a canonical record before
  touching engine state.
* New `GraphProjectionRebuilder` impl that translates canonical records
  to graph operations.
* Engine WAL becomes purely an in-memory journal; on-disk format can be
  deprecated.
* ~3-5 weeks of work; touches every graph write path.

==== Tradeoffs

* **Pros**: precise match to ADR-020 architecture — single source of
  durable truth; same model as records/document path; recovery is
  uniform across all modalities.
* **Cons**: huge scope; every write path doubles its I/O cost (canonical
  WAL append + projection update) unless the canonical WAL append is
  buffered/batched.

=== Option D — Empty the engine WAL on canonical checkpoint witness

Treat the canonical checkpoint as a "high-water mark." On recovery, if
a canonical Checkpoint exists for this graph, **truncate** the engine
WAL (don't replay it). Load the snapshot, done.

==== Scope

* `OrionPersistence::replay_wal` checks for canonical checkpoint
  presence; if found, skips engine WAL replay and just loads the
  snapshot.
* ~20 LOC.

==== Tradeoffs

* **Pros**: trivial; treats canonical WAL as the absolute authority.
* **Cons**: **DATA LOSS RISK**. Engine WAL frames written AFTER the
  canonical Checkpoint emission but BEFORE the crash are silently
  discarded. This breaks the "no acknowledged write is lost"
  durability guarantee for any write between the last `flush_wal` and
  the crash. Unacceptable for production.

=== Option E — Status-quo + observability + alert

Keep Part 1's read-side log line. Add a Prometheus metric:
`orion_recovery_canonical_checkpoint_age_seconds` (time since the
canonical checkpoint was written). High values indicate either (a)
flush_wal isn't being called often enough, or (b) the canonical WAL
isn't being persisted (production wiring bug). Don't change recovery
behavior.

==== Scope

* New metric on `OrionGraphEngine::recover`.
* ~30 LOC.

==== Tradeoffs

* **Pros**: zero risk; gives operators visibility without architectural
  commitment.
* **Cons**: doesn't actually close TD-066 (c). Recovery still depends on
  engine WAL as authority.

== Recommendation

For v0.2: **Option E + Option A as a phase-2 follow-up**.

=== Why Option E first

* v0.2 is days from release. None of the options A-D are a thin-slice
  landing on a constrained timeline.
* Option E is genuinely useful — it surfaces "is the canonical
  checkpoint emission working?" to operators without changing any
  durability semantics.
* It buys time for the LSN-correlation question to be resolved in a
  focused future session.

=== Why Option A is the right phase-2 path (not B/C/D)

* **B (snapshot+truncate on flush)** breaks `flush_wal`'s lightweight
  contract; would need a separate `commit_checkpoint()` API.
* **C (canonical write log)** is the right ADR-020 end-state but is a
  3-5 week refactor — should be its own design doc + multi-slice
  workstream.
* **D (empty engine WAL on checkpoint)** has unacceptable data-loss
  risk.
* **A** is the only path that preserves engine WAL durability AND
  establishes the correlation needed for `recover_from_canonical_wal`
  to be useful. The format change is the main cost, but with
  versioned envelopes it's tractable.

=== Phase-2 (Option A) execution sketch

Single multi-slice workstream after v0.2 release:

. Engine WAL frame schema versioning. Add `frame_version: u8` to the
  envelope so future readers can detect missing fields and default them.
  Migration test: write v1 frames, read with v2 code, confirm
  `canonical_emission_lsn = None` defaults.
. Add `canonical_emission_lsn: Option<u64>` field to the
  `UnifiedWALOperation` (or wrap in a new marker variant —
  `GraphMarker(MarkerKind::CanonicalEmission(lsn))`).
. After canonical Checkpoint emission, write the marker frame to the
  engine WAL. Test: flush_wal X times, read engine WAL, confirm X
  marker frames with matching LSNs.
. `OrionPersistence::replay_wal` scans for markers, finds the latest
  one whose LSN is `<= canonical_checkpoint_lsn`, replays only frames
  after that marker. Test: write 10 entries, flush, write 5 more,
  flush, write 3 more (crash). Recover. Confirm only the last 3 entries
  are replayed from the engine WAL (the first 15 were canonically
  witnessed and are covered by the snapshot already, assuming the
  snapshot logic also lands).

=== What this design does NOT decide

* Whether to also move toward Option C (canonical write log) as the
  ultimate end-state. ADR-020 says yes eventually; Option A is a
  stepping stone, not a permanent answer.
* Relational distributed graph placement and storage projection tiering.
  The design here is ORION projection-WAL-specific.
* Engine WAL truncation tied to canonical checkpoint LSN (TD-066 (d)).
  That depends on Option A being in place (the marker frame is what
  makes truncation safe).
* What happens if the canonical WAL is unreadable on recovery. Today's
  Part 1 code logs a warning and falls back to engine-WAL-only behavior;
  Option A would inherit that fallback.

== Recommendation for the next session that picks this up

. Build Option E first as a focused short slice (~1 hour). It's pure
  observability and unblocks operators on the v0.2 release line.
. Schedule Option A as a multi-slice workstream after v0.2:
  envelope versioning → marker emission → recovery scoping → tests.
  Estimate 3-5 days; each step is its own commit with tests.
. Defer Option C (canonical write log for graph mutations) to a
  separate design doc + workstream when ADR-020 is ready to flip from
  "ORION engine WAL is compatibility buffer" to "ORION engine WAL is
  in-memory journal." That decision needs RFC-level community input.
