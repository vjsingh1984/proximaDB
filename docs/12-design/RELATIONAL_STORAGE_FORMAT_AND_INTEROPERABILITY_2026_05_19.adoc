= Relational Storage Format and Interoperability Shape
:toc:
:toclevels: 3
:sectnums:

Status: Accepted architecture refinement +
Date: 2026-05-19 +
Scope: SQL/pgwire, relational DDL/DML, catalog tables, PAX/SST storage layouts, MVCC, open-format external tables, and future vector/document/graph/observability records

== Decision

ProximaDB relational storage MUST be shaped as a `ProximaRecord`/`ProximaType`/`ProximaValue`
system with xCatalog as the schema and capability authority. SQL/pgwire is a protocol facade over
that model. It MUST NOT define a protocol-specific row envelope, table catalog, transaction model,
or storage authority.

The relational hot path should converge on a PAX row-family layout:

* Layer 0: WAL / `CanonicalOperation::RecordUpsert` is the commit and replay authority.
* Layer 1: `ProximaRecord` is the semantic row/document/node/edge/span/event authority.
* Layer 2: PAX blocks and segments provide OLTP row-directory access plus OLAP column stripes.
* Layer 3: pgwire, Arrow Flight, Iceberg REST, REST/gRPC, SDKs, and external table adapters expose
  views over the same cataloged records.

Legacy SST/LSM layouts may remain write-optimized access methods, especially for vector-heavy and
append-heavy workloads, but they must carry the shared identity, version, timestamp, tenant, and
tombstone metadata. They are not the target relational authority.

== Recommendation

Adopt the following shape for relational work:

1. Build `proximadb-relational` behavior on canonical `ProximaRecord` records, xCatalog table
   schemas, and shared logical plans.
2. Use PAX `Oltp`, `Pax`, and `Olap` block modes as the internal format family for relational
   rows, HTAP tables, and analytical publications.
3. Modernize SST/LSM segment metadata so updates, deletes, snapshots, and vector freshness use the
   same MVCC/tombstone semantics as PAX.
4. Reserve SQL-visible internal columns with the double-underscore `__proxima_*` prefix. Do not
   make generic names such as `_deleted` or `_version` canonical.
5. Treat Parquet, CSV, Avro, ORC, JSON, XML, Arrow IPC, Iceberg, Delta, Hudi, Hive, Glue, Unity,
   and Polaris as cataloged adapters, projections, or explicitly declared external authorities.

== Comparison With PostgreSQL Storage

PostgreSQL is the compatibility model for SQL behavior, not the physical storage blueprint.

[cols="2,3,3"]
|===
| Area | PostgreSQL heap and indexes | ProximaDB target shape

| Durable row authority
| Heap tuple pages; tuple headers carry MVCC fields; WAL replays page changes.
| WAL records plus `ProximaRecord`; PAX/SST/columnar layouts are record access methods or
projections over the same semantic envelope.

| MVCC
| Tuple versions use `xmin`, `xmax`, command ids, snapshots, visibility maps, and vacuum.
| Record versions use cataloged identity plus `valid_from_ns`, `valid_to_ns`, optional transaction
or branch snapshot fields, and tombstone flags. Compaction removes obsolete versions only after
retention and snapshot rules allow it.

| Row identity
| Physical `ctid` plus logical primary keys and indexes.
| Stable `oid`/record id, cataloged primary keys, optional row-directory hash, and rebuildable
physical locations. Physical offsets are never exposed as durable identity.

| Indexes
| B-tree, GiST, GIN, BRIN, hash, extensions.
| Primary/secondary indexes, vector ANN fragments, JSON path indexes, full-text indexes, graph
adjacency projections, time indexes, and zone-map/bloom pruning metadata, all cataloged as access
methods with freshness/rebuild rules.

| Storage orientation
| Row-first heap with separate indexes; columnar behavior comes from extensions or foreign tables.
| PAX by default: a row directory for point operations and column stripes for vectorized OLAP scans.
`Oltp` and `Olap` modes specialize the same block family.

| Catalog
| PostgreSQL system catalogs are the SQL metadata authority.
| xCatalog is the product-wide control plane for relational tables, collections, graphs,
observability datasets, projections, branches, schemas, policies, and external ownership.

| Extensions and modalities
| Extensions add types, operators, indexes, and FDWs around PostgreSQL's heap/catalog model.
| Vector, document, graph, observability, SKS/entity, and event surfaces are facades and projections
over the same record/catalog/log spine.

| External tables
| FDWs and table access methods can delegate reads/writes to external systems.
| External formats are cataloged with explicit ownership, snapshot/isolation, type mapping, RLS
boundary, write/refresh mode, repair source, and freshness watermark.
|===

The design intentionally borrows PostgreSQL's relational rigor: DDL, constraints, primary keys,
foreign keys, indexes, snapshots, and SQL metadata must be real when enabled. It does not copy
PostgreSQL's heap tuple format, system column names, or vacuum model as ProximaDB's internal
authority.

== Internal Columns

SQL users need optional introspection columns for debugging, replication, audit, and compatibility.
The reserved prefix is `__proxima_`.

[cols="2,2,4"]
|===
| SQL alias | Canonical source | Purpose

| `__proxima_oid`
| column id 0 / `oid`
| Stable record identity.

| `__proxima_tenant_id`
| column id 1 / `tenant_id`
| Engine-level tenant and RLS partition key.

| `__proxima_record_version`
| row version metadata
| Monotonic or snapshot-scoped record version used for optimistic concurrency and CDC ordering.

| `__proxima_created_at_ns`
| column id 2 / `created_at_ns`
| Insert timestamp in nanoseconds.

| `__proxima_updated_at_ns`
| column id 3 / `updated_at_ns`
| Last mutation timestamp in nanoseconds.

| `__proxima_valid_from_ns`
| column id 4 / `valid_from_ns`
| MVCC/bi-temporal lower bound.

| `__proxima_valid_to_ns`
| column id 5 / `valid_to_ns`
| MVCC/bi-temporal upper bound.

| `__proxima_actor`
| column id 6 / `actor`
| Write actor or principal.

| `__proxima_origin`
| column id 7 / `origin`
| Source system, pipeline, or protocol.

| `__proxima_deleted`
| row flags / tombstone state
| Derived visibility flag. DELETE writes a tombstone or closes the previous version; it does not
physically erase the record at commit time.

| `__proxima_branch_id`
| snapshot/branch metadata
| Branchable state and time-travel isolation.

| `__proxima_schema_version`
| xCatalog schema fingerprint
| Schema version used for coercion, evolution, and replay.
|===

Single-underscore names such as `_deleted` may be accepted as import/export aliases when an
external format already uses them, but they are not canonical ProximaDB internal columns. The
double-underscore prefix reduces collision risk with application columns and makes the namespace
explicit.

== MVCC And DML Semantics

Relational DML follows append/version semantics:

* `INSERT` writes a new `ProximaRecord` with identity, tenant, timestamps, schema fingerprint, and
  typed user columns.
* `UPSERT` writes a new version for the same logical identity and closes the prior visible version
  for the affected snapshot.
* `UPDATE` is an upsert of a new version plus retention-governed invalidation of the old version.
* `DELETE` writes a tombstone or closes the current version. Physical removal is deferred to
  compaction after snapshot, retention, CDC, and branch rules allow it.
* `SELECT` evaluates snapshot visibility before projection and before returning rows through
  pgwire, Arrow Flight, REST/gRPC, or open-format scans.

The row visibility predicate is conceptually:

[source,text]
----
tenant_id matches policy
AND valid_from_ns <= snapshot_time_ns
AND (valid_to_ns IS NULL OR snapshot_time_ns < valid_to_ns)
AND tombstone is not visible for the requested snapshot
AND branch/snapshot lineage includes the version
----

This makes SQL updates/deletes, vector freshness, graph edge mutation, document replacement, and
observability retention use one version model.

== Format Schema

=== Logical Table Shape

xCatalog owns the logical schema:

[source,text]
----
TableAsset {
  asset_id
  namespace
  name
  schema_mode: strict | write | read | flexible
  columns: [ProximaColumn { name, type, nullable, default, constraints, column_id }]
  primary_key
  unique_indexes
  foreign_keys
  check_constraints
  access_methods
  retention_policy
  rls_policy
  external_mappings
}
----

Every relational row lowers to `ProximaRecord`:

[source,text]
----
ProximaRecord {
  oid, tenant_id, created_at_ns, updated_at_ns,
  valid_from_ns, valid_to_ns,
  actor, origin,
  props / typed user columns,
  labels,
  embeddings,
  graph edge fields when applicable,
  extensions
}
----

Strict relational tables reject unknown fields. Schema-on-write tables validate and catalog
evolution before accepting new fields. Flexible document/graph/entity collections record structural
variations. Schema-on-read external tables project source columns into `ProximaType` during scans.

=== PAX Row-Family Layout

PAX is the default internal relational block family:

[source,text]
----
[BlockHeader]
  tenant hash, schema fingerprint, min/max timestamps, mode, counts, checksums

[RowDirectory]
  oid hash, primary-key hash, valid_from_ns, valid_to_ns, flags, row ordinal

[ColumnStripes]
  system columns
  primary-key and partition columns
  frequently filtered scalar columns
  user columns
  JSON/path projected columns
  embedding columns
  graph edge columns
  observability time/service/trace columns
  props/labels/extension blobs

[ColumnMeta]
  min/max, null counts, bloom refs, offsets, encodings
----

Modes:

* `Oltp`: row directory first; optimized for small tables, point lookups, indexes, and DML.
* `Pax`: row directory plus column stripes; default HTAP shape.
* `Olap`: column stripes first; optimized for scans, Arrow batches, and open-format publication.

=== SST/LSM Compatibility

SST/LSM layouts remain useful for high ingest and write-optimized compaction. To participate in
relational semantics, each entry must carry or derive:

* stable `oid` and cataloged primary key;
* tenant/RLS key;
* `created_at_ns`, `updated_at_ns`, `valid_from_ns`, `valid_to_ns`;
* record version or commit sequence;
* tombstone/update flags;
* schema fingerprint;
* optional branch/snapshot metadata;
* index freshness and compaction watermark.

The LSM key order may optimize for vector id, tenant/time, primary key, or graph adjacency, but the
value must still decode to canonical `ProximaRecord` fields.

== Cross-Modal Mapping

[cols="1,3,3"]
|===
| Surface | Canonical record shape | Rebuildable projections and indexes

| Relational
| Typed columns, primary keys, constraints, tenant/time/provenance metadata.
| Primary/secondary indexes, PAX stripes, materialized views, Arrow/Iceberg publications.

| Document
| `Map`, `Json`, `Struct`, typed extracted columns, labels, structural variations.
| JSON path indexes, inverted indexes, stable-shape column stripes, schema variation stats.

| Graph
| Node and edge records. Edge records use source, target, type, weight, properties, and validity.
| Adjacency tables, CSR/COO topology, GraphAr/open graph lake publications, path indexes.

| Vector
| Embedding columns plus scalar metadata and labels on the same record.
| HNSW/IVF/PQ/DiskANN fragments, predicate-aware ANN indexes, quantized stripes.

| Observability
| Logs, metrics, spans, profiles, service dependency edges, and events as timestamped records.
| Time partitions, rollups, trace assembly indexes, service maps, SIEM/full-text indexes.

| Event streams
| Append-only event records with sequence, key, timestamp, headers, payload, and provenance.
| Consumer offsets, CDC publications, current-state materializations, compacted views.
|===

== OLTP And OLAP Query Shape

OLTP:

* point lookup uses primary-key index plus row directory;
* writes append to WAL before becoming visible;
* secondary indexes and projections update through cataloged freshness rules;
* transactions and snapshots are expressed in shared version metadata.

OLAP:

* scans use column stripes, min/max stats, bloom filters, tenant/time pruning, and Arrow batches;
* SQL aggregates, joins, filters, vector predicates, graph traversals, and document path filters
  lower to shared logical algebra;
* external engines consume Iceberg/Arrow/Parquet-compatible projections without owning hot state.

HTAP:

* one record/version model serves both paths;
* compaction can rewrite row-heavy segments into PAX or OLAP mode;
* freshness and snapshot watermarks are cataloged, visible, and testable.

== External Table Interoperability

External file and table formats are first-class cataloged assets. xCatalog must record:

* format: Parquet, CSV, Avro, ORC, JSON, XML, Arrow IPC, Iceberg, Delta, Hudi, Hive, Glue, Unity,
  Polaris, or connector-specific formats;
* location and credentials boundary;
* ownership mode;
* `ProximaType` mapping and lossy conversions;
* snapshot/isolation semantics;
* tenant/RLS enforcement boundary;
* read/write/refresh mode;
* schema evolution policy;
* repair or rebuild source;
* freshness watermark and stats;
* publication lineage and branch/snapshot mapping.

Ownership modes:

[cols="1,4"]
|===
| Mode | Meaning

| `ProximaAuthoritative`
| ProximaDB WAL and `ProximaRecord` storage own truth. External files are publications.

| `ProjectionPublication`
| A rebuildable PAX/Parquet/Iceberg/Delta/Hudi/GraphAr/Arrow projection published from
ProximaDB-owned records.

| `ImportedSnapshot`
| A point-in-time import from external files. ProximaDB owns the imported records after load.

| `ExternalAuthoritative`
| The external table owns truth. xCatalog records snapshot, isolation, policy, write mode, and
repair semantics explicitly.

| `FederatedRead`
| ProximaDB plans reads against external data without importing or owning record state.
|===

Every external row must project into `ProximaRecord`/`ProximaValue` before shared planning. Every
write back to an external authority must pass through the xCatalog ownership and policy contract.

== Migration Implications

The pgwire compatibility path should move in this order:

1. Keep parser and wire compatibility improvements covered by psql and SQLAlchemy smoke tests.
2. Replace vector-collection shims in SQL DDL/DML with xCatalog table assets and canonical
   `ProximaRecord` writes.
3. Route `INSERT`, `UPSERT`, `UPDATE`, and `DELETE` through WAL plus record storage, with tombstone
   semantics for deletes.
4. Route `SELECT` through shared logical plans and record/PAX scanners, then project PostgreSQL
   wire row descriptions from catalog metadata.
5. Add PostgreSQL metadata views as compatibility projections over xCatalog, not as independent
   catalogs.
6. Modernize SST/LSM entries to carry shared MVCC metadata before using them for mutable SQL tables.
7. Publish analytical snapshots through Arrow Flight and Iceberg/OpenTable adapters with explicit
   freshness watermarks.

== Implementation Specification

This section is the handoff from architecture to code. It identifies the foundational modules and
the contracts each module must own.

=== Foundation Crates

[cols="2,3,4"]
|===
| Module | Owns | Must not own

| `proximadb-records`
| `ProximaRecord`, `ProximaValue` tree projection, record identity, tenant/RLS fields,
`record_version`, `valid_from_ns`, `valid_to_ns`, tombstone/visibility helpers.
| SQL-specific row descriptors, PostgreSQL system column semantics, external table ownership.

| `proximadb-catalog`
| xCatalog table schemas, reserved `__proxima_*` system-column names, relational capabilities,
storage-layout descriptors, projection descriptors, open-format ownership modes, schema
validation, and row-to-record validation/projection.
| Runtime storage IO, pgwire protocol frames, physical block encoding.

| `proximadb-block-format`
| PAX block header, row directory, column stripes, canonical column IDs, MVCC row visibility,
record flattening, segment metadata, and scan pruning contracts.
| xCatalog authority decisions, SQL parsing, external catalog protocols.

| Root `src/catalog`
| Runtime implementation of the catalog service, Iceberg REST translation, OLTP metadata backends,
and compatibility projections.
| A second schema/type authority independent of `proximadb-catalog`.

| Root `src/network/postgres`
| PostgreSQL wire protocol, SQLAlchemy/psql compatibility, row descriptions, parameter handling,
PostgreSQL metadata-view compatibility.
| Durable table semantics or protocol-specific storage.

| Root `src/services/ddl` and `src/query/sql_frontend`
| SQL DDL/DML lowering into xCatalog, shared logical plans, and canonical record mutations.
| Vector-collection shims as the target relational implementation.
|===

=== xCatalog Storage Layout Contract

Every table/collection/profile that participates in SQL or open-format interoperability must carry
at least one `CatalogStorageLayout`:

[source,text]
----
CatalogStorageLayout {
  name
  authority: ProximaAuthoritative | ProjectionPublication |
             ImportedSnapshot | ExternalAuthoritative | FederatedRead
  layout_kind: RowRecord | LsmRecord | Pax | Columnar | AppendOnlyEvent |
               VectorAnn | GraphTopology | TimeSeriesBlock | ExternalTable
  physical_format: ProximaBlock | Sst | Arrow | Csv | Json | Xml | Avro |
                   Parquet | Orc | Iceberg | Delta | Hudi | GraphAr | External(...)
  write_mode: Mutable | AppendOnly | CopyOnWrite | ExternalRefresh |
              StreamingIngest | ReadOnly
  location
  snapshot_semantics
  policy_enforced_in_proxima
  lossy_type_mappings
  properties
}
----

Rules:

* ProximaDB-authoritative mutable relational tables SHOULD use a PAX primary layout.
* External-authoritative and federated-read layouts MUST declare `location`, snapshot/isolation
  semantics, policy boundary, write/refresh mode, and `ProximaType` mapping.
* Projection publications MUST declare rebuild source and freshness watermark.
* SST/LSM layouts MUST expose the same identity, tenant, version, timestamp, schema fingerprint,
  and tombstone metadata as PAX.

starting with `__proxima_`.

[cols="2,2,3"]
|===
| Name | Type | Source

| `__proxima_tenant_id` | `TEXT` | `ProximaRecord.tenant_id`
| `__proxima_record_version` | `BIGINT` | `ProximaRecord.record_version`
| `__proxima_created_at_ns` | `BIGINT` | `ProximaRecord.created_at_ns`
| `__proxima_updated_at_ns` | `BIGINT` | `ProximaRecord.updated_at_ns`
| `__proxima_valid_from_ns` | `BIGINT` | `ProximaRecord.valid_from_ns`
| `__proxima_valid_to_ns` | `BIGINT` | `ProximaRecord.valid_to_ns`
| `__proxima_actor` | `TEXT` | `ProximaRecord.actor`
| `__proxima_origin` | `TEXT` | `ProximaRecord.origin`
| `__proxima_deleted` | `BOOLEAN` | derived tombstone/visibility state
| `__proxima_branch_id` | `TEXT` | branch/snapshot metadata
| `__proxima_schema_version` | `INTEGER` | xCatalog schema version/fingerprint
|===

Compatibility aliases such as `_deleted` and `_version` may be recognized during import/export or
connector mapping, but they must canonicalize to `__proxima_deleted` and
`__proxima_record_version`.

=== Relational Mutation Contract

SQL DML lowers into `RelationalMutationKind` plus a catalog-validated `CatalogRow`:

[source,text]
----
INSERT -> new ProximaRecord
UPSERT -> new ProximaRecord version; close prior visible version when present
UPDATE -> new ProximaRecord version with projected changed fields
DELETE -> tombstone ProximaRecord and/or close prior visible version
----

Shared helpers must set:

* stable oid from primary-key values when a primary key exists;
* `tenant_id`, actor, origin, method, created/updated timestamps;
* `record_version` when the caller has OCC/CDC ordering;
* `valid_from_ns` and `valid_to_ns` for snapshot visibility;
* no embeddings on delete tombstones.

Visibility is exclusive at the upper bound:

[source,text]
----
visible_at(t) = valid_from_ns <= t AND t < valid_to_ns
----

`valid_to_ns = NULL` means current/open-ended. Legacy tombstones using `valid_to_ns = 0` remain
recognized until storage compaction migrates them to full version-chain closure.

=== PAX Row Directory Contract

The PAX row directory is the OLTP access path for PAX and OLTP blocks:

[source,text]
----
RowEntry {
  row_id_hash: u64
  valid_from_ns: i64
  valid_to_ns: i64
  flags: DELETED | UPDATED | TOMBSTONE
  row_index: u32
}
----

Rules:

* `valid_to_ns` is exclusive.
* `i64::MAX` means current/open-ended.
* Point lookup returns only rows visible at the requested snapshot.
* Hash collisions and MVCC chains must scan the same-hash range and choose the visible version.
* Column stripes remain authoritative for projected values; row directory is an access path.

=== Pgwire Compatibility Contract

pgwire must expose PostgreSQL-like behavior while lowering immediately into shared contracts:

* DDL creates/updates xCatalog schemas and storage-layout descriptors.
* DML validates through `CatalogRow` and writes canonical mutations.
* `information_schema` and `pg_catalog` compatibility views project from xCatalog.
* SQLAlchemy reflection paths must not require a hidden PostgreSQL catalog.
* Unsupported PostgreSQL features must fail deterministically with SQLSTATE-like errors, not panic.

==== SQL DDL Option Shape

The pgwire path accepts PostgreSQL-style `CREATE TABLE ... WITH (...)` options as an xCatalog
control surface. These options are metadata first: they select storage/access-method shape and
external interoperability contracts; they do not create a separate SQL-owned durable model.

[source,sql]
----
CREATE TABLE facts (
  id BIGINT PRIMARY KEY,
  tenant_id TEXT NOT NULL,
  payload JSONB,
  embedding VECTOR(384)
) WITH (
  workload = 'htap',              -- oltp | olap | htap | vector | document | graph | observability | mixed
  layout = 'pax',                 -- pax | oltp | olap | sst | lsm | columnar | vector | document | graph
  open_table_format = 'iceberg',  -- parquet | csv | avro | orc | json | xml | arrow | iceberg | delta | hudi
  ownership = 'projection',       -- proxima | projection | import | external | federated
  location = 's3://warehouse/facts',
  refresh = 'manual'
);
----

Typed lowering:

* `workload` maps to `CatalogWorkloadProfile`.
* `layout`, `storage_layout`, `specialization`, or `storage_engine` maps to
  `CatalogStorageSpecialization`.
* `open_table_format`, `table_format`, or `format` maps to `CatalogPhysicalFormat`.
* `ownership` or `authority` maps to `CatalogAuthorityMode`.
* `location`, `external_location`, or `path` becomes the external/publication URI.

Defaulting:

* Plain relational tables default to `workload = 'htap'` and PAX row-family.
* `workload = 'oltp'` defaults to PAX `Oltp` mode.
* `workload = 'olap'` defaults to PAX `Olap` mode.
* JSON columns add a rebuildable JSON/path projection descriptor.
* Vector columns add a rebuildable vector ANN projection descriptor.
* `storage_engine = 'sst'` or `layout = 'lsm'` keeps the legacy SST/LSM write-optimized primary
  layout while still requiring shared MVCC/tombstone metadata.

Open-table ownership:

* `ownership = 'projection'`: ProximaDB owns records; the external table is a publication.
* `ownership = 'import'`: external data is imported as a point-in-time snapshot.
* `ownership = 'external'`: external table owns truth; location and snapshot semantics are required.
* `ownership = 'federated'`: ProximaDB reads externally without importing record state.

=== External Table Contract

`CREATE EXTERNAL TABLE` and catalog imports must specify:

* physical format and location;
* ownership mode;
* schema mapping into `ProximaType`;
* snapshot/isolation semantics;
* tenant/RLS policy boundary;
* read/write/refresh mode;
* lossy conversions;
* repair/rebuild source;
* freshness watermark;
* schema evolution policy.

For source formats:

* CSV/XML require declared or inferred schemas before planning.
* JSON/Avro/ORC/Parquet/Arrow can infer richer types but must still record the `ProximaType`
  mapping and lossy conversions.
* Iceberg/Delta/Hudi expose table snapshots/manifests but do not become internal hot-state
  authorities unless `ExternalAuthoritative` is explicitly cataloged.

== Non-Goals

* Do not put ProximaDB's hot durable core inside PostgreSQL, DuckDB, or another external database.
* Do not make Iceberg, Delta, Hudi, Parquet, or ORC the only internal hot-state representation.
* Do not create separate durable row envelopes for SQL, document, graph, vector, or observability.
* Do not expose PostgreSQL system columns as ProximaDB's internal canonical field names.
* Do not treat `_deleted` or `_version` as canonical names; use `__proxima_deleted` and
  `__proxima_record_version`.

== Acceptance Criteria

Relational storage work is aligned with this design when:

* DDL creates xCatalog table assets with `ProximaType` columns and capability metadata.
* DML writes canonical `ProximaRecord` mutations through WAL.
* UPDATE and DELETE preserve MVCC visibility and tombstone semantics.
* pgwire, Arrow Flight, REST/gRPC, and embedded clients see consistent rows and metadata.
* PAX/SST/ANN/JSON/graph/time-series projections declare freshness and rebuild semantics.
* External table reads and writes declare ownership and convert through `ProximaValue`.
* psql, SQLAlchemy, BenchBase OLTP, and TPC-H/TPC-DS-style analytical tests run against the same
  relational/catalog/storage path instead of protocol-specific shims.
