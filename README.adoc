== 🧭 Three‑Mode Platform (Vector • Graph • SKS)

- Vector‑Only: High‑performance semantic search with progressive optimization (Binary → INT8 → PQ → FP32), SIMD‑accelerated distances, and specialized engines (SST, VIPER, HELIX).
- Graph‑Only: Native graph engine (ORION) with CSR storage, label/property indexes, BFS/DFS, Dijkstra/A*, connected components, unique constraints, REST + gRPC APIs.
- SKS Unified: Semantic Knowledge Store combining vector + graph. Hybrid queries exist in the stack; public gRPC handler is staged, with two‑step flows available today (vector → graph or graph → vector).

Ports: REST :5678, gRPC :5679. Metrics: `GET /metrics` (Prometheus).

=== Architecture Benefits

[cols="2,1,1", options="header"]
|===
| Feature | Common Challenges | ProximaDB Approach

| **Storage Architecture**
| Single engine often leads to compromises across diverse workloads.
| Employs 7 specialized engines, each meticulously optimized for distinct data patterns and access needs, ensuring peak performance and efficiency for every use case.

| **Hardware Utilization**
| Relies on generic implementations, often underutilizing modern CPU and GPU capabilities.
| Features automatic detection and intelligent utilization of SIMD (e.g., AVX-512, AVX2, NEON) and GPU acceleration, maximizing throughput and minimizing latency.

| Standard memory allocation can lead to high memory footprints and inefficient resource usage.

| Typically uses a single-phase search, which can be inefficient for complex queries or large datasets.
| Utilizes a progressive 7-phase refinement pipeline that intelligently narrows down search results from coarse to fine-grained matching, optimizing for both speed and accuracy.
|===

== 🔰 Quickstart Highlights

- Start server: `make server-start` (or `cargo run --bin proximadb-server`) → REST :5678, gRPC :5679
- Vector search (REST): `POST /api/v1/search` with `VectorSearchRequest` JSON
- Graph (REST):
  - Create node: `POST /api/v1/graph/nodes`
  - Create edge: `POST /api/v1/graph/edges`
  - Traverse: `POST /api/v1/graph/traverse` (BFS/DFS)
  - Shortest path: `POST /api/v1/graph/shortest_path`
- Graph (gRPC): `proximadb.v1.GraphService` (TraverseGraph, ShortestPath, GetNeighbors, QueryNodes/Edges, StreamTraverse)
- Hybrid SKS: Two‑step today (vector, then graph); proto includes `ExecuteHybridQuery` (server handler staged).

== 💎 Key Differentiators

=== Technical Innovation Driving Superior Value

ProximaDB stands apart through its foundational technical innovations, designed to deliver unmatched performance, efficiency, and operational simplicity.

[cols="1,1,1", frame=none, grid=none]
|===
^.^| **7-Phase Progressive Search**
Our unique multi-stage pipeline intelligently refines search results. It starts with coarse-grained filtering for speed and progressively moves to fine-grained matching for accuracy, ensuring optimal balance between latency and recall for every query.

^.^| **7 Specialized Storage Engines**
Unlike monolithic databases, ProximaDB features a pluggable architecture with 7 distinct storage engines (SST, VIPER, NOVA, SWIFT, RAPTOR, PRISM, HELIX). Each engine is meticulously optimized for specific workload patterns (e.g., OLTP, OLAP, real-time, batch), allowing you to choose the perfect fit for your data and achieve unparalleled performance and cost efficiency.

^.^| **Hardware-Aware Optimization**
ProximaDB automatically detects and leverages the full potential of your underlying hardware. By utilizing advanced SIMD instructions (such as AVX-512, AVX2, NEON) for accelerated distance computation, we ensure your vector search operations run at maximum efficiency, reducing processing time and energy consumption.
|===
