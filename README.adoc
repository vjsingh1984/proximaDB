== Why ProximaDB?

**Built for Real AI Applications**: ProximaDB solves the core challenges of production vector search - fast writes, complex filtering, storage costs, and query performance - without forcing you to choose between them.

**Key Differentiators:**

* **6 Specialized Storage Engines**: Automatically choose the right engine for your workload (write-heavy, read-heavy, balanced, low-latency)
* **Type-Safe Metadata Filtering**: Filter on String, Integer, Float, Boolean fields with full type safety and collection-level configuration
* **Hardware Acceleration**: Production SIMD (AVX2, AVX512, NEON) for 5-10x faster vector operations
* **Advanced Compression**: 4-32x storage reduction with Binary, INT8, and Product Quantization
* **Single Binary Deployment**: No external dependencies, containerized or standalone

== Quick Start

=== Run Locally

[source,bash]
----
# Option 1: Docker (recommended)
docker run -d -p 5678:5678 proximadb/proximadb:latest

# Option 2: Build from source (Rust 1.88+)
git clone https://github.com/vjsingh1984/proximaDB
cd proximaDB
cargo run --release --bin proximadb-server

# Verify server
curl http://localhost:5678/health
----

=== Create Your First Collection

[source,bash]
----
curl -X POST http://localhost:5678/v1/collections \
  -H "Content-Type: application/json" \
  -d '{
    "name": "products",
    "dimension": 768,
    "distance_metric": "COSINE",
    "storage_engine": "AUTO",
    "filterable_columns": [
      {"name": "category", "data_type": "STRING"},
      {"name": "price", "data_type": "FLOAT"},
      {"name": "in_stock", "data_type": "BOOLEAN"}
    ]
  }'
----

=== Insert Vectors with Metadata

[source,bash]
----
curl -X POST http://localhost:5678/v1/collections/products/vectors \
  -H "Content-Type: application/json" \
  -d '{
    "vectors": [
      {
        "id": "prod_001",
        "values": [0.1, 0.2, ..., 0.768],
        "metadata": {
          "category": "electronics",
          "price": 299.99,
          "in_stock": true
        }
      }
    ]
  }'
----

=== Search with Type-Safe Filters

[source,bash]
----
curl -X POST http://localhost:5678/v1/collections/products/search \
  -H "Content-Type: application/json" \
  -d '{
    "query_vector": [0.15, 0.22, ..., 0.801],
    "top_k": 10,
    "filter_expression": {
      "operator": "AND",
      "expressions": [
        {"field": "category", "operator": "EQUALS", "value": "electronics"},
        {"field": "price", "operator": "LESS_THAN", "value": 500},
        {"field": "in_stock", "operator": "EQUALS", "value": true}
      ]
    }
  }'
----

=== Adaptive Storage Engines

ProximaDB provides 6 specialized engines that optimize for different access patterns:

[cols="1,2,2,1"]
|===
|Engine |Storage Format |Best For |Status

|*SST*
|ProximaBlock (Columnar)
|Frequent writes, real-time updates
|✅ Production

|*VIPER*
|Apache Parquet
|Analytics, large scans, high compression
|✅ Production

|*NOVA*
|Hybrid Parquet
|Balanced read/write, progressive search
|✅ Production

|*SWIFT*
|Hierarchical ProximaBlock
|Ultra-low latency, cache-friendly
|✅ Production

|*RAPTOR*
|Matrix-optimized
|Adaptive workloads, unpredictable access
|✅ Production

|*HELIX*
|PCA-compressed ProximaBlock
|Image embeddings, spatial locality
|✅ Production
|===

**Engine Selection**: Use `"storage_engine": "AUTO"` for automatic selection based on collection size, workload pattern, and access frequency.

=== Type-Safe Metadata Filtering

**NEW in v0.1.4**: Full type safety for metadata filtering across all engines.

**Supported Data Types:**
* `STRING`: Text values
* `INTEGER`: 64-bit signed integers (Int64Value)
* `FLOAT`: 64-bit floating point (NumberValue)
* `BOOLEAN`: True/false values
* `DATETIME`: Timestamp values (Int64)

**Supported Operators:**
* Comparison: `=`, `!=`, `<`, `<=`, `>`, `>=`
* Logical: `AND`, `OR`, `NOT`
* Complex nested expressions

**How It Works:**
1. Define filterable columns in collection config with explicit types
2. Collection config acts as single source of truth
3. Zero storage overhead - types stored in config, not data files
4. All 6 engines support type-safe filtering

**Example:**

[source,python]
----
# Define filterable metadata with types
collection = client.create_collection(
    name="products",
    dimension=768,
    filterable_columns=[
        {"name": "price", "data_type": "FLOAT"},
        {"name": "inventory_count", "data_type": "INTEGER"},
        {"name": "featured", "data_type": "BOOLEAN"},
        {"name": "category", "data_type": "STRING"}
    ]
)

# Filter with full type safety
results = collection.search(
    query_vector=embedding,
    filter_expression={
        "operator": "AND",
        "expressions": [
            {"field": "inventory_count", "operator": "GREATER_THAN", "value": 10},
            {"field": "featured", "operator": "EQUALS", "value": true}
        ]
    }
)
----

**SIMD Acceleration** (Production-Ready):
* **x86_64**: AVX2, AVX512 with runtime detection
* **ARM64**: NEON with runtime detection
* **Performance**: 5-20x speedup over scalar implementations
* **Coverage**: Distance computation, encoding, min/max operations

**Measured Performance**:
* 128D Cosine: 20.8M ops/sec (AVX2)
* 512D Euclidean: 3.8M ops/sec (AVX2)

**GPU Acceleration** (Infrastructure Only):

* API layer and kernel code exists
* Real GPU compilation/execution: Planned for 2025

=== Compression & Quantization

**Reduce storage costs by 4-32x** while maintaining query performance:

[cols="1,1,2"]
|===
|Method |Compression |Best For

|Binary (1-bit)
|32x
|Fastest filtering, coarse similarity

|INT8 (8-bit)
|4x
|Balanced compression and accuracy

|PQ8/16/32
|8-16x
|Tunable accuracy, analytical workloads

|Full Precision
|1x (lossless)
|Maximum accuracy requirements
|===

**ProximaCodec** (Lossless f32 Encoding):
* 15 encoding schemes (PForDelta, BitPacking, RLE, Dictionary, etc.)
* Automatic scheme selection based on data patterns
* SIMD-accelerated encoding/decoding
* IEEE 754 bit pattern preservation

docker run -d \

=== Configuration

Minimal production configuration (`config/config.toml`):

[source,toml]
----
[server]
http_port = 5678
grpc_port = 5679

[storage]
data_dir = "/data"
default_engine = "auto"  # Automatic engine selection

[storage.write_buffer]
flush_threshold_mb = 256
flush_interval_secs = 300

[compute]
simd_enabled = true  # Auto-detect AVX2/NEON
----

See link:config/config.toml[complete configuration] for all options.

**Measured Benchmarks** (Linux x86_64, AVX-512, 768D embeddings, 1K vectors):

[cols="2,1,1,2"]
|===
|Engine |Search Latency |Flush Time |Best For

|*HELIX*
|1.43 ms
|41 ms
|⚡ Fastest search (spatial/clustered data)

|*SWIFT*
|2.50 ms (filtered)
|28 ms
|🚀 Fastest writes + low latency

|*SST*
|2.98 ms (LZ4)
|110 ms
|⚖️ Balanced + compression benefit

|*VIPER*
|8.0 ms
|48 ms
|📊 Analytical queries

|*NOVA*
|8.4 ms
|59 ms
|🔄 Progressive refinement
|===

**Type-Safe Filtering**: -20% to +3% overhead (filtering often improves performance!)

**Key Findings** (Validated Oct 2024):
* HELIX fastest: 1.43ms (10% faster with 1MB blocks)
* SWIFT filtering speedup: -20% (reduces result set processing)
* SST-LZ4: 7% faster than no compression (I/O savings > CPU cost)
* Block optimization: 34% average improvement (2-3MB → 1MB)
* ProximaCodec SIMD: 7.6x encoding speedup (measured)

**Compression Recommendations**:
* SST: Use LZ4 (default, 7% faster!)
* HELIX: Use any (no penalty)
* SWIFT: Avoid (latency-focused)
* VIPER/NOVA: LZ4 optional (+6-8% acceptable for storage)
