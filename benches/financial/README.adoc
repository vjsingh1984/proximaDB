= Financial Monte Carlo Option-Pricing Benchmark
:toc:
:sectnums:

A CPU-intensive, embarrassingly-parallel financial workload (European option pricing by
Geometric Brownian Motion Monte Carlo) used to demonstrate ProximaDB's Rust-native I/O +
compute against JVM Spark, reading input through the canonical object-storage `FileSystem`
trait. It is the named exemplar of the "custom Rust worker for CPU-intensive jobs" engine
in `docs/12-design/DATA_WAREHOUSE_AND_ENGINEERING_COURSE_CORRECTION_2026_06_04.adoc`.

== What it measures

The same option-contract Parquet is priced four ways on the same box and dataset:

[cols="1,3"]
|===
| Runner | Path

| `kernel-1thread` (Rust)
| `mc_price_european` in a sequential loop — pure kernel, no DataFusion, no Arrow. The
single-core floor.

| `kernel-parallel` (Rust)
| `mc_price_batch` (rayon over all cores) — pure kernel, no DataFusion. The achievable
multi-core ceiling.

| `datafusion-1query` (Rust)
| `mc_price` UDF via a single DataFusion query reading Parquet through the `FileSystem`
trait. Exposes a real engine behavior: a CPU-heavy per-row UDF runs in one place in the
query's stream graph, so a single query is effectively single-threaded for this work.

| `datafusion-Nworkers` (Rust)
| Rust-native MPP: contracts are sharded into N Parquet files and a coordinator drives one
independent DataFusion query per shard concurrently. This is the model the course-correction
prescribes for CPU-intensive ("Monte Carlo style") jobs — and the one that scales.

| `pyspark` / `numpy-baseline` (Python)
| The same workload via a Spark DataFrame UDF / vectorized numpy — the JVM and
single-process references.
|===

Reported per run: wall-clock, options/sec, paths/sec, input MB read, and (for the single
query) the I/O-vs-compute split.

== Key finding

A *single* DataFusion query serializes a CPU-bound per-row UDF (`datafusion-1query` ≈
`kernel-1thread`). Full multi-core throughput comes from the **Rust-native MPP worker model**
(`datafusion-Nworkers` ≈ `kernel-parallel`, the rayon ceiling) — a coordinator running one
DataFusion query per data shard concurrently. This is precisely why ProximaDB builds a
pluggable Rust-native worker engine for CPU-intensive jobs rather than relying on a single
engine instance, and it removes the JVM/serialization overhead a Spark UDF pays.

== Running

=== Rust benchmark (writes the shared Parquet)

[source,bash]
----
# Release build for real numbers. Writes options.parquet into --data-dir.
cargo run --release --example montecarlo_bench --features datafusion-integration -- \
    --contracts 1000000 --paths 100000 --partitions 8 \
    --data-dir /tmp/mc --out /tmp/mc/rust.csv
----

Local builds use the local filesystem (`file://`). The exact same code reads `s3://` in
production — only the URL scheme changes.

=== Python references (same Parquet, same box)

Use the project venv (`/Users/vijaysingh/code/.venv/bin/python`).

[source,bash]
----
# numpy single-process baseline
python benches/financial/option_pricing_baseline.py --parquet /tmp/mc/options.parquet --paths 100000

# PySpark reference (requires: pip install pyspark)
python benches/financial/option_pricing_spark.py --parquet /tmp/mc/options.parquet --paths 100000 --cores 8
----

Reference (debug build, 10 cores, 40k contracts × 2k paths): kernel-1thread 4.69s →
kernel-parallel 0.65s (7.2×); datafusion-1query 4.69s → datafusion-10workers 0.65s (7.25×,
matching the rayon ceiling); object-store reads ~1 GB/s through the `FileSystem` trait.
Release builds price far more paths/sec — use `--release` for headline numbers.

== Honest framing

The guaranteed win is the *execution boundary*: no JVM, no per-row serialization, Arrow-
native columnar I/O, rayon-parallel compute, and object-store reads through one trait. Report
I/O and compute separately and keep `paths` identical across runners. This is a single-box
comparison; multi-node scale-out is future work (see the pseudo-distributed blueprint).
