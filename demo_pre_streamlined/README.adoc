=== Embedding Service REST API Reference

==== 1. Generate Embedding - `/api/embeddings/embed`

Generate a vector embedding for input text using BERT models.

**Request:**
[source,json]
----
{
    "text": "ProximaDB is a high-performance vector database",
    "model": "all-mpnet-base-v2"  // optional, defaults to all-MiniLM-L6-v2
}
----

**Response:**
[source,json]
----
{
    "success": true,
    "embedding": [0.123, -0.456, ...],  // 384 or 768 dimensions
    "dimension": 768,
    "model": "all-mpnet-base-v2",
    "seed": 42  // Ensures reproducible embeddings
}
----

==== 2. Unified Text Ingestion - `/api/embeddings/ingest`

Convert text to embedding and store in ProximaDB in one step.

**Request:**
[source,json]
----
{
    "text": "Apple reported Q3 revenue of $81.8 billion",
    "collection_id": "financial_news",
    "vector_id": "apple_q3_2023",  // optional, auto-generated if not provided
    "metadata": {  // optional custom metadata
        "company": "Apple",
        "quarter": "Q3",
        "year": 2023,
        "category": "earnings"
    }
}
----

**Response:**
[source,json]
----
{
    "success": true,
    "vector_id": "apple_q3_2023",
    "message": "Vector ingested successfully"
}
----

==== 3. Unified Document Ingestion - `/api/embeddings/ingest-document`

Chunk document, generate embeddings, and batch insert into ProximaDB.

**Request:**
[source,json]
----
{
    "text": "Long document text...",
    "collection_id": "knowledge_base",
    "document_id": "doc_001",  // optional
    "strategy": "sliding_window",  // optional: sliding_window, sentence, paragraph, etc.
    "chunk_size": 512,  // optional, default 512
    "overlap": 128,  // optional, default 128
    "metadata": {  // optional, applied to all chunks
        "source": "internal_wiki",
        "department": "engineering",
        "last_updated": "2023-12-01"
    }
}
----

**Response:**
[source,json]
----
{
    "success": true,
    "chunks_created": 15,
    "document_id": "doc_001",
    "message": "Document chunked and ingested successfully"
}
----

=== Automatic Metadata Enrichment (Enhanced Service)

The enhanced embedding service automatically adds smart metadata:

**Core Metadata (Always Added):**
- `text`: Original text content (first 1000 chars)
- `text_hash`: MD5 hash of full text
- `embedding_model`: Model used for embedding
- `embedding_dimension`: Vector dimension (384 or 768)
- `created_at`: ISO timestamp
- `char_count`, `word_count`, `line_count`: Text statistics

**Extracted Metadata (Automatic):**
- `has_email`, `email_count`: Email detection
- `has_url`, `url_count`: URL detection
- `has_date`, `date_values`: Date extraction
- `has_dollar_amount`, `dollar_amount_values`: Financial data
- `has_percentage`, `percentage_values`: Percentage detection
- `has_bullet_points`, `has_numbered_list`: Structure detection

**Filterable vs Non-Filterable:**
The service automatically separates metadata into:
- **Filterable**: Simple types used for efficient filtering (category, type, source, year, etc.)
- **Non-Filterable**: Complex types or descriptive fields (arrays, nested objects, text content)

=== Text Chunking Strategies

**6 chunking strategies powered by ProximaDB SDK:**

image::chunking_strategies_comparison.svg[Chunking Strategies Comparison, 900, 600]

[cols="2,2,2,2"]
|===
|**Strategy** |**Best For** |**Advantages** |**Considerations**

|`sentence`
|Natural text processing
|✅ Semantic boundaries +
✅ Good coherence
|❌ Variable chunk sizes

|`paragraph`
|Document sections
|✅ Logical sections +
✅ Preserves structure
|❌ Large size variations

|`sliding_window`
|Consistent processing
|✅ Fixed sizes +
✅ Overlapping context
|❌ May break sentences

|`semantic`
|Structured documents
|✅ Header detection +
✅ Meaningful sections
|❌ Complex processing

|`fixed_size`
|Predictable workloads
|✅ Exact sizes +
✅ Fast processing
|❌ Breaks mid-sentence

|`recursive`
|Adaptive processing
|✅ Boundary respect +
✅ Flexible approach
|❌ More complex logic
|===

=== Embedding Data Flow

image::embedding_data_flow.svg[Embedding Data Flow, 800, 600]

**Complete workflow from text to searchable vectors:**

1. **Text Input**: Web UI sends document text to embedding service
2. **Model Loading**: BERT model (all-MiniLM-L6-v2) loaded with seed=42
3. **Chunking**: ProximaDB SDK applies selected strategy (sliding_window, semantic, etc.)
4. **Vector Generation**: Each chunk converted to 384-dimensional embedding
5. **Metadata Addition**: Chunk position, strategy, and document metadata preserved
6. **Storage Integration**: Vectors stored in ProximaDB with full metadata
7. **Search Capability**: Both ProximaDB search and in-memory similarity available

=== JavaScript Integration

**Web UI AJAX integration for real-time embedding:**

[source,javascript]
----
// Generate embeddings from Web UI
async function generateEmbedding(text, model = 'all-MiniLM-L6-v2') {
    const response = await fetch('/api/embeddings/embed', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ text, model })
    });
    return await response.json();
}

// Chunk document with strategy
async function chunkDocument(text, strategy = 'sliding_window') {
    const response = await fetch('/api/embeddings/chunk', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({
            text,
            strategy,
            chunk_size: 512,
            overlap: 128,
            document_id: `doc_${Date.now()}`
        })
    });
    return await response.json();
}

// Search similar chunks
async function searchSimilar(query, chunks, topK = 5) {
    const response = await fetch('/api/embeddings/search', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ query, chunks, top_k: topK })
    });
    return await response.json();
}

// NEW: Unified text ingestion (single-step embed + insert)
async function ingestText(text, collectionId, metadata = {}) {
    const response = await fetch('/api/embeddings/ingest', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({
            text,
            collection_id: collectionId,
            metadata
        })
    });
    return await response.json();
}

// NEW: Unified document ingestion (chunk + embed + batch insert)
async function ingestDocument(text, collectionId, options = {}) {
    const response = await fetch('/api/embeddings/ingest-document', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({
            text,
            collection_id: collectionId,
            strategy: options.strategy || 'sliding_window',
            chunk_size: options.chunk_size || 512,
            overlap: options.overlap || 128,
            metadata: options.metadata || {}
        })
    });
    return await response.json();
}

// NEW: Unified text search (single-step embed + search)
async function searchByText(query, collectionId, options = {}) {
    const response = await fetch('/api/embeddings/search-text', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({
            query,
            collection_id: collectionId,
            top_k: options.top_k || 10,
            metadata_filter: options.metadata_filter || {},
            include_text: options.include_text !== false,  // Default true
            include_metadata: options.include_metadata !== false,  // Default true
            include_vectors: options.include_vectors || false
        })
    });
    return await response.json();
}

=== 🚀 Unified Workflow

**The new unified endpoints eliminate the two-step process for both ingestion and search:**

**Traditional Two-Step Workflows:**
1. **Ingestion**: Generate embedding → Insert into ProximaDB
2. **Search**: Generate query embedding → Search ProximaDB

**New Unified Workflows (Single API Call):**
- `/api/embeddings/ingest` - For single text items
- `/api/embeddings/ingest-document` - For documents requiring chunking
- `/api/embeddings/search-text` - For text-based similarity search

**Benefits:**
- ✅ Atomic operations (no partial failures)
- ✅ Automatic metadata enrichment
- ✅ Original text stored in metadata.text
- ✅ No intermediate JSON handling
- ✅ Better error handling
- ✅ Consistent embedding model usage
- ✅ Optimized with gRPC + compression disabled for colocated services

=== Production Deployment Considerations

==== 📊 **Tab 5: SQL Query**
**Purpose**: Advanced querying with vector similarity functions

**SQL Query Examples**:

===== **Basic Vector Similarity**
```sql
SELECT metadata->>'text' as product_name,
       VECTOR_SIMILARITY(vector, [0.1, 0.2, 0.3], 'cosine') as score
FROM products 
ORDER BY score DESC 
LIMIT 5;
```

===== **Complex Metadata Filtering**
```sql
SELECT metadata->>'text' as description,
       metadata->>'price' as price,
       VECTOR_SIMILARITY(vector, [0.1, 0.2, 0.3], 'cosine') as relevance
FROM products 
WHERE (metadata->>'category' = 'electronics' AND metadata->>'price'::float > 100)
   OR metadata->>'brand' IN ('Apple', 'Samsung')
ORDER BY relevance DESC 
LIMIT 10;
```

===== **Range Queries with Similarity**
```sql
SELECT metadata->>'text' as item,
       metadata->>'rating'::float as rating
FROM reviews
WHERE metadata->>'rating'::float BETWEEN 4.0 AND 5.0
  AND VECTOR_SIMILARITY(vector, [0.2, 0.3, 0.1], 'euclidean') > 0.8
ORDER BY rating DESC, VECTOR_SIMILARITY(vector, [0.2, 0.3, 0.1], 'euclidean') DESC;
```
