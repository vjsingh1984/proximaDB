# CoreML Execution Provider — Negative Result on bge-small

Followup to the session pool + intra-op work. Wired up
`PROXIMADB_EMBED_PROVIDER=coreml` via the `ort/coreml` feature flag and
tested against the same v3 documents bench. **Hypothesis: CoreML +
Apple Neural Engine should beat CPU on Apple Silicon.**

**Result: false for bge-small-en-v1.5 on this hardware.** CoreML is
4-6× slower than the CPU execution provider for this model. Code
landed (opt-in via env var, default off) for future use with larger
models; recommendation is to NOT enable it for bge-small.

## Environment

- 10-core macOS arm64 (M-series Apple Silicon)
- `proximadb-server` release build with `--features coreml`
- BGE-small ONNX from HuggingFace `BAAI/bge-small-en-v1.5/onnx`
- 50 / 200 / 500 docs × 3 runs each, after a 3-call warmup so CoreML
  model-compile cost is amortized

## Why CoreML loses on bge-small

bge-small is **22M parameters, hidden=384, 12 layers**. That's tiny by
Apple Neural Engine (ANE) standards. ANE shines on large models with
high arithmetic intensity per kernel; on bge-small it pays:

1. **Per-batch CPU↔ANE memory transfer**. The hidden state shape
   `[batch, seq, 384]` for batch≥50, seq≈64 is only ~5 MB, but the
   round-trip per inference adds milliseconds.
2. **Kernel dispatch overhead**. ONNX ops on ANE are JIT-compiled to
   ANE programs; for small ops the dispatch overhead exceeds the
   compute time.
3. **AMX competition**. Apple's CPU cores have a built-in matrix
   accelerator (AMX) that ORT's CPU EP uses transparently. For 384×384
   matmuls AMX is competitive with ANE and avoids the transfer cost.
4. **CoreML EP doesn't currently support dynamic input shapes well**;
   it falls back to CPU for ops it can't graph-compile, adding hybrid
   execution overhead.

This is consistent with the broader Apple ML literature: ANE is the
right target for big LLM decoding (Whisper-large, Llama-3-8B in
4-bit), but bge-small belongs on the CPU's AMX path.

## When CoreML would help

- **Larger embedding models**: `bge-m3` (1024-dim, 568M params),
  `e5-mistral-7b-instruct`, OpenAI `text-embedding-3-large` (3072-dim).
  ANE's throughput advantage starts to dominate the dispatch overhead.
- **Lower power**: ANE uses ~1/10 the energy of CPU for the same
  inference. For battery-bound or thermal-bound deployments,
  trading 4× throughput for 10× power efficiency may be the right call.
- **Concurrent CPU work**: if the server is also doing heavy CPU work
  (search, JSON parsing) on the same node, offloading embeddings to
  ANE frees CPU cores even if ANE is individually slower.

For this codebase's current default model (bge-small) and dedicated
embedding nodes, **stay on CPU**.

## Code outcome

- `proximadb-embedding`: added `coreml` cargo feature gated on
  `ort/coreml`. New `EpKind::CoreMl` variant + `resolve_provider` env
  parser. Default remains `EpKind::Cpu` — no behavior change without
  explicit opt-in via env var.
- `proximadb-server`: added `coreml` passthrough feature
  (`coreml = ["onnx", "proximadb-embedding/coreml"]`). Server starts
  fine without the feature; setting `PROXIMADB_EMBED_PROVIDER=coreml`
  on a non-coreml build returns `ModelUnavailable` with a clear
  message rather than silently falling through.
- 4 new unit tests (20 total in policy_tests) cover the env parsing
  for the provider selector.
- Startup log reports `provider=Cpu|CoreMl` so deployments can verify.

## Operational recommendation

```bash
# DEFAULT (recommended for bge-small)
# PROXIMADB_EMBED_PROVIDER unset → CPU
proximadb-server --config config.toml

# CoreML only when running a larger model:
PROXIMADB_EMBED_PROVIDER=coreml \
PROXIMADB_EMBED_MODEL_DIR=/var/lib/proximadb/models/bge-large \
proximadb-server --config config.toml
```
